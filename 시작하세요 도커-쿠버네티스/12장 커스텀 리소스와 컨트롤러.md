### 12.1 쿠버네티스 컨트롤러의 개념과 동작 방식

#### 명령형(Imperative) vs. 선언적(Declarative)

- **명령형**: 무엇을 할지 구체적인 동작을 지시하는 방식입니다.
    - 예: `docker run`, `kubectl run`, `kubectl create -f`
    - 새로운 리소스를 만들어라라는 동작 자체를 명령하므로, 같은 명령을 다시 실행하면 `AlreadyExists` 오류가 납니다.
- **선언형**: 최종적으로 도달해야 할 **바람직한 상태(Desired State)** 만 정의하는 방식입니다. 현재 상태(Current State)가 다르면 쿠버네티스가 알아서 맞춥니다.
    - 예: `kubectl apply -f` (YAML 파일 = 최종 목표 상태)
    - 어떤 동작을 할지는 사용자가 정하지 않고, **컨트롤러**가 내부적으로 결정합니다.
- 선언형 흐름: `kubectl apply` → API 서버 → etcd(상태 저장) → 컨트롤러가 Watch API로 상태를 받아 알맞은 동작 수행
- 레플리카셋도 선언형의 예입니다. `kubectl get rs`의 DESIRED 항목이 바람직한 상태이고, 파드를 일부러 지우면 그 수를 맞추려고 새 파드를 만듭니다.
- 쿠버네티스는 여러 컨트롤러(디플로이먼트 컨트롤러, 노드 컨트롤러 등)를 **컨트롤러 매니저** 하나에 모아 구현했고, 이것은 `kube-system` 네임스페이스에서 파드로 실행됩니다.

### 12.2 커스텀 리소스에 대한 개념

- 커스텀 리소스는 사용자 정의 리소스이며, 파드나 디플로이먼트와 똑같이 하나의 리소스 종류로 취급됩니다.
    - 예: Redis를 커스텀 리소스로 만들면 `kubectl get redis`, `kubectl describe redis` 사용 가능
- 활용 방법
    - 여러 오브젝트(디플로이먼트, 서비스, 컨피그맵 등)를 하나로 묶어 **패키지처럼** 사용
        - 예: `WebApp` 커스텀 리소스 하나로 프론트엔드/백엔드/DB 디플로이먼트와 서비스를 한 번에 생성하고 생애 주기를 관리
    - 쿠버네티스와 무관한 로직을 커스텀 리소스와 연동

#### 커스텀 리소스를 사용하기 위한 단계

1. 커스텀 리소스의 현재 상태를 바람직한 상태로 바꿔 줄 **컨트롤러를 구현하고 실행**
2. 커스텀 리소스의 상세 정보를 정의하는 **CRD(Custom Resource Definition)** 생성
3. CRD에 정의된 형식에 맞춰 **커스텀 리소스 생성**
4. 컨트롤러가 커스텀 리소스 생성을 감지하고, 바람직한 상태가 되도록 작업 수행

### 12.3 커스텀 리소스를 정의하기 위한 CRD(Custom Resource Definition)

- CRD는 커스텀 리소스를 이렇게 쓰겠다고 쿠버네티스에 **등록하는 리소스**일 뿐, CRD 자체가 커스텀 리소스는 아닙니다.
    - 클래스(CRD)와 인스턴스(커스텀 리소스)의 관계로 이해하면 쉽습니다.
- `kubectl get crd`로 목록 확인 가능 (네트워크 플러그인용 CRD가 기본으로 있을 수 있음)

예제 12.1의 주요 항목:

1. **metadata.name**: CRD 이름. 반드시 `spec.names.plural` + `.` + `spec.group` 형태여야 합니다. → `alices.k106.com`
    - 참고: 책 본문에는 alice + k106.com이라고 적혀 있지만, 규칙대로라면 복수형인 alices가 맞고 YAML에도 `alices.k106.com`으로 되어 있습니다.
2. **spec.group, versions**: 커스텀 리소스가 속할 API 그룹과 버전. 커스텀 리소스 YAML에서는 `apiVersion: k106.com/v1alpha1`로 씁니다. `scope: Namespaced`는 네임스페이스에 속한다는 뜻입니다.
3. **spec.names**: 커스텀 리소스를 부르는 이름
    - plural(복수형): `kubectl get alices` (파드라면 `kubectl get pods`)
    - singular(단수형): `kubectl get alice` (파드라면 `kubectl get pod`)
    - shortNames(줄임말): `kubectl get ac` (파드라면 `kubectl get po`)
    - kind: YAML에서 `kind: Alice` (파드라면 `kind: Pod`)
4. **spec.validation (schema.openAPIV3Schema)**: 커스텀 리소스에 저장될 데이터 형식과 필수 항목 정의
    - `spec`이 반드시 있어야 하고, 그 아래 `myvalue`(문자열)가 필수

실습 흐름:

- `kubectl apply -f my-crd-example-k8s-latest.yaml`로 CRD 등록
- `kubectl apply -f my-cr-example.yaml`로 `kind: Alice` 커스텀 리소스 생성
- 이후 `kubectl get alices`, `kubectl describe ac my-custom-resource` 등 일반 리소스처럼 사용 가능

### 12.4 커스텀 리소스와 컨트롤러

- CRD로 커스텀 리소스를 만들어도 그 자체는 **etcd에 저장된 데이터일 뿐**, 실제로 동작하는 파드나 서비스가 아닙니다.
- 커스텀 리소스가 생성됐을 때 무엇을 할지 정의한 **컨트롤러를 별도로 구현**해야 비로소 의미가 생깁니다.
    - 레플리카셋의 동작이 컨트롤러 매니저 안에서 수행되는 것과 같은 원리입니다.
- 동작 순서 (그림 12.4)
    1. 커스텀 리소스를 정의하는 CRD 생성
    2. 커스텀 리소스 생성
    3. 컨트롤러가 API 서버의 Watch로 생성을 감지
    4. 커스텀 리소스가 원하는 상태가 되도록 동작 수행 (예: alice, bob 파드 생성, 웹 서버용 파드와 서비스 구성, AWS EC2 인스턴스 생성 등)
- **Reconcile**: 현재 상태를 바람직한 상태로 맞추는 동작. 레플리카셋이 삭제된 파드를 다시 만드는 것도 Reconcile의 일종입니다.
- **오퍼레이터(Operator) 패턴**: CRD와 컨트롤러를 함께 구현해 쿠버네티스를 확장하는 방식. 유명한 오픈소스들이 이 방식으로 제공됩니다 (operatorhub.io 참고).
- 컨트롤러를 처음부터 직접 구현하는 것은 어렵기 때문에 **Operator SDK**, **KubeBuilder** 같은 프레임워크를 쓰면 Reconcile 로직만 구현하면 됩니다.
- 참고: 커스텀 리소스를 쓰기 위해 반드시 CRD나 오퍼레이터가 필요한 것은 아니며, 오퍼레이터 개발 방법은 책에서 다루지 않습니다.
