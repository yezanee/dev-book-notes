## 도입부

- 실제 운영 클러스터라면 모니터링 시스템은 필수입니다. 부하 급증, 장애 발생, 리소스 사용 패턴 파악 같은 상황에서는 CPU·메모리 같은 기초 메트릭부터 확인하며 트러블슈팅을 시작합니다.
- 필요한 메트릭은 CPU, 메모리 외에도 디스크, 네트워크 I/O, 초당 요청 수, 애플리케이션 고유 메트릭까지 다양합니다. 그런데 **쿠버네티스는 자체 모니터링 기능을 제공하지 않으므로** 오픈소스를 조합하거나 상용 솔루션을 사용해야 합니다.
- 오픈소스 대표 조합
    - **프로메테우스**: 쿠버네티스에서 가장 많이 쓰이는 시계열 DB
    - **그라파나**: 시각화
    - **AlertManager**: 슬랙 알람 등
- 오픈소스는 장기 데이터 관리, DB 장애 대응 등을 직접 해결해야 합니다. 유료 솔루션(Datadog, NewRelic, CloudWatch)은 편하지만 비용이 듭니다.
- 정답은 없습니다. 인력이 부족하면 Datadog, 커스터마이징이나 쿠버네티스 호환성이 중요하면 프로메테우스가 나을 수 있으니 각자 환경에 맞는 솔루션을 찾는 것이 우선입니다.

## 14.1 모니터링 기본 구조

- CAdvisor 웹 UI는 단기 메트릭만 보여주고 체계적인 저장·분석은 되지 않습니다.
- 메트릭 수집 흐름(Pull 구조)
    1. 프로메테우스가 CAdvisor의 `/metrics` 경로로 요청
    2. CAdvisor가 프로메테우스 형식의 시계열 메트릭(키-값) 반환
    3. 프로메테우스가 저장
- 프로메테우스에 대상 엔드포인트 정보(서비스 디스커버리 정보)만 지정해두면 자동으로 수집합니다.
- 메트릭 데이터 포맷은 RDBMS와 전혀 다르며, `<메트릭 이름>{라벨} <값>` 형태입니다. (예: `process_open_fds 12`)
- **exporter**: `/metrics` 같은 경로를 노출해 메트릭을 수집할 수 있도록 해주는 서버입니다. 직접 라이브러리로 커스텀 exporter를 만들 수도 있고 오픈소스를 가져다 쓸 수도 있으며, CAdvisor도 그중 하나입니다.
- 대부분의 오픈소스는 `/metrics`를 기준 경로로 삼습니다. kubelet, kube-apiserver에도 존재하며, 접근하려면 적절한 클러스터 롤 바인딩이 필요합니다.
    - kubelet의 `/metrics`: kubelet 자체 메트릭
    - kubelet의 `/metrics/cadvisor`: 컨테이너 수준 메트릭

## 14.2 모니터링 메트릭의 분류

메트릭은 크게 세 단계로 나눌 수 있습니다(절대적인 기준은 아님).

- **인프라 수준**: 호스트 레벨. 파일 디스크립터 수, 디스크 사용량, NIC 패킷 전송량 등. node-exporter가 여기에 해당합니다.
- **컨테이너 수준**: 컨테이너별 CPU·메모리, 프로세스 상태, 리소스 할당량, 파드 상태 등. CAdvisor가 여기에 해당합니다.
- **애플리케이션 수준**: 그 외 애플리케이션이 정의한 모든 메트릭. 마이크로서비스 트레이싱, 비즈니스 로직 데이터, 서버 프레임워크 메트릭 등.

추가로 짚을 점

- 실제로 다루게 될 데이터는 대부분 인프라와 컨테이너 수준입니다. CAdvisor는 컨테이너 수준이지만 인프라 메트릭도 일부 제공합니다. (예: `machine_cpu_cores`)
- `container_cpu_xxx`, `container_memory_xxx` 같은 메트릭을 시계열 DB에 수집하고 가공하면 컨테이너 수준 모니터링이 됩니다.
- 목표는 호스트, 컨테이너, 애플리케이션 수준의 메트릭을 적절히 수집할 수 있는 시스템을 만드는 것입니다.

## 14.3 쿠버네티스 모니터링 기초

데이터독, CloudWatch 대신 무료인 프로메테우스 중심 시스템을 다룹니다. 유료를 쓰기로 했더라도 한 번은 직접 구축해보는 것이 좋은 공부가 됩니다.

### 14.3.1 metrics-server

- 쿠버네티스가 제공하는 애드온 중 가장 기초적인 것으로, 컨테이너·인프라 레벨 메트릭을 수집합니다. 파드 오토스케일링, 리소스 사용량 확인 등에 필요하므로 설치를 권장합니다.
- `docker stats`처럼 `kubectl top`으로 파드·노드 사용량을 볼 수 있지만, 설치 전에는 `error: Metrics API not available`가 출력됩니다.
- 여러 노드로 구성된 클러스터에서는 메트릭을 모아주는 별도 컴포넌트가 필요하고, 그 역할을 metrics-server가 맡습니다.
- 설치 절차
    1. 공식 깃허브에서 `components.yaml` 다운로드
    2. 디플로이먼트 args에 `-kubelet-insecure-tls` 추가
    3. `kubectl apply -f components.yaml` (ClusterRole, RoleBinding, APIService, ServiceAccount, Deployment, Service 등 생성)
- `kube-system` 네임스페이스에서 Running 확인 후 `kubectl top po`, `kubectl top no` 사용 가능합니다.
- 애드온은 빠르게 업데이트되므로 명령어가 동작하지 않으면 책 깃허브를 참고하라고 안내합니다.

### 14.3.2 metrics-server 동작 원리: APIService 리소스

모니터링 구축과 직접 관련은 없지만 API 확장, 인증 등과 엮여 있어 이해해두기를 권장하는 절입니다.

**kubelet의 /metrics/resource**

- kubelet은 CAdvisor를 내장하며, 10250 포트의 `/metrics/resource`로 파드·노드 메트릭을 제공합니다.
- 그냥 curl로 요청하면 `Unauthorized`가 반환됩니다. 권한 정보가 없기 때문입니다.
- 해결 방법: ClusterRole로 권한을 정의하고 서비스 어카운트에 연결한 뒤, 그 토큰을 헤더에 담아 요청해야 합니다.
- metrics-server YAML에는 이미 `nodes/metrics` 리소스 접근 권한이 부여되어 있습니다. 따라서 `kubectl create token metrics-server -n kube-system`으로 만든 토큰을 `Authorization: Bearer` 헤더에 넣으면 메트릭이 정상 반환됩니다.
- `k` 옵션과 `-kubelet-insecure-tls`는 같은 맥락입니다. kubelet이 자체 서명 인증서를 쓰기 때문에 인증서 신뢰 여부와 상관없이 통신하기 위한 옵션입니다.
- 정리하면 metrics-server는 각 노드 kubelet에서 주기적으로 메트릭을 수집해 정제한 뒤 외부에 제공하고, `kubectl top`은 이를 사용합니다.

**확장된 API 서버로서의 metrics-server**

- metrics-server 서비스에 직접 curl을 보내면 `system:anonymous`에 대한 403 응답이 옵니다. API 서버와 같은 형식의 응답인데, metrics-server가 **확장된 API 서버** 역할을 하기 때문입니다.
- 확장된 API 서버란 API 서버 스펙을 준수하는 별도 서버를 쿠버네티스에 등록해 API 서버처럼 사용하는 것을 말합니다.
- 이 등록은 **APIService** 리소스로 하며, metrics-server 배포 시 함께 생성됐습니다.
    - `service.name: metrics-server`, `namespace: kube-system`
    - `group: metrics.k8s.io`, `version: v1beta1`
    - 의미: kube-system의 metrics-server 서비스에 접근해서 metrics.k8s.io API를 제공한다
- 이런 방식을 **API Aggregation**이라고 하며, 추가 API를 묶어 쿠버네티스 API처럼 쓰는 것입니다.
- 동작 순서
    1. APIService로 metrics-server를 확장 API 서버로 등록
    2. 사용자가 kube-apiserver에 metrics.k8s.io API 요청
    3. API Aggregation Layer가 metrics-server로 요청을 전달
    4. metrics-server가 `/stats/summary`에서 수집한 노드·파드 메트릭으로 응답
- 확인 방법
    - `kubectl get --raw /apis/metrics.k8s.io | jq` 실행 시 APIGroup 정보가 출력됩니다.
    - `kubectl get --raw /apis/metrics.k8s.io/v1beta1/nodes` 또는 `/pods`를 호출하면 `kubectl top`이 쓰는 메트릭을 볼 수 있습니다.
    - `kubectl proxy`를 쓰면 인증 헤더 없이 `localhost:8001`로 API 서버에 접근할 수 있습니다.

### 14.3.3 kube-state-metrics

- 쿠버네티스 **리소스 상태**에 관한 메트릭을 제공하는 애드온입니다. (예: 파드가 Running인지, 디플로이먼트 레플리카 수)
- 설치: 깃허브 클론 후 `examples/standard`에서 `kubectl apply -f .`
- metrics-server보다 구성이 단순해서 `kube-state-metrics.kube-system.svc:8080/metrics`로 curl 요청만 보내면 바로 확인할 수 있습니다. (예: `kube_configmap_info`)

### 14.3.4 node-exporter

- **인프라 수준** 메트릭을 제공하는 exporter로, 파일 시스템, 네트워크 패킷 등 호스트 측면의 상세 메트릭을 제공합니다.
- node-exporter 공식 저장소는 쿠버네티스용 YAML을 직접 제공하지 않으므로 kube-prometheus 저장소의 매니페스트를 참고합니다. 책은 이를 기반으로 만든 `chapter14/node-exporter`를 사용합니다.
- kube-prometheus는 모니터링 시스템을 한 번에 설치할 수 있게 해주지만, 이 장은 하나씩 직접 설치하며 구조를 익히는 것이 목적입니다.
- `kubectl apply -f .` 실행 시 `monitoring` 네임스페이스, 데몬셋, 서비스, 서비스 어카운트가 생성됩니다.
- **데몬셋**으로 배포되므로 모든 노드에 파드가 하나씩 생깁니다.
- 파드 IP와 노드 IP가 같은데, `hostNetwork: true`(docker의 `-net host`와 같은 효과) 때문입니다.
- 노드 IP의 **9100 포트** `/metrics`로 요청하면 메트릭을 확인할 수 있습니다. (예: `node_disk_writes_completed_total`)
- 불필요한 메트릭은 데몬셋 args에 `-no-collector`를 추가해 수집하지 않을 수 있습니다.

## 14.4 프로메테우스를 활용한 메트릭 수집

지금까지의 메트릭 수집 도구를 정리하면 다음과 같습니다.

- **kubelet 내장 CAdvisor**: 노드의 컨테이너 수준 메트릭. metrics-server는 kubelet의 `/metrics/resource`에서 수집해 메모리에 임시 저장하고 확장 API로 제공. 원본 CAdvisor 메트릭은 `/metrics/cadvisor`에 별도로 존재
- **kube-state-metrics**: 리소스 상태 메트릭. 인증 없이 8080 포트 `/metrics`
- **node-exporter**: 인프라 수준 메트릭. 데몬셋으로 전 노드 배포, 9100 포트 `/metrics`

세 도구 모두 `/metrics` 엔드포인트를 제공하므로 프로메테우스에 엔드포인트만 설정하면 자동 수집됩니다. 다만 프로메테우스 자체를 제대로 활용하려면 프로메테우스에 대한 별도 학습이 필요하며, 이 절은 대략적인 구조와 흐름 이해가 목표입니다.

### 14.4.1 프로메테우스 설치

- 설치 방법은 여러 가지(디플로이먼트 직접 배포, 바이너리 실행 등)가 있지만, 이 절에서는 **프로메테우스 오퍼레이터 + 커스텀 리소스** 방식을 씁니다. 12장의 커스텀 리소스·컨트롤러 개념과 거의 같습니다.
- 오퍼레이터는 Prometheus 커스텀 리소스 생성을 감지하면 프로메테우스 스테이트풀셋(파드)을 생성합니다. 수집 대상 등 설정도 커스텀 리소스로 정의하면 자동으로 리로드·적용됩니다.
- 오퍼레이터 사용이 필수는 아니며 취향과 목적에 따라 고르면 됩니다.
- 설치 절차
    1. `prometheus-operator` 저장소 클론 후 `kubectl apply -f bundle.yaml` 실행 (CRD 등 생성). annotations too long 에러가 나면 `-server-side --force-conflicts` 사용
    2. default 네임스페이스에서 오퍼레이터 파드 확인
    3. `kind: Prometheus` 리소스(`prometheus-simple.yaml`) 생성. `serviceMonitorNamespaceSelector: {}`, `serviceMonitorSelector: {}`처럼 빈 값이면 모든 ServiceMonitor를 선택
    4. `prometheus-prometheus-0` 파드와 `prometheus-operated` 서비스(ClusterIP, 9090) 생성 확인
- 웹 UI 접근: ClusterIP라 브라우저에서 직접 접근할 수 없으므로 `kubectl port-forward svc/prometheus-operated 19090:9090` 후 `127.0.0.1:19090`으로 접속합니다. port-forward는 svc를 생략하면 파드에도 쓸 수 있습니다.

### 14.4.2 프로메테우스로 메트릭 수집하기

**ServiceMonitor**

- 오퍼레이터 없이 쓰면 파드 내부 `prometheus.yml`에 엔드포인트를 직접 넣고 리로드해야 하지만, **ServiceMonitor** 커스텀 리소스를 쓰면 어떤 엔드포인트에서 수집할지를 쿠버네티스 리소스로 정의해 자동 적용할 수 있습니다.
- ServiceMonitor는 어떤 서비스에 연결된 파드로부터 메트릭을 가져올지 알려주는 역할입니다. 라벨 셀렉터(`app.kubernetes.io/name: node-exporter`)로 서비스를 선택하고, 그 서비스에 연결된 파드들을 수집합니다.
- 적용: `kubectl apply -f node-exporter-serviceMonitor.yaml`

**Push vs Pull**

- Push: exporter가 DB로 전송하는 방식 (예: CAdvisor → InfluxDB)
- Pull: DB가 exporter에 접근해 당겨오는 방식
- 프로메테우스는 Pull 방식이며, 이를 **scrape**라고 부릅니다.

**트러블슈팅 과정**

1. [Status] → [Configuration]에서 `scrape_configs`에 node-exporter job이 반영된 것을 확인합니다.
2. 그런데 [Status] → [Targets]가 비어 있습니다.
3. 가장 먼저 파드 로그를 확인합니다. (`kubectl logs -f prometheus-prometheus-0 -c prometheus`)
4. `system:serviceaccount:default:default`가 pods, endpoints를 list할 수 없다는 에러가 나옵니다. 서비스 어카운트와 권한을 설정하지 않았기 때문입니다.
5. 해결: `prometheus-clusterRole.yaml`, `prometheus-clusterRoleBinding.yaml`, `prometheus-serviceAccount.yaml` 적용 후 Prometheus 리소스에 `serviceAccountName: prometheus-k8s`를 추가해 재적용하면 파드가 재생성됩니다. (port-forward는 재실행이 필요할 수 있음)
6. Targets에 node-exporter가 UP으로 표시되고, [Graph]에서 파일 시스템·디스크·네트워크 관련 메트릭을 볼 수 있습니다.

**나머지 대상 추가**

- `kube-state-metrics-serviceMonitor.yaml`, `kubelet-serviceMonitor.yaml`도 적용합니다.
- Targets에 kube-state-metrics, kubelet/0, kubelet/1, node-exporter가 표시됩니다. 숫자(4/4 up 등)는 노드 수에 따라 다릅니다.
- ServiceMonitor 세부 설정은 프로메테우스 의존적이라 책에서는 깊게 다루지 않지만, 제대로 쓰려면 반드시 알아야 합니다.
- 웹 UI의 [Graph]에서 메트릭 이름(예: `container_memory_working_set_bytes`)을 선택하고 Execute하면 간단히 조회할 수 있습니다.
- 프로메테우스는 메모리를 많이 쓰므로 리텐션을 짧게 두는 것이 일반적입니다. 기본은 최근 24시간이며 `-storage.tsdb.retention.time`으로 조정합니다. 장기 데이터는 **타노스(Thanos)** 같은 솔루션을 고려할 수 있습니다.

### 14.4.3 그라파나로 프로메테우스 메트릭 시각화하기

- 프로메테우스 호환 도구면 무엇이든 되지만, 대시보드 도구로 그라파나를 사용합니다.
- 배포: `chapter14/grafana.yaml`(Deployment, `grafana/grafana:7.0.0` 이미지 + Service)을 `kubectl apply`
- 테스트용이라 볼륨을 마운트하지 않았지만, 운영 환경에서는 **퍼시스턴트 볼륨**을 반드시 쓰는 것이 좋습니다.
- 접속: ClusterIP + `kubectl port-forward svc/grafana 3000:3000` 후 `127.0.0.1:3000`, 초기 계정은 admin/admin
- 데이터 소스 등록
    1. Configuration → Data Sources → Add data source → Prometheus 선택
    2. URL에 `http://prometheus-operated.default.svc:9090` 입력
    3. Save & Test에서 Data source is working 확인
- 대시보드 가져오기
    - 직접 만들어도 되지만 grafana.com 공개 대시보드를 ID로 Import할 수 있습니다.
    - 저자가 만든 node-exporter + kubelet CAdvisor용 대시보드 ID는 **13077**입니다.
    - Dashboards → Manage → Import에서 ID 입력 후 Load, Prometheus 데이터 소스 선택, Import 순서로 진행합니다.
    - 노드 메모리·CPU·파일시스템 사용률, 파드/컨테이너 CPU 사용량 등이 시각화됩니다.
- 나만의 대시보드를 구성하려면 **PromQL**(프로메테우스 쿼리 언어)과 데이터 포맷에 대한 이해가 필요합니다.
