## 4.1 도커 컴포즈를 사용하는 이유

- 웹 서버 + DB처럼 여러 컨테이너로 구성된 애플리케이션은 `docker run`을 컨테이너마다 옵션과 함께 반복 입력해야 해서 테스트 단계에서 번거로움
- 도커 컴포즈는 여러 컨테이너의 옵션과 환경을 **하나의 YAML 파일**에 정의하고, 이를 읽어 컨테이너를 순차적으로 생성
- run 명령어의 옵션을 거의 그대로 옮길 수 있고, 의존성, 네트워크, 볼륨도 함께 정의 가능
- 스웜 모드 서비스처럼 컨테이너 수 조절과 서비스 디스커버리도 지원
- 컨테이너가 적고 옵션이 단순하면 그냥 `docker run`이 더 편할 수도 있음

## 4.2 도커 컴포즈 설치

- 리눅스에서 도커를 설치했거나 Docker Desktop(윈도우/맥)을 쓰면 기본 포함
- `docker compose version`으로 확인 (책 기준 v2.33.1)
- 없으면 GitHub 릴리스에서 바이너리를 받거나 공식 문서대로 플러그인 설치

## 4.3 도커 컴포즈 사용

### 4.3.1 도커 컴포즈 기본 사용법

- 컨테이너 설정이 정의된 YAML 파일을 읽어 도커 엔진으로 컨테이너를 생성하므로, 가장 먼저 YAML 파일을 작성해야 함

#### 4.3.1.1 docker-compose.yml 작성과 활용

```yaml
services:
  web:
    image: alicek106/composetest:web
    ports:
      - "80:80"
    links:
      - mysql:db
    command: apachectl -DFOREGROUND
  mysql:
    image: alicek106/composetest:mysql
    command: mysqld
```

- 들여쓰기는 탭 불가, 공백 2칸 사용
- 아무 설정 없이 `docker compose up -d`를 실행하면 현재 디렉터리의 docker-compose.yml을 읽음
- `services`: 생성될 컨테이너들을 묶어놓은 단위
- `web`, `mysql`: 서비스 이름. 그 아래에 image, ports, links, command 등 컨테이너 옵션을 정의
- 생성된 컨테이너는 `docker ps`와 `docker compose ps` 둘 다로 확인 가능

#### 4.3.1.2 도커 컴포즈의 프로젝트, 서비스, 컨테이너

- 하나의 프로젝트 → 여러 서비스 → 서비스마다 여러 컨테이너
- 컨테이너 이름 규칙: `[프로젝트 이름]-[서비스 이름]-[번호]` (예: ubuntu-web-1)
- 프로젝트 이름을 지정하지 않으면 yml 파일이 있는 디렉터리 이름이 프로젝트 이름이 됨
- 주요 명령어
    - `docker compose scale mysql=2`: 서비스의 컨테이너 수 조절
    - `docker compose up -d mysql`: 특정 서비스만 생성
    - `docker compose run web /bin/bash`: 컨테이너를 만들며 인터랙티브 셸 사용
    - `docker compose down`: 프로젝트 삭제 (컨테이너 정지 및 삭제, 기본 네트워크도 삭제)
    - `p 프로젝트명`: 프로젝트 이름 지정. 하나의 yml로 이름이 다른 여러 프로젝트를 만들고 제어 가능

### 4.3.2 도커 컴포즈 활용

#### 4.3.2.1 YAML 파일 작성

- 기존 run 명령어를 YAML로 변환하는 것이 컴포즈 사용법의 대부분
- YAML은 **서비스 정의, 볼륨 정의, 네트워크 정의** 3가지로 구성되며 서비스 정의를 가장 많이 사용
- `f 경로`로 yml 파일 위치와 이름 지정 가능. `p`와 함께 쓸 땐 `f`로 파일을 먼저 지정한 뒤 `p`로 프로젝트를 명시

**(1) 서비스 정의**

- **image**: 사용할 이미지. 로컬에 없으면 저장소에서 자동으로 내려받음
- **links**: `-link`와 동일. `SERVICE:ALIAS` 형식으로 별칭 접근 가능
- **environment**: `-env`, `e`와 동일. 배열 형식(`KEY=value`)과 딕셔너리 형식(`KEY: value`) 모두 가능
- **command**: run 명령어 마지막에 붙는 커맨드. 배열 형태도 가능
- **depends_on**: 명시한 서비스의 컨테이너가 먼저 생성되고 실행됨. links와 달리 서비스 이름으로만 접근 가능
    - 의존 서비스 없이 특정 서비스만 띄우려면 `docker compose up --no-deps web`
    - links와 depends_on은 **실행 순서만 보장**하고 애플리케이션 준비 여부는 확인하지 않음. 책에서는 entrypoint에 `until` 루프로 대상(예: mysql:3306)을 확인하는 셸 스크립트를 넣는 방법을 소개
- **ports**: `p`와 동일. 단, `80:80`처럼 호스트 포트를 고정하면 단일 호스트에서 scale로 컨테이너를 늘릴 수 없음
- **build**: 지정한 디렉터리의 Dockerfile로 이미지를 빌드해서 사용
    - `context`, `dockerfile`, `args`로 빌드 컨텍스트, Dockerfile 이름, 빌드 인자 설정 가능
    - image를 지정하지 않으면 이미지 이름은 `[프로젝트 이름]-[서비스 이름]`
    - Dockerfile을 바꿔도 자동으로 다시 빌드하지 않으므로 `docker compose up -d --build` 또는 `docker compose build [서비스]` 사용
- **extends**: 다른 YAML 파일이나 같은 파일의 서비스 설정을 상속. `file`을 생략하면 현재 파일에서 찾음. depends_on, links, volumes_from은 상속 불가

**(3) 네트워크 정의**

- **driver**: 기본은 브리지. overlay 등 다른 드라이버 지정 가능하고 옵션은 `driver_opts`로 전달. overlay는 스웜 모드 환경에서만 생성 가능
- **ipam**: subnet, ip_range, gateway 등 IP 관리 설정
- **external**: 매번 새로 만들지 않고 기존 네트워크를 사용. driver, driver_opts, ipam과 함께 쓸 수 없음

**(4) 볼륨 정의**

- **driver**: 볼륨 드라이버 지정. 기본값은 local, 추가 옵션은 `driver_opts`
- **external**: 프로젝트마다 볼륨을 새로 만들지 않고 기존 볼륨 사용

**(5) YAML 파일 검증하기**

- `docker compose config`: 오타나 포맷 오류 검사. `f`로 대상 파일 지정 가능

#### 4.3.2.2 도커 컴포즈 네트워크

- 네트워크를 따로 정의하지 않으면 프로젝트별로 `[프로젝트 이름]_default` 브리지 네트워크가 생성되고, down 시 삭제됨
- up이나 scale로 생성된 컨테이너는 모두 이 네트워크에 연결
- 서비스 내 컨테이너는 `-net-alias`가 서비스 이름으로 자동 설정되므로, `mysql`이라는 호스트 이름으로 접근하면 mysql 서비스 컨테이너 중 하나의 IP로 변환되고 여러 개면 라운드 로빈으로 분산
- 스웜 모드 서비스와 겉보기 동작은 비슷하지만 원리는 다름

#### 4.3.2.3 도커 스웜 모드와 함께 사용하기

- 컴포즈용 YAML을 스웜 클러스터에 배포한 것이 **스택**. 컴포즈의 서비스가 스웜 모드 서비스로 변환된 것
- 스택은 컴포즈가 아니라 스웜 매니저가 생성하므로 `docker stack` 명령어로 제어하고, 매니저 노드에서만 생성/삭제 가능

**스택 사용하기**

- `docker stack deploy -c docker-compose.yml mystack`: 스택 생성
- links, depends_on 같은 의존성 항목은 무시됨 (`Ignoring unsupported options: links`). links는 양쪽 컨테이너가 같은 호스트에 있어야 하기 때문
- `docker stack ls`, `docker stack ps mystack`: 스택과 컨테이너 확인
- `docker stack services mystack`는 `docker service ls`와 같은 정보 출력
- 서비스 이름 규칙: `[스택 이름]_[서비스 이름]`
- 컨테이너 수 조절은 `docker service scale mystack_web=2`
- 삭제는 `docker stack rm mystack` 권장

**스택 네트워크**

- 스택 생성 시 `[스택 이름]_default` 네트워크가 자동 생성
- 컴포즈와 달리 기본이 **overlay**이고 SCOPE가 swarm
- `-attachable`이 설정되지 않아 일반 컨테이너는 이 네트워크를 쓸 수 없음

## 4.4 도커 학습을 마치며: 도커와 컨테이너 생태계

- 2016년 벤더 종속을 막기 위해 컨테이너 표준인 **OCI**(Open Container Initiative) 발표. 런타임과 이미지 스펙을 표준화
- 이후 Moby 프로젝트 안에서 도커가 **runC, containerd, 도커 엔진**으로 분리
- 계층 구조
    - **dockerd(도커 엔진)**: 사용자가 상호작용하는 엔드유저용 도구
    - **containerd**: 여러 runC 컨테이너 프로세스와 이미지를 관리
    - **runC**: 컨테이너와 1:1로 매칭되는 실제 런타임
- 핵심: **도커 데몬 자체는 컨테이너가 아님**. runC와 containerd는 도커 엔진 없이도 독립적으로 사용 가능하며, 흔히 말하는 도커 컨테이너는 이들의 총칭에 가까움
- 다른 런타임 예시: kata 컨테이너(격리 강화), firecracker(AWS), cri-o(쿠버네티스용, containerd 대응), Podman(도커 엔진 대응)
- 지금은 키워드만 알아두고 필요할 때 깊게 익히면 충분

## 실무 관점 보충

- **links는 레거시**입니다. 같은 프로젝트의 서비스끼리는 기본 네트워크에서 서비스 이름으로 바로 통신되므로 보통 쓰지 않습니다.
- **준비 상태 대기 문제**는 지금은 `healthcheck`와 `depends_on`의 `condition: service_healthy` 조합이 표준입니다.

```yaml
services:
  app:
    depends_on:
      mysql:
        condition: service_healthy
  mysql:
    image: mysql:8
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 5s
      retries: 10
```

- 스케일은 `docker compose up -d --scale mysql=2` 형태도 많이 씁니다.
- 책의 extends 예시 중 `service: extend-web`은 아래 정의된 `extend_web`과 이름이 달라 그대로 쓰면 오류가 납니다.
