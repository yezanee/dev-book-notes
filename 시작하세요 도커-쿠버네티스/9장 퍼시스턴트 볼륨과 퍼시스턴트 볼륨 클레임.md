**도입: 왜 볼륨이 필요한가**

- 지금까지 다룬 디플로이먼트는 상태가 없는(stateless) 앱이었지만, DB처럼 데이터를 보유해야 하는 상태가 있는(stateful) 앱은 데이터를 영속적으로 저장할 방법이 필요함. 디플로이먼트를 지우면 파드와 그 안의 데이터도 함께 사라지기 때문.
- 도커에서는 `docker run -v`나 `docker volume`으로 호스트와 디렉터리를 공유해 데이터를 보존했음.
- 쿠버네티스에서도 호스트 디렉터리를 파드와 공유할 수 있지만, 파드가 다른 노드로 옮겨지면 이전 노드의 데이터를 쓸 수 없다는 한계가 있음.
- 해결책은 어느 노드에서도 네트워크로 접근 가능한 퍼시스턴트 볼륨을 쓰는 것. 대표적으로 NFS, AWS EBS, Ceph, GlusterFS 등이 있음.

## 9.1 로컬 볼륨: hostPath, emptyDir

- hostPath는 호스트와 볼륨을 공유할 때, emptyDir은 파드 내 컨테이너끼리 볼륨을 공유할 때 사용.
- 자주 쓰이진 않지만 YAML에서 볼륨을 정의하고 쓰는 방식에 익숙해지기 위해 먼저 다룸.

### 9.1.1 워커 노드의 로컬 디렉터리를 볼륨으로 사용: hostPath

- `spec.volumes`에 `hostPath.path: /tmp`로 볼륨을 정의하고, 컨테이너의 `volumeMounts`에서 이름으로 참조해 `/etc/data`에 마운트. 컨피그맵을 볼륨으로 쓰던 방식과 형식이 비슷함.
- 컨테이너의 `/etc/data`에 파일을 만들면 파드가 배치된 워커 노드의 `/tmp`에 그대로 생김 (`kubectl get pods -o wide`로 노드 확인 가능).
- 단점: 파드가 다른 노드로 옮겨가면 데이터를 쓸 수 없음. 스케줄링(11.2절)으로 특정 노드에 고정해도 그 노드가 죽으면 데이터를 잃음.
- 유용한 경우: CAdvisor 같은 모니터링 툴처럼 모든 노드에 배치되어 호스트 디렉터리나 도커 소켓에 접근해야 하는 특수한 파드.
- 그 외에는 보안과 활용성 측면에서 신중히 고려해야 함.

### 9.1.2 파드 내의 컨테이너 간 임시 데이터 공유: emptyDir

- 영속 저장용이 아니라 파드 실행 중에만 필요한 휘발성 데이터를 컨테이너끼리 공유하는 임시 공간.
- 비어 있는 상태로 생성되고, 파드가 삭제되면 데이터도 함께 삭제됨.
- 예제: `content-creator` 컨테이너의 `/data`와 아파치 웹 서버(`httpd`)의 `/usr/local/apache2/htdocs/`를 같은 emptyDir(`emptyDir: {}`)로 연결.
    - content-creator에서 `/data/test.html`을 만들면 웹 서버가 그 파일을 바로 서빙함.
    - 파드 IP로 curl 요청 시 `Hello, Kubernetes!` 응답 확인.
- 활용 예: 깃허브 소스코드를 받아와 앱 컨테이너에 공유하는 사이드카, 설정 파일을 동적으로 갱신하는 컨테이너 등.

## 9.2 네트워크 볼륨

- NFS, iSCSI, GlusterFS, Ceph 같은 온프레미스 볼륨부터 AWS EBS, GCP gcePersistentDisk 같은 클라우드 볼륨까지 마운트 가능.
- 네트워크로 접근만 되면 클러스터 내부든 외부든 위치는 상관없음. 단, 클라우드 종속 볼륨은 클러스터 생성 시 해당 클라우드용 옵션이 설정돼 있어야 함.
- 선택 기준: 읽기/쓰기 속도, 마운트 방식(1:1 또는 1:N), 구축 비용 등. 정답은 없으므로 직접 비교하고 벤치마크해 보는 것을 권장.

### NFS를 네트워크 볼륨으로 사용하기

- NFS는 여러 클라이언트가 동시에 마운트할 수 있는 네트워크 스토리지. 클러스터링 솔루션보다 안정성은 떨어지지만 서버 하나로 간편하게 쓸 수 있음.
- NFS 서버와 클라이언트가 필요한데, 클라이언트는 워커 노드 기능을 쓰므로 서버만 구축하면 됨.
- 실습: 클러스터 내부에 임시 NFS 서버를 디플로이먼트(`nfs-deployment.yaml`, 포트 2049/20048/111, `privileged: true`)와 서비스(`nfs-service.yaml`)로 생성.
- 파드(`nfs-pod.yaml`)에서 `volumes`에 `nfs` 항목(`path: /`, `server`)을 정의하고 `/mnt`에 마운트.
- 주의점: `server`에 서비스 DNS 이름이 아닌 Cluster IP를 넣어야 함. NFS 마운트는 컨테이너가 아니라 워커 노드에서 일어나는데, 노드는 쿠버네티스 DNS를 쓰도록 설정돼 있지 않기 때문.
    - `kubectl get svc nfs-service -o jsonpath='{.spec.clusterIP}'`로 IP를 얻어 `sed`로 치환한 뒤 apply.
    - `o jsonpath`는 리소스 JSON 중 특정 필드만 뽑는 옵션이며, jq와 함께 쓰면 더 편리함.
- 확인: 파드 안에서 `df -h`를 보면 NFS 서버 IP가 `/mnt`에 마운트되어 있음.
- 파드가 ContainerCreating에서 멈추면 `kubectl describe pods`로 원인을 보고, 해당 워커 노드에 `apt-get install nfs-common` 설치.
- `/mnt`에 저장한 파일은 파드가 다른 노드로 가거나 재시작돼도 유지됨.
- 이 NFS 서버는 테스트용. 실제 운영에서는 백업 스토리지, 설정 튜닝, DNS 이름 준비 등이 필요함.

## 9.3 PV, PVC를 이용한 볼륨 관리

### 9.3.1 퍼시스턴트 볼륨과 퍼시스턴트 볼륨 클레임을 사용하는 이유

- 지금까지는 파드 YAML에 볼륨 정보(NFS 종류, 엔드포인트)를 직접 적었음. 테스트에는 괜찮지만 배포용으로는 문제가 됨.
- 예: MySQL 디플로이먼트 YAML에 NFS를 고정해 두면 다른 부서나 외부에서 쓸 때도 반드시 NFS가 필요하고, iSCSI나 GlusterFS를 쓰려면 YAML을 따로 여러 벌 만들어야 함. 즉 볼륨과 앱 정의가 강하게 결합됨.
- PV와 PVC는 파드가 볼륨의 세부 사항을 몰라도 볼륨을 쓸 수 있게 추상화해 줌. NFS인지 EBS인지 상관없이 쓸 수 있는 것이 핵심.
- 사용 흐름 (인프라 관리자와 개발자 역할 분리):
    1. 인프라 관리자가 네트워크 볼륨 정보(엔드포인트 등)로 PV를 미리 생성.
    2. 개발자는 파드 YAML에 "영속 저장용 외부 볼륨이 필요하다"는 의미의 PVC를 명시하고 생성.
    3. 쿠버네티스가 PV 속성과 PVC 요구사항이 일치하면 둘을 바인드하고, 파드는 PVC를 통해 볼륨을 마운트.
- 결과적으로 앱 YAML에는 `nfs:` 대신 `persistentVolumeClaim: claimName: ...`만 들어가므로 더 보편적인 YAML이 됨.
- PVC로는 크기, 1:N 또는 1:1 쓰기 가능 여부, 읽기 전용 등의 조건도 전달할 수 있음 (뒤에서 다룸).

### 9.3.2 퍼시스턴트 볼륨과 퍼시스턴트 볼륨 클레임 사용하기

- 리소스 이름은 `persistentvolume`, `persistentvolumeclaim`이며 보통 `pv`, `pvc`로 줄여 씀 (`kubectl get pv,pvc`).
- 이번 실습은 kops로 AWS에 설치한 클러스터에서 EBS를 사용. GKE라면 GCP Persistent Disk 사용 가능하며, 개념은 같고 생성 방법만 조금 다름.
- 지금부터 인프라 관리자로서 PV를 등록하고, 개발자로서 PVC를 사용하는 흐름으로 진행.

**AWS에서 EBS를 퍼시스턴트 볼륨으로 사용하기**

- awscli로 5GB gp3 EBS 생성 (`aws ec2 create-volume --size 5 ...`), 볼륨 ID를 `$VOLUME_ID`에 저장.
    - kops 클러스터라면 `KubernetesCluster=<클러스터 이름>` 태그가 필요해 `-tag-specifications`로 붙임.
    - EBS의 리전과 가용 영역은 반드시 워커 노드와 같아야 함 (EC2 인스턴스 목록에서 확인).
- PV 정의(`ebs-pv.yaml`): `capacity.storage: 5Gi`, `accessModes: ReadWriteOnce`, `csi` 항목(`driver: ebs.csi.aws.com`, `fsType: ext4`, `volumeHandle: <VOLUME_ID>`).
    - 최근 버전에서는 in-tree 방식 대신 aws-ebs-csi-driver(CSI)를 설치해야 하며, 노드나 파드에 적절한 IAM 권한이 필요함. kops는 자동 설치되어 있고, GKE도 기본 CSI 드라이버가 있음.
- `sed`로 VOLUME_ID를 치환해 apply. PV는 네임스페이스에 속하지 않는 클러스터 단위 오브젝트.
- 생성 직후 `kubectl get pv` 상태는 Available.
- PVC + 파드 정의(`ebs-pod-pvc.yaml`):
    - PVC `my-ebs-pvc`: `storageClassName: ""`, `accessModes: ReadWriteOnce`, `resources.requests.storage: 5Gi`.
    - 파드의 `volumes`에서 `persistentVolumeClaim.claimName: my-ebs-pvc`로 사용.
- PVC의 accessModes와 resources는 요구 조건이며, 앞서 만든 PV와 일치하므로 바인드됨.
    - 일치하는 PV가 없으면 파드는 Pending으로 남음. 예를 들어 3Gi PV만 있으면 5Gi 요구를 못 채워 바인드 안 됨. 쿠버네티스가 주기적으로 재확인하므로 나중에 조건에 맞는 PV가 생기면 자동 연결.
- 결과: PV와 PVC 모두 Bound, 파드 Running, 파드 내 `/mnt`에 약 5G 볼륨(`/dev/xvdcl`) 마운트 확인.
- PVC는 PV와 달리 네임스페이스에 속하는 오브젝트 (예제에서는 default).
- 전체 흐름 정리:
    1. AWS에서 EBS 생성 후 ID 기록.
    2. 그 ID로 PV 등록 (accessModes, 크기 설정).
    3. PVC 정의 및 생성 (크기 5Gi, RWO 요구).
    4. 조건이 맞으면 PV와 PVC가 Bound.
    5. 파드가 PVC를 사용해 EBS를 컨테이너에 마운트.
- 파드 YAML에 nfs를 직접 쓰는 게 더 직관적으로 보일 수 있지만, PVC를 쓰면 배포하는 쪽은 실제 볼륨 구현을 몰라도 추상화된 인터페이스로 볼륨을 쓸 수 있다는 점이 핵심.

### 9.3.3 퍼시스턴트 볼륨을 선택하기 위한 조건 명시

- PVC는 실제 스펙을 몰라도 되지만, 최소 크기, 다중 마운트 여부, 읽기 전용 여부 같은 최소 조건은 전달해야 함.
- 예: PVC가 1:1 읽기쓰기 + 5Gi를 요구하면, NFS(1:N, 읽기 전용, 3Gi) PV가 아니라 EBS(1:1, 읽기쓰기, 5Gi) PV에 바인드됨.
- NFS는 1:N 마운트 가능, EBS는 1:1만 가능. NFS 크기는 보통 호스트 스토리지 크기, EBS는 생성 시 정한 크기.

**accessModes와 볼륨 크기, 스토리지클래스, 라벨 셀렉터를 이용한 퍼시스턴트 볼륨 선택**

- accessModes 종류 (괄호는 kubectl 출력명):
    - ReadWriteOnce (RWO): 1:1 마운트, 읽기쓰기 가능
    - ReadOnlyMany (ROX): 1:N 마운트, 읽기 전용
    - ReadWriteMany (RWX): 1:N 마운트, 읽기쓰기 가능
    - ReadWriteOncePod (RWOP): 하나의 파드만 1:1 마운트 가능
- RWO의 1:1은 노드 기준. 한 노드에만 마운트되지만 그 노드의 여러 파드는 같은 볼륨을 쓸 수 있음. 클러스터 전체에서 단 하나의 파드만 쓰게 하려면 RWOP 사용.
- EBS는 RWO, 1:N이 가능한 NFS라면 RWX가 적절.
- 볼륨 크기: PV의 `capacity.storage`와 PVC의 `resources.requests.storage`가 맞아야 바인드.
- 주의: accessModes와 크기는 메타데이터일 뿐 실제로 강제되지 않음. EBS에 RWX를 설정하는 잘못된 구성도 가능하고, 로컬 볼륨에 크기를 적어도 그 크기의 파티션이 생기지는 않음. 적절한 볼륨을 찾아주는 라벨 같은 역할로 이해.
- 스토리지 클래스: PV와 PVC 양쪽에 같은 `storageClassName`(예: `my-ebs-volume`)을 적으면 서로 매칭됨.
    - 명시하지 않으면 `""`로 취급되어 클래스 없는 것끼리 매칭.
    - 단, PVC에 storageClassName을 아예 안 쓰면 기본 스토리지 클래스가 있을 때 그것이 적용되므로, 쓰지 않으려면 `storageClassName: ""`를 명시하는 게 좋음.
    - 스토리지 클래스는 다이나믹 프로비저닝에도 쓰임 (9.3.5).
- 라벨 셀렉터: PV에 `labels`(예: `region: ap-northeast-2a`)를 붙이고, PVC에서 `selector.matchLabels`로 지정해 특정 PV에 바인드. 서비스와 디플로이먼트 연결 방식과 같음.

### 9.3.4 퍼시스턴트 볼륨의 라이프사이클과 Reclaim Policy

- `kubectl get pv`의 STATUS로 상태 확인: 생성 직후 Available, PVC와 연결되면 Bound (다른 PVC와 연결 불가).
- PVC를 삭제하면 PV는 Available이 아니라 Released가 됨. Released PV는 재사용 불가하지만 데이터는 남아 있으므로, PV를 지우고 다시 만들면 Available로 다시 사용 가능.
- Reclaim Policy: PVC 삭제 시 PV 데이터를 어떻게 처리할지 정하는 정책. Retain, Delete, Recycle이 있음.
- Retain (기본값): 라이프사이클은 Available → Bound → Released. 스토리지의 실제 데이터는 보존됨.
- Storage Object in Use Protection: 연결된 리소스가 있으면 삭제 명령을 내려도 실제로는 삭제되지 않음 (PVC와 연결된 PV, 파드가 사용 중인 PVC 등). 연결이 사라질 때까지 보호됨.
- Delete: PVC 삭제 시 PV도 자동 삭제되고, 가능하면 연결된 외부 스토리지까지 삭제.
    - 실습(`ebs-pv-delete.yaml`, `persistentVolumeReclaimPolicy: Delete`): PVC와 파드를 지우자 PV도 사라지고(`No resources found`) EBS 볼륨까지 삭제됨. 데이터가 모두 유실되므로 주의.
- Recycle: 데이터를 모두 지운 뒤 PV를 Available로 되돌림. PV나 외부 스토리지 자체는 남는다는 점이 Delete와 다름. 현재는 Deprecated.
- 모든 스토리지가 모든 정책을 지원하진 않음. EBS나 GCP 영구 디스크는 동적 프로비저닝 기반이라 Delete 가능, NFS는 Delete 불가하고 Recycle 가능.
- 정리: PVC 삭제 시 Retain이면 PV가 Released, Delete면 PV와 외부 볼륨까지 삭제, Recycle이면 데이터 삭제 후 Available.

### 9.3.5 StorageClass와 Dynamic Provisioning

**다이나믹 프로비저닝과 스토리지 클래스**

- 지금까지는 EBS를 미리 만들고 ID를 YAML에 적는 수동 방식이었음.
- 다이나믹 프로비저닝: PVC 조건에 맞는 PV가 없으면 PV와 외부 스토리지를 자동으로 함께 생성하는 기능. 외부 스토리지를 미리 만들 필요가 없음.
- 스토리지 클래스에 정의된 정보를 참고해 스토리지를 생성함.
- 흐름:
    1. 관리자가 스토리지 클래스를 미리 정의 (예: fast는 SSD, slow는 HDD).
    2. 개발자가 storageClassName을 명시해 PVC 생성. 조건에 맞는 PV는 아직 없음.
    3. 조건에 맞는 PV가 없으므로 해당 클래스 설정에 따라 외부 스토리지를 동적으로 생성 (fast면 SSD).
    4. 생성된 스토리지가 PV로 등록되고 PVC와 바인딩.
- 모든 클러스터에서 되는 것은 아니며, 다이나믹 프로비저닝을 지원하는 프로비저너가 활성화돼 있어야 함. AWS는 aws-ebs-csi-driver, GKE는 GcePersistentDiskCsiDriver.

**AWS에서 다이나믹 프로비저닝 사용하기**

- 시작 전 `kubectl delete pv,pvc,pods,deployment --all`로 기존 리소스 정리.
- `kubectl get storageclass`(약어 `sc`)로 확인. kops 설치 시 기본 클래스(`kops-csi-1-21 (default)`)가 이미 있음.
- HDD(st1)와 범용 SSD(gp3) 두 스토리지 클래스 생성 (`storageclass-slow.yaml`, `storageclass-fast.yaml`):
    - `provisioner: ebs.csi.aws.com` (aws-ebs-csi-driver의 EBS 동적 프로비저너)
    - `parameters.type`: st1 또는 gp3 (그 외 gp2, sc1, io1 등 가능. GCP는 pd-ssd, pd-standard)
    - `allowedTopologies`에 클러스터가 위치한 가용 영역 지정
- `storageClassName: fast`, RWO, 1Gi로 PVC(`pvc-fast-sc.yaml`) 생성.
    - 원래라면 PV가 없어 Pending이어야 하지만, 동적으로 gp3 EBS와 PV가 생성되어 Bound 됨. AWS 콘솔에서도 1GiB gp3 볼륨 확인 가능.
- PVC에 storageClassName을 아예 안 쓰면 기본 스토리지 클래스로 다이나믹 프로비저닝됨. 원하지 않으면 `storageClassName: ""` 명시.
- 조건을 만족하는 기존 PV가 이미 있으면 다이나믹 프로비저닝은 일어나지 않음.
- 주의: 동적 생성된 PV의 Reclaim Policy는 스토리지 클래스의 `reclaimPolicy`를 상속하며 기본값이 Delete. 그래서 PVC를 지우면 EBS도 함께 삭제됨.
    - Retain을 쓰려면 스토리지 클래스 YAML에 `reclaimPolicy: Retain`을 명시하거나, `kubectl edit`나 `patch`로 PV의 `persistentVolumeReclaimPolicy`를 변경.

**다이나믹 프로비저닝에서 특정 스토리지 클래스를 기본값으로 사용**

- 스토리지 클래스에 `storageclass.kubernetes.io/is-default-class: "true"` 어노테이션을 추가하면 기본 클래스가 됨 (`kubectl get sc`에 `(default)` 표시).
- 클래스를 명시하지 않으면 기본 클래스로 프로비저닝, `""`로 지정하면 프로비저닝 안 함.
