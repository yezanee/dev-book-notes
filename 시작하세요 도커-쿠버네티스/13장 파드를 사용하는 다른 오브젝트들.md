디플로이먼트가 `spec.template`으로 파드를 정의했듯이, 파드를 사용하는 상위 오브젝트는 파드의 기능을 그대로 활용합니다. 이 장에서는 디플로이먼트 외에 상황에 따라 필요한 상위 오브젝트들을 다룹니다.

### 13.1 잡(Jobs)

- 잡은 **특정 동작을 수행하고 종료해야 하는 작업**을 위한 오브젝트입니다.
- 디플로이먼트의 목표가 파드가 계속 실행 중인 상태라면, 잡의 목표는 **파드가 정상 종료(종료 코드 0, Completed)되는 것**입니다.
- 그래서 파드의 `restartPolicy`를 `Never` 또는 `OnFailure`로 명시해야 합니다.
- 예제 13.1: busybox로 Hello, World를 출력하고 종료 → 파드는 Completed, 잡의 COMPLETIONS는 1/1
- 쓰임새: 서버처럼 항상 떠 있을 필요 없는 **배치 작업** (프레임 렌더링, 파일 인코딩, 데이터 가공 등)
- 주의할 점
    - 동시성을 엄격히 보장하는 병렬 처리용이 아닙니다.
    - 실패 시 restartPolicy에 따라 재시작될 수 있으므로 작업은 **멱등성**을 갖는 것이 좋습니다.
- 공식 문서에는 메시지 큐나 Redis에 작업 큐를 두고 잡이 꺼내 처리하는 패턴 등도 소개되어 있습니다.

#### 잡의 세부 옵션

- **spec.completions**: 잡이 성공하려면 몇 개의 파드가 정상 종료돼야 하는지 (기본값 1)
    - 3으로 설정하면 파드가 **하나씩 순차적으로** 3번 생성되고, 3개가 모두 완료되면 잡 성공 (COMPLETIONS 3/3)
- **spec.parallelism**: 동시에 실행할 파드 수 (기본값 1)
    - completions 없이 3으로 설정하면 파드 3개가 한 번에 생성됨
- 두 옵션을 함께 쓰면 속도 조절 가능
    - 예: completions 8, parallelism 2 → 2개씩 실행하며 총 8개가 성공하면 종료
- 관련 옵션
    - **spec.backoffLimit**: 실패 시 재시도 최대 횟수 (기본 6번). OnFailure면 같은 파드 재시작, Never면 새 파드 생성
    - **spec.activeDeadlineSeconds**: 파드가 실행될 수 있는 최대 시간. 초과하면 강제 종료되고 잡은 실패 처리 (작업이 막혀서 무한정 머무는 상황 방지)

#### 크론잡(CronJobs)으로 잡을 주기적으로 실행하기

- 크론잡은 잡을 **주기적으로 실행**하는 오브젝트입니다. 데이터 백업, 이메일 전송 등에 적합합니다.
- 리눅스 크론(Cron)과 같은 스케줄 문법을 사용합니다.
- 예제 13.5 주요 항목
    - `schedule: "*/1 * * * *"`: 1분마다 실행
    - `jobTemplate`: 실행할 잡의 spec을 그대로 작성
- 생성하면 1분마다 `cronjob-example-숫자` 형태의 잡이 새로 만들어집니다.
- 기록 보관: 성공한 잡은 최대 3개, 실패한 잡은 최대 1개까지 남습니다. `spec.successfulJobsHistoryLimit`, `spec.failedJobsHistoryLimit`으로 변경 가능합니다.

### 13.2 데몬셋(DaemonSets)

- 데몬셋은 **모든 노드에 동일한 파드를 하나씩** 생성하는 오브젝트입니다.
- 로깅, 모니터링, 네트워킹 에이전트처럼 노드마다 하나씩 있어야 하는 경우에 유용합니다.
    - 예: `kube-proxy`, `calico-node`가 `kube-system`에서 데몬셋으로 실행됨
- 예제 13.6 주요 항목
    - [1] `kind: DaemonSet`
    - [2] 디플로이먼트처럼 **라벨 셀렉터**로 파드를 관리하므로, 셀렉터와 일치하는 라벨을 파드 템플릿에 지정
    - [3] **Toleration**: 마스터 노드의 Taint를 허용해 마스터 노드에도 파드를 배치 (필수는 아님)
    - [4] **resources.limits**: 노드 에이전트 역할이라 자원 부족으로 중지되면 곤란하므로 Guaranteed 클래스로 설정하는 것이 좋음 (필수는 아님)
- 생성하면 노드 4개에 파드가 하나씩, 총 4개 생성됩니다. 약칭은 `kubectl get ds`입니다.
- 특정 노드에만 배치하려면 11.2절의 **nodeSelector**나 **Node Affinity**를 사용합니다.
- 노드에 장애가 생겨도 파드가 다른 노드로 퇴거(Evict)되면 안 되므로, 데몬셋 파드에는 다양한 Toleration이 기본으로 설정됩니다.

참고로, 최신 쿠버네티스(1.24 이후)에서는 마스터 노드 Taint 키가 `node-role.kubernetes.io/control-plane`으로 바뀌었습니다. 실습 중 마스터 노드에 파드가 안 뜬다면 이 키로 Toleration을 추가해 보세요.

### 13.3 스테이트풀셋(StatefulSets)

#### 스테이트풀셋 사용하기

- 상태가 없는(Stateless) 앱은 디플로이먼트로 쉽게 배포하지만, DB처럼 **상태를 갖는(Stateful) 앱**은 데이터 관리와 개별 파드 접근 방법을 고려해야 해서 복잡합니다.
- 스테이트풀셋은 상태를 갖는 파드를 관리하기 위한 오브젝트입니다. (예전 이름은 펫셋(PetSet), 1.5 버전부터 변경)
- **가축 vs 애완동물 비유**
    - 가축(디플로이먼트 파드): 이름 없이 언제든 대체 가능. 파드 이름도 랜덤 (`pod-658ff6d49c-x6r96`)
    - 애완동물(스테이트풀셋 파드): 고유한 이름으로 구분되고 대체 불가능 (`my-pod-0`, `my-pod-1`)
- 예제 13.7을 적용하면 스테이트풀셋(파드 3개)과 서비스 1개가 생성되고, 파드 이름은 `statefulset-example-0`, `1`, `2`처럼 **0부터 숫자가 붙습니다.** 약칭은 `kubectl get sts`입니다.
- replicas가 여러 개면 기본적으로 0번부터 차례대로, **이전 파드가 완전히 준비된 뒤** 다음 파드를 생성합니다. (`spec.podManagementPolicy`로 변경 가능)
- **spec.serviceName**: 스테이트풀셋 파드에 접근할 서비스 이름을 지정하는 특이한 항목
    - 일반 서비스는 랜덤한 파드로 트래픽을 분산하는데, 스테이트풀셋은 **개별 파드**에 접근해야 하기 때문입니다.
- **헤드리스 서비스(Headless Service)**
    - `clusterIP: None`으로 설정한 서비스이며, `kubectl get svc`에서도 Cluster IP가 None으로 표시됩니다.
    - 서비스 이름이 DNS SRV 레코드로 쓰여서, `nslookup statefulset-service`를 하면 각 파드의 IP가 나옵니다.
    - **`<파드 이름>.<서비스 이름>`** 형태로 특정 파드에 직접 접근할 수 있습니다. (예: `statefulset-example-0.statefulset-service`)
- 디플로이먼트 파드에는 헤드리스 서비스를 쓰지 않았던 것을 떠올리면 가축과 애완동물의 차이가 이해됩니다. 이 개념은 데브옵스 전반에서 자주 나옵니다.

#### 스테이트풀셋과 퍼시스턴트 볼륨

- 상태를 갖는 앱은 데이터 보존을 위해 파드에 **퍼시스턴트 볼륨**을 마운트하는 것이 일반적입니다.
- 파드가 여러 개면 파드마다 PVC를 만들어야 하는 번거로움이 있는데, **spec.volumeClaimTemplates**를 정의하면 파드마다 PVC가 자동 생성되고 다이나믹 프로비저닝으로 PV까지 만들어집니다.
    - 이름 그대로 파드가 사용할 PVC의 **템플릿**을 정의하는 항목입니다.
- 예제 13.8: `storageClassName: generic` (AWS EBS를 동적 프로비저닝하도록 미리 설정해 둔 스토리지 클래스), `ReadWriteOnce`, 1Gi
- 적용하면 PV 3개와 PVC 3개(`webserver-files-statefulset-volume-0`, `1`, `2`)가 Bound 상태로 생성됩니다.
- 주의: 스테이트풀셋을 삭제해도 **volumeClaimTemplates로 생성된 PV와 PVC는 삭제되지 않습니다.** 재생성되거나 파드 수가 줄어도 데이터를 안전하게 보존하기 위함이므로 직접 삭제해야 합니다.

#### 리소스 정리

- 실습 YAML이 있는 디렉터리에서 `kubectl delete -f ./`로 한 번에 삭제할 수 있습니다.
- 단, volumeClaimTemplates로 생성된 외부 볼륨은 직접 삭제해야 합니다.
