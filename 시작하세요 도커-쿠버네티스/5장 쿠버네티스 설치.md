쿠버네티스를 처음 접하신다면 5장은 **쿠버네티스를 어디에, 어떤 도구로 설치할 수 있는지** 고르는 장이라고 보시면 됩니다. 아직 쿠버네티스로 뭘 하는지는 6장부터 본격적으로 나오고, 여기서는 실습 환경을 준비하는 게 목표예요.

## 0. 먼저 큰 그림: 쿠버네티스가 뭔가요?

도커를 이미 쓰셨으니 이렇게 연결하면 쉽습니다.

- **도커 엔진**: 서버 1대에서 컨테이너를 띄우는 도구
- **도커 컴포즈**: 여러 컨테이너를 YAML로 한 번에 정의해서 띄우는 도구 (그래도 서버는 1대)
- **도커 스웜**: 서버 여러 대를 하나의 클러스터로 묶어서 컨테이너를 배치하는 도구
- **쿠버네티스**: 도커 스웜과 같은 역할(여러 서버를 묶어 컨테이너 관리)인데, 기능이 훨씬 풍부해서 실무에서 사실상 표준이 된 도구

이렇게 여러 서버에 컨테이너를 알아서 배치하고, 죽으면 다시 살리고, 트래픽에 따라 늘리고 줄이는 걸 **컨테이너 오케스트레이션**이라고 부릅니다. 쿠버네티스는 그리스어로 조타수(배를 조종하는 사람)라는 뜻이고, 그래서 로고가 배의 키 모양이에요.

몇 가지 용어를 미리 알아두면 5장이 훨씬 잘 읽힙니다.

- **클러스터**: 쿠버네티스로 묶인 서버들의 집합
- **노드**: 클러스터에 속한 서버 한 대
- **마스터 노드(컨트롤 플레인)**: 클러스터 전체를 관리하는 관제탑 역할의 서버
- **워커 노드**: 실제로 컨테이너가 돌아가는 서버
- **kubectl**: 쿠버네티스를 조작하는 CLI. 도커의 `docker` 명령어 같은 존재입니다

**장점**

- 영속 볼륨, 스케줄링, 장애 복구, 오토스케일링, 서비스 디스커버리, 인그레스 등 운영에 필요한 거의 모든 기능 제공
- 구글, 레드햇 등이 함께 개발해서 안정성에 대한 신뢰가 높음
- CNCF(리눅스 재단 산하의 클라우드 네이티브 오픈소스 단체) 소속이라 주변 도구들과 연동이 잘 됨. containerd, 프로메테우스도 같은 CNCF 소속입니다

**단점**

- 배울 게 많고 구조가 복잡함
- 작은 조직에서는 쿠버네티스 자체를 관리하는 게 짐이 되는 오버 엔지니어링이 될 수 있음

## 5.1 쿠버네티스 설치 환경의 종류

도커는 설치 방법이 거의 하나지만, 쿠버네티스는 목적에 따라 설치 방법이 크게 갈립니다.

**개발 용도 (내 컴퓨터에서 가볍게)**

- Minikube
- Docker Desktop에 내장된 쿠버네티스

이 둘은 노드 1개짜리라서 설치는 쉽지만, 여러 서버에 컨테이너를 분산 배치하는 쿠버네티스의 핵심 기능을 제대로 체험하기 어렵습니다.

**서비스 테스트 또는 운영 용도 (여러 서버로)**

- kubeadm, kubespray: 서버를 내가 직접 준비하고 그 위에 쿠버네티스를 설치
- kops: AWS 같은 클라우드에서 서버, 네트워크까지 자동으로 만들어주면서 설치
- EKS, GKE: 클라우드 회사가 쿠버네티스 자체를 서비스로 제공 (매니지드 서비스)

그림 5.1의 핵심은 세 단계가 서로 트레이드오프라는 점이에요.

- **자체 서버(온프레미스)에 설치**: 모든 걸 세밀하게 설정할 수 있지만 관리가 가장 힘듦
- **클라우드 서버(예: EC2) 위에 직접 설치**: 서버/네트워크는 AWS가 관리하고, 쿠버네티스 설치와 관리는 내가 함
- **EKS, GKE 같은 매니지드 서비스**: 관리가 가장 편하지만 클라우드 의존성과 비용이 가장 큼

위로 갈수록 관리 복잡도는 줄고 클라우드 의존성은 커집니다. 책에서는 처음 배울 때는 매니지드 서비스로 바로 가기보다 직접 설치해보면서 전체 구조를 이해하는 걸 권장합니다.

**참고 메모**: 로드 밸런서(LoadBalancer)나 퍼시스턴트 볼륨 같은 일부 기능은 클라우드에서만 제대로 동작합니다. 그래서 책은 이런 기능을 설명할 때 kops(AWS)나 GKE로 만든 클러스터를 기준으로 합니다.

## 5.2 쿠버네티스 버전 선택

- 쿠버네티스는 업데이트가 매우 빨라서, 작은 버전 차이로도 사용법이 달라질 수 있음
- 운영 환경이라면 버전을 신중히 골라야 하지만, 지금 학습 단계에서는 너무 최신도 너무 옛날도 아닌 버전이면 충분
- 책은 2025년 4월 기준 최신인 **1.32 버전**을 기준으로 설명
- 책 예제를 똑같이 따라 하고 싶다면 설치할 때 버전을 명시하는 게 좋음

## 5.3 개발 용도의 쿠버네티스 설치

### 5.3.1 Docker Desktop에서 쿠버네티스 사용

가장 쉬운 방법입니다. 별도 설치 없이 켜기만 하면 돼요.

1. Docker Desktop 오른쪽 위 톱니바퀴(Settings) 클릭
2. Kubernetes 탭에서 Enable Kubernetes 체크
3. Apply & Restart 클릭

설치 방식으로 kubeadm과 kind 중 고를 수 있는데, kind를 고르면 가상 노드를 여러 개 띄울 수 있다는 차이가 있습니다. 관련 이미지를 내려받느라 시간이 좀 걸리고, 끝나면 터미널에서 `kubectl version`으로 Client Version과 Server Version이 둘 다 나오는지 확인하면 됩니다.

다만 Docker Desktop에서는 일부 네트워크, 볼륨 기능이 제대로 안 될 수 있어서, 책은 이건 가벼운 테스트용으로만 쓰고 이후 실습은 제대로 된 클러스터에서 하라고 권장합니다.

### 5.3.2 Minikube로 쿠버네티스 설치

Minikube는 로컬에서 가상 머신이나 도커 컨테이너 안에 쿠버네티스를 띄워주는 도구입니다. 여러 드라이버(VirtualBox, Qemu 등)를 지원하는데, 책은 가장 쉬운 도커 기반으로 설명합니다.

1. **minikube, kubectl 바이너리 내려받기**: 맥이면 명령어의 `linux`를 `darwin`으로, Apple Silicon이면 `amd64`를 `arm64`로 바꿔서 실행
2. **도커 설치**: 도커 드라이버를 쓰니까 도커가 먼저 있어야 함
3. **설치 실행**: `minikube start --driver=docker`
4. **확인**: `kubectl version`
5. **삭제**: `minikube delete`

주의할 점은 Minikube가 **root 유저로는 설치를 허용하지 않는다**는 것입니다. 그래서 일반 유저가 docker 명령을 쓸 수 있도록 `sudo usermod -aG docker $USER && newgrp docker`로 docker 그룹에 추가해야 해요.

## 5.4 여러 서버로 구성된 쿠버네티스 클러스터 설치

이제부터가 진짜 클러스터입니다. 책은 **마스터 1대 + 워커 3대**, 총 4대 구성을 기준으로 합니다.

**설치 전 모든 서버에서 확인할 것**

- 모든 서버의 시간이 ntp로 동기화되어 있는지
- 서버끼리 MAC 주소가 겹치지 않는지 (VM을 복사해서 만들면 겹칠 수 있음)
- 서버마다 최소 2GB 메모리, 2 CPU 이상인지
- 메모리 스왑 비활성화: `swapoff -a` (스왑이 켜져 있으면 컨테이너 성능이 들쭉날쭉해서 대부분의 설치 도구가 허용하지 않음)

이번 장의 구성은 학습용 간소화 버전이고, 실제 운영이라면 마스터 노드 다중화 같은 추가 설정이 필요하지만 지금은 신경 쓰지 않아도 됩니다.

### 5.4.1 kubeadm으로 설치

kubeadm은 쿠버네티스 커뮤니티가 공식 권장하는 설치 도구입니다. Minikube나 kubespray도 내부적으로는 kubeadm을 쓸 정도로 기본이 되는 도구예요. 일반 리눅스 서버라면 온프레미스든 클라우드든 상관없이 쓸 수 있고, 책은 AWS의 Ubuntu 24.04 EC2 4대를 예시로 듭니다.

**① 쿠버네티스 저장소 추가 (모든 노드)**

apt로 kubeadm 등을 설치할 수 있도록 공식 저장소의 키와 주소를 등록합니다. 다른 버전을 원하면 명령어 속 `1.32`만 바꾸면 됩니다.

**② containerd 및 kubeadm 설치 (모든 노드)**

여기서 5장에서 가장 중요한 개념 하나가 나옵니다.

> **쿠버네티스는 도커 엔진을 직접 쓰지 않는다**
> 
- 쿠버네티스는 **CRI(컨테이너 런타임 인터페이스)**라는 표준 규격을 통해 컨테이너를 제어합니다. 컨테이너 생성, 삭제 같은 명령을 정해진 형식으로 주고받는 일종의 프로토콜이에요
- 이 CRI를 지원하는 구현체가 **containerd**나 **cri-o**입니다
- 우리가 `docker run`을 칠 때도 사실 내부에서는 도커 엔진이 containerd를 시켜서 컨테이너를 만들고 있었습니다. 도커만 쓸 때는 몰라도 상관없어서 그동안 설명을 안 한 것뿐이에요
- 쿠버네티스(kubelet)는 도커 엔진을 건너뛰고 containerd와 바로 대화합니다. 그래서 이론적으로는 도커 없이 containerd만 있어도 됩니다
- 이 경우 컨테이너를 직접 들여다보려면 `docker` 대신 `crictl`이라는 명령어를 쓰는데, 대부분은 kubectl로 해결되니 이런 게 있다 정도만 알면 됩니다

책에서는 도커를 설치하면 containerd가 같이 깔리니까 그걸 활용합니다.

1. `wget -qO- get.docker.com | sh`로 도커 설치
2. 도커와 같이 설치된 containerd는 기본적으로 CRI가 꺼져 있어서, `containerd config default > /etc/containerd/config.toml`로 기본 설정을 덮어씀
3. config.toml에서 `SystemdCgroup = true`로 변경 (리소스 관리를 systemd 방식으로 맞춰주는 설정)
4. `service containerd restart`
5. `apt-get install -y kubelet kubeadm kubectl kubernetes-cni`로 쿠버네티스 패키지 설치

설치되는 것들의 역할은 이렇습니다.

- **kubelet**: 각 노드에서 실제로 컨테이너를 관리하는 에이전트
- **kubeadm**: 클러스터를 초기화하고 노드를 합류시키는 설치 도구
- **kubectl**: 사람이 쿠버네티스를 조작하는 CLI
- **kubernetes-cni**: 네트워크 플러그인을 위한 기본 구성 요소

**③ 클러스터 초기화 (마스터 노드에서만)**

```
kubeadm init --apiserver-advertise-address 172.31.0.100 \
--pod-network-cidr=192.168.0.0/16 --cri-socket unix:///run/containerd/containerd.sock
```

- `-apiserver-advertise-address`: 다른 노드가 마스터에 접근할 IP
- `-pod-network-cidr`: 컨테이너들이 쓸 내부 IP 대역. 서버 네트워크 대역과 겹치면 안 됨
- `-cri-socket`: containerd를 런타임으로 쓰겠다는 지정
- 특정 버전이 필요하면 `-kubernetes-version 1.32` 추가

성공하면 두 가지를 해야 합니다.

- 출력에 나온 `mkdir -p $HOME/.kube` 등 3줄을 마스터에서 실행: kubectl이 클러스터에 접속할 수 있도록 접속 정보 파일(kubeconfig)을 내 홈 디렉터리에 복사하는 과정
- 맨 마지막에 출력된 `kubeadm join ...` 명령을 **각 워커 노드에서** 실행: 끝에 `-cri-socket unix:///run/containerd/containerd.sock`을 붙여야 함. This node has joined the cluster가 나오면 합류 성공

**④ 컨테이너 네트워크 애드온 설치 (마스터에서)**

서로 다른 서버에 있는 컨테이너끼리 통신하려면 **CNI(네트워크 플러그인)**가 필요합니다. cilium 등 여러 선택지가 있지만 책은 calico를 씁니다. `kubectl create -f`로 calico의 tigera-operator.yaml과 custom-resources.yaml을 적용하면 됩니다.

calico는 기본적으로 192.168.0.0/16 대역을 쓰기 때문에, kubeadm init에서 다른 대역(예: 10.244.0.0/16)을 썼다면 custom-resources.yaml을 내려받아 cidr 값을 맞춰서 수정해야 합니다.

**⑤ 확인**

- `kubectl get pods --namespace kube-system`: 쿠버네티스 핵심 컴포넌트들이 모두 Running이면 성공
- `kubectl get nodes`: 노드 4대가 모두 Ready인지 확인. 마스터는 ROLES에 control-plane으로 표시됨

**삭제/재설치**: `kubeadm reset`. 그래도 설치가 계속 실패하면 `/etc/kubernetes` 디렉터리에 이전 파일이 남아 있는 경우가 있으니 옮기거나 지운 뒤 다시 시도하세요.

### 5.4.2 kops로 AWS에서 설치

kubeadm은 서버를 내가 먼저 만들어둬야 하지만, **kops는 EC2 인스턴스, 네트워크까지 알아서 만들어주면서** 쿠버네티스를 설치합니다. AWS를 세부적으로 몰라도 클러스터를 만들 수 있다는 게 장점입니다.

1. **kops, kubectl 바이너리 내려받기**: 책은 kops 1.31.0 사용. 최신 버전은 kops 깃허브 릴리스 페이지에서 확인
2. **AWS 사용자 생성 및 AWS CLI 설정**: kops가 AWS 리소스를 만들 수 있도록 적절한 권한의 IAM 사용자 키를 aws CLI에 등록 (자세한 과정은 책 깃허브 링크 참고)
3. **S3 버킷 생성**: kops는 클러스터 설정 정보를 S3에 저장합니다. 버킷 생성 후 버저닝을 켜두고, 버킷 이름은 전 세계에서 고유해야 하니 본인만의 이름으로 지정
4. **환경 변수 설정**
    - `export NAME=mycluster.k8s.local` (클러스터 이름)
    - `export KOPS_STATE_STORE=s3://버킷이름`
5. **SSH 키 생성**: `ssh-keygen -t rsa -N "" -f ./id_rsa` (EC2에 배포될 키)
6. **클러스터 설정 파일 생성**: `kops create cluster --zones ap-northeast-2a --networking calico --ssh-public-key ./id_rsa.pub $NAME`. 이 시점엔 아직 실제 리소스는 안 만들어지고 설정만 생성됨
7. **옵션 수정**
    - 워커: `kops edit ig --name $NAME nodes-ap-northeast-2a`에서 maxSize, minSize를 3으로 (오토 스케일링 그룹의 최소/최대 개수라서 둘을 같게 하면 고정 3대)
    - 마스터: `kops edit ig --name $NAME control-plane-ap-northeast-2a`에서 machineType을 t3.medium으로
8. **실제 생성**: `kops update cluster --yes $NAME`. 5~10분 정도 걸림
9. **접속 설정 및 확인**
    - `kops export kubeconfig --admin`: kubectl이 이 클러스터를 바라보게 설정
    - `kops validate cluster`: 설치 진행 상황 확인
    - `kubectl get nodes`: 마스터 1 + 워커 3이 Ready인지 확인
10. **삭제**: `kops delete cluster $NAME --yes` (단, S3에 저장된 설정 파일은 남음)

클러스터 이름이 `.k8s.local`로 끝나면 별도 도메인 없이 동작하고, Route53에 구입한 도메인이 있다면 `NAME=도메인`으로 설정해 클러스터를 도메인에 등록할 수도 있습니다.

### 5.4.3 GKE로 쿠버네티스 사용하기

kubeadm이나 kops가 어렵게 느껴진다면 매니지드 서비스도 선택지입니다. GKE는 클릭 몇 번으로 클러스터가 만들어지고 마스터 노드 관리도 구글이 맡아줍니다. 대신 세부 구조를 배우기에는 덜 적합합니다. 구글 클라우드는 신규 가입 시 12개월간 300달러 크레딧을 주니 비용이 부담되면 활용하세요.

**① 클러스터 생성**

1. GKE 콘솔 접속 후 [만들기] 클릭
2. 오른쪽 위 [Standard 클러스터로 전환] 클릭. Autopilot은 노드까지 자동 관리해주지만 학습 목적이라 일반적인 Standard 모드 선택
3. 위치 유형을 [영역]으로 바꿔 리소스를 너무 많이 쓰지 않게 설정
4. 노드 풀은 기본값 그대로 두고 [만들기]. 5~10분 후 노드 3개짜리 클러스터 완성

**② 클러스터에 연결**

- **웹에서**: 클러스터 오른쪽 메뉴의 [연결] → [Cloud Shell에서 실행]. 브라우저 터미널이 열리고 접속 명령어가 자동 입력됨
- **내 터미널에서**: gcloud CLI를 설치/설정한 뒤(부록 B 참고) `gcloud container clusters get-credentials 클러스터이름 --zone 리전` 실행, 그다음 kubectl 설치

마지막으로 `kubectl get nodes`와 `kubectl version`으로 노드와 버전을 확인하면 끝입니다.

## 한눈에 보는 핵심 정리

- 쿠버네티스는 여러 서버를 하나로 묶어 컨테이너를 관리하는 오케스트레이션 도구이고, 도커 스웜의 강화판이라고 생각하면 됨
- 설치 방법은 목적별로 다름: 로컬 테스트는 Docker Desktop, Minikube / 직접 설치는 kubeadm / AWS 자동 구축은 kops / 완전 관리형은 EKS, GKE
- 어떤 방법이든 마지막 확인은 `kubectl get nodes`로 노드가 Ready인지 보는 것
- 쿠버네티스는 도커 엔진이 아니라 CRI를 통해 containerd와 직접 통신함
- kubeadm 설치 흐름: 스왑 끄기 → containerd 설정 → kubeadm init(마스터) → kubeadm join(워커) → CNI(calico) 설치

실습 환경을 고르실 때 팁을 하나 드리면, AWS를 이미 다뤄보셨으니 EC2 4대에 kubeadm으로 직접 설치해보는 게 구조를 이해하는 데 가장 좋습니다. 다만 kops나 GKE, EC2 여러 대는 켜두는 동안 계속 과금되니 실습이 끝나면 꼭 삭제하거나 중지해 두세요.
