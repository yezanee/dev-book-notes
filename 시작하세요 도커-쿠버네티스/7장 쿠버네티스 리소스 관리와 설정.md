지금까지 배운 파드, 레플리카셋, 디플로이먼트, 서비스는 배포에 꼭 필요한 기본 4종 세트입니다. 7장은 여기에 더해 애플리케이션을 효율적으로 관리하기 위해 자주 쓰는 세 가지 오브젝트를 다룹니다.

- **네임스페이스(Namespace)**: 리소스를 묶는 논리적인 그룹
- **컨피그맵(ConfigMap)**: 일반 설정값 저장소
- **시크릿(Secret)**: 비밀번호처럼 민감한 값 저장소

---

## 7.1 네임스페이스(Namespace): 리소스를 논리적으로 구분하는 장벽

도커에서는 컨테이너를 그룹으로 나눌 방법이 없어서 `docker ps` 하면 전부 한꺼번에 보였습니다. 쿠버네티스의 네임스페이스는 파드, 레플리카셋, 디플로이먼트, 서비스 같은 리소스를 담는 **가상의 칸막이 공간**입니다.

예를 들어 모니터링용 리소스는 `monitoring`, 테스트용은 `testbed`, 또는 조직별로 네임스페이스를 나누면 클러스터 하나를 여러 개의 가상 클러스터처럼 쓸 수 있습니다.

### 네임스페이스 기본 개념 이해

```bash
kubectl get namespaces
kubectl get ns          # 줄임말
```

아무것도 안 만들어도 기본 4개가 있습니다: `default`, `kube-node-lease`, `kube-public`, `kube-system`.

- **default**: `-namespace` 옵션을 생략하면 자동으로 쓰이는 네임스페이스입니다. 지금까지 만든 리소스는 전부 여기에 있었습니다.
- **kube-system**: 쿠버네티스가 돌아가는 데 필요한 핵심 컴포넌트(coredns, etcd, kube-apiserver, kube-scheduler 등)가 있는 곳입니다. 클러스터의 DNS 서버 서비스(`kube-dns`)도 여기 있습니다. 잘 모를 땐 건드리지 않는 게 좋습니다.

```bash
kubectl get pods --namespace default
kubectl get pods -n kube-system     # -n 으로 줄여 쓰기
```

**주의할 점 두 가지**

- 네임스페이스는 **논리적** 구분일 뿐 **물리적** 격리가 아닙니다. 다른 네임스페이스의 파드가 같은 노드에서 돌 수도 있습니다.
- 라벨과의 차이: 라벨(`kubectl get pods -l app=webserver`)도 리소스를 분류하지만, 네임스페이스는 더 넓은 용도로 쓰입니다. ResourceQuota로 네임스페이스별 자원 사용량을 제한하거나, 어드미션 컨트롤러로 특정 네임스페이스의 파드에 사이드카를 자동으로 붙이는 식입니다(11.1절에서 다시 다룸).
- 2장의 **리눅스 네임스페이스**(네트워크, 마운트, 프로세스 격리용 커널 기능)와는 이름만 같고 전혀 다른 개념입니다.

### 네임스페이스 사용하기

생성 방법은 두 가지입니다.

```yaml
# 예제 7.1 production-namespace.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: production
```

```bash
kubectl apply -f production-namespace.yaml
# 또는
kubectl create namespace production
```

특정 네임스페이스에 리소스를 만들려면 YAML의 **`metadata.namespace`** 에 지정하면 됩니다.

```yaml
# 예제 7.2 hostname-deploy-svc-ns.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hostname-deployment-ns
  namespace: production
...
---
apiVersion: v1
kind: Service
metadata:
  name: hostname-svc-clusterip-ns
  namespace: production
...
```

- `--` 로 구분하면 YAML 파일 하나에 여러 리소스를 정의할 수 있고, `kubectl apply -f` 한 번에 모두 생성됩니다.
- 조회: `kubectl get pods,services -n production`
- 모든 네임스페이스 조회: `kubectl get pods --all-namespaces`

### 네임스페이스의 서비스에 접근하기

6장에서 서비스 이름만으로 접근할 수 있다고 했던 건 정확히는 **같은 네임스페이스 안에서만** 가능합니다. default에 있는 테스트 파드에서 production의 서비스를 이름만으로 부르면 `Could not resolve host` 에러가 납니다.

다른 네임스페이스의 서비스는 **`<서비스 이름>.<네임스페이스 이름>.svc`** 형태로 접근합니다.

```bash
curl hostname-svc-clusterip-ns.production.svc:8080
```

서비스 DNS의 전체 이름(FQDN)은 `<서비스 이름>.<네임스페이스 이름>.svc.cluster.local` 입니다.

삭제는 `kubectl delete namespace production` 으로 하며, **안에 있는 리소스도 전부 함께 삭제**되니 먼저 목록을 확인하는 게 좋습니다.

### 네임스페이스에 종속되는 쿠버네티스 오브젝트와 독립적인 오브젝트

모든 리소스가 네임스페이스에 속하는 건 아닙니다.

- **네임스페이스에 속하는(namespaced) 오브젝트**: 파드, 서비스, 레플리카셋, 디플로이먼트, 컨피그맵, PVC 등. 확인은 `kubectl api-resources --namespaced=true`
- **속하지 않는 오브젝트**: 노드(nodes), 네임스페이스 자체, componentstatuses 등 클러스터 전반에 쓰이는 저수준 오브젝트. 확인은 `kubectl api-resources --namespaced=false`

그래서 `kubectl get nodes` 에 `--namespace` 를 붙여도 의미가 없습니다. 지금은 "저수준 관리용 오브젝트는 네임스페이스 밖에 있을 수 있다" 정도만 알아두면 됩니다.

> 참고: 기본 네임스페이스는 kubeconfig 파일(10.5절)로 바꿀 수 있고, `kubens` 라는 오픈소스 도구로 `kubens kube-system` 처럼 간단히 전환할 수도 있습니다.
>

## 7.2 컨피그맵(Configmap), 시크릿(Secret): 설정값을 파드에 전달

애플리케이션에는 `LOG_LEVEL=INFO` 같은 키-값 설정이나 `nginx.conf` 같은 설정 파일이 필요합니다. 전달 방법을 비교해 보면 다음과 같습니다.

- **도커 이미지에 넣기**: 이미지는 빌드 후 바뀌지 않으니 유연성이 떨어집니다.
- **YAML에 환경 변수 하드코딩** (예제 7.3, `env:` 에 `LOG_LEVEL: INFO` 직접 작성): 운영/개발처럼 값만 다른 YAML 파일이 여러 개 생깁니다.
- **컨피그맵/시크릿 사용**: 파드 YAML은 하나로 두고, 환경마다 다른 컨피그맵을 만들어 연결합니다. 즉 **애플리케이션과 설정값을 분리**할 수 있습니다.

Spring Boot로 치면 코드는 그대로 두고 `application-prod.yml`, `application-dev.yml` 을 바꿔 끼우는 것과 비슷한 발상입니다. 도커 스웜의 config, secret과도 거의 같은 개념입니다.

### 7.2.1 컨피그맵(Configmap)

#### 컨피그맵 사용 방법 익히기

컨피그맵은 일반 설정값을 담는 오브젝트이며 **네임스페이스에 속합니다**.

```bash
kubectl create configmap log-level-configmap --from-literal LOG_LEVEL=DEBUG

# 키-값 여러 개
kubectl create configmap start-k8s \
  --from-literal k8s=kubernetes \
  --from-literal container=docker
```

확인 방법:

```bash
kubectl get cm                                  # cm 줄임말
kubectl describe configmap log-level-configmap
kubectl get configmap log-level-configmap -o yaml
```

파드에서 컨피그맵을 쓰는 방법은 크게 두 가지이며, 애플리케이션이 설정값을 어떻게 읽느냐에 따라 고릅니다.

- **환경 변수로 사용**: 앱이 시스템 환경 변수에서 값을 읽는다면 이 방법. `echo $LOG_LEVEL` 로 확인 가능
- **파일로 마운트해 사용**: 앱이 `nginx.conf` 같은 파일에서 설정을 읽는다면 이 방법. 예를 들어 `/etc/config/log_level` 파일 안에 `INFO` 가 들어감

#### 컨피그맵의 데이터를 컨테이너의 환경 변수로 가져오기

**방법 1. envFrom: 컨피그맵의 모든 키-값을 가져오기**

```yaml
# 예제 7.4 all-env-from-configmap.yaml
spec:
  containers:
    - name: my-container
      image: busybox
      args: ['tail', '-f', '/dev/null']
      envFrom:
      - configMapRef:
          name: log-level-configmap   # 키-값 1개
      - configMapRef:
          name: start-k8s             # 키-값 2개
```

```bash
kubectl exec container-env-example -- env
# LOG_LEVEL=DEBUG, container=docker, k8s=kubernetes  → 총 3개
```

출력에 보이는 `KUBERNETES_SERVICE_PORT` 등은 쿠버네티스가 default 네임스페이스의 `kubernetes` 서비스 접근 정보를 자동으로 넣어준 것입니다.

**방법 2. valueFrom + configMapKeyRef: 원하는 키만 골라서 가져오기**

```yaml
# 예제 7.5 selective-env-from-configmap.yaml
env:
- name: ENV_KEYNAME_1          # (1) 컨테이너에 생길 환경 변수 이름
  valueFrom:
    configMapKeyRef:
      name: log-level-configmap  # (2) 참조할 컨피그맵
      key: LOG_LEVEL             # (3) 가져올 키
- name: ENV_KEYNAME_2
  valueFrom:
    configMapKeyRef:
      name: start-k8s
      key: k8s                   # → ENV_KEYNAME_2=kubernetes
```

정리하면:

- **envFrom**: 컨피그맵의 모든 키-값을 그대로 가져옴
- **valueFrom + configMapKeyRef**: 원하는 키만 골라 원하는 이름의 환경 변수로 가져옴

> 참고: 예제는 파드 기준이지만 디플로이먼트, 스테이트풀셋, 데몬셋 등 파드를 기반으로 하는 오브젝트의 파드 템플릿에서도 똑같이 쓸 수 있습니다.
> 

#### 컨피그맵의 내용을 파일로 파드 내부에 마운트하기

**모든 키-값을 파일로 마운트**

```yaml
# 예제 7.6 volume-mount-configmap.yaml
spec:
  containers:
    - name: my-container
      image: busybox
      volumeMounts:
      - name: configmap-volume    # 아래 volumes에서 정의한 이름
        mountPath: /etc/config    # 파일이 놓일 경로
  volumes:
  - name: configmap-volume
    configMap:
      name: start-k8s             # 가져올 컨피그맵
```

- `spec.volumes`: 파드에서 쓸 볼륨 목록 정의 (여기서 볼륨 이름은 이 YAML 안에서만 쓰는 이름이고 실제 볼륨 오브젝트가 생기는 건 아님)
- `spec.containers.volumeMounts`: 그 볼륨을 컨테이너 어느 디렉터리에 붙일지 지정

결과적으로 **키 이름이 파일 이름, 값이 파일 내용**이 됩니다.

```bash
kubectl exec configmap-volume-pod -- ls /etc/config        # container, k8s
kubectl exec configmap-volume-pod -- cat /etc/config/k8s   # kubernetes
```

이렇게 리소스 데이터를 파드 디렉터리에 놓는 것을 공식 문서에서는 **투사(Projection)** 라고 부릅니다.

**원하는 키만 골라서 마운트**

```yaml
# 예제 7.7 selective-volume-configmap.yaml
volumes:
- name: configmap-volume
  configMap:
    name: start-k8s
    items:                  # 가져올 키 목록
    - key: k8s
      path: k8s_fullname    # 만들어질 파일 이름
```

→ `/etc/config/k8s_fullname` 파일에 `kubernetes` 가 들어갑니다.

> configMapKeyRef, envFrom 같은 항목을 외울 필요는 없고, 어떤 방식들이 있는지 이해해 두는 게 목표입니다.
> 

#### 파일로부터 컨피그맵 생성하기

볼륨으로 쓸 때는 `nginx.conf`, `mysql.conf` 같은 **설정 파일 자체를 통째로** 컨피그맵에 넣는 경우가 많습니다.

```bash
# --from-file: 파일 이름이 키, 파일 내용이 값
echo Hello, world! >> index.html
kubectl create configmap index-file --from-file index.html

# 키 이름 직접 지정
kubectl create configmap index-file-customkey --from-file myindex=index.html

# --from-env-file: 키=값 형식 파일의 각 줄을 개별 키-값으로
kubectl create configmap from-envfile --from-env-file multiple-keyvalue.env
```

- 정적 파일(index.html, nginx.conf)을 넣을 땐 `-from-file`
- 환경 변수 여러 개를 넣을 땐 `-from-env-file`

#### YAML 파일로 컨피그맵 정의하기

- `-dry-run` 과 `o yaml` 을 함께 쓰면 실제로 만들지 않고 YAML만 출력해 줍니다. 이걸 파일로 저장해 `apply` 하면 됩니다.

```bash
kubectl create configmap my-configmap \
  --from-literal mykey=myvalue --dry-run=client -o yaml > my-configmap.yaml
kubectl apply -f my-configmap.yaml
```

dry run은 실행 가능 여부만 검토하는 기능입니다.

- `-dry-run=client`: kubectl(클라이언트)에서 가상으로 실행
- `-dry-run=server`: API 서버에서 실제로 성공할지까지 검토

단점은 설정이 많으면 YAML이 너무 길어진다는 것입니다(100줄짜리 nginx.conf를 다 넣어야 함). 이럴 땐 **kustomize** 를 쓰면 편합니다(시크릿 절에서 설명).

### 7.2.2 시크릿(Secret)

#### 시크릿 사용 방법 익히기

시크릿은 SSH 키, 비밀번호처럼 **민감한 정보**를 저장하는 용도이고, 네임스페이스에 속합니다. 사용법은 컨피그맵과 거의 같지만 용도별로 더 세분화돼 있습니다.

```bash
kubectl create secret generic my-password --from-literal password=1q2w3e4r

echo mypassword > pw1 && echo yourpassword > pw2
kubectl create secret generic our-password --from-file pw1 --from-file pw2
```

`generic` 은 시크릿의 종류를 뜻합니다(뒤에서 설명).

```bash
kubectl get secret my-password -o yaml
# data:
#   password: MXEydzNlNHI=
```

값이 **base64로 인코딩**돼 저장됩니다. `echo MXEydzNlNHI= | base64 -d` 하면 `1q2w3e4r` 이 나옵니다. 그래서 YAML로 직접 시크릿을 만들 때도 값은 base64로 인코딩된 문자열을 넣어야 합니다.

> 초보자가 자주 오해하는 부분: base64는 **암호화가 아니라 인코딩**이라 누구나 바로 디코딩할 수 있습니다. 책에서는 따로 언급하지 않지만, 시크릿 YAML을 Git에 그대로 올리는 건 위험합니다.
> 

파드에서 쓰는 방법은 컨피그맵과 같고 이름만 configmap → secret으로 바뀝니다.

- **전체를 환경 변수로** (예제 7.8): `envFrom` + `secretRef`
- **특정 키만 환경 변수로** (예제 7.9): `valueFrom` + `secretKeyRef`
- **전체를 파일로 마운트** (예제 7.10): `volumes` 에 `secret.secretName`
- **특정 키만 파일로 마운트** (예제 7.11): `secret.items` 에 `key`, `path` 지정

```yaml
# 예제 7.11 selective-mount-secret.yaml
volumeMounts:
- name: secret-volume
  mountPath: /etc/secret
volumes:
- name: secret-volume
  secret:
    secretName: our-password
    items:
    - key: pw1
      path: password1     # → /etc/secret/password1
```

책 예제 주석에는 `/etc/config/password1` 로 적혀 있지만 mountPath가 `/etc/secret` 이므로 실제 경로는 `/etc/secret/password1` 입니다(아래 실행 결과도 그렇습니다).

YAML에는 base64 값을 넣었더라도, **파드에서 환경 변수나 파일로 꺼내면 디코딩된 원래 값**으로 보입니다.

```bash
kubectl exec selective-volume-pod -- cat /etc/secret/password1   # mypassword
```

#### 이미지 레지스트리 접근을 위한 docker-registry 타입의 시크릿 사용하기

`kubectl get secrets` 의 **TYPE** 이 시크릿 종류입니다. 지금까지 만든 건 모두 **Opaque** 타입이며, `generic` 으로 만들면 이 타입이 됩니다. 사용자가 정의하는 일반 데이터용입니다(opaque는 불투명하다는 뜻).

사설 레지스트리나 도커 허브 프라이빗 저장소, GCR, ECR에서 이미지를 받으려면 인증이 필요합니다. 도커에서는 `docker login` 을 썼지만 쿠버네티스에서는 **인증 정보를 시크릿으로** 만듭니다. 방법은 두 가지입니다.

```bash
# 1. docker login 후 생기는 ~/.docker/config.json을 그대로 사용
kubectl create secret generic registry-auth \
  --from-file=.dockerconfigjson=/root/.docker/config.json \
  --type=kubernetes.io/dockerconfigjson

# 2. 명령어에 직접 인증 정보 입력
kubectl create secret docker-registry registry-auth-by-cmd \
  --docker-username=alicek106 \
  --docker-password=1q2w3e4r
  # --docker-server는 선택, 생략하면 docker.io(도커 허브)
```

생성된 시크릿 타입은 `kubernetes.io/dockerconfigjson` 입니다. 디플로이먼트에서는 `imagePullSecrets` 로 사용합니다.

```yaml
# 예제 7.12 deployment-from-private-repo.yaml
spec:
  containers:
  - name: test-container
    image: <이미지 이름>
  imagePullSecrets:
  - name: registry-auth-registry
```

> 기본적으로 이미지가 워커 노드에 없을 때만 받아오며, 이 동작은 `imagePullPolicy` 로 바꿀 수 있습니다.
> 

#### TLS 키를 저장할 수 있는 tls 타입의 시크릿 사용하기

TLS 연결에 쓰는 인증서와 비밀키를 저장하는 타입입니다. `--cert`, `--key` 로 파일을 지정합니다.

```bash
# 테스트용 키 페어 생성
openssl req -new -newkey rsa:4096 -days 365 -nodes \
  -x509 -subj "/CN=example.com" -keyout cert.key -out cert.crt

kubectl create secret tls my-tls-secret --cert cert.crt --key cert.key
```

타입은 `kubernetes.io/tls` 이고, 데이터는 `tls.crt`, `tls.key` 라는 키로 base64 인코딩돼 저장됩니다. 나중에 인그레스 같은 고급 기능에서 쓰게 됩니다.

#### 좀 더 쉽게 컨피그맵과 시크릿 리소스 배포하기

- `-dry-run -o yaml` 로 YAML을 뽑으면 인증서처럼 긴 데이터가 YAML에 그대로 들어가 가독성도 나쁘고 데이터와 YAML이 분리되지 않습니다. 이를 해결하는 것이 **kustomize** 입니다(kubectl 1.14부터 지원).

```yaml
# 예제 7.13 kustomization.yaml
secretGenerator:
- name: kustomize-secret
  type: kubernetes.io/tls
  files:
  - tls.crt=cert.crt      # tls.crt 키에 cert.crt 내용
  - tls.key=cert.key
```

```bash
kubectl kustomize ./      # 생성될 리소스 미리 보기 (dry-run과 비슷)
kubectl apply -k ./       # 생성
kubectl delete -k ./      # 삭제
```

컨피그맵은 `configMapGenerator` 를 쓰며, 컨피그맵에는 종류가 없으므로 `type` 은 적지 않습니다(예제 7.14).

kustomize로 만든 리소스 이름 뒤에는 데이터 기반 **해시값**이 자동으로 붙습니다(예: `kustomize-secret-gtc5562mc4`). kubectl에서도 `--append-hash` 옵션으로 같은 효과를 낼 수 있고, 데이터가 바뀌면 이름도 바뀌므로 설정 업데이트 때 유용합니다.

#### 컨피그맵이나 시크릿을 업데이트해 애플리케이션의 설정값 변경하기

수정 방법은 `kubectl edit`, YAML 수정 후 `kubectl apply`, `kubectl patch` 가 있습니다.

```bash
sed -i -e 's/myvalue/yourvalue/g' my-configmap.yaml
kubectl apply -f my-configmap.yaml     # configured
```

여기서 **전달 방식에 따라 반영 여부가 다르다**는 게 핵심입니다.

- **환경 변수로 전달한 경우**: 컨피그맵을 바꿔도 자동 반영되지 않습니다. 파드를 다시 생성해야 합니다.
- **파일로 마운트한 경우**: 파드 안의 파일 내용은 자동으로 갱신됩니다.

단, 파일이 바뀌어도 **이미 실행 중인 프로세스가 그걸 다시 읽지는 않습니다.** 반영하려면 직접 로직을 만들어야 합니다.

- 변경된 파일을 다시 읽도록 SIGHUP 시그널을 보내는 사이드카 컨테이너를 붙이기
- 애플리케이션에서 쿠버네티스 API의 Watch로 변경 알림을 받아 자동 리로드하기

정답은 없지만, 쿠버네티스용 애플리케이션을 설계할 때 꼭 고려해야 할 부분입니다.
