## 들어가며

이 장부터 쿠버네티스의 고급 기능 파트가 시작됩니다. 실제 운영 환경에서는 기초 오브젝트(파드, 디플로이먼트, 서비스)만으로는 부족하고, 다음과 같은 기능이 필요해집니다.

- 7계층 레벨의 요청 처리 (가상 호스트, 경로 기반 라우팅)
- 데이터를 영속적으로 보관할 외부 볼륨
- 여러 사용자가 함께 쓰는 클러스터의 권한 관리
- 특정 파드가 CPU, 메모리를 독차지하지 못하게 하는 자원 제한

앞으로 인그레스, 영구 볼륨(PV), 권한 관리(RBAC), 자원 사용량 제한, 스케줄링, 파드 라이프사이클, 애플리케이션 업데이트 방법을 차례로 다룹니다.

**인그레스란?** 외부에서 내부로 들어오는 요청을 네트워크 7계층(HTTP) 레벨에서 어떻게 처리할지 정의하는 쿠버네티스 오브젝트입니다. 서비스가 외부 요청을 받아들이는 통로였다면, 인그레스는 받은 요청을 어디로 어떻게 보낼지 정하는 규칙표라고 생각하면 됩니다. 기본 기능은 세 가지입니다.

- **외부 요청의 라우팅**: `/apple`, `/apple/red` 같은 경로별로 어떤 서비스로 보낼지 지정
- **가상 호스트 기반 요청 처리**: 같은 IP로 들어와도 도메인 이름에 따라 다르게 처리
- **SSL/TLS 보안 연결 처리**: 여러 서비스에 대한 인증서를 한곳에서 적용

## 8.1 인그레스를 사용하는 이유

디플로이먼트 A, B, C 세 개를 외부에 노출해야 한다고 해봅시다.

**인그레스 없이 (그림 8.1)**

- 디플로이먼트마다 NodePort나 LoadBalancer 서비스를 하나씩 만들어야 함
- 클라이언트는 서비스마다 다른 URL로 접근
- SSL/TLS, 도메인, 라우팅 같은 세부 설정을 서비스마다 일일이 해야 해서 관리가 번거로움

**인그레스 사용 (그림 8.2)**

- 외부 진입점은 인그레스의 URL 단 하나
- 요청은 인그레스에 정의된 규칙에 따라 알맞은 서비스(디플로이먼트)로 전달
- 라우팅, 인증서 같은 설정을 한 지점에서 관리

비유하자면, 인그레스 없이는 건물 각 사무실마다 따로 출입문을 내는 것이고, 인그레스는 정문 하나에 안내 데스크를 두고 방문객을 각 사무실로 안내하는 방식입니다. 핵심은 외부 요청 처리 규칙을 쿠버네티스 자체 기능으로 한곳에서 편하게 관리한다는 점입니다.

## 8.2 인그레스의 구조

인그레스는 `ingress` 또는 줄여서 `ing`로 조회합니다.

```bash
kubectl get ingress
kubectl get ing
```

### 인그레스 YAML 작성 (예제 8.1)

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ingress-example
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
  - host: alicek106.example.com        # [1]
    http:
      paths:
      - path: /echo-hostname           # [2]
        pathType: Prefix
        backend:
          service:
            name: hostname-service     # [3]
            port:
              number: 80
```

- **[1] host**: 이 도메인 이름으로 들어온 요청에만 규칙을 적용합니다. host는 여러 개 정의할 수 있습니다.
- **[2] path**: 이 경로로 들어온 요청을 backend의 서비스로 보냅니다. path도 여러 개 가능합니다.
- **[3] name, port**: 요청이 전달될 서비스 이름과 포트입니다. 즉 `/echo-hostname` 요청은 hostname-service의 80번 포트로 갑니다.
- **annotations**: 인그레스의 추가 기능을 설정하는 항목으로, 8.3에서 다룹니다.
- 참고로 쿠버네티스 1.14 이전에는 apiVersion이 `extensions/v1beta1`이었고, 지금은 `networking.k8s.io/v1`을 씁니다.

### 인그레스만으로는 아무 일도 일어나지 않는다

`kubectl apply`로 인그레스를 만들고 `kubectl get ingress`로 확인하면 목록에는 보이지만, 이것만으로는 요청이 처리되지 않습니다. 인그레스는 규칙을 적어둔 선언적 오브젝트일 뿐이고, 실제로 요청을 받는 서버가 아니기 때문입니다.

실제로 외부 요청을 받아 규칙대로 처리하는 것은 **인그레스 컨트롤러(Ingress Controller)** 라는 별도 서버입니다. 인그레스 컨트롤러가 인그레스 규칙을 읽어와(로드해) 사용합니다. 정리하면 이렇습니다.

- 인그레스: 규칙표 (무엇을 어디로 보낼지)
- 인그레스 컨트롤러: 규칙표를 보고 실제로 트래픽을 처리하는 서버

인그레스 컨트롤러 종류로는 Nginx 웹 서버 인그레스 컨트롤러(가장 대표적), Kong 같은 API 게이트웨이, GKE 등 클라우드 플랫폼이 제공하는 컨트롤러가 있고, 이 책은 Nginx를 사용합니다.

### Nginx 인그레스 컨트롤러 설치

공식 깃허브의 YAML 한 번으로 관련 리소스가 모두 설치됩니다.

```bash
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.12.1/deploy/static/provider/cloud/deploy.yaml
```

- `ingress-nginx` 네임스페이스가 생기고, 그 안에 Nginx 디플로이먼트, 서비스어카운트, 롤, 컨피그맵 등이 한꺼번에 생성됩니다.
- `kubectl get pods,deployment -n ingress-nginx`로 보면 `ingress-nginx-controller` 파드가 Running 상태입니다. admission 관련 파드 두 개는 설치 작업용 일회성 Job이라 Completed가 정상입니다.

### 인그레스 컨트롤러를 외부에 노출하는 서비스 (그림 8.5)

인그레스 컨트롤러도 결국 파드이므로, 외부에서 닿으려면 서비스가 필요합니다. 설치 시 `ingress-nginx-controller`라는 **LoadBalancer 타입 서비스**가 자동으로 생깁니다.

- **AWS, GKE 같은 클라우드**: LoadBalancer가 DNS 이름(AWS)이나 IP(GKE)를 자동으로 받습니다. 운영에서는 여기에 실제 도메인을 연결하는 것이 일반적입니다.
- **가상 머신 등 클라우드가 아닌 환경**: LoadBalancer 대신 NodePort 서비스를 만들어 사용합니다 (예제 8.2).

```yaml
apiVersion: v1
kind: Service
metadata:
  name: ingress-nginx-controller-nodeport
  namespace: ingress-nginx
spec:
  ports:
  - name: http
    nodePort: 31000
    port: 80
    protocol: TCP
    targetPort: http
  - name: https
    nodePort: 32000
    port: 443
    protocol: TCP
    targetPort: https
  selector:
    app.kubernetes.io/component: controller
    app.kubernetes.io/instance: ingress-nginx
    app.kubernetes.io/name: ingress-nginx
  type: NodePort
```

http는 31000, https는 32000 노드 포트로 열리고, selector로 Nginx 컨트롤러 파드를 가리킵니다.

- **온프레미스 운영**: MetalLB나 오픈스택의 로드 밸런서를 쓸 수도 있습니다.

### 테스트용 디플로이먼트와 서비스 생성

요청의 최종 도착지인 `hostname-deployment`와 `hostname-service`를 만듭니다. 이 서비스는 **ClusterIP 타입**입니다. 외부 노출은 인그레스 컨트롤러가 맡으므로 뒤쪽 서비스는 굳이 외부에 노출할 필요가 없기 때문입니다. (어떤 타입이든 동작은 하지만 ClusterIP가 권장됩니다.)

### 요청 보내보기와 404의 원인

LoadBalancer 주소로 `/echo-hostname`에 curl을 보내면 **404 Not Found**가 나옵니다. 인그레스에 `host: alicek106.example.com`을 지정했기 때문에, 그 도메인으로 들어온 요청만 처리하고 LB 주소 같은 다른 이름으로 들어온 요청은 무시하기 때문입니다.

해결 방법은 상황별로 다음과 같습니다.

- **curl의 `-resolve` 옵션**: 도메인을 임시로 특정 IP에 매핑
    
    ```bash
    curl --resolve alicek106.example.com:80:<부하 분산기 IP> alicek106.example.com/echo-hostname
    ```
    
- **`/etc/hosts` 수정**: 온프레미스나 GKE처럼 IP만 있을 때 `10.20.30.40 alicek106.example.com` 같은 줄을 추가
- **NodePort 환경**: 노드 IP와 31000 포트로 `-resolve` 사용 (방화벽, 보안 그룹에서 31000 포트가 열려 있어야 함)
- **AWS**: `kubectl edit ingress ingress-example`로 host 값을 LB의 DNS 이름으로 직접 수정

성공하면 `You accessed to path "/"`와 함께 응답한 컨테이너의 hostname, IP가 출력됩니다.

**최소 설정 인그레스 (예제 8.3)**: host, path를 꼭 써야 하는 것은 아닙니다. host를 빼고 path를 `/`로 두면 도메인과 상관없이 모든 요청을 hostname-service로 보냅니다. 다만 실무에서는 host, path를 쓰는 경우가 대부분입니다.

### 인그레스 컨트롤러의 동작 원리 이해

전체 구성(그림 8.6)과 사용 순서는 다음과 같습니다.

1. 공식 YAML로 Nginx 인그레스 컨트롤러를 생성
2. 컨트롤러를 외부에 노출할 서비스를 생성 (LoadBalancer 또는 NodePort)
3. 요청 처리 규칙을 담은 인그레스 오브젝트를 생성
4. 컨트롤러로 들어온 요청이 인그레스 규칙에 따라 알맞은 서비스로 전달

**3번에서 규칙이 자동 반영되는 이유**: 인그레스 컨트롤러는 쿠버네티스의 **Watch API**로 인그레스 리소스의 생성, 수정, 삭제를 계속 지켜보다가 변경이 생기면 Nginx 설정에 바로 반영합니다. 기본적으로 모든 네임스페이스의 인그레스를 읽어옵니다. Watch는 `kubectl get pods -w`처럼 직접 체험해 볼 수 있습니다.

**바이패스(bypass)**: 규칙상으로는 hostname-service로 보낸다고 적었지만, 실제로 Nginx는 서비스의 ClusterIP를 거치지 않습니다. 서비스가 만들어 둔 **엔드포인트(파드들의 실제 IP:포트)** 로 요청을 직접 보냅니다.

```bash
kubectl get endpoints
# hostname-service   192.168.1.246:5000,192.168.2.156:5000,192.168.3.173:5000
```

즉 서비스는 어느 파드들이 대상인지 알려주는 목록 역할만 하고, 실제 트래픽은 컨트롤러에서 파드로 곧장 갑니다.

## 8.3 인그레스의 세부 기능: annotation을 이용한 설정

인그레스는 YAML의 `annotations` 항목으로 다양한 옵션을 켤 수 있습니다. 앞에서 쓴 `nginx.ingress.kubernetes.io/rewrite-target`은 이름 그대로 **Nginx 인그레스 컨트롤러 전용** 기능입니다.

### rewrite-target: /

인그레스 경로로 들어온 요청을 지정한 경로로 바꿔서 전달합니다.

- `/echo-hostname` 요청은 hostname-service에 `/`로 전달됩니다.
- 단, `/echo-hostname`으로 시작하는 모든 요청이 `/`로 바뀝니다. `/echo-hostname/alice/bob`으로 보내도 서비스는 `/`를 받습니다.

### rewrite-target과 캡처 그룹 (예제 8.4)

캡처 그룹(Captured groups)은 정규 표현식의 괄호로 경로 일부를 잘라내 변수처럼 쓰는 방법입니다.

```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$2
spec:
  rules:
  - http:
      paths:
      - path: /echo-hostname(/|$)(.*)
        pathType: ImplementationSpecific
```

- 첫 번째 괄호 `(/|$)`가 `$1`, 두 번째 괄호 `(.*)`가 `$2`입니다.
- `/echo-hostname/` 뒤에 오는 나머지 경로를 `$2`로 잡아 전달합니다.
- 정규식 경로를 쓰므로 pathType이 `ImplementationSpecific`으로 바뀐 점도 눈여겨보세요.

결과는 다음과 같습니다.

- `/echo-hostname` 요청은 `/`로 전달
- `/echo-hostname/color` 요청은 `/color`로 전달
- `/echo-hostname/color/red` 요청은 `/color/red`로 전달

즉, 앞부분 접두사를 떼고 요청 경로를 다시 쓰는(rewrite) 것입니다. 실무에서 `/api/user/...` 요청을 user 서비스에 `/...`로 넘기는 식으로 자주 씁니다.

### 그 밖의 annotation

- **app-root**: 루트 경로(`/`)로 접근하면 특정 path로 리다이렉트
- **ssl-redirect**: http 요청을 https로 리다이렉트
- 전체 목록은 공식 문서(kubernetes.github.io/ingress-nginx/user-guide/nginx-configuration/annotations/)에서 확인

주의할 점은 이 annotation들이 Nginx 인그레스 컨트롤러에서만 동작한다는 것입니다. 다른 컨트롤러를 쓴다면 그 컨트롤러의 공식 문서를 따라야 합니다.

## 8.4 Nginx 인그레스 컨트롤러에 SSL/TLS 보안 연결 적용

인그레스의 큰 장점 중 하나는 뒤쪽 디플로이먼트, 서비스가 아니라 **앞단의 인그레스 컨트롤러에서 SSL/TLS를 한 번에 처리**할 수 있다는 점입니다. 컨트롤러에 인증서를 적용해 두면 뒤에 있는 모든 애플리케이션이 그 혜택을 받습니다. 그래서 인그레스 컨트롤러를 보안 연결을 위한 관문(Gateway)이라고도 합니다.

클라우드에서는 AWS ACM처럼 플랫폼이 관리하는 인증서를 LoadBalancer에 붙일 수도 있지만, 이 장에서는 직접 서명한 인증서로 기초를 익힙니다.

### 1단계: 인증서와 비밀키 생성

```bash
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout tls.key -out tls.crt -subj "/CN=alicek106.example.com/O=alicek106"
```

- `/CN`에는 인그레스 컨트롤러에 접근할 실제 도메인 이름을 넣어야 합니다.
- AWS의 동적 DNS를 쓴다면 `/CN=*.ap-northeast-2.elb.amazonaws.com`처럼 와일드카드도 가능합니다.
- 결과로 비밀키 `tls.key`와 인증서 `tls.crt`가 생깁니다.

### 2단계: tls 타입 시크릿 생성

```bash
kubectl create secret tls tls-secret --key tls.key --cert tls.crt
```

### 3단계: 인그레스에 tls 항목 추가 (예제 8.5)

```yaml
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - alicek106.example.com
    secretName: tls-secret
  rules:
  - host: alicek106.example.com
    ...
```

- `spec.tls.hosts`: 보안 연결을 적용할 도메인
- `spec.tls.secretName`: 앞에서 만든 tls 시크릿 이름

즉, alicek106.example.com으로 들어오는 요청은 tls-secret의 인증서로 보안 연결을 맺겠다는 뜻입니다.

### 4단계: 확인

```bash
curl https://alicek106.example.com/echo-hostname -k
```

- `k`는 신뢰할 수 없는(직접 서명한) 인증서를 허용하는 옵션입니다.
- https로 정상 응답이 옵니다.
- http로 접근하면 **308 Permanent Redirect**가 돌아옵니다. TLS가 적용된 인그레스에는 Nginx 컨트롤러가 `ssl-redirect` annotation을 자동으로 true로 설정해 https로 리다이렉트하기 때문입니다.

## 8.5 여러 개의 인그레스 컨트롤러 사용하기

하나의 클러스터에 인그레스 컨트롤러를 여러 개 둘 수 있고, 어떤 인그레스 규칙을 어떤 컨트롤러가 처리할지는 **인그레스 클래스(IngressClass)** 로 정합니다. 지금까지 썼던 `ingressClassName: nginx`가 바로 이것입니다.

nginx라는 인그레스 클래스는 Nginx 컨트롤러 설치 시 자동으로 생성됩니다. 설치 YAML(deploy.yaml)을 내려받아 보면 확인할 수 있습니다.

- 컨트롤러 디플로이먼트 실행 인자에 `-ingress-class=nginx`, `-controller-class=k8s.io/ingress-nginx`가 있음
- 같은 파일 안에 아래 IngressClass 리소스도 함께 정의됨

```yaml
apiVersion: networking.k8s.io/v1
kind: IngressClass
metadata:
  name: nginx
spec:
  controller: k8s.io/ingress-nginx
```

```bash
kubectl get ingressclass
# NAME    CONTROLLER             PARAMETERS   AGE
# nginx   k8s.io/ingress-nginx   <none>       79m
```

연결 관계를 정리하면 다음과 같습니다.

- 인그레스 YAML의 `ingressClassName: nginx`
- nginx 인그레스 클래스는 `k8s.io/ingress-nginx` 컨트롤러를 가리킴
- Nginx 컨트롤러는 자신이 nginx 클래스를 담당한다고 설정되어 있음
- 그래서 이 인그레스 규칙은 Nginx 컨트롤러에 적용됨

같은 원리로 `ingressClassName`에 Kong 같은 다른 컨트롤러의 클래스 이름을 쓰면 해당 컨트롤러에 규칙이 적용됩니다. 인그레스 클래스로 어떤 컨트롤러를 쓸지 유연하게 지정할 수 있는 것입니다.

## 한 줄 요약

인그레스는 규칙표, 인그레스 컨트롤러는 그 규칙을 실행하는 서버이고, 외부 요청은 LB/NodePort 서비스, 인그레스 컨트롤러, 엔드포인트(파드) 순으로 흘러갑니다. 라우팅, rewrite, TLS를 모두 이 앞단 한곳에서 처리하는 것이 핵심입니다.

참고로 실무 동향을 덧붙이면, 쿠버네티스 커뮤니티는 2025년 말에 ingress-nginx 프로젝트의 은퇴를 발표했고 후속 표준으로 Gateway API를 밀고 있습니다. 책의 개념(규칙과 컨트롤러 분리, 클래스로 컨트롤러 선택)은 Gateway API에도 그대로 이어지니, 이 장의 원리를 확실히 이해해 두면 나중에 넘어가기 수월합니다.
