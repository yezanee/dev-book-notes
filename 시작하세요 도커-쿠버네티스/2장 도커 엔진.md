## 2.1 이미지와 컨테이너

### **2.1.1 도커 이미지**

- 컨테이너를 만들 때 쓰는 원본으로, VM의 iso 파일과 비슷한 개념입니다.
- 여러 계층으로 된 바이너리이고 **읽기 전용**입니다.
- 이름 형식은 `[저장소]/[이미지명]:[태그]`입니다.
    - 저장소를 생략하면 도커 허브 공식 이미지로 인식합니다.
    - 이미지명은 생략할 수 없습니다.
    - 태그를 생략하면 `latest`로 인식합니다.

### **2.1.2 도커 컨테이너**

- 이미지로 만든 격리된 공간으로, 파일 시스템, 자원, 네트워크가 분리됩니다.
- 이미지와 컨테이너는 **1:N 관계**입니다.
- 변경사항은 컨테이너 계층에만 저장되므로 원본 이미지는 절대 바뀌지 않습니다.

## 2.2 도커 컨테이너 다루기

### 2.2.1 컨테이너 생성

- `docker run -i -t`에서 `i`는 상호 입출력, `t`는 tty입니다. 둘 중 하나라도 빠지면 셸을 정상적으로 쓸 수 없습니다.
- 로컬에 이미지가 없으면 도커 허브에서 자동으로 pull합니다.
- 컨테이너의 기본 사용자는 root이고, 호스트 이름은 컨테이너 ID 앞부분입니다.
- 컨테이너에서 빠져나오는 방법은 두 가지입니다.
    - `exit` 또는 `Ctrl+D`: 컨테이너가 **정지**되면서 나옵니다.
    - `Ctrl+P, Q`: 컨테이너를 **정지하지 않고** 나옵니다.
- **run과 create의 차이**
    - `run` = pull(없을 때) → create → start → attach(-it 사용 시)
    - `create` = pull(없을 때) → create까지만 하고 들어가지 않습니다.
- 그 외 명령어로는 `docker pull`, `docker images`, `docker start`, `docker attach`가 있습니다.
- 컨테이너 ID는 앞 3~4자리만 입력해도 됩니다. 단, 앞자리가 겹치는 컨테이너가 있으면 에러가 납니다.

### 2.2.2 컨테이너 목록 확인

- `docker ps`는 실행 중인 컨테이너만, `docker ps -a`는 정지된 것까지 전부 보여줍니다.
- 출력 항목
    - CONTAINER ID: 전체 ID는 `docker inspect`로 확인합니다.
    - IMAGE: 생성에 사용한 이미지입니다.
    - COMMAND: 시작 시 실행되는 명령어로, 이미지에 내장되어 있습니다. run이나 create 끝에 명령어를 쓰면 **덮어씁니다**. 예를 들어 `echo hello`로 덮으면 bash가 실행되지 않아 출력 후 바로 종료됩니다.
    - STATUS: Up(실행 중), Exited(종료), Pause(일시정지)
    - PORTS: 개방 포트와 호스트 연결 포트
    - NAMES: `-name`을 주지 않으면 형용사_명사 형태로 무작위 생성됩니다. 중복은 불가하고 `docker rename`으로 바꿀 수 있습니다.
- 출력이 너무 길면 `-format "table {{.ID}}\t{{.Status}}"`처럼 Go 템플릿으로 원하는 항목만 볼 수 있습니다.

### 2.2.3 컨테이너 삭제

- `docker rm`을 쓰며, 삭제한 컨테이너는 복구할 수 없습니다.
- 실행 중인 컨테이너는 바로 지울 수 없습니다. `stop` 후 `rm`을 하거나 `rm -f`로 강제 삭제합니다.
- `docker container prune`: 정지된 컨테이너를 모두 삭제합니다.
- `docker ps -a -q`에서 `a`는 전체, `q`는 ID만 출력입니다.
    - `docker stop $(docker ps -a -q)`
    - `docker rm $(docker ps -a -q)`

### 2.2.4 컨테이너를 외부에 노출

- 컨테이너는 기본적으로 **172.17.0.x** IP를 순차적으로 받고, eth0과 lo 인터페이스를 가집니다.
- 아무 설정이 없으면 외부에서 접근할 수 없고 호스트에서만 접근할 수 있습니다. (Docker Desktop for Mac은 호스트에서도 불가)
- `p [호스트 포트]:[컨테이너 포트]`로 포트를 바인딩합니다.
    - 특정 호스트 IP 지정: `p 192.168.0.100:7777:80`
    - 여러 포트 개방: `p`를 여러 번 씁니다.
    - `p 80`처럼 컨테이너 포트만 쓰면 호스트 포트가 무작위로 잡히므로 `docker ps`나 `docker port`로 확인해야 합니다.
- 흐름: 호스트 IP:80 접근 → 컨테이너 80번 포트로 포워딩 → 웹 서버
- `80:81`처럼 실제 서비스하지 않는 컨테이너 포트로 연결하면 접근할 수 없습니다.
- ubuntu:24.04에는 ifconfig가 없어서 `net-tools`를 따로 설치해야 합니다.

### 2.2.5 컨테이너 애플리케이션 구축

- **한 컨테이너에 한 프로세스**가 도커의 철학입니다. DB와 웹 서버는 분리된 컨테이너로 구성하는 것을 권장합니다.
- `d` (Detached 모드)
    - 컨테이너를 백그라운드로 실행합니다.
    - 컨테이너 안에서 **포그라운드 프로그램이 반드시 실행 중이어야** 하며, 없으면 바로 종료됩니다. ubuntu를 `d`로만 실행하면 Exited(0)이 됩니다.
    - 반대로 mysql을 `it`로 실행하면 mysqld 로그만 보이고 입력은 불가능합니다.
    - `i -t -d`를 함께 쓰면 셸은 실행되지만 내부로 들어가지 않고, 컨테이너도 종료되지 않습니다. 테스트용으로 유용합니다.
- `e`: 컨테이너 내부 환경변수를 설정합니다. 비밀번호 같은 민감 정보는 환경변수보다 secret 기능을 쓰는 것이 바람직합니다.
- `docker exec`: 실행 중인 컨테이너 내부에서 명령어를 실행합니다.
    - `docker exec -it [컨테이너] /bin/bash`로 셸에 들어갈 수 있습니다.
    - exec로 들어간 경우에는 `exit`해도 컨테이너가 종료되지 않습니다. 메인 프로세스가 계속 돌고 있기 때문입니다.
    - `d`로 실행한 컨테이너에 `attach`하면 실행 중인 프로그램 출력만 보게 되므로 의미가 없습니다.
- `-link [컨테이너]:[별명]`
    - 내부 IP는 재시작할 때마다 바뀔 수 있으므로 별명(alias)으로 접근하게 해줍니다.
    - 연결 대상 컨테이너가 실행 중이 아니면 에러가 납니다. 즉, **실행 순서 의존성**도 정의합니다.
    - **deprecated** 옵션이므로 브리지 네트워크 사용을 권장합니다.
- start, stop, restart는 여러 컨테이너 이름을 나열해서 한 번에 실행할 수 있습니다.

### 2.2.6 도커 볼륨

- 이미지는 읽기 전용, 컨테이너 레이어는 쓰기 가능입니다. 그래서 **컨테이너를 삭제하면 데이터도 사라집니다**. 이를 막는 방법이 볼륨입니다.
- 볼륨 활용 방법은 세 가지입니다.

**1) 호스트 볼륨 공유**

- `v [호스트 경로]:[컨테이너 경로]`
- 호스트에 디렉터리가 없으면 자동으로 생성합니다.
- 동기화가 아니라 **완전히 같은 디렉터리**입니다. 즉, 마운트입니다.
- 호스트 디렉터리가 이미 있으면 컨테이너의 기존 디렉터리를 **덮어씁니다**.
- 파일 단위 공유도 가능하고, `v`를 여러 개 쓸 수 있습니다.

**2) 볼륨 컨테이너**

- `-volumes-from [컨테이너]`
- `v`를 적용한 컨테이너를 통해 볼륨을 **간접적으로** 공유받습니다.
- 볼륨 공유만 담당하는 컨테이너로 활용할 수 있습니다.

**3) 도커 볼륨**

- `docker volume create --name myvolume`, `docker volume ls`
- `v [볼륨 이름]:[컨테이너 경로]` 형식으로 씁니다.
- 기본 드라이버는 `local`이며, 실제 위치는 `/var/lib/docker/volumes/[볼륨명]/_data`입니다. 사용자가 알 필요는 없습니다.
- `docker inspect --type volume [볼륨명]`으로 정보를 확인합니다.
- `v /root`처럼 컨테이너 경로만 주면 16진수 이름의 볼륨이 자동 생성됩니다.
- 컨테이너를 삭제해도 볼륨은 남으므로 `docker volume prune`으로 정리합니다.

**기타**

- `-mount` 옵션도 같은 기능입니다.
    - 도커 볼륨: `-mount type=volume,source=myvolume,target=/root`
    - 호스트 경로: `-mount type=bind,source=/home/...,target=/...`
- `docker container inspect`, `docker volume inspect`처럼 접두어로 대상을 명시할 수 있습니다.
- **스테이트리스**: 데이터는 외부에 두고 컨테이너는 상태를 갖지 않는 설계로, 권장됩니다.
- **스테이트풀**: 컨테이너 자체에 데이터를 저장하는 설계로, 지양합니다.

### 2.2.7 도커 네트워크

**구조**

- 연결 흐름: 컨테이너 eth0 ↔ 호스트 veth ↔ docker0 브리지 ↔ 호스트 eth0
- veth는 virtual eth의 약자입니다. 컨테이너마다 하나씩 도커 엔진이 자동으로 생성합니다.
- docker0 브리지는 veth와 호스트 eth0을 이어주는 역할을 합니다. `brctl show docker0`으로 확인할 수 있습니다.

**드라이버 종류**

- 기본 제공: bridge, host, none, container, overlay
- 서드파티: weave, flannel, openvswitch
- `docker network ls`를 하면 bridge, host, none이 기본으로 존재합니다.
- 기본 bridge는 서브넷 172.17.0.0/16, 게이트웨이 172.17.0.1입니다. `docker network inspect`로 확인합니다.

**브리지 네트워크**

- `docker network create --driver bridge mybridge`로 만들고, `-net mybridge`로 연결합니다.
- 새로 만든 브리지는 다음 대역(172.18.x)을 차례로 할당받습니다.
- `docker network connect / disconnect`로 유동적으로 붙이고 뗄 수 있습니다. 단, **bridge, overlay에서만 가능**하고 none, host에서는 불가합니다.
- `-subnet`, `-ip-range`, `-gateway`로 대역을 지정할 수 있으며, subnet과 ip-range는 같은 대역이어야 합니다.

**호스트 네트워크** (`--net host`)

- 호스트 네트워크 환경을 그대로 사용하고, 호스트 이름도 호스트와 같아집니다.
- 포트 포워딩 없이 바로 서비스할 수 있습니다.

**논 네트워크** (`--net none`)

- 네트워크를 쓰지 않으며, lo만 존재합니다.

**컨테이너 네트워크** (`--net container:[ID]`)

- 다른 컨테이너의 네트워크 네임스페이스를 공유합니다. 내부 IP와 MAC 주소가 같아집니다.
- 새 IP를 받지 않고, veth도 생성되지 않습니다.
- **-net-alias**
- **사용자 정의 브리지**에서 사용합니다.
- 내장 DNS 서버(**127.0.0.11**)가 별명을 해당 컨테이너 IP들로 변환합니다.
- 같은 별명을 가진 컨테이너가 여럿이면 **라운드 로빈** 방식으로 IP 목록 순서를 바꿔서 반환합니다.
- `dig`로 확인할 수 있습니다. (dnsutils 설치 필요)
- 참고로 `-link`는 디폴트 브리지 네트워크의 DNS를 사용합니다.

**MacVLAN**

- 호스트의 NIC를 가상화해서 컨테이너가 물리 네트워크상에서 **가상 MAC 주소**를 갖게 합니다.
- 172.17.x.x 대신 실제 네트워크 장비(라우터, 스위치)의 대역 IP를 할당받아, 같은 네트워크의 다른 장비와 직접 통신할 수 있습니다.
- MacVLAN을 쓰는 컨테이너는 같은 IP 대역을 쓰는 다른 서버나 컨테이너와 통신할 수 있습니다.
- 단, **기본적으로 호스트와는 통신할 수 없습니다**. 예를 들어 서버 1의 컨테이너 A는 서버 2와는 통신되지만 자기 호스트인 서버 1과는 통신되지 않습니다.
- 생성: `docker network create -d macvlan ...`
- 주요 옵션
    - `d`: 드라이버 지정으로, `-driver`와 같습니다.
    - `-subnet`: 컨테이너가 쓸 네트워크 대역입니다. 네트워크 장비의 대역을 그대로 따릅니다.
    - `-ip-range`: 해당 호스트에서 컨테이너에 할당할 IP 범위입니다. 여러 호스트의 범위가 **겹치면 안 됩니다**. 예를 들어 /28이면 2⁴ = 16개 IP를 쓸 수 있습니다.
    - `-gateway`: 네트워크 장비의 게이트웨이입니다.
    - `o macvlan_mode=bridge`: MacVLAN을 bridge 모드로 사용합니다.
    - `o parent=eth0`: 부모 네트워크 인터페이스를 지정합니다.
- 핵심은 **bridge 모드 사용**과 **부모 인터페이스 지정이 필요하다**는 두 가지입니다.

### 2.2.8 컨테이너 로깅

#### json-file (기본 로깅 드라이버)

- 도커는 컨테이너의 **StdOut과 StdErr**를 별도 메타데이터 파일로 저장합니다.
- `docker logs [컨테이너]`로 확인합니다.
    - `d`로 실행해서 attach할 수 없는 컨테이너도 로그로 상태를 볼 수 있습니다.
    - 예를 들어 mysql을 `e` 없이 실행하면 컨테이너가 시작되지 않는데, `docker logs`로 환경변수 누락 에러를 바로 확인할 수 있습니다.
- 옵션
    - `-tail N`: 마지막 N줄만 출력합니다.
    - `-since [유닉스 시간]`: 특정 시간 이후 로그만 출력합니다.
    - `t`: 타임스탬프를 표시합니다.
    - `f`: 실시간 스트림으로 출력하며, 개발할 때 유용합니다.
- `it`로 실행한 컨테이너는 bash에서 입출력한 내용도 로그에 남습니다.
- 저장 위치: `/var/lib/docker/containers/${CONTAINER_ID}/${CONTAINER_ID}-json.log`
- 로그를 방치하면 json 파일이 계속 커져서 호스트 저장 공간을 다 쓸 수 있습니다. 그래서 `-log-opt`로 크기를 제한합니다.
    - `max-size`: 로그 파일 최대 크기입니다. 기본값은 무제한(-1)이고 k, m, g 단위를 씁니다.
    - `max-file`: 로그 파일 개수입니다. 기본값은 1입니다.
- 로깅 드라이버 종류: json-file(기본), syslog, journald, fluentd, awslogs 등이 있습니다.
- 도커 데몬 시작 옵션에 `-log-driver`나 `-log-opt`를 넣으면 모든 컨테이너에 일괄 적용됩니다.

#### syslog

- 유닉스 계열 OS에서 로그를 수집하는 오래된 표준입니다. 인터페이스가 동일해서 체계적으로 수집하고 분석할 수 있습니다.
- `-log-driver=syslog`를 쓰면 기본적으로 로컬호스트의 syslog에 저장됩니다. 우분투 24.04에서는 `/var/log/syslog` 또는 `journalctl -u docker.service`로 확인합니다.
- **rsyslog**로 원격 중앙 서버에 로그를 저장할 수 있습니다.
    - 서버 쪽: rsyslog 컨테이너를 514 포트(tcp, udp)로 띄우고 rsyslog.conf에서 수신 설정을 활성화합니다.
    - 클라이언트 쪽 `-log-opt`
        - `syslog-address=tcp://[서버IP]:514`: 원격 주소이며 udp도 가능합니다.
        - `tag`: 로그를 분류하는 태그입니다.
        - `syslog-facility`: 로그를 생성하는 주체별로 저장 파일을 나눕니다. 기본값은 daemon이고 kern, user, mail 등이 있습니다.
- 별도 UI는 없지만 logentries, LogAnalyzer 같은 분석기와 연동할 수 있습니다.
- 컨테이너로 구현하면 호스트 OS와 관계없이 쓸 수 있다는 장점이 있습니다.

#### fluentd

- 로그를 수집하고 저장하는 오픈소스 도구로, 도커가 공식 플러그인을 제공합니다.
- 데이터 포맷이 **JSON**이고, AWS S3, HDFS, MongoDB 등 다양한 저장소에 저장할 수 있습니다.
- 흐름: 도커 서버 → fluentd 서버 → MongoDB
- fluent.conf의 `<match docker.**>`는 태그가 docker로 시작하는 로그를 매칭해서 MongoDB로 보낸다는 의미입니다.
- fluentd 기본 포트는 **24224**입니다.
- 사용법: `-log-driver=fluentd --log-opt fluentd-address=[IP]:24224 --log-opt tag=docker.xxx`
- 공식 fluentd 이미지에는 MongoDB 플러그인이 없어서 별도로 설치해야 합니다.

#### 아마존 클라우드워치 (awslogs)

- AWS EC2에서 도커를 쓰면 별도 도구 설치 없이 드라이버 옵션만으로 사용할 수 있습니다.
- 절차는 4단계입니다.
    1. 클라우드워치용 IAM 역할 생성 (신뢰할 수 있는 엔터티: AWS 서비스 → EC2, 권한: CloudWatchFullAccess)
    2. 로그 그룹 생성
    3. 로그 그룹 안에 로그 스트림 생성
    4. EC2 인스턴스에 IAM 역할 연결 후 로그 전송
- 실무에서는 FullAccess가 아니라 **필요한 권한만** 부여해야 합니다.
- 옵션: `-log-driver=awslogs`, `awslogs-region`, `awslogs-group`, `awslogs-stream`
- region은 EC2 인스턴스 리전이 아니라 **로그 그룹이 생성된 리전**입니다. 서울은 ap-northeast-2입니다.

### 2.2.9 컨테이너 자원 할당 제한

- 옵션을 주지 않으면 컨테이너는 호스트 자원을 **제한 없이** 씁니다. 그러면 다른 컨테이너뿐 아니라 호스트까지 멈출 수 있습니다.
- 설정값은 `docker inspect`의 HostConfig에서 확인합니다.
- 실행 중인 컨테이너의 제한을 바꾸려면 `docker update [옵션] [컨테이너]`를 씁니다.

#### 메모리 제한

- `-memory`: 단위는 m, g이고 **최소 6MB**입니다.
- 할당된 메모리를 초과하면 컨테이너가 **자동으로 종료**됩니다.
- `-memory-swap`: Swap은 기본적으로 메모리의 **2배**로 설정되지만 별도로 지정할 수 있습니다.

#### CPU 제한

- `-cpu-shares`
    - 가중치 기반의 **상대값**입니다. 기본값은 **1024**이고, 이는 1의 비중을 뜻합니다.
    - 다른 컨테이너가 없으면 100%를 씁니다.
    - 1024와 512 컨테이너가 같이 돌면 약 2:1로 나눠 씁니다.
- `-cpuset-cpus`
    - 특정 CPU만 사용하도록 지정합니다. 번호는 0부터 시작합니다.
    - `=2`는 3번째 CPU, `"0,3"`은 1번과 4번째, `"0-2"`는 1~3번째 CPU입니다.
- `-cpu-period`, `-cpu-quota`
    - CFS(Completely Fair Scheduler) 주기는 기본 100ms(100000)입니다.
    - 컨테이너는 **quota / period** 만큼 CPU 시간을 받습니다.
    - 예: period=100000, quota=25000이면 1/4 성능입니다.
- `-cpus`
    - CPU 개수를 직관적으로 지정합니다.
    - `-cpus=0.5`는 `-cpu-period=100000 --cpu-quota=50000`과 같습니다.
- CPU 집약적인 병렬 워크로드에는 **-cpuset-cpus**가 유리합니다. CPU 친화성(Affinity)을 보장해서 캐시 미스와 컨텍스트 스위칭을 줄일 수 있기 때문입니다.

## 2.3 도커 이미지

- 기본 저장소는 **도커 허브**입니다. create, run, pull 시 도커 허브에서 검색해서 내려받습니다.
- 공식(Official) 라벨이 없는 이미지는 제대로 동작하지 않을 수 있습니다.
- 비공개 저장소는 유료이며, 대안으로 사설 레지스트리를 직접 구축할 수 있습니다.
- `docker search [키워드]`: 도커 허브에서 이미지를 검색합니다. STARS는 즐겨찾기 수입니다.
- 접두어를 생략하면 도커 허브(docker.io)이고, gcr.io 같은 다른 레지스트리와 구분하기 위해 접두어를 씁니다.

#### 2.3.1 이미지 생성

- `docker commit [OPTIONS] CONTAINER [REPOSITORY[:TAG]]`
    - `a`: author, 작성자 메타데이터입니다.
    - `m`: 커밋 메시지입니다.
- 태그를 생략하면 latest입니다.

#### 2.3.2 이미지 구조

- `docker inspect`의 **Layers** 항목으로 구조를 확인합니다.
- 커밋하면 컨테이너에서 **변경된 사항만 새 레이어로 저장**하고, 기존 레이어를 공유하면서 새 이미지를 만듭니다.
    - 예: ubuntu → first(레이어 +1) → second(레이어 +1)
    - docker images에서 세 이미지가 각각 78.1MB로 보여도, 실제 전체 크기는 78.1MB + first 파일 + second 파일입니다.
- `docker history [이미지]`: 이미지가 어떤 레이어로 만들어졌는지 보여줍니다.
- inspect는 이름이 겹치면 컨테이너를 먼저 조회하므로 `-type`을 명시하는 게 좋습니다.

#### 이미지 삭제

- `docker rmi [이미지]`
- 사용 중인 컨테이너가 있으면 삭제할 수 없습니다. `rmi -f`로 강제 삭제해도 레이어는 남고 이름만 지워지므로 의미가 없습니다. 컨테이너를 먼저 삭제해야 합니다.
- 강제 삭제하면 이미지 이름이 `<none>`이 되는데, 이를 **댕글링(dangling) 이미지**라고 합니다.
    - 조회: `docker images -f dangling=true`
    - 일괄 삭제: `docker image prune`
- 출력 의미
    - `Untagged`: 이미지에 부여된 **이름만** 삭제됨
    - `Deleted`: 레이어가 **실제로** 삭제됨
- 하위 이미지가 남아 있으면 상위 이미지를 rmi해도 레이어는 삭제되지 않습니다. 부모 이미지가 존재하지 않아야 실제 파일이 삭제됩니다. 반대로 second를 지워도 다른 태그가 가리키는 ubuntu 레이어는 남습니다.

#### 2.3.3 이미지 추출

- **save / load**
    - `docker save -o xxx.tar [이미지]`: 커맨드, 이름, 태그 등 **모든 메타데이터 포함**해서 추출합니다.
    - `docker load -i xxx.tar`: 완전히 동일한 이미지로 복원합니다.
- **export / import**
    - `docker export -o xxx.tar [컨테이너]`: 컨테이너의 **파일 시스템만** tar로 추출하고, 설정 정보는 저장하지 않습니다.
    - `docker import xxx.tar [이미지명]`
- 차이를 정리하면 save는 이미지 대상이고 메타데이터를 포함하며, export는 컨테이너 대상이고 파일 시스템만 담습니다. 참고로 commit은 detached 모드, 커맨드 같은 컨테이너 설정도 이미지에 저장합니다.
- 단점: 단일 파일이라 레이어 구조를 활용하지 못합니다. 이미지 여러 개를 추출하면 용량을 각각 차지합니다.

#### 2.3.4 이미지 배포

- 파일 배포는 비효율적이라 두 가지 방법을 씁니다.
    - **도커 허브**: 간편하지만 비공개 저장소 수에 제한이 있고 무료는 1개입니다.
    - **사설 레지스트리**: 직접 관리해야 해서 번거롭지만 사내망 배포에 적합합니다.

**도커 허브 저장소**

- 저장소 이름은 `[계정명]/[이미지명]`입니다.
- 공개(public)는 누구나 search/pull 할 수 있고, 비공개(private)는 권한 있는 계정만 가능합니다.
- 올리는 순서
    1. `docker tag [기존 이미지] [계정명/이미지:태그]`: 이름을 **추가**하는 것이며 기존 이름은 사라지지 않습니다.
    2. `docker login -u [ID]`: 로그인 정보는 `~/.docker/config.json`에 저장되고, `docker logout`으로 삭제합니다.
    3. `docker push [계정명/이미지:태그]`
- push 시 **이미 저장소에 있는 레이어는 전송하지 않습니다** (Mounted from library/ubuntu).
- 이미지에 아키텍처 정보가 있지만, pull 시 호스트 CPU 아키텍처에 맞는 이미지를 자동으로 받으므로 신경 쓸 필요가 없습니다.
- 비공개 저장소에서 다른 계정에 권한을 주려면 **Collaborators**에 추가합니다. Collaborator는 push도 가능합니다.

**도커 사설 레지스트리**

- 레지스트리 자체가 컨테이너로 구현되며, 공식 이미지 `registry:2.x`를 씁니다. 1.x는 쓰지 않습니다.
- 기본 포트는 **5000**이고 RESTful API를 제공합니다. 확인은 `curl localhost:5000/v2/`로 합니다.
- `-restart` 정책
    - `always`: 정지될 때마다 재시작하고, 도커 엔진이 재시작해도 함께 시작됩니다.
    - `on-failure:5`: 종료 코드가 0이 아닐 때 최대 5번 재시작을 시도합니다.
    - `unless-stopped`: stop으로 정지했다면 엔진이 재시작해도 시작하지 않습니다.
- push 방법: 이미지 접두어를 `[호스트IP]:5000/` 형태로 tag한 뒤 push합니다. 도메인을 써도 됩니다.
- 도커 데몬은 기본적으로 **HTTPS가 아닌 레지스트리에 접근을 막습니다**.
    - 테스트용으로는 데몬 시작 옵션에 `-insecure-registry=[IP]:5000`을 추가하고 재시작합니다.
    - pull도 같은 플래그가 필요합니다.
- 레지스트리 컨테이너는 내부 디렉터리에 **도커 볼륨**을 만들어서 push된 이미지를 저장합니다.
    - 컨테이너를 삭제해도 볼륨은 남습니다.
    - 함께 지우려면 `docker rm --volumes [컨테이너]`를 씁니다.
- insecure-registry만으로는 인증 없이 누구나 push/pull이 가능합니다. 그래서 **Nginx 서버 컨테이너**와 연동해서 로그인 기반 접근 제한을 겁니다.

**Nginx로 접근 권한 생성**

- 로그인 인증은 insecure 레지스트리에서는 쓸 수 없습니다. 그래서 **Self-Signed 인증서로 TLS를 적용**합니다. 신뢰할 수 있는 인증서가 있다면 그걸 써도 됩니다.
- 전체 흐름
    1. openssl로 ROOT 인증서(CA) 생성: ca.key, ca.crt
    2. 레지스트리용 키와 CSR(인증서 서명 요청) 생성 후, ROOT 인증서로 서명해서 domain.crt 발급
    3. `htpasswd`로 로그인 계정/비밀번호 파일 생성 (우분투는 apache2-utils, CentOS는 httpd-tools)
    4. nginx.conf 작성: SSL 인증 파일 위치와 레지스트리로의 **프록시(Proxy)** 설정
    5. 레지스트리 컨테이너는 `p` 없이 생성. 실제 프런트엔드는 Nginx라서 외부에 노출할 필요가 없습니다.
    6. Nginx 컨테이너를 443 포트로 띄우고 `-link`로 레지스트리 연결, `v`로 인증서 디렉터리 공유
- 처음 `docker login https://[IP]`를 하면 **certificate signed by unknown authority** 에러가 납니다. Self-signed 인증서는 신뢰할 수 없기 때문입니다.
    - 해결: ca.crt를 시스템의 신뢰할 수 있는 인증서 목록에 추가하고 도커를 재시작합니다.
        - 우분투: `/usr/local/share/ca-certificates/`에 복사 후 `update-ca-certificates`
        - CentOS: `/etc/pki/ca-trust/source/anchors/`에 복사 후 `update-ca-trust`
- https로 로그인했으므로 이미지 접두어에 **포트 없이 IP만** 쓰면 됩니다. 자동으로 443으로 연결되기 때문입니다.

**사설 레지스트리 RESTful API**

- 레지스트리는 별도 CLI가 없어서 **RESTful API**로 제어합니다. 기본 5000번 포트입니다.
- Nginx 인증을 걸었다면 curl에 `u 계정:비밀번호`와 https를 사용합니다.
- 주요 API
    - `/v2/_catalog`: 저장된 이미지 목록 (이름만, 태그는 안 나옴)
    - `/v2/(이미지)/tags/list`: 특정 이미지의 태그 목록
    - `/v2/(이미지)/manifests/(태그)`: 이미지 상세 정보
- **매니페스트(manifest)**: 레지스트리에 저장된 이미지 정보의 묶음입니다.
    - 형식은 스키마 버전 1, 2가 있습니다. 헤더에 `Accept: application/vnd.docker.distribution.manifest.v2+json`을 넣으면 버전 2, 안 넣으면 버전 1이 나옵니다.
- 이미지는 **매니페스트 + 레이어 바이너리 파일**로 나뉘고, 각각을 고유하게 식별하는 ID가 **다이제스트(Digest)**입니다.

**이미지 삭제 (API)**

- 매니페스트와 레이어 파일을 **따로** 삭제해야 합니다.
    - 매니페스트: `DELETE /v2/(이미지)/manifests/(매니페스트 다이제스트)` (Docker-Content-Digest 값 사용)
    - 레이어: `DELETE /v2/(이미지)/blobs/(레이어 다이제스트)` (매니페스트의 Layers에서 확인)
- 그냥 호출하면 **UNSUPPORTED** 에러가 납니다. 삭제 기능이 기본 비활성화(false)이기 때문입니다.
    - 해결: `e REGISTRY_STORAGE_DELETE_ENABLED=true`로 레지스트리를 생성합니다.
- 성공하면 **202 Accepted**가 반환됩니다.
- 매니페스트만 지우면 레이어 파일은 남아 있어서, 같은 이미지를 다시 push하면 **Layer Already Exist**가 출력됩니다.
- 도메인을 **localhost**로 쓰면 `-insecure-registry` 설정 없이도 push할 수 있습니다. 도커 엔진이 기본적으로 127.0.0.0/8을 insecure 목록에 넣어두기 때문입니다. (`docker info`로 확인)

**레지스트리 옵션 설정**

- 레지스트리는 **컨테이너 환경변수**로 설정합니다. 삭제 기능, 스토리지 백엔드, 저장 디렉터리, 웹훅, Notification, S3/Azure 드라이버 등이 있습니다.
- 로그인과 인증서 기능도 환경변수로 설정할 수 있고, 이 경우 레지스트리가 자체적으로 인증합니다.
- 매번 `e`를 쓰는 대신 **yml 파일**로 설정할 수 있습니다.
    - 기본 위치: 컨테이너 내부 `/etc/docker/registry/config.yml`
    - `v`로 직접 작성한 config.yml을 덮어씌워 적용합니다.
    - `http.addr`은 반드시 명시해야 합니다.
- rootdirectory 기본값은 `/var/lib/registry`입니다.
- 환경변수와 yml의 관계: `REGISTRY_` 접두어 + 상위 항목을 포함한 이름으로 같은 설정을 표현합니다. 예를 들어 `REGISTRY_STORAGE_FILESYSTEM_ROOTDIRECTORY`는 yml의 storage → filesystem → rootdirectory와 같습니다.

## 2.4 Dockerfile

#### 2.4.1 이미지를 생성하는 방법

- **방법 1 (commit)**: 빈 이미지로 컨테이너 생성 → 환경 설치와 소스 복사 → 커밋
    - 동작은 보장되지만 수작업이 많습니다.
- **방법 2 (Dockerfile)**: 필요한 작업을 파일에 기록하고 **build** 명령어로 자동 생성
    - 반복 작업의 번거로움이 줄고, 깃 같은 도구로 빌드와 배포를 자동화할 수 있습니다.
    - 이미지 대신 Dockerfile을 배포할 수도 있고, 도커 허브의 대부분 이미지는 Dockerfile을 함께 제공합니다.
- 장기적으로 Dockerfile이 유리한 이유: 필요한 패키지 설치를 명확히 할 수 있고, 이미지 생성을 자동화할 수 있으며, 배포가 쉽습니다.

#### 2.4.2 Dockerfile 작성

- 기본 파일명은 **Dockerfile**이고, 도커는 현재 디렉터리의 이 파일을 읽습니다.
- Dockerfile은 **빈 디렉터리**에 두는 것이 좋습니다. 빌드 컨텍스트 때문입니다.
- 한 줄에 하나의 명령어이고, 위에서 아래로 차례대로 실행됩니다. 명령어는 대문자로 쓰는 게 일반적입니다.

**기본 명령어**

- `FROM`: 베이스 이미지입니다. **반드시 한 번 이상** 입력해야 하고, 없으면 자동으로 pull합니다.
- `LABEL`: 키:값 형태의 메타데이터입니다. `docker inspect`로 확인합니다.
- `RUN`: 컨테이너 내부에서 명령어를 실행합니다.
    - 빌드 중에는 **별도 입력이 불가능**하므로 `apt-get install -y`처럼 미리 Yes를 지정해야 합니다. 입력을 요구하면 오류로 간주하고 빌드가 종료됩니다.
    - JSON 배열 형태(`["/bin/bash", "-c", "..."]`)는 셸을 실행하지 않아서 환경변수가 동작하지 않습니다. 셸을 쓰려면 `["sh", "-c", "..."]` 형태로 씁니다.
- `ADD`: 빌드 컨텍스트의 파일을 이미지에 추가합니다. JSON 배열이면 마지막 원소가 목적지입니다.
- `WORKDIR`: 명령어를 실행할 디렉터리로, cd와 같습니다. 여러 번 쓰면 cd를 여러 번 한 것과 같습니다.
- `EXPOSE`: 이미지가 사용할 포트를 **명시만** 합니다. 자동으로 호스트에 바인딩되지 않으며, `P`와 함께 쓰입니다.
- `CMD`: 컨테이너 시작 시 실행할 명령어로, **한 번만** 사용할 수 있습니다.
    - docker run 끝에 커맨드를 입력하면 CMD를 덮어씁니다.
    - apachectl -DFOREGROUND처럼 포그라운드 프로그램이면 `d`로 실행해야 합니다.

#### 2.4.3 Dockerfile 빌드

**이미지 생성**

- `docker build -t [이미지명] [Dockerfile 경로]`
    - `t`를 안 쓰면 16진수 이름이 되므로 쓰는 게 좋습니다.
    - 경로는 로컬이 일반적이고, 외부 URL도 가능합니다.
- `docker run -P`: 이미지의 **EXPOSE 포트 전부**를 호스트의 랜덤 포트에 연결합니다. `docker ps`나 `docker port`로 확인합니다.
- 라벨 필터링: `docker images --filter "label=purpose=practice"`
    - 라벨은 이미지뿐 아니라 컨테이너(`docker run --label`, `docker ps --filter`)와 도커 엔진에도 쓸 수 있습니다.

**빌드 과정 (중요)**

- `[2/6]` 같은 표시는 Dockerfile 명령어 순서입니다.
- **ADD, RUN 등 명령어 한 줄마다 새 컨테이너를 만들어 실행하고 커밋해서 레이어 하나를 만듭니다.**
    - 즉, 빌드가 끝나면 명령어 줄 수만큼의 레이어가 존재합니다.
- 빌드 중 임시 컨테이너는 **buildkit**이 제어해서 `docker ps`로 보이지 않습니다. `DOCKER_BUILDKIT=0`으로 비활성화하면 볼 수 있습니다.

**캐시를 이용한 빌드**

- 이전 빌드와 같은 명령어 줄까지는 **CACHED**로 재사용합니다. 불필요한 재실행을 막아줍니다.
- `f` 또는 `-file`: Dockerfile 이름을 지정합니다.
- 캐시가 오히려 문제인 경우: `RUN git clone` 같은 명령어는 저장소가 바뀌어도 캐시를 써서 **옛 소스코드**를 사용합니다.
    - 해결: `-no-cache`
- `-cache-from [이미지]`: 특정 이미지를 캐시로 지정합니다. 기존 Dockerfile을 확장할 때 유용합니다.

**멀티 스테이지 빌드**

- 문제: golang 이미지로 빌드하면 Hello World 프로그램인데도 이미지가 **800MB 이상**입니다. 빌드용 패키지와 라이브러리가 포함되기 때문입니다.
- 해결: 하나의 Dockerfile에 **FROM을 여러 개** 정의해서 실행 파일만 최종 이미지에 담습니다. (도커 17.05 이상)
    - 첫 FROM(golang)에서 빌드하고, 두 번째 FROM(alpine)에서 `COPY --from=0`으로 실행 파일만 복사합니다.
    - 결과: 888MB가 10MB로 줄어듭니다.
- 스테이지는 FROM 순서대로 0, 1, 2...로 구분됩니다. `FROM golang as builder`처럼 이름을 붙이고 `-from=builder`로 쓸 수도 있습니다.
- alpine, busybox는 필수 런타임만 들어 있는 아주 작은 리눅스 이미지로, 경량 이미지 제작에 적합합니다.

#### 2.4.4 기타 Dockerfile 명령어

**ENV, VOLUME, ARG, USER**

- `ENV`: 환경변수를 지정합니다. `${NAME}` 또는 `$NAME`으로 사용합니다.
    - 이미지에도 저장되어 컨테이너에서 쓸 수 있습니다.
    - run의 `e`로 같은 이름을 쓰면 덮어씁니다.
    - `${env:-value}`: 값이 없으면 value 사용
    - `${env:+value}`: 값이 있으면 value, 없으면 빈 문자열
- `VOLUME`: 호스트와 공유할 컨테이너 내부 디렉터리를 지정합니다. 컨테이너 생성 시 볼륨이 자동 생성됩니다.
- `ARG`: build 시 `-build-arg 키=값`으로 입력받는 변수입니다. 기본값을 지정할 수 있습니다.
    - ARG와 ENV를 같은 이름으로 정의하면 **ENV가 덮어씁니다**.
- `USER`: 이후 명령어를 실행할 사용자를 지정합니다.
    - 기본은 root인데, 호스트의 root 권한을 가질 수 있어 보안상 바람직하지 않습니다. 예를 들어 root 소유 호스트 디렉터리를 공유하면 마음대로 조작할 수 있습니다.
    - 배포용 이미지는 **root가 아닌 사용자**를 설정하는 것이 좋습니다. (run의 `-user`도 가능)

**ONBUILD, STOPSIGNAL, HEALTHCHECK, SHELL**

- `ONBUILD`: 이 이미지를 **베이스로 하는 자식 이미지**를 빌드할 때 실행할 명령어입니다.
    - 자기 자신을 빌드할 때는 실행되지 않습니다.
    - 자식에게만 적용되고, **손자에게는 상속되지 않습니다**.
    - ONBUILD, FROM을 제외한 명령어를 저장해둘 수 있습니다.
- `STOPSIGNAL`: 컨테이너 정지 시 보낼 시스템 콜입니다. 기본값은 **SIGTERM**입니다.
    - run의 `-stop-signal`로도 설정 가능하며, docker stop과 kill 모두에 적용됩니다.
- `HEALTHCHECK`: 프로세스는 살아 있지만 앱이 동작하지 않는 상태를 감지합니다.
    - `-interval`: 체크 주기
    - `-timeout`: 이 시간을 넘기면 실패로 간주
    - `-retries`: 이 횟수만큼 실패하면 **unhealthy**
    - `docker ps`의 STATUS에 (healthy)가 표시되고, 로그는 inspect의 State → Health → Log에서 확인합니다.
    - 체크에 쓰는 명령어(curl 등)는 이미지에 설치되어 있어야 합니다.
- `SHELL`: 기본 셸을 바꿉니다. 기본값은 리눅스 `/bin/sh -c`, 윈도우 `cmd /S /C`입니다.

**ADD, COPY**

- 기능 자체는 같지만 차이가 있습니다.
    - `COPY`: **로컬** 컨텍스트 파일만 복사
    - `ADD`: 로컬 + **외부 URL** + **tar 파일**(자동으로 압축 해제해서 추가)
- COPY 기능이 ADD에 포함되는 셈입니다.
- **ADD는 권장하지 않습니다.** 어떤 파일이 추가될지 빌드 시점에 정확히 알 수 없기 때문입니다. COPY는 명확합니다.

**ENTRYPOINT, CMD (중요)**

- 둘 다 컨테이너 시작 시 실행할 명령어를 지정하지만, ENTRYPOINT는 **CMD를 인자로 받는 스크립트 역할**을 합니다.
    - ENTRYPOINT 없음: CMD를 그대로 실행 (예: /bin/bash 실행)
    - ENTRYPOINT 있음: **ENTRYPOINT + CMD(인자)**로 실행 (예: entrypoint가 echo, cmd가 /bin/bash면 `echo /bin/bash` 실행)
- 둘 다 없으면 컨테이너가 생성되지 않고 에러가 나므로 **반드시 하나는 설정**해야 합니다.
- Dockerfile에서 `ENTRYPOINT ["echo"]` + `CMD ["hello", "world"]`처럼 조합할 수 있습니다. run의 `-entrypoint`와 마지막 인자로 재정의하면 덮어씁니다.
- **스크립트 실행 패턴**
    1. 필요한 설정과 실행을 스크립트로 정리
    2. ADD 또는 COPY로 스크립트를 이미지에 복사 (스크립트는 컨테이너 내부에 있어야 함)
    3. ENTRYPOINT를 스크립트로 설정
    4. 빌드
    5. 인자는 docker run의 cmd로 전달
    - 예: `docker run ... entrypoint_image first second`면 스크립트의 $1, $2로 first, second가 들어갑니다.

**JSON 배열 형태와 일반 형식의 차이**

- 일반 형식으로 쓰면 앞에 **`/bin/sh -c`가 자동으로 추가**됩니다.
    - `CMD echo test` → `/bin/sh -c echo test`
- JSON 배열 형태는 입력한 그대로 실행됩니다.
    - `CMD ["echo", "test"]` → `echo test`
- /bin/sh를 쓸 수 없는 이미지라면 JSON 배열 형태를 써야 합니다.

#### 2.4.5 Dockerfile 빌드 시 주의할 점

- 좋은 습관: `\`로 줄을 나눠 가독성 높이기, `.dockerignore`로 불필요한 파일을 빌드 컨텍스트에서 제외, 빌드 캐시 활용
- **핵심 함정**: 레이어 구조 때문에 파일을 지워도 용량이 줄지 않습니다.
    - 예: RUN으로 100MB 파일 생성 → 다음 RUN으로 삭제해도 이미지는 78MB가 아니라 **약 183MB**입니다.
    - 삭제는 "삭제했다"는 변경사항 레이어가 추가될 뿐이고, 100MB 파일은 이전 레이어에 남아 있기 때문입니다.
- 해결: **`&&`로 여러 명령어를 하나의 RUN으로 묶습니다.** RUN 하나가 레이어 하나이므로 레이어 수도 줄어듭니다.
- 레이어 구조의 장점도 있습니다.
    - A, B 앱이 같은 500MB 라이브러리를 쓴다면 라이브러리 이미지를 먼저 만들고 그 위에 각 앱을 빌드하면 1GB가 아니라 500MB 레이어를 **공유**합니다.
    - 배포 시에도 변경된 레이어만 받으면 되므로 빠릅니다.
- 남이 만든 이미지에 불필요한 레이어가 많다면 `docker export | docker import`로 **레이어를 하나로** 줄일 수 있습니다. 단, 이미지 설정(CMD 등)은 잃어버립니다.
- export/import로 레이어를 하나로 줄이면 CMD, ENTRYPOINT 같은 **이미지 설정이 사라집니다**.
- 그래서 그 이미지로 컨테이너를 만들면 **No command specified** 에러가 나며 생성되지 않습니다.

## 2.5 도커 데몬

#### 2.5.1 도커의 구조 (중요)

- 도커는 **클라이언트로서의 도커**와 **서버로서의 도커**로 나뉩니다.
    - `which docker` → `/usr/bin/docker`: 도커 클라이언트(CLI)
    - `ps aux | grep docker` → `/usr/bin/dockerd`: 실제 도커 엔진 프로세스
- **도커 서버(dockerd)**: 실제로 컨테이너를 생성, 실행하고 이미지를 관리하는 주체입니다. 외부에서 API 입력을 받아 기능을 수행하며, 입력을 받을 준비가 된 상태를 **도커 데몬**이라고 합니다.
- **도커 클라이언트**: 도커 데몬의 API를 사용할 수 있게 해주는 CLI입니다.
- 명령어 처리 흐름
    1. 사용자가 docker version 같은 명령어 입력
    2. /usr/bin/docker가 **`/var/run/docker.sock` 유닉스 소켓**으로 데몬에 전달
    3. 데몬이 명령어를 파싱하고 작업 수행
    4. 결과를 클라이언트로 반환해서 출력
- 유닉스 소켓은 **같은 호스트 내**의 데몬에게 명령을 전달할 때 사용됩니다. 원격은 tcp로 제어합니다.

#### 2.5.2 도커 데몬 실행

- 서비스로 시작/정지: `service docker start`, `service docker stop`
    - 우분투는 설치 시 자동으로 서비스 등록되어 호스트 재시작해도 자동 실행됩니다.
    - 레드햇 계열은 자동 실행이 안 되므로 `systemctl enable docker`가 필요합니다.
- 서비스 대신 `dockerd`로 직접 실행할 수도 있습니다. 마지막에 `API listen on /var/run/docker.sock`이 출력되면 준비 완료입니다.
- 직접 실행은 디버깅이나 트러블슈팅에 편하지만, **포그라운드로 터미널을 차지**하므로 운영 환경에서는 service, systemctl로 관리하는 게 좋습니다.

#### 2.5.3 도커 데몬 설정

- 옵션 확인: `dockerd --help`
    - 앞에서 쓴 --insecure-registry, --log-driver, --storage-opt 등이 모두 데몬 옵션입니다.
- 적용 방법은 두 가지입니다.
    - dockerd 명령어에 직접 옵션 추가
    - 설정 파일(`/etc/default/docker`)의 **DOCKER_OPTS**에 입력 후 서비스로 실행 (일반적인 방법)
- 두 방식은 같은 설정이고, 직접 실행하느냐 서비스로 실행하느냐의 차이만 있습니다.

#### 2.5.3.1 도커 데몬 제어: -H

- `H`는 도커 데몬의 API를 사용할 수 있는 방법(바인딩 주소)을 추가합니다.
- 아무 옵션 없이 실행하면 기본으로 유닉스 소켓을 씁니다. 즉 `dockerd`와 `dockerd -H unix:///var/run/docker.sock`은 같습니다.
- `H tcp://0.0.0.0:2375`처럼 IP와 포트를 주면 **Docker Remote API**로 원격 제어할 수 있습니다.
    - RESTful API 형식이라 HTTP 요청(curl 등)으로 제어합니다.
    - 예: `curl [IP]:2375/version`은 `docker version`과 같습니다.
- 주의: **tcp만 지정하면 유닉스 소켓이 비활성화**되어 로컬 docker 명령어를 못 씁니다. 그래서 보통 `H unix:///var/run/docker.sock -H tcp://0.0.0.0:2375`처럼 **둘 다** 설정합니다.
- `-tls=false`로 Remote API를 열면 누구나 인증 없이 호출할 수 있어서 보안 취약점이 됩니다. TLS 인증을 반드시 적용하는 게 좋습니다.
- 클라이언트 쪽에서 원격 데몬을 지정하는 방법
    - 환경변수: `export DOCKER_HOST="tcp://[IP]:2375"`
    - 옵션: `docker -H tcp://[IP]:2375 version`
    - H를 안 쓰면 로컬 데몬을 제어합니다.
- **docker context**: 여러 데몬을 번갈아 쓸 때 DOCKER_HOST를 유동적으로 관리하는 방법입니다.
    - `docker context ls`: 목록 확인
    - `docker context create [이름] --docker "host=tcp://[IP]:2375"`: 등록
    - `docker context use [이름]`: 전환 (이후 모든 명령이 해당 데몬으로 전달)
- 실무에서는 HTTP로 직접 요청하기보다 **언어별 라이브러리**로 Remote API를 쓰는 게 일반적입니다.

#### 2.5.3.2 도커 데몬에 보안 적용: --tlsverify

- 기본적으로 보안 연결이 설정되어 있지 않아서, IP와 포트만 알면 누구나 도커를 제어할 수 있습니다.
- 필요한 파일은 **총 5개**입니다.
    - 서버(데몬) 측: **ca.pem, server-cert.pem, server-key.pem**
    - 클라이언트 측: **ca.pem, cert.pem, key.pem**
- 생성 흐름
    1. 서버 측: CA 키(ca-key.pem)와 공용 키(ca.pem) 생성 → 서버 키 생성 → CSR 생성 → extfile.cnf에 접속 IP 기록 → CA로 서명해서 server-cert.pem 생성
    2. 클라이언트 측: 키와 CSR 생성 → extfile.cnf에 `extendedKeyUsage = clientAuth` 추가 → CA로 서명해서 cert.pem 생성
    3. 파일 권한을 읽기 전용(0400)으로 바꾸고 `~/.docker`로 모아둠 (필수는 아님)
- 데몬 실행: `dockerd --tlsverify --tlscacert=... --tlscert=... --tlskey=... -H=0.0.0.0:2376 -H unix:///var/run/docker.sock`
- **포트 관례**: 보안 미적용은 **2375**, 보안 적용은 **2376** (규칙은 아니지만 커뮤니티 관례)
- 인증 파일 없이 접근하면 TLS 관련 에러가 납니다. 클라이언트도 `-tlscacert`, `-tlscert`, `-tlskey`, `-tlsverify`를 줘야 합니다.
- 매번 입력이 귀찮으면 환경변수로 설정합니다.
    - `DOCKER_CERT_PATH`: 인증 파일 위치
    - `DOCKER_TLS_VERIFY=1`: TLS 인증 사용 여부
    - 셸 종료 시 초기화되므로 `~/.bashrc`에 export를 넣어둡니다.
- curl로 쓸 때는 `https://`와 `-cert`, `-key`, `-cacert`를 추가합니다.

#### 2.5.3.3 스토리지 드라이버 변경: --storage-driver

- **스토리지 드라이버**: 컨테이너와 이미지를 저장하고 관리하는 스토리지 백엔드 기술입니다. 이미지를 **불변(immutable)인 읽기 전용 파일 시스템**으로 쓸 수 있게 해주는 핵심 기술입니다.
- 확인: `docker info | grep "Storage Driver"`
- 28.0.1 기준 기본값은 **overlay2**이며, 대부분의 리눅스에서 별도 설정 없이 씁니다.
- 지원 드라이버: overlay2, btrfs, zfs 등. **하나만** 선택해서 적용할 수 있습니다.
- **드라이버별로 컨테이너와 이미지가 따로 관리됩니다.** overlay2를 쓰다가 zfs로 바꾸면 기존 이미지와 컨테이너를 쓸 수 없습니다.
- 무조건 좋은 드라이버는 없습니다. 대부분 overlay2로 충분하고, 성능이나 안정성을 우선하면 btrfs나 zfs도 선택지입니다.
- 저장 위치는 `/var/lib/docker/[드라이버 이름]`이고, `-data-root`로 바꿀 수 있습니다. 빈 디렉터리를 지정하면 초기화된 상태로 실행됩니다.
- 여러 드라이버 디렉터리가 한곳에 있으면 데몬이 어떤 걸 쓸지 몰라 시작되지 않을 수 있으므로 드라이버를 명시하는 게 좋습니다.

**스토리지 드라이버의 원리: CoW (중요)**

- 이미지는 읽기 전용이고, 컨테이너는 그 위에 얇은 컨테이너 레이어를 만듭니다. 실제 쓰기 작업에는 **Copy-on-Write(CoW)**가 사용됩니다.
- **스냅숏**: 원본 파일은 읽기 전용으로 두고, 변경되면 새 공간을 할당하는 개념입니다.
- 읽기: 원본 파일에 그냥 접근합니다.
- 쓰기: 원본을 **스냅숏 바깥 공간에 복사**한 뒤 복사본에 쓰기를 반영합니다.
- 도커에 적용하면
    - 이미지 레이어 = 스냅숏
    - 컨테이너 = 스냅숏을 사용하는 변경점
    - 컨테이너에서 이미지 파일을 바꾸면 컨테이너 레이어로 복사해서 쓰고, 커밋하면 변경 사항이 새 스냅숏, 즉 새 이미지 레이어가 됩니다.
- 드라이버마다 용어는 다르지만 기본적으로 CoW 원리를 씁니다.

**OverlayFS (overlay2)**

- 도커에서 overlay2라는 이름으로 쓰이며, 커널 4.0 이상이면 기본 사용 가능합니다.
- 구조는 세 가지입니다.
    - **lowerdir**: 이미지 레이어
    - **upperdir**: 컨테이너 레이어 (변경 사항, 실제 디렉터리명은 diff)
    - **merged**: 둘을 통합해 보여주는 컨테이너 마운트 지점
- 다른 드라이버처럼 여러 계층이 쌓인 게 아니라, 여러 이미지 레이어를 **하나의 마운트 지점에서 통합**해서 씁니다.
- 위치: `/var/lib/docker/overlay2`. `init`이 붙은 디렉터리가 방금 만든 컨테이너이고, 그 안에 diff, link, lower, merged, work가 있습니다. `mount | grep overlay2`로도 확인할 수 있습니다.
- 이미지 파일에 쓰기할 때 upperdir로 **copy_up**을 하므로, 큰 파일에 처음 쓸 때는 지연이 생길 수 있습니다. 읽기/쓰기가 많다면 **도커 볼륨** 사용을 고려합니다.

**btrfs**

- 리눅스 파일 시스템으로 SSD 최적화, 데이터 압축 등을 제공합니다.
- OverlayFS와 달리 **파일 시스템을 별도로 구성**해야 쓸 수 있고, `/var/lib/docker`가 btrfs 공간에 마운트되어 있어야 합니다. 우분투나 데비안 계열 권장.
- 설정 흐름: 데몬 정지 → `mkfs.btrfs`로 풀 생성 → /var/lib/docker 재생성(기존 이미지/컨테이너 삭제되므로 백업 필요) → /etc/fstab에 마운트 추가 → `mount -a` → `-storage-driver=btrfs`로 재시작
- 이미지와 컨테이너를 **서브볼륨(subvolume)과 스냅숏** 단위로 관리합니다. 베이스 레이어가 서브볼륨, 그 위 레이어들이 스냅숏입니다.
- 쓰기 시 파일 전체가 아니라 **블록 레벨에서 CoW**를 수행합니다.

**ZFS**

- 썬 마이크로시스템즈(현 오라클)가 개발했고 압축, 레플리카, 중복 제거 기능이 있습니다.
- 라이선스 문제로 리눅스 커널에 기본 탑재되지 않아서 **ZFS on Linux(ZoL)**로 별도 설치합니다. (`zfsutils-linux`, `modprobe zfs`)
- 설정 흐름: zpool 생성 → ZFS 파일 시스템을 /var/lib/docker에 마운트 → `-storage-driver=zfs`로 재시작
- 구조: 이미지 베이스 레이어가 **ZFS 파일 시스템**, 그 위가 **ZFS 스냅숏**, 컨테이너 레이어는 스냅숏에서 만든 **ZFS 클론(clone)**입니다.
- 쓰기에 **RoW**를 사용하며, 새 데이터는 allocate-on-demand로 128KB 블록을 할당받습니다.
- *ARC(Adaptive Replacement Cache)**로 디스크 블록을 캐시해서 PaaS 환경에도 괜찮습니다.
- 단, **메모리를 많이 소모**하는 무거운 파일 시스템이므로 컨테이너가 많으면 자원 사용량을 수시로 확인해야 합니다.

#### 2.5.4 도커 데몬 모니터링

#### 디버그 모드

- `dockerd -D`: Remote API 입출력과 로컬 클라이언트 명령어까지 모두 로그로 출력합니다.
- 가장 확실한 방법이지만, 불필요한 정보가 너무 많고 **포그라운드로 실행**해야 한다는 단점이 있습니다.
- 서비스로 실행했다면 로그 파일에서 확인합니다. (systemd 기반은 `journalctl -u docker`)

#### events, stats, system df

- **events** (`docker events` 또는 `docker system events`)
    - 데몬에서 일어나는 일을 **실시간 스트림 로그**로 보여줍니다.
    - 모든 명령이 아니라 컨테이너(attach, commit, create 등), 이미지(pull, push 등), 볼륨, 네트워크, 플러그인 관련 결과가 출력됩니다.
    - `-filter 'type=image'`처럼 필터링합니다. 타입은 container, image, volume, network, plugin, daemon입니다.
- **stats** (`docker stats`)
    - 실행 중인 모든 컨테이너의 CPU, 메모리 제한/사용량, 네트워크 I/O, 블록 I/O를 스트림으로 출력합니다.
    - 한 번만 보려면 `-no-stream`
    - Remote API의 stats는 바이트 단위로 훨씬 자세한 정보를 반환합니다.
- **system df** (`docker system df`)
    - 이미지, 컨테이너, 로컬 볼륨, 빌드 캐시의 총 개수, 사용 중인 개수, 크기, **삭제로 확보 가능한 공간(RECLAIMABLE)**을 출력합니다.
    - 정리 명령어: `docker container prune`, `docker volume prune`, `docker image prune`(댕글링 이미지 삭제)

#### CAdvisor

- 구글이 만든 컨테이너 모니터링 도구로, 컨테이너로 간단히 설치하고 자원 사용량을 시각화합니다.
- 기본 8080 포트로 대시보드에 접근합니다.
- 많은 정보를 보여줄 수 있는 이유: 호스트의 디렉터리들을 **볼륨으로 마운트**했기 때문입니다.
    - `/var/run`: 유닉스 소켓
    - `/sys`: 컨테이너용 **cgroup** 정보 (CPU, Memory 등 격리 자원별 디렉터리)
    - `/var/lib/docker`: 컨테이너, 이미지 파일
- 한계
    - 대시보드는 **60초간**의 정보만 보여줍니다. 장기 분석은 InfluxDB, Prometheus 등과 연동합니다.
    - **단일 호스트만** 모니터링할 수 있습니다. 클러스터 환경에서는 쿠버네티스나 스웜 모드 같은 오케스트레이션 툴과 Prometheus 등을 함께 씁니다.

#### 2.5.5 파이썬 Remote API 라이브러리

- 작업이 많거나 복잡하면 HTTP 요청을 직접 짜기보다, Remote API를 래핑한 **라이브러리**를 쓰는 게 편합니다. Go, C#, C++, Python, Java 등 다양하게 있습니다.
- 파이썬은 **docker-py** (Python 3 이상, `pip3 install docker`)
- 사용법
    - `docker.DockerClient(base_url='unix://var/run/docker.sock')`: 로컬 연결
    - 원격이면 base_url에 `http://[IP]:2375` 입력
    - `client.info()`: 엔진 정보 출력
    - `client.containers.run('nginx', detach=True, ports={'80/tcp': 80})`: `docker run -d -p 80:80 nginx`와 동일
