## 6.1 쿠버네티스를 시작하기 전에

설치를 마쳤다면 이제 쿠버네티스를 사용해 볼 차례입니다. 다만 그 전에, 도커 스웜 모드와 비교했을 때 쿠버네티스만의 고유한 특징 몇 가지를 짚고 넘어갑니다.

### 모든 리소스는 오브젝트 형태로 관리됩니다.

도커 스웜에서는 서비스(service)라는 단위로 컨테이너 묶음을 다뤘죠. 쿠버네티스는 이걸 훨씬 잘게 쪼개서, 컨테이너 묶음(Pod), 그걸 관리하는 컨트롤러(ReplicaSet), 사용자(ServiceAccount), 심지어 서버(Node)까지 전부 **오브젝트**라는 형태로 다룹니다.

- `kubectl api-resources`: 쓸 수 있는 오브젝트 종류 전체 목록. SHORTNAMES 열에 줄임말(po, rs, svc 등)도 나옴
- `kubectl explain pod`: 특정 오브젝트의 간단한 설명

종류가 엄청 많지만 외울 필요는 없고, 자주 쓰는 건 실습하다 보면 자연스럽게 익혀집니다. 처음 보는 오브젝트는 공식 문서를 보며 필요할 때 익히면 됩니다.

### 쿠버네티스는 명령어로도 사용할 수 있지만, YAML 파일을 더 많이 사용합니다.

`kubectl` 명령어로도 대부분의 작업이 가능하지만, 쿠버네티스에서는 **YAML 파일로 오브젝트를 정의하고 `kubectl apply -f`로 적용하는 방식**이 기본입니다. 도커 스웜에서 스택을 YAML로 만들었던 것과 비슷한데, 쿠버네티스는 컨테이너뿐 아니라 설정값(ConfigMap), 비밀값(Secret) 등 **거의 모든 리소스**를 YAML로 정의한다는 점이 다릅니다.

여기서 알아두면 좋은 개념이 **선언형(Declarative)** 방식입니다. nginx 컨테이너 3개를 실행하라고 명령하는 게 아니라, nginx 파드가 3개 있는 상태여야 한다고 YAML에 적어두면 쿠버네티스가 알아서 그 상태를 맞춰주는 방식이에요. 그래서 책도 쿠버네티스를 잘 쓰는 법을 한마디로 하면 YAML 파일을 잘 작성하는 것이라고 할 정도입니다.

### 쿠버네티스는 여러 개의 컴포넌트로 구성돼 있습니다.

쿠버네티스 노드의 역할은 크게 **마스터**(클러스터 관리)와 **워커**(애플리케이션 컨테이너 실행)로 나뉩니다. 도커 스웜은 도커 데몬 하나면 됐지만, 쿠버네티스는 여러 컴포넌트가 동시에 실행되며 협업합니다.

마스터 노드에서 실행되는 것은 다음과 같습니다.

- **kube-apiserver (API 서버)**: 모든 요청의 입구. kubectl 명령도 결국 여기로 감
- **kube-controller-manager (컨트롤러 매니저)**: 레플리카셋처럼 원하는 상태를 유지시키는 관리자들의 묶음
- **kube-scheduler (스케줄러)**: 새 파드를 어느 워커 노드에 배치할지 결정
- **coreDNS (DNS 서버)**: 클러스터 내부에서 이름으로 서로를 찾을 수 있게 해줌

모든 노드에서 실행되는 것은 다음과 같습니다.

- **kube-proxy**: 네트워크 규칙을 관리해 서비스로 들어온 요청을 파드로 전달
- **네트워크 플러그인 (calico, flannel 등)**: 다른 서버에 있는 파드끼리 통신하게 해주는 오버레이 네트워크
- **kubelet**: 각 노드의 에이전트. 컨테이너 생성과 삭제는 물론 마스터와 워커 사이의 통신도 담당. kubelet이 제대로 실행되지 않으면 그 노드는 쿠버네티스와 제대로 연결되지 않음

이 컴포넌트들은 대부분 컨테이너로 떠 있어서, 마스터 노드에서 `crictl ps`를 해보면 많은 컨테이너가 보입니다. 단, kubelet은 컨테이너가 아니라 노드에 직접 설치된 프로그램으로 실행돼요. (Docker Desktop이라면 설정에서 Show system containers를 체크하면 docker ps로도 볼 수 있지만, 지식 없이 핵심 컴포넌트를 건드리지 않는 게 좋습니다.)

5장에서 본 CRI 개념도 다시 나옵니다. 쿠버네티스 입장에서 containerd나 cri-o도 하나의 컴포넌트일 뿐이고, 쿠버네티스는 도커에 내장된 기능이 아니라 OCI 표준을 구현한 런타임이면 무엇이든 쓸 수 있습니다.

책 결론처럼 지금은 **kubelet이 모든 노드에서 기본적으로 실행되고, 마스터에는 API 서버 등이 컨테이너로 실행된다** 정도만 알면 충분합니다.

## 6.2 파드(Pod): 컨테이너를 다루는 기본 단위

쿠버네티스에는 셀 수 없이 많은 리소스가 있지만, 컨테이너 애플리케이션을 구동하려면 반드시 알아야 할 오브젝트가 네 가지 있습니다: **파드, 레플리카셋, 서비스, 디플로이먼트**. 이 중 가장 기초인 파드부터 봅니다.

미리 큰 그림을 잡아두면 이렇습니다. 디플로이먼트가 레플리카셋을 만들고, 레플리카셋이 파드를 만들며, 서비스는 그 파드들 앞에서 요청을 받아주는 창구 역할을 합니다.

### 6.2.1 파드 사용하기

도커 엔진의 기본 단위가 컨테이너, 스웜의 기본 단위가 서비스였다면, 쿠버네티스의 기본 단위는 **파드**입니다. 파드는 1개 이상의 컨테이너로 구성된 컨테이너의 집합이에요. nginx 웹 서버를 띄운다면 파드 1개에 nginx 컨테이너 1개를 넣는 게 가장 기본적인 형태이고, 같은 nginx를 여러 개 띄우고 싶다면 이런 파드를 여러 개 만들면 됩니다.

**nginx-pod.yaml**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-nginx-pod
spec:
  containers:
  - name: my-nginx-container
    image: nginx:latest
    ports:
    - containerPort: 80
      protocol: TCP
```

쿠버네티스 YAML은 일반적으로 이 네 가지 항목으로 구성됩니다.

- **apiVersion**: 이 오브젝트의 API 버전. 지금은 오브젝트 종류마다 값이 다르다 정도만 알면 됨 (Pod는 v1, ReplicaSet과 Deployment는 apps/v1)
- **kind**: 리소스 종류. 쓸 수 있는 값은 `kubectl api-resources`의 KIND 열에서 확인 가능
- **metadata**: 라벨, 주석, 이름 같은 부가 정보
- **spec**: 리소스를 생성하기 위한 상세 정보. 파드라면 어떤 이미지로 어떤 컨테이너를 띄우고 어떤 포트를 쓸지

파드를 다루는 기본 명령어는 다음과 같습니다.

- `kubectl apply -f nginx-pod.yaml`: 파드 생성
- `kubectl get pods`: 파드 목록 확인
- `kubectl describe pods my-nginx-pod`: 상세 정보 (IP, 상태 등)
- `kubectl exec -it my-nginx-pod -- bash`: 파드 컨테이너 안으로 들어가기. `docker exec`와 같고, `-` 뒤가 컨테이너에서 실행할 명령
- `kubectl logs my-nginx-pod`: 로그 확인 (`docker logs`와 같음)
- `kubectl delete -f nginx-pod.yaml` 또는 `kubectl delete pod my-nginx-pod`: 삭제

`containerPort: 80`을 적었다고 외부에서 접속할 수 있는 건 아닙니다. describe로 확인한 파드 IP(예: 172.17.0.4)는 **클러스터 내부에서만 통하는 IP**예요. `docker run`을 `-p` 옵션 없이 실행한 것과 비슷한 상태라고 보면 됩니다.

그래서 테스트하려면 클러스터 노드에 접속해서 `curl 파드IP`를 하거나, 아래처럼 임시 테스트용 파드를 띄워서 그 안에서 curl을 날립니다. `--rm`이 붙어 있어서 exit하면 이 테스트 파드는 자동으로 삭제됩니다.

```
kubectl run -i --tty --rm debug \
  --image=alicek106/ubuntu:curl --restart=Never bash
```

외부나 내부에서 제대로 접근하려면 6.5절의 **서비스**가 필요합니다.

### 6.2.2 파드 vs. 도커 컨테이너

여기까지만 보면 파드는 컨테이너 하나와 다를 게 없어 보입니다. IP가 있고, exec로 들어갈 수 있고, logs로 로그도 보니까요. 그럼 왜 굳이 파드라는 개념을 만들었을까요? 여러 이유가 있지만 핵심 중 하나는 **파드 안의 컨테이너들은 여러 리눅스 네임스페이스를 공유한다**는 점입니다.

책은 nginx 컨테이너가 있는 파드에 우분투 컨테이너(ubuntu-sidecar-container)를 하나 더 넣는 실험으로 이걸 보여줍니다.

```yaml
  - name: ubuntu-sidecar-container
    image: alicek106/rr-test:curl
    command: ["tail"]
    args: ["-f", "/dev/null"]   # 컨테이너가 종료되지 않도록 유지
```

- YAML에서 (대시)로 시작하는 항목은 리스트라서, containers 아래에 여러 컨테이너를 나열할 수 있음
- `command`는 도커의 Entrypoint, `args`는 도커의 Cmd와 같음
- 적용 후 `kubectl get pods`를 보면 READY가 **2/2**로 표시됨. 파드 안 컨테이너 2개 중 2개가 준비 완료라는 뜻
- 특정 컨테이너를 지정하려면 `c` 옵션 사용: `kubectl exec -it my-nginx-pod -c ubuntu-sidecar-container -- bash`

이제 우분투 컨테이너 안에서 `curl localhost`를 치면 **nginx 응답이 옵니다.** 우분투 컨테이너에는 nginx가 없는데도요. 두 컨테이너가 같은 네트워크 네임스페이스를 공유해서, 마치 같은 컴퓨터에서 실행되는 프로세스처럼 localhost로 통신할 수 있기 때문입니다.

도커에서 배웠던 `docker run --net container:컨테이너이름` (컨테이너 네트워크)과 같은 원리예요. 쉽게 말해 파드 안 컨테이너들은 IP 하나를 같이 쓰는 룸메이트 같은 관계입니다. 네트워크 말고도 여러 네임스페이스를 공유하지만, 지금은 **파드 내부의 컨테이너들은 네트워크와 같은 리눅스 네임스페이스를 공유한다**까지만 알면 됩니다.

참고로 이미 생성된 파드에 문제가 생겼을 때는 `kubectl debug <파드> --image alpine -it`처럼 디버깅용 컨테이너를 임시로 붙여 조사할 수 있습니다. 기존 파드에 영향을 주지 않는 유용한 방법이에요. 노드 단위로도 쓸 수 있고(`kubectl debug node/<노드> -it --image=alpine`), 이때는 노드의 파일 시스템이 디버그 컨테이너의 /host에 마운트됩니다.

### 6.2.3 완전한 애플리케이션으로서의 파드

그럼 하나의 파드에 컨테이너를 여러 개 막 넣어도 될까요? 기준은 **하나의 파드는 하나의 완전한 애플리케이션**이라는 점입니다.

- nginx 컨테이너는 그 자체로 완전한 애플리케이션이니, 한 파드에 nginx를 2개 넣는 건 바람직하지 않음
- 대신 nginx를 **보조하는** 컨테이너는 같이 넣을 수 있음. 예를 들어 설정 파일 변경사항을 갱신해주는 리로더(reloader), 로그를 수집하는 프로세스
- 이렇게 주 컨테이너의 기능을 확장하기 위해 추가한 컨테이너를 **사이드카(sidecar) 컨테이너**라고 부름
- 사이드카 컨테이너는 파드 내의 다른 컨테이너와 네트워크 환경 등을 공유하고, 같은 파드의 컨테이너들은 **항상 같은 워커 노드에서 함께 실행**됨

실제로는 대부분 파드 1개에 컨테이너 1개로 쓰고, 이 책 예제도 대부분 그렇습니다. 앞의 우분투 컨테이너는 사실 nginx를 보조하지 않으니 엄밀히는 사이드카라고 보긴 어렵다고 책에서도 각주로 언급합니다.

참고로 파드의 네트워크 네임스페이스는 파드마다 자동 생성되는 **pause 컨테이너**로부터 공유받는 구조입니다. pause 컨테이너가 네임스페이스를 들고 있고 다른 컨테이너들이 거기에 붙는 방식이에요. `ps aux | grep pause`나 containerd를 쓴다면 `ctr --namespace=k8s.io c ls`로 확인할 수 있습니다.

## 6.3 레플리카셋(Replica Set) : 일정 개수의 파드를 유지하는 컨트롤러

### 6.3.1 레플리카셋을 사용하는 이유

파드는 훌륭한 컨테이너 묶음이지만, 파드만 YAML로 정의해서 만들면 그 생애 주기에 문제가 있습니다.

- 파드를 `kubectl delete`로 삭제하면 그냥 영원히 사라짐. 오직 사용자가 직접 관리해야 함
- 마이크로서비스에서는 동일한 컨테이너 여러 개에 외부 요청을 분배해야 하는데, 파드를 여러 개 만들려면 my-nginx-pod-a, my-nginx-pod-b처럼 이름만 다른 파드를 일일이 정의해야 해서 비효율적임 (참고로 YAML 파일 하나에 `--`를 구분자로 써서 여러 리소스를 정의할 수 있음)
- 파드가 떠 있던 **노드에 장애가 생겨도** 다른 노드에서 다시 생성되지 않음. 책 실험에서 `kubectl get pods -o wide`로 파드가 있는 워커 노드를 확인한 뒤 그 EC2를 직접 종료하니, 파드는 Terminating 상태로 남아 있을 뿐 복구되지 않음

이런 한계 때문에 파드만 단독으로 쓰는 경우는 거의 없고, **레플리카셋**을 함께 쓰는 게 일반적입니다. 레플리카셋의 역할은 두 가지입니다.

- 정해진 수의 동일한 파드가 항상 실행되도록 관리
- 노드 장애 등으로 파드를 쓸 수 없다면 다른 노드에서 파드를 다시 생성

레플리카셋이 대신 파드를 관리해주기 때문에, 앞으로 파드를 직접 관리할 일은 거의 없습니다.

### 6.3.2 레플리카셋 사용하기

**replicaset-nginx.yaml**

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: replicaset-nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-nginx-pods-label
  template:                      # 여기서부터 파드 정의
    metadata:
      name: my-nginx-pod
      labels:
        app: my-nginx-pods-label
    spec:
      containers:
      - name: nginx
        image: nginx:latest
        ports:
        - containerPort: 80
```

위쪽(replicas, selector)이 **레플리카셋 정의**, 아래쪽(template)이 **파드 정의**입니다.

- **spec.replicas**: 유지할 파드 개수
- **spec.selector**: 어떤 라벨의 파드를 관리할지 (6.3.3에서 자세히)
- **spec.template**: 파드를 만들 때 쓸 설계도. 앞의 nginx-pod.yaml 내용과 거의 같음. 이를 **파드 스펙** 또는 **파드 템플릿**이라고 부름

책은 앞으로 `metadata.name`처럼 상위 항목부터 점으로 이어서 YAML 위치를 표현합니다. 예를 들어 metadata.name의 값은 replicaset-nginx이고, `spec.selector.matchLabels.app`의 값은 my-nginx-pods-label입니다.

동작은 이렇게 확인합니다.

- `kubectl apply -f replicaset-nginx.yaml` 후 `kubectl get po`를 보면 replicaset-nginx-xxxxx 형태로 파드 3개가 생김
- `kubectl get rs`로 레플리카셋 확인 (DESIRED, CURRENT, READY 모두 3)
- pods 대신 po, replicasets 대신 rs처럼 줄임말을 써도 동일하게 동작함. 목록은 `kubectl api-resources`의 SHORTNAMES 열에 있음
- 개수를 바꾸려면 삭제 후 재생성할 필요 없이, YAML에서 `replicas: 4`로 바꾸고 다시 `kubectl apply -f` 하면 됨. 이때 출력이 created가 아니라 **configured**로 나옴 (기존 리소스를 수정했다는 뜻). `kubectl edit`, `kubectl patch`로도 수정 가능
- `kubectl delete rs replicaset-nginx` 또는 `kubectl delete -f`로 지우면 레플리카셋이 만든 파드도 함께 삭제됨

### 6.3.3 레플리카셋의 동작 원리

겉보기엔 레플리카셋과 파드가 단단히 연결된 것 같지만, 실제로는 **라벨 셀렉터(Label Selector)를 통한 느슨한 연결(loosely coupled)**입니다. 레플리카셋은 내가 만든 파드를 기억하는 게 아니라, 이 라벨을 단 파드가 지금 몇 개 있는지를 계속 세는 방식으로 동작해요.

라벨은 metadata에 붙이는 키-값 형태의 정보(예: `app: my-nginx-pods-label`)입니다. 리소스를 분류하는 용도를 넘어 **서로 다른 오브젝트가 서로를 찾을 때** 쓰입니다.

- `kubectl get pods --show-labels`: 라벨까지 같이 출력
- `kubectl get pods -l app`, `kubectl get pods -l app=my-nginx-pods-label`: 특정 라벨을 가진 파드만 출력

레플리카셋은 selector.matchLabels의 라벨과 일치하는 파드 수를 세서, replicas보다 적으면 template으로 새로 만들고 많으면 삭제합니다. 책의 세 가지 실험이 이걸 증명합니다.

**실험 1.** `app: my-nginx-pods-label` 라벨을 단 파드를 직접 1개 만든 뒤 레플리카셋(replicas: 3)을 생성하면, 레플리카셋은 **2개만** 새로 만듭니다. 이미 라벨이 맞는 파드가 1개 있으니까요.

**실험 2.** 그 수동 파드를 삭제하면, 라벨 맞는 파드가 2개로 줄었으니 레플리카셋이 즉시 1개를 새로 만들어 3개를 맞춥니다.

**실험 3.** `kubectl edit pods <파드이름>`으로 레플리카셋이 만든 파드 하나의 labels를 지우면, 레플리카셋 입장에선 라벨 맞는 파드가 2개로 줄었으므로 **새 파드를 하나 더 만듭니다.** 라벨을 지운 파드는 더 이상 관리 대상이 아니라서 수동으로 만든 파드와 같은 신세가 되고, 레플리카셋을 지워도 남아 있어서 직접 삭제해야 합니다.

여기서 오해하지 말아야 할 점은 레플리카셋의 목적이 **파드를 생성하는 것이 아니라 일정 개수의 파드를 유지하는 것**이라는 점입니다. 적으면 만들고, 많으면 지워서 replicas 숫자에 맞춰 바람직한 상태를 만듭니다.

몇 가지 덧붙이면 이렇습니다.

- 이 실험들은 이해를 돕기 위한 것이고, 레플리카셋과 같은 라벨의 파드를 직접 만드는 건 바람직하지 않음
- `kubectl edit`은 모든 종류의 오브젝트에 쓸 수 있고, YAML에 적지 않은 상세 설정까지 보여줌. 레플리카셋이 만든 파드에는 **ownerReferences** 항목에 자기를 만든 레플리카셋 정보가 들어 있음. 소유자(owner)가 삭제되면 딸린 리소스도 같이 삭제되는 구조
- selector처럼 두 리소스의 라벨을 일치시켜 기능을 쓰는 경우가 앞으로 자주 나오니, 라벨에 친숙해지는 게 좋음

## 6.4 디플로이먼트(Deployment) : 레플리카셋, 파드의 배포를 관리

### 6.4.1 디플로이먼트 사용하기

실제 운영 환경에서는 레플리카셋을 YAML로 직접 쓰는 경우가 거의 없습니다. 대부분 레플리카셋과 파드의 정보를 함께 정의하는 **디플로이먼트**를 씁니다. 디플로이먼트는 앞으로 파드와 함께 가장 많이 보게 될 오브젝트예요.

**deployment-nginx.yaml**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-nginx-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-nginx
  template:
    metadata:
      name: my-nginx-pod
      labels:
        app: my-nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.10
        ports:
        - containerPort: 80
```

레플리카셋 YAML에서 kind만 Deployment로 바뀐 것과 거의 같습니다.

- `kubectl apply -f deployment-nginx.yaml`로 생성
- `kubectl get deployment` (또는 `deploy`): READY 3/3
- `kubectl get replicasets`: 디플로이먼트가 만든 레플리카셋이 **자동으로** 하나 생겨 있음
- `kubectl get pods`: 레플리카셋이 만든 파드 3개

즉 **디플로이먼트가 레플리카셋을 만들고, 레플리카셋이 파드를 만드는** 구조입니다. 그래서 디플로이먼트를 삭제하면 레플리카셋과 파드도 함께 삭제됩니다 (`kubectl delete deploy my-nginx-deployment`).

이름을 보면 my-nginx-deployment-**85d657c94d**-84trw처럼 중간에 해시값이 붙어 있는데, 이 해시는 파드 템플릿으로부터 계산된 값입니다. 다음 절에서 왜 중요한지 나옵니다.

### 6.4.2 디플로이먼트를 사용하는 이유

레플리카셋만으로도 파드 개수 유지는 되는데 왜 상위 개념인 디플로이먼트를 쓸까요? 핵심 이유는 **애플리케이션의 업데이트와 배포를 더욱 편하게 하기 위해서**입니다. Deploy라는 단어 그대로 배포와 관리를 담당해요.

- 업데이트할 때마다 레플리카셋 변경 사항을 **리비전(revision)**으로 남겨서 롤백 가능
- 무중단 서비스를 위한 **롤링 업데이트** 전략 지정 가능

실습 흐름은 다음과 같습니다.

1. `kubectl apply -f deployment-nginx.yaml --record`로 디플로이먼트 생성
2. 이미지 버전 변경: `kubectl set image deployment my-nginx-deployment nginx=nginx:1.11 --record`. `nginx=nginx:1.11`은 템플릿의 containers 중 name이 nginx인 컨테이너의 이미지를 nginx:1.11로 바꾸라는 뜻. YAML에서 image를 직접 고쳐 `kubectl apply -f` 하거나 `kubectl edit`을 써도 똑같음
3. `kubectl get pods`: 해시값이 67fff69f59인 새 파드들로 바뀌어 있음
4. `kubectl get replicasets`: 레플리카셋이 **2개**. 67fff69f59(새 버전, nginx:1.11)는 파드 3개, 85d657c94d(첫 버전, nginx:1.10)는 replicas가 0인 채로 **삭제되지 않고 남아 있음**
5. `kubectl rollout history deployment my-nginx-deployment`: 리비전 목록과 각 변경을 일으킨 명령(CHANGE-CAUSE) 확인
6. `kubectl rollout undo deployment my-nginx-deployment --to-revision=1`: 리비전 1로 롤백. 다시 rs를 보면 85d657c94d가 3개, 67fff69f59가 0개로 바뀌어 있음

포인트는 4번입니다. 디플로이먼트는 업데이트할 때 이전 레플리카셋을 지우지 않고 파드 수만 0으로 줄여 리비전으로 보존해 둡니다. 그래서 언제든 되돌릴 수 있어요. 게임 세이브 파일을 여러 개 남겨두는 것과 비슷합니다.

함께 알아둘 내용은 다음과 같습니다.

- 파드 템플릿에서 계산된 해시값은 각 레플리카셋의 라벨 셀렉터에 **pod-template-hash**라는 라벨로 자동 설정됨. 그래서 여러 레플리카셋이 겹치지 않는 라벨로 파드를 관리함 (`kubectl get replicasets --show-labels`로 확인)
- `kubectl describe deploy my-nginx-deployment`로 현재 리비전 번호와 활성화된 레플리카셋(NewReplicaSet) 확인 가능
- **-record 옵션은 1.32 기준 deprecated**라서 나중에 삭제될 수 있음. 에러가 나면 빼고 실습해도 되고, 빼더라도 이전 레플리카셋은 보존되지만 CHANGE-CAUSE가 <none>으로 표시될 뿐

이처럼 디플로이먼트는 여러 레플리카셋을 관리하기 위한 상위 오브젝트이고, 리비전 관리와 다양한 롤링 업데이트 정책을 쓸 수 있어서 쿠버네티스도 공식적으로 디플로이먼트 사용을 권장합니다. 롤링 업데이트 전략은 11.3절에서 다시 다루니, 지금은 **디플로이먼트는 레플리카셋의 상위 오브젝트이며 일반적으로 디플로이먼트를 통해 파드를 생성한다** 정도만 알면 됩니다.

### 리소스 정리

이번 실습에서 만든 리소스를 모두 삭제하고 넘어갑니다.

```
kubectl delete deployment,pod,rs --all
```

## 6.5 서비스(Service) : 파드를 연결하고 외부에 노출

지금까지 파드에 접근하려면 describe로 IP를 알아내 클러스터 내부에서 접근해야 했습니다. 여기엔 문제가 있습니다.

- 파드 IP는 로컬 개발 환경이나 클러스터 내부에서만 쓸 수 있음
- 파드 IP는 **영속적이지 않아** 항상 변할 수 있음. 레플리카셋이 파드를 새로 만들 때마다 IP가 바뀐다고 생각하면 됨
- 여러 디플로이먼트를 하나의 애플리케이션으로 연동하려면 파드 IP가 아닌, **서로를 발견(Discovery)할 수 있는 방법**이 필요

도커에서는 `-p` 옵션으로 컨테이너를 만들자마자 외부에 노출했고, 오버레이 네트워크나 사용자 정의 네트워크, `--link` 옵션으로 이름 기반 접근도 했습니다. 하지만 쿠버네티스는 디플로이먼트를 만들 때 파드를 외부로 노출하지 않습니다. 디플로이먼트 YAML의 `containerPort`는 단지 **파드의 애플리케이션이 쓸 내부 포트를 정의한 것**일 뿐이에요.

이 포트를 외부에 노출하거나 다른 디플로이먼트의 파드가 내부적으로 접근하게 하려면 **서비스**라는 별도 오브젝트를 만들어야 합니다. 서비스의 핵심 기능은 세 가지입니다.

- 여러 개의 파드에 쉽게 접근할 수 있도록 **고유한 도메인 이름** 부여
- 여러 개의 파드에 접근할 때 요청을 분산하는 **로드 밸런서** 기능
- 클라우드 플랫폼의 로드 밸런서, 클러스터 노드의 포트 등을 통해 **파드를 외부로 노출**

참고로 파드끼리의 통신 자체는 설치할 때 깔았던 calico 같은 네트워크 플러그인의 오버레이 네트워크 덕분에 가능합니다. 플러그인마다 기능과 성능 차이는 있지만, 핵심 기능을 쓰는 데는 큰 문제가 없습니다.

### 6.5.1 서비스(Service)의 종류

실습용으로 파드의 호스트 이름을 응답해주는 웹 서버 디플로이먼트를 먼저 만듭니다.

**deployment-hostname.yaml (핵심 부분)**

```yaml
kind: Deployment
metadata:
  name: hostname-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: webserver
  template:
    metadata:
      name: my-webserver
      labels:
        app: webserver
    spec:
      containers:
      - name: my-webserver
        image: alicek106/rr-test:echo-hostname
        ports:
        - containerPort: 80
```

`kubectl get pods -o wide`로 각 파드의 IP를 확인하고 임시 debug 파드에서 curl을 날려보면 Hello, hostname-deployment-xxx처럼 파드 이름이 응답으로 옵니다.

서비스는 **파드에 어떻게 접근할 것인가**에 따라 종류가 나뉘므로, 목적에 맞는 종류를 골라야 합니다. 주로 쓰는 건 세 가지예요.

- **ClusterIP**: 쿠버네티스 내부에서만 파드에 접근. 외부 노출 없음. 클러스터 내부에서만 쓰는 파드에 적합
- **NodePort**: 파드에 접근할 수 있는 포트를 클러스터의 **모든 노드**에 동일하게 개방. 외부에서 접근 가능. 포트는 랜덤으로 정해지지만 지정도 가능
- **LoadBalancer**: 클라우드 플랫폼의 로드 밸런서를 동적으로 프로비저닝해 파드에 연결. 외부 접근 가능하고, 일반적으로 AWS, GCP 같은 클라우드 환경에서만 사용

정리하면 내부 전용이면 ClusterIP, 외부에서도 접근하려면 NodePort, 실제 운영 환경이면 LoadBalancer입니다.

### 6.5.2 ClusterIP 타입의 서비스 – 쿠버네티스 내부에서만 파드에 접근하기

**hostname-svc-clusterip.yaml**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: hostname-svc-clusterip
spec:
  ports:
    - name: web-port
      port: 8080
      targetPort: 80
  selector:
    app: webserver
  type: ClusterIP
```

- **spec.selector**: 어떤 라벨의 파드에 접근할지 결정. `app: webserver` 라벨을 가진 파드(위 디플로이먼트의 파드들)가 접근 대상이 됨. 레플리카셋과 똑같이 **라벨로 연결**된다는 점이 핵심이고, 쿠버네티스의 라벨은 단순한 부가 정보 이상의 기능을 가짐
- **spec.ports.port**: 서비스는 클러스터 내부 전용 고유 IP(ClusterIP)를 할당받는데, 그 IP로 접근할 때 쓰는 포트
- **spec.ports.targetPort**: selector로 선택된 파드들이 내부적으로 쓰는 포트. 파드 템플릿의 containerPort와 같은 값이어야 함
- **spec.type**: 서비스 종류

port와 targetPort는 **서비스의 8080으로 들어온 요청을 파드의 80으로 넘겨준다**고 기억하면 됩니다. 도커의 `-p 8080:80`과 비슷한 느낌이에요.

동작 확인은 다음과 같습니다.

- `kubectl apply -f hostname-svc-clusterip.yaml`
- `kubectl get services` (또는 `svc`): hostname-svc-clusterip가 CLUSTER-IP 10.101.98.33, PORT 8080/TCP로 생성됨
- 만든 적 없는 **kubernetes**라는 서비스도 보이는데, 파드 내부에서 쿠버네티스 API에 접근하기 위한 서비스로 10장에서 다룸
- debug 파드에서 `curl 10.101.98.33:8080`을 여러 번 날리면 **매번 다른 파드 이름**이 응답으로 옴. 별도 설정 없이도 서비스가 연결된 파드들에 대해 자동으로 **로드 밸런싱**을 해주는 것

서비스는 IP뿐 아니라 **서비스 이름**으로도 접근됩니다(`curl hostname-svc-clusterip:8080`). 쿠버네티스는 내부 DNS를 구동하고 있고, 파드들은 자동으로 이 DNS를 쓰도록 설정되기 때문이에요.

실무에서 파드끼리 서로를 찾아 연결할 때는 파드 IP 대신 이 **서비스 이름**을 씁니다. 예를 들어 Spring 백엔드가 다른 마이크로서비스를 부를 때 접속 주소에 서비스 이름을 적어두는 식이에요. 파드가 재생성돼 IP가 바뀌어도 서비스 이름은 그대로니까 문제가 없습니다.

ClusterIP 서비스로 파드에 접근하는 과정을 정리하면 이렇습니다.

1. 특정 라벨의 파드를 연결하기 위해 서비스 YAML에 selector 정의
2. 파드에 접근할 때 쓰는 포트(containerPort)를 targetPort에 정의
3. port 항목에 8080을 명시해 서비스의 Cluster IP와 8080 포트로 접근하게 설정
4. `kubectl apply -f`로 생성하면 서비스는 클러스터 내부에서만 쓸 수 있는 고유한 내부 IP를 할당받음
5. 클러스터 내부에서 서비스 IP 또는 서비스 이름으로 파드에 접근

단, ClusterIP 타입은 외부에서는 접근할 수 없습니다. 외부 노출이 필요하면 NodePort나 LoadBalancer를 써야 합니다.

참고로 서비스의 selector와 파드 라벨이 매칭되면, 쿠버네티스는 **엔드포인트(endpoint)**라는 오브젝트를 서비스와 같은 이름으로 자동 생성합니다. `kubectl get endpoints`(또는 `ep`)로 보면 서비스가 실제로 가리키는 파드 IP:포트 목록, 즉 서비스의 도착점이 나와요. 자동 생성되니 자세히 알 필요는 없습니다. 다만 엔드포인트는 **엔드포인트 슬라이스(endpointslices)**로 대체되는 중이고 1.33부터 deprecated라서, ep 명령이 안 되면 `kubectl get endpointslices`를 쓰면 됩니다.

서비스 삭제는 `kubectl delete svc hostname-svc-clusterip` 또는 `kubectl delete -f hostname-svc-clusterip.yaml`입니다.

### 6.5.3 NodePort 타입의 서비스 – 서비스를 이용해 파드를 외부에 노출하기

NodePort는 이름 그대로 **모든 노드(Node)의 특정 포트(Port)를 개방해** 서비스에 접근하는 방식입니다. 스웜 모드에서 컨테이너를 외부로 노출하던 방식과 비슷해요.

YAML은 ClusterIP와 똑같고 **type만 NodePort**로 바꾸면 됩니다. 동작 방식만 다를 뿐 같은 서비스 리소스라서 selector, 포트 설정 같은 기본 사용법은 모두 동일합니다.

```yaml
metadata:
  name: hostname-svc-nodeport
spec:
  ports:
    - name: web-port
      port: 8080
      targetPort: 80
  selector:
    app: webserver
  type: NodePort
```

`kubectl apply -f hostname-svc-nodeport.yaml` 후 `kubectl get services`를 보면 TYPE이 NodePort, PORT(S)가 **8080:31514/TCP**로 나옵니다. 31514가 **모든 노드에서 동일하게 접근할 수 있는 포트**예요. `kubectl get nodes -o wide`로 노드의 INTERNAL-IP, EXTERNAL-IP를 확인한 뒤 어느 노드든 IP:31514로 접속하면 같은 서비스에 연결됩니다. 실제로 노드 3대(10.43.0.30, .31, .32)에 각각 curl을 보내면 모두 응답이 오고, 응답하는 파드도 매번 달라집니다.

내부 IP로 접근하려면 클러스터 내부에 접속한 상태여야 하고, 외부 IP로 테스트하려면 방화벽을 열어야 합니다. GKE는 별도 방화벽 규칙을 추가해야 하고(`gcloud compute firewall-rules create ...`), AWS도 Security Group에 Inbound 규칙을 추가하지 않으면 NodePort 통신이 실패할 수 있습니다.

노드에 개방되는 포트는 기본적으로 30000번대 범위에서 랜덤으로 선택되지만, YAML에 `nodePort` 항목을 정의하면 원하는 포트를 고를 수 있습니다.

```yaml
spec:
  ports:
  - name: web-port
    port: 8080
    targetPort: 80
    nodePort: 31000
```

이제 포트 항목이 세 개가 되었으니 정리해 두면 좋습니다.

- **nodePort (31000)**: 노드에 열리는 포트. 외부에서 노드IP:31000으로 접근
- **port (8080)**: 서비스(ClusterIP)가 받는 포트. 내부에서 서비스IP:8080 또는 서비스이름:8080으로 접근
- **targetPort (80)**: 최종적으로 요청이 도착하는 파드의 포트

포트 범위 자체를 바꾸려면 API 서버 실행 옵션에 `--service-node-port-range=30000-35000`처럼 지정합니다. 너무 낮은 포트는 시스템 예약 포트일 수 있으니 기본 범위인 30000번 이상을 쓰는 게 좋아요. (책에는 기본 범위가 30000~32768로 적혀 있는데, 공식 기본값은 30000~32767입니다.)

그런데 이상한 점이 하나 있습니다. NodePort 서비스인데도 CLUSTER-IP 항목에 내부 IP(10.110.9.251)가 할당돼 있어요. 실제로 debug 파드에서 `curl 10.110.9.251:8080`이나 `curl hostname-svc-nodeport:8080`을 해보면 잘 됩니다. 이는 **NodePort 타입의 서비스가 ClusterIP의 기능을 포함하고 있기 때문**입니다. 그래서 NodePort 서비스는 내부 네트워크와 외부 네트워크 양쪽에서 접근할 수 있습니다. 트래픽 흐름으로 정리하면 이렇습니다.

1. 외부에서는 각 노드에 개방된 포트(31514)로 요청을 보내고, 요청은 서비스에 연결된 파드 중 하나로 라우팅됨
2. 클러스터 내부에서는 ClusterIP 타입과 동일하게 접근

다만 실제 운영 환경에서 NodePort로 서비스를 직접 외부에 제공하는 경우는 많지 않습니다. 포트 번호를 80이나 443으로 설정하기에 적절하지 않고, SSL 인증서 적용이나 라우팅 같은 복잡한 설정을 하기 어렵기 때문이에요. 그래서 NodePort는 **인그레스(Ingress)**라는 오브젝트에서 간접적으로 쓰이는 경우가 많습니다. 인그레스는 8장에서 나오고, 지금은 외부 요청을 실제로 받아들이는 관문 정도로 알면 됩니다. 이 절에서 배운 LoadBalancer와 NodePort를 합치면 인그레스를 쓸 수 있게 됩니다.

참고로 특정 클라이언트의 요청을 항상 같은 파드가 처리하게 하려면 서비스 spec에 `sessionAffinity: ClientIP`를 설정합니다. 세션을 서버 메모리에 저장하는 애플리케이션이라면 필요할 수 있어요. (백엔드 설계상으로는 Redis 같은 외부 세션 저장소를 쓰는 편이 더 일반적입니다.)

### 6.5.4 클라우드 플랫폼의 로드 밸런서와 연동하기 – LoadBalancer 타입의 서비스

LoadBalancer 타입은 서비스를 만드는 순간 **로드 밸런서를 새로 생성해** 파드와 연결합니다. NodePort는 각 노드의 IP를 알아야 접근할 수 있었지만, LoadBalancer는 클라우드가 도메인 이름과 IP를 할당해 주기 때문에 더 쉽게 파드에 접근할 수 있어요.

단, **로드 밸런서를 동적으로 생성하는 기능을 제공하는 환경에서만** 쓸 수 있습니다. 보통 AWS, GCP 같은 클라우드 환경이고, 가상 머신이나 온프레미스에서는 쓰기 어렵습니다. 책은 AWS는 kops로 설치한 클러스터, GCP는 GKE를 기준으로 설명합니다. AWS에서 클라우드 프로바이더를 설정해 kubeadm으로 설치한 클러스터를 써도 됩니다.

**hostname-svc-lb.yaml**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: hostname-svc-lb
spec:
  ports:
    - name: web-port
      port: 80
      targetPort: 80
  selector:
    app: webserver
  type: LoadBalancer
```

이번에는 `port`를 80으로 했습니다. LoadBalancer에서 port는 **로드 밸런서에 접근하기 위한 포트**이기 때문이에요.

`kubectl get svc` 결과에서 눈여겨볼 곳은 **EXTERNAL-IP**입니다.

- AWS라면 a5f81...elb.amazonaws.com 같은 로드 밸런서 주소가 자동 할당됨 (GKE는 DNS 이름이 아닌 IP로 표시)
- 이 주소와 80 포트(ports.port)로 curl을 보내면 파드에 접근되고, 다른 타입과 마찬가지로 요청은 여러 파드로 로드 밸런싱됨
- CLUSTER-IP도 할당돼 있어서 파드에서는 서비스 IP나 이름으로 접근 가능

그런데 PORT(S)를 보면 `80:32620/TCP`로 나옵니다. 32620은 **각 노드에서 동일하게 접근할 수 있는 포트**예요. 실제로 노드IP:32620으로 curl을 해도 접속됩니다. LoadBalancer를 만들었는데 왜 이 포트가 열렸을까요? LoadBalancer 서비스가 파드로 요청을 전달하는 원리 때문입니다.

1. LoadBalancer 서비스가 생성되면 모든 워커 노드에 파드에 접근할 수 있는 랜덤 포트(32620)가 개방됨
2. 클라우드에서 생성된 로드 밸런서로 요청이 들어오면, 워커 노드 중 하나의 32620 포트로 전달됨
3. 워커 노드로 전달된 요청은 파드 중 하나로 전달되어 처리됨

AWS 콘솔에서 로드 밸런서를 확인하면 모든 워커 노드가 등록돼 있고, 요청이 각 워커의 32620 포트로 전달되는 걸 볼 수 있습니다. 즉 LoadBalancer 타입을 명시했지만 **NodePort의 기능도 간접적으로 자동 사용**하고 있는 셈이에요. LoadBalancer는 NodePort 앞에 클라우드 로드 밸런서를 하나 더 세운 것이라고 이해하면 정확합니다.

AWS 콘솔에서 유형을 보면 classic으로 생성돼 있습니다. AWS 클라우드 컨트롤러 매니저는 아무 설정이 없으면 클래식 로드 밸런서를 만들기 때문이에요. NLB(네트워크 로드 밸런서)를 쓰고 싶다면 metadata에 주석(annotation)을 추가합니다.

```yaml
metadata:
  name: hostname-svc-nlb
  annotations:
    service.beta.kubernetes.io/aws-load-balancer-type: "nlb"
```

- *주석(annotations)**은 라벨처럼 리소스의 추가 정보를 나타내는 키-값 쌍입니다. 그런데 리소스 종류에 따라 쿠버네티스에 **미리 정의된 특별한 주석**들이 있어서, 이걸 붙이면 리소스에 특별한 설정을 줄 수 있어요. 위 예시는 클래식 대신 NLB를 만들라는 설정입니다. 앞으로 자주 등장하니 라벨과 함께 익숙해지면 좋습니다. 둘을 구분하자면 라벨은 selector로 **선택되어 오브젝트끼리 서로를 찾는 데** 쓰이고, 주석은 선택용이 아닌 **추가 정보나 설정값**입니다.

사실 쿠버네티스 자체만으로는 특정 클라우드에 종속적인 로드 밸런서를 만들 수 없습니다. 이게 가능하려면 **클라우드 컨트롤러 매니저(Cloud Controller Manager, CCM)**라는 컴포넌트가 설치돼 있어야 하는데, kops는 설치할 때 CCM을 기본으로 깔아줘서 쉽게 된 거예요. `kubectl get po -n kube-system`으로 보면 aws-cloud-controller-manager 파드가 떠 있습니다. CCM은 클라우드마다 사용법이 달라서 책에서는 자세히 다루지 않으며, **ELB나 NLB처럼 특정 클라우드에 종속적인 외부 기능을 쓰려면 별도의 쿠버네티스 컴포넌트가 필요하다** 정도로 이해하면 충분합니다.

로드 밸런서 사용을 마쳤다면 서비스를 삭제합니다. 서비스를 지우면 **AWS에 생성된 로드 밸런서도 함께 삭제**됩니다. 반대로 말하면 실습 후에 안 지우고 두면 로드 밸런서 요금이 계속 나가니 꼭 정리하세요.

```
kubectl delete -f hostname-svc-lb.yaml
```

#### 온프레미스 환경에서 LoadBalancer 타입의 서비스 사용하기

LoadBalancer 타입은 일반적으로 클라우드에서 쓰이지만, 필요하다면 직접 보유한 온프레미스 서버에서도 쓸 수 있습니다. 단, 쿠버네티스가 이 기능을 직접 제공하는 것은 아니고, **MetalLB**나 오픈스택 같은 특수한 환경을 직접 구축해야 합니다. MetalLB를 쓰면 비교적 쉽게 LoadBalancer 타입을 쓸 수 있지만, 쿠버네티스 공식 프로젝트가 아니라서 유지보수가 지속적이지 않을 수 있다는 점에 유의해야 합니다. 관심이 있다면 MetalLB 공식 설치 문서를 참고하면 됩니다.

### 6.5.5 트래픽의 분배를 결정하는 서비스 속성 : externalTrafficPolicy

LoadBalancer나 NodePort로 들어온 요청은 노드 하나로 간 다음, 거기서 다시 파드 중 하나로 전달됩니다. 그런데 이 원리가 경우에 따라 비효율적일 때가 있습니다.

워커 노드 A에 파드 a, 노드 B에 파드 b가 있다고 해봅시다. 모든 노드에 같은 포트가 열려 있으니, 노드 A로 들어온 요청은 (1) A의 파드 a 또는 (2) B의 파드 b로 전달될 수 있어요. A로 들어온 요청은 A 안의 파드 a가 처리하면 충분한데, 굳이 B의 파드 b로 넘어가면 문제가 생깁니다.

- *불필요한 네트워크 홉(hop)**이 한 단계 더 생김
- 노드 간 리다이렉트로 트래픽의 출발지 주소가 바뀌는 **SNAT**이 발생해서, **클라이언트의 IP 주소가 보존되지 않음**

클라이언트 IP가 사라진다는 건, 예를 들어 Spring 서버에서 요청자 IP를 로그로 남기거나 IP 기반 제한을 걸 때 실제 사용자 IP 대신 노드 IP가 찍힐 수 있다는 뜻입니다.

이 동작은 서비스의 `externalTrafficPolicy` 항목이 결정합니다. `kubectl get svc hostname-svc-nodeport -o yaml`로 서비스의 모든 속성을 출력해 보면 기본값이 **Cluster**로 돼 있어요. `-o` 옵션으로 yaml이나 json 형식으로 출력하면 쿠버네티스가 자동으로 설정한 상세 항목까지 모두 볼 수 있어서 디버깅할 때 유용합니다.

- **Cluster (기본값)**: 클러스터의 모든 노드에 랜덤 포트를 개방하고, 어느 노드로 들어온 요청이든 클러스터 전체의 파드 중 하나로 전달. 지금까지 사용한 NodePort, LoadBalancer의 기본 동작
- **Local**: 파드가 생성된 노드에서만 파드로 접근할 수 있고, 로컬 노드의 파드 중 하나로 요청이 전달됨. 추가 네트워크 홉이 없고 클라이언트 IP도 보존됨 (파드의 소스 코드에서 실제 클라이언트 IP 확인 가능)

Local로 실습해 보면 차이가 확실히 보입니다.

```yaml
spec:
  externalTrafficPolicy: Local
  ports:
    - name: web-port
      port: 80
      targetPort: 80
  selector:
    app: webserver
  type: LoadBalancer
```

1. 위 YAML(hostname-svc-lb-local.yaml)로 서비스 생성
2. `kubectl scale --replicas=1 deployment hostname-deployment`로 파드를 1개로 줄임. `kubectl scale`은 디플로이먼트의 파드 개수를 바로 바꾸는 명령어
3. `kubectl get pods -o wide`로 보면 파드가 ip-10-43-0-31 노드에만 있음
4. 각 노드IP:30641로 curl을 보내면 **파드가 있는 10.43.0.31에서만 응답**이 오고, 나머지 노드는 응답 없음
5. AWS 콘솔에서도 파드가 있는 노드 하나만 InService, 나머지는 OutOfService로 표시됨. 로드 밸런서가 파드가 없는 노드로는 요청을 전달하지 않는 것

그렇다고 Local이 무조건 좋은 건 아닙니다. 파드가 노드마다 고르게 스케줄링되지 않으면 **요청이 고르게 분산되지 않을 수 있어요.** 노드 A에 파드 2개, 노드 B에 파드 1개가 있다면, 로드 밸런서는 노드 단위로 50%씩 나누므로 노드 A의 두 파드는 각각 25%, 노드 B의 파드 하나는 혼자 50%를 받습니다. 특정 파드에 부하가 몰리니 자원 활용률(utilization) 측면에서 바람직하지 않죠. 11.2절의 **PodAntiAffinity** 같은 스케줄링 기능으로 파드를 노드에 최대한 고르게 배포하면 이 단점을 어느 정도 해결할 수 있습니다.

결국 Cluster와 Local은 둘 다 장단점이 있어서 뚜렷한 정답은 없습니다. 불필요한 홉으로 인한 레이턴시나 클라이언트 IP 보존이 중요하지 않다면 Cluster를, 반대라면 Local을 고려하면 됩니다.

참고로 **internalTrafficPolicy**도 있습니다. externalTrafficPolicy의 개념을 클러스터 내부 트래픽에 적용한 것이에요.

- 기본값은 Cluster: 서비스에 연결된 모든 파드로 트래픽 전달 (지금까지 본 동작)
- Local로 설정하면 요청을 보낸 클라이언트와 **같은 노드에 있는 파드로만** 요청 전달. 네트워크 요청이 같은 노드 안에서 처리되니 시간이 단축됨
- 단, 클라이언트가 있는 노드에 파드가 없으면 다른 노드에 파드가 있더라도 **서비스 요청이 실패함**

### 6.5.6 요청을 외부로 리다이렉트하는 서비스 : ExternalName

서비스는 ClusterIP, NodePort, LoadBalancer 세 가지만 알아도 충분하지만, 쿠버네티스를 **외부 시스템과 연동**해야 할 때는 ExternalName 타입을 쓸 수 있습니다.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: externalname-svc
spec:
  type: ExternalName
  externalName: my.database.com
```

- 쿠버네티스 내부 파드들이 externalname-svc라는 이름으로 요청을 보내면, 쿠버네티스 DNS가 my.database.com으로 접근하도록 **CNAME 레코드**를 반환함
- 즉 externalname-svc로 요청하면 실제로는 my.database.com에 접근하게 됨
- selector도 연결된 파드도 없고, 외부 도메인에 붙인 내부 별명이라고 생각하면 됨
- 쿠버네티스와 별개로 존재하는 레거시 시스템과 연동할 때 유용

백엔드 관점에서 예를 들면, Spring 애플리케이션 설정에는 DB 주소로 externalname-svc만 적어두고 실제 주소는 AWS RDS 엔드포인트로 연결해 두는 식입니다. 나중에 DB 주소가 바뀌어도 애플리케이션 설정은 그대로 두고 서비스의 externalName만 바꾸면 돼요.

DNS 레코드도 복습해 두면 좋습니다.

- **CNAME 레코드**(Canonical Name): 도메인을 가리키는 **다른 이름**. externalname-svc → my.database.com
- **A 레코드**: 도메인 이름이 **IP로** 직접 변환되는 경우. hostname-svc-nodeport → 10.110.9.251 (일반 서비스는 이쪽)

- `kubectl exec -it <파드> [-c 컨테이너] -- bash`: 컨테이너 내부 접속
- `kubectl logs <파드>`: 로그
- `kubectl edit <종류> <이름>`: 실행 중인 리소스 바로 수정
- `kubectl delete -f <파일 또는 디렉터리>`, `kubectl delete <종류> <이름>`: 삭제
- `kubectl run -i --tty --rm debug --image=alicek106/ubuntu:curl --restart=Never bash`: 임시 테스트 파드
- `kubectl scale --replicas=N deployment <이름>`: 파드 개수 즉시 변경
- `kubectl set image deployment <이름> <컨테이너>=<이미지>`: 이미지 변경
- `kubectl rollout history deployment <이름>`, `kubectl rollout undo deployment <이름> --to-revision=N`: 리비전 확인과 롤백
- `kubectl get po -n kube-system`: 시스템 컴포넌트 파드 확인

**헷갈리기 쉬운 포인트**

- containerPort를 적어도 외부 노출은 안 됨. 외부에 열려면 서비스가 필요
- 레플리카셋과 서비스는 둘 다 라벨과 selector로 파드를 찾음. 6장 전체를 관통하는 개념
- 레플리카셋은 파드를 만드는 게 아니라 개수를 유지함
- 디플로이먼트는 업데이트할 때 예전 레플리카셋을 지우지 않고 replicas 0으로 보관해서 롤백 가능
- 서비스 타입은 포함 관계: ClusterIP ⊂ NodePort ⊂ LoadBalancer
- 포트 3종 세트: nodePort(노드) → port(서비스) → targetPort(파드)
- 파드끼리 통신할 땐 파드 IP 말고 서비스 이름을 씀
- externalTrafficPolicy: Cluster는 고른 분산 대신 홉 추가와 클라이언트 IP 손실, Local은 홉 없고 IP 보존 대신 부하 불균형 가능
