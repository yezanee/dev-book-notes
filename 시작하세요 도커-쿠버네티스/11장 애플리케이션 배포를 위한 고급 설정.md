## 11.1 파드의 자원 사용량 제한

쿠버네티스의 장점은 여러 서버를 묶어 하나의 리소스 풀처럼 쓰는 것입니다. 자원이 부족하면 서버를 추가하는 **스케일 아웃**도 중요하지만, 그만큼 중요한 것이 이미 가진 자원을 빠짐없이 쓰는 **자원 활용률(Utilization)** 을 높이는 일입니다.

- 놀고 있는 컨테이너에 자원을 너무 많이 줬다면 활용률이 낮은 상태
- 그래서 컨테이너별 자원 사용량을 적절히 제한하고, 남는 자원을 어떻게 쓸지 전략이 필요
- 이번 절의 흐름: 기본적인 자원 할당 방법 → 활용률을 높이는 오버커밋 → ResourceQuota, LimitRange

참고 용어로, 서버 대수를 늘리는 것은 스케일 아웃, 기존 서버 스펙을 올리는 것은 스케일 업입니다.

### 11.1.1 컨테이너와 파드의 자원 사용량 제한 : Limits

도커에서 배운 것 복습부터 시작합니다. `docker run`에는 `--memory`(최대 메모리), `--cpus`, `--cpu-shares`, `--cpu-quota`, `--cpu-runtime` 같은 옵션이 있었고, 이 중 `--cpu-shares`는 고정 할당량이 아니라 **비율**이라는 점이 특별했습니다. 아무 옵션도 안 주면 컨테이너는 호스트의 CPU, 메모리를 전부 쓸 수 있었습니다.

쿠버네티스도 내부적으로 도커와 똑같이 리눅스의 **cgroup**을 쓰기 때문에 같은 원리로 제한할 수 있습니다. 지금까지 만든 파드들은 자원 제한이 없었으므로, 노드 자원을 다 써버려 노드 전체가 고갈될 위험이 있었습니다.

가장 간단한 해결책은 파드 YAML에 `resources.limits`를 적는 것입니다.

```yaml
spec:
  containers:
  - name: nginx
    image: nginx:latest
    resources:
      limits:
        memory: "256Mi"   # docker run --memory 256m 과 같음
        cpu: "1000m"      # docker run --cpus 1 과 같음 (1000m = CPU 1개)
```

- `m`은 밀리코어로, 1000m이 CPU 1개
- 파드 안에 컨테이너가 여러 개면 컨테이너마다 따로 자원을 지정할 수 있음

노드의 가용 자원은 `kubectl describe node <노드이름>`으로 확인합니다(도커의 `docker info`에 해당).

- `kubectl get pods -o wide`로 파드가 어느 노드에 떴는지 먼저 확인
- **Non-terminated Pods**: 그 노드에서 실행 중인 파드별 자원 할당량. 내가 만든 파드 외에 kube-system의 네트워크 핵심 컴포넌트(calico, coredns, kube-proxy 등)도 기본적으로 자원을 할당받아 보임
- **Allocated resources**: 노드에 있는 모든 파드의 할당량 합계
- ephemeral-storage는 컨테이너 내부 임시 저장 공간, attachable-volumes-aws-ebs는 AWS 인스턴스에 붙일 수 있는 EBS 개수로, 이것들도 쿠버네티스에서는 자원으로 취급

### 11.1.2 컨테이너와 파드의 자원 사용량 제한하기 : Requests

describe 출력에 처음 보는 **Requests**라는 항목이 있습니다.

- **Limits**: 컨테이너가 사용할 수 있는 최대치(상한선)
- **Requests**: **적어도 이만큼은 컨테이너에게 보장되어야 한다**는 최소치

Requests를 이해하려면 먼저 **오버커밋(Overcommit)** 을 알아야 합니다. 오버커밋은 실제 가진 자원보다 더 많은 양을 컨테이너들에게 할당해서 전체 활용률을 높이는 방법입니다.

**정적 할당의 문제 (그림 11.1)**

- 1GB 서버에 컨테이너 A, B를 만들고 각각 500MB씩 고정 할당
- A는 거의 안 쓰고 B는 500MB에 꽉 차 있음
- A의 남는 메모리를 B가 빌려 쓰면 좋겠지만, 제한이 고정이라 B는 500MB를 넘을 수 없음 → 활용률 저하

**오버커밋 적용 (그림 11.2)**

- 같은 1GB 서버에서 Limits를 750MB씩 두 컨테이너에 줌 (합 1.5GB)
- 실제로 1.5GB를 쓸 수 있는 건 아니지만, A가 적게 쓰면 B가 A의 남는 자원을 기회적으로 쓸 수 있음
- 앞서 만든 resource-limit-pod의 Limits가 바로 이 개념

**그런데 충돌이 생기면?**

A가 500MB를 쓰는 중에 B가 750MB를 쓰려고 하면 메모리 충돌이 납니다. 그래서 각 컨테이너가 **사용을 보장받을 수 있는 경계선**을 정하는데, 이것이 Requests입니다 (그림 11.3).

- A, B 모두 Requests 500MB, Limits 750MB라면 둘 다 500MB 안에서는 아무 문제 없음
- A가 500MB를 쓰는 중 B가 750MB를 시도하면 B는 A의 경계선을 침범하는 것이므로 B의 메모리 사용이 실패함 (메모리 실패는 OOM으로 처리, 뒤에서 설명)

YAML에서는 `resources.requests`로 지정합니다.

```yaml
resources:
  limits:
    memory: "256Mi"
    cpu: "1000m"
  requests:
    memory: "128Mi"
    cpu: "500m"
```

해석하면 **최소 128Mi는 보장되고, 남는 메모리가 있으면 최대 256Mi까지 쓸 수 있다**는 뜻입니다. CPU도 마찬가지로 최소 0.5 CPU 보장, 여유가 있으면 최대 1 CPU입니다.

**스케줄링 기준은 Limits가 아니라 Requests (그림 11.4)**

- Requests는 보장해야 하는 최소치이므로 노드 총 자원보다 많이 할당할 수 없음
- 스케줄러는 Requests만큼 여유가 있는 노드를 골라 파드를 배치함
- 예: 1GB 노드에 이미 Requests 500MB 파드가 있으면, Requests 500MB 파드는 들어가고 600MB 파드는 못 들어감
- Requests를 낮게 잡으면 배치는 잘 되지만 보장받는 자원은 줄어듦
- 반면 Limits의 합은 노드 물리 자원을 초과해도 됨 (이게 오버커밋)

### 11.1.3 CPU 자원 사용량의 제한 원리

#### 쿠버네티스에서의 CPU Requests와 Limits

- CPU는 m 단위, 1개 CPU = 1000m, CPU가 2개인 서버면 최대 2000m까지 Requests 할당 가능
- 0.5, 1.5처럼 그냥 숫자로 써도 됨 (0.5 = 500m)

**Limits.cpu = `docker run --cpus`**

`limits.cpu: 1000m`은 최대 CPU 1개만큼 사용 가능하다는 뜻이고, `--cpus 1` 또는 `--cpu-period 100000 --cpu-runtime 100000`과 같습니다.

**Requests.cpu = `docker run --cpu-shares`**

- `-cpu-shares` 복습 (그림 11.5):
- Case 1: A, B, C의 shares가 1024, 1024, 512이고 CPU가 포화 상태면 2:2:1 비율로 나눠 씀
- Case 2: 유휴 CPU가 있으면 shares 값과 상관없이 CPU를 전부 쓸 수도 있음

즉 shares(Requests)와 cpus(Limits)를 함께 쓰면 CPU에 오버커밋을 적용할 수 있습니다. 예를 들어 Limits 700m, Requests 500m인 컨테이너는 1개 CPU 중 최대 0.7개까지 쓸 수 있습니다 (그림 11.6).

**Requests가 실제 cpu shares로 바뀌는 식**

- `(Requests 밀리코어 값 × 1024) / 1000 = CPU Share 값`
- 500m이면 512가 컨테이너의 `-cpu-shares`로 설정됨
- cgroup v1에서만 cpu.shares를 쓰고, cgroup v2에서는 cpu.weight를 씀. 값의 스케일은 달라도 동작 원리는 같으니 cgroup 기능으로 Requests가 구현된다는 것만 알면 충분

**상황별 동작**

- 컨테이너가 하나뿐이면 Requests와 상관없이 Limits(700m)까지 사용
- 두 컨테이너(각각 Limits 700m, Requests 500m)가 CPU를 최대로 쓰려 하면 (그림 11.7): Requests 비율이 같으니 1:1로 나눠 씀. 결국 500m은 각자 보장되는 최소치. 1000m의 Requests를 다 소진했으므로 Requests를 가진 새 컨테이너는 더 할당할 수 없음
- 경합(Contention) 발생 시 (그림 11.8): A가 Requests 이상을 쓰는 중에 B가 자기 Requests만큼 쓰려 하면 A에 **CPU 스로틀(throttle)** 이 걸리고, B는 Requests만큼 확보함
- 할당되지 않은 여유 CPU가 남아 있는 경우 (그림 11.9): A Requests 500m, B 250m이면 남는 CPU도 Requests 비율인 2:1로 나눠 씀

**압축 가능 vs 압축 불가능 리소스**

- CPU는 **압축 가능(compressible)** 리소스: 경합이 나도 스로틀로 사용량을 억제하면 그만
- 메모리, 스토리지는 **압축 불가능(incompressible)** 리소스: 경합이 나면 우선순위가 낮은 컨테이너의 프로세스가 먼저 종료됨 (뒤의 QoS 클래스에서 설명)

참고로 1000m은 CPU 1개만큼의 **성능**이지 CPU 1개를 **독점**한다는 뜻이 아닙니다. 프로세스가 여러 CPU에 걸쳐 처리될 수 있어 컨텍스트 스위치나 캐시 미스로 성능이 떨어질 수 있으며, 특정 CPU를 배타적으로 쓰게 하려면 kubelet 옵션으로 **CPU Manager**를 설정해야 합니다.

### 11.1.4 QoS 클래스와 메모리 자원 사용량 제한 원리

중간 정리:

- 컨테이너는 최대 Limits까지 쓸 수 있고, 최소 Requests는 보장받음
- Requests보다 많이 쓰는 것이 오버커밋이고, 다른 컨테이너와 충돌하면 사용이 실패할 수 있음
- CPU는 경합이 나도 스로틀만 걸릴 뿐 컨테이너 자체엔 큰 문제 없음

그런데 메모리는 다릅니다. 이미 데이터가 적재되어 있어 압축할 수 없기 때문에, 쿠버네티스는 가용 메모리를 확보하려고 **우선순위가 낮은 파드나 프로세스를 강제로 종료**하도록 설계되어 있습니다. 종료된 파드는 다른 노드로 옮겨지는데 이를 **퇴거(Eviction)** 라고 합니다 (그림 11.10).

핵심 질문은 **노드에 메모리가 부족하면 어떤 파드가 먼저 종료돼야 하는가**이고, 이를 위해 쿠버네티스는 Limits와 Requests 값으로 우선순위를 계산하고 3가지 **QoS(Quality of Service) 클래스**를 파드에 붙입니다.

#### 쿠버네티스에서의 메모리 부족과 OOM(Out Of Memory)

**노드 Conditions**

- 노드에는 이상 상태를 나타내는 Conditions가 있고 `kubectl describe nodes | grep -A9 Conditions`로 확인
- 종류: MemoryPressure, DiskPressure 등. kubelet이 주기적으로 갱신
- 평소엔 MemoryPressure가 False, 가용 메모리가 부족해지면 True

**MemoryPressure가 True가 되면**

- 기본값은 가용 메모리 100Mi 이하일 때 발생
- 노드의 모든 파드에 순위를 매겨 가장 우선순위가 낮은 파드를 다른 노드로 퇴거시킴
- 그 노드에는 더 이상 새 파드를 할당하지 않음
- 우선순위는 QoS 클래스와 메모리 사용량으로 결정
- 이런 임계치를 **Hard Eviction Threshold**라고 하며 kubelet 옵션으로 조정 가능. DiskPressure가 True가 되면 사용하지 않는 도커 이미지를 자동 삭제하기도 함

**OOM Killer**

- kubelet이 MemoryPressure를 감지하기도 전에 메모리가 급격히 늘면, 리눅스의 **OOM Killer**가 우선순위 점수가 낮은 컨테이너의 프로세스를 강제 종료해 메모리를 확보함
- 점수는 두 가지: `oom_score_adj`(기본 조정값)와 `oom_score`(최종 점수). OOM Killer는 `oom_score`를 보고 종료 대상을 고름
- 모든 프로세스에 자동으로 점수가 매겨지며, **점수가 높을수록 종료되기 쉬움**
- 절대 죽으면 안 되는 핵심 프로세스는 매우 낮은 값을 받음. 예: kubelet은 -999 (`/proc/<PID>/oom_score_adj`로 확인)
- 메모리를 많이 쓸수록 최종 oom_score가 갱신됨
- 도커에서는 `-oom-score-adj` 옵션으로 직접 지정 가능

#### QoS 클래스의 종류 – (1) Guaranteed 클래스

- QoS 클래스는 BestEffort, Burstable, Guaranteed 3가지이며, 설정하지 않아도 자동으로 붙음
- `kubectl describe pod <이름> | grep QoS`로 확인
- **Limits와 Requests 값이 완전히 같을 때** Guaranteed
- 앞의 resource-limit-pod는 limits만 적었는데도 Guaranteed였음. **Requests 없이 Limits만 쓰면 Requests도 Limits와 같은 값으로 설정**되기 때문
- 명시적으로 만들려면 limits와 requests를 똑같이 적으면 됨
- 오버커밋이 허용되지 않으므로 할당받은 자원을 안정적으로 보장받음
- 내부 프로세스의 oom_score_adj가 -997로, 도커 데몬이나 kubelet과 거의 같은 수준으로 보호됨 → 시스템 컴포넌트가 요구하지 않는 한 강제 종료될 일이 없음
- 컨테이너가 여러 개면 **모든 컨테이너**의 Requests와 Limits가 같아야 Guaranteed

#### QoS 클래스의 종류 – (2) BestEffort 클래스

- Requests와 Limits를 **아예 설정하지 않은** 파드 (resources 항목 자체가 없음)
- 이번 장 이전에 만든 파드들은 전부 BestEffort
- Limits가 없으니 유휴 자원이 있으면 제한 없이 다 쓸 수 있지만, Requests도 없으니 보장받는 자원이 전혀 없음
- 즉 노드 자원을 전부 쓸 수도, 하나도 못 쓸 수도 있음

#### QoS 클래스의 종류 – (3) Burstable 클래스

- Requests와 Limits가 설정되어 있고 **Limits가 Requests보다 큰** 파드
- Requests만큼은 보장받고, 상황에 따라 Limits까지 순간적으로 확장(burst)해 쓸 수 있음
- 쉽게 구분하는 법: Guaranteed도 BestEffort도 아니면 전부 Burstable
- 예: limits 256Mi/1000m, requests 128Mi/500m인 resource-limit-with-request-pod
- Requests 안에서 쓰면 문제없지만, Requests를 넘어 Limits 범위를 쓰다 다른 파드와 경합하면 Requests보다 더 많이 쓰고 있는 파드나 프로세스의 우선순위가 낮아짐

#### QoS 클래스와 메모리 부족

- kubelet이 메모리 부족을 감지하면 우선순위가 가장 낮은 파드를 종료하고 다른 노드로 퇴거시킴
- 메모리가 급격히 늘면 OOM Killer가 OOM 점수가 가장 높은 컨테이너의 프로세스를 강제 종료할 수도 있음
- 퇴거된 파드는 다른 노드에서 다시 생성되고, OOM Killer로 종료된 프로세스의 컨테이너는 파드의 재시작 정책(restartPolicy)에 따라 다시 시작됨 (11.3절에서 자세히)
- OOM Killer는 **프로세스**를 죽이는 것이지 컨테이너나 파드를 죽이는 게 아님. init 프로세스가 아닌 다른 프로세스가 메모리를 많이 쓰면 그 프로세스만 종료될 수도 있음

**우선순위 순서**

- 기본: Guaranteed > Burstable > BestEffort
- 메모리가 부족하면 BestEffort가 먼저, 그다음 Burstable이 종료됨. Guaranteed는 더 낮은 파드가 없을 때 마지막으로 종료
- 단, 절대적이지 않음. Burstable과 BestEffort는 **메모리를 많이 쓸수록 우선순위가 낮아지므로** 현재 사용량에 따라 순서가 역전될 수 있음

#### 자원 오버커밋의 필요성

- 오버커밋은 원리가 복잡하고, 파드가 언제 얼마나 쓸지 예측하기 어려워 예상치 못한 문제가 생길 수 있음
- 이 장에서 자세히 다룬 건 **이런 방법도 가능하다**는 걸 보여주기 위함이지 필수가 아님
- 안정성이 꼭 필요하다면 모든 파드를 Limits = Requests로 맞춰 Guaranteed로 운영하는 것도 정답이 될 수 있음

### 11.1.5 ResourceQuota와 LimitRange

여러 개발팀이 쿠버네티스를 쓴다면 팀마다 클러스터를 주는 게 이상적이지만 관리가 번거롭고 비용도 큽니다. 대안은 팀별 네임스페이스를 만들고 롤, 롤 바인딩 같은 RBAC로 권한을 나누는 것인데, 한 네임스페이스가 자원을 과하게 쓰면 다른 네임스페이스가 자원 부족을 겪을 수 있습니다. 그래서 네임스페이스별 자원 한도를 정할 필요가 있고, 이를 위한 오브젝트가 **ResourceQuota**와 **LimitRange**입니다.

- ResourceQuota: 네임스페이스의 자원 사용량 제한
- LimitRange: 자원 할당의 기본값이나 범위 설정

#### 11.1.5.1 ResourceQuota로 자원 사용량 제한

ResourceQuota는 특정 네임스페이스에서 쓸 수 있는 **자원 사용량의 합**을 제한하는 오브젝트입니다.

- 할당 가능한 자원(CPU, 메모리, PVC 크기, 컨테이너 임시 스토리지 등)의 총합 제한
- 생성 가능한 리소스(서비스, 디플로이먼트 등)의 **개수** 제한. 관리자 실수로 리소스가 끝없이 생성되어 클러스터가 느려지고 장애가 나는 것을 막기 위함
- 네임스페이스에 종속되는 오브젝트이며, 기본으로는 아무것도 없음 (`kubectl get quota` 또는 `resourcequota`로 확인)

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: resource-quota-example
  namespace: default
spec:
  hard:
    requests.cpu: "1000m"
    requests.memory: "500Mi"
    limits.cpu: "1500m"
    limits.memory: "1000Mi"
```

- Requests와 Limits를 꼭 같이 제한할 필요도, CPU와 메모리를 한 ResourceQuota에 넣을 필요도 없음
- **단일 파드가 아니라 네임스페이스 전체 합계**에 대한 제한이라는 점에 유의
- `kubectl describe quota`로 Used(현재 사용) / Hard(한도) 확인. describe에서 이름을 생략하면 모든 리소스 정보를 한 번에 출력
- 새 파드가 한도를 넘으면 파드 생성 API 요청 자체가 실패. 예: limits.cpu 500m 파드는 3개(1500m)까지만 생성 가능
- ResourceQuota 생성 **이전**부터 있던 파드가 한도를 넘게 쓰고 있어도 종료되지는 않음

**실습: 메모리 과다 파드**

- limits.memory 3000Mi 파드를 apply하면 즉시 `exceeded quota` 에러 (한도 1000Mi)

**실습: 디플로이먼트로 생성하면?**

- 디플로이먼트 apply는 에러 없이 성공하지만, 파드 목록을 보면 파드가 없음
- 이유: **파드를 만드는 주체는 디플로이먼트가 아니라 레플리카셋**. 디플로이먼트는 레플리카셋의 메타데이터를 선언적으로 가질 뿐
- 그래서 에러 로그는 `kubectl describe rs <이름>`의 이벤트(FailedCreate)에 남음 (DESIRED 1, CURRENT 0)
- 레플리카셋은 계속 재시도하므로 Quota가 바뀌거나 자원이 생기면 정상 생성됨
- 재시도는 무작정 빠르게 하지 않고 **지수 함수 간격**으로 함 (10초, 20초, 40초, 80초, 160초 …)

#### ResourceQuota로 리소스 개수 제한하기

제한 가능한 대상:

- 디플로이먼트, 파드, 서비스, 시크릿, 컨피그맵, PVC 등의 개수
- NodePort 타입 서비스 개수, LoadBalancer 타입 서비스 개수
- QoS 클래스 중 BestEffort에 속하는 파드 개수

`count/pods` 형식으로 정의합니다.

```yaml
spec:
  hard:
    requests.cpu: "1000m"
    requests.memory: "500Mi"
    limits.cpu: "1500m"
    limits.memory: "1000Mi"
    count/pods: 3
    count/services: 5
```

- 파드가 이미 3개면 4번째 파드 생성은 `exceeded quota ... count/pods=3` 에러로 거절
- 이름 형식은 `count/<오브젝트 이름>.<API 그룹 이름>`
- pods, secrets 같은 코어 API 그룹("")은 그룹명 생략, apps 그룹의 디플로이먼트는 `count/deployments.apps`
- 어느 API 그룹인지는 `kubectl api-resources`로 확인
- 그 밖의 예: `count/resourcequotas`, `count/secrets`, `count/configmaps`, `count/persistentvolumeclaims`, `count/services.nodeports`, `count/services.loadbalancers`, `count/deployments.apps`

#### ResourceQuota로 BestEffort 클래스의 파드 개수 제한하기

Requests와 Limits가 없어 노드 자원을 제한 없이 쓸 수 있는 BestEffort 파드의 개수도 제한할 수 있습니다.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: besteffort-quota
  namespace: default
spec:
  hard:
    count/pods: 1
  scopes:
    - BestEffort
```

- **scopes**는 필수 항목은 아니며, BestEffort, Terminating, NotTerminating, NotBestEffort 같은 파드 상태를 값으로 넣을 수 있음
- BestEffort 파드는 자원 설정이 없으므로 limits.cpu 같은 항목과 연결해 쓸 수 없고, `count/pods`만 유효하게 동작
- NotBestEffort는 BestEffort가 아닌 다른 QoS 클래스, Terminating은 종료 시간(activeDeadlineSeconds)이 명시된 파드. 보통 잡(Job, 13장)에서 쓰이므로 대부분의 파드는 NotTerminating에 속함. 이 세 가지는 limits.cpu 등과 count/pods 모두 연결 가능
- 실습: besteffort-1은 생성, besteffort-2는 `exceeded quota` 에러

**중요한 함정**

- BestEffort 파드 개수를 따로 허용하지 않은 채 ResourceQuota로 CPU, 메모리를 제한하면 BestEffort 파드 생성이 실패함
- 에러: `must specify limits.cpu,limits.memory,requests.cpu,requests.memory`
- 즉 ResourceQuota로 limits/requests 합을 설정했다면 **파드에도 반드시 해당 항목을 정의**해야 함
- 이 불편함을 해결하는 것이 LimitRange (기본값을 자동으로 넣어줌)
- 에러가 안 난다면 기본으로 limitrange가 있을 수 있으니 `kubectl get limitrange`로 확인

#### 11.1.5.2 LimitRange로 자원 사용량 제한

LimitRange는 특정 네임스페이스에서 할당되는 자원의 **범위 또는 기본값**을 지정하는 오브젝트입니다.

- 자원 설정이 없는 컨테이너에 기본 Requests/Limits를 자동으로 넣어줌
- 파드나 컨테이너의 CPU, 메모리, PVC 스토리지 크기의 최솟값/최댓값 설정
- ResourceQuota처럼 네임스페이스에 종속되며 기본으로는 없음 (`kubectl get limitranges` 또는 `limits`)

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: mem-limit-range
spec:
  limits:
  - default:          # 1. 자동 설정될 기본 Limits
      memory: 256Mi
      cpu: 200m
    defaultRequest:   # 2. 자동 설정될 기본 Requests
      memory: 128Mi
      cpu: 100m
    max:              # 3. 최댓값
      memory: 1Gi
      cpu: 1000m
    min:              # 4. 최솟값
      memory: 16Mi
      cpu: 50m
    type: Container   # 5. 컨테이너 단위로 적용
```

1. **default**: Limits가 없으면 이 값을 Limits로 설정
2. **defaultRequest**: Requests가 없으면 이 값을 Requests로 설정
3. **max**: 설정 가능한 Limits의 최대치. 넘으면 생성 실패
4. **min**: 설정 가능한 Requests의 최소치. 이보다 적으면 생성 실패
5. **type**: 적용 단위. Container 외에 Pod, PersistentVolumeClaim도 가능

동작 확인:

- 자원 설정 없이 `kubectl run`으로 파드를 만들면 describe에서 Limits 200m/256Mi, Requests 100m/128Mi가 자동으로 들어가 있음
- requests.cpu 10m인 파드는 `minimum cpu usage per Container is 50m, but request is 10m` 에러로 거절

**maxLimitRequestRatio**

오버커밋되는 비율, 즉 Limits / Requests 비율의 상한을 정합니다.

```yaml
spec:
  limits:
  - maxLimitRequestRatio:
      memory: 1.5
      cpu: 1
    type: Container
```

- 메모리 Limits 200Mi, Requests 100Mi인 파드는 비율이 2라서 1.5를 넘으므로 거절
- 값을 **1로 설정하면 Guaranteed 파드만 생성하도록 강제**하는 용도로도 쓸 수 있음

**파드 단위 제한 (type: Pod)**

- 파드의 사용량은 파드 안 모든 컨테이너 자원의 합
- 예: `max.memory: 1Gi`, `min.memory: 200Mi`, `type: Pod`이면 컨테이너들의 메모리 합이 200Mi 이상 1Gi 이하여야 함

정리하면, ResourceQuota로 네임스페이스의 Limits/Requests를 설정하면 기본적으로 BestEffort 파드 생성이 거부되지만, LimitRange를 쓰면 컨테이너에 기본 자원을 일괄 설정해줄 수 있습니다.

### 11.1.6 ResourceQuota, LimitRange의 원리 : Admission Controller

API 요청이 처리되는 순서 (그림 11.11):

**HTTP 핸들러 → Authentication(인증) → Authorization(인가) → Mutating Admission Controller → Validating Admission Controller → etcd**

어드미션 컨트롤러란 **사용자의 API 요청이 적절한지 검증하고, 필요하면 API 요청을 변형하는 단계**입니다. 부적절한 요청은 거절하고, 필요하면 요청 파라미터를 바꿀 수 있습니다.

- 모르는 사이에 이미 여러 개를 쓰고 있었음: 서비스 어카운트, ResourceQuota, LimitRange 모두 어드미션 컨트롤러의 한 종류
- 두 단계: **검증(Validating)** 은 요청을 검사, **변형(Mutating)** 은 요청을 적절히 수정

파드 생성 요청 흐름:

1. 사용자가 `kubectl apply -f pod.yaml`로 API 서버에 요청
2. x509 인증서, 서비스 어카운트 등으로 인증
3. 롤, 클러스터 롤 등으로 인가
4. ResourceQuota가 자원 할당 요청이 적절한지 **검증**. 네임스페이스 한도를 넘으면 요청 거절
5. 자원 할당이 없으면 LimitRange가 CPU, 메모리 기본값을 추가해 **원래 요청 데이터를 변형**

(실제로는 둘 다 검증과 변형을 복합적으로 하지만 이해를 위해 나눠 설명한 것)

**활용**

- 기본 어드미션 컨트롤러는 대부분 활성화되어 있어 신경 쓸 필요 없음
- 직접 구현해 등록할 수도 있음. 예: Nginx 컨테이너가 80이 아닌 포트를 쓰도록 잘못 정의되면 자동으로 고쳐주기
- 어노테이션에 따라 사이드카 컨테이너를 자동 추가하는 **주입(Injection)** 패턴도 가능. 서비스 메시인 Istio가 이 방식으로 프록시 사이드카를 주입함

**Validating Admission Policy (쿠버네티스 1.30부터)**

직접 개발이 부담스럽다면 CEL(Common Expression Language)로 리소스 생성, 삭제 요청을 검증할 수 있습니다. 예를 들어 디플로이먼트 레플리카 수는 5개 이하여야 한다는 규칙:

```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: "my-test-policy"
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
    - apiGroups: ["apps"]
      apiVersions: ["v1"]
      operations: ["CREATE", "UPDATE"]
      resources: ["deployments"]
  validations:
    - expression: "object.spec.replicas <= 5"
```

- 정책(ValidatingAdmissionPolicy)과 이를 연결하는 바인딩(ValidatingAdmissionPolicyBinding, `validationActions: [Deny]`)을 함께 만듦
- 레플리카 6개짜리를 `-dry-run=server`로 apply하면 `failed expression: object.spec.replicas <= 5`로 거부

## 11.2 쿠버네티스 스케줄링

스케줄링이란 컨테이너나 가상 머신 같은 인스턴스를 새로 만들 때 **어느 서버에 생성할지 결정하는 일**입니다 (그림 11.12).

스케줄링이 중요한 이유 예시:

- 빠른 파일 입출력을 위해 SSD가 있는 서버에 컨테이너를 배치해야 할 때
- 모든 서버에 고르게 배포해 서버 장애에도 무중단, 즉 고가용성(HA)을 확보해야 할 때

쿠버네티스는 다양한 스케줄링 방법을 제공하고 복잡한 전략을 직접 구현할 수도 있습니다. 이 절에서는 스케줄링 과정을 먼저 보고, YAML에서 쓸 수 있는 스케줄링 설정값들을 다룹니다.

### 11.2.1 파드가 실제로 노드에 생성되기까지의 과정

지금까지 배운 내용 기준의 큰 흐름:

1. ServiceAccount, RoleBinding 등으로 요청자의 인증 및 인가
2. ResourceQuota, LimitRange 같은 어드미션 컨트롤러가 요청을 변형하거나 검증
3. 검증을 통과해 승인되면 워커 노드 중 한 곳에 파드 생성

스케줄링은 3번에서 수행됩니다.

**관여하는 컴포넌트: kube-scheduler와 etcd**

- 둘 다 kube-system 네임스페이스에서 파드로 실행 중이라 `kubectl get pods -n kube-system`으로 확인 가능
- kube-scheduler: 쿠버네티스 스케줄러
- etcd: 클러스터의 전반적인 상태 데이터를 저장하는 일종의 데이터베이스. 분산 코디네이터(Distributed Coordinator)의 일종으로, 디플로이먼트나 파드 목록, 클러스터 정보 등 대부분의 데이터가 여기 저장됨 (다른 분산 코디네이터로는 주키퍼, Consul 등)
- etcd 데이터는 **무조건 API 서버(kube-apiserver)를 통해서만** 접근 가능. `kubectl get pods`를 하면 API 서버가 etcd에서 읽어 돌려주는 구조 (그림 11.13)

**nodeName 항목이 핵심**

- etcd의 파드 데이터에는 어느 노드에서 실행되는지 나타내는 `nodeName`이 있음 (`kubectl get pods mypod -o yaml | grep -F3 nodeName`)
- 단계별 흐름:
    1. 요청이 최종 승인되면 API 서버는 파드 데이터를 etcd에 저장하는데, **nodeName이 비어 있는 상태**로 저장. 아직 스케줄링 전이라 데이터로만 존재
    2. kube-scheduler는 API 서버의 **Watch**를 통해 nodeName이 빈 파드가 생겼다는 걸 감지
    3. 스케줄러가 적절한 노드를 골라 API 서버에 노드와 파드의 바인딩을 요청 → **nodeName에 선택된 노드 이름이 설정됨**
    4. 각 노드의 kubelet이 Watch로 nodeName이 설정됐다는 소식을 받고, 해당 노드의 kubelet이 컨테이너 런타임으로 파드를 실제 생성

### 11.2.2 파드가 생성될 노드를 선택하는 스케줄링 과정

가장 중요한 건 **스케줄러가 적절한 노드를 어떻게 선택하느냐**이고, 크게 두 단계를 거칩니다.

- **노드 필터링**: 파드를 할당할 수 있는 노드와 아닌 노드를 걸러냄
    - Requests만큼의 가용 자원이 없는 노드 제외
    - 마스터 노드는 기본적으로 파드를 할당할 수 없는 노드
    - STATUS가 Ready가 아닌(장애 난) 노드 제외
    - 남은 목록은 스코어링 단계로 전달
- **노드 스코어링**: 소스코드에 정의된 알고리즘 가중치로 점수 계산
    - 파드의 도커 이미지가 이미 있는 노드는 빨리 띄울 수 있으니 점수 증가 (Image Locality)
    - 가용 자원이 많을수록 높은 점수 (Least Requested)
    - 점수를 합산해 가장 높은 노드를 최종 선택

스코어링은 내장 로직이라 직접 수정할 일이 드물고, 보통은 YAML에 스케줄링 조건을 적어 **필터링 단계**에 반영합니다. 이번 장도 필터링에서 쓸 수 있는 방법 위주로 설명합니다.

### 11.2.3 NodeSelector와 Node Affinity, Pod Affinity

(이번 장 예제는 별도 언급이 없으면 마스터 1대, 워커 3대 클러스터 기준)

#### nodeName과 nodeSelector를 사용한 스케줄링 방법

가장 확실한 방법은 YAML에 노드 이름(nodeName)을 직접 적는 것입니다.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  nodeName: ip-10-43-0-30.ap-northeast-2.compute.internal
  containers:
  - name: nginx
    image: nginx:latest
```

- `kubectl get pods -o wide`로 보면 지정한 노드에 할당되어 있음
- 하지만 바람직하지 않음: 노드 이름이 고정이라 다른 환경에서 YAML을 재사용하기 어렵고, 노드 장애에 유연하게 대처할 수 없음
- 대안 중 가장 쉬운 것이 노드의 **라벨(Label)** 사용. 특정 라벨이 있는 노드에만 파드를 할당할 수 있고, 라벨은 쿠버네티스가 자동으로 붙인 것도 있고 직접 추가할 수도 있음

**노드 라벨 확인과 추가**

- `kubectl get nodes --show-labels`로 노드 라벨 확인
- 기본 라벨은 대부분 `kubernetes.io/` 접두어로 시작하며, 쿠버네티스가 예약해서 쓰는 라벨이라는 뜻
- 기본 라벨에는 OS(linux), CPU 아키텍처(amd64), 호스트 이름 등이 있음
- 라벨은 `<키=값>` 형태이고, 추가는 `kubectl label nodes <노드 이름> <라벨>`

실습에서는 워커 3대 중 1대에 `mylabel/disk=ssd`, 2대에 `mylabel/disk=hdd`를 붙입니다.

```bash
kubectl label nodes ip-10-43-0-30... mylabel/disk=ssd
kubectl label nodes ip-10-43-0-31... mylabel/disk=hdd
kubectl label nodes ip-10-43-0-32... mylabel/disk=hdd
# 삭제는 키 뒤에 -(대시)
kubectl label nodes ip-10-43-0-32... mylabel/disk-
```

**nodeSelector 사용**

```yaml
spec:
  nodeSelector:
    mylabel/disk: hdd
  containers:
  - name: nginx
    image: nginx:latest
```

- 해당 라벨을 가진 노드가 여러 개면 그중 하나가 선택됨 (그림 11.14에서는 Worker Node 2, 3 중 하나)
- 노드 이름에 종속되지 않는 YAML을 쓸 수 있다는 게 nodeName 대비 장점
- 주의: 스케줄링은 **파드 하나하나에 대해 독립적으로** 수행됨. 디플로이먼트(replicas: 3)의 파드 템플릿에 nodeSelector를 넣어도 3개가 한 노드에 몰리는 게 아니라 각 파드가 hdd 노드들 중 따로따로 배치됨

#### Node Affinity를 이용한 스케줄링 방법

nodeSelector는 라벨 키-값이 같은지만 비교하므로 활용이 제한적입니다. **Node Affinity**는 이를 확장한 라벨 선택 기능으로, **반드시 충족해야 하는 조건(Hard)** 과 **선호하는 조건(Soft)** 을 따로 정의할 수 있습니다.

옵션 2가지 (이름이 길지만 앞부분만 보면 구분 쉬움):

- `requiredDuringSchedulingIgnoredDuringExecution`
- `preferredDuringSchedulingIgnoredDuringExecution`

**required (Hard 조건)**

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: mylabel/disk
            operator: In     # values 중 하나만 만족하면 됨
            values:
            - ssd
            - hdd
```

- `operator: In`이면 노드 라벨이 `mylabel/disk=ssd` 또는 `hdd`인 노드에 배치
- operator 종류: In, NotIn, Exists, DoesNotExist, Gt(값이 큼), Lt(값이 작음). 그래서 nodeSelector보다 표현력이 좋음
- required는 반드시 만족해야 하는 제약이므로 nodeSelector의 확장판이라고 생각하면 쉬움

**preferred (Soft 조건)**

```yaml
nodeAffinity:
  preferredDurationSchedulingIgnoredDuringExecution: # 실제 키는 preferredDuringScheduling...
  - weight: 80       # 조건을 만족하는 노드에 1~100 가중치 부여
    preference:
      matchExpressions:
      - key: mylabel/disk
        operator: In
        values:
        - ssd
```

(위 주석의 키 이름은 실제로 `preferredDuringSchedulingIgnoredDuringExecution`입니다.)

- 조건을 반드시 만족할 필요는 없고, 만족하는 노드가 있으면 그 노드를 **더 선호**한다는 뜻
- **weight**: 1~100 사이 가산점. 필터링 이후의 **노드 스코어링 단계**에서 적용됨
- ssd 라벨이 없는 노드에도 배치될 수 있지만 ssd 노드에 배치될 확률이 높아지므로 소프트(Soft) 제약 조건이라 부름

**IgnoredDuringExecution의 의미**

스케줄링 조건은 **파드를 할당할 당시에만** 유효합니다. 이미 배치된 뒤 노드 라벨이 바뀌어도 퇴거(Eviction)는 일어나지 않습니다. 이름 그대로 스케줄링 중에는 유효하고(required During Scheduling), 일단 실행된 뒤에는 무시된다(Ignored During Execution)는 뜻입니다.

#### Pod Affinity를 이용한 스케줄링 방법

Node Affinity가 조건을 만족하는 **노드**를 고른다면, **Pod Affinity**는 조건을 만족하는 **파드와 함께** 실행되도록 스케줄링합니다. 사용법은 거의 같고, required/preferred 옵션도 똑같이 씁니다.

```yaml
spec:
  affinity:
    podAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchExpressions:
          - key: mylabel/database
            operator: In
            values:
            - mysql
        topologyKey: failure-domain.beta.kubernetes.io/zone
```

- nodeAffinity 대신 podAffinity를 쓰고, **topologyKey**라는 새 항목이 생김
- 의미: `mylabel/database=mysql` 라벨을 가진 파드와 함께 위치하도록 스케줄링
- 단, 그 파드와 **무조건 같은 노드**라는 뜻이 아님. topologyKey는 해당 라벨 기준으로 나뉜 **토폴로지(그룹) 범위의 노드**를 선택한다는 뜻

**토폴로지 이해 (그림 11.15)**

- 노드들이 topologyKey 라벨의 값에 따라 여러 그룹(토폴로지)으로 나뉜다고 생각
- 예: `kubernetes.io/zone` 값이 ap-northeast-2a인 그룹(노드 A, B)과 2b인 그룹(노드 C, D)
- mysql 파드가 노드 A에 있으면, 새 파드는 노드 A 또는 같은 그룹의 노드 B에 배치될 수 있음
- 대표 활용: 응답 시간을 최대한 줄여야 하는 두 파드를 같은 가용 영역(AZ)이나 리전(Region)의 노드에 두는 경우

**topologyKey를 호스트 이름으로 지정하면 (그림 11.16)**

```yaml
topologyKey: kubernetes.io/hostname
```

- `kubernetes.io/hostname`은 설치 시 모든 노드에 자동으로 붙는 라벨로, 값은 각 노드의 호스트 이름
- 호스트 이름은 고유하므로 토폴로지 하나에 노드가 하나뿐
- 따라서 반드시 mysql 파드가 있는 **바로 그 노드**를 선택하게 됨

#### Pod Anti-affinity를 이용한 스케줄링 방법

Pod Affinity의 반대입니다. 특정 파드와 **같은 토폴로지의 노드를 선택하지 않는** 방법이며, 고가용성을 위해 파드를 여러 가용 영역이나 리전에 퍼뜨리는 전략에 쓸 수 있습니다. 사용법은 podAffinity를 **podAntiAffinity**로 바꾸기만 하면 됩니다.

```yaml
spec:
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchExpressions:
          - key: mylabel/database
            operator: In
            values:
            - mysql
        topologyKey: failure-domain.beta.kubernetes.io/zone
```

- mysql 파드가 zone=ap-northeast-2a 노드에 있으면, 2a가 아닌 다른 토폴로지(그림 11.17에서는 노드 C, D 쪽)에 배치됨

**Soft 버전도 가능**

- required를 쓰면 토폴로지마다 반드시 하나의 파드만 할당되지만
- preferred를 쓰면 한 토폴로지에 여러 개가 들어갈 수도 있음
- preferred 사용 시 `podAffinityTerm` 아래에 labelSelector와 topologyKey를 넣고 `weight`를 함께 지정

**활용: 데몬셋처럼 노드마다 하나씩 배치하는 디플로이먼트**

데몬셋(DaemonSet)은 모든 노드에 같은 파드를 하나씩 만드는 오브젝트입니다(13장). 디플로이먼트로 비슷한 효과를 내려면 파드 템플릿에 자기 자신의 라벨로 Anti-affinity를 걸고 topologyKey를 hostname으로 둡니다.

```yaml
template:
  metadata:
    labels:
      app: deployment-nginx
  spec:
    affinity:
      podAntiAffinity:
        requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchExpressions:
            - key: app
              operator: In
              values:
              - deployment-nginx
          topologyKey: "kubernetes.io/hostname"
```

- 노드 하나가 곧 토폴로지 하나이므로, 같은 디플로이먼트의 파드끼리 서로 다른 노드로 흩어짐
- 한 노드에 두 개가 스케줄링되는 일이 생기지 않음

참고로 podAffinity와 podAntiAffinity는 기본적으로 **같은 네임스페이스의 파드만** 대상으로 합니다. `namespaceSelector`를 추가하면 다른 네임스페이스 파드도 고려하며, `namespaceSelector: {}`처럼 빈 값이면 모든 네임스페이스가 대상이 됩니다.

### 11.2.4 Taints와 Tolerations 사용하기

#### Taints와 Tolerations를 이용한 파드 스케줄링

- **Taints**: 특정 노드에 얼룩(Taint)을 지정해서 그 노드에 파드가 할당되는 것을 막는 기능
- **Tolerations**: 그 얼룩을 용인(Toleration)할 수 있다고 파드에 설정하면 Taint가 있는 노드에도 할당 가능
- 그림 11.18: Node 1에 Taints A, Node 2에 Taints B가 있을 때, Toleration A를 가진 Pod 1은 Node 1에만 갈 수 있고, Toleration이 없는 Pod 2는 둘 다 못 감

Taint는 사용자가 직접 설정할 수도 있고, 특정 이벤트로 쿠버네티스가 자동 설정하기도 합니다. 라벨처럼 키=값 형태이지만 뒤에 **effect(Taint 효과)** 가 붙는 점이 다릅니다.

```bash
# 형식: kubectl taint nodes <노드이름> key=value:effect
kubectl taint node ip-10-43-0-30... alicek106/my-taint=dirty:NoSchedule
# 삭제는 라벨처럼 뒤에 -
kubectl taint nodes <노드이름> key:effect-
```

**Taint 효과 3가지**

- **NoSchedule**: 파드를 스케줄링하지 않음
- **NoExecute**: 파드의 실행 자체를 허용하지 않음
- **PreferNoSchedule**: 가능하면 스케줄링하지 않음 (NoSchedule의 소프트 버전)

**Toleration 정의**

```yaml
spec:
  tolerations:
  - key: alicek106/my-taint
    value: dirty
    operator: Equal       # 키의 값이 dirty와 같으면(Equal)
    effect: NoSchedule    # 효과가 NoSchedule인 경우 이 Taint를 용인
  containers:
  - name: nginx
    image: nginx:latest
```

주의: Toleration은 그 Taint를 **용인할 수 있다**는 뜻일 뿐, 그 노드에 **반드시** 배치한다는 뜻이 아닙니다. 테스트로 꼭 그 노드에 보내려면 nodeSelector 등을 함께 써야 합니다.

**마스터 노드의 기본 Taint**

- 지금까지 파드가 마스터가 아닌 워커 노드에만 배치된 이유는 쿠버네티스가 마스터에 기본 Taint를 걸어두기 때문
- `kubectl describe nodes <마스터 노드>`에서 확인 가능
    - Taints: `node-role.kubernetes.io/control-plane:NoSchedule`
    - Unschedulable: false (스케줄링 대상이 되는 노드라는 뜻)
- 즉 마스터도 파드를 받을 수는 있는 노드인데 Taint 때문에 일반 파드가 안 들어갔던 것
- 이 Taint는 키-값이 아니라 값이 생략된 형태이며, 생략된 값은 빈 문자열("")로 간주

마스터 Taint도 Toleration으로 용인할 수 있습니다. 단, 마스터에는 API 서버 같은 핵심 컴포넌트만 두는 게 바람직하다는 점을 유념해야 합니다.

```yaml
spec:
  tolerations:
  - key: node-role.kubernetes.io/control-plane
    effect: NoSchedule
    operator: Equal
    value: ""
  nodeSelector:
    node-role.kubernetes.io/control-plane: ""   # 마스터에서도 생성되도록 지정
```

**마스터에서 돌고 있는 파드의 Toleration**

- `kubectl describe pod kube-apiserver-... -n kube-system`을 보면 QoS Class는 Burstable, Tolerations는 `:NoExecute`
- 키와 값에 상관없이 모든 NoExecute 종류의 Taint를 용인한다는 뜻
- YAML로 보면 `effect: NoExecute`, `operator: Exists`

**operator: Exists**

operator는 Equal 외에 Exists도 가능하며, Exists는 와일드카드처럼 동작합니다. key, value, effect 중 명시하지 않은 항목은 값에 상관없이 모두 용인합니다.

- `operator: Exists`만 쓰면 모든 종류의 Taint를 용인
- `key: my-key` + `operator: Exists`면 키 이름이 my-key인 모든 Taint를 값에 상관없이 용인
- `key: my-key` + `effect: NoExecute` + `operator: Exists`면 키가 my-key이고 효과가 NoExecute인 Taint를 값에 상관없이 용인

#### NoExecute와 tolerationSeconds

- **NoSchedule**: 새 파드의 스케줄링만 막음. 기존에 실행 중이던 파드는 그대로 동작
- **NoExecute**: 스케줄링을 막을 뿐 아니라 그 노드에서 **실행 중인 파드도 종료**시킴. 물론 NoExecute에 대한 Toleration이 있는 파드는 종료되지 않음
- 디플로이먼트나 레플리카셋으로 만든 파드라면 종료되더라도 레플리카셋이 개수 부족을 감지하고 다른 노드에 새로 만들므로, 결과적으로 다른 노드로 옮겨가는 퇴거(Eviction)가 됨 (그림 11.19)

```bash
kubectl taint node ip-10-43-0-30... alicek106/your-taint=your-taint-value:NoExecute
```

**자동으로 붙는 Toleration**

아무 파드나 describe해 보면 이런 Toleration이 자동으로 들어가 있습니다.

- `node.kubernetes.io/not-ready:NoExecute for 300s`
- `node.kubernetes.io/unreachable:NoExecute for 300s`

쿠버네티스는 문제가 생긴 노드에 자동으로 Taint를 붙입니다. 노드가 준비되지 않은 상태(NotReady), 네트워크가 불안정한 상태(Unreachable), 메모리 부족(memory-pressure), 디스크 공간 부족(disk-pressure) 등이 있고, 특히 NotReady와 Unreachable은 노드 자체의 장애일 수 있어 위의 NoExecute Taint가 붙습니다. `kubectl get nodes`에서 STATUS가 NotReady인 경우도 마찬가지입니다.

**tolerationSeconds**

- 위 Toleration은 장애로 not-ready나 unreachable Taint가 생겨도 **300초 동안은 용인**하겠다는 뜻
- 300초 안에 노드가 정상으로 돌아와 Taint가 없어지지 않으면 파드는 다른 노드로 옮겨감
- 즉 노드 장애가 나도 즉시 옮겨가는 게 아니라 기본적으로 300초 후에 옮겨감
- 이 값이 **tolerationSeconds**이며, Taint가 추가됐을 때 그 Taint를 용인할 수 있는 최대 시간

```yaml
- effect: NoExecute
  key: node.kubernetes.io/not-ready
  operator: Exists
  tolerationSeconds: 300
```

이 두 Toleration은 **DefaultTolerationSeconds**라는 어드미션 컨트롤러가 파드에 추가하며, 필요하면 파드 YAML에서 직접 재정의할 수 있습니다.

### 11.2.5 Cordon, Drain 및 PodDistributionBudget

(책 제목 표기는 Distribution이지만 본문의 오브젝트 이름은 PodDisruptionBudget입니다.)

#### cordon을 이용한 스케줄링 비활성화

Taint보다 명시적으로 노드의 스케줄링을 막는 방법입니다.

```bash
kubectl cordon <노드 이름>     # 스케줄링 금지
kubectl uncordon <노드 이름>   # 해제
```

- `kubectl get nodes`의 STATUS에 `Ready,SchedulingDisabled`가 표시됨
- describe로 보면 `node.kubernetes.io/unschedulable:NoSchedule` Taint가 추가되고 Unschedulable도 true가 됨
- NoExecute가 아니라 NoSchedule Taint이므로, **이미 실행 중인 파드는 종료되지 않음**

#### drain 명령어로 노드 비활성화하기

- drain은 cordon처럼 스케줄링을 금지하는 것에 더해, 기존 파드를 다른 노드로 **퇴거(Eviction)** 시킴
- 커널 버전 업그레이드, 유지 보수 등으로 노드를 잠시 중지해야 할 때 유용

```bash
kubectl drain <노드 이름>
```

- 데몬셋 파드(calico-node, kube-proxy 등)가 있으면 `cannot delete DaemonSet-managed Pods` 에러로 실패. 이때도 cordon은 이미 적용된 상태
- 데몬셋을 무시하려면 `-ignore-daemonsets` 옵션 추가 → 경고와 함께 다른 파드들이 evicting됨
- 디플로이먼트, 레플리카셋, 잡, 스테이트풀셋 등이 만들지 않은 **단일 파드**(`kind: Pod`로 직접 만든 파드)가 있어도 drain은 실패함. 단일 파드는 종료되면 다른 노드에서 다시 만들어지지 않기 때문. 무시하려면 `-force` 옵션

#### PodDisruptionBudget으로 파드 개수 유지하기

**문제 상황 (그림 11.20)**

- 디플로이먼트(replicas: 1)의 파드가 있는 Node 1을 drain하면 Pod-A가 Terminating, 레플리카셋이 개수 불일치를 감지해 Node 2에 Pod-A'를 새로 만듦
- 새 파드가 준비되기 전까지는 사용자 요청을 처리할 수 없음
- replicas를 여러 개로 두면 장애는 피할 수 있지만, drain한 노드에 파드가 여러 개 있었다면 그만큼 처리량이 일시적으로 감소

**PodDisruptionBudget(PDB)**

drain 등으로 퇴거가 발생할 때 특정 개수 또는 비율만큼의 파드는 반드시 정상 상태를 유지하도록 하는 오브젝트입니다.

```bash
kubectl get poddisruptionbudgets
kubectl get pdb   # 보통 PDB라고 부름
```

```yaml
apiVersion: policy/v1beta1
kind: PodDisruptionBudget
metadata:
  name: simple-pdb-example
spec:
  maxUnavailable: 1      # 비활성화될 수 있는 파드의 최대 개수 또는 비율(%)
  # minAvailable: 2
  selector:              # PDB 대상 파드를 고르는 라벨 셀렉터
    matchLabels:
      app: webserver
```

- **maxUnavailable**: drain 등으로 파드가 종료될 때 최대 몇 개까지 동시에 종료될 수 있는지. 1이면 하나씩 종료되고 다른 노드에서 다시 생성됨
- **minAvailable**: 최소 몇 개의 파드가 정상 상태를 유지해야 하는지
- 둘 다 숫자 또는 30%, 50% 같은 비율로 설정 가능
- 의미만 다를 뿐 같은 기능이므로 **둘 중 하나만** 정의해야 함

**selector 주의점**

디플로이먼트 같은 **컨트롤러의 라벨이 아니라 파드의 라벨**을 입력해야 합니다. 그래서 파드 템플릿의 `metadata.labels`에 `app: webserver`를 넣어야 이 PDB가 적용됩니다.

- PDB가 있으면 라벨이 일치하는 파드가 퇴거될 때 PDB 값에 따라 정상 파드 개수가 일정하게 유지됨
- maxUnavailable을 0(0%)으로, 또는 minAvailable을 100%로 설정하면 drain이 진행되지 않을 수 있으니 적절한 값을 넣어야 함

**삭제(Delete)와 퇴거(Eviction)의 차이**

- 결과적으로 파드가 없어진다는 점은 같지만 완전히 다른 개념
- 삭제는 `kubectl delete pod`처럼 PDB와 상관없이 파드를 지움
- 퇴거는 쿠버네티스 내부의 Evict라는 별도 API로 구현되어 있고, PDB의 영향을 받음

### 11.2.6 커스텀 스케줄러 및 스케줄러 확장

#### 커스텀 스케줄러 구현

쿠버네티스는 기본 스케줄러(kube-scheduler) 외에 여러 스케줄러를 동시에 쓸 수 있도록 지원합니다. 별도 스케줄러는 직접 구현하거나 설정해야 합니다.

- 파드에 자동으로 추가되는 `schedulerName`을 보면 기본값은 `default-scheduler` (kube-scheduler 파드)
- 기본 스케줄러는 schedulerName이 default-scheduler인 파드만 스케줄링함
- 내 스케줄러를 쓰려면 파드에 schedulerName을 따로 지정

```yaml
spec:
  schedulerName: my-custom-scheduler
  containers:
  - name: nginx-container
    image: nginx
```

커스텀 스케줄러가 해야 할 일은 앞에서 배운 스케줄링 단계를 그대로 소스코드로 옮기는 것입니다.

1. API 서버의 Watch API로 새로 생성된 파드 데이터를 받아옴
2. nodeName이 비어 있고 schedulerName이 내 스케줄러 이름과 일치하는지 검사 (schedulerName은 스케줄러를 나타내는 고유한 값)
3. 적절한 스케줄링 알고리즘을 수행한 뒤, 바인딩 API 요청으로 선택된 노드 이름을 파드의 nodeName에 설정
- 쿠버네티스 SDK로 위 단계를 구현할 수만 있다면 언어는 상관없음. Go도 되고 파이썬도 됨 (책 깃허브의 chapter11-2/custom-scheduler-python 참고)
- 단, 노드 필터링, 스코어링 같은 기본 스케줄러의 알고리즘 없이 전부 직접 구현해야 하므로, 꼭 필요한 게 아니면 기본 스케줄러를 쓰는 게 오히려 바람직할 수 있음
- API 서버와 통신해야 하므로 보통 kube-scheduler처럼 클러스터 내부에 파드로 실행함. 원리만 테스트하려면 마스터 노드에서 간단한 셸 스크립트로 해볼 수도 있음

#### 쿠버네티스 스케줄러 확장하기

- 쿠버네티스 소스코드를 받아 스케줄러 부분만 수정해 직접 빌드하는 방법
- **스케줄링 프레임워크**로 기본 스케줄러에 추가 로직을 덧붙이는 방법
- 어떤 방법이든 신중하게 도입해야 함. 커스텀 스케줄러나 Extender 서버 자체가 장애 나면 어떻게 할지, 기본 스케줄러로 되는 기능을 불필요하게 다시 만드는 건 아닌지, 확장 기능의 한계는 무엇인지 꼼꼼히 따져봐야 함

## 11.3 쿠버네티스 애플리케이션 상태와 배포

가장 쉬운 배포 방법은 지금까지처럼 `kubectl apply -f`로 디플로이먼트를 만드는 것이고(그림 11.21), 더 고도화된 방식을 원하면 Spinnaker, Helm, Kustomize, ArgoCD, Jenkins 같은 지속적 배포(Continuous Delivery) 도구를 쓸 수 있습니다. 배포 패러다임은 빠르게 변하고 정답이 없어서, 책에서는 서드 파티 도구는 다루지 않습니다.

단순히 새 버전을 띄우는 것이라면 새 이미지로 바꾼 디플로이먼트 YAML을 apply하면 됩니다. 디플로이먼트가 버전별로 레플리카셋을 관리하기 때문입니다(6.4절).

**안정적인 배포를 위해 고려할 것들**

- 기존 버전을 지우고 새 버전을 배포해야 할 수도, 이전 버전으로 롤백해야 할 수도 있음
- 잠시 중단돼도 괜찮다면 기존 디플로이먼트를 지우고 새로 만들면 충분
- 하지만 무중단이 필요하면 그 사이에 다운 타임(Down Time)이 생기고, 삭제되는 파드가 처리 중이던 요청이 완료되지 않을 수 있음

쿠버네티스가 제공하는 기능:

- 새 버전을 점진적으로 배포하는 **롤링 업데이트**
- 배포된 버전을 내부적으로 저장해 원하는 버전으로 되돌리기
- 새 파드가 요청을 처리할 준비가 됐는지 확인
- 삭제될 파드가 애플리케이션을 우아하게 종료(Graceful Termination)하도록 설정

이 절에서는 롤링 업데이트를 먼저 보고, 파드가 생성되어 종료되기까지의 생애 주기(Lifecycle)를 설명합니다. 참고로 장애 상황을 시뮬레이션하는 카오스 테스트 같은 기능은 쿠버네티스가 직접 제공하지 않으며, 이런 고급 배포 전략에는 Istio 같은 서비스 메시를 고려할 수 있습니다.

### 11.3.1 디플로이먼트를 통해 롤링 업데이트

#### 디플로이먼트를 이용한 레플리카셋의 버전 관리

- 실무에서 파드를 직접 만드는 경우는 거의 없고, 디플로이먼트를 만들면 그에 속한 레플리카셋이 파드를 생성
- 레플리카셋 대신 디플로이먼트를 쓰는 이유(6.2절 요약): 레플리카셋의 변경 사항을 저장하는 **리비전(revision)** 을 디플로이먼트가 관리해서 배포를 쉽게 하기 위함
- 디플로이먼트가 바뀌면 새 레플리카셋이 생성되고 새 버전이 배포됨 (그림 11.22: 여러 버전의 레플리카셋 중 하나만 활성)
- `-record` 옵션을 붙여 적용하면 이전 레플리카셋 정보가 디플로이먼트 히스토리에 기록되고, 리비전을 이용해 원하는 버전으로 롤백 가능

```bash
kubectl apply -f deployment-v1.yaml --record
kubectl apply -f deployment-v2.yaml --record
kubectl rollout history deployment nginx-deployment
# REVISION 1, 2와 각 CHANGE-CAUSE가 출력됨
```

리비전은 기본적으로 10개까지 저장되며, `revisionHistoryLimit`으로 최대 개수를 지정할 수 있습니다.

```yaml
spec:
  revisionHistoryLimit: 3
```

#### 디플로이먼트를 통한 롤링 업데이트 설정

새 파드를 만드는 것 자체는 단순하지만, 배포 중에 애플리케이션이 중단돼도 되는지에 따라 방법을 골라야 합니다.

**Recreate 방식 (그림 11.23)**

- 기존 버전 파드를 모두 삭제한 뒤 새 버전 파드를 생성
- 일시적으로 요청을 처리하지 못해도 괜찮은 애플리케이션에 적합
- `strategy.type`에서 설정

```yaml
spec:
  replicas: 3
  strategy:
    type: Recreate
```

- v2를 apply하면 기존 파드 3개가 모두 Terminating이 된 뒤 새 파드가 만들어짐
- 그 사이 요청을 처리할 수 없으므로 중단이 허용되지 않으면 부적절

**롤링 업데이트 (그림 11.24)**

- 파드를 조금씩 삭제하고 생성하는 방식. 업데이트 도중에도 요청을 처리할 파드가 계속 있으므로 중단이 없음
- 별도 설정이 없어도 디플로이먼트는 **기본적으로 롤링 업데이트**
- 세부 옵션을 쓰려면 `strategy.type`을 RollingUpdate로 명시

```yaml
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 2
      maxUnavailable: 2
```

**세부 옵션 (둘 다 숫자 또는 비율, 기본값 25%)**

- **maxUnavailable**: 업데이트 도중 사용 불가능한 상태가 되는 파드의 최대 개수. 실행 중인 파드 수가 일정 이하로 내려가지 않게 유지함. 25%면 적어도 75%는 요청을 처리할 수 있는 상태
- **maxSurge**: 업데이트 도중 전체 파드 수가 replicas보다 얼마나 더 많을 수 있는지. 곧 새 버전 파드를 얼마나 많이 만들 수 있는지. 25%면 이전 버전과 새 버전 파드의 합이 replicas 대비 최대 125%
- 비율 사용 시 기준은 replicas 값. maxSurge의 소수점은 반올림, maxUnavailable의 소수점은 버림

**구체적인 예시: replicas 4, maxUnavailable 1, maxSurge 2**

(전체 파드 수는 최소 3개, 최대 6개)

- t0: 업데이트 전, v1 파드 4개
- t1: maxUnavailable이 1이므로 최소 3개는 실행 중이어야 함 → v1 파드 1개 삭제 (v1 3개)
- t2: 최대 6개까지 가능하므로 v1 삭제와 동시에 v2를 상한까지 생성. v1이 3개 남았으니 6 - 3 = 3개의 v2 생성
- t3: 최소 3개를 벗어나지 않는 선에서 v1 삭제. v2가 3개 있으니 v1 3개를 모두 삭제해도 됨
- t4: replicas만큼 v2를 맞춰(4개) 롤링 업데이트 완료

책 깃허브의 rolling-update-example-v1.yaml, v2.yaml로 직접 따라 할 수 있으며, 파드 준비 시간에 따라 예시와 다르게 진행될 수도 있습니다. 실습 출력을 보면 일부 v1 파드가 Terminating인 동안 v2 파드들이 ContainerCreating 상태로 함께 존재합니다.

**주의점**

- maxUnavailable을 0으로 하면 업데이트 중에도 적어도 replicas만큼은 유지됨
- 이때 maxSurge까지 0이면 상한선과 하한선이 같아져 새 파드를 만들 수 없음 → 업데이트가 진행되지 않으므로 **둘 다 0은 허용되지 않음**
- 롤링 업데이트 중에는 **기존 버전과 새 버전이 공존**하는 순간이 있음. 그래서 이 애플리케이션과 통신하는 다른 컴포넌트들은 어느 버전과 통신해도 문제가 없어야 함

#### 블루 그린 배포 사용하기

기존 버전 파드를 그대로 둔 채 새 버전 파드를 미리 만들어 두고, **서비스의 라우팅만 변경**하는 배포 방식입니다.

- 장점: 롤링 업데이트와 달리 두 버전이 동시에 서비스되지 않고, Recreate처럼 중단 시간도 없음
- 쿠버네티스가 자체 기능으로 지원하진 않지만, 배운 기능으로 간단히 구현 가능

진행 순서 (그림 11.25):

1. 기존 버전(v1) 디플로이먼트가 있고, 서비스는 요청을 v1 파드로 전달 중
2. 새 버전(v2) 디플로이먼트를 생성
3. 서비스의 라벨(셀렉터)을 바꿔 요청이 새 버전 디플로이먼트로 가도록 수정
4. 새 버전이 잘 동작하면 기존 디플로이먼트 삭제. 롤백이 필요하면 서비스 라벨을 이전 상태로 되돌림

단점: 특정 순간에는 replicas의 **두 배**에 해당하는 파드가 실행되므로 일시적으로 자원을 많이 소모합니다.

### 11.3.2 파드의 생애 주기(Lifecycle)

롤링 업데이트를 할 때는 두 가지를 확인하는 게 좋습니다.

- 새 파드가 Running이 되었더라도 초기화 작업 등으로 아직 요청을 처리할 준비가 안 됐을 수 있음
- 기존 파드를 종료할 때는 처리 중인 요청을 전부 끝낸 뒤 종료해야 함

이를 신경 쓰지 않으면 업데이트 중 요청이 제대로 처리되지 않은 채 파드가 종료될 수 있습니다. 그래서 쿠버네티스는 파드 시작 시 애플리케이션 준비 여부를 확인하고, 종료 시 우아하게 종료되도록 하는 기능을 지원합니다. 이번 절에서는 파드의 라이프사이클을 보고, 상태 검사를 위한 livenessProbe, readinessProbe, startupProbe를 다룹니다.

#### 11.3.2.1 파드의 상태와 생애 주기

어렵게 느껴지지만, `kubectl get pods`의 STATUS에서 봐왔던 것에 대한 설명이라고 생각하면 됩니다.

- **Pending**: 생성 요청은 API 서버가 승인했지만 어떤 이유로 아직 실제로 생성되지 않은 상태. 예: 아직 노드에 스케줄링되지 않음
- **Running**: 파드의 컨테이너가 모두 생성되어 정상 실행된 상태. 쿠버네티스가 바람직한 상태(Desired)로 간주하는 상태
- **Completed**: 정상적으로 실행되어 종료됨. 컨테이너의 init 프로세스가 종료 코드 0을 반환한 경우
- **Error**: 정상적으로 실행되지 않은 상태로 종료됨. init 프로세스가 0이 아닌 종료 코드를 반환한 경우
- **Terminating**: 삭제 또는 퇴거되기 위해 삭제 상태에 머물러 있는 경우

배포 시 중요한 건 Running과 Terminating입니다. 요청은 Running 파드로 가야 하고 Terminating 파드로 가면 안 되기 때문입니다. Completed와 Error는 파드가 어떻게 종료됐는지 보여주는 증거라서 알아두면 좋습니다.

#### Completed, Error와 restartPolicy

리눅스 프로세스는 종료될 때 종료 코드를 반환하고, 컨테이너의 init 프로세스가 반환한 값에 따라 파드 상태가 Completed 또는 Error가 됩니다.

init 프로세스란 리눅스가 구동될 때 가장 먼저 실행되는 프로세스로 보통 PID 1번입니다. 컨테이너에서는 Dockerfile 등에 설정된 CMD와 Entrypoint의 조합이 init 프로세스가 됩니다. 예를 들어 우분투 이미지는 /bin/bash, Nginx 이미지는 nginx 웹 서버 프로세스이며, **init 프로세스가 종료되면 컨테이너도 종료**됩니다.

**Completed 실습**

```yaml
spec:
  containers:
  - name: completed-pod-example
    image: busybox
    command: ["sh"]
    args: ["-c", "sleep 10 && exit 0"]
```

- 10초 대기 후 종료 코드 0으로 종료
- `kubectl get pod --watch`로 보면 Running → Completed → Running → Completed가 반복되고 RESTARTS가 증가
- 이유: 기본 재시작 정책 **restartPolicy가 Always**라서 컨테이너가 종료되면 자동으로 다시 시작됨

**restartPolicy 값**

- **Always** (기본값): 종료되면 항상 재시작
- **Never**: 종료되어도 절대 재시작하지 않음
- **OnFailure**: 실패했을 때, 즉 0이 아닌 종료 코드를 반환했을 때만 재시작

```yaml
spec:
  restartPolicy: Never
  containers:
  ...
```

- Never로 만들면 종료 후에도 재시작하지 않고 Completed 상태에 머묾
- Never나 OnFailure는 잡(Job), 크론잡(CronJob)으로 만든 파드처럼 작업이 끝나면 다시 실행될 필요가 없을 때 유용

**Error 실습**

- args를 `exit 1`로 바꾸고 restartPolicy: Never로 생성하면 Running → Error
- restartPolicy를 명시하지 않았다면 Always가 되어 Error 뒤에도 계속 재시작됐을 것

**CrashLoopBackOff (그림 11.26)**

- 상태 흐름: ContainerCreating → Running → Completed(Always일 때 재시작) 또는 Error(Always나 OnFailure일 때 재시작) → CrashLoopBackOff → 일정 시간이 지난 뒤 다시 Running
- 파드는 종료될 때마다 즉시 재시작되는 게 아님
- 쿠버네티스는 작업이 실패하면 일정 간격을 두고 재시도하며, 실패 횟수가 늘수록 재시도 간격이 지수 형태로 늘어남. 그 중간 상태가 **CrashLoopBackOff**
- 실패를 반복할수록 CrashLoopBackOff에 머무는 시간이 길어짐 (출력 예시에서 AGE가 44s, 74s, 118s, 2m52s … 로 벌어짐)

#### 11.3.2.2 Running 상태가 되기 위한 조건

- 쿠버네티스는 대부분 Running을 바람직한 상태로 간주하며, 이는 컨테이너들이 정상 생성됐다는 뜻
- 하지만 파드를 만들었다고 무조건 Running이 되는 것도 아니고, Running이라고 해서 내부 애플리케이션이 제대로 동작한다는 보장도 없음
- 그래서 쿠버네티스는 다음 기능들을 제공
    - Init Container
    - postStart
    - livenessProbe, readinessProbe
- 필수는 아니지만 애플리케이션이 많고 복잡해질수록 활용을 고민하는 게 좋음

#### Running 상태가 되기 위한 조건 : Init 컨테이너

- 파드 안에서 **애플리케이션 컨테이너보다 먼저 실행**되어 초기화를 수행하는 컨테이너
- 사용법은 애플리케이션 컨테이너와 거의 같고, 애플리케이션 실행 전에 특정 작업을 미리 해두는 용도
- `initContainers`라는 별도 항목에 정의하며, 여러 개면 **순서대로** 실행됨

```yaml
spec:
  initContainers:   # 초기화 컨테이너를 이 항목에 정의
  - name: my-init-container
    image: busybox
    command: ["sh", "-c", "echo Hello World!"]
```

앞의 예제는 `initContainers` 아래에 초기화 컨테이너를, `containers` 아래에 애플리케이션 컨테이너(nginx)를 정의한 형태입니다.

```bash
kubectl apply -f init-container-example.yaml
kubectl get pods -w
# STATUS: Init:0/1 → PodInitializing → Running
```

- initContainers에 정의한 컨테이너가 먼저 실행된 뒤 containers의 컨테이너가 생성됨
- Init 컨테이너가 **하나라도 실패하면** 애플리케이션 컨테이너는 실행되지 않고, restartPolicy에 따라 Init 컨테이너가 재시작됨
- 즉 파드가 Running이 되려면 Init 컨테이너가 무사히 끝나야 함

**활용 예시**

- Init 컨테이너 안에서 dig, nslookup 등으로 다른 디플로이먼트가 생성되기를 기다리기
- 애플리케이션 컨테이너가 쓸 설정 파일 등을 미리 준비해 두기

쿠버네티스는 여러 리소스를 한 번에 만들 때 리소스 간 의존성을 정의하는 기능을 따로 제공하지 않지만, Init 컨테이너로 간접적으로 의존성을 정의할 수 있습니다.

```yaml
initContainers:
- name: wait-other-service
  image: busybox
  command: ['sh', '-c', 'until nslookup myservice; do echo waiting..; sleep 1; done;']
```

myservice라는 서비스가 조회될 때까지 1초마다 반복해서 기다리는 예시입니다.

**참고 1: 파드 환경 공유**

Init 컨테이너도 파드에 포함된 컨테이너이므로 파드의 환경을 공유합니다. emptyDir 볼륨을 쓰거나 파드의 네트워크 정보를 가져올 수도 있습니다.

**참고 2: 네이티브 사이드카(native sidecar)**

- Init 컨테이너에 `restartPolicy: Always`를 명시하면 사이드카(Sidecar) 컨테이너로 취급됨
- 애플리케이션 컨테이너보다 먼저 실행되고, 종료되지 않고 계속 실행되는 것이 목적

```yaml
spec:
  containers:
  - name: nginx
    image: nginx
  initContainers:
  - name: my-native-sidecar-container
    image: busybox
    command: ['sh', '-c', 'tail -f /dev/null']
    restartPolicy: Always
```

- 파드가 삭제될 때 애플리케이션 컨테이너가 중지될 때까지 종료가 유예됨
- 즉 사이드카 컨테이너의 라이프사이클을 쿠버네티스 레벨에서 보장해준다는 장점

#### Running 상태가 되기 위한 조건 : postStart

파드의 컨테이너가 실행되거나 삭제될 때 특정 작업을 하도록 **라이프사이클 훅(Hook)** 을 정의할 수 있습니다.

- **postStart**: 컨테이너가 시작될 때 실행
- **preStop**: 컨테이너가 종료될 때 실행 (Terminating 상태에서 다시 설명)

postStart 사용 방식 2가지:

- **HTTP**: 컨테이너 시작 직후 특정 주소로 HTTP 요청 전송
- **Exec**: 컨테이너 시작 직후 컨테이너 내부에서 특정 명령어 실행

어느 쪽이든 상관없지만 책에서는 보편적인 Exec 방식을 사용합니다.

```yaml
spec:
  containers:
  - name: poststart-hook
    image: nginx
    lifecycle:
      postStart:
        exec:
          command: ["sh", "-c", "touch /myfile"]
```

```bash
kubectl apply -f poststart-hook.yaml
kubectl exec poststart-hook -- ls /myfile   # /myfile 존재 확인
```

- 컨테이너가 실행됨과 동시에 /myfile이 생성됨
- 단, postStart는 컨테이너의 **Entrypoint와 비동기적으로** 실행되므로 어느 쪽이 먼저 실행된다는 보장은 없음
- postStart의 명령어나 HTTP 요청이 제대로 실행되지 않으면 컨테이너는 Running이 되지 않고, Init 컨테이너처럼 restartPolicy에 따라 재시작됨
- postStart 단계가 오래 걸리면 그만큼 Running까지 걸리는 시간도 길어짐
- 로그 확인: Init 컨테이너 로그는 `kubectl logs <파드 이름> -c <컨테이너 이름>`으로 볼 수 있지만, postStart의 실행 로그는 에러가 나지 않는 한 따로 확인할 수 없음

#### 11.3.2.3 애플리케이션의 상태 검사 : livenessProbe, readinessProbe, startupProbe

Init 컨테이너가 차례로 실행되고, 컨테이너 안에서 postStart가 실행된 뒤에야 파드가 Running이 됩니다. 하지만 이것들이 정상 실행됐다고 해서 애플리케이션이 제대로 동작한다는 보장은 없습니다. 실행됐더라도 여러 이유로 요청을 처리할 수 없는 상태일 수 있기 때문입니다.

**파드 시작 후 컨테이너 내부의 동작 순서 (그림 11.27)**

파드 생성 → Init Containers(Container 1 → Container 2 → …) → Application Containers(postStart → Running), 그리고 Running 상태를 startupProbe, readinessProbe, livenessProbe가 검사

쿠버네티스는 애플리케이션이 요청을 처리할 수 있는 상태인지 판별하기 위해 세 가지 방법을 제공합니다. Running이 되기 위한 필수 조건은 아니지만, 실제로 요청을 처리할 수 있는지 확인하는 데 씁니다.

- **livenessProbe**: 컨테이너 안의 애플리케이션이 **살아있는지(liveness)** 검사. 실패하면 컨테이너는 restartPolicy에 따라 **재시작**
- **readinessProbe**: 애플리케이션이 사용자 요청을 처리할 **준비가 됐는지(readiness)** 검사. 실패하면 컨테이너는 **서비스의 라우팅 대상에서 제외**
- **startupProbe**: 애플리케이션 시작(startup) 시 수행되는 초기화 작업 등이 완료됐는지 확인. startupProbe에 성공해야 livenessProbe, readinessProbe가 시작되며, 실패하면 restartPolicy에 따라 재시작

**liveness와 readiness의 차이**

비슷해 보이지만 목적이 명확히 다릅니다.

- livenessProbe: 애플리케이션이 정상 상태를 유지하는지 **지속적으로** 검사. 실패는 내부에 뭔가 문제가 생겼다는 뜻이므로 정상으로 되돌리기 위해 컨테이너를 재시작
- readinessProbe: 시작 후 초기화가 끝나 **준비가 됐는지** 검사. 실패는 잠시 동안만 요청을 처리할 수 없다는 뜻일 수도, 개발자가 의도적으로 잠시 요청을 막은 것일 수도 있음. 그래서 재시작하지 않고, 서비스의 라우팅 대상과 엔드포인트(endpoint) 리소스에서 파드 IP를 제외함. 시간이 지나 준비가 끝나 검사에 성공하면 다시 라우팅 대상에 추가됨

**startupProbe**

초기화 작업 등이 완료됐는지 검사하는 기능입니다. 시작할 때 많은 데이터를 로드하거나 마이그레이션 작업 등으로 수분 이상 걸린다면 startupProbe로 완료 여부를 검사할 수 있고, 성공해야만 liveness/readiness 검사가 수행됩니다.

#### livenessProbe로 애플리케이션의 상태 검사

```yaml
spec:
  containers:
  - name: livenessprobe-pod
    image: nginx
    livenessProbe:   # 이 컨테이너에 대해 livenessProbe 정의
      httpGet:       # HTTP 요청으로 상태 검사
        port: 80     # <파드의 IP>:80/ 경로로 헬스 체크 요청
        path: /
```

**검사 방식 3가지** (livenessProbe, readinessProbe 공통, 하나를 선택)

- **httpGet**: HTTP 요청을 보내 검사. 응답 코드가 200 또는 300번대가 아니면 실패로 간주. 포트, 경로, 헤더, HTTPS 사용 여부 등 지정 가능
- **exec**: 컨테이너 안에서 명령어를 실행해 검사. 종료 코드가 0이 아니면 실패
- **tcpSocket**: TCP 연결이 수립될 수 있는지 체크. 연결이 안 되면 실패

**실습**

- 생성하면 주기적으로 파드 IP로 HTTP 요청을 보내 상태 검사
- Nginx는 기본적으로 80 포트의 / 경로에서 index.html을 제공하므로 검사 통과
- 일부러 실패시키기:

```bash
kubectl exec livenessprobe-pod -- rm /usr/share/nginx/html/index.html
kubectl get pods -w   # 잠시 후 RESTARTS가 0 → 1로 증가
```

- livenessProbe 실패로 컨테이너가 재시작됐고, 재시작으로 index.html이 원래대로 돌아왔으므로 검사는 다시 성공
- `kubectl describe po livenessprobe-pod`의 Events에서 `Liveness probe failed: HTTP probe failed with statuscode: 403`, 그리고 `failed liveness probe, will be restarted` 확인 가능
- Events는 `kubectl get events --sort-by=.metadata.creationTimestamp`로도 볼 수 있음

#### readinessProbe로 애플리케이션의 상태 검사하기

readinessProbe는 아직 준비되지 않은 파드가 요청을 받지 않도록 하는 기능입니다. 실패했더라도 시간이 지나 준비될 수 있으므로 **일시적으로 라우팅 대상에서 제외**하는 작업만 합니다.

테스트용 파드와 서비스:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: readinessprobe-pod
  labels:
    my-readinessprobe: test
spec:
  containers:
  - name: readinessprobe-pod
    image: nginx           # Nginx 서버 컨테이너
    readinessProbe:        # <파드의 IP>:80/로 상태 검사 요청
      httpGet:
        port: 80
        path: /
---
apiVersion: v1
kind: Service
metadata:
  name: readinessprobe-svc
spec:
  ports:
  - name: nginx
    port: 80
    targetPort: 80
  selector:
    my-readinessprobe: test
  type: ClusterIP
```

- 세부 옵션은 livenessProbe와 같은 방식으로 씀
- Nginx는 매우 빨리 준비되므로 실패 없이 곧바로 서비스로 접근 가능. `kubectl get pods -w`에서 READY가 0/1 → 1/1로 바뀌는 것 확인
- `curl readinessprobe-svc`로 접근하면 HTML 응답
- `kubectl get endpoints`에서 readinessprobe-svc가 파드 IP(예: 192.168.75.111:80)로 라우팅되고 있음

**실패시켜 보기**

```bash
kubectl exec readinessprobe-pod -- rm /usr/share/nginx/html/index.html
kubectl get pods -w   # READY 1/1 → 0/1, RESTARTS는 0 그대로
```

- livenessProbe와 달리 **RESTARTS는 증가하지 않고** READY 상태인 컨테이너만 하나 줄어듦
- 준비되지 않은 것으로 간주되어 서비스가 요청을 전달하지 않음. curl은 `Connection timed out`
- `kubectl get endpoints`를 보면 readinessprobe-svc의 ENDPOINTS에서 파드 IP가 제거되어 있음

**참고: minReadySeconds**

readinessProbe를 적용하기 어렵거나 초기화 시간이 어느 정도 필요하면 디플로이먼트의 `minReadySeconds`를 쓸 수 있습니다. 업데이트 시 컨테이너가 준비되기 위한 최소 대기 시간으로, 새 파드가 생성된 뒤 이 시간이 지나야 파드의 삭제 및 생성이 계속됩니다.

```yaml
spec:
  replicas: 1
  minReadySeconds: 30
  strategy:
    type: RollingUpdate
```

#### livenessProbe와 readinessProbe의 세부 옵션

상태 검사 주기, 타임아웃 등을 명시적으로 설정할 수 있고, 설정하지 않으면 기본값이 적용됩니다.

- **periodSeconds**: 상태 검사 주기. 기본값 10초
- **initialDelaySeconds**: 파드 생성 뒤 상태 검사를 시작할 때까지의 대기 시간. 기본적으로 설정되어 있지 않음
- **timeoutSeconds**: 요청 타임아웃. 기본값 1초
- **successThreshold**: 성공으로 간주할 검사 성공 횟수. 기본값 1
- **failureThreshold**: 실패로 간주할 검사 실패 횟수. 기본값 3

```yaml
readinessProbe:
  httpGet:
    port: 80
    path: /
  periodSeconds: 5
  initialDelaySeconds: 10
  timeoutSeconds: 1
  successThreshold: 1
  failureThreshold: 3
```

#### 11.3.2.4 Terminating 상태와 애플리케이션의 종료

새 버전을 배포할 때 새 파드가 준비됐는지 확인하는 것만큼 중요한 것이 **기존 버전의 파드를 무사히 종료시키는 것**입니다. 요청을 처리하던 도중 파드가 삭제되어 애플리케이션이 비정상 종료되면 사용자는 Empty Reply 같은 잘못된 응답을 받을 수 있습니다.

가장 좋은 방법은 애플리케이션 **소스코드 레벨에서 종료 처리 로직**을 구현하는 것입니다. 예: 이미 도착한 사용자 요청을 마저 끝내기, DB 커넥션 같은 리소스 정리. 그런데 이 로직이 언제 실행될지 알려면 파드가 삭제될 때 무슨 일이 일어나는지 알아야 합니다.

**kubectl delete로 파드를 삭제하면**

1. 삭제될 예정이라는 의미의 `deletionTimestamp` 값이 파드 데이터에 추가되고, 파드는 Terminating 상태가 됨
2. 다음 3가지가 **동시에** 실행됨
    - 2.1 파드에 preStop 라이프사이클 훅이 있다면 preStop 실행
    - 2.2 레플리카셋으로 생성된 파드라면 레플리카셋의 관리 영역에서 벗어나고, 레플리카셋은 새 파드 생성을 시도
    - 2.3 파드가 서비스 리소스의 라우팅 대상에서 제외됨
3. preStop 훅이 끝나면 리눅스 시그널 중 **SIGTERM**이 컨테이너에 전달됨. 컨테이너의 init 프로세스는 SIGTERM을 받은 뒤 종료돼야 함
4. 유예 기간이 지나도 프로세스가 종료되지 않으면 **SIGKILL**이 전달됨. 유예 기간은 기본 30초이며 `terminationGracePeriodSeconds`로 설정

그림 11.28의 시간 순서로 보면: 0초에 preStop 실행 → preStop 훅 실행 중 → SIGTERM 전달 → 프로세스 종료 중 → t1(terminationGracePeriodSeconds, 기본 30초)에 아직 안 끝났다면 SIGKILL 전달

이 중 우아한 종료를 위해 직접 장치를 마련할 수 있는 부분은 **2.1 preStop 훅**과 **3번 SIGTERM 전달** 단계입니다.

**preStop 훅**

- 컨테이너가 종료되기 전에 실행되는 작업으로, postStart처럼 exec나 HTTP 요청으로 사용
- 예: 프로세스를 종료하는 명령어를 쓰거나, 서버 종료를 실행하는 /abort 같은 경로로 HTTP 요청을 보낼 수 있음

```yaml
spec:
  containers:
  - name: prestop-hook
    image: nginx
    lifecycle:
      preStop:
        exec:
          command: ["/usr/sbin/nginx", "-s", "quit"]
```

**SIGTERM 처리**

- preStop 실행 후 컨테이너들에 SIGTERM을 보내 곧 종료될 것이라고 알림
- 애플리케이션 소스코드에서 SIGTERM을 받았을 때 어떻게 행동할지 구현해 둬야 함
- 처리 로직 없이 종료되면 클라이언트가 응답을 제대로 받지 못할 수 있음
- SIGTERM을 받고도 유예 시간 안에 종료되지 않으면 SIGKILL로 강제 종료

**유예 기간 설정**

```yaml
spec:
  terminationGracePeriodSeconds: 10
```

- `kubectl delete --grace-period=10`처럼 명령어로도 설정 가능
- 0으로 설정하면 파드의 컨테이너를 강제로 종료한다는 의미

#### 리소스 정리

```bash
cd chapter11-3/
kubectl delete -f ./
```

### 11.3.3 HPA를 활용한 오토스케일링

서버 개수를 고정해 두는 것은 비효율적입니다. 부하가 적으면 리소스를 낭비하고, 부하가 많으면 서버가 감당할 수 있는 양보다 많은 요청을 처리해야 할 수 있기 때문입니다. 그래서 쿠버네티스는 리소스 사용량에 따라 디플로이먼트의 파드 개수를 자동으로 조절하는 **HPA(Horizontal Pod Autoscaler)** 를 제공합니다.

**사전 조건: metrics-server**

- HPA는 내장 기능이지만, 14.3.1절의 **metrics-server**라는 리소스 메트릭 수집 도구를 설치해야 정상 동작
- 오토스케일링하려면 CPU, 메모리 사용량 정보를 어딘가에서 받아야 하는데, 쿠버네티스가 자체적으로 메트릭을 수집하지는 않기 때문
- 이 절은 metrics-server를 설치해 `kubectl top`을 쓸 수 있다고 가정
- 14장 모니터링은 12, 13장의 데몬셋, 커스텀 리소스 등을 알아야 이해가 쉬우므로, 가능하면 12, 13장을 읽은 뒤 14장에서 metrics-server를 써볼 때 HPA도 같이 써보는 것을 권장

**HPA YAML**

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: simple-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: simple-deployment   # 이 디플로이먼트의 자원 사용량을 체크
  metrics:
  - resource:
      name: cpu               # CPU 사용량 체크
      target:
        averageUtilization: 50   # 평균 활용률이 50% 이상인 경우
        type: Utilization
    type: Resource
  maxReplicas: 5              # 파드는 5개까지 늘어날 수 있음
  minReplicas: 1
```

**averageUtilization의 의미**

- 단순 CPU 사용량이 아니라 **파드에 할당된 request 대비** 얼마나 쓰고 있는지가 기준
- 예: CPU request가 1000m이면 사용률 50%가 되는 지점, 즉 500m을 기준으로 오토스케일링

**단일 파드 예시 (그림 11.29)**

- Pod A가 600m 사용 → 600m / 1000m × 100 = 60%로 50%보다 크므로 오토스케일링 수행
- 요청량이 같다면 파드를 늘리면 부하가 분산됨 → Pod A, B가 각각 300m
- HPA는 평균이 타깃 값보다 아래가 될 때까지 진행하므로, 이 예시에서는 파드 2개가 된 시점이 안정화된 상태

**여러 파드 예시 (그림 11.30)**

- 파드가 여러 개면 모든 파드 사용률의 **평균값**을 씀
- Pod A, B가 각각 600m → (600m + 600m) / 1000m / 2(파드 개수) × 100 = 60% → 오토스케일링
- 타깃 값보다 낮아질 수 있을 만큼 파드를 더 생성 → 3개가 되어 각각 400m

**실습**

```bash
kubectl apply -f simple-hpa.yaml
kubectl apply -f simple-deployment-svc.yaml   # CPU request를 설정한 디플로이먼트 + 서비스
kubectl get hpa
# TARGETS: cpu: 0%/50%, MINPODS 1, MAXPODS 5, REPLICAS 1
```

- TARGETS에 0%처럼 숫자가 나오면 HPA가 metrics-server로부터 메트릭을 정상적으로 받아오는 것
- 부하 생성에는 **ab(apache benchmark)** 사용. 순간적으로 많은 HTTP 요청을 보내는 벤치마크 도구

```bash
kubectl run -i --tty --rm debug --image=alpine sh
/ # apk add apache2-utils
/ # for i in $(seq 1 5); do ab -c 5 -n 100000 http://simple-deployment-svc:8080/; done;
```

- 다른 터미널에서 확인하면 TARGETS가 73%/50%, REPLICAS 4처럼 파드 개수가 늘어남
- 부하가 계속 가해져도 maxReplicas가 5라서 그 이상 늘어나지 않음

**메트릭 수집 주기 참고**

- HPA는 metrics-server의 API로부터 메트릭을 받아오며, 이 주기는 컨트롤러의 `-horizontal-pod-autoscaler-sync-period` 옵션으로 조정 가능 (기본 15초). GKE, EKS 등에서는 변경 불가
- metrics-server가 kubelet의 CAdvisor에서 메트릭을 가져오는 주기가 크면 HPA 반응이 늦어질 수 있음
- metrics-server의 `-metric-resolution`으로 수집 주기 조절 가능 (기본 60초). CAdvisor는 기본 15초마다 수집하므로 15초 이하로 설정하는 건 큰 의미가 없을 수 있음

**오토스케일링이 늘 좋은 건 아님**

- 예: 초기화할 때 잠시 CPU를 과도하게 쓰는 JVM 기반 애플리케이션
- HPA는 파드 생성 시간이 아니라 CPU 사용률을 기준으로 하므로 불필요하게 계속 스케일 아웃(scale-out)될 수 있고, 이게 계속 파드가 증식하는 연쇄 작용을 일으킬 수도 있음
- 반대로 CPU 사용률이 갑자기 낮아지면 여러 파드를 한꺼번에 스케일 인(scale-in)해서 안정성에 영향을 줄 수 있음

이에 대비해 HPA의 세밀한 동작을 제어하는 기능이 있습니다.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: scaling-policy-hpa
spec:
  ...
  behavior:
    scaleDown:                          # 1. 파드가 줄어드는 경우의 전략
      stabilizationWindowSeconds: 180   # 2. 스케일링 윈도우
      policies:                         # 3. 한 번에 몇 개의 파드를 생성/삭제하는지
      - type: Pods
        value: 4
        periodSeconds: 60
      - type: Percent
        value: 10
        periodSeconds: 60
      selectPolicy: Max                 # 4. 위 policies 중 어떤 값을 쓸지
    # scaleUp: 에도 동일한 스펙 정의 가능
```

**behavior 항목 설명**

1. **scaleDown / scaleUp**: 줄어들 때의 전략(scaleDown)과 늘어날 때의 전략(scaleUp). 예제는 scaleDown만 정의
2. **stabilizationWindowSeconds**: 파드 증감 개수를 계산할 때, 이 윈도우 안에서 **계속** 스케일링 조건이 만족돼야만 스케일링을 진행. 180초면 과거 180초 동안 계속 CPU 사용률이 낮게 유지돼야 파드를 줄임. 하나라도 조건을 만족하지 않으면 줄이지 않음. CPU 사용률이 기준점 근처에서 반복해서 오르내릴 때 파드가 불필요하게 자주 늘었다 줄었다 하는 현상을 막는 옵션
3. **policies**: 세부 전략. 예제는 한 번에 최대 4개까지, 또는 전체의 최대 10%까지 줄일 수 있게 설정. 한 번 스케일링이 이뤄지면 periodSeconds 동안은 추가 스케일링이 발생하지 않음
4. **selectPolicy**: policies 중 어떤 값을 쓸지. Max면 4개와 10% 중 더 큰 값을 선택. 예: 80개에서 10개로 줄여야 하면 처음엔 10%인 8개씩 줄이다가, 전체 개수가 일정 수준 이하로 내려가면 4개씩 줄임

**stabilizationWindowSeconds 예시 (그림 11.31, 180초 가정)**

- 10:00~10:02 구간에 CPU 사용률이 기준점(50%)을 넘었으므로, 10:03에 일시적으로 떨어져도 파드를 바로 줄이지 않음
- 10:08이 되었을 때는 과거 180초 동안 계속 사용률이 낮았으므로, 그제서야 파드를 줄이는 스케일링 진행

**기본값 (spec.behavior를 설정하지 않았을 때)**

이 세부 항목을 모두 반드시 설정해야 하는 건 아니며, 명시하지 않으면 다음 기본값이 쓰입니다.

```yaml
behavior:
  scaleDown:
    stabilizationWindowSeconds: 300
    policies:
    - type: Percent
      value: 100
      periodSeconds: 15
  scaleUp:
    stabilizationWindowSeconds: 0
    policies:
    - type: Percent
      value: 100
      periodSeconds: 15
    - type: Pods
      value: 4
      periodSeconds: 15
    selectPolicy: Max
```

즉 기본적으로 늘릴 때는 즉시(윈도우 0초) 15초마다 100% 또는 4개 중 큰 쪽만큼, 줄일 때는 300초 동안 조건이 유지돼야 15초마다 최대 100%까지 줄일 수 있습니다.

**참고: 특정 컨테이너 기준 스케일링**

HPA는 기본적으로 파드에 정의된 **모든 컨테이너의 리소스 합계**를 기준으로 합니다. 필요하면 특정 컨테이너의 사용량과 requests를 기준으로 할 수 있습니다.

```yaml
metrics:
- type: ContainerResource
  containerResource:
    container: postfix
    name: cpu
    target:
      type: Utilization
      averageUtilization: 60
```
