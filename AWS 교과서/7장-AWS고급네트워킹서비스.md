## 7.1 DNS란 무엇인가

우리는 웹사이트에 접속할 때 IP 주소가 아니라 `google.com` 같은 도메인 이름을 씁니다.
이게 가능한 이유가 바로 **DNS(Domain Name System)** 덕분입니다.
DNS는 문자로 된 도메인 이름을 실제 통신에 필요한 IP 주소로 변환해주는 서비스입니다.
통신 방식은 UDP 53번 포트를 사용합니다.

**도메인 구조**는 `blog.cloudneta.net`을 예로 들면 이렇게 쪼갤 수 있습니다.

- **루트 도메인**: 맨 끝의 점(생략하고 씀)
- **톱 레벨 도메인(TLD)**: `.net`, `.com`, `.kr` 같은 최상위 도메인
- **세컨드 레벨 도메인(SLD)**: `cloudneta` - TLD 안에서 유일하게 식별되는 이름
- **서브 도메인**: `blog`, `test`처럼 용도별로 앞에 붙이는 이름

**DNS 서버는 역할별로 나뉘어 있습니다.**

- 루트 네임 서버: TLD에 해당하는 네임 서버 정보를 알려줌 (전 세계 13개)
- TLD 네임 서버: 해당 TLD 내 SLD 네임 서버 정보를 알려줌
- SLD 네임 서버: 실제 도메인에 대한 최종 응답 권한을 가진 서버

이 사이를 중계하는 게 **DNS 해석기**입니다.
사용자가 도메인 주소를 물으면, 해석기가 루트 → TLD → SLD 네임 서버 순으로 차례차례 물어가며 최종 IP 주소를 알아내 사용자에게 전달하는 구조예요.

**DNS 레코드 유형**도 정리하면,

- **A**: 도메인 → IPv4 매핑
- **AAAA**: 도메인 → IPv6 매핑
- **NS**: 해당 도메인을 관리하는 네임 서버 지정
- **CNAME**: 도메인 별칭 지정 (다른 도메인을 가리킴)

<br>

## 7.2 Amazon Route 53

AWS가 제공하는 관리형 DNS 서비스입니다. 이름의 "53"은 DNS가 쓰는 UDP 53번 포트에서 따온 겁니다.

주요 기능 세 가지

1. **도메인 이름 등록** — 등록대행소 역할 수행
2. **호스팅 영역 생성** — 등록한 도메인의 권한 있는 네임 서버(SLD 네임 서버) 역할
3. **레코드 작성** — DNS 요청 처리 방식 정의

**라우팅 정책**이 Route 53의 핵심 기능인데, 다양한 방식으로 응답을 제어할 수 있습니다.

- **단순 라우팅**: 여러 대상 중 랜덤 응답
- **가중치 기반**: 가중치 비율대로 대상 선택 (예: 90:10)
- **지연 시간 기반**: 사용자와 가까운 리전의 대상으로 응답 (지연 시간 낮은 쪽)
- **장애 조치**: 액티브/패시브로 나눠 상태 검사(health check) 후 장애 시 자동 전환
- 그 외 지리 위치, 지리 근접, 다중 값 응답 라우팅도 있음

<br>

## 7.3 CDN(Content Delivery Network)

콘텐츠 제공자와 사용자가 지리적으로 멀리 떨어진 상황에서 콘텐츠를 빠르게 전달하는 기술입니다. 원본을 가진 **오리진 서버**의 부하와 지연 문제를 해결하기 위해, 캐시 서버를 여러 지역에 분산 배치하고 콘텐츠를 캐싱해서 사용자에게 가까운 곳에서 응답하는 방식입니다.

**캐싱 동작 방식**

- **Cache Miss**: 캐시 서버에 콘텐츠가 없어 오리진에 요청 → 받아서 저장 후 응답
- **Cache Hit**: 캐시 서버에 이미 콘텐츠가 있어 바로 응답

콘텐츠 저장 시간을 **TTL(Time To Live)**이라고 하며, 캐싱 방식은 두 가지로 나뉩니다.

- **정적 캐싱**: 이미지, JS, CSS처럼 안 바뀌는 정적 콘텐츠를 TTL 동안 저장해두고 Cache Hit로 응답
- **동적 캐싱**: 요청마다 달라지는 동적 콘텐츠는 저장하지 않거나 짧은 TTL만 적용, 지속적으로 Cache Miss 상태로 통과시킴

<br>

## 7.4 Amazon CloudFront

AWS의 CDN 서비스로, 전 세계 엣지 로케이션(edge location)과 리전별 엣지 캐시를 활용해 콘텐츠를 빠르게 배포합니다.

**구성 요소**

1. **오리진**: 원본 콘텐츠를 가진 대상 (EC2, ELB, S3, 또는 온프레미스 서버 가능)
2. **Distribution**: 오리진과 엣지를 연결하는 논리적 단위
3. **리전 엣지 캐시**: 오리진과 엣지 로케이션 사이의 큰 단위 캐시 영역
4. **엣지 로케이션**: 사용자와 가장 가까운 작은 단위의 캐시 지점

**주요 기능**

- 정적/동적 콘텐츠 각각에 최적화된 캐싱
- HTTPS 기능: 오리진이 HTTPS를 지원하지 않아도 CloudFront가 알아서 HTTPS 통신을 중계
- 다수의 오리진을 하나의 Distribution에서 선택적으로 처리
- 서명된 URL/쿠키로 접근 제어(인증된 사용자만 접근 허용)

<br>

## 7.5 실습: Amazon CloudFront로 CDN 서비스 구성하기

### 실습 목표

(1) 오리진 서버와 **직접 통신**하는 방식과 (2) **CloudFront를 경유**하는 방식의 성능 차이를 직접 비교해보는 실습입니다.

지연 시간 차이를 극대화하려고 일부러 사용자와 먼 **상파울루 리전**에 오리진 서버를 배치했어요.

### 실습 흐름

**1) 기본 인프라 배포**

CloudFormation으로 VPC, EC2(오리진 서버), 보안 그룹 등을 한 번에 자동 배포.

**2) Route 53으로 1차 검증**

생성된 EC2의 퍼블릭 IP를 Route 53의 A 레코드에 연결해서, 오리진에 직접 접속했을 때의 속도를 기준선으로 측정합니다. (평균 **2.35초**)

**3) CloudFront Distribution 생성**

- 오리진 대상 지정(EC2의 퍼블릭 DNS 주소)
- HTTPS 사용을 위해 ACM에서 와일드카드 인증서(`.도메인`) 발급 — DNS 검증 방식으로 진행
- WAF는 실습이라 비활성화, 캐시/프로토콜 설정 후 배포 생성

**4) Route 53에 CloudFront 별칭(Alias) 레코드 추가**

`cdn.도메인` 형태로 CloudFront Distribution을 가리키는 레코드를 만들어서, 이 주소로 접속하면 CloudFront를 경유하게 만듭니다.

**5) 성능 비교 검증**

- **최초 접속**: 엣지 로케이션에 캐시가 없어 오리진까지 갔다 옴 → 응답 헤더 `X-Cache: Miss from cloudfront`, 지연 시간 **3.41초** (오히려 직접 접속보다 느림)
- **재접속(캐시 비우고 강력 새로고침)**: 엣지 로케이션에 캐시된 콘텐츠로 즉시 응답 → `X-Cache: Hit from cloudfront`, 지연 시간 **0.89초**로 대폭 단축
- `X-Amz-Cf-Pop` 헤더 값으로 어느 엣지 로케이션이 응답했는지도 확인 가능 (실습에서는 서울 인천 엣지가 응답)

### 핵심적으로 배운 것

**Cache Miss는 최초 1회의 비용이다.** CDN이 무조건 빠른 게 아니라, 처음 캐싱하는 순간에는 오히려 오리진 왕복 때문에 더 느릴 수 있습니다. 하지만 그 이후부터는 압도적으로 빨라진다는 게 이번 실습에서 수치로 확인한 핵심 포인트입니다. (2.35초 → 0.89초, 캐시 히트 시 거의 62% 단축)

**HTTPS는 CloudFront 앞단에서 해결된다.** 오리진 서버가 HTTP만 지원해도, ACM 인증서를 CloudFront에 붙이면 사용자-CloudFront 구간은 HTTPS로 암호화되고, CloudFront-오리진 구간만 HTTP로 남습니다. 오리진에 인증서를 직접 설치할 필요가 없어집니다.

**Route 53의 별칭(Alias) 레코드**로 도메인을 AWS 리소스(CloudFront, ALB 등)에 직접 연결할 수 있다는 것도 실습 포인트였어요. 일반 CNAME과 달리 루트 도메인에도 사용 가능하고 AWS 내부적으로 최적화되어 있습니다.

### 실무 적용 관점

- **정적 자산(이미지, JS, CSS, 동영상)이 많은 웹서비스라면 CloudFront 같은 CDN 도입이 사실상 필수**입니다.
    - 오리진 부하 감소 + 사용자 체감 속도 개선을 동시에 잡을 수 있습니다.
- 오리진이 특정 리전에 몰려 있고 사용자는 전 세계에 분산되어 있는 서비스(글로벌 서비스)일수록 CDN의 효과가 극대화됩니다.
- 반대로, **자주 바뀌는 동적 콘텐츠(API 응답, 개인화된 데이터)**는 캐싱 효과가 제한적이니 TTL을 짧게 주거나 캐싱 대상에서 제외하는 정책 설계가 필요합니다.
- **HTTPS 인증서 관리 부담을 CloudFront/ACM으로 위임**하는 패턴은 실무에서도 자주 쓰이는 구조입니다. 오리진 서버 여러 대에 각각 인증서를 관리하지 않아도 되니 운영 편의성이 큽니다.
