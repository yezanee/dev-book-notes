## 6.1 데이터베이스와 DBMS

### **데이터 vs 정보**

- 데이터: 원시적인 자료로 그 자체로는 의미나 가치가 없음
- 정보: 데이터를 특정 목적에 따라 가공하고 의미를 부여한 결과

### **데이터베이스와 DBMS**

- 데이터베이스: 데이터를 하나에 모아 두는 집합
- DBMS: 데이터베이스를 관리하는 시스템으로, 사용자의 논리적 명령을 해석해 필요한 데이터를 찾아주는 시스템

### **데이터베이스 모델 유형**

- **계층형**: 트리 구조 기반, 1:N 상하 종속 관계. 빠른 접근 가능하지만 구조 변경 유연성 부족
- **네트워크형**: 1:N뿐 아니라 1:1, N:N 구조 가능. 형태는 자유롭지만 복잡성 높음
- **관계형**: 열(column)과 행(row)으로 된 테이블 단위. 데이터 변화에 유연하게 대응 가능하며 현재 가장 널리 사용됨 (SQL 사용)
- **객체 지향형**: 객체(object) 단위로 표현, 비정형 데이터 지원하지만 호환성·복잡성 문제로 제한적 활용

### **관계형 DBMS의 SQL 언어**

- 데이터 정의(DDL): CREATE, ALTER, DROP
- 데이터 조작(DML): SELECT, INSERT, UPDATE, DELETE
- 데이터 제어(DCL): GRANT, REVOKE

## 6.2 AWS 데이터베이스 서비스

AWS는 데이터베이스 유형별로 다양한 서비스 제공

- 관계형: RDS/Aurora
- 키-값: DynamoDB
- 문서형: DocumentDB
- 인-메모리: ElastiCache
- 그래프형: Neptune
- 시계열: Timestream
- 원장: QLDB

### **6.2.1 Amazon RDS**

- 클라우드 환경에서 관계형 데이터베이스를 간편하게 설정·운영하는 서비스
- Aurora, PostgreSQL, MariaDB, Oracle, SQL Server 등 다양한 엔진 선택 가능
- 행(row)과 열(column)로 구성된 테이블 구조, SQL 기반 제어

## **6.2.2 Amazon RDS 데이터 복제**

- **Multi-AZ**: 액티브-스탠바이 구조, 동기식 복제로 데이터 정합성 유지 → 고가용성 목적
- **Read Replica**: 원본은 Primary DB에 두고 비동기식 복제로 읽기 전용 복제본 생성 → 최대 15개, 다른 리전도 가능 → 읽기 성능 확장 목적

### **6.2.3 Amazon Aurora**

- AWS가 자체 개발한 엔터프라이즈급 관계형 DB 엔진 (RDS 위에서 동작)
- 오픈소스 호환성 우수, 비용 효율 높음
- 공유 스토리지 기반으로 3개 가용 영역에서 총 6개 복제본 유지 → 일반 MySQL(EBS 기반 동기식 복제, AZ 2개)보다 스토리지 내결함성이 뛰어남

### **6.2.4 Amazon DynamoDB**

- 비관계형(NoSQL) 키-값 데이터베이스, SQL을 사용하지 않음
- 구조: 파티션 키(필수, 데이터 분산 기준) + 소트 키(선택) + 속성(attributes)으로 구성된 항목(items)
- 서버리스 방식으로 프로비저닝·패치 불필요, 자동 확장/축소
- 대규모 환경에서도 일관되게 10ms 미만 처리 성능 제공

### **6.2.5 Amazon ElastiCache**

- 인-메모리 데이터베이스, 데이터를 메모리에 저장해 빠른 처리 가능 (대용량엔 부적합)
- **Memcached**: 범용 메모리 객체 캐싱 시스템과 호환
- **Redis**: 캐시·메시지 브로커·대기열 용도, 1ms 미만 지연으로 실시간 애플리케이션 지원

## 6.3 실습 - 웹 서버와 Amazon RDS 연동하기

### 배운 것

- Amazon RDS는 관계형 DB를 클라우드에서 쉽게 설정하고 운영할 수 있게 해주는 서비스다
- **Multi-AZ**는 고가용성을 위한 기능이다. Primary DB와 Standby Replica가 동기식으로 복제되어 있다가, 장애가 생기면 Standby가 자동으로 Primary로 승격된다
- **Read Replica**는 성능 확장을 위한 기능이다. 원본 데이터를 비동기식으로 복제해서 읽기 전용 복제본을 만들고, 읽기 트래픽을 분산시킨다
- 두 기능은 목적이 다르다: Multi-AZ는 "죽지 않게", Read Replica는 "더 빠르게"

### 실습에서 한 것

- CloudFormation으로 VPC, 서브넷, EC2 등 기본 인프라를 자동 배포
- Multi-AZ가 켜진 RDS1과 꺼진 RDS2를 각각 만들어서 비교
- RDS2를 중지시켜보니 서비스가 그냥 끊어짐 (단일 DB라 대안이 없음)
- **RDS1을 재부팅하면서 장애 조치를 걸어보니, Standby가 Primary로 자동 승격되면서 서비스가 안 끊기고 IP만 바뀜 (페일오버 직접 확인)**
- RDS1의 Read Replica(RDS1-RR)를 만들어서, 원본에 쓴 데이터가 복제본에도 동기화되는 걸 확인
- 복제본에 직접 쓰기를 시도하니 read-only 에러로 막힘 (읽기 전용이라는 걸 실제로 체감)

### 실무에 적용할 수 있는 부분

- 운영 서비스라면 **Multi-AZ는 사실상 기본 옵션으로 켜두는 게 맞다.** 장애 났을 때 자동 복구가 되느냐 안 되느냐 차이가 크다
- 트래픽이 몰리는 서비스, **특히 읽기 요청이 압도적으로 많은 경우(조회 위주 API, 대시보드 등)엔 Read Replica로 읽기를 분산**시키는 걸 고려할 수 있다
- Read Replica를 쓰려면 자동 백업이 켜져 있어야 한다는 제약이 있으니, DB 설계 초기에 백업 정책부터 챙겨야 한다
- 페일오버가 일어나면 DB의 IP나 엔드포인트가 바뀔 수 있다는 점을 감안해서, 애플리케이션은 IP를 하드코딩하지 말고 엔드포인트(도메인) 기준으로 연결하는 게 안전하다
