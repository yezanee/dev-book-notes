## 8.1 AWS 리소스를 다루는 3가지 방법

| 방법 | 특징 |
| --- | --- |
| **AWS 관리 콘솔** | 웹 기반 GUI, 직관적이라 입문 단계에 적합. 단, 대규모 운영·반복 작업엔 부적합 (→ Terraform 같은 IaC 권장) |
| **AWS CLI** | 명령줄 기반 통합 도구. 콘솔보다 빠르고, 스크립트 작성 시 유용 |
| **AWS SDK** | 파이썬·Go·자바 등 언어별 라이브러리. 프로그래밍적으로 AWS 리소스 제어 가능 |

세 방법 모두 결국 **AWS API**를 호출하는 방식이라는 점이 핵심입니다.

### AWS API란?

- **API**: 두 애플리케이션이 상호작용하도록 돕는 매개체
- 사용 조건 두 가지
    1. **인증(authentication)** + **인가(authorization)** 확인 → 적법한 사용자인지, 권한이 있는지 체크
    2. **명세서**에 따른 규칙 준수 (요청 형식, 데이터 유형 등)

**흐름 요약**: 사용자 요청 → AWS API가 인증·인가 확인 → 통과 시 해당 AWS 서비스(EC2, S3 등)로 요청 전달 → 처리

> 💡 **AWS CloudTrail**: 인증·인가 이후 발생하는 API 활동 기록(로깅)을 남기는 서비스. 보안 사고·장애 발생 시 신속 대응을 위해 매우 중요.

## 8.2 AWS IAM (Identity & Access Management)

**핵심 한 줄**: IAM = "**누구냐 넌?**"(인증) + "**너 권한 있니?**"(인가)를 관리하는 서비스. **추가 비용 없이** 사용 가능.

### 구성 요소 4가지

- **AWS 계정 루트 사용자**: 처음 생성된 계정, **모든 권한** 보유 → 직접 사용은 비권장
- **IAM 사용자(user)**: 계정 내 개별 사용자, 자체 자격 증명 보유
- **IAM 그룹(group)**: 사용자 묶음 → 권한을 그룹 단위로 일괄 관리
- **IAM 정책(policy)**: 허용/거부 권한을 정의하는 객체
- **IAM 역할(role)**: **임시 자격 증명**을 제공하는 IAM 자격 증명 (장기 암호·키 없음)
- **보안 주체(principals)**: 루트 사용자, IAM 사용자, IAM 역할로 로그인해 AWS에 요청하는 주체

### 루트 사용자 vs IAM 사용자

| 구분 | 권한 | 특징 |
| --- | --- | --- |
| 루트 사용자 | 전체 권한(AWS) | 해킹 시 계정 전체 위험 → **직접 사용 비권장** |
| IAM 사용자 | 제한 권한(AWS) | 해킹돼도 격리·차단·로그 분석 가능 → **강력 권장** |

### 인증 → 인가 동작 순서

1. **인증**: ID/암호(또는 접근 키)가 올바른지 확인
2. **인가**: 인증된 사용자가 해당 작업 권한이 있는지 확인 (예: S3 FullAccess가 있어야 S3 업로드/삭제 가능)

### IAM 정책 구조 (JSON)

```json
{
  "Statement": [{
    "Effect": "Allow or Deny",
    "Principal": "principal",
    "Action": ["action"],
    "Resource": ["*"],
    "Condition": {"key":"value"}
  }]
}
```

- **Effect**: 허용/차단
- **Principal**: 접근 주체
- **Action**: 허용·차단할 작업
- **Resource**: 대상 리소스(ARN)
- **Condition**: 적용 조건

### IAM 역할(Role) - 실전 활용 시나리오

IAM 역할은 **임시 자격 증명**(+Token, 시간 만료)을 발급하는 "역할 수임(AssumeRole)" 방식으로 동작합니다.

1. **EC2 인스턴스가 S3에 접근해야 할 때**
→ S3 Full 권한이 연결된 **IAM 역할**을 EC2 인스턴스 프로파일로 연결 → 개발자가 별도 자격 증명을 관리할 필요 없음
2. **외부 사용자가 AWS 리소스에 접근해야 할 때**
→ 외부 사용자 관리 시스템과 AWS IAM 시스템을 연동 → IAM 역할 기반 임시 자격 증명으로 접근

**활용 예**: EC2 Instance Profile, Cross-Account, SAML 2.0, Web Identity Provider 등

## 실무 적용 포인트

### 1. **팀원별 권한 분리 (admin/viewuser 패턴)**

- 신입/외부 협력사 → `ViewOnlyAccess`로 조회만 허용
- 시니어/인프라 담당자 → 필요한 서비스만 골라 `AdministratorAccess` 대신 **최소 권한 정책** 부여
- 실무에서는 **AdministratorAccess를 실사용자에게 거의 주지 않고**, 필요한 서비스(EC2, S3 등)별로 정책을 쪼개 부여하는 것이 표준

### 2. **위험한 작업 차단용 Deny 정책**

- 예: "운영 환경 EC2는 절대 종료 금지", "특정 리전 밖 리소스 생성 금지" 등을 인라인/관리형 정책으로 강제
- 실수로 인한 **운영 서버 삭제 사고 방지**에 실전 활용 가능

### 3. **EC2 Instance Profile (IAM 역할)로 자격 증명 관리 부담 제거**

- 애플리케이션 코드에 `AWS Access Key`를 **하드코딩하지 않는 것**이 보안 모범 사례
- 이 실습의 S3IAMRoleEC2처럼, EC2에 IAM 역할을 연결하면:
    - 액세스 키 발급·순환·유출 위험 관리 불필요
    - 키가 코드/깃허브에 노출되는 사고 원천 차단
    - 실무에서 **Lambda, ECS, EKS** 등 대부분의 컴퓨팅 서비스에 동일 패턴 적용됨

### 4. **CloudFormation으로 인프라 재현성 확보**

- 실습 인프라 전체가 YAML 템플릿 하나로 배포/삭제됨 → **IaC(Infrastructure as Code)** 개념을 자연스럽게 체험
- 실무에서는 이런 방식으로 "개발/스테이징/운영" 환경을 동일하게 반복 구성
