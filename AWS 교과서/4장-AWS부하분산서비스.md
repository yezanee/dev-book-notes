## 4.1  Amazon ELB 기능 소개

### 4.1.1 부하분산이 필요한 이유

서버 하나로 클라이언트 요청을 받으면 두 가지 문제가 생깁니다. 트래픽이 몰리면 그 서버 혼자 감당해야 하고, 그 서버에 장애가 나면 서비스 전체가 멈춥니다.

이걸 해결하는 방법이 부하분산(load balancing)입니다. **동일한 역할을 하는 서버 여러 대에 트래픽을 나눠주는 방식**이고, 이 작업을 해주는 장치가 **로드 밸런서**입니다. 클라우드 환경에서는 **여러 가용 영역에 분산된 서버로 트래픽을 나눠주기 때문에**, 특정 서버 하나가 죽어도 서비스는 계속 살아있는 고가용성을 확보할 수 있습니다.

### 4.1.2 AWS의 로드 밸런싱 서비스, ELB

AWS는 **ELB(Elastic Load Balancing)**라는 이름으로 로드 밸런싱 서비스를 제공합니다. EC2 인스턴스, 컨테이너, 람다 함수 등으로 들어오는 트래픽을 **여러 대상에 자동으로 분산**해주고, **여러 가용 영역**에서 동작하기 때문에 애플리케이션 가용성을 높여줍니다.

CloudWatch와 연동해서 상태를 모니터링할 수 있고, Auto Scaling과 함께 쓰면 트래픽이 늘어날 때 인스턴스를 자동으로 늘리거나 줄일 수도 있습니다.s

### 4.1.3 ELB를 이루는 세 가지 구성 요소

- **로드 밸런서**: 클라이언트 요청을 받아서 적절한 대상으로 전달하고, 응답을 다시 클라이언트에 돌려주는 역할
- **대상 그룹**: 트래픽을 분산할 대상들의 묶음. 여기 속한 대상들의 상태를 주기적으로 확인(health check)해서, 정상인 대상에게만 요청을 보냄
- **리스너**: 로드 밸런서가 어떤 프로토콜·포트로 트래픽을 받을지, 그리고 받은 요청을 어느 대상 그룹으로 보낼지 규칙을 정의

### 4.1.4 ELB 동작 방식

클라이언트는 ELB의 도메인 주소(DNS) 하나만 알면 됩니다. 그 뒤에 서버가 몇 대 있는지, 어떤 서버가 응답했는지는 전혀 몰라도 됩니다. ELB가 중간에서 이걸 다 가려주기 때문입니다.

전체 흐름은 아래 4단계입니다.

**요청 수신 → 대상 그룹 선택 → 트래픽 분산 → 응답 반환**

#### 사전 작업: ELB 생성

Amazon ELB를 생성하면 선택한 가용 영역에 로드 밸런서 노드가 생성되고, 리스너를 구성할 수 있습니다.

리스너는 다양한 프로토콜(HTTP, HTTPS, TCP 등)을 사용해 클라이언트 요청을 수신하며, 이 요청을 어떤 대상 그룹으로 전달할지에 대한 라우팅 규칙을 정의합니다.

이 구성이 끝나면 실제 트래픽 처리는 아래 4단계로 진행됩니다.

#### 1단계. 클라이언트 요청 수신

로드 밸런서가 클라이언트 요청을 수신합니다.

이때 로드 밸런서는 클라이언트와 연결을 유지하며, 요청을 수신하기 위해 리스너를 등록합니다.

#### 2단계. 대상 그룹 선택

수신한 클라이언트 요청을 처리할 **대상 그룹**을 선택합니다.

대상 그룹은 다음과 같은 다양한 유형의 대상으로 구성될 수 있습니다.

- EC2 인스턴스
- IP 주소
- 람다 함수
- ALB

#### 3단계. 트래픽 분산

로드 밸런서는 선택한 가용 영역에 위치한 대상 그룹의 대상으로 트래픽을 전달합니다.

이 과정에서 로드 밸런서는 대상 그룹 안에서 **상태가 정상인 대상**을 선택하고 그 대상으로 트래픽을 분산합니다.

각 대상의 가용성 상태는 계속 모니터링되며, 가용하지 않은 대상은 자동으로 제외됩니다.

#### 4단계. 응답 반환

대상이 처리한 응답을, 로드 밸런서를 거쳐 클라이언트에게 돌려줍니다.

클라이언트는 이 응답을 로드 밸런서로부터 받은 것으로 인식하며, 실제로 어떤 대상이 처리했는지는 알 수 없습니다.

### 4.1.5 ELB 교차 영역 로드 밸런싱

로드 밸런서는 가용 영역별로 노드를 하나씩 두는데, 문제는 가용 영역마다 인스턴스 수가 다를 수 있습니다.

예를 들어 A 영역에 인스턴스 2대, C 영역에 8대가 있다면, 트래픽을 단순히 50:50으로 나눠도 A 영역 인스턴스 한 대당 부하가 C 영역보다 훨씬 커집니다.

- **교차 영역 로드 밸런싱(cross-zone load balancing)**을 켜면 가용 영역 경계를 넘어서 전체 인스턴스 수를 기준으로 균등하게 트래픽을 나눠줍니다. 위 예시라면 총 10대 인스턴스에 똑같이 10씩 분산되는 식이죠. 참고로 ALB는 이 기능이 기본적으로 켜져 있고, NLB는 기본적으로 꺼져 있습니다.

### 4.1.6 ELB의 네 가지 종류

| 종류 | 특징 |
| --- | --- |
| **CLB** | 초기 버전, 레거시 취급. 현재는 잘 안 씀 |
| **ALB** | URL 경로·호스트·쿼리 문자열 기반 라우팅 가능. 웹 애플리케이션에 특화 |
| **NLB** | 처리량과 응답 속도가 가장 뛰어남. 고정 IP 지원. 게임 서버·VoIP 등에 적합 |
| **GWLB** | 서드파티 방화벽·보안 장비로 트래픽을 우회시킬 때 사용 |

#### **ALB vs NLB**

- **ALB**: HTTP/HTTPS 처리에 특화된 애플리케이션 레벨의 로드 밸런서로, OSI 모델의 7계층에서 라우팅 동작이 가능합니다. 람다(lambda)를 대상 그룹으로 지정할 수 있습니다.
- **NLB**: TCP, UDP, TLS에 대한 트래픽을 처리할 수 있는 OSI 4계층의 로드 밸런서로, ELB 중 가장 빠르고 높은 처리량을 지원합니다. 고정 IP를 사용할 수 있습니다.

## 4.2 ALB와 NLB로 로드 밸런싱 직접 구성해보기

### 1. 기본 인프라는 CloudFormation으로 한 번에 배포

인프라를 하나하나 손으로 만들면 시간도 오래 걸리고 실수하기 쉽습니다. 그래서 AWS는 **CloudFormation**이라는 IaC(코드로 인프라를 관리하는) 서비스를 제공합니다. YAML/JSON으로 작성된 템플릿을 업로드하면, 그 안에 정의된 리소스(VPC, EC2, 보안 그룹 등)를 자동으로 생성해주는 방식입니다.

실습에서는 이미 준비된 템플릿 URL(S3에 올라가 있는 yaml 파일)을 CloudFormation 스택 생성 화면에 입력하고, 스택 이름과 키 페어만 지정해주면 약 5분 뒤 VPC, 서브넷, 보안 그룹, EC2 인스턴스까지 전부 자동으로 만들어집니다.

이렇게 만들어진 서버 3대에는 미리 HTTP와 SNMP 서비스가 설치되어 있고, 서버마다 살짝 다른 폴더 구조(dev, mgt)를 가지고 있는데, 이건 나중에 경로 기반 라우팅 실습에 쓰입니다.

### 2. ALB 생성하고 기본 동작 확인하기

1. 먼저 **대상 그룹**(ALB-TG)을 만들고 서버 3대를 전부 등록합니다.
2. EC2 > 로드밸런서에서 **Application Load Balancer**를 생성합니다. 이때 VPC는 ELB-VPC, 가용 영역은 두 곳 다 체크, 리스너는 HTTP:80 → 방금 만든 대상 그룹으로 연결합니다.
3. 생성이 끝나면 ALB는 각 가용 영역마다 노드를 하나씩 만들고, ALB만의 도메인 주소(DNS)가 생깁니다.

MyEC2에서 `curl $ALB`를 여러 번 반복해보면, 세 대의 서버가 거의 균등하게(약 33%씩) 응답하는 걸 확인할 수 있습니다. 이건 ALB가 **교차 영역 로드 밸런싱**이 기본적으로 켜져 있어서, 가용 영역에 상관없이 전체 인스턴스 기준으로 트래픽을 고르게 분산하기 때문입니다.

### 3. 경로 기반 라우팅 구성하기

이번엔 URL 경로에 따라 다른 서버 그룹으로 트래픽을 보내는 걸 해봅니다.

- `/dev/*` 경로 → **DEV-TG**(SERVER-1만 포함)
- `/mgt/*` 경로 → **MGT-TG**(SERVER-2, 3 포함)

방법은 대상 그룹을 두 개(DEV-TG, MGT-TG) 새로 만든 다음, ALB 리스너에 규칙을 추가하는 겁니다. "경로 조건이 `/dev/*`면 DEV-TG로, `/mgt/*`면 MGT-TG로 보내라"는 규칙을 우선순위와 함께 등록하면 끝입니다.

`curl $ALB/dev/index.html`을 반복하면 SERVER-1만 응답하고, `curl $ALB/mgt/index.html`을 반복하면 SERVER-2·3만 번갈아 응답하는 걸로 규칙이 제대로 동작하는지 확인할 수 있습니다.

### 4. User-Agent 기반 라우팅 (특정 기기 차단)

ALB는 HTTP 헤더까지 들여다볼 수 있는 7계층 로드 밸런서이기 때문에, User-Agent 값으로도 규칙을 만들 수 있습니다.

- HTTP 헤더 이름: `User-Agent`
- 값이 `iphone*` 또는 `android*`면 → **고정 응답 반환**(503 에러, "iphone or android Access Deny" 메시지)

이 규칙을 추가한 뒤 실제 스마트폰 브라우저로 ALB IP에 접속해보면 접근이 차단되는 걸 확인할 수 있습니다. 이건 ALB가 HTTP를 이해하기 때문에 가능한 고급 기능이고, 뒤에 나올 NLB에서는 불가능합니다.

### 5. NLB 생성하고 ALB와 차이 비교하기

이번엔 4계층(TCP/UDP) 로드 밸런서인 **NLB**를 만들어봅니다. 이번엔 HTTP가 아니라 SNMP(UDP 161번 포트) 트래픽을 분산합니다.

- 대상 그룹(NLB-TG): 프로토콜 UDP, 포트 161, 서버 3대 등록
- NLB 생성 후 리스너는 UDP:161 → NLB-TG로 연결

MyEC2에서 `snmpget`을 60번 반복해보면 SERVER-1이 30회, SERVER-2·3이 각각 15회씩 응답합니다. ALB와 다르게 균등하지 않은 이유는 **NLB는 교차 영역 로드 밸런싱이 기본적으로 꺼져 있기 때문**입니다. 즉 가용 영역별로 도착한 요청을 그 영역 안에서만 라운드로빈으로 나누는 겁니다.

이후 NLB 속성에서 교차 영역 로드 밸런싱을 수동으로 **활성화**하면, 그때부터는 ALB처럼 세 서버가 균등하게 응답합니다(설정 반영까지 약 5분 소요).

### 6. ALB와 NLB의 출발지 IP 보존 방식 차이

이건 실무에서 은근히 중요한 포인트입니다.

- **ALB**: 클라이언트 트래픽을 로드밸런싱하면서 출발지 IP를 자신의(ALB의) 사설 IP로 바꿔서 전달합니다. 그래서 서버 로그에는 실제 클라이언트가 아니라 ALB의 IP만 찍힙니다. 진짜 클라이언트 IP를 알고 싶다면 HTTP 헤더의 **X-Forwarded-For(XFF)** 필드를 확인해야 합니다. (Apache 로그 포맷에 `%{X-Forwarded-For}i`를 추가하면 XFF 값이 로그에 남습니다.)
- **NLB**: 클라이언트의 출발지 IP를 그대로 보존한 채 서버에 전달합니다. 패킷 덤프(tcpdump)로 확인해보면 서버 입장에서 클라이언트 IP가 그대로 보입니다. 단, NLB는 4계층까지만 이해하기 때문에 HTTP 헤더(XFF) 개념 자체가 없고, 대상 그룹을 인스턴스가 아닌 IP로 지정하면 이마저도 보존되지 않습니다.

## 실무에서는 어떻게 쓰일까?

### 1. ALB 경로 기반 라우팅

하나의 도메인 아래에서 여러 서비스를 운영할 때 씁니다.

- `example.com/api/*` → 백엔드 API 서버 그룹
- `example.com/static/*` → 정적 파일 서버 그룹
- `example.com/admin/*` → 관리자 페이지 서버 그룹

마이크로서비스 아키텍처에서 API 게이트웨이 역할을 ALB 하나로 대신하는 경우가 많습니다. 서비스별로 서버를 따로 운영해도 사용자는 도메인 하나만 기억하면 됩니다.

### 2. User-Agent / HTTP 헤더 기반 라우팅

- 모바일 앱 전용 API와 웹 브라우저용 API 서버를 분리
- 특정 봇(크롤러)이나 오래된 브라우저의 접근 차단
- 특정 국가·언어 헤더에 따라 다른 콘텐츠 서버로 분기

### 3. X-Forwarded-For(XFF)

ALB 뒤에 있는 서버는 실제 접속자 IP를 모르기 때문에, 다음 상황에서 XFF가 필수입니다.

- 로그인 시도 위치 기반 이상 탐지 (보안)
- 특정 국가 IP 차단/허용 (지역 제한 서비스)
- 접속자별 트래픽 분석, 어뷰징 탐지

### 4. NLB가 쓰이는 상황

NLB는 IP를 보존하고 지연시간이 매우 짧아서, HTTP가 아닌 프로토콜을 다뤄야 할 때 선택합니다.

- **게임 서버** (TCP/UDP 기반, 낮은 지연시간이 생명)
- **VoIP, 실시간 스트리밍**
- **IoT 기기 통신** (SNMP, MQTT 등 비HTTP 프로토콜)
- 클라이언트의 **실제 IP가 서버 로직에 꼭 필요한 경우** (예: 사설 네트워크 내부 통신, VPN 게이트웨이)
- **고정 IP**가 필요한 화이트리스트 기반 방화벽 연동

### 5. 교차 영역 로드 밸런싱

가용 영역마다 서버 대수가 다르게 배포된 실전 환경(예: 오토스케일링으로 대수가 유동적일 때)에서 특정 서버에 부하가 몰리는 걸 막기 위해 켜두는 게 일반적입니다. ALB는 기본 활성화, NLB는 필요시 수동으로 켜야 한다는 점을 기억해두면 실무에서 헷갈리지 않습니다.

## 참고) ALB vs API Gateway는 별개의 AWS 서비스

| 구분 | ALB | API Gateway |
| --- | --- | --- |
| 계층 | OSI 7계층 로드 밸런서 | 완전관리형 API 게이트웨이 |
| 주 목적 | 트래픽을 여러 서버(대상 그룹)로 분산 | API 요청의 인증·제한·변환·관리 |
| 라우팅 | 경로/호스트/헤더 기반 (단순) | 훨씬 세밀한 API 라우팅 |
| 인증 | 기본적으로 없음 (별도 구성 필요) | IAM, Cognito, API Key, Lambda 인증 등 내장 |
| 요청 제한 | 없음 | Throttling, 사용량 플랜(Usage Plan) 내장 |
| 요금 | 로드밸런서 사용 시간 + 처리량 | API 호출 건당 과금 |
| 캐싱 | 없음 | 응답 캐싱 지원 |
| 대상 | EC2, IP, Lambda, 컨테이너 | Lambda, HTTP 엔드포인트, AWS 서비스 |

### 언제 뭘 쓰나

#### **ALB를 쓰는 경우**

- 일반적인 웹 애플리케이션에서 서버 여러 대로 트래픽 분산
- 컨테이너(ECS/EKS) 서비스 앞단에서 로드 밸런싱
- 단순한 경로 기반 라우팅 정도면 충분한 경우

#### **API Gateway를 쓰는 경우**

- 외부 개발자에게 API를 공개하고 API Key로 사용량을 관리해야 할 때
- Lambda 기반 서버리스 아키텍처의 진입점
- 요청 속도 제한(Rate Limiting), 요청/응답 변환이 필요할 때
- OAuth, Cognito 등으로 세밀한 인증이 필요할 때

#### 실제로는 같이 쓰는 경우가 많음

API Gateway 뒤에 ALB를 연결해서, "API Gateway가 인증·제한을 처리하고 → ALB가 실제 서버들로 트래픽을 분산"하는 조합도 흔합니다. 즉 경쟁 관계가 아니라 **역할이 다른 도구**라고 보시면 정확합니다.
