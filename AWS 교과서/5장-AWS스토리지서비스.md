## 5.1 스토리지 개요

스토리지는 데이터를 보관하는 공간입니다. USB, 외장 하드처럼 물리적 저장 장치부터 클라우드 환경의 서비스형 스토리지까지 다양한 형태가 있으며, 클라우드에서는 물리적 장치를 직접 관리하지 않고 필요한 만큼만 사용할 수 있습니다.

## 5.2 스토리지 서비스 및 주요 기능

데이터 저장 방식에 따라 세 가지로 구분됩니다.

### **5.2.1 블록 스토리지**

- 데이터를 일정 크기의 블록 단위로 분할 저장
- 운영체제에서 일반 디스크 장치처럼 인식
- SAN(Storage Area Network)이나 가상 머신 디스크로 사용
- AWS 서비스: **Amazon EBS**

### **5.2.2 파일 스토리지**

- 데이터를 파일과 디렉터리 구조로 저장
- 여러 시스템에서 동시 접근·공유 가능하지만 파일이 늘어나면 정리에 시간이 소요됨
- NAS(Network Attached Storage)에 주로 사용
- AWS 서비스: **Amazon EFS**

### **5.2.3 객체 스토리지**

- 데이터를 객체 단위로, 계층 구조 없이 단일 평면 주소 공간에 저장
- 객체는 데이터 + 메타데이터 + 고유 식별자(키)로 구성
- HTTP 기반 REST API로 접근
- 대용량 비정형 데이터(이미지, 영상)에 적합
- AWS 서비스: **Amazon S3**

**스토리지 선택 기준**: 내구성, 가용성, 보안, 비용, 확장성, 성능, 통합성을 고려해 목적에 맞게 선택해야 합니다.

## 5.3 Amazon EBS

- EC2 인스턴스에 연결하는 **블록 스토리지 볼륨** 서비스
- EC2와 독립적인 수명 주기를 가져, 인스턴스를 종료해도 볼륨과 데이터는 유지되고 다른 인스턴스에 재연결 가능
- 하나의 인스턴스에 여러 EBS 볼륨을 연결해 용량 확장 가능
- **주요 특징**: 데이터 가용성(동일 AZ 내 자동 복제), 데이터 지속성, AES-256 암호화, 스냅샷을 통한 백업, Elastic Volumes로 무중단 크기/유형/성능 변경
- **볼륨 유형**: SSD 계열(범용 SSD, 프로비저닝 IOPS SSD) / HDD 계열(처리량 최적화 HDD, 콜드 HDD) → 지연 시간 민감도, 처리량, 비용에 따라 선택
- **스냅샷**: S3에 저장되는 증분 방식 백업.
    - 첫 스냅샷은 전체 데이터, 이후는 변경분만 저장. 스냅샷 간 데이터 블록을 공유하는 구조로, 특정 스냅샷을 삭제해도 다른 스냅샷이 참조 중인 블록은 유지됨.
    - 계정 간 공유, 리전 간 복사(재해 복구)도 가능

### Amazon EFS

- AWS의 **완전 관리형 네트워크 파일 시스템** 서비스, NFS v4 프로토콜 기반
- 여러 EC2 인스턴스가 **동시에** 같은 파일 시스템을 공유·접근 가능 (EBS는 특정 AZ 종속적이지만 EFS는 멀티 AZ 지원)
- 저장 데이터양에 따라 자동 확장(페타바이트급), 사용한 만큼만 과금
- 인프라 프로비저닝·패치·모니터링을 AWS가 자동 수행 → 사용자는 개발/운영에 집중 가능
- 웹 콘텐츠 저장, 사용자 홈 디렉터리 공유, 분석 데이터 저장 등에 활용

## 5.4 Amazon S3

- 대표적인 **객체 스토리지** 서비스, 데이터는 버킷(bucket)이라는 컨테이너 안에 객체 단위로 저장
- **99.999999999%(11 9's)** 내구성, 사실상 무제한 확장성
- 정적 웹 사이트 호스팅 기능 제공 (웹 서버 없이 운영 가능)
- **구성 요소**
    - 버킷: 리전 단위로 생성, 이름/리전은 생성 후 변경 불가
    - 객체: 데이터 + 메타데이터 + 키로 구성
    - 키: 버킷 내 객체를 고유 식별하는 이름
    - 버전 관리: 동일 키의 객체 여러 버전을 저장, Version ID로 복원 가능
- 하나의 리전 내 최소 3개 이상 AZ에 데이터 자동 복제 → 높은 내구성·가용성
- **스토리지 클래스**: S3 Standard(자주 접근) → Standard-IA/One Zone-IA(낮은 빈도) → Glacier 계열(장기 보관)
    - Lifecycle 정책으로 자동 전환 가능, Intelligent-Tiering은 접근 패턴 자동 분석 후 최적 계층 이동
- **보안**: IAM 정책, 버킷 정책(JSON 기반), ACL로 접근 제어. Block Public Access로 실수로 인한 공개 노출 방지. Pre-signed URL로 특정 객체에 임시 접근 권한 부여 가능. 기본적으로 객체는 비공개이며 명시적 권한 부여가 필요

## 5.5 실습 - 다양한 AWS 스토리지 서비스 구성하기 정리

### 실습 개요

CloudFormation으로 기본 인프라(VPC, 서브넷, EC2 2대 등)를 자동 배포한 뒤, EBS·EFS·S3를 직접 구성하고 삭제까지 진행하는 종합 실습입니다.

### 실습 단계별 정리

#### 1) 기본 인프라 배포

- CloudFormation 스택(storagelab)을 생성해 VPC, 서브넷 2개(AZ1/AZ3), EC2 인스턴스 2대(STG1, STG2), 보안 그룹, IAM Role(S3 Full 정책 연동) 등을 한 번에 배포
- `lsblk`, `df -hT`, `blkid`로 루트 볼륨의 디바이스 정보 확인

#### 2) EBS 스토리지 추가 생성 및 사용

- 새 EBS 볼륨(gp3, 20GiB)을 STG1과 **같은 AZ**에 생성 후 연결
- 핵심 포인트: **EBS 볼륨은 단일 가용 영역에 종속** → 다른 AZ의 인스턴스(STG2)에는 연결 불가
- `mkfs`로 포맷 → `mkdir`/`mount`로 마운트 → 파일 생성/확인
- `/etc/fstab`에 UUID 등록해 재부팅 후에도 자동 마운트되도록 설정 (nofail 옵션 포함)

#### 3) 볼륨 크기 변경 및 스냅샷

- 루트 볼륨을 20GiB로 확장 → `growpart`(파티션 조정) → `xfs_growfs`(파일시스템 조정) 순으로 반영
- 스냅샷 생성(FirstSnapshot) → 데이터 변경 후 두 번째 스냅샷(SecondSnapshot) → **증분 백업**이라 두 번째부터는 빠르게 완료됨을 확인

#### 4) EFS 생성 및 공유 스토리지 구성

- EFS(리전 유형, 자동 백업 해제, 암호화 해제)를 생성해 CH5-VPC와 연결, NFS(2049) 포트 보안 그룹 적용
- STG1, STG2 양쪽에서 동일한 EFS를 `/var/www/html/efs`에 마운트
- 한쪽에서 파일을 생성/삭제하면 다른 쪽에서도 즉시 반영됨을 확인 → **여러 AZ의 서버가 파일을 실시간 공유**하는 구조 검증

#### 5) Public S3로 외부 접근 확인

- 버킷 생성 시 ACL 활성화, 퍼블릭 액세스 차단 해제
- 업로드 직후에는 기본적으로 **비공개**라 외부 접근 시 AccessDenied 발생
- 객체별 ACL을 퍼블릭으로 설정하거나, **버킷 정책(JSON)**으로 `s3:GetObject`를 전체 허용해 버킷 전체를 공개 → 이후 업로드하는 모든 객체가 별도 설정 없이 공개됨
- EC2 웹 서버의 index.html에서 S3 객체 URL을 참조해 정적 콘텐츠를 서빙하는 것까지 확인

#### 6) Private S3로 제한된 접근 및 백업

- AWS CLI(`aws s3 mb`, `aws s3 cp`, `aws s3 sync`)로 프라이빗 버킷 생성 및 데이터 백업
- `crontab`에 `aws s3 sync --delete` 명령을 등록해 **1분마다 자동 동기화(백업)** 구성
- 평소엔 외부 접근이 완전히 차단되지만, **Pre-signed URL**(`aws s3 presign`, 유효시간 120초)로 특정 사용자에게 임시로만 접근을 허용하는 방법 확인

## 실무 적용 포인트

#### **EBS (블록 스토리지)**

- 이 서버만의 전용 디스크가 필요할 때
    - 데이터베이스 서버
    - 온라인 쇼핑몰의 주문/결제 처리 서버
    - 게임 서버
    - 회사 사내 그룹웨어 ERP tjqj
- AZ 종속성 때문에 "EC2가 어느 AZ에 있는지"를 항상 염두에 두고 볼륨을 생성해야 함
    - 흔한 실수가 다른 AZ 인스턴스에 연결 시도해서 막히는 경우
- 볼륨 크기 확장은 무중단으로 가능하지만, **파티션+파일시스템 확장을 직접 해줘야** 실제로 용량이 늘어남
    - 운영 중 디스크 풀 경고가 뜰 때 표준 대응 절차로 활용 가능
- 스냅샷은 증분 방식이라 정기 스냅샷 정책(Data Lifecycle Manager)을 걸어두면 저비용으로 시점 백업 체계를 구축할 수 있음
- fstab에 `nofail` 옵션을 꼭 넣어야, 재부팅 시 볼륨이 분리되어 있어도 부팅 실패하지 않음 (실무에서 자주 놓치는 부분)

#### **EFS (파일 스토리지)**

- 오토스케일링 그룹처럼 **여러 인스턴스가 동일한 콘텐츠를 서빙해야 하는 웹 서비스**(워드프레스 업로드 폴더, 공유 로그/설정 파일 등)에 적합
- EBS와 달리 AZ 종속이 없어 멀티 AZ 아키텍처에서 세션 스토리지나 공유 자산 저장소로 사용
- 사용량 기반 과금이라 초기 용량 설계 부담이 없다는 점을 어필해 스토리지 관리 리소스를 줄이는 데 활용 가능

#### **S3 (객체 스토리지)**

- Public 버킷은 정적 웹 호스팅, CDN 오리진(CloudFront 연계), 이미지/동영상 서빙 등에 사용
    - 다만 **버킷 정책으로 열 때 Resource 범위를 명확히 제한**(`bucket/*`처럼 객체 단위로)해서 의도치 않은 노출을 막아야 함
- Private 버킷 + `aws s3 sync --delete` cron 조합은 실무에서 흔한 **저비용 자동 백업 파이프라인** 패턴
    - 로그 서버나 애플리케이션 서버에 바로 적용 가능
- Pre-signed URL은 고객에게 파일 다운로드 링크를 임시로 발급하거나, 프론트엔드에서 직접 S3로 업로드시키는(서버 부하 절감) 용도로 실무에서 매우 자주 사용됨
- 실습에서 IAM Role을 EC2에 연동해뒀듯, 실무에서도 **액세스 키를 코드에 박아넣지 않고 IAM Role로 권한을 부여**하는 것이 표준 보안 관행

#### **공통 운영 팁**

- CloudFormation으로 인프라를 코드화해두면 실습처럼 반복 배포·삭제가 쉬워짐 → 실무에서도 테스트 환경 구성/파기에 그대로 응용 가능
- 자원 삭제 순서(스냅샷 → 볼륨 → EFS → S3 → 스택)처럼, 의존성이 있는 리소스는 역순으로 정리해야 삭제 오류를 피할 수 있음
