## 1-1 AWS 서버리스

AWS 서버리스는 서버를 신경 쓰지 않고 애플리케이션을 구축하고 실행할 수 있게 해주는 AWS 서비스입니다. 물리 또는 가상 서버를 빌려주는 플랫폼과 달리, 인프라 관리와 운영 요소까지 서비스에 포함해 제공하기 때문에 사용자가 도메인 로직에 집중할 수 있습니다.

웹 서비스를 배포하려면 서버 고민이 반드시 따라옵니다. 프론트엔드 빌드 결과물을 브라우저에 제공하는 웹 서버, 도메인 로직을 가진 백엔드 서버가 그 예입니다. 따라서 서비스 개발은 코드 작성으로 끝나지 않고 서버 구축, 배포, 운영까지 포함합니다.

### 1-1-1 기존의 서버 개발

두 수를 입력받아 합을 반환하는 웹 서비스를 예로 들어, 기존 방식의 전 과정을 살펴봅니다.

- **개발**: Node.js Express로 HTTP API 백엔드를 만들고, React 등으로 프론트엔드를 만든 뒤, 백엔드에서 프론트엔드 페이지를 제공하는 코드를 작성합니다.
- **배포**: 클라우드 업체에서 가상 서버를 할당받고, 코드를 복제해 기동합니다. 이제 IP로 접근할 수 있습니다.
- **도메인 연결**: 도메인을 구입하고, 네임 서버를 구축하거나 업체의 DNS 서비스로 IP를 연결합니다.
- **HTTPS 적용**: LetsEncrypt 등에서 SSL 인증서를 발급받고, 백엔드 코드를 수정해 다시 배포합니다. 인증서는 만료 기간이 있어 주기적으로 재발급하고 서버를 갱신해야 합니다.
- **로그 관리**: 오류 발생 시 서버에 접속해 로그 파일을 확인해야 합니다. 디스크 용량에 한계가 있으므로 오래된 로그를 압축하거나 삭제하는 로직도 필요합니다.
- **모니터링**: 정상/비정상 응답 수를 지표 서버에 보고하고, 이를 시각화하는 대시보드와 비정상 응답이 일정 수준 이상일 때 알리는 경보를 구축해야 합니다.
- **증설**: 요청이 급증하면 가상 서버를 추가 할당하고, 모든 서버에 코드를 배포한 뒤, 로드밸런서를 설정하고 도메인을 연결해야 합니다.
- **비용**: 가상 서버 단위로 비용을 내므로 요청량과 무관합니다. 고객이 1명이어도 서버 10대를 켜두면 10대 요금을 매시간 냅니다. 확장성을 생각하면 여유 있게 확보하는 게 좋지만, 비용을 생각하면 요청량에 맞추는 게 좋아서 사용량 예측 기반의 자동 규모 조절 장치까지 필요합니다.

정리하면 처음 세 단계(개발)를 빼면 전부 서버 운영 작업입니다. 데브옵스 도구로 자동화할 수는 있지만, 사이트 신뢰성이 워낙 중요해서 운영은 피할 수 없습니다. 동시에 더 나은 서비스를 위해서는 도메인 쪽(예: 아주 큰 수를 빠르게 더하기, 여러 수를 한 번에 더하기)에도 집중해야 합니다.

### 1-1-2 서버리스 기반의 서비스 개발

같은 서비스를 AWS 서버리스로 구성하면 다음과 같습니다.

- **AWS Lambda**: 백엔드 코드를 실행하는 컴퓨팅 자원입니다. 업로드한 코드를 제한된 자원 안에서 HTTP 등의 이벤트에 의해 실행하고 결과를 반환합니다.
- **Amazon API Gateway**: HTTP 이벤트를 생성합니다. HTTP 요청을 받으면 Lambda를 실행해 도메인 로직을 처리하고, 그 결과를 HTTP 응답으로 돌려줍니다.
- **Amazon S3**: 프론트엔드 페이지를 제공하는 클라우드 저장소로, 업로드한 파일을 HTTP로 제공하는 정적 웹사이트 호스팅 기능이 있습니다. 로직 실행은 못 하지만 정적 파일 서버로 쓰기 편합니다.
- **Amazon CloudFront**: S3의 정적 파일을 CDN으로 더 빠르게 제공합니다. S3 데이터센터보다 Edge가 훨씬 많아 네트워크 접근성이 좋고, HTTPS 제공과 Route 53 연계를 통한 사용자 도메인 사용이 가능합니다.
- **Amazon Route 53**: API Gateway와 CloudFront에 사용자 도메인을 붙이기 위한 DNS 서비스입니다. AWS 내부 서비스 간 DNS는 별칭으로 연결되므로 IP가 바뀌어도 네임 서버를 갱신할 필요가 없습니다.
- **HTTPS**: API Gateway와 CloudFront는 기본으로 HTTPS를 지원하고 AWS 인증서를 쓰므로 갱신 작업이 필요 없습니다. 사용자 도메인은 AWS Certificate Manager로 관리하며 이것도 자동 갱신됩니다.
- **로그**: Lambda, API Gateway, CloudFront의 로그는 모두 Amazon CloudWatch에 모입니다. 별도 저장소이므로 압축과 삭제를 고민할 필요가 없고, 필요하면 로그 스트림별 만료 정책을 정할 수 있습니다.
- **모니터링**: CloudWatch로 AWS 지표를 대시보드로 구성할 수 있습니다. API Gateway의 2XX/4XX/5XX 응답 수, Lambda의 실행 시간과 호출 빈도 등을 쉽게 확인할 수 있습니다.
- **비용**: API Gateway와 Lambda는 요청 횟수 기반 종량제라서 요청이 없으면 요금이 없습니다.
- **확장성**: 요청이 급증해도 Lambda가 여러 개 동시에 실행됩니다. 별도 설정 없이 1천 개까지 동시 실행되므로, 요청 하나에 1초가 걸린다면 초당 1천 건을 처리할 수 있습니다. API Gateway와 CloudFront의 HTTPS 요청 한도도 각각 초당 1만 건, 25만 건으로 높고 상향도 가능합니다. 대규모 트래픽이 아니라면 서버 확장을 고민할 필요가 없습니다.

**CloudFormation 등장 배경**: 서비스별 기능을 잘 쓰면 가상 서버보다 관리가 쉽지만, 수많은 서비스를 관리 도구로 각각 제어하는 건 복잡합니다. 그래서 인프라와 서비스 요소를 코드로 관리하는 AWS CloudFormation이 나왔습니다. YAML 파일에 필요한 서비스를 선언해 제출하면 자원을 할당하고 연결해주며, 여러 서비스를 하나의 스택으로 묶어 관리할 수 있습니다.

이제 시스템은 크게 3요소로 정리됩니다.

- CloudFormation으로 관리하는 인프라 및 서비스 요소(API Gateway, Lambda, S3, CloudFront, CloudWatch, Route 53)
- Lambda에 올릴 백엔드 코드
- S3에 올릴 프론트엔드 코드

프론트엔드 코드는 달라지는 게 없지만 백엔드 코드는 다시 개발해야 할 수 있습니다. Lambda 인스턴스는 요청이 처리되는 동안에만 실행되기 때문입니다. 한 번 켜지면 운영 작업 외에는 꺼지지 않던 기존 서버와 가장 큰 차이점입니다.

**서버리스의 진입 장벽**

- CloudFormation 선언은 모든 AWS 서비스와 옵션을 지정해야 하므로 제대로 알지 못하면 쓰기 어렵고, 매번 문서를 찾아가며 작성해야 합니다.
- 서비스 간 할당과 연동을 위해 AWS IAM 규칙도 정의해야 하는데, 서비스와 행위마다 필요한 권한 체계를 알아야 합니다.
- 시스템을 CLI로 제어하고 자동화하려면 AWS CLI도 익혀야 합니다.

다만 문서의 위치만 기억해도 금방 익숙해지고, 웹 서비스용 서버리스 모델은 상당히 정형화되어 있어 쉽게 쓸 수 있는 도구와 템플릿이 많습니다. 책은 그중 가장 오래되고 인기 있는 **Serverless Framework**를 사용합니다.

## 1-2 개발 환경 구축

전체 준비 항목은 다음과 같습니다.

- AWS 계정 생성, 액세스 키 발급, 로컬에 AWS CLI를 설치해 액세스 키 설정
- Node.js 개발 환경 구축과 Serverless Framework 설치
- 코드 편집을 위한 VSCode 설치
- 대부분의 도구가 POSIX 기준이므로, 윈도우에서는 Git Bash나 WSL로 환경을 통일

### 1-2-1 AWS 계정 설정

**계정 생성**

- 관리 콘솔 우측 상단의 가입 메뉴에서 **AWS 계정 새로 만들기**를 누르고, 이메일 입력, 휴대폰 인증, 결제 카드 등록을 마치면 가입이 완료됩니다.
- 결제 수단은 필수지만, 서버리스 서비스 대부분이 프리 티어를 지원해 개인 연습 수준의 비용은 거의 없습니다.
- 처음 로그인하면 지역이 버지니아 북부(us-east-1)나 오하이오(us-east-2)로 되어 있을 수 있습니다. 그대로 자원을 만들면 의도치 않은 데이터센터를 쓰게 되므로 우측 상단 지역 메뉴에서 **아시아 태평양 (서울) ap-northeast-2**로 변경합니다.

**프로그램 액세스 키**

- 매번 웹 콘솔로 자원을 제어하는 건 자동화가 어렵고 번거롭기 때문에 AWS는 프로그램 액세스 키를 제공합니다. 이 키를 AWS API 요청에 함께 보내 자원을 제어합니다.
- 키로 할 수 있는 작업 범위는 키가 소속된 계정의 권한 범위입니다.
- 가입 이메일 기반 계정은 **루트 계정**이며 모든 권한을 가집니다. 그래서 루트 계정의 키로는 모든 자원을 제어할 수 있으므로, 비밀번호는 물론 키도 절대 공유하면 안 됩니다.

**발급 방법**

1. 우측 상단 계정 메뉴에서 **보안 자격 증명**으로 이동합니다.
2. 액세스 키 항목에서 **새 액세스 키 만들기**를 누르면 즉시 발급됩니다.
3. 액세스 키 ID는 목록에 계속 노출되지만, **비밀 키는 생성 시에만** 볼 수 있습니다. 잃어버리면 기존 키를 삭제하고 새로 발급해야 합니다.
4. **액세스 키 표시**로 직접 확인해 보관하거나, **키 파일 다운로드**로 CSV 파일을 받습니다. 키 보관이 익숙하지 않다면 AWS CLI 설정 전까지는 CSV를 받아두는 편이 낫습니다.

**보안 주의사항**

- 루트 계정 키를 실수로 소스 코드에 넣어 GitHub에 올리는 사고가 잦았고, 그로 인해 자원이 남용되어 요금 폭탄을 맞은 사례도 꽤 있습니다.
- 최근 GitHub는 올라간 키를 검색에 노출하지 않지만 여전히 위험합니다.
- 소스 코드뿐 아니라 CI 시스템이나 서비스에서 디버깅 목적으로 키를 로그에 출력하는 것도 조심해야 합니다.
- 근본 원인은 루트 키의 권한이 너무 강하다는 점입니다. 개인 학습이 아닌 상용 서비스라면 AWS IAM에서 필요한 자원에 대한 접근 권한만 가진 사용자를 따로 만들고, 그 사용자의 키를 발급해 사용해야 합니다.

### 1-2-2 AWS CLI 설치

AWS는 REST API를 제공하므로 curl로도 요청할 수 있지만, 모든 URL과 파라미터 규격을 알기 어려워서 AWS CLI를 사용합니다. AWS API를 이해하기 쉬운 명령으로 실행해주는 도구입니다.

**OS별 설치**

- **리눅스**: zip 파일을 curl로 받아 압축을 풀고 `sudo ./aws/install`로 설치합니다. `/usr/local/bin`에 `aws` 실행 파일이 생깁니다.
- **맥OS**: `AWSCLIV2.pkg`를 받아 설치 관리자를 실행합니다. 모든 사용자용으로 설치하면 루트 권한으로 `/usr/local/bin/aws`에 설치됩니다. 현재 사용자 전용으로 설치하면 쓰기 권한이 있는 폴더에 설치되는데, 그 경로가 `$PATH`에 없을 수 있으므로 직접 추가하거나 `/usr/local/bin`에 심볼릭 링크를 만들어야 합니다.
- **윈도우**: `AWSCLIV2.msi`를 받아 실행하면 `C:\Program Files\Amazon\AWSCLIV2`에 설치됩니다.

**설치 확인**

- `aws --version`으로 확인합니다.
- 명령 입력 시 프롬프트 기호는 입력하지 않습니다. 리눅스와 맥OS는 유저 권한이면 `$`, 루트 권한이면 `#`, 윈도우는 `C:\>`로 표시됩니다. 책의 예제는 `$`를 기본으로, 필요한 경우만 `#`을 씁니다.
- 2022년 8월 기준 버전은 2.7.22입니다. 자동 업데이트가 없으므로 새 버전이 나오면 패키지를 다시 받아 설치하고, 두 번째부터는 `./aws/install --update`로 업그레이드합니다. 명령이 없거나 알 수 없는 오류가 나면 버전부터 확인합니다.

**`aws configure` 설정**

- 액세스 키와 시크릿 액세스 키 두 값을 모두 설정해야 정상 동작합니다.
- **Default region name**: 지역을 따로 지정하지 않을 때 쓸 기본 지역입니다. 서울은 `ap-northeast-2`이며, 실행 시 `-region`으로 재정의할 수 있습니다.
- **Default output format**: 응답 포맷입니다. `text`, `table`, `yaml`도 가능하지만 보통 `json`을 씁니다. `-output`으로 재정의할 수 있습니다.

**2022년 8월 기준 지역 코드**

- 아시아 태평양: ap-east-1(홍콩), ap-northeast-1(도쿄), ap-northeast-2(서울), ap-northeast-3(오사카), ap-south-1(뭄바이), ap-southeast-1(싱가포르), ap-southeast-2(시드니), ap-southeast-3(자카르타)
- 유럽: eu-central-1(프랑크푸르트), eu-north-1(스톡홀름), eu-south-1(밀라노), eu-west-1(아일랜드), eu-west-2(런던), eu-west-3(파리)
- 미국: us-east-1(버지니아 북부), us-east-2(오하이오), us-west-1(캘리포니아 북부), us-west-2(오레곤)
- 기타: af-south-1(케이프타운), ca-central-1(캐나다 중부), me-south-1(바레인), sa-east-1(상파울루)

**지역 관련 주의점**

- CloudFront, Route 53처럼 위치와 무관하게 전 지역에서 제공되는 서비스도 있지만, S3, API Gateway, Lambda처럼 각 지역 데이터센터 안에서만 제공되는 서비스도 있으므로 잘못된 지역을 쓰지 않도록 주의해야 합니다.
- 한국 대상 서비스라면 도쿄보다 서울 지역을 써야 응답 지연이 줄어듭니다.
- 신규 서비스는 지역마다 출시 시점이 다르므로, 새 기능을 빨리 쓰고 싶다면 AWS 지역 서비스 페이지를 주기적으로 확인합니다.

**설정 확인과 프로파일**

- `aws iam get-user`로 현재 키가 어느 계정 소속인지 조회할 수 있습니다. 정상이면 UserName, UserId, Arn, CreateDate 등이 담긴 JSON이 나옵니다.
- 여러 계정의 키를 다룰 때는 `-profile`을 씁니다. `aws configure --profile 이름`으로 프로파일별 키를 설정하고, `aws --profile 이름 ...`으로 골라 씁니다. 예를 들어 개발 환경(lacti-dev)과 상용 환경(lacti-prod)을 분리해 관리할 수 있습니다.

### 1-2-3 Node.js

**특징**

- 크롬 V8 엔진 기반의 자바스크립트 런타임입니다.
- 자바스크립트는 문법이 비교적 간단하고, `async/await`로 비동기 작업을 쉽게 처리할 수 있습니다.
- 단일 스레드지만 이벤트 루프 기반으로 비동기 IO를 잘 처리해 전반적인 성능이 괜찮습니다.
- 라이브러리와 생태계가 크고, 패키지 매니저 `npm`이 있으며, 타입스크립트로 타입 정보를 추가할 수 있습니다.

**버전 선택**

- LTS 버전은 장기간 지원하도록 운영되는 버전이고, 현재 버전은 최신 기능이 있지만 지원 기간이 짧습니다. 최신 기능이 필요 없다면 LTS를 권장합니다.

**책에서 Node.js를 쓰는 이유**

- Serverless Framework도 Node.js 기반이므로 코드와 설정을 같은 언어로 작성할 수 있습니다.
- Lambda에서 첫 기동 지연 시간이 빠른 편입니다.
- 리눅스, 맥OS, 윈도우에서 모두 잘 돌아가고 프론트엔드에서도 쓸 수 있습니다.
- Lambda가 런타임을 자체 제공하므로 버전만 맞추면 별도 환경 구성이 필요 없습니다.

**Lambda 지원 현황(2022년 8월 기준)**

- Node.js 16, 14, 12를 지원합니다. 16은 2022년 5월부터 지원했고, 12는 2022년 11월 지원 종료 예정이므로 가능하면 16을 권장합니다.
- 다만 집필 시점(2022년 4월)에는 LTS가 14였고 Lambda도 14까지만 지원했기 때문에 모든 예제는 14로 작성되었습니다.
- 설치 후 `node --version`(예: v14.20.0), `npm --version`(예: 8.17.0)으로 확인합니다.

**package.json**

- 프로젝트 설명, 의존 패키지 목록, 추가 명령을 관리하는 선언 파일입니다.
- `npm init`은 대화식으로, `npm init -y`는 기본값으로 생성합니다.
- `npm install --save`로 추가한 패키지는 `dependencies`에 이름과 버전이 기록됩니다. 이 파일을 공유하면 다른 사람도 같은 버전을 설치할 수 있습니다.
- 의존 패키지가 의존하는 패키지의 버전은 `package-lock.json`에 정리되므로 함께 공유하는 것이 좋습니다.
- 개발 시에만 필요한 패키지는 `devDependencies`(`-save-dev`), 없어도 되는 패키지는 `optionalDependencies`(`-save-optional`)로 관리합니다.
- 의존성이 기록된 프로젝트를 받았다면 `npm install` 한 번으로 `node_modules`에 모두 설치됩니다.
- `scripts`에는 `npm run`으로 실행할 명령을 정의합니다. 보통 `start`(로컬 실행), `build`(빌드), `deploy`(배포)를 둡니다. 예를 들어 `"start": "node main.js"`라면 `npm run start`가 `node main.js`를 실행합니다.

### 1-2-4 nvm

**필요성**

- Node.js는 업데이트가 잦고, Lambda도 LTS 상황에 따라 런타임 버전을 추가합니다.
- 어떤 Lambda는 16, 다른 Lambda는 14를 써야 할 수도 있습니다. 로컬에 최신 버전 하나만 두고 개발할 수도 있지만, 버전이 다르면 로컬에서 되던 코드가 Lambda에서 오류를 낼 수 있으므로 Lambda 환경과 버전을 맞추는 것이 좋습니다.
- 버전 관리 도구 nvm을 쓰면 여러 버전을 쉽게 설치하고 전환할 수 있습니다.

**설치**

- bash 환경에서 curl로 install.sh를 받아 실행합니다. URL 중간의 `v0.39.1`은 버전이며, 항상 최신을 쓰려면 `master`를 사용합니다.
- 맥OS는 Homebrew로도 설치 가능합니다.
- `.bashrc`에 `NVM_DIR` 환경 변수와 nvm 로딩 스크립트를 추가하고 `source ~/.bashrc`로 다시 읽으면 사용할 수 있습니다.

**사용법**

- 여러 버전을 `~/.nvm`에 저장하고 선택한 버전으로 alias를 만듭니다.
- `nvm install 12`, `nvm install 14`처럼 설치합니다. 메이저 버전만 지정하면 해당 메이저의 최신(2022년 8월 기준 14는 v14.20.0)이 설치됩니다.
- `nvm use 12`, `nvm use 14`로 버전을 전환합니다.
- `nvm alias default 14`로 기본 버전을 지정하고, `nvm use default`로 기본 버전을 씁니다.

**마이너 버전 업데이트**

- 해당 메이저 버전을 다시 `nvm install`하면 됩니다.
- `nvm reinstall-packages 과거버전`으로 과거 버전에서 전역 설치했던 패키지를 새 버전에 다시 설치하고, `nvm uninstall 과거버전`으로 과거 버전을 지웁니다. (예: 14.17.0 에서 14.20.0 으로)
- 메이저 버전을 올릴 때는 프로젝트의 `node_modules`를 삭제 후 재설치해야 버전 불일치 문제가 생기지 않습니다.

### 1-2-5 타입스크립트

**개요**

- 마이크로소프트가 만든 오픈소스 언어로, 자바스크립트에 타입을 부여한 슈퍼셋입니다.
- 자바스크립트는 타입이 없어 유연하지만, 추론 엔진의 한계를 넘는 복잡한 프로그램에서는 개발자가 직접 타입을 고려해야 하는 문제가 생깁니다.
- 여러 타입 검사 도구 중 Serverless Framework가 가장 적극적으로 지원하는 타입스크립트를 사용합니다.

**설치와 실행**

- `npm install -g typescript`로 전역 설치할 수 있습니다.
- 자바스크립트는 `.js`, 타입스크립트는 `.ts`입니다. `.ts` 파일을 작성하고 `tsc`나 babel로 `.js`를 생성합니다.
- 예: `hello.ts` 작성 후 `tsc hello.ts`로 `hello.js`를 만들고 `node hello.js`로 실행합니다.

**프로젝트별 버전 관리**

- 프로젝트마다 다른 버전을 써야 할 수 있으므로 `package.json`에 등록하는 것이 좋습니다. 개발 단계에서만 쓰므로 `npm install --save-dev typescript`로 설치합니다.
- 이 경우 `node_modules` 안에 설치되어 `tsc`를 바로 실행할 수 없고, `./node_modules/.bin/tsc`처럼 전체 경로를 써야 합니다. 대신 `npx tsc`를 쓰면 간편합니다.

**ts-node**

- 매번 컴파일 후 node로 실행하는 건 번거롭습니다. ts-node는 타입스크립트 파일을 바로 실행하도록 node를 감싼 패키지입니다.
- Node.js 타입 정보가 필요하므로 `npm install --save-dev ts-node @types/node@14`로 함께 설치하고 `npx ts-node`로 실행합니다.
- 전역 설치도 가능하지만, 전역 버전과 프로젝트 버전이 다르면 IDE가 잘못된 버전을 선택해 문제가 생길 수 있으니 주의합니다.

### 1-2-6 Visual Studio Code

- 마이크로소프트가 만든 코드 편집기로 리눅스, 맥OS, 윈도우에서 모두 쓸 수 있습니다.
- 확장이 다양하면서도 로컬 자원 소모가 적고, 오픈소스라 무료입니다.
- 다운로드 페이지에서 OS에 맞는 설치 파일을 받아 설치합니다.
- 확장(Extensions)으로 Git 변경점 표시, 괄호 색 구분 등 편의 기능을 추가할 수 있습니다. 책이 추천하는 확장은 다음과 같습니다.
    - **Prettier - Code formatter**: 코드를 Prettier 기준으로 포맷팅합니다. 저장 시 자동 포맷팅을 켜면 코드 스타일을 신경 쓰지 않아도 됩니다.
    - **ESLint**: 자바스크립트/타입스크립트 코드에서 자주 하는 실수를 정적 분석으로 알려줍니다.
    - **AWS Toolkit**: VSCode에서 AWS 서비스에 접근하게 해줍니다. 서버리스 스택 배포 후 로그 확인 등이 쉬워집니다.

### 1-2-7 direnv

**배경**

- 공용 상수나 코드에 넣기 민감한 값은 환경 변수로 관리합니다.
- 모든 환경 변수를 `.bashrc` 같은 셸 최상위 설정에 넣을 수도 있지만, 프로젝트마다 값이 다르면 번거롭습니다.
- 흔한 방법은 프로젝트 디렉터리에 `load_env.sh` 같은 스크립트를 두고(`.gitignore`에 추가해 GitHub 유출 방지) 필요할 때 실행하는 것입니다.
- 하지만 제한된 권한의 키를 쓰거나 시스템 내부에서 다른 키를 관리하는 등 경우가 많아지면 스크립트 파일을 각각 관리하기가 번거롭습니다.

**direnv 동작 방식**

- 셸에 통합되어, 디렉터리에 진입했을 때 `.envrc` 파일이 있으면 그 파일을 실행합니다.
- 의도치 않은 스크립트 실행을 막기 위해 첫 진입 시에는 차단되고, `direnv allow`로 허용해야 합니다. 허용 후에는 진입할 때마다 자동 로딩됩니다.
- `.envrc`가 수정되면 다시 `direnv allow`로 허용해야 합니다.
- 상위 디렉터리의 `.envrc`도 함께 쓰려면 `source_up`을 사용합니다. 명시하지 않으면 상위 `.envrc`는 모두 무시됩니다. (예: `parent/child`에서 `source_up`을 쓰면 parent와 child의 `.envrc`가 모두 로딩됨)

**설치**

- Unix 계열용 도구라 리눅스와 맥OS에서는 바로 쓸 수 있고, 윈도우는 WSL2나 Git Bash 환경이 필요합니다.
- 설치 절차
    1. GitHub releases 페이지에서 환경에 맞는 파일을 받습니다. (64bit 맥OS는 `direnv.darwin-amd64` 또는 `direnv.darwin-arm64`, 64bit 리눅스는 `direnv.linux-amd64`)
    2. 파일 이름을 `direnv`로 바꾸고 `chmod +x`로 실행 권한을 준 뒤 실행 가능한 경로로 옮깁니다.
    3. `eval "$(direnv hook bash)"`를 셸 설정 파일(bash라면 `.bashrc`)에 추가합니다.
- 공식 설치 스크립트(`curl -sfL https://direnv.net/install.sh | bash`)는 1, 2단계를 자동으로 해주지만, `$PATH`의 첫 번째 쓰기 가능 디렉터리에 파일을 넣어 의도치 않은 위치에 설치될 수 있으므로 가급적 직접 설치하는 것이 낫습니다.
- 우분투는 `apt install direnv`, 맥OS는 `homebrew install direnv`로도 설치 가능합니다.

### 1-2-8 Docker

**개요와 필요성**

- 리눅스의 프로세스 격리 기술로 애플리케이션을 컨테이너로 실행하고 관리하는 오픈소스 프로젝트입니다. 컨테이너는 실행에 필요한 모든 의존성을 완전한 파일 시스템 안에 감쌉니다.
- AWS는 Lambda 환경을 로컬에서 흉내 낼 수 있는 Docker 이미지를 제공하므로, Lambda에 올릴 코드를 로컬에서 쉽게 테스트할 수 있습니다.
- Lambda 실행 환경이 복잡할 경우 코드 압축 파일 대신 Docker 이미지로 컨테이너를 구성해 배포할 수도 있습니다.

**설치**

- 공식 문서(docs.docker.com/get-docker)를 따르면 됩니다.
- 리눅스는 시스템 패키지로 설치합니다. 맥OS와 윈도우는 별도 VM이나 WSL2로 Docker 환경을 만드는 Docker 데스크톱을 설치 마법사로 설치합니다.
- 리눅스에서 `get-docker.sh` 설치 스크립트를 받아 `sudo`로 바로 실행할 수도 있지만, 잘못되었거나 악의적인 스크립트라면 시스템에 큰 문제를 일으킬 수 있으므로 번거롭더라도 배포판별 패키지를 직접 설치하는 것이 안전합니다.
- 우분투 직접 설치 절차: apt 업데이트, 필수 패키지(apt-transport-https, ca-certificates, curl, gnupg, lsb-release) 설치, Docker GPG 키 등록, Docker 저장소를 sources.list에 추가, 다시 업데이트 후 `docker-ce`, `docker-ce-cli`, `containerd.io` 설치.

**설치 후 설정**

- 루트 권한으로 설치한 Docker는 유저 계정에서 바로 실행할 수 없습니다. `sudo usermod -aG docker $USER`로 현재 사용자를 docker 그룹에 추가하고 셸에 다시 로그인해야 합니다.
- 리눅스 GUI 터미널을 쓰는 경우 X-Window 세션을 다시 시작해야 할 수도 있습니다.
- `docker run hello-world`로 정상 동작을 확인합니다.

### 1-2-9 리눅스용 윈도우 하위 시스템(WSL)

**필요성**

- 책의 모든 예제는 Bash 셸 기준입니다. 윈도우 cmd는 Bash와 호환되지 않아 일부 예제가 실행되지 않을 수 있습니다.
- 추천 서비스 설명의 파이썬 런타임 부분, 의존 시스템 실행을 위한 Docker 부분도 윈도우에 맞게 고쳐야 하는 번거로움이 있습니다.
- Git Bash, Docker 데스크톱, Anaconda를 각각 설치해 맞출 수도 있지만 버전 호환 문제로 일부 예제가 동작하지 않을 수 있습니다.

**VM 대비 WSL의 장점**

- VMWare나 VirtualBox로 리눅스를 쓸 수도 있지만 자원을 많이 쓰고, 호스트(윈도우)와 게스트(리눅스) 사이 파일 교환과 네트워크 설정이 번거롭습니다.
- WSL은 가상 머신보다 부족한 부분은 있지만 예제 개발과 실행에는 충분합니다. 윈도우에 통합된 시스템이라 메모리, 네트워크, 파일 시스템을 공유할 수 있어 편리하므로 WSL 사용을 권장합니다.

**설치(윈도우 10 기준)**

- **간단 설치**: 윈도우 참가자 프로그램에 가입하고 빌드 20262 이상이라면, 관리자 권한 명령줄에서 `wsl --install`을 실행합니다. 재시작하면 우분투가 설치되어 있고, 처음 실행 시 계정과 암호를 설정합니다.
- **수동 설치**: 참가자 프로그램을 쓰지 않는 경우입니다. 윈도우 10 버전 1903 이상, 빌드 18362 이상이어야 WSL2를 설치할 수 있고(WSL 안에서 Docker를 제대로 쓰려면 WSL2 필요), 더 낮다면 윈도우 업데이트부터 합니다.
    1. 관리자 권한 파워셸에서 `dism.exe`로 Microsoft-Windows-Subsystem-Linux 기능을 활성화합니다.
    2. 같은 방식으로 VirtualMachinePlatform 기능을 활성화합니다.
    3. x64용 최신 WSL2 Linux 커널 업데이트 패키지를 받아 실행합니다.
    4. `wsl --set-default-version 2`로 WSL2를 기본 버전으로 설정합니다.
    5. Microsoft Store에서 리눅스 배포판을 설치합니다. 책은 우분투 기준으로 설명하므로 우분투 20.04를 권장합니다. 설치 후 계정과 암호를 설정합니다.
- 각 단계에서 필요에 따라 재시작이 필요할 수 있습니다.

## 1-3 Serverless Framework 소개

**개요**

- zero-friction serverless development(마찰 없는 서버리스 개발)를 가치로 삼는 오픈소스 프로젝트입니다.
- JavaScript AWS(JAWS)라는 이름으로 시작해 지금은 AWS뿐 아니라 GCP, Azure 등도 지원하는 서버리스 프레임워크가 되었습니다.
- 최대한 관례적인 방법으로 서버리스 웹 서비스를 쉽게 정의하고 관리할 수 있고, 플러그인 생태계로 기능을 확장할 수 있습니다.

**동작 원리**

- `serverless.yml` 파일로부터 각 클라우드의 IaC 서비스용 선언을 생성합니다. AWS라면 CloudFormation 선언을 만들어 제출하고 서버리스 스택을 생성하거나 갱신합니다.
- 함수 코드 용량이 작으면 Lambda에 인라인으로 업로드하고, 그렇지 않으면 S3에 zip으로 올린 뒤 Lambda와 연결합니다.
- 결국 인프라와 코드를 통합한 서버리스 스택을 `serverless.yml` 하나로 관리할 수 있습니다.

### 1-3-1 간단한 선언 예시

Lambda 함수의 인자를 그대로 반환하는 HTTP API 예시입니다.

```yaml
service: first-serverless
provider:
  name: aws
  runtime: nodejs14.x
  region: ap-northeast-2
functions:
  echo:
    handler: handler.echo
    events:
      - httpApi: GET /echo
```

- `service`: 서버리스 스택 이름으로, CloudFormation에서 이 이름으로 스택을 찾을 수 있습니다.
- `provider.name`: 배포할 클라우드 업체로, `aws`면 AWS에 배포합니다.
- `provider.runtime`: `nodejs14.x`로 Node.js 14를 사용합니다.
- `provider.region`: `ap-northeast-2`로 서울 지역에 배포합니다.
- `functions`: 스택에 포함할 함수와 실행 트리거를 정의합니다.
    - `echo`라는 함수를 정의합니다.
    - `echo.handler`: 진입점을 `handler.js` 파일에서 export된 `echo` 함수로 지정합니다.
    - `echo.events.httpApi`: httpApi로 실행하며, `/echo`에 GET 요청을 보내면 `echo` 함수가 실행됩니다.

Serverless Framework는 이 파일을 해석해 `GET /echo`를 처리하는 API Gateway 자원과 `handler.echo`를 실행하는 Lambda 자원을 할당하고, 둘을 연결하며, Lambda 로그가 CloudWatch Logs에 남도록 연결합니다.

### 1-3-2 도구 익히기

**설치**

- Node.js 기반 도구라 `npm install -g serverless`로 설치합니다.
- 2022년 8월 기준 3.21.0까지 나왔고 업데이트가 빠르며, 버전에 따라 템플릿이 바뀔 수 있어 책의 출력 예제가 실제와 다를 수 있습니다.

**프로젝트 생성(대화식)**

- `serverless` 또는 축약 별칭 `sls`를 인자 없이 실행하면 대화식으로 프로젝트를 만듭니다.
- 템플릿 목록: AWS Node.js와 Python 각각에 대해 Starter, HTTP API, Scheduled Task, SQS Worker, Express API(Python은 Flask API), Express API with DynamoDB(Python은 Flask API with DynamoDB), 그리고 Other가 있습니다. 가장 기본은 `AWS - Node.js - Starter`입니다.
- 이후 프로젝트 이름을 입력합니다. 예제에서는 `hello-world`를 쓰며, 현재 디렉터리 아래 같은 이름의 디렉터리가 생깁니다.
- 이어서 Serverless Framework 관리 서비스(org)에 등록할지 묻습니다. 이 서비스에 연동하면 app.serverless.com에서 배포 이력과 API 호출 현황을 볼 수 있지만, 기능이 제한적이고 느려서 책에서는 다루지 않습니다(Skip).
- 바로 배포할지도 묻는데, 여기서는 구조만 볼 것이므로 No를 선택합니다.
- 생성 후 안내되는 명령: `serverless deploy`(배포), `serverless info`(엔드포인트와 자원 조회), `serverless invoke`(함수 호출), `serverless --help`(명령 탐색)
- 생성 파일: `handler.js`, `README.md`, `serverless.yml` (`tree` 명령이 없다면 apt나 brew로 설치)
    - `serverless.yml`은 앞의 예시와 크게 다르지 않습니다.
    - `README.md`는 배포 및 로컬 테스트 방법과, `serverless.yml`에서 쓸 수 있는 AWS Events 온라인 문서를 소개합니다.
    - `handler.js`에는 `hello` 함수가 정의되어 있습니다.

**프로젝트 생성(명령식)**

- `sls create`로 대화식 없이 생성할 수 있습니다. `sls create --help`로 전체 템플릿 목록(aws-nodejs, aws-nodejs-typescript, aws-nodejs-docker, aws-python 등)을 볼 수 있습니다.
- 예: `sls create --template aws-nodejs --name hello-world --path hello-world`
    - `-name`: 스택 이름
    - `-path`: 프로젝트를 만들 디렉터리

**`sls package`: 빌드**

- `serverless.yml`을 CloudFormation용 선언으로 변환하고 Lambda에 올릴 코드를 빌드합니다. 결과물은 `.serverless` 디렉터리에 저장됩니다.
- `cloudformation-template-create-stack.json`: 스택 생성을 요청하는 선언 파일입니다.
- `cloudformation-template-update-stack.json`: 이미 스택이 있을 때 갱신을 요청하는 선언 파일입니다. 배포 시 스택 존재 여부를 확인해 적절한 파일을 제출합니다.
- `hello-world.zip`: Lambda에서 실행할 함수를 압축한 파일입니다. 지금은 `handler.js`만 있지만, 의존 패키지를 쓰면 `node_modules`도 포함됩니다.
- `serverless-state.json`: `serverless.yml`에서 관례적으로 설정되는 기본값, 시스템 간 연동을 위한 추가 설정 등 자동 생성된 모든 문맥이 담긴 선언입니다. 배포에 필요한 IAM Policy가 어떻게 생성되었는지, Lambda 기본 타임아웃이 몇 초인지 등을 확인할 수 있습니다.

**`sls deploy`: 배포**

- 먼저 `sls package`를 수행해 선언 파일과 코드를 만들고, CloudFormation에 제출해 스택을 구축한 뒤, Lambda API로 빌드한 코드를 쓰도록 함수를 갱신합니다.
- 완료되면 걸린 시간, 함수, 엔드포인트 등을 간단한 보고서로 보여줍니다. (예: 스택 hello-world-dev, 함수 hello-world-dev-hello 392 B)
- aws-nodejs 템플릿의 예제는 us-east-1(버지니아 북부) 지역에 `hello-world-dev-hello`라는 Lambda 함수를 만듭니다.

**`sls invoke -f 함수명`: 실행**

- `sls invoke -f hello`로 실행하면 함수의 반환값(statusCode 200과 메시지가 담긴 body)을 화면에 표시합니다.

**로그 확인**

- Serverless Framework는 Lambda 로그를 받는 CloudWatch Logs 자원도 함께 만듭니다. 그래서 코드에서 `console.log` 계열로 남긴 로그를 CloudWatch Logs에서 볼 수 있습니다.
- 확인 경로: AWS 관리 콘솔의 CloudWatch Logs 로그 그룹, 또는 VSCode AWS Toolkit의 CloudWatch 하위 로그 스트림
- 셸에서는 `sls logs -f 함수명`으로 바로 볼 수 있습니다. 함수를 한 번도 실행하지 않았거나 실행 직후 너무 빨리 요청하면 No existing streams 오류가 날 수 있습니다.
- 예제는 별도 로그를 남기지 않아 시작/종료 로그만 남습니다.

**REPORT 행 정보**

- `Duration`: 함수 수행 시간
- `Billed Duration`: 이를 올림한 과금 기준 시간
- `Memory Size`: Lambda에 부여한 메모리 크기
- `Max Memory Used`: 그중 최대로 사용한 양
- `Init Duration`: 함수가 초기화되어 실제 코드가 실행되기 전까지 걸린 시간
- 이 정보로 수행 시간을 최적화하거나 메모리를 적당히 맞출 수 있고, 초기화 시간이 길어지지 않도록 최적화 방법을 찾을 수 있습니다.

**`sls logs` 옵션**

- `t`, `-tail`: 새로 추가되는 로그를 계속 따라가며 출력(Tailing)
- `-startTime`: 지정한 시간까지만 과거 데이터를 조회, 즉 조회 시작 시간 지정(기본 10분, 10m)
- `-filter`: 지정 패턴에 맞는 로그 검색
- `i`, `-interval`: `-tail` 사용 시 로그 확인 주기(기본 1000밀리초)
- `sls logs --help`로 확인할 수 있습니다. 가끔 버그로 필수 옵션을 지정해야 도움말이 나오는 경우가 있는데, 이때는 `sls logs -f X --help`처럼 `f`에 의미 없는 값을 주면 됩니다.
- **`-filter` 패턴 규칙**
- 대소문자를 구분하는 문자열이며, 찾을 문자열을 그대로 입력하면 됩니다.
- 띄어쓰기로 구분된 키워드는 AND 조건으로 검색합니다.
- 제외는 , OR 조건은 `?`를 함께 쓸 수 있습니다.
- 자세한 내용은 CloudWatch Logs의 필터 및 패턴 구문 문서에서 확인합니다.

**`sls deploy function -f 함수명`: 함수만 배포**

- CloudFormation 스택 변경 없이, 이미 구성된 스택 안의 Lambda 코드만 갱신하므로 전체 `deploy`보다 훨씬 빠릅니다.
- 함수를 자주 고치며 테스트할 때 시간 효율이 좋습니다.
- 코드와 설정이 바뀌지 않았다면 아무 작업도 하지 않습니다(skipped).

**`sls info`: 스택 정보 조회**

- 배포 이후에도 service, stage, region, stack, functions 정보를 다시 볼 수 있어 관리 콘솔 없이 확인할 때 유용합니다.

**`sls remove`: 스택 삭제**

- 대부분은 스택이 관리하는 자원을 따로 수정하지 않으므로 이 명령으로 간단히 삭제됩니다.
- 하지만 스택이 만든 API Gateway에 관리 콘솔로 지정 도메인을 따로 붙였거나, S3 Bucket에 파일을 올려 비어 있지 않다면, 그 자원을 직접 해제하기 전까지 삭제가 실패합니다.
- 이때 `sls remove`는 실패로 끝나지만 배포 메타데이터는 이미 삭제된 상태라, 다시 실행하면 이미 삭제된 스택이라는 오류가 납니다.
- 결국 CloudFormation 관리 콘솔이나 AWS CLI로 문제 부분을 찾아 제거한 뒤 스택 삭제를 다시 진행해야 하는데, 매우 번거롭습니다. 따라서 삭제 전에 스택 선언 밖에서 조작한 자원 변경점이 있는지, S3 Bucket이 비어 있는지 미리 확인하는 것이 좋습니다.

## 참고: 2026년 기준으로 달라진 점

책이 2022년 기준이라 그대로 따라 하면 막히는 부분이 있을 수 있습니다.

- **Node.js 런타임**: Node.js 14, 16은 Lambda에서 이미 지원 종료되었습니다. `runtime: nodejs14.x`로는 새 함수를 만들 수 없으므로 현재 지원되는 LTS 버전(예: nodejs20.x 이상)으로 바꾸고, nvm으로 로컬 버전도 맞추세요.
- **Serverless Framework**: 2024년 v4부터 실행 시 계정 로그인이 필요하고, 일정 매출 이상 조직에는 유료 라이선스 정책이 생겼습니다. 책과 동일하게 실습하려면 `npm install -g serverless@3`으로 v3를 설치하는 방법이 있습니다.
- **액세스 키**: AWS는 루트 계정 액세스 키 발급 자체를 권장하지 않습니다. 개인 학습이라도 IAM 사용자(또는 IAM Identity Center)를 만들어 그 키를 쓰는 편이 안전합니다.

정확한 최신 지원 버전은 AWS Lambda 런타임 문서에서 한 번 확인해 보시는 걸 추천합니다.
