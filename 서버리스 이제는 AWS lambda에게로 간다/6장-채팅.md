### 6-1 WebSocket API

**왜 필요한가**

- REST API와 HTTP API는 클라이언트가 요청해야만 서버가 응답할 수 있다. 서버가 먼저 데이터를 보내야 하는 경우(오래 걸리는 작업의 완료 알림, 게임 상태 변경 등)에는 적합하지 않다.
- HTTP 연결을 WebSocket으로 업그레이드하면 양방향 통신이 가능하다. API Gateway는 이를 위해 별도의 WebSocket API를 제공한다.
- 이벤트 형식은 HTTP API의 V2보다 REST API의 V1에 더 가깝다.

**라우트 유형과 반환값**

- `$connect`: 연결을 맺을 때 호출된다. 200을 반환하면 연결을 허용하고, 4xx나 5xx를 반환하면 거부한다.
- `$disconnect`: 연결이 끊길 때 호출된다. 반환값은 동작에 영향을 주지 않고, 보통 200을 반환한다.
- `$default`: 메시지를 받았는데 매칭되는 라우트가 없을 때 호출된다. 본문이 JSON이 아닐 때도 여기로 온다.
- `$default`를 지정하지 않으면 클라이언트는 500 Internal server error를 받는다. 다만 요금이 계속 나가므로 이런 경우에는 바로 연결을 끊는 것을 권장한다.
- 반환 형식은 `{ statusCode }`이고 body는 생략할 수 있다. 값을 반환하지 않으면 500이 발생한다.

**connectionId와 @connections API**

- 연결마다 고유한 `connectionId`가 부여된다.
- `https://API_ID.execute-api.REGION.amazonaws.com/STAGE/@connections/CONNECTION_ID`로 IAM 서명된 요청을 보내 연결을 제어한다.
    - GET: 연결 정보를 조회한다(연결 시각, 마지막 활성 시각, 접속자 IP, User-Agent).
    - POST: 해당 연결에 메시지를 비동기로 보낸다. 서버에서 메시지를 보내려면 반드시 이 API를 써야 한다.
    - DELETE: 연결을 끊는다. 종료 코드는 지정할 수 없고 항상 1000(Normal close)으로 종료된다.
- IAM 서명을 직접 처리하기 번거로우므로 aws-sdk의 `ApiGatewayManagementApi`를 사용한다.

### 6-2 에코

**구성**

- aws-sdk 2.1055.0을 사용한다(2022년 8월 Lambda 기본 탑재 버전).
- serverless.ts의 functions에 `websocket: { route: "$default" }` 이벤트를 등록한다.
- `$connect`와 `$disconnect`에 함수를 등록하지 않으면 모든 연결이 바로 수락되고, 끊길 때는 아무 일도 일어나지 않는다.

**handleMessage 구현 포인트**

- connectionId는 `event.requestContext.connectionId`로 얻는다. APIGatewayEvent 타입은 REST/HTTP API와 공용이라 타입이 `string | undefined`이므로, WebSocket에서는 값이 반드시 있다는 의미로 `!`를 붙인다.
- 본문이 비어 있으면 돌려줄 내용이 없으므로 무시한다.
- `ApiGatewayManagementApi`의 endpoint는 `domainName/stage`로 조합한다.
- `postToConnection`의 Data는 string이다. 객체를 보낼 때는 `JSON.stringify`로 직렬화한다.
- 마지막에 statusCode 200을 반환한다. 반환하지 않으면 클라이언트는 500을 받지만 연결은 유지된다.

**6-2-1 로컬 테스트**

- serverless-offline 플러그인을 사용한다. WebSocket은 기본 3001 포트(`ws://localhost:3001`)를 쓰고, @connections URL은 `http://localhost:3001`이다.
- `IS_OFFLINE` 환경 변수로 endpoint를 로컬과 AWS 중에서 분기한다. 포트가 충돌하면 `-websocketPort`로 바꾸고 endpoint도 함께 수정한다.
- 2022년 8월 기준으로 serverless-offline은 `$connect` 라우트가 없으면 정상 동작하지 않는다. 그래서 200만 반환하는 빈 handleConnect를 추가한다.
- 테스트 클라이언트로 wscat을 전역 설치하고 `wscat -c "ws://localhost:3001"`로 접속한다.

**6-2-2 배포**

- `sls deploy`로 배포하면 wss 엔드포인트가 출력된다(API Gateway가 SSL을 지원).
- 첫 메시지에서는 콜드 스타트 지연이 느껴지지만, 이후 Lambda가 재사용되면 거의 체감되지 않는다.

**6-2-3 라우트 선택 표현식**

- `provider.websocketsApiRouteSelectionExpression`에 `"$request.body.action"`을 지정하면 본문의 action 값으로 라우트가 분기된다.
- 예시로 `route: "talk"`는 handleTalkAction이 처리하고, 그 외 메시지는 `$default`로 가서 `deleteConnection`으로 연결을 끊는다(약속하지 않은 메시지를 보내는 클라이언트를 비정상으로 간주).
- handleTalkAction은 message가 없으면 연결을 끊고, 있으면 JSON으로 감싸 되돌려준다.
- 장점
    - HTTP API의 path별 함수 분리처럼 메시지 유형별로 함수를 나눌 수 있다.
    - 변경된 함수만 배포할 수 있어 다른 기능에 영향을 주지 않는다.
    - `package: individually`와 웹팩 트리 쉐이킹을 함께 쓰면 함수별 번들이 작아져 콜드 스타트가 줄어든다.
- 한계
    - 라우트는 action 값만 확인할 뿐, 나머지 필드 검증은 직접 해야 한다(TypeScript 타입은 런타임을 보장하지 않음).
    - JSON Schema와 Ajv로 검증을 맡길 수 있지만 패키지가 커진다. 콜드 스타트가 중요하면 직접 작성하는 편이 낫다.

### 6-3 채팅 전파 (브로드캐스트)

**개념**

- Lambda는 메시지를 보낸 연결의 ID만 알 수 있다. 접속한 모든 연결에 보내려면 연결 ID를 저장소에 보관해야 한다.
- 흐름은 다음과 같다. 이번 예제부터는 사용자 정의 라우트 없이 `$default`에서 모두 처리한다.
    - `$connect`: DynamoDB에 connectionId를 저장한다.
    - `$default`: 모든 connectionId를 Scan한 뒤 메시지를 전파한다.
    - `$disconnect`: connectionId를 삭제한다.

**6-3-1 연결 ID 관리**

- `DocumentClient`를 만들 때 IS_OFFLINE이면 `localhost:8000`의 로컬 DynamoDB에 연결한다.
- handleConnect는 put, handleDisconnect는 delete를 수행한다. 예외 처리는 따로 하지 않는다.
    - `$connect`에서 예외가 나면 연결이 거부된다. ID를 등록하지 못한 연결은 어차피 아무것도 할 수 없으므로 이 편이 합리적이다.
    - `$disconnect`의 실패는 클라이언트에 영향이 없고 에러 지표로만 남는다.

**6-3-2 메시지 전파**

- Scan은 `ProjectionExpression`으로 connectionId만 가져온다.
- 결과에 `LastEvaluatedKey`가 있으면 이를 다음 요청의 `ExclusiveStartKey`로 넣어 반복한다. Limit을 지정하지 않으면 1MB 단위로 끊어서 가져온다.
- 모든 ID에 대해 `Promise.all`로 postToConnection을 호출한다.
- 한계: API Gateway에 통합된 Lambda는 29초 제한이 있어 연결이 많으면 일부에게 전송하지 못할 수 있다.
    - 해결책은 handleMessage가 큐에만 넣고, 별도 Lambda(최대 900초)가 비동기로 전파하는 구조다.

**6-3-3 서버리스 스택 선언**

- 테이블 키는 connectionId 하나(HASH)이고, `PAY_PER_REQUEST` 과금을 사용한다.
- IAM 권한은 PutItem, Scan, DeleteItem이며, 테이블 ARN은 `Fn::GetAtt`로 가져온다.
- 테이블 이름은 TABLE_NAME 환경 변수로 주입한다.
- 로컬용으로 serverless-dynamodb-local 플러그인을 쓰고 `custom.dynamodb`에 `stages: ["dev"]`, `migrate: true`를 설정한다.

**6-3-4 로컬 테스트 / 6-3-5 배포**

- `sls dynamodb install`(최초 1회, `.dynamodb` 디렉터리 생성) 후 `sls dynamodb start`를 실행한다. 이때 선언된 테이블이 자동 생성된다.
- TABLE_NAME은 `.envrc`로 관리하면 편하다.
- 터미널 두 개로 wscat을 접속해 한쪽 메시지가 다른 쪽에 도착하는지 확인한다.
- 배포 후에는 `aws dynamodb list-tables`로 테이블 생성을 확인한다.

### 6-4 주제-구독-전파

**요구사항**

- 클라이언트는 연결할 때 헤더로 사용자 정보를 보낸다.
- 메시지로 구독할 주제를 전달한다.
- talk 메시지는 그 주제를 구독한 모든 연결에 전달된다. 즉 간단한 채팅방 서비스다.
- 회원 가입, 로그인, 주제 생성 로직은 생략한다(앞의 블로그 예제에서 다룸).

**6-4-1 테이블 설계**

- 도메인은 연결, 사용자, 주제다. 한 사용자는 여러 연결과 여러 구독 주제를 가질 수 있고, 한 연결의 구독 변경은 그 사용자의 모든 연결에 반영되어야 한다.
- DynamoDB는 JOIN이 어려우므로 비정규화한 4개 테이블을 사용한다.
    - ConnectionUser (connectionId → userId): Lambda는 connectionId만 알기 때문에 사용자를 식별하는 데 쓴다.
    - UserConnection (userId → Set connectionIds): 구독 변경을 사용자의 모든 연결에 반영하는 데 쓴다.
    - UserTopic (userId → Set topicIds): 사용자의 구독 주제를 관리한다.
    - TopicConnection (topicId → Set connectionIds): 주제를 구독한 모든 연결에 메시지를 보내는 데 쓴다.
- TopicUser 대신 TopicConnection을 둔 이유: 채팅에서는 구독이나 연결 변경보다 메시지 교환이 훨씬 잦다. 정합성을 조금 양보하더라도 전송 시 바로 조회할 수 있게 한 것이다.
- DynamoDB의 Set 타입은 ADD와 DELETE로 원자적 갱신이 가능해 동시성 문제를 줄여준다.

**6-4-2 DynamoDB 테이블 선언**

- `DynamoDBTable(tableName, keyName)` 헬퍼로 구조가 같은 4개 테이블을 생성한다. 테이블 이름은 각각 환경 변수로 주입한다.
- `DynamoDBTableRoleStatement({ 테이블변수 })` 헬퍼는 Put, Get, Update, Delete 권한을 만든다.
    - 변수명을 문자열로 받으면 이름 변경에 취약하므로 객체로 받아 `Object.keys(table)[0]`으로 꺼낸다.
- provider.iam.role.statements, provider.environment, resources.Resources에 모두 등록한다.

**6-4-3 DynamoDB 연동 구현 (db.ts)**

- ConnectionUser(1:1 관계): `insertConnectionUserId`, `deleteConnectionUserId`, `findUserIdByConnectionId`를 제공한다.
- 나머지 세 테이블(1:N 관계)은 `StringSetTable(tableName, keyName, setName)`으로 일반화한다.
    - `create`: 빈 문서를 put한다.
    - `get`: 문서를 `Record<string, any>`로 반환한다. 테이블별 유니온 타입이 번거로워 이렇게 처리한다. Set은 실제로 `{ values: string[] }` 형태다(aws-sdk의 DynamoDbSet).
    - `exists`: get 결과가 undefined인지 확인한다.
    - `appendValue`: `ADD ${setName} :v`와 `db.createSet([value])`를 사용한다. ADD는 Set이 아직 없어도 원자적으로 생성하며 추가한다.
    - `removeValue`: `DELETE` 명령으로 원자적으로 제거한다.
    - `getValues`: 값이 없으면 null 검사를 피하기 위해 빈 배열을 반환한다.
- append와 remove에는 `ConditionExpression: attribute_exists(key)`를 건다.
    - 동시에 문서가 삭제될 때 불필요한 수정을 막아준다.
    - 주제 문서는 별도 HTTP API로만 생성되므로, 생성되지 않은 주제에 대한 구독도 막을 수 있다.

**6-4-4 연결 맺음과 끊음**

- handleConnect
    - `x-user-id` 헤더가 없거나 UserTopic에 해당 사용자 문서가 없으면(미가입) 400으로 연결을 거부한다.
    - 정상이면 ConnectionUser 기록, UserConnection에 connectionId 추가, 사용자가 구독 중인 모든 주제의 TopicConnection에 새 연결을 추가한다.
    - 중간에 예외가 나면 400을 반환한다.
- 이 구현의 문제
    - handleConnect는 연결 완료 후가 아니라 연결 수락 여부를 결정하는 단계에서 호출된다. 200을 반환하기 전까지 그 연결은 유효하지 않다.
    - 그 사이에 TopicConnection에는 이미 등록되어 있으므로, 해당 주제에 talk가 발생하면 전송이 실패한다.
    - 해결하려면 연결이 완전히 수립된 뒤 초기화용 메시지를 따로 받아 처리해야 한다.
- handleDisconnect
    - 역순으로 정리한다. 구독 주제마다 TopicConnection에서 제거하고, UserConnection에서 제거하고, ConnectionUser를 삭제한다.
    - userId를 못 찾으면 500을 반환한다. 반환값이 클라이언트에 영향은 없지만 IntegrationError 지표로 모니터링하기 위함이다. 예외를 던져 Lambda 에러 지표로 잡는 것도 좋은 방법이다.

**6-4-5 메시지 전파 처리**

- 메시지 타입
    - SubscribeMessage `{ type: "subscribe", topic }`: 채팅방 입장.
    - UnsubscribeMessage `{ type: "unsubscribe", topic }`: 채팅방 퇴장.
    - TalkMessage `{ type: "talk", topic, text }`: 채팅방에 메시지 전송.
- 응답 TalkResponse는 `{ type: "talk", topic, sender, text }`이다. 앞으로 여러 유형을 받을 수 있어 type을 유지하고, sender에는 보낸 사람의 x-user-id를 담는다.
- handleMessage
    - `sendMessage` 래퍼는 개별 전송 실패를 로그만 남기고 바깥으로 전파하지 않는다. 받는 쪽 문제 때문에 보낸 쪽 연결이 끊기면 안 되기 때문이다. 상용 서비스라면 불안정한 수신 연결을 어떻게 다룰지 정책을 정해야 한다.
    - userId를 조회하고 body를 JSON.parse한 뒤 `processMessage`에 위임한다. 사용자가 없거나 본문이 잘못되면 deleteConnection 후 400을 반환한다.
- processMessage는 type별 switch로 분기한다. 라우트 선택 표현식을 썼다면 이 switch는 필요 없다.
- subscribeTopic: UserTopic에 주제를 추가하고(이후 새 연결도 자동 구독), 사용자의 모든 연결을 TopicConnection에 추가한다.
- unsubscribeTopic: TopicConnection에서 먼저 제거한 뒤 UserTopic에서 제거한다. 이 순서여야 `$disconnect` 처리와의 경합에서 부정합이 생기지 않는다.
- 남은 문제: 트랜잭션이 없다
    - 사용자 문서는 있는데 주제 문서가 없으면 UserTopic만 갱신되고 TopicConnection은 실패해 정합성이 깨진다.
    - 최소한 실패 원인을 사전에 검사해야 하고, 가장 좋은 방법은 두 갱신을 트랜잭션으로 묶는 것이다.
    - 근본적으로는 사용자별 액터 모델로 이벤트 처리 순서를 보장할 수 있다. 하지만 Lambda에서는 별도 메시지 큐와 분산 잠금이 필요해 범위를 벗어나며, 간단한 모델은 7장 게임에서 다룬다.
- talk
    - text가 없으면 에러를 던진다.
    - TopicConnection에 자기 connectionId가 없으면(구독하지 않은 주제) 에러를 던진다.
    - TalkResponse는 한 번만 stringify해서 모든 수신자에게 `Promise.all`로 보낸다.

**6-4-6 사용자 및 주제 생성 API**

- HTTP API를 사용한다.
    - `POST /user/{userId}`: UserConnection과 UserTopic 문서를 생성한다.
    - `POST /topic/{topicId}`: TopicConnection 문서를 생성한다.
- 생성을 외부(관리자)에 위임하므로 시스템이 특정 도메인에 묶이지 않는다.
- 인증은 생략한다. 필요하면 4장의 Lambda 권한 부여자를 쓴다.

**6-4-7 함수 등록**

- WebSocket 함수 3개(`$connect`, `$disconnect`, `$default`)와 httpApi 함수 2개를 한 스택에서 관리한다.

**6-4-8 로컬 테스트**

- `.envrc`에 4개 테이블 이름(wt-connection-user, wt-user-connection, wt-user-topic, wt-topic-connection)을 지정하고 `sls dynamodb start`를 실행하면 모두 생성된다.
- 로컬 DynamoDB 내용은 오픈 소스 웹 콘솔 dynamodb-admin으로 볼 수 있다.
    - `npm install -g dynamodb-admin`으로 설치한다.
    - `DYNAMO_ENDPOINT=http://localhost:8000`을 지정해 실행한다. Windows에서는 set이나 cross-env를 쓴다.
- `sls offline`을 실행하면 WebSocket(3001)과 HTTP API(3000) 목록이 함께 출력된다
- curl로 `POST /user/user1`, `POST /topic/topic1`을 호출해 사용자와 주제를 하나씩 만든다. dynamodb-admin에서 사용자-주제, 주제-연결 테이블에 문서가 생긴 것을 확인할 수 있다.
- wscat은 `H` 옵션으로 헤더를 붙일 수 있다. `x-user-id: user1`로 접속해 subscribe 후 talk를 보내면, 응답에 sender로 user1이 붙어서 돌아온다.
- 같은 사용자로 재접속해도 구독 해지 전까지는 계속 메시지를 받고, 다른 사용자가 같은 주제를 구독해도 전파가 잘 된다.
- 등록되지 않은 사용자 ID로 접속하면 400과 함께 연결이 거부된다.

**6-4-9 배포**

- `sls deploy`를 실행하면 wss 엔드포인트 하나와 HTTP POST 엔드포인트 두 개가 출력된다.
- 4개 테이블 이름이 환경 변수로 잘 들어갔는지, `aws dynamodb list-tables`로 테이블이 생성됐는지 확인한다.

### 6-5 인증

**WebSocket API에서 Lambda 권한 부여자의 특징**

- HTTP/REST API는 모든 요청마다 권한 부여자를 실행하지만, WebSocket API는 연결을 맺을 때 한 번만 실행한다.
- 흐름은 두 단계다.
    - 권한 부여자가 거부하면 handleConnect는 실행되지 않고 연결이 거부된다.
    - 권한 부여자가 허가해도 handleConnect가 다시 연결을 거부할 수 있다.
- 얼핏 handleConnect와 하는 일이 겹쳐 보이지만, 권한 부여자가 반환한 context를 이후 모든 WebSocket 이벤트에서 `requestContext.authorizer`로 꺼내 쓸 수 있다는 점이 결정적 차이다.
- 그래서 connectionId로 userId를 찾던 연결-사용자(ConnectionUser) 테이블 자체를 없앨 수 있다.

**6-5-1 Lambda 권한 부여자 구현**

- REST API 방식을 따른다. HTTP API V2처럼 간단히 허가 여부만 반환할 수 없고 IAM 정책 문서를 반환해야 한다.
- TOKEN 유형은 쓸 수 없고 REQUEST 유형만 가능하다. 타입은 `APIGatewayRequestAuthorizerHandler`를 쓴다.
- 구현 포인트
    - 토큰은 `token` 쿼리 파라미터로 받는다. 브라우저 표준 WebSocket은 Authorization 같은 HTTP 헤더를 실어 보낼 수 없기 때문이다. 예제에서는 편의상 userId를 그대로 토큰으로 쓰지만, 실제로는 블로그 예제처럼 OAuth 토큰을 쓸 수 있다.
    - 토큰이 없거나 해당 사용자가 없으면 문자열 `Unauthorized`를 throw한다. API Gateway가 이를 401로 바꿔 응답한다.
    - 허가 시에는 `execute-api:Invoke`를 Allow하는 정책을 반환하고, Resource에는 `event.methodArn`을 넣는다.
    - context에 넣은 값은 이후 Lambda에서 `requestContext.authorizer`로 받을 수 있어 매번 다시 조회하지 않아도 된다.
- principalId 활용
    - 정책이 적용되는 대상의 고유 ID로, 개발자가 자유롭게 정할 수 있다.
    - 이번 예제처럼 값이 userId 하나라면 context 대신 principalId에 넣는 것으로 충분하다. principalId도 `requestContext.authorizer`로 전달되기 때문이다.
    - 의미 있는 값을 넣는 게 좋다. 로깅을 켜면 CloudWatch Logs에 principalId가 함께 남아 문제 추적에 쓸 수 있다.

**6-5-2 이벤트 처리 함수 수정**

- handleConnect: `x-user-id` 헤더 검사와 사용자 존재 확인(권한 부여자가 이미 처리)을 제거하고, `requestContext.authorizer.principalId`를 userId로 쓴다. insertConnectionUserId 호출도 삭제한다.
- handleDisconnect: findUserIdByConnectionId 대신 authorizer의 principalId를 쓰고, deleteConnectionUserId를 삭제한다.
- handleMessage: 마찬가지로 DynamoDB 조회 없이 principalId를 userId로 쓴다.
- 트레이드오프
    - `requestContext.authorizer`에는 `integrationLatency` 필드로 권한 부여자 실행 시간이 담긴다. 권한 부여자의 콜드 스타트까지 포함되면 수백 밀리초가 될 수 있어, 연결 시점만 보면 handleConnect에서 직접 처리하는 편이 빠를 수 있다.
    - 하지만 이후 `$default`, `$disconnect`에서 이득이 있다. 이번 예제에서는 handleMessage와 handleDisconnect의 DynamoDB 호출이 1회씩 줄었다.
    - 연결을 맺고 끊는 것보다 메시지 교환이 훨씬 잦으므로 handleMessage를 가볍게 만드는 쪽이 유리하다. 연결 시 준비할 정보가 복잡할수록 효과가 커진다.

**6-5-3 서버리스 스택 수정**

- 연결-사용자 테이블과 해당 IAM 권한을 serverless.ts에서 제거한다.
- `authorize` 함수를 등록한다. 권한 부여자로 호출되므로 이벤트는 연결하지 않으며, 필요하면 timeout이나 memorySize만 조정한다.
- handleConnect의 websocket 이벤트에 `authorizer: { name: "authorize", identitySource: "route.request.querystring.token" }`을 지정한다.
- identitySource 주의사항
    - 이 값이 요청에 없으면 WebSocket API는 권한 부여자를 실행하지도 않고 바로 401로 거부한다.
    - 즉 모든 연결을 허가하는 권한 부여자를 붙여도 token 파라미터가 없으면 연결이 안 된다.
    - 이 경우 권한 부여자가 실행되지 않았으니 Lambda 로그도 없다. API Gateway 수준 로그를 켜야 원인을 알 수 있으며, 모르면 시간을 크게 낭비할 수 있다.

**6-5-4 WebSocket API 로깅**

- `provider.logs.websocket.level`로 활성화하며 INFO 또는 ERROR를 고를 수 있다. Serverless Framework에서는 HTTP/REST API와 달리 로그 서식 옵션은 지원하지 않는다. 허가 성공 로그까지 보려면 INFO를 쓴다.
- 로그는 CloudWatch Logs의 `/aws/apigateway/API_ID/STAGE` 그룹에 남고, 요청마다 생성되는 requestId로 추적할 수 있다.
- 세 가지 경우의 로그 차이
    - token이 없는 경우: 권한 부여자 실행 로그 없이 곧바로 Unauthorized request로 분류되고 401이 반환된다.
    - token은 있지만 거부된 경우: 권한 부여자 실행 로그가 명확히 남는다. Incoming identity에 토큰이 마스킹되어 찍히고, 요청 헤더나 본문은 TRUNCATED로 잘려 기록된다. 이후 Unauthorized로 401을 반환한다.
    - 허가된 경우: 권한 부여자가 반환한 정책 문서(principalId 포함)가 찍히고, 사용 계획(Usage Plan)의 API Key 검사가 진행된다($connect는 API Key가 필요 없어 통과). 이어 handleConnect가 실행되어 Status 200, Integration latency 680ms 같은 값이 남고 연결이 수락된다.
- 운영 팁: API Gateway 수준 로그는 통합 동작을 검증할 때 외에는 쓸 일이 거의 없다. 권한 부여자를 붙이는 개발 기간에만 켜고, 감사 로그가 필요 없다면 CloudWatch Logs 비용을 생각해 꺼두는 게 좋다.

### 6-6 사용자 지정 도메인

**설정**

- serverless-domain-manager 플러그인을 쓴다(`sls plugin install --name serverless-domain-manager`).
- `custom.customDomain`에 설정한다.
    - `apiType: "websocket"`으로 지정한다.
    - 도메인과 인증서 설정은 기존과 같다.
    - WebSocket API는 리전 API만 지원하므로 `endpointType: "regional"`로 지정한다.
    - Route53 레코드를 새로 만들 때는 `createRoute53Record`를 true로 둔다.

**stage와 basePath 함정**

- WebSocket API도 stage가 필수이며, 지정하지 않으면 dev가 기본값이다. 기본 주소는 `wss://WS_ID.execute-api.REGION.amazonaws.com/STAGE` 형태가 된다.
- @connections 명령은 `https://.../STAGE/@connections/CONNECTION_ID`로 보낸다. 배포 전에는 WS_ID를 모르므로 지금까지는 `requestContext.domainName`과 `stage`를 조합해 endpoint를 만들었다.
- basePath를 지정하지 않으면 해당 stage 전체가 도메인의 `/`에 매핑된다.
    - 연결 주소는 `wss://ws.lacti.link`가 되고, `/dev`로는 연결할 수 없다.
    - 그런데 `requestContext.stage`는 여전히 dev이므로 코드가 만드는 endpoint는 `ws.lacti.link/dev`가 된다.
    - 실제로 올바른 @connections URL은 `https://ws.lacti.link`이므로 불일치가 발생한다. 클라이언트는 Internal server error를 받고, Lambda 로그에는 AccessDeniedException이 찍힌다.
- basePath를 stage와 같게 지정하면 연결 주소가 `wss://ws.lacti.link/dev`가 되고, domainName과 stage 조합으로 만든 URL과 일치한다.

**대안과 해결**

- `MANAGEMENT_API_URL` 같은 환경 변수로 endpoint를 주입하는 방법도 있다. 단, 이 경우 기본 execute-api 주소로 접속해도 @connections 명령은 사용자 지정 도메인 주소로 나간다는 점을 계속 인지하고 있어야 한다.
- 가장 간단한 해결책은 basePath를 stage와 동일하게 설정하는 것이다.
- `sls create_domain`으로 도메인과 Route53 레코드를 만들고, `sls deploy`로 API를 도메인 경로에 등록한다. 이후 `wss://ws.lacti.link/dev?token=USER_ID`로 접속한다.

### 6-7 상용 서비스 고려

**6-7-1 채팅 서비스**

- 회원 관리와 인증
    - 허가되지 않은 사용자가 계속 접속해 자원을 소모하거나, 아무 주제나 구독해 스팸을 뿌리는 것을 막아야 한다.
    - 가입 후 이용 전 인증이 필요하다. 이메일은 대량 생성이 쉬우므로 가능하면 휴대폰 인증이 낫다.
    - 구독 가능 범위, 수신만 가능한지 송신도 가능한지 등 권한 관리를 설계한다.
    - 신고 채널과 운영 관리 도구도 필요하다.
- 남용 방지: 초당 1건 같은 메시지 횟수 제한(Rate Limit), 동일 내용 반복 차단, 특정 키워드 차단 같은 단순한 장치로 1차 차단이 가능하다.
- 대화 보관: 1:1 상담처럼 기록이 필요하면 메시지를 SQS에도 보내고, 보관 모듈이 주기적으로 꺼내 상담별로 임시 분류한 뒤 상담 종료 이벤트를 받으면 S3에 업로드한다.
- 이전 대화 조회: 현재는 전파만 하고 저장하지 않는다. 저장소에 보관하면서 단조 증가 ID를 부여하면 특정 시점 이전 메시지 N개를 가져오는 기능을 만들 수 있다. 운영 도구까지 고려하면 HTTP API로 만드는 게 편하다.
- 불안정한 모바일 네트워크
    - postToConnection이 계속 실패하는데 연결은 끊기지 않을 수 있다.
    - 현재처럼 `await Promise.all`로 모든 전송 완료를 기다리면, 한 명의 타임아웃이 멀쩡한 다른 클라이언트의 지연까지 늘린다.
    - 대기를 사용자 범위로 한정하고, 자주 실패하면 연결을 끊고, 재전송하되 중복 제거 처리를 해야 한다.
- 미디어 전송: 3장의 사진 최적화 서비스와 연계한다. 별도 서비스로 업로드한 뒤 CDN 주소를 메시지로 보내고, 저화질과 고화질을 함께 만들어 비용을 아끼며, 업로드 재시도 로직도 둔다.
- 봇 확장
    - 주제의 대화를 받아볼 웹훅을 등록해, 전파 시 웹훅으로도 보내준다.
    - 반대로 HTTP API로 주제에 메시지를 넣는 기능(Incoming Webhook)도 만들 수 있다. 요청자의 권한을 확인하고, 모두가 쓸 수 있다면 발송 속도를 제한한다.
- 대규모 오픈 채팅방: 구독 연결이 많으면 Lambda 수행 시간 초과가 날 수 있어 구조를 바꿔야 한다.
    - handleMessage는 전파 대기열에 넣고 바로 종료한다.
    - 대기열을 구독하는 비동기 Lambda(최대 900초)가 담당 사용자 집합에 전파한다.
    - 이런 Lambda를 여러 개 띄워 병렬 전파하고, 시간 안에 못 끝내면 다시 실행(Recurring)해 이어서 처리한다.

**6-7-2 이벤트 채널**

- 채팅은 이벤트를 교환하는 이벤트 채널로 일반화할 수 있다. 실시간 알림이나 게임 메시지 전파에도 같은 구조를 쓴다. 추가로 고려할 점은 전달 속도와 정확히 한 번(Exactly once) 전달이다.
- 전달 속도
    - 게임은 수신자는 적지만 이벤트 횟수가 많아 지연이 생기기 쉽고, 주원인은 Lambda 콜드 스타트다.
    - 수신 Lambda는 최대한 가볍게 만들어 이벤트를 대기열에 넣고 바로 끝낸다. 빨리 끝날수록 인스턴스 재사용률이 높아진다.
    - 게임 동안 계속 실행되는 Lambda가 대기열을 구독해 상태를 변경하고 전파한다. 실행 상태를 유지하므로 콜드 스타트 피해가 없다. 7장에서 자세히 다룬다.
- 정확히 한 번 전달
    - 쉽게 떠올릴 방법은 수신자가 ACK를 보내고, 시간 내 ACK가 없으면 재전송하는 것이다.
    - 하지만 처리 후 보낸 ACK가 유실되면 이미 처리한 메시지가 다시 오고, 수신자가 지연되면 처리 중인 메시지를 또 받을 수 있다.
    - 완벽한 구현은 매우 어렵다. 제약 상황을 상정하고 구현하거나, 수신 측에서 멱등 처리를 하도록 안내하는 편이 낫다.

**6-7-3 WebSocket API의 한계**

- Stateful한 연결을 Stateless한 Lambda로 처리할 수 있어 편하지만, Lambda 제약(통합 Lambda 최대 29초)을 그대로 받는다.
- WebSocket API 자체의 제약
    - 토큰 버킷 알고리즘으로 초당 요청수(RPS)를 제한한다.
    - 엣지 최적화 API는 불가하고 리전 API만 가능하다.
    - 리전-계정당 초당 새 연결은 500개까지다(서포트 티켓으로 상향 가능).
    - Lambda 권한 부여자는 최대 8KB까지 반환할 수 있어 context에 많은 데이터를 넣을 수 없다.
    - API 하나에 라우트와 Lambda 통합은 300개까지다(티켓으로 상향 가능).
    - 프레임 하나는 최대 32KB이며 늘릴 수 없다.
    - 메시지는 최대 128KB로, 4개 프레임으로 나뉘어 전송된다. 더 크면 1009 종료 코드로 연결이 끊기며 늘릴 수 없다.
    - 아무것도 하지 않는 유휴 연결은 10분 뒤 끊기며 늘릴 수 없다.
    - 메시지를 주고받더라도 연결은 2시간 뒤 끊기며 늘릴 수 없다.
- 마지막 네 가지가 가장 까다롭다. 메시지를 32KB 미만으로 설계하고 크면 여러 개를 합치는 구조를 쓰거나, S3에 업로드하고 객체 키만 주고받는다. 연결 시간은 피할 수 없으므로 처음부터 재연결 시나리오를 고려해 설계한다.

**6-7-4 글로벌 서비스 고려**

- 엣지 최적화를 못 쓰므로 직접 구성해야 하며 방법은 두 가지다.
- CloudFront
    - 별도 추가 구성 없이 WebSocket을 지원한다. 오리진으로 WebSocket API를 지정한다.
    - 오리진 요청 정책에서 `Sec-WebSocket-Key`, `Sec-WebSocket-Accept`, `Sec-WebSocket-Protocol`, `Sec-WebSocket-Version` 헤더를 전달하도록 한다. 확장이 필요하면 `Sec-WebSocket-Extensions`도 전달한다.
- Route53 지연 시간 라우팅 정책
    - 서비스 지역마다 WebSocket API를 배포하고, 지연 시간 라우팅 레코드에 모든 리전 API를 등록한다. 클라이언트는 가장 가까운 데이터센터에 연결된다.
    - 엣지에서 서비스 리전까지 가는 시간을 없애므로 CloudFront보다 지연 시간이 나을 수 있다.
    - 다만 저장소를 쓴다면 다중 지역 동기화가 필요할 수 있고, 운영 비용이 크게 늘 수 있으므로 신중히 선택한다.

### 6-8 모니터링

**6-8-1 WebSocket API 지표**

- 요청-응답 구조가 아니라서 HTTP API 지표와 조금 다르다.
    - ConnectCount: `$connect` 라우트 Lambda로 전달된 메시지 수.
    - MessageCount: 클라이언트와 주고받은 메시지 수.
    - IntegrationError: Lambda가 4XX나 5XX를 반환한 수.
    - ClientError: Lambda 실행 전에 API Gateway가 4XX를 반환한 수.
    - ExecutionError: Lambda 호출 중 발생한 오류 수.
    - IntegrationLatency: API Gateway가 Lambda에 요청을 보내고 응답을 받기까지의 시간.
- 보는 방법
    - 초당 500 연결 제한이 있으므로 장애 후 대응하지 말고 ConnectCount 추세를 미리 본다.
    - MessageCount가 늘면 Lambda가 부족할 수 있으니 Lambda 동시 실행수(ConcurrentExecutions)와 함께 본다.
    - IntegrationLatency를 Lambda Duration과 함께 본다. 통합 시간은 늘었는데 수행 시간이 그대로라면 Lambda가 제대로 실행되지 못하고 있다는 뜻이다.
    - 에러는 IntegrationError, ClientError, ExecutionError로 확인하고, HTTP API 때처럼 Lambda 지표와 API Gateway 지표를 모두 본다.
- 로그나 지표가 생성되지 않는 경우
    - 413 Request Entity Too Large가 발생한 경우.
    - 429 Too Many Requests가 과도하게 발생하는 경우.
    - 사용자 지정 도메인에 연결된 API가 없어 4XX가 나는 경우.
    - WebSocket API 내부 오류로 5XX가 나는 경우.
- 대응: 너무 큰 본문이나 과도한 요청을 클라이언트에서 막고, 도메인 설정 실수에 대비해 외부 관찰자를 두어 주기적으로 서비스 동작을 확인한다.

### 6-9 비용 계산

**6-9-1 시나리오**

- 서울 리전, 하루 이용자 20만 명, 전체 가입자 500만 명.
- 연결당 평균 30분 유지, 사용자당 하루 메시지 100개, 하루 3번 연결(동시에는 1개).
- 주제당 평균 구독자 3명, 주제 100만 개, 메시지는 모두 32KB 미만.
- Lambda 수행 시간은 권한 부여자 100ms, `$connect`와 `$disconnect` 100ms, `$default` 80ms, 메모리 1,024MB.
- HTTP API, 구독 과정, CloudWatch 비용은 무시하고 한 달은 30일로 계산한다.

**6-9-2 WebSocket 비용**

- 메시지 건수는 32KB 단위로 센다(31KB는 1건, 33KB는 2건). 처음 10억 건은 백만 건당 1.14USD, 이후 0.94USD이고 연결 시간은 백만 연결-분당 0.285USD다.
- 메시지: 20만 명 × 100개 × 3명 전파 × 30일 = 18억 건, 1892USD.
- 연결 시간: 20만 명 × 30분 × 3회 × 30일 = 5억 4천만 분, 153.9USD.

**6-9-3 DynamoDB 비용**

- 구독 변경에 따른 접근은 메시지 교환에 비해 미미하므로 스토리지와 주제-연결 테이블 조회만 계산한다.
- 스토리지: 사용자-주제 750MB(500만 명 × 150바이트), 주제-연결 60MB(100만 개 × 60바이트)로 1GB 미만이며, 1GB로 잡아도 0.27075USD다.
- 읽기: 송신 메시지 6억 건마다 조회하므로 162.6USD다.

**6-9-4 Lambda 비용**

- 연결 맺음과 끊음은 월 1,800만 건이고, 한 번에 Lambda 3개(권한 부여자, connect, disconnect 기준)가 호출된다. 호출 비용 10.8USD, 수행 시간 비용 90.18USD.
- 메시지 송신은 월 6억 건으로, 호출 비용 120USD, 수행 시간(80ms) 비용 801.6USD.

**6-9-5 비용 일람 (총 3231.35USD)**

- WebSocket 메시지 교환: 1892USD, 58.55%.
- Lambda 수행 시간: 891.78USD, 27.60%.
- DynamoDB 읽기: 162.6USD, 5.03%.
- WebSocket 연결 시간: 153.9USD, 4.76%.
- Lambda 호출: 130.8USD, 4.05%.
- DynamoDB 스토리지: 0.27USD, 0.01%.
- WebSocket API와 Lambda를 합치면 3068.48USD로 전체의 95%다.
- 서버 비교: c5.xlarge(4vCPU, 8GiB) 약 22.2대 비용에 해당한다. 서버 1대가 1만 연결을 받아 처리하는 수준이므로 여유롭게 감당 가능해, 비용 효율만 보면 WebSocket API가 좋지 않다. 다만 요청이 고르게 분포하지 않아도 대응할 수 있어 운영 비용 측면에서는 나은 선택일 수 있다.

**6-9-6 비용 줄이기**

- 가장 큰 비용인 메시지 교환은 횟수를 줄이지 않는 한 줄일 방법이 마땅치 않다.
- 대신 Lambda 수행 시간을 줄이는 쪽을 노린다. 수행 시간을 수백 ms로 크게 잡은 이유는 DynamoDB와 @connections 명령의 지연 때문이다.
- @connections 지연은 어쩔 수 없지만, DynamoDB 대신 Redis를 쓰면 사용자-주제, 주제-연결 테이블 접근 시간을 줄여 비용을 조금이라도 아낄 수 있다.

### 6-10 정리

- @connections 명령으로 연결에 메시지를 보내거나 연결을 끊고, 라우트와 라우트 선택 표현식으로 메시지 유형별 함수를 분리할 수 있다.
- Lambda 권한 부여자로 연결 시점에 필요한 정보를 만들어 두고, 이후 모든 Lambda에서 재사용할 수 있다.
- 서버리스의 가장 큰 장점은 처리 문맥의 무상태화다. 연결 상태는 @connections로 분리되고 Lambda는 실행 문맥 안의 상태만 가지므로, 인스턴스 간 의존성이 없어 확장과 운영이 쉽다. 연결 ID처럼 꼭 필요한 상태는 외부 저장소에 두며, VPC 구성이 필요 없다는 점에서 DynamoDB가 좋은 선택이다.
- 다만 가격은 저렴하지 않다. 대량 연결과 빠른 메시지 교환이 목표라면 점유된 자원을 최대한 활용하는 서버를 직접 작성하는 편이 낫다. 모든 비동기 알림에 도입하기보다 비용 효율이 좋은 도메인이나 운영상 이득이 큰 경우에 도입한다.
- 다음 7장에서는 WebSocket API와 Lambda로 게임 서버를 서버리스로 구축한다.

### 핵심 포인트

- WebSocket API의 권한 부여자는 연결 시 한 번만 실행되지만, 그 결과가 연결 수명 동안 따라다닌다는 점이 핵심이다. 덕분에 메시지마다 하던 사용자 조회를 없앨 수 있다.
- identitySource 누락이나 basePath 미설정처럼 Lambda 로그에 흔적이 남지 않는 실수가 실제로 시간을 가장 많이 잡아먹는다. 개발 중에는 API Gateway 수준 로그를 켜두는 게 안전하다.
- 프레임 32KB, 메시지 128KB, 유휴 10분, 최대 2시간은 바꿀 수 없는 제약이므로 메시지 크기 설계와 재연결 시나리오는 처음부터 넣어야 한다.
- 비용의 95%가 메시지 교환과 Lambda에서 나온다. 트래픽이 꾸준하고 많다면 서버 방식이 싸고, 트래픽이 들쭉날쭉하거나 운영 부담을 줄이고 싶다면 서버리스가 유리하다는 판단 기준으로 기억하면 좋다.s
