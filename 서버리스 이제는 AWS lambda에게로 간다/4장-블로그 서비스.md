### 4-1 서비스 소개 및 설계

**목표 기능**

1. 허가된 사용자만 글을 작성할 수 있다.
2. 모든 사용자는 작성된 글을 조회할 수 있다.
3. 작성된 모든 글을 최신순으로 조회할 수 있다.

**핵심 관점**

- 블로그, 게시판, 쇼핑몰 모두 본질은 데이터를 저장했다가 원하는 형태로 조회하는 것이다. 댓글, 권한 관리도 결국 저장소의 영속성 관리 문제로 볼 수 있다.
- 서버리스는 상태가 없으므로 저장소를 따로 운영해야 한다. 이 장에서는 DynamoDB, MySQL, SQLite 세 가지로 같은 API를 구현해서 장단점을 비교한다. (S3는 사진 서비스에서 다뤘으므로 제외)

**설계 결정**

- 글 ID는 `encodeURIComponent(title)` 값을 사용한다.
    - 장점: URL에 제목이 드러나 SEO에 유리하고, ID 자동 생성이 어려운 저장소에서도 쉽게 쓸 수 있다.
    - 단점: 제목이 바뀌면 ID도 바뀐다. 그래서 수정 시 제목이 변경되면 새 글 등록 후 예전 글을 삭제하는 로직이 필요하다.
- 조회 시 ID가 유효하지 않으면 404를 반환한다.
- 목록 조회는 저장소가 정렬을 지원하면 맡기고, 지원하지 않으면 전체 조회 후 직접 정렬한다. 페이징과 미리보기는 지원하지 않는다.

### 4-2 기본 API 구현

**API 5개**

- `POST /api/post`: 글 생성. 요청 `{title, content}`, 응답 `{title}`
- `GET /api/post/{title}`: 글 조회. 응답 `{title, content, created, modified}`
- `PUT /api/post/{title}`: 글 수정. 요청 `{title, content}`, 응답 `{title}`. 경로의 title과 본문의 title이 다르면 제목 변경으로 처리
- `DELETE /api/post/{title}`: 글 삭제
- `GET /api/post`: 글 목록 조회. 응답 `{title, created}[]` (최신순)

**serverless.ts**

- Hello API 구현체를 복사해 `service`만 `simple-blog`로 변경
- `runtime: nodejs14.x`, `region: ap-northeast-2`, `plugins: ["serverless-webpack"]`
- 저장소별 필요한 AWS 자원은 나중에 `resources.Resources` 안에 CloudFormation 형식으로 선언

**파일 구조는 3개로 분리**

- `models.ts`: `Post { title, content, created, modified? }`와 목록용 `PostListItem { title, created }` 인터페이스 정의
- `handler.ts`: API Gateway 요청 처리
    - `createPost`: body가 없으면 404, `storage.insert`가 false면 400 (동시 요청 충돌로 간주)
    - `updatePost`: 경로의 title을 `oldTitle`로, `modified` 시간을 추가해 `storage.update` 호출. 실패 시 400
    - `readPost`: `storage.select` 결과가 null이면 404. 타입 추론 문제 시 `APIGatewayProxyHandlerV2<Post>` 명시
    - `deletePost`: 글 존재 여부와 상관없이 오류가 없으면 200
    - `listPosts`: `storage.list()` 결과를 그대로 반환
    - JSON.parse 실패 같은 예외 처리는 예제 간결성을 위해 생략
- `storage.ts`: `insert`, `select`, `update`, `remove`, `list` 5개 함수의 스텁. `update`는 생성 시간이 필요 없으므로 `Omit<Post, "created">`를 인자로 받는다. handler에서는 `import * as storage from "./storage"`로 묶어서 사용

이후로는 저장소가 바뀌어도 `storage.ts`와 serverless.ts의 Resources만 교체하면 된다.

### 4-3 DynamoDB 연동

#### 자원 선언

- `PostTable`을 `AWS::DynamoDB::Table`로 선언
    - `TableName: "post"`
    - `KeySchema`: title을 HASH 키로 지정 (HASH는 파티션 분산, RANGE는 파티션 내 정렬)
    - `AttributeDefinitions`: title을 S(문자열)로 명시. 키 타입은 S, N, B 세 가지
    - `BillingMode: PAY_PER_REQUEST`
- 키 설계 시 요청이 여러 파티션에 고르게 분산되도록 해야 하며, 정렬이 필요하면 GSI(전역 보조 색인)를 쓰는 편이 낫다. 단 GSI는 별도 읽기/쓰기 용량을 소모해 비용이 추가된다.

**BillingMode 비교**

- PAY_PER_REQUEST: 용량 지정 없이 요청 수만큼 과금. 설정이 단순
- PROVISIONED: 초당 읽기/쓰기 용량을 미리 지정. 트래픽이 꾸준하고 예측 가능하면 최대 7배 정도 저렴하지만, 사용하지 않아도 과금되고 버스트 초과 요청은 처리 못 함. Auto Scaling은 CloudWatch 지표 기반이라 급변하는 트래픽에는 늦다

**IAM 권한**

- `PutItem`, `GetItem`, `UpdateItem`, `DeleteItem` 4개만 허용 (배치나 트랜잭션용 추가 권한은 불필요)
- Resource는 `{ "Fn::GetAtt": ["PostTable", "Arn"] }`으로 ARN을 가져온다
- 문자열 PostTable과 변수 이름이 어긋나는 문제를 막기 위해 `getVariableName({ PostTable })`처럼 객체 키에서 변수 이름을 꺼내는 트릭을 소개
- 최종적으로 `iam.role.statements`에 권한, `resources.Resources`에 PostTable 추가

#### AWS SDK

- Lambda 런타임에 내장된 버전과 맞춰 `aws-sdk@2.1055.0`을 optional로 설치
- `webpack.config.js`의 `externals`에 `/aws-sdk/` 추가해 번들 용량 증가 방지

#### CRUD 구현

- 저수준 `DynamoDB` 클래스는 모든 필드에 `{ S: ... }` 같은 타입 명시가 필요해 번거로우므로 `DocumentClient` 사용
- **insert**: `put`은 기존 값을 덮어쓰므로 `ConditionExpression: "attribute_not_exists(title)"`로 중복 생성 방지
    - `ConditionalCheckFailedException`이거나 `error.retryable`이면 false 반환(클라이언트 재시도 유도, 400)
    - 그 외는 throw해서 500
    - 재시도 가능 오류는 `DocumentClient`의 `maxRetries`로 지수 백오프 자동 재시도 가능
- **select**: `get` 결과의 `Item`이 undefined면 null 반환 (`?? null`)
- **update**는 두 경우로 나뉜다 (DynamoDB는 키 변경을 지원하지 않기 때문)
    1. 제목이 그대로인 경우: `update` + `UpdateExpression: "SET content = :content, modified = :modified"`. 예약어와 겹치면 `ExpressionAttributeNames`에 `#` 별칭 사용. 조건이 없으므로 동시 수정 시 Last Write Wins 발생
    2. 제목이 바뀐 경우: 예전 글 조회(없으면 false) → 새 제목 글 존재 확인(있으면 false) → `{...oldPost, ...post}`로 newPost 구성 → `transactWrite`로 Delete(`attribute_exists`)와 Put(`attribute_not_exists`)을 원자적으로 실행
- `batchWrite`는 효율용 묶음 처리이고, `transactWrite`는 원자성(전부 성공 또는 전부 취소)을 보장한다는 차이
- 충돌을 로직으로 완벽히 해결할 수 없다면 클라이언트가 실패를 인지하도록 알려주는 편이 좋다
- **remove**: 조건 없이 `delete`. 이미 없는 글을 삭제해도 성공으로 처리 (필요하면 `attribute_exists` 추가)

> 책 오타 주의: p.210 별칭 예시 코드에서 `ExpressionAttributeName`의 키가 `":m"`으로 되어 있는데, 본문 설명대로 `"#m": "modified"`가 맞고 속성명도 `ExpressionAttributeNames`(복수형)이다.
> 

#### 글 목록 구현

- DynamoDB에서 최신순 목록을 얻으려면 한 파티션에 모으고 `created`를 정렬 키로 둬야 하는데 성능과 키 의미가 망가진다. 정석은 GSI
- 책에서는 동시성 제어를 보여주기 위해 다른 방식을 택한다
    - 같은 post 테이블에 title이 `$_`인 목록 문서를 두고 `Posts { title, version, entries: PostListItem[] }` 구조로 관리
    - `fetchPosts`는 문서가 없어도 `{ title: "$_", version: 0, entries: [] }`를 반환해 이후 예외 처리를 줄임
    - `list()`는 `fetchPosts().entries` 반환
- **낙관적 락**: `updateItem`에서 `ConditionExpression: "version = :version"`으로 직전 버전(`version - 1`)일 때만 갱신. 동시에 A, B가 version=1을 읽고 수정하면 먼저 쓴 쪽만 성공하고 나중 쪽은 버전 불일치로 실패
- **자동 재시도** `modifyPostEntries(modify)`
    1. 목록을 읽고 `modify` 적용 후 최신순 정렬
    2. `fast-equals`의 `deepEqual`로 변경점이 없으면 쓰기 생략
    3. 변경점이 있으면 version+1로, version이 0이면 `createItem`, 아니면 `updateItem`
    4. 조건 실패나 retryable 오류면 `continue`로 재시도, 최대 `maxRetryCount`(10)회 초과 시 throw
    - 처리 순서와 무관하게 결과가 같은 교환 법칙이 성립하면 최종적 일관성을 가진다
    - 단점은 재시도로 처리 용량을 많이 소모한다는 것. 경합이 잦으면 재시도 전 sleep으로 완화
- 생성 시 목록에 concat, 제목 변경 수정 시 예전 항목 filter 후 새 항목 concat, 삭제 시 filter

**이 방식의 한계 (책에서 직접 지적)**

- 글 작업과 목록 갱신이 트랜잭션으로 묶이지 않아 목록 갱신만 실패할 수 있다. 묶으면 목록 version이 사실상 전역 락이 되어 동시 처리 능력이 크게 떨어진다
- 생성 직후 삭제처럼 교환 법칙이 성립하지 않는 경우, 순서가 뒤바뀌면 삭제된 글이 목록에 남을 수 있다
- 항목 최대 크기 400KB 제한으로 제목 400B 가정 시 약 1천 개가 한계이고 페이징에도 부적합
- 결론: 간단하지만 신뢰성이 없는 방법이며, 제대로 하려면 GSI 기반 쿼리/스캔을 써야 한다

#### 로컬 환경과 테스트

- Localstack은 전체 기능에 비용이 들고, 로컬과 실제 환경 차이로 배포 후 문제가 생기기도 해 개발용 계정을 분리하는 경우도 많다
- **serverless-offline**: `sls plugin install --name serverless-offline`. CLI 버그로 자동 등록이 안 되면 plugins에 직접 추가하며 항상 마지막에 둔다. `sls offline`으로 3000 포트에서 API 실행
- **serverless-dynamodb-local**: plugins 순서는 `["serverless-webpack", "serverless-dynamodb-local", "serverless-offline"]`
    - `custom.dynamodb`에 `stages: ["dev"]`, `start.migrate: true`(시작 시 CloudFormation 테이블 정의 반영) 설정
    - Java(JRE 8 이상) 필요. `sls dynamodb install` 후 `sls dynamodb start`로 8000 포트 실행
    - 코드에서는 `process.env.IS_OFFLINE`이면 `region: "localhost"`, `endpoint: "http://localhost:8000"`인 DocumentClient 사용
- **curl 테스트**: 한글 본문은 `Content-Type: application/json`을 반드시 지정해야 Base64로 인코딩되어 전달되지 않는다. 경로의 한글 제목은 URL 인코딩. 생성 → 목록 → 조회 → 제목 변경 수정 → 예전 제목 404 확인 → 새 제목 조회(modified 추가 확인) → 삭제 200 → 빈 목록 순서로 확인
- **배포**: `sls deploy` 후 `API_URL`만 바꿔 동일한 curl 테스트 실행

#### 4-3 정리

- DynamoDB는 키-값 데이터를 대량으로 빠르게 처리하는 데 강하지만, 정렬 조건 스캔은 KeySchema와 파티션 구조를 이해하고 GSI를 구성해야 한다
- 공식 예제처럼 사용자 ID를 HASH, 거래일을 RANGE로 두는 구조가 잘 맞는다. 블로그라면 제목을 주 키로 두고 게시판 이름과 작성일을 HASH, RANGE로 하는 보조 색인이 나을 수 있다
- 메타데이터를 키-값으로 유지하고 큐레이션용 전시 목록을 운영하는 도메인(예: 음악 메타데이터)에는 이번 구현 방식도 활용 가능

### 4-4 MySQL 연동 (p.232까지)

**개요**

- RDS로 제공되어 사용법은 직접 설치한 MySQL과 같고 가용성은 AWS가 관리
- CloudFormation으로 인스턴스는 선언할 수 있지만 테이블 구조는 정의할 수 없다
- 인스턴스가 계속 켜져 있어야 하므로 요청 기반이 아닌 사양 기반 과금. 수평 확장이 필요하면 Aurora(더 비쌈)

**MySQLDBInstance 선언** (`AWS::RDS::DBInstance`)

- `AllocatedStorage: "5"`: 기본 standard 스토리지는 5GB~3,072GB. `StorageType`을 SSD나 IOPS로 바꾸면 최소 20GB, 가격 약 1.1배
- `DBInstanceClass: "db.t3.micro"`: T3(저렴), M5(일반), R5(메모리), X1(엔터프라이즈)
- `Engine: "MySQL"`: Aurora, MariaDB, Oracle, Postgres, SQL Server도 가능
- `DBName: "blog"`
- `MasterUsername`, `MasterUserPassword`: 환경 변수에서 주입. 비밀번호에 `/`, `@`, 큰따옴표, 공백 불가
- `PubliclyAccessible: true`: 외부 네트워크에서 접속 가능하도록 공인 주소 부여
- `DeletionPolicy: "Snapshot"`: 스택 삭제 시 스냅샷 생성 후 삭제 (Delete, Retain도 가능)

**보안상 올바른 구성 (예제에서는 생략, 7장에서 다룸)**

1. VPC 구성
2. VPC 내 서브넷 생성
3. RDS를 해당 네트워크에서 동작
4. Lambda도 같은 네트워크에서 동작 (인터넷 필요 시 인터넷 게이트웨이와 NAT 게이트웨이 추가)
5. 운영 접근용 프록시나 게이트웨이 구축
- 단점: 구성 요소와 비용 증가, 운영 접근 번거로움, Lambda 대량 실행 시 네트워크 자원 고갈 주의

**Lambda 연결**

- MySQL은 DB 내부 계정으로 권한을 관리하므로 IAM statement 불필요
- `provider.environment`에 `MYSQL_HOST`(`Fn::GetAtt`의 `Endpoint.Address`), `MYSQL_ROOT_USER`, `MYSQL_ROOT_PASSWORD` 전달
- 루트 계정 사용은 설명 편의를 위한 것이며, 실서비스라면 필요한 권한만 가진 별도 계정을 만들어야 한다

**방화벽 설정**

- 기본 VPC의 기본 보안 그룹은 아웃바운드는 전부 허용, 인바운드는 전부 차단. 따라서 `PubliclyAccessible`과 별개로 그대로는 접근 불가
- `aws ec2 describe-security-groups --group-names default`로 GroupId 확인
- `aws ec2 authorize-security-group-ingress`로 tcp 3306을 `0.0.0.0/0`에 개방
- 보안상 매우 나쁘지만 Lambda는 IP 대역을 한정하기 어려워 예제에서는 이렇게 처리. 걱정된다면 별도 VPC 안에서 Lambda와 MySQL을 함께 운영해야 한다
- 배포 후 `mysql-client`로 접속 확인

**MySQL 라이브러리**

- `mysqljs` 대신 Promise 지원이 더 좋고 타입 선언이 내장된 `mysql2` 사용 (`npm install --save mysql2`)
- 웹팩 빌드 시 `cardinal` 누락 경고가 뜨는데 실행에는 문제가 없으므로 `webpack.config.js`에서 경고 무시 설정

#### 4-4-4 CRUD 구현

**연결 관리**

- `mysql2/promise`의 `createConnection`으로 연결. host, user, password는 환경 변수, database는 `blog`
- `connectionPromise`를 전역 변수로 두어 Lambda 인스턴스가 재사용될 때 연결도 재사용 (재연결 비용 절약)
- 단점: Lambda 인스턴스가 완전히 종료되기 전까지(약 10분) 연결이 살아 있어 MySQL 입장에서는 낭비. 동시에 대량의 Lambda가 뜨면 연결이 많이 쌓인다. 이를 효율화하려면 Amazon RDS Proxy로 연결 풀을 공유
- `doQuery(dbWork)` 헬퍼: 연결을 await으로 가져와 작업 함수에 넘겨주는 구조

**함수별 구현**

- `insert`: `INSERT INTO post (title, content, created, modified) VALUES (?, ?, ?, NULL)`. `?` 파라미터 대리자로 SQL Injection 방지. `Duplicate entry` 오류만 false로 처리하고 나머지는 throw
- `select`: `SELECT * FROM post WHERE title = ?`. `execute`는 `[RowDataPacket[], FieldPacket[]]`을 반환하므로 구조 분해(`const [rows]`)로 첫 항목만 받고, 다시 `const [row]`로 첫 행만 꺼내 모델로 변환. 없으면 null
- `update`: `UPDATE post SET title = ?, content = ?, modified = ? WHERE title = ?`. MySQL은 기본 키 변경을 지원하므로 DynamoDB처럼 트랜잭션이나 삭제 후 삽입이 필요 없다. 결과 `OkPacket.affectedRows === 1`로 올바른 oldTitle로 요청했는지 검증
- `remove`: `DELETE FROM post WHERE title = ?`. 삭제 여부는 확인하지 않음 (필요하면 affectedRows 확인)
- `list`: `SELECT title, created FROM post ORDER BY created DESC`. 테이블 수준 쿼리와 정렬이 되므로 DynamoDB처럼 목록 문서를 직접 관리할 필요가 없다
- 단, 테이블을 CloudFormation으로 선언할 수 없으므로 스택 배포 후 직접 접속해 테이블을 만들어야 한다

#### 4-4-5 로컬 테스트

- MySQL은 serverless 플러그인이 없으므로 Docker로 직접 구성 (RDS와 같은 MySQL 8)
    - `docker run --rm --name mysql -p 3306:3306 -e MYSQL_ROOT_PASSWORD=... -v $PWD/mysql-data:/var/lib/mysql mysql:8`
    - `-rm`: 남은 컨테이너 삭제 후 시작 / `-name`: Ctrl+C로 안 꺼지므로 `docker kill`용 이름 지정 / `v`: 재시작해도 데이터 유지
- 클라이언트는 mysql-shell(CLI) 또는 MySQL Workbench(GUI). `mysql -h 127.0.0.1 -u root -p`
- DB 생성: `CREATE DATABASE blog CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci`
    - utf8mb4는 4바이트까지 지원해 이모지 저장 가능, unicode_ci는 general_ci보다 정확한 정렬
- 테이블: `title VARCHAR(400) NOT NULL PRIMARY KEY`, `content TEXT`, `created VARCHAR(30)`, `modified VARCHAR(30)`. `DESC post`로 구조 확인
- serverless.ts의 environment는 serverless-offline보다 먼저 평가되므로 여기서 바꾸지 않고, `storage.ts`에서 `IS_OFFLINE`이면 host `127.0.0.1`, user `root`로 접속
- `sls offline` 후 DynamoDB 때 쓰던 curl 스크립트 재사용. 끝나면 `docker kill mysql`

#### 4-4-6 ~ 4-4-8 배포, 테이블 작성, 테스트

- `sls deploy`로 API와 RDS 인스턴스 생성 (함수 크기 580kB, DynamoDB 때 17kB와 비교됨)
- `aws rds describe-db-instances`로 `Endpoint.Address` 확인. Lambda는 환경 변수로 받지만 직접 접속할 때는 이 주소를 알아야 한다
- 접속 정보는 host, user, password, database 네 가지. GUI 클라이언트의 연결 테스트로 확인하고, 실패하면 방화벽 설정부터 의심
- 로컬과 같은 `CREATE TABLE` 쿼리를 RDS에서도 실행
- API는 동일하므로 `API_URL`만 바꿔 curl 테스트

#### 4-4-9 정리

- 장점: 테이블 수준 쿼리, JOIN, 기본 키 변경 지원으로 DynamoDB보다 구현이 훨씬 간단. 인덱스와 제약 조건 추가 가능. 오랜 기간 검증되어 대부분 도메인에 활용법이 있다
- 단점: 구조를 벗어난 데이터 불가, 스키마를 CloudFormation으로 관리 불가, 수직 확장(Scale-up)만 지원해 트래픽이 높으면 샤딩이나 비싼 Aurora 필요
- 테이블을 다각도로 JOIN하거나 트랜잭션 활용도가 높다면 NoSQL보다 나은 선택. 다만 이 블로그처럼 단순한 서비스에는 과할 수 있음

### 4-5 SQLite 연동

#### 개념과 설계

- 서버가 아니라 애플리케이션에 내장되는 DB. DB 전체가 파일 하나이므로 대규모에는 부적합하지만 소규모라면 별도 DB 시스템 없이 간편
- 별도 DB 자원 없이 S3 Bucket에 DB 파일을 보관
- **읽기**: Bucket에서 파일 다운로드 → 열기 → 조회. S3 객체는 원자적으로 관리되므로(업로드 완료 전까지는 이전 파일이 보임) 읽기 중 수정 반영이 필요 없다는 가정하에 잠금 없이 처리
- **쓰기**: 두 Lambda가 같은 버전1을 받아 각자 버전2, 버전3을 올리면 늦게 올린 쪽이 덮어써서 수정 하나가 사라진다 (그림 4-5-3)
- 해결: 쓰기 시 잠금을 획득해 한 번에 하나의 수정만 허용. 잠금 비용은 DB 작업에 비해 저렴하므로 큰 문제 아님
- Lambda 자체로는 잠금 구현이 어려워 ElastiCache Redis(`cache.t3.micro`)를 사용

#### 4-5-1 자원 선언

- `S3Bucket`(`BUCKET_NAME` 환경 변수)과 `s3:PutObject`, `s3:GetObject` 권한
- `RedisInstance`: `AWS::ElastiCache::ReplicationGroup`
    - `ReplicationGroupId`: `REDIS_NAME` 환경 변수
    - `ReplicationGroupDescription`: 필수값, 한글 미지원이라 영어로
    - `CacheNodeType: cache.t3.micro` (2 vCPU, 0.5GB, SET과 DEL만 쓰므로 충분)
    - `Engine: redis`, `ReplicasPerNodeGroup: 0`, `AutomaticFailoverEnabled: false`
    - 실제 운영이라면 자동 장애 조치, `NumNodeGroups`(샤드 수), `ReplicasPerNodeGroup`(복제본 수)을 설정하지만 여기선 잠금용이라 생략
- ElastiCache는 반드시 VPC 안에 생성되며, RDS의 `PubliclyAccessible` 같은 우회 옵션이 없다. 따라서 Lambda도 그 VPC에 연결해야 한다

#### 4-5-2 VPC 설정

기본 VPC를 최대한 활용하되 일부 수정이 필요하다.

- `aws ec2 describe-vpcs`로 `IsDefault: true`인 VpcId 확인 (`jq`로 필요한 필드만 추출)
- `describe-subnets`로 가용 영역별 서브넷 ID 확인
- `describe-route-tables`: 기본 라우트는 `172.31.0.0/16 → local`, `0.0.0.0/0 → 인터넷 게이트웨이`
- **문제**: 이 규칙만으로는 서브넷 안의 Lambda가 S3와 통신할 수 없다
- **해결**: S3용 VPC 엔드포인트(Gateway 타입) 생성
    - `aws ec2 create-vpc-endpoint --service-name com.amazonaws.ap-northeast-2.s3 --vpc-id ... --route-table-id ...`
    - 라우트 테이블에 `pl-78a54011`(S3의 관리형 접두사 목록) → `vpce-...` 규칙이 자동 추가됨. S3 IP는 여러 개이고 바뀔 수 있어 접두사 목록을 사용 (DynamoDB도 마찬가지)
- 보안 그룹: 기본 보안 그룹에 Redis 포트 6379를 VPC 대역 `172.31.0.0/16`에서만 허용하는 ingress 규칙 추가
- serverless.ts
    - Redis에 `SecurityGroupIds` 지정 (서브넷을 따로 지정하지 않으면 기본 VPC 사용)
    - Lambda는 `functions`별 `vpc` 또는 `provider.vpc`로 지정. 잠금이 필요한 `createPost`, `updatePost`, `deletePost`에만 `vpc: { subnetIds, securityGroupIds }` 추가
    - 원래는 ID를 환경 변수로 관리하는 게 좋지만 설명 편의상 직접 입력

#### 4-5-3 ~ 4-5-4 SQLite 라이브러리와 Lambda Layer

- Node.js SQLite 라이브러리 중 가장 빠른 `better-sqlite3` 사용. 그런데 네이티브 의존성이 있어 웹팩 번들링이 번거롭고, 웹팩을 안 쓰면 node_modules 전체가 들어가 패키지가 커진다
- 해결: better-sqlite3만 **Lambda Layer**로 분리하고 나머지 코드는 웹팩으로 번들
    - Layer는 미리 준비된 파일 시스템 레이어로, 여러 Lambda가 공유하므로 기동 시간과 배포 시간이 줄어든다
    - Layer 생성만 목적이면 Serverless Framework보다 AWS CLI가 간단
- 절차
    1. 별도 프로젝트에서 `npm install better-sqlite3`
    2. Layer 압축 파일은 `nodejs/node_modules` 구조여야 하므로 `mkdir nodejs && mv node_modules nodejs && zip -r layer.zip nodejs`
    3. `aws lambda publish-layer-version --layer-name better-sqlite3 --zip-file fileb://./layer.zip --compatible-runtimes nodejs14.x`
    4. 반환된 `LayerVersionArn`을 `provider.layers`에 추가 (함수별 지정도 가능)
- 직접 업로드는 50MB까지, 그 이상은 S3에 올려 `-content`로 연결 (성능상 50MB 이하 권장)
- sharp 같은 네이티브 라이브러리에도 같은 방식이 유용
- 본 프로젝트에는 `better-sqlite3`와 `@types/better-sqlite3`을 설치하고, `webpack.config.js`의 `externals`에 `/better-sqlite3/` 추가 (함수 크기 178kB)

#### 4-5-5 SQLite 기반 쿼리 함수

**S3 헬퍼 3개** (사진 서비스 예제와 거의 동일)

- `s3Exists`: `headObject`. ListBucket 권한이 없으므로 파일이 없으면 404가 아닌 `Forbidden`이 와서 이걸로 판단
- `s3Download`: 해시 계산이 필요 없으므로 메모리 버퍼 대신 `getObject().createReadStream()`을 `fs.createWriteStream`으로 pipe
- `s3Upload`: `putObject`에 `fs.createReadStream` 전달 (ContentType 등 생략)

**doRead / doWrite** (그림 4-5-5)

- 공통: 객체 키 `simple-blog.db`, 로컬 경로 `os.tmpdir()` 아래
- `doRead`: 파일이 없으면 null 반환. 있으면 다운로드 후 열어서 작업하고 `finally`에서 `fs.unlinkSync`로 임시 파일 삭제. 삭제해야 Lambda 재사용 시 오래된 DB 파일을 읽는 문제를 막는다
- `doWrite`: `doInLock` 안에서 실행. 파일이 없으면(첫 요청) 새 DB를 만들고 `CREATE TABLE` 실행, 있으면 다운로드 후 열기. 작업 후 다시 업로드
- 스키마를 코드에서 생성하므로 MySQL보다 낫다고 볼 수도 있지만, 스키마 변경이나 마이그레이션이 생기면 버전 테이블을 두고 파일과 코드의 스키마 버전을 비교하는 로직을 직접 짜야 한다 (번거롭지만 스키마 히스토리 관리라는 장점도 있음)

> 책 코드 주의: p.260에서 상수는 `createTableSQL`로 선언했는데 p.261에서는 `db.exec(createTableQuery)`로 호출한다. 그대로 치면 참조 오류가 나므로 이름을 맞춰야 한다.
> 

#### 4-5-6 잠금 함수

- `@redis/client` 사용 (타입 선언 포함)
- `doInLock(work)`: `createClient`로 연결 → `acquireLock` 실패 시 throw → `work()` 실행 → `finally`에서 `DEL` 후 `quit`
- `acquireLock`: `waitTimeoutMillis`(3초) 동안 `client.set(key, value, { NX: true, PX: lockTimeoutMillis })`를 반복 시도. 실패 시 0~30ms 랜덤 sleep 후 재시도(Busy-waiting). 결과가 `OK`면 획득
- `lockTimeoutMillis`(5초) 지나면 TTL로 자동 해제
- `RedisClientType`은 라이브러리 제네릭이 복잡해 `ReturnType<typeof createClient>`로 꺼내 씀

**책이 짚는 고민거리**

1. 동시 요청이 너무 많으면 잠금을 못 얻고 Lambda timeout 발생 → 정해진 시간 내에서만 재시도하는 게 낫다
2. 잠금을 쥔 채 Lambda가 timeout으로 죽으면 영원히 잠김 → TTL 필요
3. 작업이 TTL보다 오래 걸리면 다른 Lambda가 임계 구역에 진입하고, 원래 Lambda가 나중에 남의 잠금까지 지워버릴 수 있다
4. Redis가 재시작되며 잠금 상태를 잃으면 중복 진입 가능
- 완벽하게 하려면 제대로 된 분산 잠금이 필요하지만, 동시 수정이 적은 도메인이라면 대기 최대 시간과 잠금 유지 최대 시간 두 가지 설정으로 충분하다는 입장

> 책 본문 주의: 본문은 SETEX 명령과 EX 옵션으로 설명하지만 실제 코드는 `SET`에 `NX`(없을 때만 쓰기)와 `PX`(밀리초 TTL)를 쓴다. 존재하지 않을 때만 삽입하는 옵션은 EX가 아니라 NX가 맞다. 그리고 3번 문제는 잠금 값에 고유 토큰을 넣고 해제할 때 값이 내 것인지 확인 후 지우는 방식(Lua 스크립트)으로 상당 부분 막을 수 있다.
> 

#### 4-5-7 CRUD 함수

- DB 연결과 동시성 제어가 준비되면 MySQL 구현과 거의 같다
- 파라미터 대리자는 `?` 대신 `@NAME`. `prepare(sql)` 후 `run(객체)`로 객체 속성값을 매핑
- `insert`: `UNIQUE constraint failed: post.title` 오류면 false
- `select`: `get({ title })`, 모델 이름이 컬럼과 같아 변환 없이 반환. 없으면 null
- `update`: `run({ ...post, oldTitle })`, `RunResult.changes === 1`로 검증
- `remove`: `DELETE ... WHERE title = @title`
- `list`: `ORDER BY created DESC`와 `all()`. 파일이 없어 null이면 빈 배열
- better-sqlite3가 인자와 결과를 JSON 객체로 다뤄 코드가 더 간단하고, 파일이 없으면 테이블까지 새로 만드므로 새 환경 구축 시 MySQL보다 신경 쓸 게 적다

#### 4-5-8 ~ 4-5-10 로컬 환경과 테스트

**로컬 S3 선택지**

- LocalStack: 거의 모든 AWS 서비스 지원, `serverless-localstack` 플러그인 있음. 하지만 ElastiCache, RDS, API Gateway V2 등 절반 이상이 유료
- MinIO: S3 호환, 커뮤니티판 무료, 웹 UI 제공. 단 Serverless 플러그인이 없어 Docker로 직접 관리
- serverless-s3-local: Node.js로 만든 s3rver 사용. 기본 설정으로 충분해 가장 간편
- 개인 개발은 serverless-s3-local, 공용 테스트 환경은 MinIO, 여러 AWS 자원이 필요하면 LocalStack

**serverless-s3-local 설정**

- `sls plugin install --name serverless-s3-local`, plugins는 `["serverless-webpack", "serverless-s3-local", "serverless-offline"]` 순서
- `IS_OFFLINE`이면 `accessKeyId`/`secretAccessKey`를 `S3RVER`, `endpoint: http://localhost:4569`, `s3ForcePathStyle: true`
- 파일은 `buckets/BUCKET_NAME/OBJECT_KEY._S3rver_object` 형태로 메타데이터, 본문, md5가 저장됨

**로컬 Redis**

- `docker run --rm --name redis -it -p 6379:6379 redis:6`
- `IS_OFFLINE`이면 `127.0.0.1`, 아니면 `REDIS_HOST`로 접속 (암호 설정이 없어 다른 차이 없음)
- `sls offline` 후 같은 curl 스크립트로 테스트, 끝나면 Ctrl+C

#### 4-5-11 배포

- `sls deploy`로 API, S3 Bucket, ElastiCache Redis 생성. curl 테스트는 동일

#### 4-5-12 느린 응답 시간

- 첫 요청이 1초 이상 걸린다. Layer 설정, Redis 통신, S3 다운로드와 업로드 시간이 겹치기 때문
- 구간별 시간을 보려면 AWS X-Ray(분산 추적)를 써야 하며, 책에서는 REST API에서만 가능하다고 설명하고 이후 REST API 단원에서 다룬다

#### 4-5-13 응용 (Lambda + SQLite를 더 잘 쓰는 법)

1. 수정이 극히 적다면: Lambda 초기화 시 한 번만 DB 파일을 받아 인스턴스가 재사용되는 동안 계속 사용. 이후 응답이 매우 빠름
2. 수정이 아예 없다면: DB 파일을 코드와 함께 배포. S3 통신과 비용이 0. 데이터가 바뀔 때마다 재배포
3. 수정이 많다면: 잠금 대기가 길어지므로 액터 모델 도입. 잠금을 가진 Lambda에게 다른 Lambda가 작업을 위임 (7장에서 상세히)
- 데이터가 정적이거나, 드물게 수정되거나, 배치로 주기적으로 생성되고, JSON이나 CSV로 다루기엔 구조가 복잡할 때 좋은 선택

#### 4-5-14 정리

- 장점: 관계형 구조와 JOIN 지원, DB 파일 하나를 S3에 두고 필요할 때 받아 쓰므로 비용과 자원 절약
- 단점: 일정 규모 이상 데이터 처리 어려움, 스키마 관리를 로직으로 해야 함, 다운로드와 업로드로 지연 발생, 잠금을 위해 Redis와 VPC 구성 필요
- 수정이 드물거나 접근이 드물거나 조회만 하는 경우(예: 배치 분석 결과를 SQLite로 만들어 조회 API 제공) API Gateway, Lambda, S3만으로 매우 효율적
- 단순 CRUD는 키-JSON으로도 충분하지만 목록 관리에는 DB가 편하다. MySQL은 빠르지만 비싸므로 약간의 지연을 허용한다면 SQLite + S3로 저비용 시스템 가능

### 4-6 저장소 비교

#### 4-6-1 응답 지연 시간

- **DynamoDB**: 키 해시로 파티션에 분산하므로 특정 파티션에 부하가 몰리지 않는 한 요청량이 많아도 일정한 응답 시간. AWS 문서 기준 10ms 미만. 키-값으로 관리 가능하고 키 해시를 잘 설계하면 지연 시간 측면에서 최선
- **MySQL**: 대부분 빠르지만 복잡한 쿼리에서 지연이 생기지 않도록 인덱스 추가, 실행 계획 조정, 구조 변경 같은 꾸준한 관리가 필요. 데이터가 많아지면 샤딩, 요청이 몰리면 CPU와 메모리 부족 문제. DynamoDB는 이런 부분을 대신 관리해주지만 MySQL은 직접 해야 함. 잘 관리하면 복잡한 쿼리 패턴에서도 빠름
- **SQLite**: 애플리케이션과 같은 주소 공간에서 실행되므로 쿼리 자체는 매우 빠름. 하지만 S3와 Lambda 사이 통신이 늘 수십 ms 이상이고 잠금까지 쓰므로 최소 100ms 이상. EFS로 줄일 수는 있지만 다운로드 시간을 완전히 없애진 못함

#### 4-6-2 비용

- **DynamoDB**: 읽기, 쓰기 요청과 저장 용량에 과금. 프로비저닝이 온디맨드보다 저렴
    - 책 기준 온디맨드: 100만 읽기 0.27USD, 100만 쓰기 약 1.36USD, 스토리지 1GB-월 0.27USD
    - RCU 1은 4KB 이하 최종적 일관 읽기 2개, WCU 1은 1KB 이하 쓰기 1개이므로 데이터 크기에 따라 비용이 달라짐
- **MySQL**: 항상 켜진 인스턴스의 시간당 비용(가장 저렴 0.025USD, 가장 비싼 13.68USD)과 스토리지(범용 1GB-월 0.131USD). 꾸준한 대량 요청이면 DynamoDB보다 저렴해질 수 있음. 다만 보통은 도메인과 쿼리 패턴으로 DB를 고르므로 비용 비교의 의미는 크지 않다는 입장
- **SQLite**: 자체 비용은 없고 S3와 Lambda 실행 시간이 비용. Redis는 프리티어 수준이라 제외
    - S3: 100만 읽기 0.35USD, 100만 쓰기 4.5USD. DB 파일이 아주 커질 수 없으니 스토리지 비용은 무시 가능
    - Lambda: 1GB 인스턴스를 100ms씩 100만 회 실행 시 1.33USD
    - 데이터 크기와 무관하게 비용이 일정. 1KB 수준이면 DynamoDB가 싸지만 그보다 크면 이쪽이 저렴. 관계형 기능을 요청당 과금으로 쓸 수 있다는 점이 특징

#### 4-6-3 유지 보수

- **DynamoDB**: 테이블 구조가 없어 자유롭게 넣을 수 있는 대신, 읽는 쪽에서 타입이나 버전 같은 메타데이터로 최신 형태로 변환하는 로직을 두거나 마이그레이션 배치를 운영. 관리 콘솔 웹 UI로 값 확인과 수정 가능
- **MySQL**: 구조 변경 시 모든 데이터가 새 구조를 만족하도록 마이그레이션과 상하위 호환성을 신경 써야 함. 대신 읽을 때 항상 기대한 형태가 보장되어 편함. AWS 웹 UI는 없지만 mysql-shell, Workbench 등 도구가 많음. VPC 내부 인스턴스라면 프록시가 필요해 수고가 늘어남
- **SQLite**: 접근 도구가 부족하고, S3 파일을 받아 수정 후 올리는 동안 다른 Lambda가 새 버전을 올릴 수 있어 직접 수정이 어려움. 운영 작업으로 잠금을 오래 쥐면 서비스에 영향. 그래서 스키마 변경과 마이그레이션을 애플리케이션 코드 로직으로 처리하고 하위 호환을 위해 과거 버전 로직도 유지해야 해서 운영이 가장 까다롭게 느껴질 수 있음

#### 4-6-4 유리한 시나리오

- **DynamoDB**: 대량 데이터를 키-값으로 보관할 수 있을 때. 문서는 400KB 제한 내에서 적절한 크기를 유지하고, 참조할 다른 문서의 키 집합을 직접 관리해도 되는 경우. 데이터 개수는 많지만 열람은 적은 도메인(음악, 영화, 도서, 쇼핑처럼 유일 키가 있고 일부만 전시하는 경우). 어떻게 진화할지 모르는 전시 데이터는 NoSQL이 낫다
- **MySQL**: 데이터가 항상 최신 구조를 유지해야 하고 관계를 엮어 조회하거나 함께 갱신해야 하는 경우. 정규화가 필요한 복잡한 도메인(회원 정보, 결제). 단 이 경우에도 과거 데이터나 변경 이력은 더 이상 바뀌지 않으므로 DynamoDB 같은 NoSQL이 나을 수 있음
- **SQLite + S3**: 관계형 특성은 필요하지만 별도 시스템 운영이 번거로울 때. 수정이 적거나 없거나 오프라인으로 미리 DB 파일을 만들어둘 수 있을 때. 몇 MB 수준이면 코드와 함께 배포해 응답 시간 개선. 요청당 과금 관계형 DB나 미리 계산된 데이터 조회에 유용

### 4-7 프론트엔드 연동

#### 도입과 프로젝트 생성

#### 4-7-4 서버 API 연동

- `fetch`로 비동기 호출. `.json()`은 `Promise<any>`이므로 반환 타입을 직접 명시해 암시적 형 변환
- `fetchPostListItems()`: `GET /api/post` → `PostListItem[]`
- `fetchPost(title)`: `GET /api/post/${title}` → `Post`. URL 인코딩은 브라우저가 처리
- `formatDate`: ISO 문자열을 `Date.parse`로 타임스탬프로 바꾼 뒤 `toLocaleString("ko")`로 변환 (date-fns 같은 의존성 추가를 피함)
- `createPost(title, content)`: `POST`, `Content-Type: application/json` 헤더와 `JSON.stringify` 본문
- `updatePost(oldTitle, title, content)`: 주소에는 예전 제목, 본문에는 새 제목
- `deletePost(title)`: 본문 없이 `response.ok`로 성공 판단, 실패 시 Error throw

#### 4-7-5 컴포넌트 구현

- **PostList**: 상태 없는 컴포넌트. `postItems`, `onView`, `onNew`를 속성으로 받음. `ul > li`로 목록을 그리고 클릭 이벤트는 외부로 위임. 반복 생성되는 li는 `key`에 고유값(title) 지정 필요 (가상 DOM 갱신 판단에 사용)
- **DateField**: `dt`/`dd`를 묶는 재사용 컴포넌트. date가 없으면 null 반환(React는 null, false를 렌더링하지 않음). `<></>`(React.Fragment)로 감싸 감싸는 요소 없이 집합 반환
- **Viewer**: 상태 없이 글 정보를 렌더링. 생성/수정 일시는 DateField, 본문 줄바꿈은 `react-nl2br`로 br 변환. 목록, 수정 버튼 이벤트는 위임
- **Editor**: 생성과 수정 모두 지원(post가 있으면 수정, null이면 생성). `React.useState`로 title, content 상태 관리. 초기값 표시는 `value`가 아닌 `defaultValue`, 변경은 `onChange`로 상태 갱신. 삭제 버튼은 `post &&`로 수정 시에만 노출. Ref로 DOM에 직접 접근하는 방법도 있지만 부득이한 경우가 아니면 비권장
- **App**: 세 가지 상태로 화면 전환
    - `postItems`: 글 목록
    - `post`: 현재 글
    - `editMode`: 보기/편집 모드
    - `useEffect(fn, [])`로 마운트 시점에 목록 조회
    - 분기: 편집 모드가 아니면 post 유무에 따라 Viewer 또는 PostList, 편집 모드면 Editor
    - 저장 시 post가 있으면 `updatePost(post.title, ...)`, 없으면 `createPost`. 성공 후 글 재조회, 보기 모드 전환, 목록 갱신. 오류 처리는 간결함을 위해 alert로 대신
    - 삭제 성공 시 post 초기화, 보기 모드 전환, 목록 갱신

#### 4-7-6 프록시 서버

- API는 `localhost:3000`, 웹은 `localhost:3001`이면 출처가 달라 CORS 오류 발생
- 개발 서버의 프록시 기능 사용: `package.json`에 `"proxy": "http://localhost:3000"`을 넣으면 개발 서버가 모르는 주소 요청을 API 서버로 위임
- 나중에 인증처럼 로컬에서 처리하기 힘든 부분이 있을 때 proxy에 AWS 배포 주소를 넣어 쓸 수도 있음

#### 4-7-7 개발 서버 시작

- serverless-offline과 개발 서버가 둘 다 3000을 써서 충돌. 매번 Y를 누르는 대신 `sls offline --httpPort 8000` 또는 `PORT=4000 npm start`
- `package.json`의 `scripts.start`에 `PORT=4000 react-scripts start`, Windows 호환은 `cross-env` 사용

#### 4-7-8 주소 기반 라우트

- 지금 구조는 SPA라 주소가 바뀌지 않음. 새로 고침 시 상태 초기화, 글 주소 공유 불가, 검색 엔진 참조 불가 문제
- `react-router-dom` 도입 (타입 내장)
- 주소 설계
    - 글 목록: `/`
    - 글 보기: `/글-주소`
    - 새 글: `/_new` (그래서 `_new`라는 제목은 쓸 수 없지만 설명 편의상 유지)
    - 글 수정: `/글-주소/edit`
- 이벤트 위임 대신 `Link`로 이동. 전체 페이지를 새로 받는 href 대신 필요한 부분만 갱신
- 페이지 컴포넌트 분리
    - `PostListPage`: 목록 조회 후 PostList 렌더링
    - `PostViewPage`: `useParams`로 title을 얻어 조회. 준비 전이면 불러오는 중 표시. 의존 배열에 `[title]`을 넣어야 같은 컴포넌트가 재사용될 때 주소 변경에 맞춰 다시 조회
    - `PostNewPage`: post는 null. 저장 후 `navigate(/${title}, { replace: true })`로 생성 페이지를 히스토리에 남기지 않음. 취소는 `navigate(-1)`, 삭제는 빈 함수
    - `PostEditPage`: 조회 로직과 Editor를 함께 가짐. 저장 후 replace로 글 페이지 이동, 삭제 후 `/`로 replace 이동
- App은 `BrowserRouter > Routes > Route`로 구성. `:title`로 주소 변수 선언, `element`로 컴포넌트 지정, `path="*"`는 일치하지 않는 모든 주소(`/` 포함)를 목록 페이지로
- 이제 새로 고침이나 다른 브라우저에서 주소를 열어도 정상 동작. 단, 정적 파일 서버에서는 해당 주소에 실제 파일이 없어 접근이 안 되는 문제가 있고 이는 배포 단원에서 다룸

> 책 코드 주의: p.302의 import에 `Switch`가 있는데 코드에서는 `Routes`를 쓴다. react-router v6에서는 `Switch`가 없어졌으므로 `import { BrowserRouter, Route, Routes }`로 바꿔야 한다. 그리고 p.286의 `npm install --save add react-nl2br`에서 `add`는 불필요한 오타다.
> 

#### 4-7-9 ~ 4-7-10 빌드와 로컬 테스트

- `npm run build`로 최적화된 HTML, CSS, JS를 `build` 디렉터리에 생성. 정적 파일이라 로직 없는 정적 파일 서버로 제공 가능
- `npm install -g serve` 후 `serve -p 5000 -s build`로 확인
- 그런데 모든 API 요청이 실패. serve에는 프록시 기능이 없어서 `/api/post`가 `localhost:5000/api/post`로 가기 때문

#### 4-7-11 서버 주소 문제 해결

- 서버 주소가 달라야 하는 세 상황
    1. `npm start`로 프록시 연결: `/api/post`
    2. 로컬 빌드를 serve로 띄워 로컬 API와 테스트: `http://localhost:3000/api/post`
    3. 빌드 결과를 서버리스 스택에 올려 배포: `https://API_GATEWAY/api/post`
- 다른 출처면 CORS 문제가 있지만 브라우저가 로컬 자원은 예외 처리하므로 여기서는 주소 문제만 해결 (CORS는 S3와 CloudFront 배포 때 다룸)
- CRA는 `REACT_APP_` 접두사 환경 변수를 빌드 시 실제 값으로 치환. `fetch(${process.env.REACT_APP_SERVER}/api/post)`
- `package.json` scripts
    - `start`: `cross-env PORT=4000 REACT_APP_SERVER= react-scripts start` (빈 값이라 프록시 사용)
    - `build:local`: `REACT_APP_SERVER=http://localhost:3000`
    - `build`: `REACT_APP_SERVER=https://API_GATEWAY`

- 빌드 결과를 서버리스로 제공하는 방법은 두 가지

    2. API 서버리스 스택에 포함해 API Gateway와 Lambda가 HTML, CSS, JS를 직접 반환

#### serverless.ts

- Lambda가 없는 스택이라 provider에 런타임 생략
- 타입 라이브러리 없이 `export =`로 바로 노출. 오류가 나면 `tsconfig.json`에 `"module": "commonjs"`
- `custom.s3Sync`
    - `bucketName`: `WEBSITE_BUCKET_NAME` 환경 변수
    - `localDir`: `../blog-pages/build`
    - `params`: 파일 패턴별 메타데이터. `index.html`은 `Cache-Control: no-cache`, `static/**/*`는 `public, max-age=31536000`(1년)
- Content-Type은 플러그인이 자동 설정. 그 외 헤더가 없으면 no-cache로 동작하거나 CloudFront 설정을 따름. React 빌드의 static 파일은 해시가 붙어 있어 오래 캐시해도 됨

#### 자원 선언 (s3-cloudfront.ts)

- **OAI**: `AWS::CloudFront::CloudFrontOriginAccessIdentity`, Comment만 지정
- **BlogStaticFileBucket**: BucketName만 지정 (사진 서비스의 Lifecycle, AccelerateConfiguration은 불필요)
- **BlogStaticFileBucketOAIPolicy**: OAI의 `S3CanonicalUserId`에 `s3:GetObject` 허용. 하나의 Bucket에 여러 사이트가 있다면 `/*` 대신 `/PREFIX/*`로 제한
- **S3Origin**: Id `S3Origin`, DomainName은 `${WEBSITE_BUCKET_NAME}.s3.ap-northeast-2.amazonaws.com`, `OriginAccessIdentity`는 `Fn::Join`으로 `origin-access-identity/cloudfront/{OAI}` 구성
- **캐시 동작**: 사진 서비스와 달리 이번엔 구성. `DefaultCacheBehavior`와 경로별 `CacheBehaviors`가 있으며, 오리진이 S3 하나뿐이면 `DefaultCacheBehavior`만으로 충분
    - `TargetOriginId: "S3Origin"`, `ViewerProtocolPolicy: "redirect-to-https"`

#### 캐시 정책과 압축

- CloudFront는 어떤 캐시 키와 TTL을 쓸지 `CachePolicy`로 관리. `aws cloudfront create-cache-policy`로 만들거나 관리형 정책 사용 (`list-cache-policies`에서 Type이 managed인 항목)
- 이 예제는 `CachingOptimized`(`658327ea-...`) 사용. 캐시 키에 포함되는 값을 최소화해 효율을 높이되, `Accept-Encoding`은 포함해 압축 형식별로 따로 캐시
- `Compress: true`를 켜면 브라우저가 지원할 때 압축된 콘텐츠 전송
- 캐시 누락 시 오리진에는 URL, 본문, 일부 기본 헤더만 전달되고 쿼리 문자열, 기타 헤더, 쿠키는 빠짐. 필요하면 `OriginRequestPolicy`를 만들거나 관리형(`UserAgentRefererHeaders`, `CORS-S3Origin` 등)을 `OriginRequestPolicyId`로 연결. 이 예제는 불필요해서 설정 안 함

#### 도메인과 인증서

- 사진 서비스와 같은 환경 변수 방식. `SUB_DOMAIN=blog`, `ROOT_DOMAIN=lacti.link`로 `blog.lacti.link` 사용
- `ACM_CERTIFICATE_ARN`은 사진 서비스와 동일 (확인은 `aws --region us-east-1 acm list-certificates`)
- `ViewerCertificate`: `MinimumProtocolVersion: TLSv1.2_2021`, `SslSupportMethod: sni-only`

#### SPA 라우팅 처리

- react-router는 실제 파일이 없는 경로도 index.html의 JS가 해석해서 화면을 구성. 그래서 `/처음-쓰는-글` 같은 주소로 들어와도 일단 index.html이 내려가야 함
- 정적 파일 라우팅은 서버가, 글 같은 동적 주소는 JS가 처리
- S3에 없는 객체는 ListBucket 권한이 없어 403이 나므로, `CustomErrorResponses`로 403을 200 + `/index.html`로 바꿔줌. `ResponsePagePath`는 반드시 `/`로 시작

#### 4-8-2 CORS 문제 해결

- CORS는 다른 출처의 리소스 접근을 막는 브라우저 안전 장치
    - 단순 요청(Simple request): 응답에 CORS 헤더를 붙여 허용 여부 알림
    - 프리플라이트 요청(Preflighted request): 먼저 `OPTIONS`로 허용 여부 확인
- 요청자는 `Origin` 헤더를 보내고 서버는 `Access-Control-Allow-Origin`으로 응답. 없으면 브라우저가 요청을 취소
- 관련 헤더와 HTTP API 설정 속성
    - `Access-Control-Allow-Origin`: `allowedOrigins`
    - `Access-Control-Allow-Headers`: `allowedHeaders`
    - `Access-Control-Allow-Methods`: `allowedMethods`
    - `Access-Control-Allow-Credentials`: `allowCredentials` (쿠키나 Authorization 전송 허용)
- 직접 구현하면 모든 함수에 헤더를 넣고 OPTIONS 함수도 추가해야 하지만, `provider.httpApi.cors`로 간단히 해결
    - `allowedOrigins: [process.env.CORS_ALLOW_ORIGIN]`, 메소드 GET/POST/PUT/DELETE, 헤더 `Content-Type`, `allowCredentials: true`
- HTTP API는 API 단위로만 CORS 설정. 함수별로 하려면 REST API나 직접 구현
- 개발 중에 로 열어도 상용에서는 반드시 서비스 도메인으로 한정
- 확인 방법
    - `aws apigatewayv2 get-api --api-id API_ID`의 `CorsConfiguration`
    - `curl -v -XOPTIONS`에 `access-control-request-method`, `access-control-request-headers`, `origin`을 넣어 204 응답과 allow 헤더 확인. 잘못된 오리진이면 allow 헤더가 빠짐

#### 4-8-3 배포

- `cdn-stack`에서 `sls deploy`: CloudFormation 자원 생성 후 s3-sync로 빌드 결과 업로드
- 인프라 변경 없이 웹 페이지만 바꿀 때는 `sls s3sync`가 훨씬 빠름

### 4-9 CloudFront의 다중 오리진 사용

#### 문제의식

1. CloudFront 웹과 API Gateway의 주소가 달라 빌드 시 API 주소 주입과 CORS 대응이 번거로움
2. HTTP API는 리전 API만 지원해서 엣지 로케이션의 이점이 없음. 엣지 최적화는 REST API 전용
- REST 엣지 최적화로 2번은 풀려도 1번(도메인 분리)은 남으므로, AWS 문서는 CloudFront 배포에 API Gateway를 오리진으로 추가하는 방식을 권장

#### 구성 변경 (s3-cloudfront.ts)

- 단일 오리진: 브라우저가 CORS 검증 후 JS로 API Gateway에 요청
- 다중 오리진: `/api/*`는 API Gateway, 나머지는 S3로. 같은 도메인이라 CORS 불필요. 대신 CloudFront 전송 요금과 API Gateway 전달 비용 추가
- `APIOrigin`: DomainName은 API 주소, `OriginProtocolPolicy: https-only`, `OriginSSLProtocols: ["TLSv1.2"]`
- `APIOriginCacheBehavior`
    - `PathPattern: /api/*`
    - `ViewerProtocolPolicy: https-only` (페이지가 이미 HTTPS로 리다이렉트되므로 충분)
    - `AllowedMethods`: 세 옵션 중 GET, HEAD, OPTIONS, PUT, PATCH, POST, DELETE 전체
    - `CachePolicyId`: 관리형 `CachingDisabled`(`4135ea2d-...`)로 모든 요청을 그대로 전달
- 배포 설정에 `Origins: [S3Origin, APIOrigin]`, `CacheBehaviors: [APIOriginCacheBehavior]` 추가

#### 4-9-1 ~ 4-9-2 서버 주소와 배포

- `build`의 `REACT_APP_SERVER`를 빈 값으로 두어 상대 경로(`GET /api/post`)로 요청
- `blog-pages`에서 빌드 후 `cdn-stack`에서 `sls deploy`

#### 4-9-3 동작 이해

- 경로 패턴이 있는 동작(`CacheBehaviors[0]`, APIOrigin)이 우선순위가 높고 기본 동작(S3Origin)이 마지막
- 오리진이 오류를 응답하면 CustomErrorResponses의 페이지 경로를 기본 동작 오리진에 요청하므로, 다중 오리진과 오류 페이지를 함께 쓸 때 의도치 않은 페이지가 나가지 않게 주의

#### 4-9-4 장점과 단점

- 장점: 정적 페이지 제공에 가장 비용 효율적. index.html 외에는 Cache-Control로 브라우저 캐시 극대화, 압축, 전 세계 엣지 활용
- 단점: 배포용 스택이 추가로 필요하고, 도메인을 맞추려면 다중 오리진 설정이 필요. 계정당 S3 Bucket과 CloudFront 배포 수 제한 때문에 서비스마다 이렇게 만들면 자원이 고갈될 수 있음
- 대안: 하나의 Bucket에 여러 프로젝트를 넣고 Lambda@Edge로 파일을 고르는 방식 (서브 도메인별 서비스에 적합하지만 운영 도구용으로는 번거로움). 이런 경우 API 스택에 웹 페이지를 함께 배포하는 편이 나을 수 있음

### 4-10 API Gateway에서 웹 페이지 제공

- API Gateway는 HTML, CSS, JS, 이미지 같은 바이너리도 응답 가능. API와 웹 페이지를 같은 스택으로 제공할 수 있어 편리
- 다만 API Gateway 응답 비용과 Lambda 파일 처리 비용이 CloudFront + S3보다 비싸므로, 트래픽 많은 상용보다는 사내 운영툴이나 개발자 도구에 적합
- `serverless-aws-static-file-handler` 플러그인도 있지만 타입 정의가 없어 직접 구현

#### 의존성과 serveStatic 함수

- `mime-types`(+ `@types/mime-types`)로 Content-Type 결정, `serverless-plugin-scripts`로 빌드 시 복사 명령 실행
- `staticHandler.ts`의 `serveStatic`으로 분리해서 각 함수가 필요한 패키지만 갖도록 (첫 기동 시간 이득)
- 동작
    - `event.rawPath`가 `/`면 `index.html`, 아니면 `pages` 디렉터리에서 해당 파일
    - 파일이 없으면 `index.html` 반환 (JS 라우팅으로 글 페이지 처리)
- 바이너리 응답 규칙: Lambda는 문자열만 반환할 수 있으므로
    1. 바이너리는 Base64로 인코딩
    2. `isBase64Encoded: true`
    3. `Content-Type`에 적절한 MIME 타입
- `.css, .html, .js, .json, .map, .svg, .txt`만 텍스트로 보고 나머지는 base64. 모르는 타입은 `application/octet-stream`
- 캐시 정책은 CloudFront와 동일 (index.html은 no-cache, 나머지 1년)

#### 4-10-1 서버리스 스택 설정

- SQLite 예제라 Lambda Layer가 provider에 공용으로 걸려 있었는데, serveStatic은 better-sqlite3가 불필요하므로 `layers`를 각 함수로 옮김
- `serveStatic` 이벤트는 가장 마지막에 선언 (경로가 겹치면 선언 순서대로 우선)
    - `/`, `/{fileName}`, `/static/{type}/{fileName}` 세 경로만 등록해 잘못된 요청에 Lambda가 불필요하게 실행되는 것을 막음
- 프론트엔드 결과물이 포함되어 크기가 커지므로 `package.individually: true`로 함수별 패키지 분리
- `custom.scripts.hooks["webpack:package:packExternalModules"]`에서 `[ -d .webpack/serveStatic ] && cp -r ../blog-pages/build .webpack/serveStatic/pages || true`
    - `sls deploy function -f`로 일부 함수만 배포할 때를 대비해 디렉터리 존재 여부 확인
    - exitcode가 0이 아니면 배포가 실패하므로 `|| true`

#### 4-10-2 ~ 4-10-3 서버 주소와 배포

- 같은 도메인이므로 `REACT_APP_SERVER`는 빈 값
- `sls deploy`로 `GET /`, `/{fileName}`, `/static/{type}/{fileName}` 추가
- 프론트엔드만 바뀌었으면 `npm run build` 후 `sls deploy function -f serveStatic`으로 빠르게 배포

#### 4-10-4 도메인 연결

- `serverless-domain-manager` 플러그인 사용. `custom.customDomain`
    - `apiType`: http, rest, websocket 중 선택
    - `domainName: bloga.lacti.link` (blog는 CloudFront가 사용 중)
    - `certificateName: lacti.link` (`.lacti.link`를 포함한 인증서를 찾음. 못 찾으면 `certificateArn`으로 직접 지정)
    - `endpointType: regional` (HTTP API는 리전만 가능)
    - `createRoute53Record: true`로 A, AAAA 레코드 자동 생성
- `sls create_domain`으로 사용자 지정 도메인 생성 (엣지 최적화는 오래 걸리지만 리전은 금방)
- 도메인 생성과 API 연결이 분리된 이유는 하나의 도메인에 여러 API를 API mapping으로 붙일 수 있기 때문 (예: `api.lacti.link/auth`, `/log`)
- `sls deploy`를 해야 API가 도메인에 연결됨. API mapping 없이(none) 연결되면 모든 요청이 그 API로 감

#### basePath와 스테이지 주의점

- HTTP API는 스테이지를 지정하지 않으면 `$default`를 쓰지만, REST API는 기본 스테이지가 없어 주소 앞에 스테이지가 붙음
    - Auth API(`$default`): `GET /test` → 실제 `/test`
    - Game API(`prod`): `GET /profile` → 실제 `/prod/profile`
- 사용자 지정 도메인은 basePath와 스테이지를 함께 매핑해 실제 주소를 감출 수 있음
    - `/auth` + `$default`: `domain/auth/test` ↔ `AUTH.API/test`
    - `/game` + `prod`: `domain/game/profile` ↔ `GAME.API/prod/profile`
- 문제는 Lambda가 받는 `rawPath`가 접근 경로에 따라 달라진다는 점 (`/auth/test` vs `/test`). serveStatic처럼 경로를 직접 해석한다면 주의
- 대책: `aws apigatewayv2 update-api --disable-execute-api-endpoint`로 기본 주소를 막거나, serverless-offline의 `-noPrependStageInUrl`과 코드 처리로 통일

### 4-11 REST API 사용

#### REST API만의 기능

1. VPC 엔드포인트로 프라이빗 API
2. AWS WAF 연동
3. API 수준 캐시
4. 응답 압축 (`minimumCompressionSize`)
5. 바이너리 미디어 유형 지정
6. AWS X-Ray 분산 추적 (API Gateway가 느린지 Lambda가 느린지, 초기화 문제인지 코드 문제인지 구분)
7. 사용량 계획(Usage Plan)과 API 키
    - 사용량 계획: 속도(Rate), 버스트(Burst), 일/주/월 할당(Quota)을 API 집합(배포 + 스테이지)에 적용. 메소드와 경로 수준 규칙도 가능
    - API 키: `X-API-Key` 헤더로 보내면 연결된 사용량 계획 기준으로 허용 여부 결정

#### 4-11-1 서버리스 스택 변경

- 모든 함수 이벤트의 `httpApi`를 `http`로 변경
- HTTP API는 Content-Type을 보고 알아서 바이너리로 바꿨지만 REST API는 `provider.apiGateway.binaryMediaTypes: ["image/*"]` 명시 필요
- `minimumCompressionSize: 1024`로 1KB 이상 응답 압축
- customDomain은 `apiType: rest`, `endpointType: edge`, 도메인은 `blogb.lacti.link`

#### 4-11-2 코드 변경

- REST API는 집필 시점 기준 API Gateway V1만 지원하므로 모든 함수를 V1 형식으로
- 타입: `APIGatewayProxyHandlerV2` → `APIGatewayProxyHandler`
- 반환값(`APIGatewayProxyResult`)
    1. 반드시 `statusCode`와 `body`(string) 포함
    2. 필요하면 `headers`, `multiValueHeaders`
    3. 바이너리는 Base64 + `isBase64Encoded: true`
- V2는 객체를 반환하면 알아서 200 + body로 바꿨지만 V1은 `{ statusCode: 200, body: JSON.stringify(post) }`로 직접 구성. 404도 body 필요. listPosts도 await 후 stringify
- 요청 차이
    - 경로 파라미터 URL 디코딩: V2는 자동, V1은 `decodeURIComponent` 직접 호출 (readPost, updatePost, deletePost 모두)
    - 경로: V2는 `event.rawPath`, V1은 `event.path` (serveStatic 수정)
- 운영 팁: 호환성이 완벽하다는 확신이 없으면 기존 스택을 두고 REST API 스택을 새로 배포해 검증한 뒤 Route53 레코드를 바꾸는 편이 안전. 단 S3, Redis 같은 자원 소유권이 예전 스택에 남으므로, 처음부터 의존 자원 스택을 API와 분리하는 것도 방법

#### 4-11-3 로컬 테스트

- SQLite 로컬 환경 재사용 (Docker Redis + serverless-offline)
- REST API는 스테이지 필수. `provider.stage`로 지정하며 기본값 dev
- 주소에 스테이지 접두사가 붙음 (`GET /dev/api/post`). 사용자 지정 도메인으로 숨길 수 있음
- serverless-offline도 같은 규칙. 로컬과 배포의 주소 체계를 맞추려면 `-noPrependStageInUrl`. 상용에서 스테이지를 노출하면 개발 버전 주소를 유추한 공격이 가능하므로 숨기는 게 좋음

#### 4-11-4 X-Ray 추가

- 통합 패키지 `aws-xray-sdk` 대신 필요한 기능만 있는 `aws-xray-sdk-core@3.3.1` 설치 (3.3.2부터는 AWS SDK V3를 참조. 당시 Lambda 런타임은 V2만 내장이라 V2를 써야 패키지에서 SDK를 뺄 수 있었음)
- `provider.tracing: { apiGateway: true, lambda: true }`
- AWS 클라이언트 추적
    - 전체: `AWSXRay.captureAWS(RawAWS)`
    - 일부만: `AWSXRay.captureAWSClient(new AWS.S3())` (이 예제는 이쪽)
    - serverless-offline은 X-Ray를 지원하지 않으므로 `IS_OFFLINE`일 때는 추적하지 않게 분기
- 함수 수행 시간 측정
    - 동기: `captureFunc`를 감싼 `captureFn(name, fn)`. doRead, doWrite의 SQLite 쿼리 측정
    - 비동기: `captureAsyncFunc`는 언제 끝날지 모르므로 subsegment를 받아 성공 시 `close()`, 실패 시 `close(error)`를 직접 호출. 이를 감싼 `captureAsyncFn` 작성 (subsegment가 undefined일 수 있는 타입이라 `?.` 사용)
    - doInLock의 `connectToRedis`, `acquireLock`, `releaseLock` 구간을 각각 측정

#### 4-11-5 X-Ray 지표 분석

- Lambda 콘솔 모니터링의 X-Ray 탭 또는 X-Ray Analytics에서 확인 (수집까지 약간의 시간 필요)
- **글 목록 조회, 첫 기동 포함**: API Gateway 1.06초, Lambda 1.04초 (둘 사이 통신 약 20ms)
    1. Initialization 전까지 약 380ms: Firecracker microVM 준비(약 100ms)보다 코드를 가져와 인스턴스를 구성하는 시간이 큼. 코드는 X-Ray 포함 240KB 수준이지만 better-sqlite3 Layer가 약 4MB
    2. Initialization 621ms: 코드를 메모리에 올리고 전역 공간 초기화
    3. Invocation 163ms: S3 HeadObject 75ms, GetObject 50ms, doRead 5ms. 대부분 S3 통신
    - 전체의 80%가 첫 기동 지연
- **글 목록 조회, WarmUp 이후**: 통신 13ms, Initialization 사라짐, HeadObject 37ms와 GetObject 88ms (S3 지연은 불규칙), doRead 0ms (JIT 최적화 효과)
- **글 수정, 첫 기동 포함**: 1.25초
    1. API Gateway와 Lambda 통신 25ms
    2. Initialization 전까지 320ms (같은 Layer를 쓰는 조회 API가 먼저 불러와서 약간 빨라진 것으로 추정)
    3. Initialization 632ms
    4. Redis 연결과 잠금 획득/해제 합계 38ms
    5. S3 확인, 가져오기, 업로드 각각 50ms 이상
    6. doWrite 10ms
- **글 수정, WarmUp 이후**: 통신 15ms, 첫 기동 지연 사라짐, Redis 합계 7ms, S3 30~50ms, SQLite 2ms
- 결론
    - Lambda 콜드 스타트는 무시하기 어려운 수준
    - X-Ray 자체도 지연을 추가하므로, 상용에서는 필요할 때만 켜거나 샘플링 규칙으로 일부만 수집
    - 해결책: Provisioned Concurrency(사용량 예측 필요), 주기적인 WarmUp 호출, 콜드 스타트가 덜한 Rust나 Go 런타임

#### **4-11-6 정리**

HTTP API는 싸고 단순하지만 기능이 부족함. REST API는 V2와 완벽히 호환되지 않아 수정이 필요하지만 캐시, 압축, 사용량 계획, X-Ray 추적 같은 기능을 쓸 수 있음.

### 4-12 인증 구현

#### 인증 방식의 기본 개념

- 방법 1: 요청마다 비밀 키를 보내 검증. 간단하지만 키가 노출되기 쉬운 웹 서비스에는 부적합
- 방법 2: 아이디와 비밀번호로 인증 API를 호출해 토큰을 받고, 이후 토큰으로 접근. 주로 이 방식을 사용
- 방법 2에서 결정할 세 가지
    - 자격 증명 전달 형식: 평문, Base64, Basic Authentication(`id:pw`를 Base64로 변환)
    - 토큰 형식: UUID 같은 임의 토큰을 서버 저장소에 매핑하거나, 필요한 정보를 모두 담은 JWT를 써서 저장소 없이 처리
    - 토큰 전달 방식: `Set-Cookie`로 받아 `Cookie`로 다시 보내거나, `Authorization` 헤더 사용

#### JWT 구조

- 헤더(서명 알고리즘), 페이로드(클레임), 서명의 세 부분
- Base64 URL 인코딩 사용(URL 안전 문자, 패딩 제외)

#### OAuth 흐름

1. 인증 제공자(구글 등)에 콜백 주소를 등록해 토큰 가로채기를 방지
2. 허가 토큰이 없으면 인증 페이지로 이동
3. 사용자가 인증
4. 제공자가 콜백 주소로 접근 토큰 전달
5. 브라우저가 접근 토큰을 웹 서비스에 전달
6. 웹 서비스가 토큰 유효성 검증과 프로필 조회
7. 권한 범위를 담은 JWT(허가 토큰) 생성 후 사용자에게 전달
8. 사용자는 만료 전까지 허가 토큰으로 자원 접근
- 접근 토큰을 계속 쓰려면 RefreshToken, RevokeToken 보관과 권한 매핑 관리가 필요함
- 이 예제는 단순화를 위해 구글 프로필 API로 이메일을 얻고, 환경 변수 `ADMIN_EMAIL`과 같으면 관리 권한을 부여한 뒤 이를 JWT에 담음. 서버에 별도 저장소 없음
- 허가 토큰은 쿠키로 관리. `HttpOnly`, `Secure` 옵션 덕분에 로컬 스토리지보다 안전하고, fetch 시 `credentials` 옵션으로 쿠키를 포함 가능

#### 4-12-1 Lambda 인증

- API Gateway 권한 부여자 3종
    - Lambda 권한 부여자: 통합 Lambda 실행 전에 별도 Lambda로 허용 여부 결정
    - JWT 권한 부여자: 주로 Amazon Cognito와 함께 사용
    - IAM 역할 및 정책
- 이 예제는 Lambda 권한 부여자 사용. HTTP API는 V2 형식이며, V1처럼 IAM Role statement를 반환할 필요 없이 boolean만 반환하면 되어 편리함

#### 4-12-2 함수 구현 (`authHandler.ts`)

- `fetchGoogleUserinfo`: `https` 내장 모듈로 `www.googleapis.com/oauth2/v3/userinfo`를 `Bearer` 토큰으로 호출. 토큰이 무효하면 4XX가 와서 검증과 정보 조회를 한 번에 처리. `node-fetch`를 쓰면 번들이 137KB에서 274KB로 늘어 콜드 스타트에 불리하므로 외부 라이브러리를 최소화
- `loginGoogle`
    - 쿼리 파라미터 `token`이 없으면 400, 구글 조회 실패 시 401
    - `fast-jwt`의 `createSigner`로 `{ email, admin }` JWT 생성 (`JWT_SECRET_KEY` 사용)
    - 토큰 유효 기간과 쿠키 만료를 모두 1주일로 설정
    - `Set-Cookie: login=JWT; Path=/; Expires=...; Secure; HttpOnly`
- `logout`: 같은 쿠키를 `Expires`를 epoch(1970년)로 내려 브라우저에서 삭제
- `parseTokenFromCookie`: `cookie-parser` 없이 `login=`으로 시작하는 값을 직접 추출
- `authorize` (Lambda 권한 부여자)
    - 타입: `APIGatewayRequestSimpleAuthorizerHandlerV2WithContext<AuthorizationContext>`
    - JWT 검증 후 `isAuthorized: admin`, `context: { email, admin }` 반환. 실패 시 `isAuthorized: false`
    - 권한 판단을 로그인 시점의 JWT 페이로드에 미리 넣어 두고 여기서는 검증만 하므로 매우 빠름(수 μs)
    - context는 실제 함수에서 `event.requestContext.authorizer.lambda`로 접근 가능(예: 작성자 정보)
    - 거부되면 통합 함수는 호출되지 않고, 결과는 캐시되며, 인증 실패 요청에는 요금이 청구되지 않음. 과도한 요청 공격의 비용 방어 효과
- `grant`: 프런트엔드가 현재 로그인 상태를 묻는 API. 토큰이 잘못되어도 오류 대신 `{ email: null, admin: false }` 반환

#### 4-12-3 서버리스 스택 변경

- `provider.httpApi.authorizers.auth` 설정
    - `type: "request"`: V2는 요청 기반만 지원. 대신 `identitySource`로 캐시 키를 지정할 수 있어 토큰 기반이 필요 없어짐
    - `functionName: "authorize"`
    - `enableSimpleResponses: true`: boolean 응답 사용
    - `identitySource: ["$request.header.cookie"]`: 자격 증명 위치이자 캐시 키. 경로별로 캐시를 나눠야 하면 `$context.routeKey` 추가
- VPC 문제
    - 기본 VPC의 Lambda ENI에는 퍼블릭 IP가 없어 인터넷 접근 불가. 해결하려면 Elastic IP 또는 NAT 게이트웨이가 필요한데 둘 다 상시 비용 발생
    - `authorize`는 구글 API(인터넷)만 필요하고 Redis는 불필요하므로 `vpc`를 지정하지 않음. SQLite도 안 쓰므로 `layers`도 제외
- 함수 등록
    - `loginGoogle`: 아직 토큰이 없으므로 권한 부여자 없음
    - `logout`: 토큰이 있을 때만 의미 있으므로 `authorizer: "auth"`
    - `grant`: 토큰이 없어도 응답해야 하므로 권한 부여자 없음
    - `authorize`: 이벤트로 시작되는 함수가 아니므로 `events` 없음
    - `createPost`, `updatePost`, `deletePost`에 `authorizer: "auth"` 추가
- 디버깅: `httpApi` 액세스 로그 format에 `$context.authorizer.error` 추가. CloudWatch Logs `/aws/http-api/STACK_NAME`에서 확인
- 환경 변수로 `JWT_SECRET_KEY`, `ADMIN_EMAIL` 주입

#### 4-12-4 빌드 오류 수정

- 함수와 라이브러리가 늘면 웹팩 빌드 시 heap out of memory 발생
- 원인: `ts-loader`가 타입 체크까지 수행
- 해결: `transpileOnly: true`로 컴파일만 하고, 타입 체크는 `fork-ts-checker-webpack-plugin`으로 별도 프로세스에서 처리. 빌드 시간도 단축되며 Serverless Framework TS 템플릿의 기본 구성이기도 함

#### 4-12-5 CloudFront 수정

- 오리진 요청 정책을 지정하지 않으면 URL과 일부 기본 헤더만 전달되어 쿼리 파라미터와 쿠키가 사라지고 인증이 동작하지 않음
- `AllViewer` 정책은 Host 헤더까지 덮어써서 API Gateway가 403을 반환하므로 사용 불가
- `AllViewerExceptHostHeader` 정책을 직접 정의: 쿠키 all, 쿼리 문자열 all, 헤더는 Host를 뺀 whitelist
- API 오리진 캐시 동작에 `OriginRequestPolicyId: { Ref: ... }`로 연결하고 `resources`에 등록 후 `sls deploy`

#### 4-12-6 프런트엔드 작업

- `react-google-login` 사용(구글 클라이언트 ID 필요, 설정은 Appendix B)
- API 함수: `requestLogin(accessToken)`, `requestLogout()`, `requestGrant()`. `Set-Cookie`는 브라우저가 알아서 처리하므로 await만 하면 됨
- 허가 정보 전파: props로 넘기는 대신 React Context 사용
    - `GrantContext = React.createContext({ admin: false })`
    - App에서 `useEffect`로 `requestGrant` 후 상태 갱신, `Router` 상위에 `GrantContext.Provider` 배치
- `AdminComponent`: admin이면 children을 Fragment로 감싸 렌더링, 아니면 빈 Fragment. 새 글, 수정 링크에 적용
- `AdminPage`: admin이 아니면 접근 불가 화면을 보여주는 페이지 단위 가드. `/_new`, `/:title/edit` Route를 감쌈
- `LogInOutButton`
    - 로그인 상태에 따라 `GoogleLogin` 또는 `GoogleLogout` 반환
    - 프로필은 서버 로그인 API에서 가져오므로 `fetchBasicProfile={false}`
    - 성공 시 서버 로그인 후 `window.location.reload()`로 전체 갱신(설명 편의상 선택한 방식)
    - App에는 `logged={!!grant.email}`로 Provider와 같은 레벨에 추가

#### 4-12-7 테스트

- `serverless-offline`은 2022년 8월 기준 Lambda 권한 부여자 미지원이라 로컬 서버 불가
- 서버를 배포한 뒤 프런트엔드 `package.json`의 `proxy`를 배포된 API 주소로 바꿔 webpack 개발 서버가 프록시하도록 함
- 로그인 전에는 새 글 링크가 없고, 운영자 이메일로 로그인하면 나타나며, 비로그인 상태로 `/_new` 접근 시 접근 불가 화면 확인

#### 4-12-8 정리

- 권한 부여자는 통합 Lambda와 분리되어 여러 API에서 재사용 가능하고, 불필요한 실행과 비용을 사전에 차단
- OAuth로 회원 가입 부담을 줄이고, JWT로 갱신/취소 토큰 관리 부담과 외부 저장소 조회를 줄임
- 프런트엔드 노출 제어는 JS 조작으로 우회 가능하지만 서버 API가 거절하므로 문제없음. 더 개선하려면 서버에서 HTML을 동적으로 생성

### 4-13 상용 서비스 고려

#### 4-13-1 DynamoDB

- 항목 최대 400KB. 큰 글은 분할 저장 로직 필요
- 글 목록을 한 항목에 JSON으로 두는 구조는 글이 많아지면 문제. 자료 구조 개선 또는 글로벌 보조 인덱스(GSI) 활용
- 쿼리와 스캔은 최대 1MB 반환이라 이어서 조회하는 페이징 필요
- 한 자릿수 ms 지연을 유지하려면 파티션 치우침(핫 파티션) 방지, 해시 키 설계, 자주 읽는 글은 별도 캐시
- 온디맨드는 트래픽 예측이 어렵거나 거의 0일 때 유리. 꾸준한 트래픽이면 프로비저닝(RCU, WCU)이 훨씬 저렴하며 Auto Scaling으로 변동 대응
- 테이블 처리량 상한 40,000, 파티션당 읽기 3,000과 쓰기 1,000. 넘으면 해시 키 분산이나 DAX 도입

#### 4-13-2 MySQL (RDS)

- 직접 운영할 때와 성능 지표가 다를 수 있으므로 쿼리 패턴별 테스트와 CloudWatch CPU, 메모리, IO 모니터링 필요
- 예제는 `db.t3.micro`. 워크로드가 단순해 작성 일시 인덱스 정도면 충분
- 확장 수단: 인스턴스 상향, 읽기 복제본, 캐시 레이어, 파티셔닝(테이블 최대 16TB)
- Aurora는 Auto Scaling 가능하지만 MySQL보다 약 20% 비쌈. Aurora Serverless는 콜드 스타트 방지를 위해 최소 ACU 유지 시 시간당 최소 0.1USD
- 최대 연결 수: 연결당 12,582,880바이트를 가정. 예: `db.m5.xlarge`(16GB)는 1,365개. Lambda 인스턴스마다 연결을 맺으므로 동시 실행 수가 이를 넘으면 장애. 인스턴스 상향 또는 파라미터 그룹의 `max_connections` 조정
- 느린 쿼리 모니터링: `slow_query_log` 활성화, `log_output=FILE`, `cloudwatch-logs-export-configuration`. 파라미터 그룹 변경은 재시작이 필요하므로 상용 전에 미리 설정

#### 4-13-3 SQLite

- S3(파일 보관)와 ElastiCache Redis(잠금) 사용
- 서비스마다 버킷을 만들면 계정 상한에 걸림. 공용 버킷을 별도 CloudFormation으로 두고 접두사로 디렉터리를 나누는 편이 좋음
- 파일이 커지면 쿼리와 S3 전송이 느려짐. 글 제목 MD5의 첫 바이트(16진수)로 256개 파일로 분할 가능(예: `blog_fb.db`). 단, 리밸런싱, 특정 파티션 집중, 글 목록용 인덱스 파일 직접 관리 문제가 따름
- S3와 Lambda 간 파일 교환은 약 100ms. Amazon EFS를 Lambda에 연결하면 작은 파일 기준 10ms까지 단축 가능(추가 비용)
- Redis는 SET이 약 2μs, CPU 60%로 초당 500K GET/SET 처리 가능해 병목 가능성 낮음. 잠금 전용 인스턴스를 스택마다 두는 것은 낭비이므로 공용 Redis를 별도 스택으로 공유하되 장애 전파와 서브넷 문제에 주의
- 기본 VPC 사용은 보안상 좋지 않으며 별도 VPC 구축 권장(7장)
- 동시 수정이 많으면 잠금 대기로 지연이 급증. 잠금 실패 시 처리 중인 인스턴스에 요청을 넘기는 액터 모델로 개선 가능(7장)

#### 4-13-4 API 요청 횟수 제한

- API Gateway는 토큰 버킷 기반. 계정-지역 단위로 초당 10,000 요청, 버킷 5,000
- 비용 방어를 위해 더 낮은 제한을 직접 설정: ThrottlingRateLimit(초당), ThrottlingBurstLimit(버스트)
- HTTP API: `aws apigatewayv2 update-stage`
    - `-api-id`는 `get-apis`로 확인
    - `-stage-name '$default'`(쉘 해석 방지를 위해 홑따옴표)
    - `-default-route-settings`는 스테이지 단위, 경로 단위는 `-route-settings`
    - 계정 한도보다 높게 설정해도 계정 한도로 제한됨
- REST API는 `aws apigateway` 명령이 JSON Patch 수준이라 복잡함. `serverless-api-gateway-throttling` 플러그인(HTTP/REST 모두 지원)으로 `maxRequestsPerSecond`, `maxConcurrentRequests` 설정, 경로별로는 http 이벤트의 `throttling`
- 웹 페이지를 API Gateway로 제공하면 페이지 하나에 index.html, css, js 등 여러 요청(예: 5번)이 동시에 발생하므로 버스트를 넉넉히

#### 4-13-5 인증

- 권한 부여자 결과 캐시 시간은 `resultTtlInSeconds`(예: 300). 여유가 있으면 길게
- 실행 순서는 API Gateway, 권한 부여자, 통합 함수. 권한 부여자도 Lambda 비용이 들고, 전체가 API Gateway 최대 대기 29초 안에 끝나야 함
- 그래서 권한 부여자는 코드가 단순하고 외부 접근이 적으며 패키지가 작아야 함
- 거절 결과도 캐시되면 그동안 요청이 과금 없이 거절되어 의도치 않은 요청 방어에 유용

#### 4-13-6 CloudFront와 S3

- 블로그는 웹 페이지 파일만 관리하므로 사진 서비스처럼 보존 기간을 고민할 필요 없음
- 용량이 작아  전체 무효화도 가능하지만, 나중에 큰 리소스가 생기면 S3 재접근으로 지연이 생길 수 있어 자동화 시 주의
- `s3 sync`는 크기만 비교하므로 같은 글자 수 오타 수정처럼 크기가 같으면 갱신되지 않음. `aws s3 cp`로 덮어쓰고 무효화 요청. 빌드마다 이름이 바뀌는 .js, .css는 문제없고 index.html이 주로 해당
- S3 버킷은 계정당 100개(요청 시 최대 1,000개). 하나의 버킷에 접두사로 서비스 구분(CloudFront OAI의 prefix 권한, s3sync의 `bucketPrefix`)
- CloudFront 배포는 계정당 200개
    - 경로로 구분(`domain.com/service/`): 하나의 배포에 경로별 동작 구성. 전체 경로 무효화 금지
    - 서브 도메인으로 구분: CNAME에 `.domain.com` 와일드카드(명시 목록은 최대 100개)와 Lambda@Edge로 오리진 선택. Lambda@Edge는 us-east-1에 배포하지만 로그는 실행 지역에 남음
- SEO, 소셜 미리보기, 다국어: React는 JS 실행 후에야 콘텐츠가 완성되므로 봇이 제대로 못 읽음. SSR 필요
    - CRA는 전환이 어려워 `react-snap` 등 사용, 요즘은 Gatsby나 Next.js로 시작하는 경우가 많음
    - 결과물을 S3에 올리거나 `serverless-nextjs`로 Lambda@Edge 렌더링
    - 국가별 분기는 `CloudFront-Viewer-Country` 헤더를 Lambda@Edge 또는 CloudFront Functions에서 활용

### 4-14 모니터링

#### 4-14-1 DynamoDB 모니터링

- 관리형이라 부담은 적지만 제한 초과 여부 모니터링은 필요. 테이블 상세의 모니터링 탭에서 CloudWatch 그래프 확인
- 사용량과 스로틀 지표
    - 읽기/쓰기 사용량: 프로비저닝 대비 사용 추적. 트래픽 예측이 어려우면 온디맨드로 지표를 쌓은 뒤 프로비저닝으로 전환
    - 스로틀된 요청: 용량을 초과한 요청 수. Batch 계열은 한 요청에서 여러 이벤트 발생 가능
    - 스로틀된 이벤트: 테이블 읽기/쓰기뿐 아니라 보조 인덱스 갱신까지 집계
- 지연 시간: 데이터 증가, 파티션 치우침 시 늘어날 수 있으므로 GET, PUT, 필요하면 쿼리와 스캔 지연 측정
- 오류: HTTP 500은 시스템 오류(DynamoDB 장애), 400은 사용자 오류(잘못된 요청). 조건부 확인 실패는 별도 집계
- AutoScaling 한계: CloudWatch 지표가 분 단위라 급격한 트래픽에 대응이 늦고, 용량 변경 횟수에 일 제한이 있음. 이를 감안해 구성하고 지속 모니터링 필요
- **DynamoDB AutoScaling 보충**: 결국 트래픽을 추산해야 가능한 일이므로, 관련 지표를 미리 최대한 많이 모아두고 지속적으로 최적화해야 함.

#### 4-14-2 MySQL 모니터링

- AWS는 RDS의 가용성은 책임지지만 성능까지 보장하지는 않음. 자주 쓰는 쿼리 패턴을 직접 테스트해 지표를 모으고, 지연이 생기면 상위 인스턴스로 바꿔 개선되는지 확인
- 데이터가 쌓이면 파티션을 나눠 과거 데이터를 분리하고, 오래 걸리는 쿼리나 테이블을 꾸준히 튜닝
- CloudWatch 기본 지표: CPU 사용률, DB 연결 수, 여유 스토리지 공간, 사용 가능 메모리, 읽기/쓰기 IOPS. 복제본이 있다면 복제 지연도 함께 모니터링
- 느린 쿼리 로그는 기본적으로 꺼져 있으므로 상용에서는 켜두는 것을 권장
    - 기본 파라미터 그룹은 수정 불가라 새 그룹(예: `param-group-with-logging`)을 생성
    - `general_log=1`, `log_output=FILE`, `long_query_time=1`, `slow_query_log=1`
    - 즉시 적용을 골라도 로그 관련 옵션은 바로 반영되지 않음. 상태가 적용 중에서 재부팅 보류 중으로 바뀌고, 인스턴스를 재시작해야 반영됨
- 적용 후 로그 및 이벤트 탭 하단에서 error 로그, `general.log`, `slowquery.log` 확인 가능

#### 4-14-3 Redis 모니터링

- ElastiCache도 가용성은 AWS가, 성능은 사용자가 관리. CPU, 메모리, 스왑, 연결 수를 보고 인스턴스 상향 여부 판단
- CPU는 노드 사용률과 엔진 사용률을 따로 보여줌
- 이 예제는 몇 개 키에 SET만 하므로 CPU나 메모리가 고갈될 가능성은 매우 낮음
- 연결 지표: 잠금마다 연결을 새로 맺고 끊으므로 현재 연결 수는 적고 새 연결 수가 높게 나옴. CPU상 문제 수준은 아님. 항목 수는 잠금 키 1개뿐이라 최대 1개
- 명령 통계는 개별 명령이 아닌 유형별 그룹으로 제공. 명령 단위로 보려면 `redis_exporter` 같은 오픈 소스로 직접 구축
    - 콘솔의 Get Type/Set Type Commands 번역(유형 명령 가져오기/설정)은 오역으로 보인다는 저자 주석
- SET, DEL만 쓰므로 부하가 생기기 어려움. 여러 서비스가 Redis를 공유한다면 확인이 필요하지만 대개 다른 자원이 먼저 고갈됨

#### 4-14-4 인증 실패율

- API Gateway 지표는 Hello API 때와 동일하게 대시보드 구성
- Lambda 권한 부여자를 쓰면 잘못된 허가 토큰에 403이 반환되므로, 권한 부여자가 붙은 API의 `4XXError` 지표로 인증 실패율을 추적
- 의도치 않은 공격이나 잘못된 인증 로직으로 인한 과도한 거부를 감지하는 데 활용

### 4-15 비용 계산

#### 4-15-1 시나리오 가정

- 글 1천 건, 평균 2KB, 트래픽은 모두 서울
- 매시간 글 조회 1만 회, 조회 시 웹 리소스 5개를 HTTPS로 요청
- 자동화 도구로 매시간 1천 회 수정
- Lambda 수행 시간: DynamoDB/MySQL 30ms, SQLite 300ms, 인증 20ms(캐시 미사용), 메모리는 모두 1,024MB
- DynamoDB는 최종적 일관성, 글 목록 관리용 추가 쓰기와 재시도는 무시
- 무시하는 비용: 프런트엔드 S3 업로드와 캐시 무효화, Redis(프리티어로 가정), CloudWatch 로그와 모니터링
- 한 달은 30일. 유의미한 비용이 드는 서비스는 프리티어 제외, 1,024와 1,000은 구분하지 않고 자릿수만 맞춤

#### 4-15-2 비용 발생 지점

1. 웹 페이지 제공: CloudFront와 S3 오리진, 또는 API Gateway
2. Lambda 권한 부여자 실행
3. API Gateway 요청 처리
4. 통합 Lambda 실행
5. 저장소 접근: DynamoDB, MySQL, S3 위 SQLite

#### 4-15-3 CloudFront와 S3 오리진

- 빌드 결과물이 약 800KB라 S3 보관 비용은 무시
- 월 조회 720만 회 × 800KB = 5.76TB, 첫 10TB 0.120USD/GB → 691.2USD
- HTTPS 요청 720만 × 5 = 3,600만 회, 1만 건당 0.0120USD → 43.2USD
- 합계 734.4USD

#### 4-15-4 API Gateway에서 웹 페이지 제공

- HTTP API 호출 1.23USD/백만 건(첫 3억 건), 전송 0.126USD/GB(첫 10TB)
- 호출 44.28USD + 전송 725.76USD = 770.04USD
- 페이지를 반환하는 Lambda(평균 50ms 가정): 3,600만 회, 1,800백만 ms
    - 호출 7.2USD(0.2USD/백만 건) + 실행 30.06USD(0.0167USD/백만 ms) = 37.26USD
- 합계 807.3USD로 CloudFront와 S3 오리진보다 약 10% 비쌈

#### 4-15-5 API Gateway API 요청 처리

- 월 720만 회, 응답 데이터 14.4GB(2KB × 720만)
- 요청 8.856USD + 전송 1.814USD = 10.67USD

#### 4-15-6 Lambda 권한 부여자

- 캐시 없이 매번 실행, 쓰기 요청에만 사용 → 월 72만 회, 14.4백만 ms
- 호출 0.144USD + 실행 0.24048USD = 0.385USD

#### 4-15-7 통합 Lambda

- 호출 비용은 저장소와 무관하게 2.405USD
- DynamoDB/MySQL(30ms): 216백만 ms → 3.6072USD, 합계 6.012USD
- SQLite(300ms, 10배): 36.072USD, 합계 38.477USD
- 호출 비용보다 실행 시간 비용의 비중이 큼

#### 4-15-8 DynamoDB

- 읽기 단위 1개로 4KB를 2회(최종적 일관성), 쓰기 단위 1개로 1KB를 1회 처리
- 단가
    - 온디맨드: 읽기 100만 건당 0.271USD, 쓰기 100만 건당 1.3556USD
    - 프로비저닝: 읽기 단위 시간당 0.00014098USD, 쓰기 단위 시간당 0.0007049USD
- 월 읽기 720만 회, 쓰기 72만 회(글 2KB라 쓰기마다 2단위 → 144만 단위)
- 온디맨드: 읽기 0.8672USD + 쓰기 1.952064USD = 2.819USD
- 프로비저닝: 시간당 읽기 5천 단위, 쓰기 2천 단위를 3,600초로 나눠 초당 용량으로 환산 → 0.14098 + 0.28196 = 0.423USD
- 실제로는 트래픽이 균일하지 않아 여유를 두겠지만, 그래도 프로비저닝이 꽤 큰 폭으로 저렴
- 스토리지는 월 25GB까지 무료(이후 GB당 0.27075USD). 전체 20MB라 무시

#### 4-15-9 MySQL

- 인스턴스 가동 시간 기준 과금. T4g, T3는 무제한 모드라 기본 사용률을 넘으면 CPU 크레딧 추가 비용 가능
- 트래픽은 SELECT 약 2.8QPS, INSERT/UPDATE 약 0.3QPS, 데이터 20MB → db.t3.micro로 충분. 1GB 메모리로 전 데이터가 캐시에 올라가 디스크 IO도 거의 없음
- 최대 연결 수는 1GB ÷ 12,582,880 ≈ 85개. 10QPS도 안 되므로 걱정 없음
- db.t3.micro 월 18.72USD, 한 단계 위 db.t3.small은 37.44USD. 범용 SSD 0.131USD/GB-월은 무시 가능

#### 4-15-10 SQLite용 S3

- 읽기마다 GET, 쓰기마다 PUT 발생
- 읽기 2.52USD + 쓰기 0.324USD = 2.844USD
- 스토리지 0.025USD/GB(첫 50TB)는 무시, Redis는 프리티어로 비용 없음

#### 4-15-11 비용 정리 (월, USD)

- 웹 페이지 제공
    - CloudFront와 S3 오리진: 734.4
    - API Gateway에서 제공: 807.3
- API 처리
    - API Gateway 처리: 10.67
    - Lambda 권한 부여자: 0.385
- 로직 처리(통합 Lambda + 저장소)
    - DynamoDB 온디맨드: 8.831
    - DynamoDB 프로비저닝: 6.435
    - MySQL: 24.732
    - SQLite: 41.321

**해석**

1. 사진 서비스처럼 CDN 비용이 가장 큼. CloudFront와 S3 오리진이 더 효율적이지만 그래도 나머지 비용의 10배 이상
2. 권한 부여자는 캐시를 쓰면 호출 수를 줄여 더 절약 가능
3. 데이터베이스 사용량이 적은 예제라 저장소 비용은 작고, 이런 단순한 형태에서는 DynamoDB가 가장 효율적
4. MySQL은 보통 가장 비싼 자원이지만, 낮은 사양으로 충분한 경우에는 오히려 Lambda 실행 시간이 비용을 주도함

#### 4-15-12 비용 줄이기

- CDN: CloudFront 최소 트래픽 약정 할인이 가장 일반적. 구성이 복잡해지더라도 더 저렴한 CDN을 쓰는 방법도 있음
- Lambda
    - 호출이 많을수록 메모리를 적당히 줄여 절약. 단, vCPU도 같이 줄어드니 적정선을 찾아야 함
    - 패키지를 작게 유지해 콜드 스타트와 실행 시간 최적화
    - 권한 부여자는 캐시를 최대한 활용해 호출 수 감소
- API Gateway
    - GET 요청에 Cache-Control 헤더 적극 사용, REST API 캐시, 또는 CloudFront에 API를 오리진으로 두고 캐시 활용
    - 조회가 잦고 즉시 반영이 필요 없는 콘텐츠라면 캐시를 적극 검토
    - 전송 비용 절감: REST API 압축 기능, 또는 HTTP API의 Lambda가 `Accept-Encoding`을 보고 직접 압축
- DynamoDB: 모니터링으로 트래픽을 추정할 수 있다면 AutoScaling과 함께 프로비저닝 사용. 트래픽에 너무 딱 맞추면 급변 트래픽이나 긴급 운영 작업에 대응하지 못할 수 있으므로 가용률을 고려한 최적선을 찾아야 함

### 4-16 정리

- DynamoDB, MySQL, SQLite 저장소를 연동한 서버리스 블로그를 만들고, React 프런트엔드와 CDN 제공 방법, 구글 OAuth와 Lambda 권한 부여자를 통한 인증까지 구현
- API Gateway와 Lambda는 상태가 없으므로 상태 유지를 위해 저장소가 필요하며, 각 저장소의 특성에 맞게 고르는 것이 핵심
    - DynamoDB: 키-값 위주 데이터(쇼핑몰, 음악 서비스 등)
    - MySQL: 관계가 중요한 구조화 데이터(회원 관리, 결제 등)
    - S3 위 SQLite: 크지 않은 구조화 데이터를 간단히 다루는 저장소
- CloudFront와 API Gateway는 3장과 4장에 걸쳐 충분히 다뤘고, 다음 장에서는 Lambda에 집중해 블로그 글 추천 서비스를 구현할 예정
