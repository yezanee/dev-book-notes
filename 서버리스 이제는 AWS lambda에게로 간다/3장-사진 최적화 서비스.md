## 3-1 서비스 소개 및 설계

서버리스의 장점은 요청량을 예측하기 어려울 때 가용성과 확장성을 갖춘 시스템을 비용 효율적으로 구축할 수 있다는 점이다. 첫 예제로 이 점을 잘 활용하는 사진 최적화 서비스를 개발한다.

**서비스 개요**

* 고객이 업로드한 JPEG를 적당한 화질로 조절해 용량을 줄여주는 서비스
* 메신저 공유나 게시판 업로드처럼 원본이 필요 없는 경우, 상대가 원하기 전까지 최적화된 사진을 주는 게 서버와 네트워크 자원 측면에서 효율적
* S3: AWS의 고가용성 저장소
* CloudFront: 고속 CDN. S3 파일을 S3보다 싸고 빠르게 제공하고, 접근한 파일은 캐시해서 다음 요청에 더 빨리 응답

**가장 단순한 구조**

1. 고객이 API Gateway로 사진 업로드
2. Lambda가 받아서 지정 규격으로 최적화
3. 최적화한 사진을 S3에 업로드
4. CloudFront로 결과물 접근

**이 구조의 제약**

* 요청 크기 제한
  * API Gateway 10MB, Lambda 6MB → 최대 6MB
  * Lambda는 바이너리를 그대로 못 받고 Base64로 받아야 해서 실제로는 약 4MB
* 실행 시간 제한: API Gateway와 통합된 Lambda는 최대 29초
* 정리하면 사진은 최대 4MB, 최적화와 S3 업로드는 29초 안에 끝나야 함
* 요구사항에 문제가 없다면 단순한 구조가 유지보수에 유리

**제약 검토**

* 4MB 제한: 요즘 원본은 대부분 10MB 이상이라 치명적
* 29초 제한: 40MB 원본도 `jpegoptim`이 20초 안에 끝내므로 큰 문제 아님

**해결: 미리 서명된 URL**

고객이 API Gateway를 거치지 않고 S3의 미리 서명된 URL로 직접 업로드. 업로드 주소 요청 단계가 추가된다.

**구조 2: 최적화 API를 동기 호출**

1. 업로드 주소 요청 API → Lambda가 S3에서 미리 서명된 URL을 받아 반환
2. 고객이 S3 Private Bucket에 업로드
3. 사진 최적화 API 호출 → Lambda가 `/tmp`에 다운로드, `jpegoptim` 실행, Public Bucket에 업로드, Private의 원본 삭제, CDN 주소 반환
4. CloudFront로 접근

* Private Bucket은 원본 임시 저장 공간. CloudFront와 연결된 Public Bucket과 분리하지 않으면 처리 중인 원본이 노출될 수 있음
* 장점: 동기 처리라 진행 중임을 알릴 수 있고, 완료 후 CDN 주소 전달 가능

**구조 3: S3 객체 생성 이벤트로 최적화**

업로드가 끝나면 S3 객체 생성 이벤트로 Lambda가 실행된다. 장점:

1. 최적화 API를 노출하지 않아 내부 구조를 숨길 수 있음
2. 최적화용 HTTP API 구간이 없어져 API Gateway 비용 절약
3. S3 이벤트로 기동된 Lambda는 최대 900초 실행 가능
4. 대량 최적화 시 업로드 주소 API 없이 S3에 바로 올리기만 하면 됨

* 단점: 비동기라 완료 시점을 고객이 알 수 없음
  * 업로드 주소 요청 시 CDN 주소를 함께 주고, 완료될 때까지 고객이 CDN에 반복 접근 (완료 전엔 404)
  * 최적화 후 Lambda가 CloudFront에 캐시된 404를 삭제
* 요청 폭증이나 처리 오류로 결과물이 안 생기면 고객이 끝없이 재접근할 수 있음
  * 보완: 진행 상태를 저장하고 상태 조회 API 추가, 또는 WebSockets API로 상태 통지 채널 개설
* 복잡해질수록 오류, 한도, 비용이 늘어나므로 적정한 서비스 수준(Service Level)을 정하고 그에 맞는 복잡도로 설계하는 것이 바람직

## 3-2 Lambda에서 외부 프로세스 실행 준비

**jpegoptim 선택 이유**

* `libjpeg` 기반 JPEG 최적화 명령줄 프로그램
* 최고는 아니지만 오래 쓰여 안정적이고 실행 파일을 구하기 쉬움
* Lambda에서 외부 프로그램을 실행하는 연습이 됨
* 대안 Squoosh: 구글이 C/C++를 웹 어셈블리로 컴파일한 순수 자바스크립트 도구, 외부 의존성 없음
  * 2MB JPEG, 품질 90 기준 jpegoptim 약 0.2초, Squoosh 약 5초
  * 결과 용량은 Squoosh가 조금 작지만 속도 때문에 jpegoptim 사용

**Lambda 실행 환경과 Docker 테스트**

* Lambda는 RHEL 계열 Amazon Linux 사용 → 리눅스 호환 실행 파일이어야 함
* AWS가 런타임별 Docker 이미지 제공: `public.ecr.aws/lambda/RUNTIME:VERSION` (예: `nodejs:14`)
* 기본 entrypoint는 명령줄 인자로 지정한 함수를 테스트하는 환경을 실행
* 사용법
  * `docker run -it -p 8080:8080 -v $PWD:/var/task public.ecr.aws/lambda/nodejs:14 app.handler`
  * 다른 터미널에서 `curl localhost:8080/2015-03-31/functions/function/invocations -d '{"payload":true}'`
  * CloudWatch Logs와 같은 형식의 실행 로그 출력
* CPU, 메모리, 파일 시스템 제약까지 정확히 재현하진 못하지만, 빠뜨린 외부 의존성으로 실패하는 문제를 빠르게 찾을 수 있음

**동적 라이브러리 문제**

* 실행 파일은 라이브러리를 정적으로 연결하거나 `.so`를 동적으로 참조
  * 동적이면 실행 시 모든 `.so`가 접근 가능한 경로에 있어야 함
  * 정적이면 파일이 매우 커져서, 과거 리눅스 유틸리티는 대부분 동적 방식
* jpegoptim도 동적 라이브러리 사용
* 설치: Ubuntu `sudo apt install jpegoptim`, macOS `brew install jpegoptim`
* `ldd $(which jpegoptim)`로 참조 라이브러리 확인 (libjpeg.so.8, libc.so.6 등)
* Lambda에서 실행하는 방법 두 가지
  1. ldd 결과 파일을 모두 함께 Lambda에 복사
  2. 소스에서 정적 연결로 다시 빌드
* 2번이 확실하지만 소스를 구하기 어렵거나 정적 빌드가 잘 안 되는 경우가 많아 1번 사용
* 주의: ldd 결과 파일이 Lambda 환경과 호환돼야 함
  * x86 Ubuntu, WSL은 그대로 사용 가능
  * macOS용 빌드는 형식이 달라 불가 → Docker로 `ubuntu:20.04`를 띄워 진행 (`apt update` 먼저)

**exodus로 의존성 묶기**

* `.so`를 하나씩 모으는 건 번거로움 (jpegoptim은 적지만 ffmpeg는 매우 많음, 다행히 ffmpeg는 정적 빌드 제공)
* exodus: 실행 파일과 모든 의존성을 묶어주는 파이썬 도구
  * `pip3 install --user exodus-bundler`, PATH에 `~/.local/bin` 추가
  * 원래는 tar.gz + 쉘 스크립트로 묶어 SSH 전달용
  * Lambda용은 `-t` 옵션으로 tar.gz만 생성: `exodus -t -o jpegoptim.tar.gz $(which jpegoptim)`
  * musl/diet libc 경고는 코드 크기 최적화가 필요한 게 아니면 무시
* 압축 구조 (`exodus/` 아래)
  1. `data`: 실제 파일들이 해시 이름으로 위치
  2. `bundles`: 원래 상대 경로를 유지하며 data를 심볼릭 링크로 연결
  3. `bin`: 실행 파일 심볼릭 링크
* `exodus/bin/jpegoptim`을 실행하면 bundles 경로로 라이브러리를 찾아 정상 실행
* macOS의 Docker에서 만들었다면 `docker cp CONTAINER:/root/jpegoptim.tar.gz .`로 호스트에 복사 (`docker ps`로 이름 확인)
* Lambda 이미지에서 검증
  * Lambda 이미지엔 `tar`가 없어서 미리 풀고 `/tmp`에 마운트
  * `--entrypoint /bin/bash`로 에뮬레이터 대신 bash 실행 후 `/tmp/bin/jpegoptim` 실행
  * 실행 파일만 복사하면 `libjpeg.so.8`을 못 찾는 에러 발생

## 3-3 첫 번째 시스템 구현

세 가지 구조를 차례로 구현하며, 가장 단순한 첫 번째 시스템부터 시작한다. 지난 Hello API의 타입스크립트 구현체를 복사해서 사용.

**구조**: 사진 최적화 API 하나가 모두 처리. API Gateway로 업로드 → Lambda가 Base64로 받음 → `/tmp`에 저장 → jpegoptim → S3 업로드 → CDN 주소 반환

**serverless.ts**

* `service: photo-optimizer-api`, `frameworkVersion: "3"`, `runtime: nodejs14.x`, `region: ap-northeast-2`
* 함수 `optimizeAndUpload`, `httpApi` 경로 `/optimizeAndUpload`, 메소드 `put`
* `plugins: ["serverless-webpack"]`

**바이너리 받기**

* API Gateway로 바이너리가 올라오면 `event.body`는 Base64 문자열, `event.isBase64Encoded`는 true (`curl -T`로 확인)
* `Buffer.from(event.body, "base64")`로 디코딩, `fs.writeFileSync`로 저장
* 파일 이름은 바이너리의 MD5 해시 사용 → 같은 사진이면 이미 최적화된 파일이 있는지 검사해서 자원 낭비 방지
* body가 없거나 Base64가 아니면 400
* `finally`에서 `fs.unlinkSync`로 임시 파일 삭제

**/tmp 관리**

* Lambda 인스턴스는 재사용될 수 있어서 이전 작업의 `/tmp` 내용이 남아 있을 수 있음
* `/tmp`는 기본 512MB, 최대 10GB. 지우지 않으면 용량이 소진돼 새 파일 생성 불가
* 임시 파일은 함수 종료 전에 모두 제거

**jpegoptim 압축 해제**

* `npm install --save tar`, `npm install --save-dev @types/tar`
* `tar.x({ strip: 1, C: "/tmp" })`: 최상위 `exodus`를 제거하고 `/tmp/bin/jpegoptim`으로 풀기
* `unpackJpegoptim()`
  * 이미 풀려 있으면(인스턴스 재사용) 바로 resolve
  * `fs.createReadStream(jpegoptimPackFile).pipe(tar.x(...))`
  * exodus 오용이나 `/tmp` 부족으로 실패할 수 있으므로 에러 시 reject

**tar.gz를 배포 패키지에 포함**

* `sls package`가 만드는 `.serverless/photo-optimizer-api.zip`에 포함되어야 함
* serverless-webpack이 빌드 → Serverless Framework가 zip 압축. 그 사이에 파일을 넣어야 함
* CopyWebpackPlugin도 가능하지만 `package.individually: true`로 개별 패키징하면 다루기 어려워서, 프레임워크의 zip 단계에 간섭하는 편이 나음
* `serverless-plugin-scripts`: 각 lifecycle에 지정 명령을 실행하는 플러그인
  * `sls plugin install --name serverless-plugin-scripts`
  * 가능한 지점 중 가장 마지막인 `webpack:package:packageModules` 사용
  * `custom.scripts.hooks`에 `"webpack:package:packageModules": "cp jpegoptim.tar.gz .webpack/service"`
  * `child_process.execSync`로 실행되므로 복잡하면 쉘 스크립트로 분리
* 개별 패키징을 안 하므로 웹팩은 모든 코드를 `.webpack/service`에 넣음 → 거기 복사하면 zip에 포함
* `sls package` 후 `unzip -t`로 확인
* 가끔 버그로 플러그인이 연결되지 않으면 `plugins`에 `serverless-plugin-scripts`가 빠졌는지 확인

**코드에 외부 파일을 포함하는 이유**

* 실행 시 인터넷에서 받는 것보다 훨씬 빠르고 첫 기동 지연에도 효율적
* 배포 코드는 용량 한도 250MB인 `/var/task`에 위치. Lambda 초기화와 함께 준비되므로 EFS, 인터넷 다운로드, 컨테이너 이미지보다 빠름

**최적화 실행**

* `childProcess.execSync(`${jpegoptimPath} -o -s -m80 ${filePath}`)`
  * `-o`: 입력 파일 덮어쓰기
  * `-s`: 메타 정보 제거
  * `-m80`: 품질 80
* 이후 필요한 것: S3 Bucket 할당, Lambda에 업로드 권한 부여, CloudFront와 S3 연결

### 3-3-1 S3와 CloudFront 인프라 준비

**할당 방식**

* 관리 콘솔: 같은 시스템을 여러 번 만들거나 남이 재현할 때 번거로움
* awscli + 쉘 스크립트: 자동화 가능
* Serverless Framework의 Resources에 CloudFormation으로 선언 (권장): 스택 배포 시 자원이 함께 할당되고, 인프라를 코드로 관리

**주의: 스택 삭제 시 자원도 삭제될 수 있다**

* 스택 삭제 시 S3 객체까지 모두 삭제될 수 있음
* 보통 Bucket이 비어 있지 않으면 CloudFormation이 삭제를 실패시키지만, Serverless 메타 정보는 이미 지워져서 `sls info`로 스택을 못 찾는 문제 발생
* Bucket 이름은 고유하고 삭제 후 몇 시간 재사용 불가 → 다시 `sls deploy`하면 이름 충돌로 실패 (그림 3-3-2)
* 해결: 콘솔이나 awscli로 스택 상태 확인 후, Bucket을 비우고 함께 삭제하거나 Bucket을 retain하고 스택만 삭제
* 상태를 가진 자원(DB, 객체 저장소)이나 재생성이 오래 걸리는 자원(CloudFront)은 별도 CloudFormation이나 별도 스택으로 관리하기도 함

### 3-3-2 awscli 도구로 인프라 설정

**S3 기본**

* Bucket 단위 키-값 저장소, 키에 경로 문자를 넣어 폴더 구조 표현
* 정적 웹 호스팅으로 웹 서버 없이 HTTP 제공 가능

**Bucket 생성**

* 생성 시 배치 지역 지정, 이름은 글로벌 유일
* 삭제한 이름은 6시간 후 재사용 가능 (지역 실수하면 6시간 이상 대기)
* 서비스 지역과 다르면 불필요한 지연
* `aws s3`(파일 시스템처럼 다루는 간단한 명령) vs `aws s3api`(API 명령)
* `aws s3api create-bucket --bucket ... --create-bucket-configuration LocationConstraint=ap-northeast-2`
* 생성 시 HTTP 엔드포인트 반환. URL 형태라 이름이 글로벌 유일해야 함

**정적 웹 호스팅**

1. Bucket 정책: `Principal: *`, `s3:GetObject`, `arn:aws:s3:::BUCKET/*` → `put-bucket-policy`
2. `put-bucket-website`
   * `IndexDocument.Suffix: index.html` (폴더마다 있을 수 있어 Suffix)
   * `ErrorDocument.Key: error.html` (단일 페이지)
* 성공 시 메시지 없음. 서울 주소: `http://BUCKET.s3-website.ap-northeast-2.amazonaws.com`
* `aws s3 cp`로 올리고 curl 확인

**CloudFront가 필요한 이유**

* S3 정적 호스팅은 HTTPS 미지원
* CloudFront가 더 빠르고 저렴. S3는 CloudFront 자격으로만 접근하게 하고 제공 옵션은 CloudFront에서 설정
* 기존 Bucket 삭제 `aws s3 rb --force`, 새 Bucket `aws --region ap-northeast-2 s3 mb s3://...`
* S3 정적 호스팅을 오리진으로 쓰면
  1. CloudFront를 거치지 않고 직접 접근 가능
  2. 보안, Lambda@Edge 등을 우회할 수 있고 비용도 더 듦

**OAI (원본 액세스 ID)**

* CloudFront에서 OAI 생성 → Bucket 정책에서 OAI만 허용 → 배포가 OAI로 접근
* 여러 배포와 Bucket에서 공유 가능, 계정당 최대 100개라 서비스 도메인 수준으로 만들어 공유
* `aws cloudfront create-cloud-front-origin-access-identity --cloud-front-origin-access-identity-config CallerReference=...,Comment=...`
  * 반환된 `S3CanonicalUserId`를 Bucket 정책과 배포에 사용
* Bucket 정책의 Principal을 `CanonicalUser: S3_CANONICAL_USER_ID`로 한정

**배포(Distribution) 생성**

* `aws cloudfront create-distribution`, `--generate-cli-skeleton`으로 예제 JSON 생성 가능
* 필수 항목
  1. `CallerReference`: 중복 요청 방지 키
  2. `Comment`
  3. `Enabled`: 미리 만들고 막아두려면 false
  4. `DefaultRootObject`: 보통 `index.html`
  5. `Origins`: `Quantity`, `Items`
     * `Id`: 캐시 정책에서 참조, 유일해야 함
     * `DomainName`: `BUCKET.s3.REGION.amazonaws.com`
     * `S3OriginConfig.OriginAccessIdentity`: `origin-access-identity/cloudfront/OAI_ID`
  6. `DefaultCacheBehavior`
     * `TargetOriginId`
     * `ViewerProtocolPolicy`: `allow-all`, `redirect-to-https`(301), `https-only`(HTTP에 403)
     * `ForwardedValues`: QueryString, Cookies를 캐시 키에 넣으면 적중률이 떨어질 수 있으니 필요 없으면 끄기. 별도 캐시 정책이 권장되지만 아직 필수 항목
* 엣지 전파로 수 분 소요. `Status`가 `InProgress` → `Deployed`가 되면 `DomainName`으로 접근 가능 (`get-distribution`으로 확인)

**캐시 무효화**

* 원본을 바꿔도 무효화 전까진 예전 내용 응답
* `aws cloudfront create-invalidation --distribution-id ... --paths / /index.html`
  * 경로는 `/`로 시작, 끝에 `*` 가능, 생략 가능한 경로와 원래 경로 모두 지정
  * 최대 2분 정도, `get-invalidation`으로 `Completed` 확인

**사용자 지정 도메인과 HTTPS**

* 수정은 기본값 항목까지 모두 입력해야 해서 생성보다 까다로움
* 도메인과 인증서는 Appendix A에서 준비했다고 가정 (Route53, ACM)
* 순서
  1. `get-distribution`에서 `DistributionConfig`만 잘라 저장 (jq 사용 가능)
  2. us-east-1의 ACM 인증서 ARN 확인 (`aws --region us-east-1 acm list-certificates`)
  3. `Aliases.Items`에 도메인, `ViewerCertificate`에 `CloudFrontDefaultCertificate: false`, `ACMCertificateArn`, `TLSv1.2_2021`, `sni-only`
  4. `update-distribution`에 `--if-match`로 ETag 전달 (현재 버전과 일치할 때만 갱신)

**Route53 레코드**

* 다른 AWS 자원 연결은 별칭(`AliasTarget`) 사용
* `Action: CREATE` (수정까지 고려하면 `UPSERT`), `Type: A`
* CloudFront의 `HostedZoneId`는 `Z2FDTNDATAQYW2`, `DNSName`은 CloudFront URL, `EvaluateTargetHealth: false`
* `list-hosted-zones`로 존 확인 → `change-resource-record-sets --change-batch file://record-sets.json`
* 전파 후 `curl -v https://photo.lacti.link`로 인증서까지 확인

### 3-3-3 CloudFormation으로 인프라 선언

* awscli는 이해엔 좋지만 번거로움. 최종 상태를 선언하면 알아서 할당하는 IaC 방식이 편함
* 장점: 선언만 봐도 인프라 파악, 변경점 자동 반영, 버전 관리, `Ref`/`Fn::Join`/`Fn::GetAtt`, `Parameters`/`Output`, 재사용성
* 선언 자원
  * `OAI`: Comment만
  * `PhotoBucket`: `BucketName`, `DeletionPolicy`와 `UpdateReplacePolicy`를 `Retain`으로 해서 스택 삭제나 교체 시에도 유지
  * `PhotoBucketOAIPolicy`: `Ref`로 Bucket 참조, `Fn::GetAtt`로 `OAI.S3CanonicalUserId`에 `s3:GetObject` 부여. 참조 관계로 생성 순서 자동 결정
  * `PhotoCdn`: S3 오리진 + OAI, 캐시 정책, Aliases, 인증서. CLI와 기본값 지원이 조금 달라 주의
  * `PhotoCdnDns`: `Fn::GetAtt: [PhotoCdn, DomainName]`으로 별칭 레코드 등록
* 배포: `aws cloudformation deploy --stack-name ... --template-file s3-cloudfront.json` (약 3~4분)
* 실패 대응
  * 즉시 실패는 문법 오류
  * 나중에 실패하면 `describe-stack-events`에서 `UPDATE_FAILED`의 `ResourceStatusReason` 확인
  * 첫 생성이 실패하면 `ROLLBACK_COMPLETE` 상태로 배포 불가 → `delete-stack` 후 재배포
* YAML이 더 간결하지만, Serverless Framework와 통합하려고 JSON 사용
* 학습 비용이 큼 (콘솔 → awscli → CloudFormation 순서 추천). 내장 함수 제한, 도구 부족, 배포해야 오류 확인 가능 → AWS CDK도 좋은 대안

### 3-3-4 Serverless Framework에 인프라 선언 통합

* `tsconfig.json`에 `resolveJsonModule: true` → `import resources from "./s3-cloudfront.json"` → `config.resources`에 연결
* 또는 `.ts`에 `resources` 변수로 선언해 `export`
  * `aws cloudformation`으로 바로 배포하는 이점은 사라지지만, 타입스크립트 코드와 `process.env` 사용 가능
* `sls deploy` 한 번으로 API Gateway, Lambda, S3, CloudFront, Route53까지 배포
* 주의: 이미 CloudFormation으로 배포한 선언을 그대로 넣으면, 다른 스택에서 같은 자원을 할당하려 해서 Bucket 이름 충돌 발생
  * 처음부터 Serverless 쪽에 선언하고, 테스트 중엔 임시 이름 사용, 이름은 환경 변수로 관리
  * 기존 스택은 `delete-stack`으로 삭제 (`describe-stacks`로 `DELETE_IN_PROGRESS` 확인)
* 환경 변수
  * `.envrc`에 `BUCKET_NAME`, `ROOT_DOMAIN`, `SUB_DOMAIN`을 넣고 `direnv allow`
  * `process.env.X!`로 사용 (`!`는 반드시 존재한다는 표시)
  * `sls print`로 최종 설정 확인
  * 코드 수정 없이 재사용, 민감 정보 분리. `.envrc`는 `.gitignore`에 넣고 `.envrc.example` 제공

### 3-3-5 S3 Bucket에 파일 업로드

* serverless.ts는 개발 머신에서 해석되지만 코드는 Lambda에서 실행 → Lambda용 환경 변수는 따로 선언
  * 전체 함수: `provider.environment`, 개별 함수: `functions.<이름>.environment`
* aws-sdk
  * Lambda에 기본 설치되어 있으므로 `--save-optional --save-exact aws-sdk@2.1055.0` (런타임 문서에서 버전 확인)
  * 용량이 커서 번들에 들어가면 zip이 MB 단위로 커지고 첫 기동 지연 악화 → `webpack.config.js`의 `externals`에 추가
* `s3.upload({ Bucket, Key: ${hash}.jpg, Body: createReadStream, ContentType: "image/jpeg" }).promise()`
  * 스트림으로 메모리 절약
  * ContentType이 없으면 브라우저가 바이너리로 인식해 다운로드해버림
* IAM: `provider.iam.role.statements`에 `s3:PutObject`, Resource `arn:aws:s3:::${BUCKET_NAME}/*`
* 반환: `https://${SUB_DOMAIN}.${ROOT_DOMAIN}/${hash}.jpg`

### 3-3-6 중복 업로드 막기

* MD5 키가 이미 있으면 최적화를 건너뜀
* `headObject`로 존재 확인 (필요 권한 `s3:GetObject`)
  * 없을 때 `s3:ListObject` 권한이 있으면 `Not Found`, 없으면 `Forbidden`
* `s3Exists()`: 성공 true, `Forbidden`이면 false, 그 외 throw
* IAM Action을 `["s3:PutObject", "s3:GetObject"]`로 변경
* 테스트: `curl -T example.jpg <API>`로 4~5초 후 cdnURL, 같은 파일 재요청 시 즉시 반환
* 첫 배포는 3~4분, 이후엔 코드만 바뀌어 1분 이내

## 3-4 두 번째 시스템 구현: Public, Private Bucket 분리

**목표**: 4MB 제한 극복

**Bucket 하나를 접두사로 분리**

* 계정당 Bucket 수 제한이 있어 하나의 Bucket에서 접두사로 구분
  * 업로드: `raw/`, 결과: `photo/`
* OAI 정책 Resource를 `/photo/*`로 좁혀 CDN으로 원본 접근 차단 (이제 .ts라 문자열 보간 사용)
* Lambda IAM
  * `raw/*`: PutObject, GetObject, DeleteObject
  * `photo/*`: GetObject, PutObject

**업로드 주소 요청 API (`GET /getSignedURL`)**

* `s3.getSignedUrlPromise("putObject", { Bucket, Key, Expires })`
  * 액세스 키 없는 사용자도 만료 전까지 지정 operation을 수행할 수 있는 임시 URL
  * Promise 버전이 액세스 키 문제 대응에 유리
  * 발급엔 권한이 필요 없지만 지정 동작 권한(`s3:PutObject`)은 필요
* 만료 시간은 짧게 (예제 5분, 초 단위). 길면 공유나 반복 업로드로 악용 가능
* 키는 동시 요청끼리 겹치면 안 됨. 확률적으로 충분하게 현재 시간 + 랜덤 사용 (nanoid도 가능)
* `photoKey`와 `uploadURL`을 함께 반환, 타입은 `APIGatewayProxyHandlerV2<unknown>`

**최적화 API 변경**

* 쿼리 파라미터 `photoKey`를 받음 (`event.queryStringParameters ?? {}`), 없으면 400, raw 객체가 없으면 404
* `getObject().createReadStream()`을 `get-stream`의 `getStream.buffer()`로 읽음 (해시 계산에 전체 바이너리가 필요하므로)
* 결과 키 `photo/${hash}.jpg`, 완료 후 `deleteObject`로 raw 삭제

**테스트 흐름**

1. `getSignedURL` → photoKey, uploadURL
2. `curl -T example.jpg "<uploadURL>"` (따옴표로 감싸 `?` 해석 방지)
3. `curl -XPUT "<API>/optimizeAndUpload?photoKey=..."` → cdnURL

**한계**

* 최적화 API가 노출되어 임의 키로 반복 호출해 비용을 유발하는 공격 가능
* 작업이 다양해지면 29초 초과 가능

## 3-5 세 번째 시스템 구현: S3 이벤트로 최적화 수행

* 업로드 완료 시 S3 객체 생성 이벤트로 최적화 Lambda 실행
* 내부 이벤트로 실행된 Lambda는 고객에게 응답할 수 없어서, `getSignedURL`이 `cdnURL`과 `uploadURL`을 반환

**S3 이벤트 연결**

* `s3: { bucket, event: "s3:ObjectCreated:*", rules: [{ prefix: "raw/" }], existing: true }`
  * 삭제(`ObjectRemoved`), 복원(`ObjectRestored`) 이벤트도 가능
  * `existing: true`: 이미 s3-cloudfront.ts에서 만든 Bucket에 이벤트만 연결 (없으면 Bucket을 새로 만들려 함)
* `timeout: 900`: 여러 이벤트를 한 번에 받을 수 있어 넉넉하게

**핸들러**

* `S3Handler`: Bucket과 객체 정보를 받고 반환값 없음. 여러 이벤트가 묶여 오므로 `event.Records`를 돌며 `record.s3.object.key` 사용
* `downloadBucketObject()`: 해시가 필요 없으니 버퍼 대신 `createReadStream`을 `fs.createWriteStream`으로 pipe, 에러는 reject, close는 resolve
* `downloadAndOptimizeAndUpload(rawKey)`: rawKey는 `raw/xxx.jpg` 형태라 `path.basename`으로 처리. 다운로드, 최적화, `photo/` 업로드, 정리 후 `resultKey` 반환
* `unpackJpegoptim()`은 함수 시작 시 한 번만

**CloudFront 캐시 무효화**

* 결과 준비 전 반복 요청으로 파일 없음 응답이 캐시되면, 결과가 올라간 뒤에도 계속 그 응답이 나올 수 있음
* 처리 후 `cloudfront.createInvalidation`
  * `DistributionId`: serverless.ts에서 `Ref: "PhotoCdn"`으로 환경 변수 `DISTRIBUTION_ID`에 주입
  * `Paths.Items`: `/${resultKey}`
  * `CallerReference`: `Date.now().toString()`
* IAM `cloudfront:CreateInvalidation`은 리소스 범위 지정 불가, `Resource: "*"`

**테스트와 평가**

* 배포 후 endpoint엔 `getSignedURL`만 남고 최적화 함수는 내부에서 자동 실행
* 업로드 전 cdnURL은 403, 업로드 후 2~3초면 200 OK
* 아쉬운 점: 중복 방지 처리 불가, 완료 통지가 없어 주기적으로 확인해야 함
  * 개선하려면 진행 상태 메타데이터를 DB에 두고 조회 API, 웹소켓 통지 추가. 대부분 2~3초면 끝나는 서비스엔 과함
* 장점: `aws s3 cp`로 대량 업로드만 해도 각 객체마다 이벤트 발생, 최대 1,000개 동시 기동으로 빠르게 처리

## 3-6 상용 서비스 고려

**처리 한도**

* API Gateway: 초당 약 1만 요청 (상향 가능)
* S3: 동시 업로드, 총 용량 제한 없음, 객체 최대 5TB
* CloudFront: 최대 150Gbps, 초당 25만 요청 (상향 가능)
* 대부분 사례에 충분, S3와 CloudFront는 사실상 한도 걱정 불필요

**글로벌 업로드 속도**

* 다운로드는 CloudFront 엣지 덕분에 문제없지만, 해외에서 서울 Bucket으로의 업로드는 느림
* S3 전송 가속화
  * 엣지 로케이션으로 업로드, 10~20% 향상
  * Bucket에 `AccelerateConfiguration: { AccelerationStatus: "Enabled" }`
  * `new AWS.S3({ useAccelerateEndpoint: true })`는 `getSignedURL`에서만 사용
* 지역별 Bucket과 스택 배포
  * CloudFront 스택은 분리해서 중복 배포 방지
  * CDN 주소에 지역 코드를 넣고 Lambda@Edge로 해당 Bucket 접근
* 업로드 주소 API도 API Gateway 엣지 최적화로 개선 가능 (REST API만 지원, 다음 블로그 예제에서 다룸). 그 이상은 지역별 배포인데 관리가 복잡해 신중히

**기타 고려 사항**

* 수명 주기: `LifecycleConfiguration`에 `ExpirationInDays: 90` 같은 Rule로 자동 삭제 또는 Glacier 전환
* Lambda@Edge로 CDN 접근 시점 최적화: 원본 하나에서 여러 규격을 만들 때 유리. `serverless-plugin-cloudfront-lambda-edge` 사용, 쿼리를 캐시 키에 포함. 이번 서비스엔 불필요
* 첫 기동 지연 (5MB 기준 약 4초: 압축 해제 2초 + 최적화 2초)
  * 실행 파일을 zip에 바로 넣는 방법은 `serverless-plugin-zip-symlinks-compress-harder`로 가능하지만, `/var/task`가 읽기 전용이고 실행 권한이 없어 외부 실행 파일엔 불가
  * `provisionedConcurrency: 5`처럼 미리 준비 (추가 요금)

## 3-7 모니터링

확인 항목

1. 최적화 Lambda의 실행 빈도와 시간
2. API Gateway 요청량
3. S3 Bucket 용량
4. CloudFront 응답량

* Lambda: Duration 경보(jpegoptim 지연), Errors 모니터링(`/tmp` 부족 등)
* API Gateway: 요청 증가 시 할당량 상향, 비정상 급증이면 WAF. 경보 추가
* S3: `BucketSizeBytes`의 `StandardStorage`, 수집 주기가 길어 1일 이상 단위로만 제대로 표시. 추이는 행 위젯, 현황은 번호 위젯
* CloudFront: 글로벌이라 us-east-1에서 별도 대시보드
  * `BytesDownloaded`를 합계, 30일 번호 위젯으로 두면 월 전송량 파악
  * 4xx, 5xx 비율로 결과 준비 전 과도한 요청 확인

## 3-8 비용 계산

**비용 항목**: 업로드 주소 API(API Gateway, Lambda), S3 보관, CloudFront 전송, CloudWatch 대시보드, CloudWatch Logs

* 데이터 유입과 내부 통신은 대부분 무료 → S3 업로드, CloudFront가 S3에서 가져오는 비용 없음
* 로그는 남기지 않아 제외, 대시보드는 개당 3USD로 2개 6USD
* 주된 비용은 S3 보관과 CloudFront 전송

**S3 (Standard 클래스)**

* 6개 스토리지 클래스 중 CDN용이라 Standard 사용
* 보관: 처음 50TB GB당 0.025USD, 다음 450TB 0.024USD, 500TB 초과 0.023USD
* PUT/COPY/POST/LIST: 1,000건당 0.0045USD
* GET/SELECT 등: 1,000건당 0.00035USD
* 프리티어(1년): 5GB, GET 2만 건, PUT 등 2천 건, 송신 15GB

**CloudFront**

* 지역별로 요금이 다르고 한국이 미국보다 비쌈. 월 10TB 이상이면 할인 협의 가능
* GB당 전송 (대한민국 포함 그룹): 처음 10TB 0.120USD, 다음 40TB 0.100USD, 다음 100TB 0.095USD
  * 미국/멕시코/캐나다: 0.085, 0.080, 0.060USD
* 10,000건당 요청 (대한민국 포함 그룹): HTTP 0.0090USD, HTTPS 0.0120USD
* 무효화: 매달 1,000개 경로 무료, 이후 경로당 0.005USD
* 프리티어(1년): 1TB 송신, 1천만 요청

**서비스 비용 계산 (프리티어 제외)**

가정: 원본 평균 4MB, 결과 2MB, 하루 10만 건(월 300만 건), 결과당 10회 접근, 서울 트래픽만, 업로드 주소 Lambda 15ms, 최적화 Lambda 3초, 메모리 1GB, 30일

* 업로드 주소 API: API Gateway 3.69 + Lambda 호출 0.6 + 실행 0.752 = 5.042USD
* 최적화 Lambda: 호출 0.6 + 실행 150.3 = 150.9USD
* S3 (결과물 6TB): 보관 150 + PUT 13.5 + GET 10.5 = 174USD
* CloudFront (60TB): 전송 6,200 + 무효화 15,000 = 21,200USD
* 합계 약 21,529.942USD/월 (영구 보관 시 S3 비용 계속 증가)

해석

* 업로드 주소 API는 무시할 수준, 최적화 Lambda는 S3와 비슷
* 대부분이 CloudFront, 그중 무효화 비용이 가장 큼 → 무효화를 없애지 않는 한 세 번째 시스템은 비용상 쓸 수 없음
* 그다음은 트래픽 전송 비용. 과도한 트래픽이 예상되면 대역폭 선구매로 할인

**비용 줄이기**

1. Lambda 메모리를 실제 사용량에 맞춰 512MB, 256MB로 낮추기
2. 무효화 대신 완료 확인 API: 결과 키가 있으면 CDN 주소 전달. S3 조회 비용은 늘지만 훨씬 저렴
3. 중복 사진이 많으면 해시나 유사 이미지 메타데이터로 하나의 결과물로 관리해 보관 비용 절감

## 3-9 정리

* API Gateway, Lambda, S3, CloudFront로 사진 업로드, 외부 실행 파일 실행, CDN 제공을 하는 서버리스 스택을 구성하고, 세 가지 구조의 구현과 장단점을 비교했다.
* 확장: `pngquant`로 png 최적화, `convert`로 크기 조절과 회전, `ffmpeg`로 음성/영상 변환
* 컨테이너 이미지 기반 Lambda보다 개발과 배포는 복잡하지만, 필요한 파일만 포함해서 첫 기동 지연이 훨씬 짧다. 외부 실행 파일을 쓰면서 첫 기동 지연이나 실행 비용을 최적화할 때 유용하다.
