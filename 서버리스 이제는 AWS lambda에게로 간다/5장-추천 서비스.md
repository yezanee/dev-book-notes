## 5-1 시나리오

**목표**

- 사용자가 문서(작품)를 열람하거나 좋아요를 누른 순서를 기록해 두고, 이를 바탕으로 비슷한 문서를 추천하는 서비스를 만든다.
- 실무에서는 BigQuery ML이나 SageMaker 같은 관리형 솔루션을 쓰지만, 이 책은 Lambda에 초점을 둔다. 그래서 Word2vec 모델을 직접 만들고 API Gateway와 Lambda로 서빙한다.

**Word2vec 개념**

- 단어를 수백 차원의 벡터로 표현해서, 함께 등장하는 단어끼리 벡터 공간에서 가깝게 배치하는 모델이다.
- 방식은 두 가지다. CBOW는 주변 단어로 중심 단어를 예측하고, Skip-gram은 중심 단어로 주변 단어를 예측한다. CBOW가 더 빠르고, Skip-gram이 성능이 더 낫다고 알려져 있다.
- 이 예제에서는 문서 ID를 단어로, 같은 추적 ID에 속한 문서 열람 순서를 문장으로 본다. 예를 들어 사용자 A가 문서 3, 2, 1을 봤다면 `문서-3 문서-2 문서-1`이 한 문장이 된다.

**기반 데이터**

- 데이터 출처는 서비스 로직에서 남기는 행동 로그(Action Log)와 서버의 접근 로그(Access Log)다.
- 개별 로그를 사용자 단위로 묶으려면 키가 필요하다.
- 이 예제는 회원 기능이 없다. 대신 쿠키 사용에 동의하면 추적 ID를 발급하고, 그 이후의 행동을 로그로 남긴다.

## 5-2 개발 환경 구축

**파이썬 런타임과 컨테이너 이미지를 쓰는 이유**

1. Word2vec을 쓰려면 Gensim 라이브러리가 필요하므로 파이썬 런타임을 사용한다.
2. ML 라이브러리는 용량이 커서 ZIP 패키지 제한(250MB, `/var/task`)에 담기 어렵다. 그래서 컨테이너 이미지 기반 Lambda를 사용한다.
3. 집필 시점(2022년 8월)에는 Serverless Offline이 컨테이너 이미지를 잘 지원하지 않았다. 그래서 Serverless Framework 대신 AWS SAM CLI를 사용한다.

**파이썬 환경**

- pyenv로 파이썬 버전을 관리한다. 당시 Lambda가 지원하던 최신 버전인 3.9.13을 설치하고 `pyenv global`로 고정한다.
- virtualenv로 프로젝트별 `venv`를 만든다.
- 이렇게 하면 의존성 충돌을 막고, root 권한 없이 패키지를 설치할 수 있다. `site-packages` 크기만 보면 업로드될 용량도 가늠할 수 있다.

**ECR 로그인**

- 컨테이너 이미지를 올릴 레지스트리로 ECR을 사용한다.
- 로그인은 `aws ecr get-login-password`의 결과를 `docker login`에 파이프로 넘기는 방식이다. 리전은 ap-northeast-2이고, 계정 ID는 `aws sts get-caller-identity`로 확인한다.
- Docker는 인증 정보를 `~/.docker/config.json`에 평문으로 저장한다. 보안이 보장되지 않는 환경에서는 작업 후 반드시 `docker logout`을 해야 한다.

**SAM CLI**

- SAM은 CloudFormation을 확장한 템플릿 모델이다. `AWS::Serverless` 네임스페이스로 Lambda, HTTP API, DynamoDB 같은 자원을 간결하게 선언할 수 있다.
- AWS 공식 도구라서 새 기능(컨테이너 이미지 등)을 Serverless Framework보다 빨리 지원한다.
- 자동 업데이트가 없다. 알 수 없는 문법 오류가 나면 버전 문제를 먼저 의심해야 한다.

## 5-3 시스템 설계

**전체 흐름**

- 학습은 Lambda 제약 때문에 로컬이나 EC2에서 직접 한다. Lambda는 학습된 모델 파일을 S3에서 받아 추론만 담당한다.
- 동작 순서는 다음과 같다.
    1. 쿠키 사용에 동의하면 서비스 API가 추적 ID(GUID)를 세션 쿠키로 발급한다.
    2. 좋아요를 누르면 (추적 ID, 아트 ID)를 SQS에 넣고, Redis의 좋아요 카운트를 1 올린다.
    3. 학습 환경이 주기적으로 SQS에서 로그를 가져와 정제하고, Word2vec을 학습한 뒤 모델을 S3에 업로드한다.
    4. 추천 API(Lambda)는 S3에서 모델을 받아 유사한 아트 ID를 반환한다.

**웹 서비스**

- 아트 갤러리는 정적 웹사이트와 CDN으로 구성한다. 메타데이터는 `data.json` 하나에 담는다.
- 검색은 fuse.js를 사용한다.

**모듈 5개**

- `train`: SQS 이벤트로 Word2vec을 학습한다.
- `recommend-api`: S3의 모델로 추천 결과를 반환한다.
- `service-api`: 추적 쿠키와 좋아요 API를 제공한다.
- `website`: 프론트엔드다.
- `cdn-stack`: API와 웹페이지를 제공하는 CDN 스택이다.

## 5-4 학습 구현

**의존성**

- gensim 4.1.2와 boto3 1.21.3을 `requirements.txt`로 관리한다.
- `pip freeze`는 하위 의존성까지 모두 출력하므로, 의도한 의존성만 깔끔하게 정리하기는 어렵다.

**SQS 특성**

- 표준 대기열은 최소 1회 전송을, FIFO 대기열은 정확히 1회 전송을 보장한다. 표준 대기열이 조금 더 저렴하다.
- 한 요청에 메시지를 최대 10개까지 담을 수 있다.
- 메시지는 64KB 단위로 계산되며, 최대 256KB까지 쓸 수 있다. 256KB 메시지는 요청 4개로 간주된다.
- 보존 기간은 기본 4일이고, 1분에서 14일까지 설정할 수 있다.
- 저장할 수 있는 메시지 수에 제한이 없어서, 저렴한 로그 보관 용도로도 쓸 만하다.

**drain 함수 (SQS에서 메시지 가져오기)**

- `receive_message`를 MaxNumberOfMessages=10, WaitTimeSeconds=0으로 호출한다.
    - 실시간에 가깝게 처리해야 한다면 롱 폴링을 쓴다. 대기 시간은 최대 20초다.
- 메시지 Body는 `json.loads`로 파싱한다.
- SQS는 메시지를 자동으로 삭제하지 않는다. 그래서 ReceiptHandle로 `delete_message_batch`를 호출해 직접 지운다.
- Visibility Timeout(최대 12시간) 안에 삭제하지 않으면 메시지가 다시 수신될 수 있다. 처리 시간이 길다면 `change_message_visibility`로 시간을 조정한다.

**collect 함수**

- 메시지가 없을 때까지 읽어서 `traceId`를 키로 작품 ID를 모은다.
- 한 줄에 공백으로 이어 붙인 작품 ID를 기록한다. 즉 한 줄이 한 문장이다.
- 결과를 `event.yyyy-MM-dd.log`로 저장하고 S3의 `events/` 경로에 업로드한다.
- 모든 데이터를 메모리에 모으는 방식이라 데이터가 많아지면 메모리가 부족해진다. 이때는 중간에 저장하거나 실행 주기를 짧게 한다.

**download_event_logs 함수**

- `list_objects_v2`로 파일 목록을 가져와 임시 디렉터리로 내려받는다.
- 이미 있는 파일은 건너뛰어서 불필요한 다운로드를 줄인다.

**train 함수**

- `Reader` 클래스를 이터러블로 만들어서 파일을 한 줄씩 `yield`한다. 데이터를 메모리에 전부 올리지 않기 위해서다.
- `Word2Vec(sentences=Reader())`로 학습하고 `w.wv.save`로 `w2v.dat`를 만든 뒤 S3에 업로드한다.
- 파라미터는 모두 기본값을 쓴다. 기본 방식은 CBOW다.
- 학습 로그를 보려면 `logging`을 INFO 레벨로 켠다.
- 신경망이라서 학습이 돌아가려면 수천 건, 의미 있는 결과를 보려면 수십만 건 이상의 데이터가 필요하다. 예제 데이터는 임의로 만든 것이라 결과에 의미가 없다.

**S3 Bucket 준비**

- 이 버킷은 여러 모듈이 함께 쓰는데, 관리 주체가 모호하다.
- 버킷 하나를 위해 CloudFormation 스택을 만드는 것은 낭비라서 `aws s3 mb`로 직접 생성한다.

**학습 배포 위치**

- 고려할 점은 두 가지다. 로그 용량이 얼마나 커질 수 있는지, 그리고 학습 시간이 얼마나 길어질 수 있는지다.
- 예제 기준으로 1천 개 문서, 8백만 행, 약 2GB 데이터를 i7 CPU로 학습하는 데 약 5분이 걸렸다.
    - Lambda는 최대 15분 실행, `/tmp` 최대 10GB를 지원하므로 이 정도 규모는 Lambda로도 가능하다.
    - 하지만 상용 규모에서는 사실상 무리다.
- 학습용 컴퓨팅 자원은 별도로 두는 편이 좋다. Jenkins, Argo CD, EC2 + Instance Scheduler, cron 등을 쓸 수 있다.

**필요한 IAM 권한**

- `s3:ListBucket`: 버킷 수준 권한이다.
- `s3:GetObject`, `s3:PutObject`: 객체 수준 권한이라 자원에 `/*`를 붙인다.
- `sqs:GetQueueUrl`, `sqs:ReceiveMessage`, `sqs:DeleteMessage`: 배치 삭제에 해당하는 별도 액션은 없다.
- EC2라면 인스턴스 프로파일로, ECS라면 컨테이너 인스턴스 IAM으로 역할을 지정한다. AWS 밖에서 실행한다면 IAM 사용자의 접근 키를 환경 변수로 넣는다.

## 5-5 추천 API 구현

**추천 로직**

- `KeyedVectors.load`로 `w2v.dat`를 불러온다.
- `most_similar_cosmul(positive, negative, topn)`으로 유사 ID를 찾는다.
    - `most_similar`보다 벡터 크기(노출 빈도)의 영향을 덜 받아서 데이터 편향을 줄일 수 있다.
    - negative는 싫어요 기능이 있을 때 활용할 수 있다. 다만 결과가 반드시 올바르다는 보장은 없다.
- 예제 결과는 점수가 1을 넘는데, 임의 데이터라 의미는 없다.

**app.py 설계 포인트**

- S3 다운로드와 모델 로드를 전역 공간에서 실행한다. 이렇게 하면 콜드 스타트 때 한 번만 실행되고, 인스턴스가 재사용되는 동안 계속 활용된다.
- 인스턴스는 길어야 10분 정도 재사용되므로 오래된 모델을 보는 문제는 크지 않다.
- 모델을 즉시 갱신해야 한다면 Redis 같은 곳에 최신 버전을 두고 로컬 사본과 비교한다. 매 요청마다 S3에 접근하는 방식은 지연과 비용 때문에 피한다.
- 핸들러 입력은 다음과 같다.
    - 기준 문서 `id`는 경로 파라미터로 받고 필수다.
    - `like`, `dislike`는 쿼리 파라미터로 받고 CSV 형식이다.
    - `topn`은 기본값 10이다.
    - 쿼리 파라미터가 하나도 없으면 `queryStringParameters` 키 자체가 없으므로 따로 처리한다.

**Dockerfile과 .dockerignore**

- 베이스 이미지는 `public.ecr.aws/lambda/python:3.9`다.
- `requirements.txt`를 먼저 복사해서 설치하고, 그다음에 `app.py`를 복사한다. 자주 바뀌는 파일을 뒤로 빼서 레이어 캐시를 활용하기 위해서다.
- 진입점은 `CMD ["app.lambda_handler"]`다.
- `.dockerignore`는 `*`로 전부 제외한 뒤 `!`로 필요한 파일만 포함시킨다.

**template.yaml 주요 항목**

- `Parameters`: SAM은 환경 변수를 직접 쓸 수 없어서 BucketName을 파라미터로 주입한다.
- `PackageType: Image`: 컨테이너 이미지를 사용한다.
- `MemorySize: 2048`
- `Timeout: 29`: 컨테이너 Lambda는 초기 실행이 오래 걸려서 API Gateway 통합의 최대 시간으로 설정한다.
- `Architectures: x86_64`: 라이브러리의 arm 호환성이 확실하지 않으면 x86을 쓴다.
- `Events`: HttpApi로 `GET /recommend-api/{id}`를 받는다.
- `Policies`: SAM 정책 템플릿인 `S3ReadPolicy`를 사용한다.
- `Metadata`: Dockerfile, DockerContext, DockerTag를 지정한다.
- `Outputs`: `!Sub`과 자동 생성되는 `ServerlessHttpApi`를 조합해 API 주소를 출력한다.

**빌드와 로컬 테스트**

- `sam validate`로 템플릿을 검증하고, `sam build`로 이미지를 빌드한다. 결과물은 `.aws-sam`에 생긴다.
- `sam local start-api --port 3001`로 로컬 서버를 띄운다.
    - 요청마다 컨테이너를 새로 띄우기 때문에 전역 변수도 매번 초기화된다.
    - 컨테이너 이미지 방식에서는 코드를 수정해도 자동 반영되지 않는다. 다른 터미널에서 `sam build`를 다시 실행하면 된다.
- `sam local invoke --event event.json`으로 함수를 직접 실행할 수도 있다. 이벤트 JSON은 `sam local generate-event`로 만들 수 있다.

**배포**

- `sam deploy --guided --parameter-overrides BucketName=...`으로 첫 배포를 한다.
- 대화형으로 스택 이름, 리전, 변경 확인 여부, IAM 역할 생성 허용, 롤백 비활성화 여부 등을 정한다. 답변은 `samconfig.toml`에 저장되고, 다음부터는 `sam deploy`만 실행하면 된다.
- SAM CLI가 관리용 S3 버킷과 ECR 리포지토리를 자동으로 만든다.
- gensim 때문에 이미지 크기가 약 400MB다. 이미지 크기는 콜드 스타트에 악영향을 주므로 최대한 줄이는 게 좋다.
- changeset으로 변경 사항을 미리 확인한다. Function 하나만 선언했지만 IAM Role, Lambda Permission, ApiGatewayV2 Api와 Stage가 자동으로 추가된다.
- SAM CLI는 자원별 배포 진행 상황을 모두 보여줘서, Serverless Framework보다 오류를 파악하기 쉽다.

**5-5-5 수행 시간 확인 (콜드 스타트 분석)**

- 배포 후 첫 curl 요청은 16~20초가 걸린다. CloudWatch에 기록된 Duration은 6~8초이고, 이후 요청은 수십 ms로 처리된다.
- 차이를 보기 위해 `Tracing: Active`로 X-Ray를 켠다.
- X-Ray 결과는 다음과 같다.
    - 전체 세그먼트 시간은 16.71초로, Lambda 쪽 시간보다 훨씬 길다.
    - Initialization 6.11초가 CloudWatch의 Duration과 같다.
    - 로그에 Init Duration 항목이 없다.
    - 실제 Invocation은 3ms에 불과하다.
- 결론적으로 지연의 대부분은 큰 이미지를 가져오고 초기화하는 콜드 스타트 비용이다.
- 첫 기동 지연은 Initialization과 Init Duration을 더한 시간이다. Init Duration은 Billed Duration에서 빠진다.
- 이 예제에는 Init Duration이 아예 없다. Init Duration은 Lambda가 제공하는 런타임(Provided runtime)을 초기화하는 시간인데, 여기서는 컨테이너 이미지로 사용자 지정 런타임(Custom runtime)을 썼기 때문이다.
- 6초 중 `w2v.dat` 다운로드와 모델 로드는 200ms 이내다. 나머지 대부분은 컨테이너 실행과 파이썬 라이브러리 로딩 시간이다.
- 16초와 6초의 차이(약 10초)는 ECR에서 Lambda로 이미지를 가져오는 시간이다.
    - 배포 직후 첫 실행은 약 16초가 걸린다.
    - 인스턴스가 회수된 뒤 다시 요청하면 약 6초가 걸린다. 이미 가져온 이미지를 재사용하기 때문이다.
- 결론적으로 이미지 크기를 최대한 줄이는 게 좋다. 줄일 수 없다면 Provisioned Concurrency를 쓴다.

**ECR 리포지토리 관리 (5-5-6)**

- SAM CLI가 만든 ECR 리포지토리에는 관리 정책이 없어서, 업로드한 이미지를 전부 보관한다.
- 롤백용으로 일부 이미지를 남기는 건 도움이 된다. 하지만 코드는 버전 관리되므로 이미지는 다시 만들 수 있고, ECR 요금은 GB당 월 0.1USD라서 전부 남기는 건 낭비다.
- 수명 주기(Lifecycle) 정책의 구성 요소는 다음과 같다.
    - `rulePriority`: 규칙이 여러 개일 때 우선순위다.
    - `selection`: 대상을 고르는 기준이다.
        - `tagStatus`는 tagged, untagged, any 중 하나다.
        - `countType`은 sinceImagePushed(기간 기준) 또는 imageCountMoreThan(개수 기준)이다. 기간 기준이면 `countUnit`으로 날짜 단위를 정한다.
        - `countNumber`는 기준 수치다.
    - `action`: 현재 expire만 지원한다.
- 예제 정책은 태그와 상관없이 이미지가 1개를 넘으면 나머지를 모두 만료시킨다.
- 적용 방법은 다음과 같다.
    - 리포지토리 이름은 `samconfig.toml`의 `image_repositories` 항목이나 `aws ecr describe-repositories`로 확인한다.
    - `aws ecr put-lifecycle-policy --repository-name ... --lifecycle-policy-text file://...`로 정책을 부여한다.
    - 적용 후 24시간 이내에 정책대로 이미지가 정리된다.

### 5-6 서비스 API 구현

**API 목록** (Node.js/TypeScript, Serverless Framework 사용)

- `GET /api/accept-trace`: 추적 쿠키를 발급한다. 실제 serverless.ts 설정에서는 POST로 등록된다.
- `GET /api/{id}/like`: 작품의 좋아요 횟수를 조회한다.
- `POST /api/{id}/like`: 좋아요 횟수를 올리고, 추천용 로그(SQS 이벤트)를 생성한다.

**추적 쿠키 발급 API (5-6-1)**

- 추적 ID는 겹치지 않도록 `randomUUID`로 만든다.
- 쿠키는 최대 1일 유지한다(Max-Age). 같은 쿠키를 오래 쓸수록 한 사용자의 데이터를 더 많이 모을 수 있어 유리하다.
- 이미 추적 ID가 있으면 그 값을 재사용한다. 웹 페이지에 접근할 때마다 새 ID가 발급되면 안 되기 때문이다.
- 보안상 중요한 쿠키는 아니지만, 굳이 노출할 필요가 없어서 `Secure; HttpOnly`를 붙인다.
- `parseTokenFromCookie`는 쿠키 배열에서 `trace-id=`로 시작하는 값을 찾아 반환한다. 라이브러리를 쓰지 않고 직접 구현했다.
- 개선할 점도 있다.
    - HttpOnly라서 자바스크립트가 쿠키 존재 여부를 알 수 없고, 그래서 매번 발급 API를 호출하게 된다.
    - 해결책은 두 가지다. localStorage에 동의 여부와 만료 시간을 함께 저장해서 그 사이에는 호출하지 않거나, HttpOnly가 아닌 쿠키로 존재 여부를 확인한 뒤 없을 때만 호출한다.

**좋아요 횟수 조회 API (5-6-2)**

- 원래는 ElastiCache Redis를 스택에 선언해야 하지만, 블로그 예제의 Redis 선언을 그대로 재사용한다.
- `useRedis` 헬퍼의 특징은 다음과 같다.
    - `IS_OFFLINE` 환경 변수가 있으면 로컬 Redis(127.0.0.1)를, 없으면 `REDIS_HOST`를 사용한다.
    - 매번 연결하고 작업 후 `quit`한다. 연결 수를 제어할 수 있다면 전역에 연결을 두고 재사용하는 편이 접속 시간 면에서 낫다.
    - `@redis/client`의 타입이 복잡해서 `ReturnType<typeof createClient>`로 단순화한다.
- `fetchLike`는 `HGET`으로 값을 조회하고, 값이 없으면 0을 반환한다.
- 작품별로 키를 두는 대신 HASH 하나(`lambda-playground::art-gallery::likes`)로 관리한다. 작품이 1천 개뿐이라 충분하다.

**좋아요 API (5-6-3)**

- `markAsLike`의 동작 순서는 다음과 같다.
    1. 경로 파라미터에서 작품 ID를 받는다.
    2. `HINCRBY`로 1을 증가시킨다. 원자적 연산이라 동시성 문제가 없다.
    3. 쿠키에 추적 ID가 있으면 SQS에 이벤트를 넣는다.
    4. 증가된 값을 응답으로 돌려주고, 웹 페이지는 이 값으로 화면을 갱신한다.
- 이벤트 타입은 `LikeEvent { traceId, id }`다.
    - 학습 모듈은 파이썬, 서비스 API는 TypeScript라서 모델 코드를 공유할 수 없다. 두 쪽의 데이터 형식이 어긋나지 않도록 주의해야 한다.
- `enqueueLikeEvent`의 특징은 다음과 같다.
    - `IS_OFFLINE`이면 로컬 SQS(`http://127.0.0.1:9324`)를 사용한다.
    - `LIKE_QUEUE_NAME`으로 QueueUrl을 얻은 뒤, `JSON.stringify`한 이벤트를 `sendMessage`로 보낸다.
- `getQueueUrl` 헬퍼의 특징은 다음과 같다.
    - AWS에서는 CloudFormation이 대기열을 만들어 두므로 바로 URL을 얻는다.
    - 로컬에서는 `NonExistentQueue` 예외가 나면 그때 `createQueue`로 대기열을 만든다.
    - 실서비스 코드가 우선이므로, 먼저 조회를 시도하고 실패할 때만 생성하는 순서가 합리적이다.

**VPC에서 SQS 연결 (5-6-4)**

- VPC를 설정하지 않은 Lambda는 기본 VPC를 통해 SQS나 S3에 자유롭게 접근한다.
- 그런데 Redis가 별도 VPC에 있어서 Lambda도 같은 VPC에서 실행해야 하고, 그러면 SQS에 바로 접근할 수 없게 된다.
- S3는 게이트웨이 엔드포인트와 라우트 규칙으로 해결했지만, SQS는 인터페이스 엔드포인트가 필요하다.
    - 인터페이스 엔드포인트는 라우트 규칙이 아니라 연결할 서브넷을 지정한다. 가용 영역당 서브넷은 1개만 연결할 수 있다.
    - AWS PrivateLink 기반이며 ENI(탄력적 네트워크 인터페이스)를 사용한다.
    - 시간당 요금과 데이터 전송량 요금이 추가로 발생한다.
- 생성 절차는 다음과 같다.
    1. `aws ec2 describe-vpcs`에 jq를 붙여 기본 VPC ID를 찾는다(IsDefault가 true인 것).
    2. `aws ec2 describe-subnets --filter Name=vpc-id,...`로 서브넷 ID 목록을 확인한다.
    3. `aws ec2 create-vpc-endpoint`로 생성한다. 서비스 이름은 `com.amazonaws.ap-northeast-2.sqs`, 유형은 Interface이고, VPC ID와 서브넷 ID를 지정한다.
    4. 생성 직후 상태는 pending이다. `describe-vpc-endpoints`로 available이 되었는지 확인한다.
- 보안 그룹 설정
    - SQS는 https로 접근하므로 443 포트 인바운드를 허용해야 한다.
    - 예제는 편의상 기본 보안 그룹에 `authorize-security-group-ingress`로 443 규칙을 추가한다. 이 규칙은 기본 보안 그룹을 쓰는 모든 대상에 적용되므로 주의해야 한다.
    - 권장 방법은 엔드포인트 전용 보안 그룹을 따로 만들어 그 그룹에만 443을 여는 것이다.
- 구성이 잘못되면 Lambda가 SQS 연결 중에 타임아웃이 난다. 이때는 VPC 연결성 분석기로 문제 구간을 찾는다(7장에서 다룸).

**서버리스 스택 구성 (5-6-5)**

- `LikeQueue`(`AWS::SQS::Queue`)를 선언한다.
    - 이름은 `LIKE_QUEUE_NAME` 환경 변수로 관리한다. 학습 모듈과 같은 대기열을 써야 하기 때문이다.
    - 기본 속성 그대로 사용한다.
- IAM 권한은 `sqs:GetQueueUrl`과 `sqs:SendMessage`를 준다. 리소스 ARN은 `Fn::Join`으로 리전, 계정, 대기열 이름을 조합한다.
- VPC 설정은 Redis가 있는 VPC의 서브넷 ID와 보안 그룹 ID로 선언한다.
- 함수 3개를 등록한다.
    - `acceptTraceIdCookie`는 `POST /api/accept-trace`이며 VPC를 쓰지 않는다.
    - `markAsLike`와 `fetchLike`는 Redis에 접근해야 하므로 VPC를 쓴다.
- provider 설정
    - 런타임은 nodejs14.x, 리전은 ap-northeast-2다.
    - 환경 변수로 `LIKE_QUEUE_NAME`을 넣고, `REDIS_HOST`는 `Fn::GetAtt`로 RedisInstance의 PrimaryEndPoint 주소를 가져온다.
    - resources에 LikeQueue와 RedisInstance를 포함한다.
    - 플러그인은 serverless-webpack과 serverless-offline이다.

**로컬 테스트 (5-6-6)**

- Redis는 `docker run ... -p 6379:6379 redis:6`으로 띄운다.
- SQS는 공식 Docker 이미지가 없어서, 호환되는 ElasticMQ(`softwaremill/elasticmq`)를 사용한다.
    - 9324 포트는 SQS 인터페이스다.
    - 9325 포트는 웹 어드민이다. 메시지 수와 대기열 속성을 확인할 수 있다.
- `sls offline`으로 3개 함수가 노출되는지 확인한다.
- Redis와 SQS는 실제 요청이 처리될 때 연결되므로, curl로 API를 직접 호출해서 검증해야 한다.

**배포 (5-6-7)**

- `REDIS_HOST`(블로그 예제 스택의 Redis)와 `LIKE_QUEUE_NAME`을 설정한 뒤 `sls deploy`를 실행한다.
    - 대기열 이름은 80자 이내로, 영문, 숫자, 하이픈, 언더스코어만 쓸 수 있다.
- `aws sqs list-queues`로 대기열이 생성되었는지 확인한다.
- 서버 에러가 나면 CloudWatch Logs를 본다. 대부분 Redis나 SQS에 접근하지 못한 경우다.

### 5-7 웹 페이지 구현

**프로젝트 구조**

- create-react-app의 TypeScript 템플릿으로 시작했다.
- `data.json`과 `public/images`로 작품 데이터를 정적으로 제공한다.
- 파일 역할은 다음과 같다.
    - `App`이 라우터에 따라 `Pages.tsx`를 호출한다.
    - UI 조각은 `Components.tsx`에 있다.
    - 서버 통신 함수는 `server.ts`에 모아 둔다.
    - 프록시 설정은 `setupProxy.js`에 있다.

**추적 쿠키 사용 (5-7-1)**

- 서버와 웹 페이지가 같은 오리진을 쓰도록 구성할 예정이라서 상대 경로로 `fetch('/api/accept-trace', POST)`를 호출한다.
- localStorage의 `cookie-agree` 키에 동의 여부를 저장한다(`getCookieAgree`, `updateCookieAgree`).
- `CookieAgreement` 컴포넌트의 동작은 다음과 같다.
    - 저장된 값이 null일 때만 동의 화면을 보여준다.
    - 이미 동의한 상태라면 마운트 시점에 쿠키 발급 API를 호출한다.
    - 수락하면 화면을 숨기고, 값을 저장하고, 즉시 쿠키를 발급받는다. 거절하면 화면을 숨기고 값만 저장한다.
- 이 컴포넌트를 App의 `Switch` 바깥에 두어 모든 페이지에서 노출한다.

**좋아요 노출 (5-7-2)**

- `handleServerResponse` 헬퍼의 동작은 다음과 같다.
    - `response.ok`이면 `json.result`를 반환하고, 아니면 예외를 던진다.
    - 예외가 나면 콘솔에 기록하고 기본값(`defaultValue`)을 반환한다.
- `fetchLike`는 실패 시 null을 반환한다.
- `PictureDetail` 컴포넌트에는 `like` 상태를 둔다.
    - 작품 ID가 바뀔 때마다 null로 초기화한 뒤 다시 조회한다.
    - 값이 null이면(로딩 중이거나 에러) `...`로 표시한다.

**좋아요 버튼 (5-7-3)**

- `markAsLike`는 `POST /api/{id}/like`를 호출하고 갱신된 횟수를 받는다.
- `onLike` 콜백은 결과가 null이 아니면 상태를 갱신하고, null이면 alert를 띄운다.
    - `useCallback`의 의존성을 `[picture.id]`로 두어 불필요한 함수 생성을 막는다.
- 버튼을 누를 때마다 ElasticMQ 어드민에서 메시지 수가 늘어나는 것을 확인할 수 있다.

**추천 목록 (5-7-4)**

- `fetchRecommendation`은 `/recommend-api/{id}?topn=3`을 호출한다. 실패하면 빈 배열을 반환해 추천이 없는 것처럼 보이게 한다.
    - like, dislike 파라미터는 편의상 사용하지 않는다. 활용하려면 localStorage에 좋아요한 ID를 기록하거나 싫어요 버튼을 추가하는 방법이 있다.
- `Recommendation` 컴포넌트의 동작은 다음과 같다.
    - API는 ID만 반환하므로, 정적 데이터인 `pictureMap`으로 작품 정보로 변환한다.
    - 상태가 null이면 불러오는 중, 빈 배열이면 추천 항목 없음, 값이 있으면 `PictureList`로 보여준다.
- 로컬에서는 매번 S3에서 모델을 받아오므로 2~3초 지연이 생긴다.

**프록시 서버 구성 (5-7-5)**

- 로컬 서버가 2대라서 package.json의 `proxy` 속성으로는 해결할 수 없다. 대신 `http-proxy-middleware`를 쓴다.
- `src/setupProxy.js`에 경로별 규칙을 둔다.
    - `/recommend-api`는 3001 포트로 보낸다.
    - `/api`는 3000 포트로 보낸다.

**로컬 테스트 (5-7-6)**

- 웹팩 개발 서버의 기본 포트가 3000이라 충돌한다. `cross-env PORT=4000`으로 4000 포트를 쓰게 한다(Windows 대응 포함).
- 기동 명령 정리는 다음과 같다.
    - 추천 API: `sam local start-api --port 3001`
    - Redis: `docker run ... redis:6`
    - SQS: `docker run ... softwaremill/elasticmq`
    - 서비스 API: `sls offline`
    - 웹팩 개발 서버: `npm run start`
    - 참고로 책의 표에는 SQS와 Redis 명령이 서로 바뀌어 적혀 있다.
- `http://localhost:4000`에서 좋아요 증가, SQS 전달, 추천 목록 노출을 확인한다.

### 5-8 CDN 배포

**블로그 예제와의 차이**

- 구조는 블로그 예제와 같다(S3 + OAI, 기본 캐시 정책, React 라우트용 index.html 오류 페이지, 도메인과 인증서).
- 가장 큰 차이는 API가 2개라는 점이다. 오리진 2개와 경로별 캐시 동작을 각각 선언한다.

**APIOrigin (서비스 API)**

- 도메인은 `API_DOMAIN` 환경 변수로 받고, https-only, TLSv1.2를 쓴다.
- 경로 패턴은 `/api/*`다.
- 캐시는 사용하지 않는다(CachingDisabled 정책 ID).
- `APIOriginRequestPolicy`로 Host 헤더를 제외한 헤더, 쿠키, 쿼리를 오리진에 전달한다.
    - 블로그 스택이 이미 배포되어 있는데 같은 이름(AllViewerExceptHostHeader)의 정책을 또 만들면 Internal error로 실패한다. 이름이 겹치지 않게 해야 한다.

**RecommendAPIOrigin (추천 API)**

- 도메인은 `RECOMMEND_API_DOMAIN`으로 받고, 경로 패턴은 `/recommend-api/*`다.
- 편의상 서비스 API와 똑같이 구성했지만, 다음과 같이 더 최적화할 수 있다.
    1. GET만 쓰므로 AllowedMethods를 GET, HEAD로 제한한다.
    2. 경로만으로 추천 내용이 결정된다면 CachingOptimized 정책으로 Lambda 부담을 줄인다.
    3. 쿼리 파라미터를 쓰더라도 필요한 파라미터만 캐시 키에 넣는 정책을 만든다.
    4. 헤더와 쿠키를 넘기지 않는 요청 정책으로 네트워크와 파싱 비용을 아낀다.

**CloudFront 배포 설정**

- Origins에 S3Origin, APIOrigin, RecommendAPIOrigin을 넣는다.
- CacheBehaviors에 두 API의 캐시 동작을 넣는다.
- 나머지 설정은 http2, Aliases, ViewerCertificate다.
- 리소스를 모아서 export하고, serverless.ts에서 import한다.
- serverless.ts는 블로그 예제와 같고, 서비스 이름과 s3Sync의 `localDir`(`../website/build`)만 다르다.
    - 캐시 설정: `index.html`은 no-cache, `static/**`는 1년 캐시다.

**배포 절차**

1. `npm run build`로 웹 페이지를 빌드한다.
2. `.envrc`에 환경 변수를 정리한다. ROOT_DOMAIN, SUB_DOMAIN, ACM 인증서 ARN(us-east-1), API_DOMAIN, RECOMMEND_API_DOMAIN, 버킷 이름 등이다.
3. `sls deploy`로 배포한 뒤 `https://SUB_DOMAIN.ROOT_DOMAIN`에서 동작을 확인한다.
- 이후 스택 변경 없이 웹 페이지만 바뀌었다면 `npm run build` 후 `sls s3sync`만 실행하면 된다. 훨씬 빠르다.

### 5-9 상용 서비스 고려

**SQS 이벤트 채널 (5-9-1)**

- SQS는 저렴하고 제약이 없어서 적당한 규모에는 괜찮다. 하지만 대용량을 다루는 추천 도메인의 상용 이벤트 관리에는 맞지 않다.
- 판단 기준은 학습 쪽의 수신 속도가 서비스 API의 송신 속도보다 충분히 빠른지다.
    - 1회 수신(최대 10개)에 10ms가 걸린다고 하면 메시지 1개당 1ms다.
    - 하루 최대치는 24 × 60 × 60 × 1,000 = 8,640만 건이다.
    - 좋아요만으로는 비현실적인 숫자지만, 소셜이나 이커머스의 전체 이벤트는 쉽게 넘는다.
- 현실적인 대안은 다음과 같다.
    - CloudFront 액세스 로그를 S3에 쌓고 EC2로 정제한다.
    - S3에 로그가 쓰이는 이벤트로 Lambda를 실행해 정제한다.
    - Kinesis Stream, Athena, SageMaker를 활용한다.

**추천 Lambda의 수행 시간 (5-9-2)**

- 이미지 크기 제한은 10GB다. 350MB 이미지로도 첫 기동이 16초였고, 그중 약 10초가 이미지를 가져오는 시간이다. 라이브러리가 클수록 더 느려진다.
- 해결 방법은 세 가지다.
    1. 이미지 크기를 줄인다.
        - 작은 라이브러리를 쓰고 스테이지를 줄인다.
        - `inotifywait`로 실제로 쓰는 파일만 추려서 이미지를 만들 수도 있다.
        - 효과는 크지 않고 한계가 명확하다.
    2. Provisioned Lambda를 확보한다.
        - 이미지를 한 번 가져온 뒤에는 첫 기동이 1~3초 수준이다.
        - 그래서 1개만 확보해 두어도 같은 구역의 첫 기동이 빨라진다.
        - 다만 내부 동작이 공개되지 않았으므로, 필요한 수준만큼 확보해야 예측 가능하다.
    3. API Gateway 대신 Lambda Function URL을 쓴다.
        - API Gateway 통합의 29초 제한 때문에 첫 요청이 무조건 실패할 수 있다.
        - Function URL은 최대 900초까지 기다리고 API 호출 비용이 없다.
        - 대신 경로 파라미터, 사용자 지정 도메인, 보안 기능을 쓸 수 없다.
        - Serverless Framework에서는 `url: true`, SAM에서는 `FunctionUrlConfig`(AuthType 필수, 공개라면 NONE)로 설정한다.
        - 주소는 `https://URL_ID.lambda-url.AWS_REGION.on.aws` 형태다. SAM에서는 `RecommendFunctionUrl.FunctionUrl` 속성으로 얻는다.
        - CORS를 구성해야 하고, 경로 기반 CDN에는 붙일 수 없다. 그래도 개별 기능용 마이크로서비스에는 괜찮은 선택이다.
- 추가 대안으로 추천 결과를 미리 계산해 두는 방법이 있다.
    - 하루 한 번 사용자별로 최대 100개씩 만든다고 하자. 1천만 명에 ID가 32바이트면 하루 32GB다.
    - DynamoDB에 저장하면 약 9USD 수준이다.
    - 동적인 선호, 비선호 반영이나 신규 사용자 추천은 어렵다. 하지만 기존 사용자에게는 수 ms 이내로 응답할 수 있다.

**AVX2 지원 (5-9-3)**

- 메모리를 늘리면 CPU도 늘어나서 멀티코어 라이브러리는 성능이 오른다.
- x86 Lambda는 AVX2(SIMD 명령 집합)를 지원한다. 벡터 연산이 많은 ML 학습과 추론에서 30~40% 정도 향상을 기대할 수 있다.
- 활성화 방법은 다음과 같다.
    - 보통 Intel MKL을 사용한다.
    - PyTorch는 기본으로 MKL을 쓴다.
    - NumPy, SciPy는 MKL로 빌드해야 할 수 있다.
    - Tensorflow는 `-config=mkl`, `-copt=-mavx2` 옵션으로 빌드한다.
- 번거롭지만 추가 비용 없이 성능을 올릴 수 있다.

**모델 파일의 크기 (5-9-4)**

- `/tmp` 기본 크기는 512MB다. 모델이 이보다 크면 초기화 중 다운로드에 실패할 수 있다.
- 최대 10GB까지 늘릴 수 있다.
    - Serverless Framework에서는 `ephemeralStorageSize`를 쓴다.
    - SAM에서는 `EphemeralStorage.Size`를 쓴다.
    - 둘 다 MB 단위로 512~10240 사이 값을 지정한다.
- 비용
    - 512MB까지는 무료다.
    - 초과분은 GB-초당 0.0000000352USD다.
    - 예를 들어 10GB로 1초씩 월 1억 회 실행하면 약 33.44USD다.

### 5-10 모니터링

**기본 방향**

- Lambda와 API Gateway의 정상 응답 여부와 에러 수치를 감시하고, 원인은 CloudWatch Logs로 추적한다.
- 추천 API는 첫 기동 지연으로 타임아웃이 날 수 있으므로 함께 모니터링한다.
- Lambda 동시 실행 수가 한도에 다다르기 전에 서포트 티켓으로 상향을 요청한다.
- S3, CloudFront, Redis는 앞 예제에서 다뤘으므로 이 장에서는 SQS, ECR, PrivateLink를 다룬다.

**SQS 모니터링 (5-10-1)**

- 표준 대기열은 송수신과 보관량에 제한이 없다. 그래서 SQS 자체보다는 SQS를 쓰는 시스템의 이상을 감지하는 게 목적이다.
- SQS 접근 실패는 Lambda 에러 지표로 잡힌다.
- 진짜 문제는 학습 모듈이 데이터를 가져가지 않는 경우다.
    - `ApproximateAgeOfOldestMessage`로 가장 오래된 메시지의 수명을 본다.
    - 하루 한 번 실행하는 구성인데 86.4K초(하루)를 넘으면 이상이다.
    - 기본 보관 기간이 4일이므로, 4일 넘게 처리하지 않으면 데이터가 사라진다.
- `ApproximateNumberOfMessagesVisible`도 봐야 한다.
    - 학습 모듈이 계속 돌고 있는데도 이 값이 계속 늘어난다면, 소비 속도가 발생 속도를 못 따라간다는 뜻이다.
    - 이때는 수집을 병렬화하거나 파이프라인 자체를 개선한다.

**ECR 모니터링 (5-10-2)**

- Lambda와 함께 쓸 때 특별히 감시할 지표는 없다.
- 한도만 주의하면 된다. 등록할 수 있는 리포지토리 수와 리포지토리당 이미지 수가 각각 최대 10,000개다.
- 비용은 이미지 총 용량에 비례한다. 과거 버전을 쓸 일이 없다면 수명 주기 정책으로 오래된 이미지를 자동 삭제하는 것을 권장한다.

**PrivateLink 모니터링 (5-10-3)**

- VPC 엔드포인트는 PrivateLink로 구현되므로 PrivateLink의 모니터링 기능을 사용한다.
- 용량은 충분하다.
    - 가용 영역당 10Gbps를 지원하고, 최대 40Gbps까지 자동으로 확장된다.
    - 좋아요 이벤트 1건이 약 70B라서, 10Gbps 기준으로도 초당 천만 건 이상을 무리 없이 전달한다.
- Lambda에서 엔드포인트를 거쳐 SQS까지는 AWS가 관리하는 구간이다. 그래서 신경 쓸 부분은 두 가지뿐이다.
    - 데이터 전송량에 따른 추가 요금이 있으므로 트래픽을 본다.
    - 패킷 손실이나 비정상적인 연결 종료 같은 장애를 본다.
- 주요 지표는 다음과 같다.
    - `ActiveConnections`: 활성 동시 연결 수다. SYN_SENT와 ESTABLISHED 상태를 포함한다.
    - `NewConnections`: 새로 설정된 연결 수다.
    - `BytesProcessed`: 양방향으로 교환된 바이트 수다. 이 값의 GB 단위로 요금이 계산된다.
    - `PacketsDropped`: 엔드포인트가 삭제한 패킷 수다. 엔드포인트나 서비스의 이상을 알 수 있다. 일부 삭제는 집계되지 않을 수 있다.
    - `RstPacketsReceived`: 수신한 RST 패킷 수다. 서비스 이상을 알 수 있다.
- 용도별로 정리하면 이렇다.
    - 연결 상황은 ActiveConnections와 NewConnections로 본다.
    - 트래픽 수준은 BytesProcessed로 본다.
    - 이상 여부는 PacketsDropped와 RstPacketsReceived로 본다.
- 콘솔의 VPC 엔드포인트 상세 페이지 하단 모니터링 탭에서 확인할 수 있다. 필요한 지표는 CloudWatch 대시보드나 알람으로 등록해서 장애를 인지하고 복구한다.

### 5-11 비용 계산

**비용이 발생하는 자원**

- API Gateway: 추천 API와 서비스 API를 제공한다.
- Lambda: 두 API의 요청을 처리한다.
- ECR: 컨테이너 이미지를 관리한다.
- S3: 정적 웹 페이지, 이벤트 로그, 모델 파일을 둔다.
- CloudFront: API와 S3를 오리진으로 하는 CDN이다.
- Redis: 좋아요 횟수를 관리한다.
- SQS: 좋아요 이벤트를 학습 모듈에 전달한다.
- EC2: 학습 모듈을 실행한다(이 계산에서는 EC2로 가정).
- VPC와 VPC 엔드포인트: Lambda가 SQS와 통신하기 위해 쓴다. VPC는 기본 VPC를 사용한다.
- CloudWatch: 로그, 지표, 대시보드를 담당한다.

**시나리오 (5-11-1)**

1. 모든 트래픽은 서울에서 발생한다.
2. 모든 사용자가 추적 쿠키를 허용한다.
3. 사용자 1명이 작품 20개를 감상하고, 이때 트래픽은 2MB다.
4. 매시간 1만 명이 방문한다. 재접속은 고려하지 않는다.
5. 매시간 1천 명이 평균 5개의 좋아요를 누른다.
6. 학습은 c5.2xlarge EC2로 하루 1회, 1시간 걸린다.
7. 학습 데이터는 최대 한 달간 보존한다.
8. 학습 대상은 작품 1천 개 간의 벡터 공간이다.
9. 프론트엔드 배포용 S3 업로드 비용과 CloudFront 캐시 무효화 비용은 무시한다.
10. Redis는 ElastiCache 프리티어에 포함된다고 보고 무시한다.
11. CloudWatch 로그 보관과 모니터링 비용은 무시한다.
12. 한 달은 30일이다.
- 계산 편의상, 유의미한 비용이 나는 서비스는 프리티어를 적용하지 않는다. 1,024와 1,000도 구분하지 않고 자릿수만 맞춘다.

**새로 등장한 요금 항목 (5-11-2)**

- VPC 엔드포인트: 가용 영역별로 시간당 0.013USD다.
- VPC 엔드포인트 처리 데이터: 처음 1PB는 GB당 0.01USD이고, 이후 구간별로 할인된다.

**서버리스와 EC2 비교**

- 컴퓨팅 비용(API Gateway + Lambda)은 612.973USD로 전체의 17.4%다. 시간당 0.851USD이고, c5.2xlarge 2.2대에 해당한다.
- 요청이 항상 일정하다면 EC2와 큰 차이가 없고, 오히려 EC2가 쌀 수도 있다.
- 하지만 실제 요청은 특정 시간에 몰리고, 피크를 감당하려면 EC2가 더 필요하다. 이를 고려하면 서버리스가 비용 면에서도 효율적이라고 볼 수 있다.

**비용 줄이기 (5-11-5)**

- CDN 비용을 줄이는 방법
    - CloudFront 볼륨 할인을 받거나 더 저렴한 CDN 벤더를 쓴다.
    - 전송하는 데이터 자체를 줄인다.
    - API Gateway는 CDN을 거치지 않도록 분리한다.
- Lambda 비용을 줄이는 방법
    - 적절한 메모리 크기를 찾는 게 핵심이다. 메모리를 줄이면 비용이 줄고, 늘리면 CPU도 늘어나 수행 시간이 짧아져서 오히려 비용이 줄 수도 있다.
    - AWS Lambda Power Tuning 도구가 비용과 수행 시간 관점의 최적 메모리를 찾아준다.
- 캐시를 활용하는 방법
    - 추천 결과가 사용자와 무관하고 현재 작품에만 의존한다면, CloudFront에서 캐시한다. 이것만으로 API Gateway와 Lambda 비용을 절반 가까이 줄일 수 있다.
    - 추천이 잘 바뀌지 않는다면, 추천 결과를 포함한 정적 페이지를 만들어 S3 오리진에서 제공한다. 그러면 추천 API 자체가 필요 없다.
- 이용자가 적을 때의 방법
    - 이때는 VPC 엔드포인트 비용의 비중이 커진다.
    - Redis를 EC2나 Lightsail 같은 저렴한 인스턴스에 퍼블릭 IP로 띄우면 VPC가 필요 없어진다.
    - 그러면 Lambda가 기본 VPC에서 SQS와 바로 통신할 수 있어서 VPC 엔드포인트 비용이 사라진다.
    - 단, Redis의 보안이 위험해지므로 주의해야 한다.

### 5-12 정리

**배운 점**

- 웹 서비스의 사용자 이벤트를 학습해서 추천 API를 만드는 파이프라인을 익혔다.
    - 좋아요 이벤트를 SQS에 넣는다.
    - 학습 모듈이 이를 가공해 Word2vec을 학습한다. 단어 대신 작품 ID를 썼다.
    - 추천 API가 모델로 유사 작품 ID를 반환한다.
- SQS는 비동기 이벤트를 저렴하게 보관하기 좋았다.
- 컨테이너 이미지 Lambda는 10GB까지 지원해서 ML 모델을 쉽게 실행할 수 있었다.

**한계로 드러난 점**

- SQS의 응답 지연이 생각보다 길었다.
- 이미지가 클수록 첫 기동 지연이 길어졌다.

**남은 과제**

- 이번 장에서는 기본 VPC를 필요한 만큼만 고쳐 썼기 때문에, VPC 구성은 7장 게임 개발 단원에서 자세히 다룬다.
- 다음 단원에서는 서버가 언제든 클라이언트로 메시지를 보낼 수 있는 WebSocket API를 다룬다.
