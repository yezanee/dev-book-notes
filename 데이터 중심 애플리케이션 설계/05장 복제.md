### 0. 복제란? 왜 필요한가?

- **복제(replication):** 네트워크로 연결된 여러 장비에 똑같은 데이터의 복사본을 유지하는 것
- 복제가 필요한 3가지 이유:
    1. **지연 시간 감소:** 사용자와 지리적으로 가까운 곳에 데이터를 두면 응답이 빠름
    2. **가용성 향상:** 일부 장비가 죽어도 시스템이 계속 동작
    3. **읽기 처리량 확장:** 읽기 요청을 처리하는 장비 수를 늘려서 더 많은 읽기를 감당

데이터를 복제하는 방법(알고리즘)은 크게 3가지가 있고, 이 장 전체가 이 3가지를 다룬다.

| 방식 | 한 줄 설명 |
| --- | --- |
| 단일 리더(single-leader) | 대장 노드 하나만 쓰기 가능 |
| 다중 리더(multi-leader) | 대장이 여러 명, 각자 쓰기 가능 |
| 리더 없음(leaderless) | 대장이 아예 없음, 아무 노드나 쓰기 받음 |

> **이 장의 전제:**
데이터셋이 작아서 각 장비가 전체 데이터의 복사본을 가질 수 있다고 가정한다.
(데이터가 너무 커서 한 장비에 안 들어가는 경우는 6장 파티셔닝에서 다룸)
>

### 1. 리더 기반 복제 (Leader-based Replication)

가장 흔한 방식. **마스터-슬레이브**, **능동/수동** 복제라고도 불림.

#### 기본 동작 원리

![5-1](/데이터%20중심%20애플리케이션%20설계/image/5장/5-1.png)

1. 복제 서버(replica) 중 하나를 **리더(leader)** = 마스터/프라이머리로 지정
2. 클라이언트가 쓰기(write)를 하면 → 반드시 **리더에게만** 보낼 수 있음
3. 리더는 로컬 저장소에 먼저 기록
4. 리더가 이 변경 내용을 **복제 로그(replication log)** 또는 **변경 스트림(change stream)** 형태로 나머지 **팔로워(follower)** 들에게 전송
5. 각 팔로워는 리더가 처리한 것과 동일한 순서로 로그를 적용해서 자기 복사본을 최신 상태로 갱신

> 팔로워는 다른 말로 읽기 복제 서버(read replica), 슬레이브, 2차(secondary), 핫 대기(hot standby)라고도 부름.
> 

**중요한 규칙**: 읽기는 리더든 팔로워든 아무 데서나 가능하지만, **쓰기는 리더에게만** 허용됨. (팔로워는 클라이언트 입장에서는 읽기 전용)

이 모드는 PostgreSQL, MySQL, Oracle, SQL Server 같은 관계형 DB뿐 아니라

MongoDB, RethinkDB, Espresso 같은 비관계형 DB,

심지어 Kafka·RabbitMQ 같은 메시지 브로커에도 쓰인다.

### 2. 동기식 vs 비동기식 복제

리더가 변경 사항을 팔로워에게 보낼 때, **확인(ok) 응답을 기다리는지 여부**가 핵심 차이.

![5-2](/데이터%20중심%20애플리케이션%20설계/image/5장/5-2.png)

- **동기식(synchronous)**: 리더가 팔로워로부터 "받았다"는 응답을 받을 때까지 기다린 후에야 클라이언트에게 "쓰기 성공"이라고 알림
    - 장점: 팔로워가 항상 리더와 일치하는 최신 데이터를 가짐 (리더가 죽어도 팔로워에서 데이터를 계속 볼 수 있음)
    - 단점: 그 팔로워가 응답을 못 하면(장애, 네트워크 문제 등) **리더도 쓰기를 처리하지 못하고 멈춤**
- **비동기식(asynchronous)**: 리더는 변경사항을 보내기만 하고 응답을 기다리지 않음
    - 장점: 팔로워가 다 죽어도 리더는 계속 쓰기 처리 가능
    - 단점: 리더가 복구 불가능하게 고장나면, 아직 팔로워에 전달되지 않은 쓰기는 **유실됨** (클라이언트에게 이미 성공했다고 알렸어도!)

**현실적인 절충안**

- **반동기식(semi-synchronous)**: 팔로워 하나만 동기식, 나머지는 비동기식으로 설정. 동기 팔로워가 죽으면 다른 비동기 팔로워 중 하나가 동기로 승격됨. → 최소 2개 노드(리더+동기 팔로워 1개)에 항상 최신 데이터가 있음을 보장.

실무에서는 **완전 비동기식**으로 구성하는 경우가 많다(팔로워가 많거나 지리적으로 분산된 경우).

내구성은 떨어지지만 리더가 계속 쓰기를 처리할 수 있다는 장점 때문.

> 💡 참고: 체인 복제(chain replication) 같은 방식은 좋은 성능+가용성을 유지하면서 데이터 유실 없는 동기식 복제 변형을 연구한 결과물.

### 3. 새로운 팔로워 설정

때때로 복제 서버 수를 늘리거나 장애 노드의 대체를 위해 새로운 팔로우를 설정해야 함.

간단히 한 노드에서 다른 노드로 데이터 파일을 복사하는 것만으로는 안 됨

데이터는 계속 쓰기가 일어나는 "유동적인" 것이기 때문에, 복사 도중 시점이 어긋나서 결과가 무효화될 수 있음.

**표준 절차**:

1. 리더의 데이터베이스를 (락 없이) 특정 시점의 **스냅숏**으로 뜸
2. 스냅숏을 새 팔로워 노드로 복사
3. 팔로워가 리더에 연결해서, 스냅숏 시점 **이후** 발생한 모든 변경 요청 (스냅숏이 리더의 복제 로그에서 정확히 어느 위치에 해당하는지와 연관지어야 함. 예: PostgreSQL의 로그 일련번호, MySQL의 이진로그 좌표)
4. 팔로워가 밀린 만큼(backlog)을 다 처리하면 "따라잡았다" → 이제부터는 리더의 실시간 변경을 계속 받아 처리

### 4. 노드 중단(장애) 처리

목표: 개별 노드가 죽어도 전체 시스템은 계속 동작하고, 중단의 영향을 최소화.

#### 4.1 팔로워 장애: 따라잡기 복구(catch-up recovery)

- 각 팔로워는 리더로부터 받은 변경 로그를 로컬 디스크에 보관해두고 있음
- 팔로워가 죽었다가 재시작하면 → 로그에서 장애 직전 마지막으로 처리한 트랜잭션 확인
- 그 지점 이후의 변경사항을 리더에게 요청 → 받으면 리더를 다시 따라잡음
- 비교적 쉬운 복구

#### 4.2 리더 장애: 장애 복구(failover)

훨씬 까다로움. 절차:

1. 팔로워 중 하나를 새로운 리더로 승격
2. 클라이언트가 새 리더에게 쓰기를 보내도록 재설정
3. 다른 팔로워들이 새 리더의 변경사항을 받기 시작

**자동 장애 복구의 3단계**:

1. **리더가 장애인지 판단:** 대부분 타임아웃 방식 사용(예: 30초 무응답 시 죽은 것으로 간주)
2. **새 리더 선택:** 나머지 서버들의 다수결(선출) 또는 미리 선출된 제어 노드가 임명. 보통 가장 최신 데이터를 가진 팔로워가 후보
3. **시스템 재설정:** 클라이언트가 새 리더로 쓰기 요청하게 함, 옛 리더가 돌아왔을 때 자신이 강등된 것을 인식하게 해야 함

**장애 복구 시 발생할 수 있는 문제들**:

- 비동기 복제였다면, 새 리더가 옛 리더의 최신 쓰기를 못 받았을 수 있음
    - 옛 리더가 복귀했을 때 이 쓰기들을 어떻게 처리할지 애매함 (보통은 그냥 폐기 → 내구성 기대를 저버리는 셈)
- **깃허브 사고 사례**: 오래된(out-of-date) MySQL 팔로워가 리더로 승격되면서, 자동 증가 카운터가 예전 값부터 다시 시작
    - 그 기본키가 Redis에도 쓰이고 있어서 서로 다른 사용자의 개인 데이터가 잘못 공개되는 사고 발생
- **스플릿 브레인(split brain)**: 두 노드가 동시에 "내가 리더다"라고 믿는 위험한 상황. 충돌 해소 없이 둘 다 쓰기를 받으면 데이터 유실/오염 위험.
    - 일부 시스템엔 한쪽을 강제 종료하는 안전장치(펜싱, STONITH)가 있음
- **리더가 "죽었다"고 판단하는 타임아웃 값 설정이 어려움:** 너무 길면 복구가 늦고, 너무 짧으면 일시적 부하 급증에도 불필요한 failover가 발생해 상황을 악화시킴

→ 이런 이유로 일부 운영팀은 자동 장애 복구 기능이 있어도 **수동으로** 처리하는 걸 선호.

### 5. 복제 로그는 내부적으로 어떻게 구현될까?

#### (1) 구문 기반 복제(statement-based replication)

리더가 실행한 SQL 문(INSERT/UPDATE/DELETE) 자체를 그대로 팔로워에 전달해서 재실행.

- **문제점**:
    - `NOW()`, `RAND()` 같은 비결정적 함수 → 복제 서버마다 다른 값
    - 자동증가 칼럼이나 기존 데이터에 의존하는 구문은 반드시 **동일한 순서**로 실행돼야 함 (동시 트랜잭션 제한 필요)
    - 트리거·스토어드 프로시저 등 부수 효과가 있는 구문은 서버마다 다르게 동작할 수 있음
- MySQL 5.1 이전까지 쓰였으나 지금은 문제 있으면 로우 기반으로 전환. VoltDB는 여전히 이 방식을 쓰지만 트랜잭션을 결정적으로 만들어 안전하게 처리.

#### (2) 쓰기 전 로그(WAL) 배송

3장에서 다룬 **WAL(Write-Ahead Log)**, 즉, 어떤 디스크 블록에서 어떤 바이트를 바꿨는지"를 기록하는 저수준 로그를 그대로 팔로워에 전송.

- PostgreSQL, Oracle 등에서 사용
- **단점**: 로그가 저장소 엔진과 밀접하게 엮여 있음 → 리더와 팔로워의 DB 소프트웨어 **버전이 달라지면** 복제가 안 될 수 있음 → 무중단 업그레이드가 어려움

#### (3) 논리적(로우 기반) 로그 복제

저장소 엔진 내부 표현과 별개로, 로우(row) 단위로 "무엇이 바뀌었는지"를 기술하는 **논리적 로그** 사용.

- 삽입: 모든 칼럼의 새 값
- 삭제: 로우를 식별할 정보(보통 기본키)
- 갱신: 식별 정보 + 변경된 칼럼들의 새 값
- 장점: 저장소 엔진과 분리되어 있어 **하위 호환성**이 좋고, 리더·팔로워가 다른 DB 버전/엔진이어도 됨. 외부 시스템(데이터 웨어하우스 등)이 파싱하기도 쉬움 → 이를 **변경 데이터 캡처(CDC, change data capture)** 라 부름 (11장에서 자세히)

#### (4) 트리거 기반 복제

DB 내장 복제로는 부족한 유연성(서브셋만 복제, 다른 종류 DB로 복제, 커스텀 충돌 해소 로직 등)이 필요할 때 애플리케이션 계층에서 처리.

- **트리거**: 데이터 변경 시 자동 실행되는 사용자 정의 코드. 변경 내용을 별도 테이블에 기록 → 외부 프로세스가 읽어서 처리
- 오라클 골든게이트(GoldenGate), Databus, Bucardo 등의 도구가 이 방식
- 오버헤드가 크고 버그·제약이 더 많지만, 유연성 때문에 유용함

### 6. 복제 지연(Replication Lag) 문제

리더 기반 복제는 읽기가 많고 쓰기가 적은 부하에서 **읽기 확장(read-scaling)** 아키텍처로 유용 - 팔로워를 추가해서 읽기 요청을 분산.

단, 이 방식은 **비동기식 복제에서만** 동작 (동기식은 노드 하나만 죽어도 전체 쓰기가 막힘).

**문제**: 비동기 팔로워는 리더보다 뒤처질 수 있음(=복제 지연) → 팔로워에서 읽으면 "과거" 데이터를 볼 수 있음.

이 불일치는 일시적이며 결국 따라잡히는데, 이 성질을 **최종적 일관성(eventual consistency)** 이라 부름. ("최종적"이라는 말은 의도적으로 모호함. 뒤처짐에 대한 보장이 딱히 없기 때문)

지연이 짧으면 문제없지만, 시스템이 가용량 한계 근처에서 동작하거나 네트워크 문제가 있으면 지연이 수 초~수 분으로 늘 수 있고, 그러면 애플리케이션에 실제 문제가 발생한다.

대표적인 3가지 이상 현상은 다음과 같음.

#### 6.1 자신이 쓴 내용 읽기 (Read-after-write / Read-your-writes 일관성)

![5-3](/데이터%20중심%20애플리케이션%20설계/image/5장/5-3.png)

사용자가 데이터를 제출한 직후 자신이 쓴 것을 못 보는 문제 (아직 안 따라잡은 팔로워에서 읽었기 때문). "내가 방금 쓴 게 사라졌다"는 느낌 → 불만족스러움.

**해결 기법 예시**:

- 사용자 본인이 수정할 수 있는 데이터(예: 자기 프로필)는 항상 리더에서 읽기
- 마지막 갱신 후 일정 시간(예: 1분) 동안은 리더에서 읽고, 그 이후엔 팔로워에서 읽기
- 클라이언트가 최근 쓰기의 타임스탬프를 기억 → 그 타임스탬프까지 반영된 팔로워에서만 읽도록 시스템이 보장
- 복제 서버가 여러 데이터센터에 있으면, 리더가 있는 데이터센터로 요청을 라우팅해야 하는 등 복잡도 증가

**디바이스 간(cross-device) 문제**: 같은 사용자가 여러 기기(데스크톱+모바일)로 접근하면 더 어려움

마지막 갱신 타임스탬프를 중앙에서 관리해야 하고, 서로 다른 디바이스의 요청이 같은 데이터센터로 라우팅된다는 보장도 없음.

#### 6.2 단조 읽기 (Monotonic Read)

![5-4](/데이터%20중심%20애플리케이션%20설계/image/5장/5-4.png)

"시간이 거꾸로 흐르는" 현상 방지. 사용자가 서로 다른 지연을 가진 복제 서버에서 여러 번 읽으면, 나중 조회가 오히려 더 오래된 결과를 보여줄 수 있음(예: 새로고침했더니 방금 본 댓글이 사라짐).

단조 읽기는 강한 일관성보다는 약하지만 최종적 일관성보다는 강한 보장 → "한 번 새 데이터를 본 뒤에는 예전 데이터로 되돌아가지 않는다"는 것만 보장.

**구현 방법**: 각 사용자의 읽기가 항상 동일한 복제 서버에서 수행되게 함(예: 사용자 ID 해시값으로 서버 선택). 단, 그 서버가 고장나면 재라우팅 필요.

#### 6.3 일관된 순서로 읽기 (Consistent Prefix Read)

![5-5](/데이터%20중심%20애플리케이션%20설계/image/5장/5-5.png)

**인과성(causality)** 위반 문제. 예: A가 질문하고 B가 대답하는 대화를 제3자가 볼 때, 만약 어떤 파티션이 다른 파티션보다 느리게 복제되면 관찰자에게는 "질문하기도 전에 대답한" 것처럼 보일 수 있음.

이는 주로 **파티셔닝(샤딩)된** DB에서 발생하는 문제 - 서로 다른 파티션이 독립적으로 동작해서 전역적인 쓰기 순서가 없기 때문.

**해결책**: 서로 인과성 있는 쓰기가 동일한 파티션에 기록되게 하거나, 인과성을 명시적으로 추적하는 알고리즘 사용 (9장에서 자세히).

#### 지연 문제에 대한 최종 결론

이 모든 문제를 애플리케이션 코드에서 신경 쓰는 건 복잡하고 실수하기 쉽다.

DB가 "쓰기 후 읽기"같은 더 강한 보장을 기본으로 제공하는 게 이상적. → 이것이 바로 **트랜잭션**이 존재하는 이유!

(분산/파티셔닝된 시스템으로 넘어가면서 많은 시스템이 트랜잭션을 포기했는데, 이게 늘 필수적인 트레이드오프는 아니라는 게 저자의 입장 - 7장, 9장에서 재조명)

### 7. 다중 리더 복제 (Multi-Leader Replication)

리더 기반 복제의 단점: 리더가 하나뿐이라 리더에 연결 못 하면 쓰기가 완전히 막힘.

**해결**: 쓰기를 허용하는 노드를 하나 이상 두는 것 = **다중 리더**(마스터-마스터, 액티브/액티브 복제라고도 함). 각 리더는 동시에 다른 리더의 팔로워 역할도 함.

단일 데이터센터 내에서 다중 리더는 복잡도만 늘고 이점이 적어서 잘 안 씀. 하지만 아래 상황들에서는 유용:

**사용 사례 1: 다중 데이터센터 운영**

![5-6](/데이터%20중심%20애플리케이션%20설계/image/5장/5-6.png)

각 데이터센터에 리더 하나씩 두고, 데이터센터 간에는 서로 변경사항을 비동기로 복제.

| 비교 | 단일 리더 | 다중 리더 |
| --- | --- | --- |
| 성능 | 모든 쓰기가 리더가 있는 원격 데이터센터로 가야 해서 지연↑ | 로컬에서 처리 후 비동기 복제 → 사용자 체감 성능↑ |
| 데이터센터 중단 내성 | failover로 다른 DC의 팔로워를 승격 | 각 DC가 독립 동작, 복구되면 다시 따라잡음 |
| 네트워크 문제 내성 | DC 내부 동기 연결 문제에 민감 | 비동기라 일시적 네트워크 중단에도 잘 견딤 |

**큰 단점**: 서로 다른 두 DC에서 동일 데이터를 동시에 바꿀 수 있음 → **쓰기 충돌**이 반드시 발생 → 해소 필요.

**사용 사례 2: 오프라인 작업 클라이언트**

캘린더 앱처럼 인터넷 연결 여부와 무관하게 동작해야 하는 앱. 각 디바이스가 사실상 "하나의 데이터센터" 역할을 하는 로컬 리더를 가짐. 복제 지연이 몇 시간~며칠까지 늘어날 수 있음.

**사용 사례 3: 협업 편집 (Collaborative Editing)**

Etherpad, Google Docs처럼 여러 사람이 동시에 문서를 편집하는 앱.

- 엄밀히는 DB 복제 문제라기보다, 오프라인 편집과 유사한 구조
- 충돌 없게 하려면 편집 전 문서 잠금(락) 필요 → 단일 리더 복제와 유사한 구조가 됨
- 더 빠른 협업을 위해 잠금을 아주 작은 단위(예: 키 입력 하나)로 하면 → 다중 리더 복제와 동일한 충돌 문제 발생

#### 7.1 쓰기 충돌 다루기

![5-7](/데이터%20중심%20애플리케이션%20설계/image/5장/5-7.png)

예: 위키 페이지 제목을 사용자1은 A→B로, 사용자2는 같은 시각 A→C로 동시에 변경 → 각자 로컬 리더에서는 성공했지만, 비동기 복제되면서 충돌 감지됨. (단일 리더였다면 애초에 발생 안 했을 문제)

**충돌 감지 시점**:

- **동기 감지**: 쓰기를 확정하기 전에 모든 복제 서버가 받을 때까지 기다림 → 하지만 이건 다중 리더의 핵심 장점(각 서버가 독립적으로 쓰기 허용)을 잃는 것 → 사실상 단일 리더로 돌아가는 셈
- **비동기 감지**: 나중에서야 충돌을 알게 됨 → 그때는 사용자에게 해소를 요청하기엔 너무 늦을 수 있음

**해소 방법들**:

1. **충돌 회피**: 애초에 충돌이 안 나게 설계, 특정 레코드의 모든 쓰기가 항상 같은 리더(=같은 홈 데이터센터)를 거치도록 라우팅. 다만 DC 장애로 라우팅이 바뀌면 회피가 깨질 수 있음
2. **일관된 상태로 수렴(convergence)**: 모든 복제 서버가 결국 동일한 최종 값에 도달하게 만드는 방법들
    - 각 쓰기에 고유 ID(타임스탬프, UUID, 해시 등) 부여 → 가장 높은 ID를 가진 것이 승리 = **최종 쓰기 승리(LWW, Last Write Wins)** → 간단하지만 데이터 유실 위험 있음
    - 각 복제 서버에 고유 ID를 부여하고 ID 숫자가 높은 서버의 쓰기를 우선 → 역시 데이터 유실 가능
    - 값을 병합 (예: "B"와 "C"를 사전순으로 합쳐 "B/C")
    - 충돌 자체를 명시적 데이터 구조에 기록해두고, 나중에 애플리케이션 코드로 해소 (사용자에게 메시지 보여줌 등)
3. **사용자 정의 충돌 해소 로직**: 애플리케이션 코드가 쓰기 시점 또는 읽기 시점에 실행됨. 예) 부카르도는 충돌 시 펄 코드로 핸들러 실행
4. **자동 충돌 해소 연구**:
    - **CRDT(충돌 없는 복제 데이터타입)**: 셋, 맵, 카운터 등을 위한 자료구조로 동시 편집을 자동으로 합리적으로 해소. Riak 2.0에서 일부 구현
    - **병합 가능한 영속 데이터 구조**: Git과 유사하게 히스토리를 명시적으로 추적, 3방향 병합 사용
    - **운영 변환(operational transformation)**: Etherpad, Google Docs 같은 협업 편집 앱의 충돌 해소 알고리즘. 정렬된 리스트(문서 내 문자 목록)의 동시 편집을 위해 설계됨

> **자동 충돌 해소**: 아마존 장바구니의 충돌 해소 로직은 "추가한 상품은 보존, 삭제한 상품은 보존 안 함" → 그래서 가끔 이미 삭제한 상품이 장바구니에 다시 나타나는 부작용이 있었다고 함.
> 

#### 7.2 다중 리더 복제 토폴로지

![5-8](/데이터%20중심%20애플리케이션%20설계/image/5장/5-8.png)

**복제 토폴로지** = 쓰기가 한 노드에서 다른 노드로 전달되는 경로 구조. 리더가 2개면 경로는 하나뿐이지만, 3개 이상이면 여러 형태 가능:

- **(a) 원형(circular) 토폴로지**: 각 노드가 하나의 노드로부터만 받고 하나에게만 전달 (MySQL 기본)
- **(b) 별 모양(star) 토폴로지**: 지정된 루트 노드 하나가 나머지 모든 노드에 전달 (트리로 일반화 가능)
- **(c) 전체 연결(all-to-all) 토폴로지**: 모든 리더가 각자의 쓰기를 다른 모든 리더에게 전송 — 가장 일반적으로 쓰임

**원형/별 모양의 문제점**: 노드 하나가 장애나면 그 노드를 거쳐야 하는 복제 흐름 전체가 막힘 (복구될 때까지). → 재설정으로 우회할 수 있지만 대부분 수동 작업 필요.

![5-9](/데이터%20중심%20애플리케이션%20설계/image/5장/5-9.png)

**전체 연결의 문제점**: 일부 네트워크 연결이 다른 연결보다 빠르면, 특정 복제 메시지가 다른 메시지를 "추월"할 수 있음 → 잘못된 순서로 도착 (예: 갱신 메시지가 그 갱신의 전제가 되는 삽입 메시지보다 먼저 도착) → 인과성 위반 문제(위 6-3절과 같은 종류) 발생. 각 쓰기에 노드 식별자를 태깅해서 무한 루프는 방지하지만, 순서 문제 자체는 별도 대응(**버전 벡터** 등)이 필요.

### 8. 리더 없는 복제 (Leaderless Replication)

리더 개념 자체를 버리고, **모든 복제 서버가 클라이언트로부터 직접 쓰기를 받을 수 있게** 하는 방식.

- 초창기 복제 DB들은 대부분 리더가 없었는데, 관계형 DB가 우세해지며 잊혀졌다가 아마존 내부 **다이나모(Dynamo)** 시스템에서 부활 → Riak, Cassandra, Voldemort 등 "다이나모 스타일" 오픈소스 데이터스토어의 뿌리가 됨
- 클라이언트가 직접 여러 복제 서버에 쓰기를 보내는 방식도 있고, **코디네이터 노드**가 클라이언트 대신 이 역할을 하기도 함. 단, 리더와 달리 코디네이터는 특정 순서로 쓰기를 수행하지 않음

#### 8.1 노드가 다운됐을 때 쓰기

![5-10](/데이터%20중심%20애플리케이션%20설계/image/5장/5-10.png)

리더 기반이라면 노드가 하나 죽으면 failover가 필요하지만, 리더 없는 구조에서는 **장애 복구 개념 자체가 필요 없음**.

예: 복제 서버 3개 중 1개가 다운된 상태에서 클라이언트가 3개 모두에 병렬로 쓰기 전송 → 2개만 응답(ok) 받으면 성공으로 간주하고 나머지 하나가 놓친 건 무시.

이후 다운됐던 노드가 복구되면, 놓친 쓰기 때문에 **오래된(outdated) 값**을 갖고 있을 수 있음 → 클라이언트가 그 노드에서 읽으면 옛날 데이터를 받을 위험.

**이 문제를 위해 클라이언트는 하나의 노드가 아니라 여러 노드에 병렬로 읽기 요청을 보냄** → 여러 응답 중 버전 번호로 최신값 판단.

**두 가지 복구(따라잡기) 메커니즘**:

1. **읽기 복구(read repair)**: 클라이언트가 여러 노드에서 읽었을 때 오래된 응답을 발견 → 그 자리에서 새 값을 다시 써줌. 자주 읽는 값에 적합
2. **안티 엔트로피 처리(anti-entropy process)**: 백그라운드 프로세스가 지속적으로 복제 서버 간 데이터 차이를 찾아 누락분을 복사. (특정 순서 없이 동작하므로 데이터가 복사되기까지 지연이 있을 수 있음)
    - 안티 엔트로피가 없으면(예: Voldemort) 거의 안 읽는 값은 일부 복제본에서 계속 누락된 채로 남아 내구성이 떨어짐

#### 8.2 읽기와 쓰기를 위한 정족수(Quorum)

- **n** = 복제 서버 개수
- **w** = 쓰기가 성공했다고 간주하려면 확인해야 하는 최소 노드 수
- **r** = 읽기 시 질의해야 하는 최소 노드 수

**w + r > n** 이면, 읽은 r개 노드 중 적어도 하나는 반드시 최신 값을 갖고 있다는 것이 보장됨 (읽기 집합과 쓰기 집합이 항상 겹치기 때문). 이런 r, w 조건을 따르는 읽기/쓰기를 **정족수 읽기/쓰기**라 부름.

![5-11](/데이터%20중심%20애플리케이션%20설계/image/5장/5-11.png)

일반적인 선택: n을 홀수(3 또는 5)로 하고 w = r = (n+1)/2 (반올림). 상황에 따라 조정 가능:

- w = n, r = 1: 읽기는 빠르지만 노드 하나만 죽어도 모든 쓰기 실패
- w < n 이면: 노드 일부가 죽어도 쓰기 가능
- r < n 이면: 노드 일부가 죽어도 읽기 가능

**정족수 일관성의 한계:** w+r>n 이어도 완벽하지 않다

- 느슨한 정족수를 쓰면 w개 쓰기와 r개 읽기가 겹친다는 보장이 없음
- 두 쓰기가 동시에 발생하면 어느 게 먼저인지 불명확 → 결국 합쳐야 함(최종 쓰기 승리를 쓰면 시계 오차로 유실 가능)
- 쓰기가 읽기와 동시에 발생하면 읽기가 예전 값/최신 값 중 뭘 받을지 불분명
- 쓰기가 일부 서버에선 성공, 일부에선 실패해서 성공한 서버 수가 w보다 적으면 롤백되지 않음 → 이후 읽기가 이 값을 반환할 수도, 안 할 수도 있음
- 새 값을 가진 노드가 고장나면 예전 값을 가진 노드로 복원될 수 있음 → 정족수 조건이 깨짐

→ 다이나모 스타일 DB는 대개 최종적 일관성 용도로 최적화되어 있어서, w/r로 오래된 값을 읽을 확률을 조정할 순 있지만 **절대적으로 보장하지는 못함**. "자신이 쓴 내용 읽기"·"단조 읽기"·"일관된 순서 읽기" 같은 보장을 대개 못 받는다는 뜻.

#### 8.3 느슨한 정족수(sloppy quorum)와 암시된 핸드오프(hinted handoff)

큰 클러스터에서 네트워크 장애 시, 클라이언트가 지정된 "홈" n개 노드가 아닌 다른 접속 가능한 노드에 연결될 수 있음. 이때 선택지:

- w나 r 정족수를 못 채우면 오류를 반환할지
- 아니면 일단 쓰기를 받아들이고 (원래 저장돼야 할 n개 노드가 아니지만) 접속 가능한 노드에 임시로 기록할지

후자를 **느슨한 정족수**라 부름

비유하자면 "내 집 문이 잠겨서 못 들어가면 이웃집에 잠깐 맡기는 것". 네트워크 장애가 풀리면 임시로 받아준 노드가 원래 "홈" 노드로 데이터를 전송 = **암시된 핸드오프**.

느슨한 정족수는 쓰기 가용성을 높이지만 진짜 의미의 정족수는 아님

최신 값이 지정된 n개 노드 밖에 임시로 있을 수 있어서, w+r>n 이어도 최신 값을 읽는다는 보장이 안 됨. (모든 다이나모 구현에서 선택 사항: Riak은 기본 활성화, Cassandra·Voldemort는 기본 비활성화)

#### 8.4 다중 데이터센터 운영

리더 없는 복제도 동시 쓰기 충돌·네트워크 중단·지연 급증을 원래부터 허용하는 구조라서 다중 DC 운영에 적합. Cassandra와 Voldemort는 일반적인 리더 없는 모델에 다중 DC 지원을 구현했고, 클라이언트 쓰기는 모든 DC의 모든 복제 서버로 전송되지만 보통 **로컬 DC 안**의 정족수 노드 확인만 기다림 → DC 간 지연/중단에 영향을 덜 받음.

#### 8.5 동시 쓰기 감지 (Detecting Concurrent Writes)

다이나모 스타일 DB는 여러 클라이언트가 동시에 같은 키에 쓰는 걸 허용 → 엄격한 정족수를 써도 충돌은 발생함 (읽기 복구/암시된 핸드오프 도중에도 발생 가능).

문제는 **네트워크 지연과 부분 장애 때문에 이벤트가 노드마다 다른 순서로 도착**할 수 있다는 것.

![5-12](/데이터%20중심%20애플리케이션%20설계/image/5장/5-12.png)

예: 두 클라이언트 A, B가 키 X에 동시에 쓸 때,

노드 1은 A→못받음(B는 장애),

노드2는 A→B 순서,

노드3은 B→A 순서로 받으면

→ 그냥 "각 노드가 받은 순서대로 마지막에 도착한 값을 채택"하면 **노드마다 최종값이 달라져서 영구적으로 일관성이 깨짐**.

**최종 쓰기 승리(LWW, "동시 쓰기 버리기")**:

- 어떤 쓰기가 "최신"인지 임의로 정하는 방법. 보통 타임스탬프를 붙여서 가장 큰 타임스탬프를 채택하고 나머지는 버림
- "최신"이라는 표현 자체가 오해의 소지 있음. 클라이언트는 다른 클라이언트의 쓰기를 모르기 때문에 어느 게 먼저인지 실제로 알 수 없음. 그냥 **동시 쓰기**라고 부르는 게 맞음
- Cassandra에서 유일하게 제공하는 충돌 해소 방법, Riak에서는 선택적 기능
- **단점**: 지속성을 희생함. 클라이언트에게 모두 성공했다고 보고돼도(w개 서버에 저장은 됐지만) 결국 하나만 남고 나머지는 조용히 무시됨. 동시가 아닌 쓰기도 삭제될 수 있음
- LWW를 안전하게 쓰는 유일한 방법: **키를 한 번만 쓰고 이후엔 불변값으로 취급** (예: Cassandra는 UUID를 키로 써서 매 쓰기마다 고유 키를 부여하도록 권장)

#### 8.6 "이전 발생(happens-before)" 관계와 동시성

두 작업이 동시에 일어났는지 어떻게 판단할까?

- 작업 B가 작업 A에 대해 알거나, A에 의존하거나, A를 기반으로 한다면 → A는 B의 **이전 발생(happens-before)**
- 어느 쪽도 서로를 모른다면(=서로에게 의존하지 않으면) → 단순히 **동시 작업**

세 가지 가능성: A가 B보다 먼저, B가 A보다 먼저, 또는 A와 B가 동시.

이걸 판단하는 알고리즘이 필요한 이유: 한 작업이 다른 작업 뒤에 일어난 게 확실하면 나중 것이 이전 것을 덮어써도 되지만, 동시라면 충돌을 반드시 해소해야 하기 때문.

> 💭 **동시성과 상대성**: "같은 시각"에 일어났다는 물리적 시간의 겹침 여부는 중요하지 않다.
분산 시스템에서는 시계 문제로 정확히 같은 시각을 아는 게 실제로 매우 어렵다.
핵심은 "각 작업이 서로 알고 있었는가"이다.
(이는 물리학의 상대성 이론과도 유사한 개념: 정보는 빛의 속도보다 빠를 수 없어서, 거리 대비 시간 간격이 짧으면 두 이벤트는 서로 영향을 못 줌. 컴퓨터 시스템에서도 네트워크 지연/중단으로 한 작업이 다른 작업에 대해 알 수 없다면, 시간 간격을 두고 일어났어도 동시로 취급함)
> 

#### 8.7 이전 발생 관계 파악하기 (실제 알고리즘, 예시로 장바구니)

단일 복제본 DB를 예로: 두 클라이언트가 같은 장바구니에 동시에 상품을 추가하는 과정.

![5-13](/데이터%20중심%20애플리케이션%20설계/image/5장/5-13.png)

1. 클라이언트1이 우유 추가 → 서버는 버전 1 할당, 저장하고 값을 클라이언트에 반환
2. 클라이언트2가 (클라이언트1의 쓰기를 모른 채) 달걀 추가 → 서버는 버전 2 할당, [달걀, 우유]를 별도 값으로 저장해 반환
3. 클라이언트1이 (클라이언트2가 쓴 걸 모른 채, 이전 응답인 버전1+[우유]를 기반으로) 밀가루 추가 → 서버는 [우유, 밀가루]가 [달걀]과 동시라는 걸 인식 → [우유,밀가루]는 버전3, [달걀]은 버전2로 유지, 둘 다 클라이언트에 반환
4. 클라이언트2가 (직전 응답에서 받은 [우유]+[달걀] 두 값을 합쳐) 햄을 추가한 [달걀,우유,햄]을 버전2를 달고 전송 → 서버는 버전2인 [달걀]을 덮어쓰지만, [우유,밀가루]는 동시 발생이라 버전3으로 유지, [달걀,우유,햄]은 버전4가 됨
5. 클라이언트1이 (버전3의 [우유,밀가루]와 [달걀] 기반으로) 베이컨 추가 → [우유,밀가루,달걀,베이컨]을 버전3으로 전송 → [우유,밀가루]는 덮어쓰지만 [달걀]은 이미 이전 단계에서 덮어써짐. 서버는 달걀, 우유, 햄이 동시 발생이라 유지

![5-14](/데이터%20중심%20애플리케이션%20설계/image/5장/5-14.png)

**핵심 규칙 3가지**:

- 서버는 키의 새 버전 번호를 매 쓰기마다 증가시켜 관리하고, 클라이언트에게 값 읽을 때 **최신 버전뿐 아니라 아직 덮어써지지 않은 모든 값**을 함께 반환
- 클라이언트는 쓰기 전에 반드시 키를 먼저 읽어야 하고, 쓸 때는 **이전 읽기에서 받은 버전 번호**와 **그때 받은 모든 값을 병합한 것**을 함께 서버로 보내야 함
- 서버가 특정 버전 번호를 포함한 쓰기를 받으면, 그 버전 이하의 모든 값은 덮어쓸 수 있지만, 그보다 높은 버전 번호의 값들은 유지해야 함 (동시에 발생한 다른 쓰기이기 때문)

#### 8.8 동시에 쓴 값 병합

이 알고리즘은 데이터가 자동으로 삭제되지 않는 건 보장하지만, 클라이언트가 추가로 "병합" 작업을 해줘야 함. 이런 동시 값들을 Riak에서는 **형제(sibling)** 값이라고 부름.

**형제 값 병합** = 다중 리더 복제의 충돌 해소와 본질적으로 같은 문제.

- 장바구니라면 **합집합(union)**을 취하는 게 합리적 (우유·달걀이 두 형제 모두에 있어도 중복 없이 한 번만)
- 단, 상품 **제거(삭제)**를 지원하려면 문제 발생: 두 형제를 합치면 삭제된 상품이 다시 나타남 → 이를 막으려면 삭제 시 실제 삭제 대신, "이 버전에서 이 상품을 제거했다"는 표시(**툼스톤, tombstone**)를 남겨둬야 함. (3장의 로그 컴팩션에서 나온 개념과 동일)

### 8-9. 버전 벡터 (Version Vector)

앞의 장바구니 예제(8-7)는 **단일 복제본**을 기준으로 만든 알고리즘이었다. 그런데 리더 없는 복제는 애초에 **다중 복제본**이 전제인데, 리더가 없으니 이 알고리즘을 어떻게 확장해야 할까?

- 8-7에서는 작업 간 의존성 파악을 위해 **키당 단일 버전 번호**만 사용했다. 하지만 이 방식은 **복제본이 여러 개일 때 동시 쓰기를 받는 상황**을 다루기엔 부족하다.
- 그래서 키당 버전 번호뿐 아니라 **복제본당 버전 번호**도 함께 사용해야 한다. 즉:
    - 각 복제본은 자신이 쓰기를 처리할 때마다 **자체 버전 번호**를 증가시키고
    - 동시에 **다른 복제본들의 버전 번호**도 계속 추적해야 한다
    - 이 정보로 "어떤 값을 덮어써도 되는지"와 "어떤 값을 형제(동시 값)로 유지해야 하는지"를 구분할 수 있다

**모든 복제본의 버전 번호 모음** = **버전 벡터(version vector)**.

이를 변형한 방식 중 하나가 Riak 2.0에서 쓰는 **도티드 버전 벡터(dotted version vector).**

세부 구현은 다르지만 작동 방식은 장바구니 예제와 매우 유사하다.

**사용 방식**은 8-7의 단일 버전 번호 때와 동일한 흐름이다:

1. 값을 읽을 때 데이터베이스 복제본이 클라이언트에게 버전 벡터를 함께 보냄
2. 클라이언트가 값을 다시 쓸 때 이 버전 벡터를 데이터베이스로 다시 전송
3. (Riak은 이 버전 벡터를 **인과성 컨텍스트(causal context)**라 부르는 문자열로 부호화해서 전달함)

이렇게 버전 벡터를 사용하면 DB가 **덮어쓰기**와 **동시 쓰기**를 명확히 구분할 수 있다. 단일 복제본 예제와 마찬가지로, 애플리케이션은 여전히 형제(동시 값)를 병합해야 할 수도 있다. 하지만 버전 벡터 구조 덕분에 "하나의 복제본을 읽고 → 다른 복제본에 다시 쓰는" 작업이 안전하다는 것이 보장된다. 형제가 생겨도 올바르게 병합되는 한 데이터 손실은 없다.

> 💭 **버전 벡터 vs 벡터 시계**: 종종 버전 벡터를 "벡터 시계"라고 부르기도 하지만 둘은 완전히 같은 개념은 아니다(미묘한 차이가 있음). 간단히 말하면, **복제본 상태를 비교할 때 사용해야 할 올바른 데이터 구조가 버전 벡터**라고 기억하면 된다.

### 정리 원문 요약

이번 장에서는 **복제**를 다뤘다. 복제는 다양한 용도로 쓰일 수 있다:

- **고가용성**: 한 장비(또는 여러 장비, 전체 데이터센터)가 다운돼도 시스템이 계속 동작하게 함
- **연결이 끊긴 작업**: 네트워크 중단 중에도 애플리케이션이 계속 동작할 수 있게 함
- **지연 시간**: 사용자와 지리적으로 가까운 곳에 데이터를 배치해 더 빠르게 작업하게 함
- **확장성**: 복제본에서 읽기를 수행해 단일 장비가 감당하는 양보다 많은 읽기 작업을 처리

동일한 데이터의 복사본을 여러 장비에 유지한다는 목표 자체는 단순해 보이지만, 복제는 **매우 까다로운 문제**다. 동시성 문제, 그리고 잘못될 수 있는 모든 것들을 주의 깊게 생각해야 하고 그 결함의 결과도 신중히 다뤄야 한다. 최소한 노드 장애나 네트워크 중단 같은 것에는 반드시 대처해야 한다(소프트웨어 버그로 인한, 겉으로 드러나지 않는 데이터 오염 같은 경우까지는 고려하지 않더라도).

이 장에서 다룬 **복제의 3가지 주요 접근 방식**:

| 방식 | 동작 |
| --- | --- |
| **단일 리더 복제** | 클라이언트가 모든 쓰기를 단일 노드(리더)로 전송 → 리더는 변경 이벤트 스트림을 다른 복제 서버(팔로워)로 전송. 읽기는 어떤 복제 서버든 가능하지만 팔로워의 읽기는 오래된 값일 수 있음 |
| **다중 리더 복제** | 클라이언트가 각 쓰기를 여러 리더 노드 중 하나(받아들일 수 있는 노드)로 전송 → 리더는 변경 이벤트 스트림을 다른 모든 리더와 팔로워로 전송 |
| **리더 없는 복제** | 클라이언트가 각 쓰기를 여러 노드로 전송하고, 여러 노드에서 병렬로 읽어 오래된 데이터를 감지하고 바로잡음 |

각 방식마다 장단점이 있다:

- **단일 리더 복제**: 이해하기 쉽고, 충돌 해소를 걱정할 필요가 없어서 널리 쓰인다.
- **다중 리더 복제 / 리더 없는 복제**: 결함 있는 노드, 네트워크 중단, 지연 시간 급증이 있는 상황에서 더 견고하다. 대신 설명하기 어렵고, 일관성 보장도 거의 없다는 게 단점이다.

복제는 동기식일 수도, 비동기식일 수도 있다. 이 차이는 시스템에 결함이 생겼을 때 동작에 큰 영향을 준다. 비동기 복제는 시스템이 원활할 때는 빠르지만, 리더가 고장 나고 (아직 최신화되지 않은) 팔로워가 새 리더로 승격되면 최근에 커밋된 데이터를 잃을 수 있다는 점을 항상 염두에 둬야 한다.

또한 복제 지연이 초래하는 몇 가지 이상 현상(자신이 쓴 내용 읽기, 단조 읽기, 일관된 순서로 읽기)과, 이를 대응하는 데 도움이 되는 일관성 모델도 살펴봤다.

마지막으로, 다중 리더 복제와 리더 없는 복제에 내재된 **동시성 문제**를 다뤘다: 여러 쓰기가 동시에 발생하는 상황을 허용하기 때문에 충돌이 생길 수 있다는 것. 한 작업이 다른 작업보다 먼저 발생했는지, 아니면 동시에 발생했는지 판단하는 알고리즘(이전 발생 관계)과, 동시 갱신을 병합해 충돌을 해소하는 방법(버전 벡터, 형제 병합)을 함께 배웠다.
