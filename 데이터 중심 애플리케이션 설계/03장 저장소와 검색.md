### 1. 데이터베이스를 강력하게 만드는 데이터 구조

#### 1.1 bash 두 줄로 만든 데이터베이스

저자는 아주 극단적으로 단순한 예시로 시작합니다. bash 함수 두 개로 데이터베이스를 만든 것입니다.

```bash
db_set () {
    echo "$1,$2" >> database
}
db_get () {
    grep "^$1," database | sed -e "s/^$1,//" | tail -n 1
}
```

- `db_set key value` → `database`라는 파일 맨 끝에 `key`와 `value`를 저장 가능.
- `db_get key` → 파일에서 그 키로 시작하는 줄을 전부 찾은 다음, **가장 마지막(최신) 줄**을 반환.

같은 키를 여러 번 갱신해도 **예전 값을 지우지 않고 계속 뒤에 추가**만 합니다

그래서 조회할 때는 가장 나중에 적힌 값이 진짜 값이라는 규칙(`tail -n 1`)으로 찾습니다.

**왜 이렇게 단순한 방식이 실제로 쓸모 있을까?**

- 쓰기(`db_set`)는 파일 끝에 추가만 하면 되니까 **엄청 빠릅니다**. 실제 많은 DB가 내부적으로 이런 추가 전용(append-only) 로그를 사용합니다.
- 하지만 읽기(`db_get`)는 최악입니다. 매번 파일 전체를 처음부터 끝까지 훑어야 하기 때문입니다. 데이터가 100만 줄이면 검색도 그만큼 오래 걸립니다. 이런 걸 **O(n)** 비용이라고 하는데, 쉽게 말해 데이터가 2배 늘면 검색 시간도 2배로 늘어난다는 뜻입니다.

이 문제(느린 검색)를 풀려면 **색인(index)**이 필요합니다.

#### 1.2 색인이란 무엇인가

색인은 쉽게 말해 **책의 보기 페이지**와 같습니다. 책 내용 자체를 바꾸는 게 아니라, 해당 섹션는 몇 쪽에 있다라는 정보를 별도로 만들어 두는 것이죠.

- 색인 = 원본 데이터에서 파생된 **추가 정보** (원본 내용에는 영향 없음, 검색 속도에만 영향)
- 그런데 세상에 공짜는 없습니다. **색인을 만들면 읽기는 빨라지지만, 쓸 때마다 색인도 같이 갱신해야 하니 쓰기는 느려집니다.**

이게 바로 저장소 설계에서 계속 등장하는 핵심 트레이드오프입니다.

그래서 DB는 보통 자동으로 모든 것을 색인하지 않습니다. 애플리케이션 개발자나 데이터베이스 관리자가 애플리케이션의 전형적인 질의 패턴에 대한 지식을 활용해 **수동으로 색인을 선택**해야 합니다.

### 2. 해시 색인

#### 2.1 기본 아이디어

먼저, 키-값 데이터를 색인해봅시다. 키-값 데이터가 색인할 수 있는 유일한 종류의 데이터는 아니지만 매우 일반적이고 더욱 복잡한 색인을 위한 구성 요소로 유용합니다.

키-값 저장소는 사전 타입(dictionary type)과 매우 유사합니다. 보통 이것을 해시 맵으로 구현합니다.

메모리에 **해시 맵**을 하나 만들어 둡니다. 다만 여기서는 값 자체를 저장하는 게 아니라, **이 키의 값은 파일의 몇 번째 바이트에 있다**는 위치 정보(byte offset)만 저장합니다.

![3-1](/데이터%20중심%20애플리케이션%20설계/image/3장/3-1.png)

- 새 데이터를 쓸 때 → 파일 끝에 추가하고, 해시 맵에도 key는 방금 쓴 위치에 있다고 기록
- 데이터를 읽을 때 → 해시 맵에서 위치를 찾은 뒤, 그 위치로 바로 점프해서 value를 읽음 (전체 스캔 불필요!)

이 방식을 실제로 쓰는 게 **비트캐스크(Bitcask)**, 분산 데이터베이스 **리악(Riak)**의 기본 저장소 엔진입니다.

- 모든 key가 램(메모리)에 들어가야 한다는 조건이 있지만, 그 대신 읽기/쓰기 모두 매우 빠름
- **value는 램보다 커도 괜찮음**
    - 어차피 value는 디스크에서 한 번의 탐색으로 읽어옴. 메모리에 있는 건 위치 정보뿐.
- 이런 특성 때문에 같은 키를 자주 갱신하지만 고유한 키의 개수는 많지 않은 워크로드에 잘 맞음
    - 예를 들어 고양이 동영상 URL(키) → 조회수(값) 같은 경우, 조회 버튼을 누를 때마다 값은 자주 바뀌지만 URL 종류 자체는 한정적

#### 2.2 그런데 디스크 공간은 무한하지 않다, 세그먼트와 컴팩션

계속 파일에 추가만 하면 디스크가 꽉 찹니다. 그래서 파일을 일정 크기마다 잘라서 여러 개의 **세그먼트(segment)**로 나눕니다. 하나가 다 차면 닫고 새 세그먼트를 만듭니다.

이제 오래된 세그먼트들을 정리해야 하는데, 여기서 **컴팩션(compaction)**이 등장합니다. 컴팩션은 중복된 키를 버리고 각 키의 최신 갱신 값만 유지하는 것을 의미합니다.

![3-1](/데이터%20중심%20애플리케이션%20설계/image/3장/3-2.png)

컴팩션은 보통 세그먼트를 더 작게 만들기 때문에 컴팩션과 함께 여러 세그먼트를 하나로 **병합(merge)**할 수도 있습니다.

![3-1](/데이터%20중심%20애플리케이션%20설계/image/3장/3-3.png)

이때 중요한 규칙 하나: **세그먼트 파일은 한 번 쓰이면 절대 수정하지 않습니다.**

병합 결과는 항상 새 파일로 만들어집니다. 이 작업은 백그라운드에서 조용히 진행되고, 그동안에도 사용자는 기존 세그먼트로 정상적으로 읽고 쓸 수 있습니다.

#### 2.3 실제로 구현할 때 고려해야 할 사항

| 고려사항 | 설명 |
| --- | --- |
| 파일 형식 | CSV 같은 텍스트보다는, 길이를 먼저 적고 그 다음 원본 문자열을 그대로 쓰는 **바이너리 형식**이 더 빠르고 간단 |
| 레코드 삭제 | 삭제하고 싶으면 실제로 지우는 게 아니라 이 키는 삭제됨이라는 특수 표시(**톰스톤**, tombstone, 무덤 비석이라는 뜻처럼 여기 죽은 데이터가 있다는 표식)를 추가함 |
| 고장 복구 | 서버가 꺼졌다 켜지면 메모리에 있던 해시 맵이 사라짐. 파일을 처음부터 다시 읽어 복원할 수 있지만 시간이 오래 걸리므로, 비트캐스크는 해시 맵의 **스냅숏(snapshot, 특정 시점의 상태를 통째로 찍어둔 것)**을 디스크에 저장해 복구를 빠르게 함 |
| 부분 쓰기 | 기록 도중 서버가 죽으면 파일 일부가 깨질 수 있음 → **체크섬**(데이터가 손상됐는지 확인하는 검증값)으로 감지해서 무시 |
| 동시성 제어 | 보통 **쓰기는 한 스레드만** 담당(순서를 지키기 위해), **읽기는 여러 스레드가 동시에** 가능(파일이 불변이라 안전함) |

#### 2.4 추가만 하는 방식이 왜 오히려 좋은 설계인가

언뜻 보면 그냥 덮어쓰면 되지 왜 이렇게 복잡하게?라는 생각이 들 수 있습니다. 하지만 추가 전용 방식에는 확실한 장점이 있습니다.

- **순차 쓰기가 훨씬 빠름**
    - 하드디스크는 헤드가 이리저리 움직이는 것(무작위 쓰기)보다, 한 방향으로 쭉 이어서 쓰는 것(순차 쓰기)이 훨씬 효율적입니다. (SSD 일부도 순차 쓰기를 선호합니다.)
- **동시성 문제와 고장 복구가 단순해짐**
    - 파일이 절대 바뀌지 않으니(불변, immutable), 쓰는 도중에 죽으면 어떡하지라는 걱정을 크게 덜 수 있습니다.
- **파편화 방지**
    - 오래된 세그먼트를 병합하면서 자연스럽게 정리가 되어, 디스크에 자잘한 빈 공간이 여기저기 흩어지는 문제를 피할 수 있습니다.

#### 2.5 해시 색인의 한계

- 모든 키가 **메모리에 다 들어가야** 함 (키가 너무 많으면 곤란)
- **범위 검색에 매우 취약함**
    - 예를 들어 kitty00000부터 kitty99999 사이의 모든 키를 찾으려면 해시 맵은 하나하나 다 뒤져봐야 합니다. 정렬돼 있지 않기 때문입니다.

이 두 번째 한계를 해결하는 게 다음 주제, SS테이블입니다.

### 3. SS테이블과 LSM 트리

#### 3.1 세그먼트를 정렬해보자: SS테이블

아이디어는 간단합니다. 세그먼트 안의 키-값 쌍을 **키 순서대로 정렬**해서 저장하자는 것입니다.

이걸 **SS테이블(Sorted String Table, 정렬된 문자열 테이블)**이라고 부릅니다.

정렬만 했을 뿐인데 세 가지 큰 장점이 생깁니다.

1. **병합이 쉬워짐**
    
    ![3-1](/데이터%20중심%20애플리케이션%20설계/image/3장/3-4.png)
    
    1. 이미 정렬된 여러 파일을 합치는 건 마치 카드 여러 묶음을 정렬된 채로 하나로 합치는 것과 같습니다(병합정렬, mergesort).
    2. 파일이 메모리보다 커도 효율적으로 처리 가능합니다.
2. **메모리에 모든 키를 담을 필요가 없어짐**
    
    ![3-1](/데이터%20중심%20애플리케이션%20설계/image/3장/3-5.png)
    
    1. 정렬돼 있으니 handbag의 위치와 handsome의 위치만 알아도, handiwork는 그 사이 어딘가에 있다는 걸 알 수 있습니다.
    2. 그래서 몇 킬로바이트에 하나씩만 위치를 기록해두는 **희소 색인(sparse index, 듬성듬성이라는 뜻으로 이해하면 됩니다)**만 있으면 충분합니다.
3. **압축이 쉬워짐**
    1. 어차피 범위로 스캔해야 하니, 레코드들을 몇 개씩 묶어서(블록) 압축해도 됩니다. 디스크 공간도 아끼고 읽기 속도도 빨라집니다.

#### 3.2 SS테이블은 어떻게 만들어지는가 (LSM 트리 알고리즘)

그런데 실제 쓰기는 임의의 순서로 들어옵니다. 그런데 어떻게 이미 정렬된 파일을 만들 수 있을까요?

답: **메모리에서 먼저 정렬한 다음, 디스크에는 나중에 씁니다.**

1. 쓰기가 들어오면 일단 메모리 안의 정렬된 트리 구조(레드-블랙 트리 등)에 넣습니다. 이걸 **멤테이블(memtable)**이라고 부릅니다.
2. 멤테이블이 어느 정도 커지면(수 메가바이트) → 이미 정렬된 상태이므로 그대로 SS테이블 파일로 디스크에 씁니다.
3. 읽을 때는 멤테이블 먼저 확인 → 없으면 최신 디스크 세그먼트 → 그다음 오래된 세그먼트 순으로 확인합니다.
4. 백그라운드에서 세그먼트들을 계속 병합·컴팩션합니다.

**한 가지 위험**: 멤테이블은 메모리에만 있으므로, 디스크에 아직 안 쓴 상태에서 서버가 죽으면 최근 쓰기가 날아갑니다.
**해결책**: 쓰기가 들어올 때마다 별도의 **로그 파일**(순서 상관없이 그냥 쭉 추가만 하는 파일)에도 동시에 기록해둡니다. 멤테이블이 디스크로 무사히 넘어가면 이 로그는 버려도 됩니다.

#### 3.3 SS테이블에서 LSM 트리 만들기

이 구조 전체를 **LSM 트리(Log-Structured Merge-Tree, 로그 구조화 병합 트리)**라고 부릅니다.

이름을 풀어보면,

- Log-Structured(로그 구조화): 데이터를 추가 전용 로그 형태로 관리
- Merge(병합): 여러 세그먼트를 계속 합쳐나감
- Tree(트리): 정렬된 구조

**레벨DB, 록스DB, 카산드라, HBase** 같은 유명한 시스템들이 이 방식을 사용합니다.

검색 엔진인 **엘라스틱서치/솔라**의 내부 엔진인 **루씬(Lucene)**도 비슷한 원리를 씁니다(단어 → 그 단어가 등장하는 문서 목록을 정렬된 파일로 관리).

**핵심 개념 한 줄 요약**: 백그라운드에서 계속 작은 파일들을 큰 파일로 합쳐나가면, 데이터가 메모리보다 훨씬 커져도 문제없고, 디스크 쓰기는 항상 순차적이라 쓰기 속도가 매우 빠릅니다.

> 💡 **블룸 필터(Bloom filter)로 더 빠르게**
LSM 트리의 약점 하나: 존재하지 않는 키를 찾으려면 모든 세그먼트를 다 뒤져야 해서 느릴 수 있습니다. 이때 **블룸 필터**를 씁니다. 이건 이 키가 확실히 없다 또는 있을 수도 있다를 아주 빠르게 판별해주는 자료구조입니다. 없다고 나오면 디스크를 뒤질 필요조차 없어져서 큰 시간을 절약합니다.
> 

**컴팩션 전략 두 가지**

- **크기 계층(size-tiered)**: 비슷한 크기의 작은 SS테이블들을 큰 것에 계속 붙여나감 (HBase)
- **레벨 컴팩션(leveled)**: 데이터를 레벨별로 나눠서 점진적으로 정리 (레벨DB, 록스DB, 이름 자체가 여기서 나옴)
- 카산드라는 둘 다 지원

### 4. B 트리, 가장 오래되고 검증된 방식

#### 4.1 LSM 트리와는 완전히 다른 철학

B 트리는 1970년대에 등장해서 지금도 **대부분의 관계형 데이터베이스가 기본으로 사용하는 색인 구조**입니다.

SS테이블처럼 정렬된 키-값을 다루긴 하지만, 설계 철학이 완전히 다릅니다.

- LSM 트리: 가변 크기 **세그먼트**를 계속 새로 만들고 순차적으로 씀
- B 트리: 고정 크기 **페이지(보통 4KB)**를 만들어두고, 필요한 페이지만 **덮어쓰기**

따라서, 근본적으로 하드웨어와 좀 더 밀접한 관련이 있다.

#### 4.2 구조: 트리를 타고 내려가며 찾기

B 트리는 문자 그대로 나무(tree) 구조입니다.

![3-1](/데이터%20중심%20애플리케이션%20설계/image/3장/3-6.png)

- 한 페이지는 B 트리의 루트(root)로 지정됨. 색인에서 키를 찾으려면 루트에서 시작
- 페이지는 여러 키와 하위 페이지 참조를 포함. 각 하위 페이지는 키가 계속 이어지는 범위를 담당하고, 참조 사이의 키는 해당 범위 경계가 어디인지 나타냄
- 이걸 따라 계속 내려가면 **리프 페이지(leaf page, 나뭇잎처럼 맨 끝에 있는 페이지)**에 도착. 이 페이지는 각 키의 값을 포함하거나 값을 찾을 수 있는 페이지의 참조를 포함

한 페이지가 하위 페이지를 참조하는 수를 **분기 계수(branching factor)**라고 하는데, 보통 수백 개 정도입니다.

분기 계수가 크면 트리의 깊이가 낮아도 엄청나게 많은 데이터를 담을 수 있습니다. (예: 분기 계수 500, 4단계 트리 → 256TB까지 저장 가능)

![3-1](/데이터%20중심%20애플리케이션%20설계/image/3장/3-7.png)

n개의 키가 있어도 트리 깊이는 O(log n), 로그 함수라서 데이터가 아무리 늘어도 깊이는 아주 조금씩만 늘어납니다. 그래서 보통 3~4단계면 충분합니다.

#### 4.3 신뢰할 수 있는 B 트리 만들기: WAL

B 트리는 페이지를 **제자리에서 덮어씁니다.**

문제는, 삽입 같은 작업 중에는 여러 페이지를 동시에 고쳐야 할 때가 있는데,

그 도중에 서버가 죽으면 트리가 망가질 수 있다는 겁니다(부모-자식 관계가 깨진 **고아 페이지**가 생길 수 있음).

이를 막기 위해 **쓰기 전 로그(Write-Ahead Log, WAL)**를 씁니다.

> 💡 **WAL이란?**
이름 그대로 쓰기 전에 미리 적어두는 로그입니다.
실제로 B 트리 페이지를 고치기 **전에**, 나 이제 이렇게 바꿀 거야라는 내용을 먼저 별도 파일에 순서대로 기록해둡니다.
그러다 중간에 죽으면, 재시작할 때 이 로그를 다시 재생(replay)해서 트리를 원래 의도했던 상태로 복구합니다.
그래서 **재실행 로그(redo log)**라고도 부릅니다.
> 

여러 스레드가 동시에 B 트리를 건드릴 때는 **래치(latch, 가벼운 잠금장치)**로 보호합니다.

#### 4.4 B 트리 최적화

- **쓰기 시 복사(copy-on-write)**: WAL 대신, 바뀐 페이지를 새로운 위치에 쓰고 상위 페이지가 새 위치를 가리키게 함 (LMDB 등에서 사용)
- 페이지에 키를 축약해서 저장 → 분기 계수를 높여 트리를 더 납작하게
- 리프 페이지들을 디스크 상에서 최대한 순서대로 배치 (하지만 트리가 커지면 이게 점점 어려워짐)
- 리프 페이지끼리 옆 페이지를 가리키는 포인터를 추가 → 트리를 다시 안 타고도 순서대로 쭉 스캔 가능
- **프랙탈 트리**: 로그 구조화 개념을 일부 빌려온 변형

#### 4.5 B 트리 vs LSM 트리, 한눈에 비교

|  | LSM 트리 | B 트리 |
| --- | --- | --- |
| **쓰기 속도** | 대체로 더 빠름 | 상대적으로 느림 |
| **읽기 속도** | 상대적으로 느릴 수 있음 | 대체로 더 빠르고 예측 가능 |
| **디스크 사용 효율** | 압축이 잘 되고 파편화가 적음 | 페이지 분할 등으로 빈 공간이 생김(파편화) |
| **트랜잭션 처리** | 같은 키의 복사본이 여러 세그먼트에 흩어져 있을 수 있음 | 각 키가 한 곳에만 존재 → 락을 걸기 쉬워 강력한 트랜잭션 구현에 유리 |
- **LSM 트리가 왜 쓰기에 유리한가**:
    - B 트리는 데이터 하나를 최소 두 번 씁니다(WAL 한 번 + 실제 페이지 한 번).
    - 게다가 페이지 안의 몇 바이트만 바뀌어도 4KB 페이지 전체를 다시 써야 합니다.
    - 이렇게 실제 데이터 변경량보다 훨씬 많이 디스크에 쓰게 되는 현상을 **쓰기 증폭(write amplification)**이라고 합니다.
    - LSM 트리도 컴팩션 과정에서 쓰기 증폭이 발생하긴 하지만, 대체로 B 트리보다는 낮고 순차 쓰기 위주라 전체 쓰기 처리량이 더 높습니다. (SSD는 덮어쓸 수 있는 횟수에 한계가 있어서 쓰기 증폭이 특히 중요한 이슈입니다.)
- **LSM 트리의 단점**:
    - 백그라운드 컴팩션이 디스크 자원을 먹기 때문에, 읽기·쓰기 응답 시간이 가끔 들쭉날쭉해질 수 있습니다(B 트리가 더 예측 가능).
    - 컴팩션 속도가 쓰기 속도를 못 따라가면 세그먼트가 계속 쌓이는 문제도 생길 수 있어 모니터링이 필요합니다.
- **결론**: 어느 쪽이 항상 좋다는 정답은 없습니다.
    - B 트리는 데이터베이스 업계에 워낙 깊이 뿌리내려서 없어질 일은 없고, 새로운 시스템에서는 LSM 트리 계열이 점점 인기를 얻고 있습니다.
    - **실제 워크로드로 테스트해보고 결정하는 게 가장 확실합니다.**

### 5. 그 밖의 색인 구조들

#### 5.1 기본키 vs 보조 색인

- **기본키(primary key) 색인**: 로우/문서/정점을 고유하게 식별하는 키 (지금까지 설명한 게 다 이것)
- **보조 색인(secondary index)**: 기본키가 아닌 다른 칼럼에 거는 색인. 조인을 빠르게 해주는 핵심 도구. 문제는 값이 고유하지 않을 수 있다는 것 → 이 값을 가진 로우들의 목록을 저장하거나, 로우 식별자를 추가해서 고유하게 만드는 방식으로 해결

#### 5.2 색인 안에 무엇을 저장할 것인가

- **힙 파일(heap file) 방식**: 색인에는 실제 데이터의 위치만 저장하고, 진짜 데이터는 별도의 파일(특정 순서 없음)에 저장. 여러 보조 색인이 있어도 데이터 중복이 안 생겨서 효율적
    - 값이 커져서 원래 자리에 안 들어가면 새 위치로 옮기고, 옛 자리에는 여기 아니고 저쪽으로 가라는 **전방향 포인터(forwarding pointer)**를 남겨둠
- **클러스터드 색인(clustered index)**: 아예 색인 안에 실제 데이터를 통째로 저장 (예: MySQL InnoDB의 기본키). 힙 파일을 왔다갔다 하지 않아도 되니 읽기가 더 빠름
- **커버링 색인(covering index)**: 위 둘의 중간. 색인 안에 자주 쓰는 몇몇 칼럼만 같이 저장해서, 그 칼럼들만 필요한 질의는 원본 테이블까지 안 가도 답이 나오게 함

이런 것들은 결국 데이터를 한 번 더 복제하는 것이므로, 읽기는 빨라지지만 저장 공간이 더 들고 쓰기 비용도 늘어납니다.

#### 5.3 여러 칼럼을 한 번에 검색하려면

- **결합 색인(concatenated index)**: 여러 칼럼을 하나의 키로 이어붙임. 예를 들어 (성, 이름) 순서로 묶은 색인은 전화번호부와 비슷합니다, 성으로는 잘 찾지만, 이름만으로는 못 찾습니다(순서가 그렇게 안 돼있으니까요).
- **다차원 색인**: 지도 위의 위도·경도처럼 여러 축을 동시에 검색해야 할 때 필요. 일반 B 트리로는 두 조건을 동시에 만족하는 범위 검색이 어려워서, **R 트리** 같은 전용 구조를 씁니다(지리정보 라이브러리인 PostGIS가 이걸 사용). 색상(빨강·초록·파랑) 검색이나 (날짜, 기온) 검색 같은 데도 응용됩니다.

#### 5.4 오타까지 찾아주는 퍼지 검색

지금까지의 색인은 전부 정확히 일치해야 찾을 수 있었습니다. 하지만 검색창에 오타를 쳐도 결과가 나오는 경우가 있죠. 이걸 **퍼지(fuzzy, 애매모호한) 검색**이라고 합니다.

루씬은 **편집 거리(edit distance)**(한 글자를 몇 번 고치면 원하는 단어가 되는지 나타내는 값)를 활용해서, 오타가 있어도 비슷한 단어를 찾아줍니다.

#### 5.5 아예 다 메모리에 넣으면 안 될까?

지금까지의 방법들은 전부 디스크는 다루기 까다롭다는 전제에서 나온 해결책입니다.

그런데 요즘은 램이 저렴해져서 **인메모리 데이터베이스**(데이터를 통째로 메모리에 올려두는 DB)가 많이 등장했습니다. (레디스, 멤SQL 등)

재밌는 점: 인메모리 DB가 빠른 진짜 이유는 디스크를 안 읽어서가 아닙니다.

어차피 자주 쓰는 디스크 데이터는 OS가 알아서 메모리에 캐싱해두거든요.

진짜 이유는 **디스크에 저장하기 위한 복잡한 인코딩 작업 자체를 건너뛸 수 있어서**입니다.

레디스 같은 경우 메모리에만 두면 데이터가 날아갈 수 있으니, 디스크에 변경 로그를 남기거나 주기적으로 스냅숏을 찍어서 지속성을 확보하기도 합니다.

### 6. 관점 전환, 트랜잭션 처리(OLTP)와 분석(OLAP)

지금까지는 하나의 키로 소수의 레코드를 빠르게 찾고 고치는 상황을 다뤘습니다. 이제는 완전히 다른 사용 패턴을 살펴봅니다.

#### 6.1 OLTP: 우리가 흔히 아는 그 데이터베이스

- **OLTP(Online Transaction Processing, 온라인 트랜잭션 처리)**는 쇼핑몰 주문, 은행 이체처럼 **사용자가 직접 상호작용하며 소수의 레코드를 읽고 쓰는** 패턴입니다.

> 💡 여기서 트랜잭션은 꼭 ACID(원자성·일관성·격리성·지속성) 속성을 가져야 한다는 뜻이 아니라, 그냥 지연 시간이 짧은 읽기/쓰기의 묶음이라는 의미로 쓰입니다.
> 

#### 6.2 OLAP: 완전히 다른 종류의 질의

- **OLAP(Online Analytic Processing, 온라인 분석 처리)**는 다릅니다. 개별 레코드가 아니라 **수백만 건을 스캔해서 집계(합계, 평균, 개수 등)를 내는** 작업입니다.

예를 들면,

- 1월 매장별 총 매출은?
- 프로모션 기간 동안 바나나 판매량이 평소보다 얼마나 늘었는가?
- A 브랜드 기저귀와 가장 자주 같이 팔리는 유아식은?

이런 질의는 보통 **비즈니스 분석가**가 던지고, 그 결과가 회사 경영진의 의사결정 자료(**비즈니스 인텔리전스**)가 됩니다.

#### 6.3 OLTP vs OLAP 비교표

| 특성 | OLTP | OLAP |
| --- | --- | --- |
| 읽기 패턴 | 질의당 소수 레코드, 키 기준 | 다수 레코드를 집계 |
| 쓰기 패턴 | 사용자 입력, 저지연 | 대량 일괄 적재(ETL) |
| 주 사용자 | 최종 사용자 | 내부 분석가 |
| 데이터 관점 | 현재 최신 상태 | 시간에 따른 이력 |
| 크기 | GB~TB | TB~PB |

#### 6.4 왜 이 둘을 분리해서 관리할까: 데이터 웨어하우스

OLTP 데이터베이스는 서비스 운영에 매우 중요하기 때문에, 분석가가 무거운 질의를 마구 날리면 서비스 자체가 느려질 위험이 있습니다.

그래서 회사들은 별도의 **데이터 웨어하우스(data warehouse)**를 만듭니다.

여러 OLTP 시스템(주문 DB, 재고 DB, 배송 DB 등)에서 데이터를 뽑아내고(Extract),

분석하기 좋은 형태로 바꾸고(Transform),

웨어하우스에 쌓는(Load) 과정을 **ETL(Extract-Transform-Load)**이라고 합니다.

이렇게 분리하면 분석가가 아무리 무거운 질의를 던져도 실제 서비스(OLTP)에는 영향을 주지 않습니다.

### 7. 분석용 데이터를 어떻게 모델링할까: 별 모양 스키마

데이터 웨어하우스에서 자주 쓰이는 정형화된 설계 방식이 **별 모양 스키마(star schema)**입니다.

- 한가운데에 **사실 테이블(fact table)**: 실제로 벌어진 이벤트 하나하나(예: 판매 1건)를 기록. 로우 수가 어마어마하게 많을 수 있습니다.
- 그 주위를 둘러싼 **차원 테이블(dimension table)**: 그 이벤트의 누가/언제/어디서/무엇을 등 부가 정보 (고객, 날짜, 매장, 제품 등)

테이블 관계를 그림으로 그리면 사실 테이블이 중심에 있고 차원 테이블들이 별의 광선처럼 뻗어나가는 모양이라서 별 모양이라는 이름이 붙었습니다.

- **눈꽃송이 스키마(snowflake schema)**: 별 모양을 한 단계 더 정규화한 변형. 더 정돈되어 있지만, 분석가들은 다루기 편한 별 모양 쪽을 더 선호하는 편입니다.

### 8.칼럼 지향 저장소, 분석 질의를 위한 특별한 저장 방식

#### 8.1 왜 필요한가

사실 테이블은 칼럼이 100개가 넘기도 하지만, 실제 분석 질의는 보통 4~5개 칼럼만 사용합니다.

기존의 **로우 지향(row-oriented) 저장소**는 한 로우의 모든 칼럼 값을 나란히 붙여서 저장합니다(문서 DB와 비슷).

문제는, 5개 칼럼만 필요해도 디스크에서 **로우 전체(100개 이상의 칼럼)**를 읽어와야 한다는 점입니다. 불필요한 데이터를 잔뜩 읽는 셈이니 느립니다.

#### 8.2 발상의 전환: 칼럼별로 따로 저장하자

**칼럼 지향(column-oriented) 저장소**는 정반대로 접근합니다. 로우 단위가 아니라 **같은 칼럼끼리 모아서** 하나의 파일로 저장하는 것입니다.

이렇게 하면 질의에 필요한 칼럼 파일만 골라서 읽으면 되니, 작업량이 크게 줄어듭니다.

(참고: 카산드라·HBase의 칼럼 패밀리는 이름과 달리 실제로는 로우 지향에 가까우므로 헷갈리지 않아야 합니다.

진짜 칼럼 지향 형식의 예로는 문서 데이터도 지원하는 **파케이(Parquet)**가 있습니다.)

#### 8.3 칼럼 지향 저장소의 강력한 무기: 압축

같은 칼럼끼리 모아두면 **값이 반복되는 경우가 많아서 압축이 매우 잘 됩니다.**

대표적인 기법이 **비트맵 부호화(bitmap encoding)**입니다.

> 💡 쉽게 설명하면,
칼럼에 있는 고유한 값 하나하나마다 이 값을 가진 로우는 1, 아니면 0으로 표시한 비트 열(비트맵)을 만듭니다.
이러면 `WHERE product_sk IN (30, 68, 69)` 같은 조건은 세 개의 비트맵을 가져와 **OR 연산**만 하면 끝납니다.
여러 조건을 AND로 묶을 때도 비트맵끼리 AND 연산만 하면 되어서 매우 빠릅니다.
> 

값의 종류가 많아 비트맵에 0이 대부분이면(**희소하다**고 표현), **런 렝스 부호화(run-length encoding, 같은 값이 몇 번 반복되는지만 기록하는 압축법)**로 한 번 더 압축합니다.

#### 8.4 CPU까지 생각한 최적화: 벡터화 처리

압축된 칼럼 데이터를 CPU 캐시에 딱 맞게 잘라서 반복 처리하면(함수 호출 없이 단순 반복하는 타이트 루프), CPU가 훨씬 빠르게 처리할 수 있습니다.

이런 기법을 **벡터화 처리(vectorized processing)**라고 부릅니다.

#### 8.5 정렬까지 더하면?

칼럼 지향 저장소도 데이터를 특정 순서로 정렬해서 저장할 수 있습니다.

예를 들어 날짜 기준으로 1차 정렬해두면, 지난달 데이터를 찾는 질의는 전체를 다 안 보고 해당 구간만 스캔하면 됩니다.

정렬하면 압축 효과도 더 좋아집니다(같은 값이 연속으로 이어지니까요).

다만 이 효과는 **첫 번째 정렬 기준 칼럼**에서 가장 강력하고, 두 번째, 세 번째로 갈수록 약해집니다.

한 가지 재밌는 아이디어: 어차피 장애 대비로 데이터를 여러 서버에 복제해야 하니, **각 복제본을 서로 다른 기준으로 정렬해서 저장**하면 질의 종류에 따라 가장 적합한 복제본을 골라 쓸 수 있습니다 (버티카가 이 방식 사용).

#### 8.6 압축된 칼럼에 어떻게 쓰기를 할까

압축되고 정렬된 칼럼 한가운데에 새 로우를 끼워 넣으려면, 이론적으로는 전체 파일을 다시 써야 합니다.

이 문제는 **LSM 트리와 똑같은 방식**으로 해결합니다: 새 쓰기는 일단 메모리에 모아뒀다가, 어느 정도 쌓이면 한꺼번에 디스크의 칼럼 파일에 병합합니다.

#### 8.7 미리 계산해두기: 구체화 뷰와 데이터 큐브

똑같은 집계(합계, 평균 등)를 계속 반복해서 계산하는 건 낭비입니다. 그래서 결과를 미리 계산해서 디스크에 저장해두는 방법이 있습니다.

- **구체화 뷰(materialized view)**: 질의 결과를 실제로 디스크에 저장해두는 것. (참고로 일반 SQL 뷰는 그냥 질의를 저장해뒀다가 매번 다시 실행하는 것뿐이라 차이가 있습니다.) 원본이 바뀌면 뷰도 다시 계산해야 해서 쓰기 비용이 크므로, 읽기 위주인 데이터 웨어하우스에 적합합니다.
- **데이터 큐브(data cube)**: 여러 차원(날짜×제품×매장 등)으로 미리 집계해둔 특수한 구체화 뷰. 예를 들어 어제 매장별 총 판매량을 물으면, 원본 데이터를 다시 스캔할 필요 없이 미리 계산된 값을 바로 꺼내 씁니다.
- **단점**: 미리 정해둔 차원으로만 빠르게 조회할 수 있고, 예상 못 한 새로운 질문(예: 가격이 100달러 넘는 상품 비율은?, 가격은 차원이 아니므로)에는 유연하게 답할 수 없습니다. 그래서 대부분의 웨어하우스는 원본 데이터도 최대한 함께 보관합니다.
