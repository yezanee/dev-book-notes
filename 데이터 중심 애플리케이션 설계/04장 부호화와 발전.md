### 1. 왜 이 얘기가 중요한가

앱은 시간이 지나면 기능이 추가되거나 바뀐다. 그러면 저장하는 데이터의 형태(스키마)도 같이 바뀐다.

문제는, **코드가 모든 서버·모든 사용자에게 한 번에 배포되지 않는다**는 것이다.

- 서버는 한 대씩 순서대로 업데이트한다 (이걸 **순회식 업그레이드**라고 부른다. 서비스를 끄지 않고 한 대씩 갈아끼우는 방식)
- 클라이언트(앱, 브라우저)는 사용자가 업데이트를 언제 할지 모른다

즉, **신버전 코드와 구버전 코드가 한동안 같이 돌아간다.** 이때 데이터를 서로 읽을 수 있어야 하는데, 여기 두 가지 개념이 나온다.

| 용어 | 뜻 | 난이도 |
| --- | --- | --- |
| 하위 호환성 | 새 코드가 예전 데이터를 읽을 수 있다 | 쉬움 |
| 상위 호환성 | 예전 코드가 새 데이터를 읽을 수 있다 (자기가 모르는 필드는 무시하면 됨) | 어려움 |

그리고 **부호화(인코딩)** 라는 용어가 계속 나오는데, 별거 아니고 이런 뜻이다.

> **부호화**
메모리 속 객체(자바 객체, 파이썬 딕셔너리 등)를 파일에 저장하거나 네트워크로 보낼 수 있는 **바이트 덩어리**로 바꾸는 것.
반대로 바이트 덩어리를 다시 객체로 되돌리는 걸 **복호화**라고 한다.
>

### 2. 언어 내장 부호화 라이브러리 (비추천)

Java의 `Serializable`, Python의 `pickle`, Ruby의 `Marshal` 같은, 언어가 기본으로 제공하는 직렬화 기능들.

**편하지만 문제가 많다.**

- 그 언어에서만 읽을 수 있다 (다른 언어와 못 섞임)
- 보안 구멍이 될 수 있다 (복호화 과정에서 임의 코드가 실행될 위험)
- 버전 관리(호환성)를 신경 안 쓰고 만들어진 경우가 많다

**결론: 정말 임시로 쓰는 게 아니면 쓰지 말자.**

---

### 3. 텍스트 기반 형식: JSON / XML / CSV

가장 흔히 쓰는 형식들이지만, 생각보다 허점이 있다.

**1. 숫자가 애매하다**

- JSON은 **정수와 소수를 구분하지 않는다**
- 2의 53제곱보다 큰 정수는 자바스크립트에서 부정확해질 수 있다 (트위터가 트윗 ID를 문자열로도 같이 보내는 이유)

**2. 이진 데이터(사진, 파일 등)를 못 넣는다**

- JSON/XML은 텍스트만 지원 → 이진 데이터는 Base64로 우회해야 하는데, 이러면 크기가 33% 커진다

**3. 스키마가 있어도 강제가 안 된다**

- XML/JSON 스키마 언어가 있긴 하지만, 안 지켜도 그만인 경우가 많다

**4. CSV는 아예 스키마가 없다**

- 각 칸이 뭘 의미하는지는 순전히 앱이 알아서 해석해야 한다

그럼에도 이 형식들이 여전히 인기 있는 이유: **서로 다른 회사·팀 사이에 데이터를 주고받을 때는, 형식이 완벽한지보다 ‘다들 이걸 쓰기로 동의했다’는 게 훨씬 더 중요하기 때문**이다.

### 4. 스키마 기반 이진 부호화 (진짜 핵심 파트)

같은 데이터를 아래 형식들로 각각 부호화했을 때 크기 비교:

| 형식 | 크기 | 방식 |
| --- | --- | --- |
| JSON (텍스트) | 81바이트 | 기준 |
| MessagePack | 66바이트 | JSON을 이진으로만 바꿈 |
| Thrift (바이너리프로토콜) | 59바이트 | 필드 이름 대신 번호(태그) 사용 |
| Thrift (컴팩트프로토콜) | 34바이트 | 타입+번호를 압축 |
| Protocol Buffers | 33바이트 | Thrift와 거의 동일 원리 |
| Avro | **32바이트** | 필드 번호조차 없음, 가장 작음 |

#### 핵심 아이디어: 필드 이름 대신 스키마를 쓴다

> **스키마**란: 이 데이터는 **어떤 필드들로 구성되고, 각 필드는 무슨 타입인지**를 미리 정의해둔 명세서. 스키마가 있으면 부호화할 때 필드 이름을 매번 안 넣어도 되니까 훨씬 작아진다.
> 
- **Thrift / Protocol Buffers 방식**
    
    ```java
    struct Person {
      1: required string userName,
      2: optional i64 favoriteNumber,
      3: optional list<string> interests
    }
    ```
    
    - 필드 이름 대신 **번호(필드 태그)**를 붙여 관리한다. ‘1번은 userName이다’를 스키마가 기억하고 있으니, 실제 데이터에는 번호만 들어간다.
- **Avro 방식**
    
    ```java
    record Person {
      string userName;
      union { null, long } favoriteNumber = null;
      array<string> interests;
    }
    ```
    
    - 번호도 없다. 그냥 값들이 순서대로 나열되어 있을 뿐이다. 그래서 **읽는 쪽이 스키마를 미리 정확히 알고 있어야만** 해석이 가능하다. (반대로 그래서 제일 작다)

### 5. 스키마가 바뀌어도 안 깨지는 법 (= 스키마 발전)

#### Thrift / Protocol Buffers: "번호"로 관리한다

- **필드 추가**: 새 번호를 붙이면 된다. 예전 코드는 모르는 번호를 만나면 그냥 무시한다 → 상위 호환 OK
    - 단, 새 필드는 `optional`(선택)이어야 한다. `required`(필수)로 만들면 예전 데이터엔 그 필드가 없으니 에러가 난다
- **필드 삭제**: `optional`인 필드만 지울 수 있고, 그 번호는 앞으로 절대 재사용하면 안 된다 (예전 데이터가 그 번호로 남아있을 수 있어서)
- **필드 이름 변경**: 가능하다 (데이터엔 이름이 아니라 번호만 있으니까)
- **타입 변경**: 가능은 하지만 값이 잘릴 위험이 있다 (32비트 → 64비트 정수 등)

#### Avro: "쓰기 스키마 vs 읽기 스키마"로 관리한다

Avro의 발상이 좀 독특한데, 이렇게 이해하면 쉽다.

> **쓰기 스키마** = 데이터를 저장할 때 쓴 스키마
> 
> 
> **읽기 스키마** = 지금 코드가 기대하는 스키마
> 
> 이 둘이 완전히 같을 필요는 없다. Avro 라이브러리가 두 스키마를 이름 기준으로 비교해서 알아서 맞춰준다.
> 
- 쓰기 스키마에는 있는데 읽기 스키마엔 없는 필드 → 그냥 버린다
- 읽기 스키마는 원하는데 쓰기 스키마엔 없는 필드 → 읽기 스키마에 정해둔 기본값으로 채운다

**호환성 유지 규칙**: 기본값이 있는 필드만 추가/삭제할 수 있다.

- 널(null)을 넣고 싶으면 `union { null, long }` 같은 **유니온 타입**을 써야 한다 (이 필드는 "숫자이거나 없을 수도 있음"이라고 명시하는 것)

**"근데 번호도 없는데 대체 어떻게 읽어?"**

Avro는 읽는 쪽이 쓰기 스키마 자체를 어디선가 구해와야 한다.

- 파일 저장 시 → 파일 맨 앞에 스키마를 통째로 한 번만 적어둔다
- DB 저장 시 → 레코드마다 버전 번호만 적고, 버전별 스키마 목록을 따로 관리한다
- 네트워크 통신 시 → 연결을 맺을 때 스키마를 미리 합의한다

### 6. 데이터가 오가는 3가지 경로

부호화된 데이터가 실제로 어떻게 전달되는지, 세 가지 상황으로 정리하면:

#### ① 데이터베이스

- 쓰는 쪽이 부호화, 읽는 쪽이 복호화
- 특이한 점: DB에는 **5년 전에 쓰인 값과 방금 쓰인 값이 동시에 섞여있다.** 이걸 "**데이터가 코드보다 오래 산다**"라고 표현한다
- 그래서 신버전 코드가 데이터를 읽고 → 고쳐서 → 다시 저장할 때, **자기가 모르는 필드를 지우지 않고 그대로 살려서 저장**해야 한다. 안 그러면 구버전이 저장해둔 정보가 조용히 유실된다

#### ② 서비스 호출 (REST / RPC)

> **RPC(원격 프로시저 호출)** 란: 다른 컴퓨터에 있는 함수를 마치 내 코드 안의 함수처럼 호출하는 방식.
> 
- 문제는 네트워크 호출이 로컬 함수 호출과 근본적으로 다르다는 것. 타임아웃, 유실, 중복 처리 위험이 있는데 이걸 숨기려 하면 오히려 버그가 생긴다
- **REST**: HTTP 원칙을 그대로 활용하는 방식. 단순하고 디버깅하기 쉬워서(그냥 curl로 찔러볼 수 있음) 공개 API에 많이 쓰인다
- **gRPC** 등 최신 RPC 프레임워크: Protocol Buffers 기반, 같은 회사 안의 서비스끼리 통신할 때 많이 씀
- 호환성 원칙은 위 4~5번의 부호화 형식 규칙을 그대로 물려받는다

#### ③ 비동기 메시지 (메시지 큐)

> **메시지 브로커**란: 보내는 쪽과 받는 쪽 사이에 끼어서 메시지를 잠깐 저장했다가 전달해주는 중간 서버. (예: Kafka, RabbitMQ)
> 
- RPC처럼 응답을 바로 기다리지 않는다 (비동기, 단방향)
- 받는 쪽이 다운돼 있어도 메시지가 유실되지 않고, 여러 명에게 동시에 보낼 수도 있다
- 여기서도 "모르는 필드는 지우지 말고 보존" 원칙은 똑같이 적용된다
