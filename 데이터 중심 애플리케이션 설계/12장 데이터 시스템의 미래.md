## 1부. 데이터 통합: 여러 시스템을 하나처럼 연결하기

### 1-1. 왜 하나의 도구로는 부족한가

하나의 소프트웨어로 모든 요구사항(빠른 검색, 안정적인 저장, 복잡한 분석)을 동시에 잘 처리하기는 어렵다. 그래서 실무에서는 여러 도구를 조합해서 쓴다.

**예시**: 주문 데이터는 PostgreSQL(관계형 데이터베이스)에 저장하고, 상품 검색은 Elasticsearch(전문 검색 엔진, 텍스트에서 키워드를 빠르게 찾는 도구)가 담당한다. 이때 두 시스템의 데이터를 어떻게 맞출 것인지가 핵심 문제가 된다.

**용어 설명**

- **전문 검색 색인(full-text search index)**: 문서 안의 단어들을 미리 정리해 둬서, "이 단어가 들어간 문서 찾아줘"라는 요청에 빠르게 답할 수 있게 만든 자료구조
- **구체화 뷰(materialized view)**: 매번 다시 계산하면 오래 걸리는 질의 결과를 미리 계산해서 저장해 둔 것. 예를 들어 "이번 달 매출 합계"를 매번 전체 주문을 더해서 구하지 않고, 미리 계산된 값을 갱신해가며 유지하는 방식

### 1-2. 데이터 통합의 두 가지 방법: 연합 vs 언번들링

| 구분 | 연합 데이터베이스 (federated database) | 언번들링 데이터베이스 (unbundled database) |
| --- | --- | --- |
| 목적 | 여러 시스템에 흩어진 데이터를 **읽기** 관점에서 하나처럼 보이게 함 | 여러 시스템에 걸친 **쓰기**를 동기화함 |
| 예시 | 포스트그레스큐엘의 "외래 데이터 랩퍼(foreign data wrapper)" 기능
다른 곳에 있는 데이터를 마치 로컬 테이블처럼 질의할 수 있게 해줌 | 변경 데이터 캡처(CDC)와 이벤트 로그로 여러 저장소의 색인을 갱신 |
| 한계 | 질의 인터페이스는 우아하지만 내부 구현이 복잡함(관계형 데이터베이스의 전통) | 하나만 잘하는 작은 도구를 조합하는 유닉스 전통을 따름 |

**용어 설명**

- **언번들링(unbundling)**: "번들(묶음)을 푼다"는 뜻으로, 원래 하나의 데이터베이스 안에 통합되어 있던 기능(색인 생성, 캐시 갱신 등)을 별도의 독립된 도구로 분리해서 로그를 통해 느슨하게 연결하는 방식. 저자는 이것이 미래의 방향이라고 본다.
- 저자가 지적하는 아쉬운 점: 유닉스 셸(shell)처럼 "간단한 명령어 하나로 여러 도구를 선언적으로 연결하는" 방식(예: `mysql | elasticsearch`처럼 한 줄로 동기화를 선언)이 아직 언번들링된 데이터베이스 세계에는 존재하지 않는다.

### 1-3. 파생 데이터를 만드는 방법: 일괄 처리와 스트림 처리

원본 데이터로부터 색인, 캐시, 통계 등 **파생 데이터셋**을 만들어내는 두 가지 방법이 있다.

**용어 설명**

- **일괄 처리(batch processing)**: 정해진 크기의 데이터(예: 어제 하루치 로그 전체)를 한 번에 처리하는 방식. 느리지만 정확한 알고리즘을 쓸 수 있음
- **스트림 처리(stream processing)**: 끝없이 들어오는 데이터를 실시간으로 하나씩(또는 작은 묶음으로) 처리하는 방식. 빠르지만 근사치를 사용하는 경우가 많음

두 방식의 근본적 차이는 **스트림 처리는 끝이 없는 데이터셋에서 동작하고, 일괄 처리는 유한한 크기의 입력을 사용한다**는 점이다. 다만 최근에는 이 경계가 점점 흐려지고 있다.

**실무 예시**

- 스파크(Spark)는 일괄 처리 엔진 위에서 스트림을 마이크로 일괄 처리(micro-batch, 아주 짧은 시간 단위로 쪼갠 일괄 처리) 단위로 나눠 처리한다.
- 아파치 플링크(Flink)는 반대로 스트림 처리 엔진 위에서 일괄 처리를 수행한다.

**파생 상태가 갖는 함수형 특성**

일괄 처리는 입력이 바뀌지 않고(불변) 출력은 입력에만 의존하는 **순수 함수**처럼 동작한다. 즉 같은 입력을 넣으면 항상 같은 출력이 나온다. 이 특성 덕분에 내결함성(결함이 있어도 정상적으로 복구되는 성질)이 좋아지고, "한 데이터로부터 다른 데이터가 파생된다"는 관점에서 전체 시스템을 단순하게 생각할 수 있다.

### 1-4. 람다 아키텍처: 두 방식을 병행하는 절충안

- **람다 아키텍처(lambda architecture)**는 일괄 처리로 과거 데이터를 정확하게 재처리하고, 스트림 처리로 최근 데이터를 빠르게 근사 갱신하는 방식으로 둘을 병행 운용하자는 제안이다.

**작동 원리**

1. 스트림 처리자가 이벤트를 소비해 근사(approximate) 갱신을 뷰에 빠르게 반영한다.
2. 이후 일괄 처리자가 같은 이벤트 집합을 소비해 정확한 버전의 파생 뷰로 반영한다.

이는 "일괄 처리는 간단해서 버그가 적은 반면, 스트림 처리자는 신뢰성이 떨어지고 내결함성을 확보하기 어렵다"는 인식에서 나온 절충안이다.

**저자가 지적하는 3가지 실질적 문제**

1. 일괄 처리와 스트림 처리 양쪽 프레임워크에서 같은 로직을 유지해야 하는 부담이 크다. (서밍버드(Summingbird) 같은 라이브러리가 이를 완화하려 했지만 두 시스템을 운영하는 복잡성은 여전히 남는다.)
2. 두 파이프라인이 분리된 출력을 만들기 때문에, 사용자 요청에 응답하려면 두 출력을 병합해야 하는데 이 병합 작업이 까다롭다.
3. 전체 데이터를 반복적으로 재처리하는 비용이 크다. 그래서 실무에서는 증분 일괄 처리(예: 매 시각 끝에 그 시간 분량만 처리)를 쓰기도 하지만, 이 경우 낙오자 처리(늦게 도착한 데이터 처리)나 윈도우 경계 문제가 다시 발생한다.

**최근 흐름**: 같은 시스템에서 일괄 연산(과거 데이터 재처리)과 스트림 연산(실시간 처리)을 모두 구현해 람다 아키텍처의 단점을 없애려는 시도가 진행 중이다. (예: 아파치 빔(Beam)이 이런 연산을 표현하는 API를 제공하며, 이 API로 작성하면 플링크나 구글 클라우드 데이터플로 위에서 구동 가능하다.)

### 1-5. 데이터베이스 언번들링: 유닉스와 관계형 데이터베이스의 화해

**철학의 차이**

- **유닉스**: 논리적이지만 저수준인 하드웨어 추상화를 제공. 파이프(pipe)는 단지 바이트의 순차열일 뿐이다.
- **관계형 데이터베이스**: 디스크 구조, 동시성 제어, 장애 복구 같은 복잡성을 감춘 고수준 추상화(SQL, 트랜잭션)를 제공.

저자는 **NoSQL을 "유닉스의 저수준 추상화 접근법을 분산 OLTP(온라인 트랜잭션 처리) 데이터 저장소 분야로 적용하려는 움직임"**으로 해석한다.

### 1-6. 모든 것의 메타데이터베이스라는 관점

조직 전체의 데이터플로(데이터가 이동하고 변환되는 흐름 전체)를 하나의 거대한 데이터베이스처럼 바라볼 수 있다. 일괄 처리, 스트림 처리, ETL(추출-변환-적재) 처리를 통해 데이터를 한 형태에서 다른 형태로 옮길 때마다 이는 마치 관계형 데이터베이스 내부에서 트리거나 스토어드 프로시저, 색인 갱신 루틴이 동작하는 것과 같은 역할을 한다. 다만 그 도구들이 하나의 제품이 아니라 여러 팀이 관리하는 서로 다른 소프트웨어로 나뉘어 있을 뿐이다.

**언번들링과 통합 시스템의 장단점**

|  | 연합(읽기 통합) | 언번들링(쓰기 통합) |
| --- | --- | --- |
| 핵심 과제 | 여러 데이터 모델을 하나의 질의 인터페이스로 사상(mapping)하는 것
→ 생각을 좀 해야 하지만 관리 가능한 문제 | 여러 저장 시스템에 걸친 쓰기를 동기화하는 것 → 훨씬 어려운 엔지니어링 문제 |

**쓰기 동기화의 전통적 방법과 저자의 대안**

전통적으로는 이종 저장소 시스템 간 **분산 트랜잭션**(여러 시스템에 걸친 작업을 all-or-nothing으로 처리하는 방식)이 필요했다. 그러나 저자는 이것이 잘못된 해결책이라고 본다. 대신 **멱등성(몇 번을 실행해도 결과가 같은 성질)을 기반으로 하는 비동기 이벤트 로그**가 훨씬 강력하고 현실적인 접근법이라고 주장한다.

**로그 기반 통합의 장점: 느슨한 결합(loose coupling)**

1. **시스템 수준**: 비동기 이벤트 스트림을 사용하면 한 구성 요소에 장애가 생겨도 전체 시스템이 잘 견딘다. 이벤트 소비자가 느리거나 장애가 나면 로그가 메시지를 버퍼링(임시 저장)해두고, 문제가 해결되면 소비자가 버퍼링된 메시지로 따라잡을 수 있다.
2. **인적 수준**: 각 팀이 자신의 소프트웨어 구성 요소나 서비스를 독립적으로 개발·개선·유지보수할 수 있다.

**언번들링 대 통합 시스템, 언제 무엇을 쓸 것인가**

언번들링이 실제 미래가 되더라도 통합된 단일 데이터베이스를 완전히 대체하지는 못한다. MPP(대규모 병렬 처리) 데이터 웨어하우스의 질의 엔진처럼, 특정 작업부하에 최적화된 전문 도구는 여전히 중요하다. 즉 필요한 모든 것을 만족하는 단일 기술이 있다면 그냥 그 제품을 쓰는 것이 좋고, 언번들링과 조합(합성)의 장점은 그런 단일 소프트웨어가 없는 상황에서만 드러난다.

### 1-7. 데이터플로를 중심에 둔 애플리케이션 설계

**파생 함수로서의 애플리케이션 코드**

데이터셋이 다른 데이터셋으로부터 파생될 때는 변환 함수를 거친다. 예시는 다음과 같다.

- **보조 색인**: 기반 테이블의 각 로우나 문서마다 색인할 값을 골라 정렬하는 단순한 변환 함수
- **전문 검색 색인**: 언어 감지, 단어 분리, 어간 추출(단어의 기본형만 남기는 것, 예: "달리다", "달리는" → "달리") 등 자연어 처리 함수를 적용
- **머신러닝 모델**: 학습 데이터로부터 파생된 것으로 볼 수 있고, 새 입력 데이터를 적용하면 모델의 출력이 파생됨
- **캐시**: UI에 보여줄 형태의 데이터 집합. UI가 바뀌면 캐시를 채우는 방법의 정의도 갱신해야 함

**애플리케이션 코드와 상태의 분리**

이론상 데이터베이스가 운영체제처럼 임의의 애플리케이션 코드를 실행하는 환경이 될 수도 있지만, 실제로는 현대적 배포 요구사항(버전 관리, 롤링 업그레이드, 모니터링, 외부 시스템 통합)과 잘 맞지 않는다. 반면 메소스, 얀, 도커, 쿠버네티스 같은 **배포·클러스터 관리 도구**는 애플리케이션 코드 실행을 전문으로 하도록 설계되었다.

그래서 시스템의 일부는 **지속성 있는 데이터 저장**을 전문으로 하고, 다른 일부는 **애플리케이션 코드 실행**을 전문으로 하는 것이 합리적이다. 오늘날 대부분의 웹 애플리케이션은 상태 비저장(stateless, 서버 자체는 데이터를 기억하지 않고 매번 데이터베이스에서 가져오는 방식) 서비스로 배포된다. 함수형 프로그래밍 커뮤니티가 좋아하는 농담처럼 "우리는 교회(Church, 함수형 프로그래밍의 이론적 기초를 만든 수학자 알론조 처치)와 정치(state, 상태)는 분리하는 것이 옳다고 믿는다."

**데이터플로 관점의 재조정**

데이터베이스를 애플리케이션이 수동적으로 조작하는 변수로 취급하는 대신, 상태 변경과 그 상태를 처리하는 코드 간의 상호작용을 데이터플로로 생각해볼 수 있다. 애플리케이션 코드는 한 곳에서 상태 변화를 트리거해 다른 곳의 상태 변화에 응답한다.

**용어 설명**

- **튜플 공간(tuple space)**: 1980년대에 등장한 개념으로, 상태 변화를 관찰해 그 변화에 반응하는 방식으로 분산 연산을 표현하는 모델
- **관찰자 패턴(observer pattern)**: 변수 값이 변할 때 그것을 구독하고 있는 쪽에 자동으로 알림을 주는 프로그래밍 패턴. 대부분의 프로그래밍 언어는 이를 기본 기능으로 지원하지 않는다.

### 1-8. 쓰기 경로와 읽기 경로

이 장에서 반복적으로 등장하는 핵심 구분이다.

**용어 설명**

- **쓰기 경로(write path)**: 시스템에 정보를 기록할 때마다 일괄 처리와 스트림 처리의 여러 단계를 거쳐 그 결과를 파생 데이터셋에 통합·갱신하는 과정. 누군가 조회를 요청했는지와 무관하게, 데이터가 들어오는 대로 바로 계산한다.
- **읽기 경로(read path)**: 사용자 요청을 처리할 때 파생 데이터셋을 읽고 그 결과를 가공해 응답을 만드는 과정. 즉 누군가 요청했을 때만 발생하는 부분이다.

함수형 프로그래밍에 비유하면 **쓰기 경로는 조급한 평가(eager evaluation, 미리 계산해두는 방식)**, **읽기 경로는 느긋한 평가(lazy evaluation, 필요할 때 계산하는 방식)**와 비슷하다.

**트레이드오프**: 색인이 없다면 쓰기 경로의 작업량은 줄지만(갱신할 색인이 없으므로) 읽기 경로의 작업량이 늘어난다(전체를 grep처럼 스캔해야 함). 반대로 모든 가능한 질의 결과를 미리 계산해두면 읽기 경로 작업은 거의 없어지지만, 쓰기 경로에 막대한 비용이 발생한다(질의 조합이 무한하기 때문에 현실적으로 불가능). 캐시, 색인, 구체화 뷰는 결국 이 두 경로 사이의 경계를 옮기는 역할을 한다.

**오프라인 대응 가능한 상태 저장 클라이언트**

전통적으로 웹 브라우저는 상태 비저장 클라이언트였다. 그러나 최근 "단일 페이지" 자바스크립트 웹 앱과 로컬 저장소 덕분에 클라이언트가 많은 상태를 저장할 수 있게 되었다. 장치 상태를 **서버 상태의 캐시**로 생각할 수 있다는 것이다. 서버가 상태 변경 이벤트를 클라이언트 측 이벤트 파이프라인으로 푸시하도록 프로그래밍 모델을 확장하면, 상태 변경이 종단 간(한 장치의 상호작용부터 다른 장치의 사용자 인터페이스까지) 쓰기 경로를 따라 흐를 수 있다.

**읽기도 이벤트다**

스트림 처리자가 파생 데이터를 저장소에 기록할 때, 그리고 사용자가 저장소에 질의할 때, 그 저장소가 읽기 경로와 쓰기 경로 사이의 경계로 작동한다. 읽기 이벤트 로그를 남기면 사용자가 특정 결정을 내리기 전에 무엇을 봤는지 재구성할 수 있어 인과적 의존성을 추적하기 좋아진다는 장점도 있다. (다만 추가 저장소와 I/O 비용이 든다.)

## 2부. 정확성을 목표로: 결함이 있어도 신뢰할 수 있는 시스템 만들기

### 2-1. 정확성이란 무엇인가

데이터를 읽기만 하는 상태 비저장 서비스는 버그가 있어도 재시작하면 정상으로 돌아온다. 그러나 데이터베이스 같은 상태 저장 시스템은 "영원히 기억하게끔 설계"되었기 때문에, 무언가 잘못되면 그 효과가 영원히 지속될 수 있다.

**정확한 애플리케이션**이란 다양한 결함에 직면하더라도 시맨틱(의미, 동작 규칙)이 잘 정의되고 이해 가능한 프로그램을 뜻한다. 전통적으로 이를 달성하는 도구는 **트랜잭션의 ACID 속성**(원자성, 격리성, 지속성 등)이었지만, 저자는 이 토대가 생각보다 약하다고 지적한다.

### 2-2. 정확히 한 번 실행 (Exactly-once semantics)

**용어 설명**

- **정확히 한 번(exactly-once)** 또는 **결과적으로 한 번(effectively-once)**: 메시지 처리 중 결함이 발생해 재시도하더라도, 결함이 없었던 것과 동일한 최종 결과를 얻도록 계산을 조정한다는 뜻. 실제로 메시지가 물리적으로 한 번만 전달된다는 뜻이 아니라, 최종 효과가 한 번 처리된 것과 같다는 의미다.

**문제 상황**: 메시지 처리 중 뭔가 잘못되면 포기(메시지 버림 → 데이터 손실)하거나 재시도할 수 있다. 재시도하면 첫 시도가 성공했을 위험이 있음에도 확인할 수 없어 결국 메시지가 두 번 처리될 수 있다(같은 서비스 요금을 두 번 청구하는 등의 문제).

**해결책 1: 연산을 멱등으로 만들기**

연산이 멱등(idempotent)이라는 것은 한 번 실행하든 여러 번 실행하든 같은 효과가 나타남을 보장한다는 뜻이다. 다만 본질적으로 멱등이 아닌 연산을 멱등으로 만들려면 노력이 필요하다 — 예를 들어 갱신한 연산의 ID 집합 같은 메타데이터를 추가로 유지해야 할 수도 있다.

**해결책 2: 중복 억제**

TCP는 패킷의 일련번호를 사용해 순서를 보장하고 손실이나 중복을 확인한다. 그러나 이 중복 억제는 단일 TCP 연결 문맥 내에서만 작동한다. 만약 네트워크가 불안정해 클라이언트가 응답을 받지 못하고 재연결해 재시도하면, 이는 별도의 요청이자 별도의 트랜잭션이 되어버려 일반적인 중복제거 메커니즘은 도움이 되지 않는다.

**해결책 3: 연산 식별자(고유 요청 ID)**

클라이언트 애플리케이션에서 요청의 종단 간(end-to-end) 흐름 전체를 아우르는 고유 식별자(UUID 등)를 만들어, 웹 브라우저의 숨은 폼 필드에 포함시키고 이를 데이터베이스까지 전달하는 방법이다. 데이터베이스에 이 ID에 대한 유일성 제약 조건을 걸어두면 같은 트랜잭션이 두 번 수행되는 것을 막을 수 있다. 이는 종단 간 논증(end-to-end argument)이라는 좀 더 일반적인 원리의 한 사례다.

**종단 간 논증**: 1984년 솔처, 리드, 클라크가 제안한 원리로, "문제 기능은 통신 시스템의 종단점에 위치한 애플리케이션의 지식과 도움이 있어야만 완벽하고 정확하게 구현 가능하다"는 것이다. TCP나 이더넷 체크섬처럼 저수준에서 제공하는 신뢰성 기능이 있어도, 애플리케이션 자체가 중복 억제 같은 종단 간 대책을 갖추지 않으면 데이터 손실·손상이 발생할 수 있다.

### 2-3. 유일성 제약 조건을 로그 기반으로 강제하기

사용자명 중복 방지, 좌석 중복 예약 방지 등 유일성을 강제해야 하는 경우가 많다. 이를 위해서는 **합의(consensus, 분산된 여러 노드가 하나의 결정에 동의하는 것)**가 필요하다.

**단일 파티션에서의 처리 방법**

스트림 처리자는 단일 스레드에서 한 로그 파티션의 메시지를 순차적으로 소비한다. 유일성이 필요한 값을 기준으로 로그를 파티셔닝하면, 스트림 처리자는 충돌하는 여러 연산 중 어느 것이 먼저 들어왔는지 결정적으로 판결할 수 있다.

**같은 사용자명을 쓰려는 여러 사용자의 예시 (3단계)**

1. 모든 사용자명 요청은 메시지로 부호화해 사용자명의 해시값으로 결정된 파티션에 추가한다.
2. 스트림 처리자는 로그에서 요청을 연속해서 읽고, 로컬 데이터베이스로 어떤 사용자명이 이미 사용되었는지 추적한다. 사용 가능하면 이름을 기록하고 성공 메시지를 출력 스트림에 방출하고, 이미 쓰이고 있으면 거부 메시지를 방출한다.
3. 요청한 클라이언트는 출력 스트림을 보면서 자신이 보낸 요청에 해당하는 성공/거부 메시지가 오기를 기다린다.

**다중 파티션으로 확장하기**: 파티션 수를 늘리면 각 파티션을 독립적으로 처리할 수 있어 대규모 요청도 쉽게 처리 가능하다. 예를 들어 계좌 이체 예제에서는 요청 ID를 포함하는 파티션, 받는 사람 계좌 파티션, 보내는 사람 계좌 파티션이 각각 독립적으로 존재할 수 있고, 세 데이터가 꼭 같은 파티션에 있을 필요는 없다. 원자적 커밋(모든 파티션에 걸쳐 한 번에 확정하는 것) 없이도 종단 간 요청 ID를 사용하면 동일한 정확성을 달성할 수 있음이 밝혀졌다.

### 2-4. 적시성과 무결성

저자는 **일관성(consistency)**이라는 용어가 사실 두 가지 요구사항이 합쳐진 것이라고 지적하며, 이를 분리해서 생각할 것을 제안한다.

**적시성(Timeliness)**

사용자가 시스템을 항상 최신 상태로 관측 가능하다는 의미. 데이터의 뒤처진 복사본을 읽으면 일관성이 없는 상태를 관측할 가능성이 있다. 하지만 일관성이 없는 상태는 일시적이며, 기다렸다 재시도하면 결국 해소된다.

**무결성(Integrity)**

손상이 없다는 의미. 누락된 데이터도 없고, 모순된 데이터도, 잘못된 데이터도 없다는 뜻이다. 무결성을 위반하면 불일치가 영원히 지속된다. 기다렸다 재시도한다고 데이터베이스 손상이 저절로 고쳐지지는 않으며, 명시적인 검사와 수리가 필요하다.

**저자의 결론**: 슬로건으로 말하면 **적시성 위반은 "최종적 일관성"**이고 **무결성 위반은 "영구적 불일치"**다. 대부분의 애플리케이션에서 무결성이 적시성보다 훨씬 중요하다. 적시성을 위반하면 성가시고 혼란스러울 뿐이지만, 무결성을 위반하면 파국을 맞는다.

**실무 예시**: 신용카드 명세서에 24시간 내 결제 내역이 아직 안 보여도 괜찮다(적시성 문제일 뿐, 은행은 대부분 거래를 비동기로 확정한다). 그러나 명세서 잔고가 거래의 합과 이전 명세서 잔고를 더한 값과 다르거나(합계 오류), 결제가 구매자에게만 부과되고 상인에게는 지급되지 않는다면(돈이 사라짐) 이는 무결성 위반이며 매우 나쁜 상황이다.

**데이터플로 시스템에서 적시성과 무결성 분리하기**

ACID 트랜잭션은 대개 적시성(선형성 등)과 무결성(원자적 커밋 등) 양쪽을 함께 보장하므로 굳이 둘을 구별할 필요가 없었다. 반면 이벤트 기반 데이터플로 시스템은 이 둘을 자연스럽게 분리한다. 이벤트 스트림을 비동기로 처리할 때 소비자가 반환하기 전에 명시적으로 메시지 도착을 기다리도록 만들지 않으면 적시성은 보장되지 않는다. 하지만 사실 **무결성이 스트림 시스템의 핵심**이다.

**무결성을 지키는 메커니즘의 조합**

1. 쓰기 연산 내용을 단일 메시지로 표현하기 (원자적으로 기록하기 쉽고, 이벤트 소싱과 잘 맞음)
2. 결정적 파생 함수를 사용해 그 단일 메시지에서 모든 상태 갱신을 파생하기
3. 클라이언트가 생성한 요청 ID를 모든 처리 단계를 통해 전달하기 (종단 간 중복 억제와 멱등성 가능)
4. 메시지를 불변으로 만들고 필요 시 파생 데이터를 재처리하기 (버그에서 회복하기 쉬워짐)

이 조합은 분산 트랜잭션이나 원자적 커밋 프로토콜 없이도 무결성을 보존하면서 더 좋은 성능과 운영적 견고함을 줄 수 있는, 미래에 유망한 방향이라고 저자는 평가한다.

### 2-5. 느슨하게 해석되는 제약 조건 — 유일성이 꼭 필요한가

유일성 제약 조건을 엄격히 강제하려면 합의가 필요하고, 이는 일반적으로 모든 이벤트를 단일 노드를 거쳐 특정 파티션으로 보내 처리하는 방식으로 구현된다. 그러나 실제로 많은 애플리케이션은 훨씬 완화된 유일성 개념을 사용해 이 제한을 피한다.

**실무 사례들**

- **동시 등록 충돌**: 두 사람이 동시에 같은 사용자명을 등록하거나 같은 좌석을 예약하면, 한 사람에게 사과 메시지를 보내 다른 이름이나 좌석을 고르게 부탁할 수 있다. 이런 오류 정정 방식을 **보상 트랜잭션(compensating transaction)**이라 한다.
- **재고 초과 주문**: 소비자가 재고보다 많은 상품을 주문하면 일단 재고를 더 주문해 채우고, 배송 지연에 대해 사과하고 가격을 할인해준다.
- **초과 예약(overbooking)**: 항공사는 일부 승객이 비행기를 놓칠 것을 예상해 초과 예약을 받는다. 실제로 초과 수요가 발생하면 환급, 승급, 인근 호텔 무료 제공 등 보상 처리를 한다. 이는 "한 좌석당 한 사람"이라는 제약 조건을 비즈니스적 이유로 고의로 위반하고 사후에 처리하는 방식이다.
- **계좌 초과 인출**: 계좌 잔고보다 많은 돈을 뺀다면 은행은 초과 인출 수수료를 부과하고 빚진 돈을 갚으라고 요구한다. 일일 초과 인출 금액을 제한하면 은행이 감수해야 할 위험을 제한할 수 있다.

**핵심 통찰**: 제약 조건을 일시적으로 위반하고 나중에 사과해 바로잡는 것은 실제로 수용 가능한 방법이다. 사과에 드는 비용(돈이나 평판)은 유동적이지만 때론 매우 낮다. 이미 보낸 이메일은 취소할 수 없어도 수정한 이메일을 바로 이어 보낼 수 있는 것처럼 말이다. 다만 ATM에서 돈이 빠져나가면 직접 돌려받을 수 없는 것처럼, 되돌릴 수 없는 비용이 발생하는 경우도 있다.

이런 방식이 통하는 이유는 애플리케이션이 무결성(입금액과 출금액이 반드시 일치해야 함)은 반드시 요구하지만, 적시성(재고보다 많이 팔았다는 사실을 즉시 감지해야 함)은 반드시 필요하지 않기 때문이다.

### 2-6. 코디네이션 회피 데이터 시스템

- **코디네이션(coordination, 조정)**이란 여러 노드나 시스템이 하나의 결정을 위해 서로 통신하며 맞춰가는 과정을 말한다. 이것이 필요할수록 시스템 성능과 가용성이 떨어질 수 있다.

**두 가지 흥미로운 관찰**

1. 데이터플로 시스템은 원자적 커밋과 선형성, 그리고 파티션에 걸친 동기 코디네이션 없이도 파생 데이터에 대한 무결성 보장을 유지할 수 있다.
2. 엄격한 유일성 제약 조건은 적시성과 코디네이션을 요구하지만, 많은 애플리케이션은 느슨한 제약 조건을 사용해도 실제로는 괜찮다. 전반적으로 무결성이 보존되는 한 일시적으로 제약 조건을 위반하더라도 이후에 고칠 수 있다.

이런 **코디네이션 회피(coordination-avoiding) 데이터 시스템**은 동기식 코디네이션이 필요한 시스템보다 성능이 더 좋고 더 나은 내결함성을 지닌다. 여러 데이터센터에 분산해 운영 가능하고, 지역 간 동기식 코디네이션이 필요 없어 비동기 지역 간 복제가 가능하다. 다만 코디네이션을 도입하지 않는 이상 선형성(항상 최신 상태를 보는 성질)은 없다.

**애플리케이션의 작은 일부에만 코디네이션이 필요하다면, 시스템 전체에 코디네이션 비용을 지불할 필요는 없다**는 것이 핵심 메시지다.

### 2-7. 믿어라, 하지만 확인하라

지금까지의 논의는 "결함은 있을 수 있지만 특정 종류의 결함은 절대 발생하지 않는다"는 **시스템 모델**을 가정해왔다. 예를 들어 fsync(디스크에 데이터를 확실히 기록하도록 강제하는 시스템 호출) 이후에는 데이터가 손실되지 않는다거나, CPU 연산은 항상 옳은 결과를 낸다고 가정하는 식이다.

**가정이 깨지는 실제 사례**

- 디스크에 아무 조작도 안 했는데 데이터가 손상되는 경우가 계속 발생한다.
- 네트워크 상에서 TCP 체크섬(오류를 검출하기 위한 값)조차 통과하지 못하는 데이터 손상이 있다.
- 결함이 없는 메모리에서도 무작위 비트 플립(bit-flip, 0과 1이 뒤바뀌는 현상)을 일으킬 수 있는 병적인 메모리 접근 패턴이 있다. 이 효과는 운영체제의 보안 메커니즘을 무력화하는 데 쓰이기도 한다(**로해머**, rowhammer 기법).

무작위 비트 플립 자체는 현대 하드웨어에서 거의 발생하지 않지만, 가능성의 영역을 완전히 벗어난 것은 아니므로 어느 정도 주의가 필요하다.

**소프트웨어 버그가 발생해도 무결성 유지하기**

하드웨어 문제보다 소프트웨어 버그의 위험성이 항상 존재한다. 저자는 마이SQL이 유일성 제약 조건을 올바르게 유지하는 데 실패한 사례, 포스트그레스큐엘의 직렬성 격리 수준에서 쓰기 스큐(비정상적 동시성 문제) 현상이 발생한 사례를 직접 목격했다고 언급한다. 널리 사용되고 좋은 평가를 받는 데이터베이스에서도 이런 일이 생기니, 성숙도가 낮은 소프트웨어에서는 상황이 훨씬 심각하다.

**용어 설명**

- **감사(auditing)**: 데이터 무결성을 체크하는 작업. 즉 데이터가 손상됐는지 확인하는 절차

**검증하는 문화**

HDFS나 아마존 S3 같은 대규모 저장소 시스템은 디스크를 완전히 신뢰하지 않는다. 알지 못하는 사이에 손상이 생길 위험을 줄이기 위해 백그라운드로 프로세스를 실행해 지속적으로 파일을 읽어 다른 복제본과 비교하고 디스크 사이에서 이동시킨다.

저자는 대부분의 시스템이 "정확성 보장이 절대적이라고 가정하며 희박한 데이터 손상 가능성은 대비하지 않는다"고 지적하고, 앞으로는 무결성 확인을 완전히 위임하기보다 스스로 확인을 지속적으로 수행하는 **자가 검증(self-validation)**, **자가 감사(self-auditing)** 시스템이 더 많아지길 바란다고 말한다.

### 2-8. 감사 기능 설계

트랜잭션 로그를 캡처하더라도, 다양한 테이블에서 발생한 삽입·갱신·삭제만으로는 **왜** 이런 변경을 수행했는지 명확한 모습을 알 수 없다. 이 변경을 결정한 애플리케이션 호출은 일시적이라서 재현할 수 없다.

**반대로 이벤트 기반 시스템**은 더 나은 감사 기능을 제공한다. 사용자 입력이 단일 불변 이벤트로 표현되고, 어떤 상태 갱신 결과도 이벤트에서 파생될 수 있다. 이 파생 과정은 결정적이고 반복 가능하기 때문에, 같은 버전의 파생 코드로 같은 이벤트 로그를 재실행하면 동일한 상태 갱신 결과를 만들 수 있다. 데이터플로를 명시적으로 만들면 데이터의 **유래(provenance)**가 더욱 명확해져 무결성 확인이 수월해진다.

**감사 데이터 시스템용 도구**

- **하드웨어 보안 모듈을 사용한 주기적 서명**: 트랜잭션 로그를 변경하기 어렵게(tamper-proof) 만들 수 있지만, 애초에 올바른 트랜잭션이 로그에 들어갔는지는 보장하지 못한다.
- **암호화 도구**: 하드웨어·소프트웨어 문제와 악의적 동작에도 견고한 방식으로 시스템의 무결성을 증명하려는 시도. 비트코인, 이더리움 등 암호화폐와 블록체인, 분산 원장 기술이 이 분야를 탐구하기 위해 나타났다.

**용어 설명**

- **머클 트리(Merkle tree)**: 해시 트리로, 특정 데이터셋 내에 나타나는 레코드를 효율적으로 증명하는 데 사용하는 자료구조. 암호화폐의 과대광고 외에도 **인증서 투명성(certificate transparency)**이라는, TLS/SSL 인증 유효성을 확인하는 보안 기술에도 사용된다.

**저자의 평가**: 작업 증명(proof of work, 예: 비트코인 채굴) 기술은 엄청나게 소모적이며, 비트코인의 트랜잭션 처리량이 낮은 것은 기술적 이유보다 정치·경제적 이유 때문이라고 본다. 다만 이런 무결성 확인 방식 자체는 흥미로운 측면이 있다고 인정한다.

**다시 종단 간 논증**

시스템의 모든 개별 구성 요소가 절대 손상되지 않는다고 완전히 믿기 어렵다면, 최소한 데이터의 무결성만이라도 주기적으로 확인해야 한다. 종단 간 무결성 확인을 꾸준히 하면 시스템이 정확하다는 확신이 높아져 더 빠르게 개선해나갈 수 있다. 테스트 자동화와 마찬가지로 감사 기능은 버그를 빨리 발견할 가능성을 높여, 시스템이나 새 저장 기술에 가한 변경이 손상을 일으킬 위험을 줄인다.

## 3부. 옳은 일 하기: 데이터 시스템의 윤리적 측면

저자는 책의 마지막 절에서 기술적 논의에서 한 걸음 물러난다. 모든 시스템은 목적을 가지고 구축되지만, 그 결과가 세상에 미치는 영향은 원래 목적을 뛰어넘기도 한다. 시스템을 구축하는 엔지니어는 이 결과를 신중하게 생각해서 어떤 세상에 살고 싶은지 결정할 책임이 있다.

### 3-1. 예측 분석과 편견

- **예측 분석(predictive analytics)**은 날씨 예측, 질병 확산 예측처럼 유용하게 쓰이기도 하지만, 기결수의 재범 여부나 채무자의 채무 불이행 가능성, 보험 고객의 고액 청구 여부를 예측하는 것은 개인의 삶에 직접적인 영향을 준다.

**"아니오"가 기본값이 되는 이유**

지불 네트워크는 사기 거래를 막으려 하고, 은행은 불량 채권을 피하려 하고, 항공사는 공중 납치를 피하려 하고, 회사는 신뢰하기 어려운 사람을 고용하지 않으려 한다. 조직 입장에서 놓친 사업적 기회의 비용은 작지만 불량 채권이나 골칫거리 종업원 때문에 발생하는 비용은 크기 때문에, 조금이라도 의심스러우면 "아니오"라고 말하는 편이 조직에는 합리적이다.

그러나 알고리즘에 의한 의사결정이 보편화되면서, 사실이든 아니든 특정 알고리즘으로 위험성 있다고 딱지가 붙여진 사람은 많은 "아니오" 결정으로 고통받는다. 직업, 항공 여행, 보험 보장 범위, 부동산 임대, 금융 서비스 같은 사회의 주요 측면에서 배제되는 것을 **"알고리즘 감옥(algorithmic prison)"**이라 부른다. 인권을 존중하는 나라에서 범죄 판결 시스템은 유죄로 증명될 때까지는 무죄로 가정하지만, 자동화 시스템은 유죄 증명 없이도, 변론할 기회도 거의 없이 사람을 사회 참여에서 배제시킬 수 있다.

### 3-2. 편견과 차별

알고리즘이 내린 결정이 사람이 내린 결정보다 반드시 좋거나 나쁜 것은 아니다. 사람도 편견을 가지기 쉽고, 차별 관행이 문화적으로 제도화될 수도 있다. 데이터 기반 의사결정이 전통적 시스템에서 간과되기 쉬운 사람들에게 더 나은 기회를 줄 수 있다는 희망도 있다.

**문제는 투명성 부족**: 시스템으로 학습한 패턴은 투명하지 않다. 데이터에서 상관관계가 나왔어도 왜 그런지 알지 못할 가능성이 있다. **알고리즘에 투입된 입력에 시스템적 편견이 있다면 시스템은 그 편견을 학습하고 증폭해서 출력을 내보낼 가능성이 높다.**

**프록시 변수를 통한 간접 차별**: 개인의 인종, 나이, 성별 같은 특징을 직접 분석에 쓰지 않더라도, 인종적으로 분리된 지역에서는 우편번호나 IP 주소가 강력한 인종 예측자가 될 수 있다.

**과거 데이터의 한계**: 예측 분석 시스템은 오직 과거로부터 추정한다. 과거가 차별적이었다면 예측 분석 시스템은 차별을 성문화(codify, 규칙으로 굳혀버림)한다. 과거보다 나은 미래를 원한다면 **도덕적 상상력**이 필요하며, 이는 인간만이 제공할 수 있다.

**통계적 정확성과 개인의 오류**: 풍부한 데이터는 본질적으로 통계적이다. 즉 확률 분포가 전체적으로 정확해도 개별 사례는 잘못될 수 있다. 특정 국가의 평균 기대수명이 80세라도 특정인이 80세 생일날 사망한다는 뜻은 아니다. 예측 시스템의 출력은 확률적이기 때문에 개별적으로는 충분히 잘못될 수 있다.

### 3-3. 책임과 의무

의사결정 자동화는 아직 책임과 의무 문제가 해결되지 않았다. 사람이 실수하면 책임을 질 수 있고 영향받은 사람은 이의를 제기할 수 있다. 그러나 알고리즘이 잘못됐을 때 누가 책임을 져야 할까? 자율주행 자동차가 사고를 냈을 때는 누구의 책임일까? 신용 점수 자동화 알고리즘이 특정 인종이나 종교로 사람을 차별한다면 구제할 방법이 있을까? 머신러닝 시스템이 내린 결정을 판사가 사법 심사한다면, 판사에게 어떻게 알고리즘이 이런 결정을 내렸는지 설명할 수 있을까?

### 3-4. 피드백 루프

추천 시스템처럼 사람들에게 즉각적으로 지대한 영향을 미치지 않는 예측 애플리케이션이라도 어려운 문제에 직면한다. 서비스가 사람들이 보고자 하는 콘텐츠를 예측하는 데 익숙해지면, 사람들에게 이미 공감하는 의견만 보여줘 고정관념과 오보, 양극화를 불러오는 **에코 챔버(echo chamber, 비슷한 의견끼리만 메아리치듯 반복되는 폐쇄적 환경)** 될 수 있다.

**자기 강화 피드백 루프의 구체적 사례**: 고용 가능성 평가를 위해 신용 점수를 사용하는 고용주가 있다고 하자. 신용 점수가 좋은 노동자가 갑자기 스스로 어떻게 할 수 없는 불운으로 경제적 어려움에 처했다. 제때 청구서 지불을 못 하자 신용 점수는 나빠지고 구직을 하기도 어려워졌다. 실업은 사람을 더욱 가난으로 내몰고 신용 점수는 더 악화된다. 그러면 직업을 찾기가 훨씬 어려워진다. **이 악순환은 수학적 엄밀함과 데이터의 위장 뒤에 숨은 악독한 가정 때문에 발생한다.**

이런 피드백 루프가 언제 발생할지 항상 예측 가능한 것은 아니지만, 전체 시스템(컴퓨터화된 부분뿐 아니라 시스템과 상호작용하는 사람들까지)을 생각하면 많은 결과를 예측할 수 있다. 이 접근법을 **시스템 사고(systems thinking)**라 한다. 데이터 분석 시스템이 사람들 간에 존재하는 차이를 강화하고 증폭시키는가(부자를 더 부자로, 가난한 사람을 더 가난하게), 아니면 불의와 맞서려 하는가? 최선의 의도였더라도 의도하지 않은 결과를 반드시 주의해야 한다.

### 3-5. 감시로서의 데이터

**사고 실험**: "데이터"란 단어를 "감시"로 바꿔도 여전히 좋은 문구로 들리는지 시험해보자. "우리 감시 주도 조직은 실시간으로 감시 스트림을 수집해 감시 웨어하우스에 저장합니다. 감시 과학자들은 새로운 통찰력을 얻기 위해 선진 분석 기법과 감시 처리 기법을 사용합니다." — 어떤가?

소프트웨어가 "세상을 잡아먹으려(eat the world)" 하는 시도로 세계에서 가장 거대한 감시 인프라가 구축되었다. 스마트폰, 스마트 TV, 음성 제어 보조 장치, 유아 모니터, 심지어 클라우드 기반 음성 인식 유아 장난감까지, 사람이 사는 모든 공간에 인터넷이 연결된 마이크가 적어도 하나는 포함된 세상으로 빠르게 접근하고 있다.

**자발적 감시라는 역설**: 가장 억압적인 정권만이 모든 방에 마이크를 넣고 모든 사람의 위치를 추적할 수 있는 장치를 항상 휴대하게끔 강요할 수 있을 것이다. 그러나 사람들은 명백히 자발적이고 심지어 열정적으로 전체 감시 세계에 자신을 던진다. 차이는 단지 정부 기관이 아니라 기업이 데이터를 수집한다는 것뿐이다.

**사람들이 감시를 받아들이는 이유**: 아마도 감출 것이 없다고 느꼈기 때문일 것이다. 다른 말로, 완전히 기존 권력 구조를 따르고 소외된 소수가 아니라서 핍박을 무서워할 필요가 없는 것이다. 모든 사람이 그렇게 운이 좋은 것은 아니다. 이미 자동차 보험료와 연계된 자동차 추적 장치, 건강 추적 장치로 보장 범위가 결정되는 건강 보험이 있다. 보험 보장 범위나 고용처럼 삶의 중요한 측면에 영향을 주는 것을 결정하는 데 감시가 사용되면 더 이상 호의적으로 보이지 않기 시작한다. 더욱이 데이터 분석은 놀랍게도 침입적이다. 스마트시계나 건강 추적기의 운동 센서를 사용해 비밀번호 같은 것을 입력하는 내용을 상당히 높은 정확도로 알아낼 수 있다.

### 3-6. 동의와 선택의 자유

사용자가 서비스 약관과 개인정보 보호 정책에 동의했기 때문에 데이터 수집에 동의했다고 주장할 수 있다. 하지만 이 주장에는 문제가 있다.

- 사용자는 자신이 제공한 데이터가 무엇이고 어떻게 유지·처리되는지에 대한 지식이 거의 없다.
- 대부분의 개인정보 보호 정책은 보기보다 훨씬 애매하다. 무엇을 하는지 알지 못한 채 받은 동의는 의미가 없다.
- 서비스와 사용자 간 관계는 매우 비대칭적이고 일방적이다. 약관은 사용자가 아니라 서비스가 설정한다.
- 감시에 동의하지 않는 사람이 선택할 수 있는 실질적 대안은 서비스를 사용하지 않는 것뿐이지만, 이 선택은 무료가 아니다. 어떤 서비스가 "기본 사회적 참여를 위해 반드시 필요한 서비스"로 간주될 정도로 인기 있다면 사람들이 그 서비스를 떠나기를 바라는 것은 합리적이지 않다. **사실상** 서비스를 사용하도록 강제하는 것이다.
- 소수의 사람만이 사용자를 추적한다는 이유로 서비스 사용을 거부할 특권이 있다. 이런 특권이 없는 사람에게는 유의미한 선택의 자유가 없다.

### 3-7. 사생활과 데이터 사용

"사생활은 죽었다"는 주장은 사생활(privacy)이란 단어를 오해한 것이다. **사생활 보호가 모든 것을 비밀로 한다는 뜻은 아니다. 사생활은 누구에게 어떤 것을 보여줄지, 어떤 것을 공개로 할지, 어떤 것을 비밀로 할지 고를 수 있는 자유를 가진다는 의미다.** 사생활 보호 권리는 결정권이다.

감시 인프라를 통해 데이터를 추출할 때 사생활 보호 권리가 손상되는 것이 아니라 **데이터 수집 측으로 이전된다.** 무엇을 공개할지, 무엇을 기밀로 할지 결정할 권리를 개인에서 기업으로 이전한다는 뜻이다.

**기업의 정보 관리 방식**: 기업은 감시 결과를 최대한 기밀로 하기로 결정한다. 사용자에 관한 은밀한 정보는 간접적으로만 나타난다. 예를 들면 특정 질병으로 고통받는 사람들 같은 특별한 그룹에게 광고를 타겟팅하는 도구의 형태로 나타난다. 특정 광고에 타겟팅된 사람들 집합에서 개인을 재식별할 수 없더라도, 그 사람들은 자신이 어떤 질병에 고통받고 있는지 여부와 같은 은밀한 정보 공개에 관한 대리인(결정권자)을 잃어버린 것이다.

### 3-8. 자산과 권력으로서의 데이터

행동 데이터는 사용자가 서비스와 상호작용하면서 나오는 부산물이라는 뜻에서 때론 **"데이터 배출(data exhaust)"**이라 부른다. 하지만 경제적 관점에서 볼 때, 타겟팅 광고가 서비스 대가로 지불하는 것이라면 사람들의 행동 데이터는 서비스의 핵심 자산이다.

데이터는 가치가 있기 때문에 많은 사람들이 데이터를 원하고 기업도 데이터를 원한다. 그러나 정부 역시 비밀 거래, 강압, 법적 강요 또는 그냥 데이터를 훔치기 위해 데이터를 얻고자 한다. 기업이 부도를 맞으면 수집된 개인 데이터는 팔아 치울 수 있는 자산 중 하나가 된다. 게다가 데이터 보안이 어렵기 때문에 위반 사례가 당황스러울 정도로 자주 발생한다.

비평가들은 데이터가 단순한 자산이 아니라 **"악성 자산(toxic asset)"** 또는 최소한 **"위험 물질(hazardous material)"**이라고 말한다. 컴퓨터 시스템은 범죄자나 적대적 해외 정보 기관에게 침해당할 수 있고, 내부자가 데이터를 유출하거나, 회사가 이런 가치를 공유하지 않는 비양심적 경영자의 손에 떨어지거나, 데이터를 넘기라고 강요하는 데 거리낌이 없는 세력에게 국가 정권이 넘어갈 수도 있다. 데이터를 수집할 때는 현재의 정치적 환경뿐 아니라 **미래에 등장할 가능성이 있는 정부도 고려**해야 한다.

**"아는 것이 힘"이라는 옛 격언**이 있다. 자신은 감시를 피하면서 다른 사람들은 면밀히 감시하는 것은 권력의 가장 중요한 형태 중 하나다. 이것이 전체주의 정부가 감시를 원하는 이유다. 오늘날 기술 기업들이 명백히 정치 권력을 추구하지는 않을지라도, 기업이 축적한 데이터와 지식은 공공의 감시를 벗어나 기업에게 암암리에 시민의 삶 전반에 걸쳐 많은 권력을 부여한다.

### 3-9. 산업 혁명과의 비교

데이터는 정보화 시대의 본질적 특징이다. 산업 혁명은 주요한 기술과 농업 발전을 통해 장기간에 걸쳐 경제 성장을 지속시키고 생활 수준을 현저하게 개선했지만, 매연과 화학 처리로 인한 대기 오염과 산업·생활 폐기물로 인한 수질 오염 같은 문제도 함께 일으켰다. 환경 보호 규제, 근무 환경 안전 규약, 어린이 노동 불법화 같은 보호 수단이 확립되기까지 상당한 시간이 걸렸다.

브루스 슈나이어는 다음과 같이 말했다: "데이터는 정보화 시대의 오염 문제고 사생활 보호는 환경적 난제다. 대부분의 컴퓨터가 정보를 생산한다. 데이터는 주변에 항상 머무르면서 썩어간다. 데이터를 어떻게 다루는가, 즉 데이터를 어떻게 가지고 있고 어떻게 처분하는가가 정보 경제를 건강하게 만드는 핵심이다."

저자는 개인 데이터에 관한 기술 산업에 **문화 전환(culture shift)**이 필요하다고 믿는다. 사용자를 최적화할 지표로 삼지 말고, 존중과 존엄, 대리의 자격이 있는 인간이라는 점을 기억해야 한다. 각 개인은 스스로 자신의 사생활을 보호할 수 있어야 하며, 감시를 통해 그 통제권을 훔쳐서는 안 된다. 데이터를 통제할 수 있는 개인의 권리는 국립공원의 자연환경과 비슷하다 — 명시적으로 보호하고 돌보지 않으면 파괴된다.

**구체적 방향 제시**

- 데이터는 영원히 보관하지 않아야 하며 더 이상 필요하지 않으면 당장 폐기해야 한다. (다만 이는 불변성 개념과 충돌하는 것처럼 보이지만 해결 가능한 문제다.)
- 정책만 사용하는 것이 아니라 **암호화 프로토콜을 통한 접근 제어를 강제**하는 것이 하나의 전망 있는 방법이다.

**법률의 한계**: 1995년 유럽 데이터 보호 지침은 "개인 데이터는 명확하고 명시적이며 합법적인 목적으로 수집하고 이 목적과 맞지 않는 방향으로 추가 처리해서는 안 된다"고 규정한다. 그러나 이 법률이 오늘날 인터넷 맥락에서 효과적인지는 의심스럽다. 이 규칙은 직접적으로 **빅데이터 철학**(최대한 데이터를 수집하고 다른 데이터셋과 결합하며 새로운 통찰을 얻기 위해 실험하고 탐구하는 것)을 거스른다.

## 12장 전체 요약

이 장은 "가능한 모든 경우를 효율적으로 서비스할 수 있는 단일 도구는 없다"는 고찰로부터 출발한다. 따라서 제각기 자신의 목적을 달성하는 다른 종류의 여러 소프트웨어로 애플리케이션을 구성해야 하며, 이를 위해 일괄 처리와 이벤트 스트림을 사용해 데이터 통합 문제를 해결하는 방법을 설명했다. 이 접근법에서는 특정 시스템을 **레코드 시스템**으로 지정하고, 시스템에서 변환을 통해 다른 데이터를 파생시킨다. 이런 파생과 변환을 비동기식으로 만들고 느슨하게 연결하면 한 영역의 문제가 관련 없는 부분까지 전파되는 현상을 막을 수 있어 시스템 전체의 견고성과 내결함성이 증가한다.

그다음으로 결함이 있을 때도 모든 처리가 정확히 실행되게 하는 방법을 설명했다. 연산을 멱등으로 만드는 종단 간 연산 식별자를 사용하고, 제약 조건을 비동기 방식으로 확인하면 된다. 이 접근법은 분산 트랜잭션을 사용하는 전통적 접근법보다 훨씬 확장성 있고 견고하며, 실제로 많은 사업이 동작하는 방식과 잘 맞는다. 데이터플로로 애플리케이션을 구조화하고 제약 조건을 비동기로 확인하면 코디네이션 대부분을 피할 수 있고 무결성을 유지하면서 성능은 뛰어난 시스템을 만들 수 있다.

마지막으로 데이터 중심 애플리케이션 구축의 윤리적 측면을 검토했다. 데이터는 유용하게 사용될 수 있지만 중대한 해를 입힐 수도 있다. 데이터를 잘못 사용하면 사람들의 삶에 심각한 영향을 주는데도 대응하기 어려운 결정을 정당화해 차별과 착취를 유도하고, 감시를 일상화하며 개인정보를 노출할 수 있다. 소프트웨어와 데이터가 세상에 미치는 영향이 매우 크기 때문에, 엔지니어는 우리가 원하는 세상, 즉 사람이 사람답게 존중받는 세상을 위해 일할 책임이 있다는 메시지로 책 전체를 마무리한다.
