### 0. 도입: 세 가지 데이터 처리 방식

먼저 시스템을 세 유형으로 구분하고 시작합니다.

- 서비스(온라인 시스템): 요청이 오면 최대한 빨리 응답. 성능 지표는 응답 시간. 가용성이 중요.
- 일괄 처리 시스템(오프라인 시스템): 큰 입력 데이터를 받아 작업을 수행하고 결과를 생산. 보통 하루 한 번처럼 주기적으로 실행. 성능 지표는 처리량(주어진 크기의 데이터를 처리하는 데 걸리는 시간).
- 스트림 처리 시스템(준실시간): 온라인과 오프라인 사이. 입력 이벤트가 발생한 직후 바로 처리한다는 점에서 일괄 처리보다 지연 시간이 낮음. 일괄 처리를 기반으로 하므로 11장에서 다룸.

이 장은 일괄 처리를 다루며, 맵리듀스(2004년 논문)를 중심에 두고 설명합니다. 참고로 일괄 처리 자체는 새로운 개념이 아니라, 1890년 미국 인구조사의 홀러리스 천공카드 집계기, 1940년대와 1950년대의 IBM 카드 분류기 같은 오래된 뿌리를 가집니다.

### 1. 유닉스 도구로 일괄 처리하기

#### 1.1 예제: nginx 로그 분석

로그 한 줄 형식은 다음과 같습니다.

```
$remote_addr - $remote_user [$time_local] "$request" $status $body_bytes_sent "$http_referer" "$http_user_agent"
```

가장 인기 있는 페이지 5개 뽑기

```
cat access.log | awk '{print $7}' | sort | uniq -c | sort -rn | head -n 5
```

- cat: 로그 읽기
- awk '{print $7}': 7번째 필드(요청 URL) 추출
- sort: URL 알파벳순 정렬로 같은 URL이 연속으로 모임
- uniq -c: 인접한 중복 줄을 세어 제거
- sort -rn: 카운트 기준 내림차순 재정렬
- head -n 5: 상위 5개

#### 1.2 연쇄 명령과 맞춤형 프로그램

같은 작업을 루비 스크립트로 해시 테이블(counts = Hash.new(0))을 써서 구현할 수도 있습니다. 둘 다 유효하지만 대용량 데이터에서는 실행 흐름이 크게 다릅니다.

#### 1.3 정렬과 인메모리 집계

- 루비 스크립트: URL마다 카운트를 저장하는 해시 테이블을 메모리에 유지.
- 유닉스 파이프라인: 해시 테이블 없이 정렬된 목록에서 같은 URL이 반복되는 방식.
- 고유 URL 수(작업 세트)가 메모리(대략 1GB, 노트북도 충분)에 들어가면 해시 테이블 방식이 잘 동작.
- 작업 세트가 메모리보다 크면 정렬 접근법이 유리. 디스크에 청크를 정렬해 세그먼트 파일로 쓰고 병합하는 방식(SS테이블과 LSM 트리와 같은 원리). 순차 I/O라 디스크에서 성능이 좋음.
- GNU Coreutils의 sort는 메모리보다 큰 데이터셋을 자동으로 디스크로 흘려보내고 여러 CPU 코어로 자동 병렬 정렬함. 병목은 대개 디스크 읽기 속도.

#### 1.4 유닉스 철학

더그 맥일로이가 1964년 파이프를 발명했습니다. 1978년 정리된 유닉스 철학은 다음 네 가지입니다.

1. 프로그램은 한 가지 일만 잘하게 작성한다. 기능을 추가하려면 기존 프로그램을 고치기보다 새 프로그램을 작성한다.
2. 모든 프로그램 출력은 다른 프로그램 입력이 될 수 있다고 가정한다. 불필요한 정보를 넣지 말고, 엄격한 열 맞춤이나 대화형 입력을 고집하지 않는다.
3. 소프트웨어를 빠르게 써볼 수 있게 설계한다. 수 주 안에 만들고 거슬리는 부분은 과감히 버리고 새로 작성한다.
4. 미숙한 도움보다 도구를 사용한다. 도구를 빌드하는 데 시간이 들고 사용 후 바로 버리더라도 도구를 쓴다.

이는 오늘날의 애자일 및 데브옵스 운동과 매우 흡사한데, 놀랍게도 40년이 지났지만 거의 바뀌지 않았습니다.

**동일 인터페이스**

유닉스에서 인터페이스는 파일(정확히는 파일 디스크립터), 즉 순서대로 정렬된 바이트의 연속입니다. 실제 파일, 소켓, 표준 입력(stdin), 표준 출력(stdout), 장치 드라이버, TCP 연결까지 모두 이 인터페이스로 표현할 수 있습니다. 웹의 URL과 HTTP도 동일한 인터페이스 원리의 다른 예입니다. 웹사이트의 자원은 URL로 구분되며 다른 웹사이트끼리도 링크가 가능합니다. 반면 이전의 게시판 시스템(BBS)은 각 시스템끼리 동일하지 않았기 때문에, 다른 BBS로 옮겨가려면 전화번호를 쓰고 모뎀 설정을 형식에 맞게 넣어야 했고, 다른 곳의 내용을 직접 링크하는 것도 불가능했습니다.

관례상 많은 유닉스 프로그램은 연속된 바이트를 아스키 텍스트로 취급합니다. \n이 레코드 구분자로 선택된 이유는 딱히 없으며, 애초에 이런 목적으로 만든 0x1E(아스키 레코드 분리자)가 훨씬 좋은 선택이었을지도 모릅니다. 레코드 파싱은 공백이나 탭으로 나누는 경우가 많지만 CSV나 파이프 문자 등 다른 방법도 사용됩니다. xargs 같은 간단한 도구도 입력을 파싱하는 방식을 결정하는 명령줄 옵션이 6가지나 됩니다. 이런 동일 인터페이스는 완벽하지 않아도 수십 년이 지난 지금까지 상호 운용성 면에서 매우 대단합니다. 다만 데이터베이스 간 데이터 이동은 여전히 쉽지 않습니다(발칸화).

**로직과 연결의 분리**

프로그램을 아무 설정 없이 실행하면 stdin은 키보드에서 들어오고 stdout은 화면으로 출력됩니다. 혹은 파일에서 입력을 가져오거나 다른 파일로 출력을 재전송할 수도 있습니다. 파이프는 한 프로세스의 stdout을 다른 프로세스의 stdin과 연결하며, 이때 중간 데이터를 디스크에 쓰지 않고 작은 인메모리 버퍼를 사용해 데이터를 전송합니다. 이런 형태를 느슨한 결합, 지연 바인딩, 또는 제어 반전이라고 합니다. 이렇게 입출력을 연결하는 부분을 분리하면 작은 도구로부터 큰 시스템을 구성하기가 훨씬 수월합니다. 다만 stdin과 stdout에는 제약도 있습니다. 프로그램이 여러 입력이나 여러 출력을 받아야 할 때는 까다로워지고, 프로그램의 출력을 파이프를 이용해 네트워크와 직접 연결하지는 못합니다(netcat이나 curl 같은 도구는 예외).

**투명성과 실험**

유닉스 도구가 성공적인 이유 중 하나는 진행 상황을 파악하기가 쉽다는 점입니다.

- 유닉스 명령에 들어가는 입력 파일은 일반적으로 불변으로 처리된다.
- 어느 시점이든 파이프라인을 중단하고 출력을 less로 보내 원하는 형태의 출력이 나오는지 확인할 수 있다.
- 특정 파이프라인 단계의 출력을 파일에 쓰고 다음 단계의 입력으로 사용해서, 전체 파이프라인을 다시 시작하지 않고 중간 단계부터 재시작할 수 있다.

유닉스 도구는 관계형 데이터베이스의 질의 최적화 도구와 비교하면 상당히 불친절하고 단순하지만, 이처럼 놀랄 정도로 유용하며 특히 실험용으로 매우 좋습니다. 유닉스 도구를 사용하는 데 가장 큰 제약은 단일 장비에서만 실행된다는 점이며, 바로 이 점이 하둡 같은 도구가 필요한 이유입니다.

### 2. 맵리듀스와 분산 파일 시스템

#### 2.1 HDFS

맵리듀스는 유닉스 도구와 비슷한 면이 있지만 수천 대의 장비로 분산해서 실행이 가능하다는 점에서 차이가 있습니다. 하둡 맵리듀스 구현에서는 HDFS(하둡 분산 파일 시스템)를 입력과 출력으로 사용하는데, GFS(구글 파일 시스템)를 재구현한 오픈소스입니다. HDFS 외에도 GlusterFS, QFS 등 다양한 분산 파일 시스템이 있고, 아마존 S3, 애저 Blob 저장소, 오픈스택 스위프트 같은 객체 저장소도 여러 면에서 유사합니다.

HDFS는 비공유 원칙을 기반으로 하며, NAS나 SAN처럼 특별한 하드웨어가 필요 없이 일반적인 데이터센터 네트워크에 연결된 컴퓨터면 충분합니다. 네임노드라 부르는 중앙 서버가 어떤 파일 블록이 어느 장비에 저장됐는지 추적합니다. 장비가 죽거나 디스크가 실패하는 경우에 대비하기 위해 파일 블록은 여러 장비에 복제되며, 리드 솔로몬 코드 같은 삭제 코딩 방식을 사용해 데이터 전체를 복제하는 것보다 적은 저장소 부담으로 손실된 데이터를 복구하는 방식도 있습니다(RAID와 유사하지만 특별한 하드웨어 장치 없이 데이터센터 네트워크 상에서 이뤄진다는 차이가 있습니다). HDFS는 확장성이 뛰어나서, 이 책이 쓰인 시점 기준 가장 큰 HDFS는 수만 대의 장비를 묶어 수백 페타바이트 용량으로 운영되고 있습니다. 범용 하드웨어와 오픈소스 소프트웨어를 사용하기 때문에 전용 저장소 장치보다 훨씬 저렴합니다.

#### 2.2 맵리듀스 작업 실행하기

맵리듀스 작업은 4가지 단계로 수행됩니다.

1. 입력 파일을 읽어 레코드로 쪼갠다. 입력 형식 파서가 이 일을 담당한다.
2. 각 입력 레코드마다 매퍼 함수를 호출해 키와 값을 추출한다.
3. 키를 기준으로 키-값 쌍 전체를 정렬한다. 이 단계는 맵리듀스에 내재된 단계라서 직접 작성할 필요가 없다.
4. 정렬된 키-값 쌍 전체를 대상으로 리듀서 함수를 호출한다. 같은 키가 여러 번 등장했다면 정렬 과정에서 해당 키-값 쌍은 서로 인접하게 된다.

매퍼는 모든 입력 레코드마다 한 번씩 호출되며 입력 레코드로부터 키와 값을 추출하는 작업을 합니다. 각 입력으로부터 생성하는 키-값 쌍은 빈 쌍을 포함해 원하는 만큼 생성할 수 있고, 레코드 간 상태를 유지하지 않기 때문에 각 레코드를 독립적으로 처리합니다. 리듀서는 매퍼가 생성한 카-값 쌍을 받아 같은 키를 가진 레코드를 모아 그 값의 집합을 반복해 함수를 호출받습니다. 리듀서는 출력 레코드를 생산합니다.

입력 디렉터리 내 각 파일 또는 파일 블록을 독립된 맵 태스크에서 처리할 독립 파티션으로 간주합니다(그림 10-1에서 맵 태스크를 m1, m2, m3로 표시). 각 매퍼 입력 파일의 복제본이 있는 장비에 RAM과 CPU 여유가 충분하다면 맵리듀스 스케줄러가 입력 파일이 있는 장비에서 작업을 수행하려 합니다. 이 원리를 데이터 가까이에서 연산하기라 하는데, 이 원리를 적용하면 네트워크를 통해 입력 파일을 복사하는 부담과 네트워크 부하가 감소하고 지역성이 증가합니다.

#### 2.3 맵리듀스의 분산 실행

유닉스 명령어 파이프라인과의 가장 큰 차이점은 맵리듀스가 병렬로 수행하는 코드를 직접 작성하지 않고도 여러 장비에서 동시에 처리가 가능하다는 점입니다. 매퍼와 리듀서는 한 번에 하나의 레코드만 처리하고 입력이 어디서 오는지, 출력이 어디로 가는지 신경 쓰지 않습니다. 맵리듀스 프레임워크가 장비 간에 데이터가 이동하는 복잡한 부분을 처리해줍니다.

대부분의 경우 맵 태스크에서 실행될 애플리케이션 코드는 작업이 할당된 장비에 아직 존재하지 않기 때문에 맵리듀스 프레임워크가 적절한 장비로 코드(자바 프로그램이면 JAR 파일)를 복사합니다. 복사가 끝나면 매퍼 태스크가 시작되고, 입력 파일을 한 번에 레코드 하나씩 읽어 매퍼 콜백 함수로 전달합니다. 매퍼의 출력은 키-값 쌍으로 구성됩니다.

리듀서 측 연산도 파티셔닝됩니다. 맵 태스크 수는 입력 파일의 블록 수로 결정되지만 리듀서 태스크 수는 사용자가 설정합니다. 즉 맵 태스크 수와 리듀서 태스크 수는 다를 수 있습니다. 맵리듀스 프레임워크는 같은 키를 가진 모든 키-값 쌍을 같은 리듀서에서 처리하는 것을 보장하는데, 특정 키-값 쌍이 어느 리듀서 태스크에서 수행될지 결정하기 위해 키의 해시값을 사용합니다.

키-값 쌍은 반드시 정렬돼야 하지만 대개 데이터셋이 매우 크기 때문에 일반적인 정렬 알고리즘으로 한 장비에서 모두 정렬하기는 쉽지 않습니다. 그래서 단계를 나누어 정렬을 수행합니다. 먼저 각 맵 태스크는 키의 해시값을 기반으로 출력을 리듀서로 파티셔닝하고, 그다음 각 파티션을 매퍼의 로컬 디스크에 정렬된 파일로 기록합니다. 매퍼가 입력 파일을 읽어 정렬된 출력 파일을 기록하기를 완료하면 맵리듀스 스케줄러는 그 매퍼로부터 출력 파일을 가져올 수 있다고 리듀서에게 알려줍니다. 리듀서는 각 매퍼와 연결해서 자신이 담당하는 파티션에 해당하는 정렬된 키-값 쌍 파일을 다운로드합니다. 리듀서를 기준으로 파티셔닝하고 정렬한 뒤 매퍼로부터 데이터 파티션을 복사하는 과정을 셔플이라 합니다. 셔플이라면 카드를 섞는 것이라 생각하기 쉽지만 맵리듀스에서 셔플은 임의로 섞지 않습니다.

리듀스 태스크는 매퍼로부터 파일을 가져와 정렬된 순서를 유지하면서 병합합니다. 그렇기 때문에 다른 매퍼가 동일한 키로 레코드를 생성하면 병합된 이후 리듀서의 입력으로 들어갈 때는 서로 인접하게 됩니다.

#### 2.4 맵리듀스 워크플로

맵리듀스 작업 하나로 해결할 수 있는 문제의 범위는 제한적입니다. 로그 분석 예제에서 단일 맵리듀스 작업으로 URL당 페이지뷰 수를 구할 수 있지만 가장 인기 있는 URL을 구할 수는 없습니다. 그러기 위해서는 추가로 정렬 작업이 필요합니다.

따라서 맵리듀스 작업을 연결해 워크플로로 구성하는 방식은 꽤 일반적입니다. 맵리듀스 작업 하나의 출력을 다른 맵리듀스 작업의 입력으로 사용하는 식입니다. 하둡 맵리듀스 프레임워크는 워크플로를 직접 제공하지 않기 때문에 맵리듀스 작업은 디렉터리 이름을 통해 암묵적으로 연결되는데, 첫 번째 작업은 HDFS상에 지정된 디렉터리에 출력하도록 설정하고 두 번째 작업은 해당 디렉터리를 입력으로 사용하도록 설정해야 합니다. 맵리듀스 프레임워크 관점에서 보면 두 작업은 완전히 독립적입니다.

일괄 처리 작업의 출력은 작업이 성공적으로 끝났을 때만 유효합니다(맵리듀스는 작업이 실패하고 남은 부분 출력은 제거합니다). 그렇기 때문에 워크플로 상에서 해당 작업의 입력 디렉터리를 생성하는 선행 작업이 완전히 끝나야만 다음 작업을 시작할 수 있습니다. 하둡 맵리듀스 작업 간 수행 의존성을 관리하기 위해 다양한 스케줄러가 개발됐는데, 스케줄러의 예로 우지, 아즈카반, 루이지, 에어플로, 핀볼 등이 있습니다. 추천 시스템을 구축하는 데 사용하는 워크플로는 50개에서 100개가 일반적입니다.

피그, 하이브, 캐스캐이딩, 크런치, 플룸자바 같은 다양한 하둡용 고수준 도구는 다중 맵리듀스를 서로 적절하게 자동으로 엮어 워크플로를 설정합니다.

### 3. 리듀스 사이드 조인과 그룹화

#### 3.1 조인이 필요한 이유

여러 데이터셋에서 한 레코드가 다른 레코드와 연관이 있는 것은 일반적입니다. 관계형 모델에서는 외래키, 문서 모델에서는 문서 참조라 하고 그래프 모델에서는 간선이라 부릅니다. 연관된 레코드 양쪽(참조하는 레코드와 참조되는 레코드) 모두에 접근해야 하는 코드가 있다면 조인은 필수입니다. 비정규화 작업으로 조인을 줄일 수는 있지만 일반적으로 완전히 제거하기는 어렵습니다. 이 책에서 다루는 조인은 일반적으로 동등 조인을 말합니다.

#### 3.2 사용자 활동 이벤트 분석 예제

일괄 처리 작업에서 전형적인 조인 예제로, 왼쪽은 로그인 사용자가 웹사이트에서 활동한 이벤트 로그(활동 이벤트, 또는 클릭스트림 데이터)고 오른쪽은 사용자 데이터베이스입니다. 이벤트 로그는 사실 테이블이고 사용자 데이터베이스는 여러 차원 중 하나입니다.

이 분석 태스크는 사용자 활동과 사용자 프로필 정보를 연관시켜야 합니다. 하지만 활동 이벤트는 단지 사용자 ID만 포함하고 전체 사용자 프로필 정보를 포함하지 않습니다. 단일 활동 이벤트마다 모든 사용자 프로필 정보를 합치는 건 엄청나게 낭비이므로, 활동 이벤트에 사용자 프로필 데이터베이스를 조인해야 합니다.

이 조인을 가장 간단하게 구현하는 방법은 활동 이벤트를 훑으면서 나오는 모든 사용자 ID마다 원격 서버에 있는 사용자 데이터베이스에 질의를 보내는 것입니다. 나쁜 성능 때문에 고생할 가능성이 높습니다. 데이터베이스와 통신할 때 발생하는 왕복 시간으로 처리량이 제한되고 지역 캐시의 효율성은 데이터 분포에 크게 좌우되며, 상당히 많은 질의가 병렬로 실행되면 데이터베이스에 과부하가 걸리기 쉽습니다.

일괄 처리에서 처리량을 높이기 위해서는 가능한 한 장비 내에서 연산을 수행해야 합니다. 원격 데이터베이스에 질의한다는 건 일괄 처리가 비결정적이라는 뜻입니다. 원격 데이터베이스의 데이터가 변경될 수 있기 때문입니다. 따라서 더 좋은 방법은 사용자 데이터베이스의 사본을 ETL 처리를 통해 데이터베이스 백업으로부터 추출해서 사용자 활동 이벤트 로그가 저장된 분산 파일 시스템에 넣는 것입니다. 그러면 사용자 데이터베이스와 사용자 활동 레코드가 같은 HDFS 상에 존재하고 맵리듀스를 사용해 연관된 레코드끼리 모두 같은 장소로 모아 효율적으로 처리가 가능합니다.

#### 3.3 정렬 병합 조인

매퍼는 입력 레코드로부터 키와 값을 추출하는 것이 목적입니다. 한 매퍼는 활동 이벤트를 훑어 사용자 ID를 키로, 활동 이벤트를 값으로 추출하고 다른 매퍼는 사용자 데이터베이스를 훑어 사용자 ID를 키로 사용자 생일을 값으로 추출합니다.

맵리듀스 프레임워크에서 키로 매퍼의 출력을 파티셔닝해 키-값 쌍으로 정렬한다면, 같은 사용자의 활동 이벤트와 사용자 레코드는 리듀서의 입력으로 서로 인접해서 들어갑니다. 리듀서가 항상 사용자 데이터베이스를 먼저 보고 활동 이벤트를 시간 순으로 보게 하는 식으로 맵리듀스에서 작업 레코드를 재배열하기도 하는데, 이 기술을 보조 정렬이라 합니다.

보조 정렬 후 리듀서가 수행하는 실제 조인 로직은 간단합니다. 리듀서 함수는 모든 사용자 ID당 한 번만 호출되고, 보조 정렬 덕분에 첫 번째 값은 사용자 데이터베이스의 생년월일 레코드로 예상할 수 있습니다. 리듀서는 지역 변수에 생년월일을 저장하고 그다음부터 같은 사용자 ID가 동일한 활동 이벤트를 순회해서 본 URL과 본 사람의 연령의 쌍을 출력합니다. 그러면 맵리듀스 작업들이 각 URL마다 본 사람의 연령 분포를 계산하고 연령대별로 클러스터링할 수 있습니다.

리듀서는 특정 사용자 ID의 모든 레코드를 한 번에 처리하므로 한 번에 사용자 한 명의 레코드만 메모리에 유지하면 되고 네트워크로 아무 요청도 보낼 필요가 없습니다. 이 알고리즘을 정렬 병합 조인이라 합니다. 매퍼 출력이 키로 정렬된 후에 리듀서가 조인의 양측의 정렬된 레코드 목록을 병합하기 때문입니다.

아키텍처의 이해를 돕기 위해 매퍼가 리듀서로 메시지 전송하는 방식을 살펴보면, 매퍼가 키-값 쌍을 내보낼 때 키는 값을 보낼 목적지의 주소 역할을 합니다. 키가 IP 주소와 포트번호 같은 실제 네트워크 주소가 아니라 일반 문자열일 뿐이지만 주소처럼 동작합니다. 같은 키를 가진 키-값 쌍은 모두 같은 목적지로 배달됩니다(같은 리듀서를 호출합니다). 맵리듀스 프로그래밍 모델은 올바른 장비로 데이터를 모으는 연산의 물리적 네트워크 통신 측면과 받은 데이터를 처리하는 애플리케이션 로직을 분리합니다. 맵리듀스는 모든 네트워크 통신을 직접 관리하기 때문에 특정 장비가 죽는 것과 같이 부분적으로 실패가 발생하더라도 애플리케이션 코드 단에서 고민할 필요가 없습니다. 맵리듀스는 애플리케이션 로직에 영향이 가지 않게 실패한 태스크를 확실하게 재시도합니다.

#### 3.4 그룹화

조인 외에도 같은 곳으로 관련 데이터를 모으는 일반적인 사용 유형은 SQL에서 GROUP BY 절과 같이 특정 키로 레코드를 그룹화하는 것입니다. 같은 키를 가진 모든 레코드로 그룹을 만들고, 다음 단계로 각 그룹 내에서 집계 연산을 하는데 아래와 같은 예가 있습니다.

- 각 그룹의 레코드 수를 카운트한다(SQL로는 COUNT(*)).
- 특정 필드 내 모든 값을 더한다(SQL로는 SUM(fieldname)).
- 어떤 랭킹 함수를 실행했을 때 상위 k개의 레코드를 고른다.

맵리듀스로 그룹화 연산을 구현하는 가장 간단한 방법은 매퍼가 키-값 쌍을 생성할 때 그룹화할 대상을 키로 하는 것입니다. 그러면 파티션 및 정렬 프로세스가 같은 키를 가진 모든 레코드를 같은 리듀서로 모읍니다. 즉 맵리듀스 위에서 그룹화와 조인의 구현은 상당히 유사합니다.

특정 사용자가 취한 일련의 활동을 찾기 위해 사용자 세션별 활동 이벤트를 수집 분석할 때도 일반적으로 그룹화를 사용합니다. 이 과정을 세션화라고 하는데, 예를 들면 사용자에게 옛 버전 웹사이트를 보여줬을 때보다 새 버전 웹사이트를 보여줬을 때 구매를 더 했는지(A/B 테스트) 확인하거나, 어떤 마케팅 활동이 가치 있는지 분석하는 것을 말합니다.

사용자 요청을 받는 웹 서버가 여러 개라면 특정 사용자의 활동 이벤트는 여러 서버로 분산돼 각각 다른 로그 파일에 저장됩니다. 세션 쿠키, 사용자 ID나 유사한 식별자를 그룹화 키로 사용해 특정 사용자 활동 이벤트를 모두 한 곳으로 모으면 세션화를 구현할 수 있습니다. 이때 서로 다른 사용자의 이벤트는 다른 파티션으로 골고루 분산됩니다.

#### 3.5 쏠림 다루기

키 하나에 너무 많은 데이터가 연관된다면, 같은 키를 가지는 모든 레코드를 같은 장소로 모으는 패턴은 제대로 작동하지 않습니다. 소셜 네트워크를 예로 들면 사람들 대다수는 많아야 수백 명 정도 연결되는 데 반해 소수의 유명 인사는 팔로워가 수백만 명에 이르기도 합니다. 이렇게 불균형한 활성 데이터베이스 레코드를 린치핀 객체 또는 핫 키라 합니다.

유명 인사 한 사람에 관련된 모든 활동을 리듀서 한 개에서 모은다면 상당한 쏠림 현상이 생깁니다. 이런 현상을 핫스팟이라 합니다. 즉 한 리듀서가 다른 리듀서보다 엄청나게 많은 레코드를 처리해야 한다는 뜻입니다. 모든 매퍼와 리듀서가 완전히 끝나야만 맵리듀스 작업이 끝나기 때문에 가장 느린 리듀서가 작업을 완료할 때까지 후속 작업들은 시작하지 못한 채 기다려야 합니다.

조인 입력에 핫 키가 존재하는 경우에 핫스팟을 완화할 몇 가지 알고리즘이 있습니다.

- 피그에 있는 쏠린 조인 메서드는 어떤 키가 핫 키인지 결정하기 위해 샘플링 작업을 수행합니다. 실제 조인을 수행할 때 매퍼는 핫 키를 가진 레코드는 여러 리듀서 중 임의로 선택한 하나로 레코드를 보냅니다. 키의 해시값을 기반으로 리듀서를 결정하는 관습적인 맵리듀스와는 반대입니다. 핫 키로 조인할 다른 입력은 핫 키가 전송된 모든 리듀서에 복제합니다. 다른 조인 입력을 여러 리듀서로 복제하는 비용이 들지만 병렬화 효과가 훨씬 큽니다.
- 크런치에서 제공하는 공유 조인 메서드가 이 기법과 비슷하지만 샘플링 작업 대신 핫 키를 명시적으로 지정해야 합니다.
- 하이브는 쏠린 조인을 최적화할 때 다른 방법을 사용합니다. 핫 키를 테이블 메타데이터에 명시적으로 지정하고 핫 키와 관련된 레코드를 나머지 키와는 별도 파일에 저장합니다. 해당 테이블에서 조인할 때 핫 키를 가지는 레코드는 맵 사이드 조인을 사용해 처리합니다.

핫 키로 레코드를 그룹화하고 집계하는 작업은 두 단계로 수행됩니다. 첫 번째 맵리듀스 단계는 레코드를 임의의 리듀서로 보냅니다. 각 리듀서는 핫 키 레코드의 일부를 그룹화하고 키별로 집계해 간소화한 값을 출력합니다. 두 번째 맵리듀스 작업은 첫 단계 모든 리듀서에서 나온 값을 키별로 모두 결합해 하나의 값으로 만듭니다.

### 4. 맵 사이드 조인

지금까지 설명한 여러 조인 알고리즘은 실제 조인 로직을 리듀서에서 수행하기 때문에 리듀스 사이드 조인이라 합니다. 매퍼는 각 입력 레코드에서 키와 값을 추출해 추출한 키-값 쌍을 리듀서 파티션으로 할당하고 키별로 정렬하는, 즉 입력 데이터를 준비하는 역할을 합니다.

리듀스 사이드 접근법의 장점은 입력 데이터에 대한 특정 가정이 필요없다는 점입니다. 입력 데이터의 속성과 구조가 무엇이든 매퍼는 데이터를 조인할 준비를 할 수 있습니다. 그러나 정렬 후 리듀서로 복사한 뒤 리듀서 입력을 병합하는 모든 과정에 드는 비용이 상당하다는 점이 큰 단점입니다.

반면 입력 데이터에 대해 특정 가정이 가능하다면 맵 사이드 조인이라 불리는 기법을 사용해 조인을 더 빠르게 수행할 수 있습니다. 이 접근법은 축소된 맵리듀스 작업으로, 리듀서는 물론 정렬 작업도 없습니다. 대신 각 매퍼가 할 작업은 분산 파일 시스템에서 단순히 입력 파일 블록 하나를 읽어 다시 해당 분산 파일 시스템에 출력하는 것이 전부입니다.

#### 4.1 브로드캐스트 해시 조인

맵 사이드 조인은 작은 데이터셋과 매우 큰 데이터셋을 조인하는 경우에 가장 간단하게 적용해볼 수 있습니다. 특히 이때 사용하는 작은 데이터셋은 전체를 각 매퍼 메모리에 적재 가능할 정도로 충분히 작아야 합니다.

매퍼가 시작할 때 우선 분산 파일 시스템에서 사용자 데이터베이스를 읽어서 인메모리 해시 테이블에 넣습니다. 일단 이 작업을 수행하고 나면 매퍼는 사용자 활동 이벤트를 모두 스캔할 수 있고 각 이벤트의 사용자 ID를 해시 테이블에서 간단하게 조회할 수 있습니다. 맵 태스크를 여러 개 사용할 수도 있는데, 각 맵 태스크에 조인할 큰 입력 파일 블록 중 하나를 할당하면 됩니다. 모든 매퍼는 작은 입력 전체를 메모리에 적재합니다.

이 간단하고 효율적인 알고리즘을 브로드캐스트 해시 조인이라 합니다. 브로드캐스트라는 단어는 큰 입력의 파티션 하나를 담당하는 각 매퍼는 작은 입력 전체를 읽는다는 것을 의미합니다(그래서 실질적으로 작은 입력을 큰 입력의 모든 파티션에 브로드캐스트합니다). 해시라는 단어는 해시 테이블을 사용한다는 뜻입니다. 피그(복제 조인이란 이름), 하이브(맵조인), 캐스캐이딩, 크런치가 이런 메서드를 지원합니다. 또한 임팔라 같은 데이터 웨어하우스 질의 엔진에서도 사용합니다.

작은 조인 입력을 인메모리 해시 테이블로 적재하는 대신 로컬 디스크에 읽기 전용 색인으로 작은 조인 입력을 저장하기도 합니다. 이 색인 중 자주 사용된 부분은 운영체제의 페이지 캐시에 남습니다. 따라서 이 방법을 사용하면 데이터셋 전체가 메모리 안에 들어오지 않더라도 거의 인메모리 해시 테이블만큼 빠르게 임의 접근 조회가 가능합니다.

#### 4.2 파티션 해시 조인

같은 방식으로 맵 사이드 조인의 입력을 파티셔닝한다면 해시 조인 접근법을 각 파티션에 독립적으로 적용할 수 있습니다. 활동 이벤트와 사용자 데이터베이스를 사용자 ID의 마지막 십진수를 기준으로 파티셔닝해 재배열할 수 있습니다(따라서 양쪽 모두 10개의 파티션이 생깁니다). 예를 들어 3번 매퍼가 ID가 3으로 끝나는 모든 사용자를 해시 테이블에 올리고 ID가 3으로 끝나는 각 사용자 활동 이벤트 모두를 스캔하는 식입니다.

제대로 파티셔닝이 작동했다면 조인할 레코드 모두가 같은 번호의 파티션에 위치합니다. 그래서 각 매퍼는 각 입력 데이터셋 중 파티션 한 개만 읽어도 충분합니다. 이 방법은 각 매퍼의 해시 테이블에 적재해야 할 데이터의 양을 줄일 수 있다는 점이 장점입니다.

파티션 해시 조인은 조인할 두 입력 모두를 같은 키와 같은 해시 함수를 기반으로 같은 수로 파티셔닝해야 작동합니다. 하이브에서는 이를 버킷 맵 조인이라 합니다.

#### 4.3 맵 사이드 병합 조인

입력 데이터셋이 같은 방식으로 파티셔닝됐을 뿐 아니라 같은 키를 기준으로 정렬됐다면 변형된 맵 사이드 조인을 적용할 수 있습니다. 이때 입력 크기가 메모리에 적재 가능한지 고려할 필요가 없습니다. 매퍼는 리듀서에서 일반적으로 수행하는 것과 동일한 병합 연산을 수행할 수 있기 때문입니다. 오름차순으로 양쪽 입력 모두를 점진적으로 읽어 키가 동일한 레코드를 맞춥니다.

맵 사이드 병합 정렬이 가능하다면 선행 맵리듀스 작업이 이미 입력 데이터셋을 파티셔닝하고 정렬해 놓았다는 뜻입니다. 이론상으로는 맵 사이드 병합 정렬을 이전 맵리듀스 작업의 리듀스 단계에서 수행할 수도 있습니다. 그러나 맵 전용 작업에서 병합 조인을 수행하는 편이 나을 때도 있는데, 예를 들면 파티셔닝 및 정렬된 데이터셋이 바로 이 조인 외에 다른 용도로 필요한 경우가 그렇습니다.

#### 4.4 맵 사이드 조인을 사용하는 맵리듀스 워크플로

맵리듀스 조인의 출력을 하위 작업에서 입력으로 사용할 때, 맵 사이드 조인을 사용할지 리듀스 사이드 조인을 사용할지에 따라 그 출력 구조가 달라집니다. 리듀스 사이드 조인은 조인 키로 파티셔닝하고 정렬해서 출력합니다. 반면 맵 사이드 조인은 큰 입력과 동일한 방법으로 파티셔닝하고 정렬합니다. 파티션 조인을 사용하든 브로드캐스트 조인을 사용하든 간에 큰 조인 입력의 파일 블록마다 맵 태스크가 실행되기 때문입니다.

맵 사이드 조인을 수행하기 위해서는 크기, 정렬, 입력 데이터의 파티셔닝 같은 제약 사항이 따릅니다. 조인 전략을 최적화할 때는 분산 파일 시스템 내 저장된 데이터셋의 물리적 레이아웃 파악이 중요합니다. 단지 부호화 형식이나 데이터가 저장된 디렉터리 이름을 아는 것으로는 부족합니다. 파티션 수가 몇 개인지, 데이터가 어떤 키를 기준으로 파티셔닝되고 정렬됐는지도 꼭 알아야 합니다. 하둡 생태계에서는 데이터셋 파티셔닝 관련 메타데이터를 관리하는 HCatalog나 하이브 메타스토어를 사용하기도 합니다.

### 5. 일괄 처리 워크플로의 출력

데이터베이스 질의의 경우 트랜잭션 처리(OLTP)를 분석 목적과 구별했습니다. OLTP 질의는 색인을 사용해 사용자에게 보여줄 소량의 레코드만 특정 키로 조회하는 것이 일반적입니다. 반면 분석 질의는 대량의 레코드를 스캔해 그룹화와 집계 연산을 수행하고 그 결과를 보고서 형태로 출력합니다.

그러면 일괄 처리는 어디에 적합할까요. 트랜잭션 처리도 아니고 분석도 아닙니다. 일괄 처리는 입력 데이터셋 대부분을 스캔하는 것이 일반적이라 분석에 더 가깝습니다. 그러나 맵리듀스 작업의 워크플로는 분석 목적으로 사용하는 SQL 질의와는 다릅니다. 일괄 처리의 출력은 흔히 보고서가 아닌 다른 형태의 구조입니다.

#### 5.1 검색 색인 구축

맵리듀스는 구글에서 검색 엔진에 사용할 색인을 구축하기 위해 처음 사용됐는데, 그 당시 사용된 워크플로는 5개에서 10개의 맵리듀스 작업으로 구현됐습니다. 구글이 색인을 구축하는 목적으로는 맵리듀스를 더 이상 사용하지 않지만, 검색 색인을 구축하는 과정을 자세히 살펴보면 맵리듀스를 이해하는 데 도움이 많이 됩니다(최근에도 루씬이나 솔라용 색인을 구축하는 데 맵리듀스는 여전히 훌륭한 방법입니다).

정해진 문서 집합을 대상으로 전문 검색이 필요하다면 일괄 처리가 색인을 구축하는 데 매우 효율적입니다. 매퍼는 필요에 따라 문서 집합을 파티셔닝하고, 각 리듀서가 해당 파티션에 대한 색인을 구축합니다. 그리고 색인 파일은 분산 파일 시스템에 저장됩니다. 문서 기준으로 파티셔닝해 색인을 구축하는 과정은 병렬화가 매우 잘 됩니다. 키워드로 검색 색인에 질의하는 연산은 읽기 전용이라서 색인 파일을 한번 생성하면 불변입니다.

색인된 문서 집합이 변한다면 전체 문서 집합을 대상으로 주기적으로 전체 색인 워크플로를 재수행하고, 수행이 끝나면 이전 색인 파일을 새로 생성된 색인으로 바꾸는 것이 한 가지 방법입니다. 다른 방법으로 증분 색인을 구축하는 것도 가능한데, 색인에 문서를 추가하고 지우고 갱신하길 원한다면 루씬은 세그먼트 파일을 새로 기록하고 백그라운드에서 증분식으로 부분 파일을 병합하고 압축합니다.

#### 5.2 일괄 처리의 출력으로 키-값을 저장

검색 색인은 일괄 처리 워크플로 출력의 한 가지 예일 뿐입니다. 다른 예로 분류기 같은 머신러닝 시스템(스팸 필터, 이상 검출, 이미지 인식 등)을 구축하거나 추천 시스템(알지도 모르는 사람이나 관심 가질 만한 상품, 연관 검색 등)을 구축할 수 있습니다.

이런 일괄 처리 작업의 출력은 흔히 일종의 데이터베이스가 됩니다. 이 같은 데이터베이스는 하둡 인프라와 별도로 사용자 요청을 받는 웹 애플리케이션에서 질의해야 합니다. 가장 확실한 방법은 직접 매퍼와 리듀서 내에서 선호하는 데이터베이스 클라이언트 라이브러리를 사용해 일괄 처리 작업이 한 번에 레코드 하나씩 데이터베이스 서버로 직접 요청을 보내는 것입니다. 이 방법은 유효하지만 좋은 아이디어는 아닌데, 이유는 다음과 같습니다.

- 이전 조인과 관련한 설명처럼 모든 레코드마다 네트워크 요청을 하는 작업은 일반적인 일괄 처리 태스크의 처리량에 비해 상당히 느립니다.
- 맵리듀스 작업은 대개 많은 태스크를 동시에 실행하는데, 모든 매퍼나 리듀서가 일괄 처리에서 기대하는 속도로 동시에 같은 출력 데이터베이스에 기록한다면 데이터베이스가 과부하 상태에 빠지기 쉽습니다.
- 일반적으로 맵리듀스 작업은 성공한 경우에만 출력을 생성하는 것을 보장하지만, 작업 내부에서 외부 시스템에 기록한다면 부분적으로만 완료된 작업의 결과가 외부 시스템에 드러나는 상황이 발생할 수 있습니다.

훨씬 좋은 해결책은 일괄 처리 작업 내부에 완전히 새로운 데이터베이스를 구축해 분산 파일 시스템의 작업 출력 디렉터리에 저장하는 방법으로, 검색 색인과 유사한 구조로 저장합니다. 이 데이터 파일은 한 번 기록되면 불변이고 서버에 벌크로 적재해 읽기 전용 질의를 처리할 수 있습니다. 다양한 키-값 저장소가 맵리듀스 작업 내에서 데이터베이스 파일을 구축하는 기능을 지원하는데, 예를 들어 볼드모트, 테라핀, 엘리펀트DB, HBase 벌크 적재 등이 있습니다.

데이터베이스 파일을 생성하는 작업은 굉장히 좋은 맵리듀스 활용법입니다. 매퍼로 키를 추출한 다음 키로 정렬하는 과정은 색인을 만들 때도 꼭 필요한 작업입니다. 키-값 저장소가 대부분 읽기 전용이기 때문에(이 파일들이 일괄 처리 작업에서 기록된 후 변하지 않기 때문에) 자료 구조가 매우 단순합니다. 단적으로 이런 저장소는 WAL이 필요하지 않습니다.

볼드모트에 데이터를 적재할 때 분산 파일 시스템에서 서버의 로컬 디스크로 새 데이터 파일을 복사하는 동안 서버는 기존 데이터 파일로 요청을 계속 처리합니다. 복사를 완료하면 서버는 질의 요청을 원자적으로 새 파일로 바꿉니다. 이 과정 중 문제가 발생하면 기존 파일이 아직 남아있고 역시 불변이기 때문에 쉽게 기존 파일로 전환할 수 있습니다.

#### 5.3 일괄 처리 출력에 관한 철학

이번 장 전반부에서 설명한 유닉스 철학은 데이터플로가 프로그램이 입력을 읽어 출력을 내놓는다로 명확하기 때문에 실험을 장려합니다. 이 과정에서 입력은 변하지 않은 채 새 출력이 이전 출력을 완벽하게 교체합니다. 이 과정에는 아무런 부수 효과가 없습니다. 이는 시스템 상태를 엉망으로 만들지 않고도 얼마든지 원하는 만큼 프로그램을 수정하거나 디버깅 용도로 명령을 재실행할 수 있다는 뜻입니다.

맵리듀스 작업도 마찬가지 철학으로 출력을 취급합니다. 입력을 불변으로 처리하고 외부 데이터베이스에 기록하는 등의 부수 효과를 피하기 때문에 일괄 처리 작업은 좋은 성능을 내면서도 유지보수가 훨씬 간단합니다.

- 코드에 버그가 있어 출력이 잘못되거나 오염됐다면 코드를 이전 버전으로 돌리고 작업을 재수행해 간단하게 출력을 고칠 수 있습니다. 혹시 다른 디렉터리에 이전 출력을 기록했다면 간단하게 출력의 위치만 바꿔 복구할 수 있습니다. 읽기 쓰기 트랜잭션이 있는 데이터베이스는 이런 속성이 없습니다. 버그 있는 코드를 배포해 데이터베이스에 잘못된 데이터를 기록하면 코드를 되돌리는 것만으로 데이터베이스의 데이터를 고쳐주지 않습니다(버그 있는 코드로부터 복원할 수 있느냐에 관한 개념을 인적 내결함성이라 합니다).
- 쉽게 되돌릴 수 있는 속성의 결과로 실수를 하면 손상을 되돌릴 수 없는 환경에서보다 기능 개발을 빠르게 진행할 수 있습니다. 비가역성 최소화 원리는 애자일 소프트웨어 개발에 이롭습니다.
- 맵이나 리듀스 태스크가 실패하면 맵리듀스 프레임워크가 해당 태스크를 자동으로 다시 스케줄링하고 동일한 입력을 사용해 재실행합니다. 코드 내 버그로 발생한 실패라면 태스크가 계속해서 죽고 몇 번 시도한 뒤 결국 작업이 실패합니다. 하지만 일시적 문제로 발생한 실패라면 충분히 견딜 수 있습니다. 이런 재시도가 안전한 이유는 입력이 불변이고 맵리듀스 프레임워크가 실패한 태스크의 출력을 폐기하기 때문입니다.
- 다양한 작업에서 입력으로 동일한 파일 집합을 사용하곤 합니다. 모니터링 작업에서 지표를 계산해서 작업의 결과가 기대했던 특성을 가지는지 평가하는 경우가 그렇습니다. 현재 실행과 이전 실행의 출력을 비교해 차이를 측정하는 것이 그 사례 중 하나입니다.
- 유닉스 도구와 마찬가지로 맵리듀스 작업은 입출력 디렉터리를 설정하는 등의 연결 작업과 로직을 분리합니다. 그래서 로직과 연결 작업에서 발생하는 관심사를 각각 따로 처리할 수 있고 잠재적으로 코드 재사용도 가능합니다. 한 팀이 한 가지 일을 잘 처리하는 작업을 구현하는 데 집중하는 동안 다른 팀은 언제 어디에서 작업을 수행하는 게 좋을지 결정할 수 있습니다.

이 영역에서는 유닉스에서 잘 동작한 설계 원칙이 하둡에도 잘 동작하는 것 같지만 유닉스와 하둡은 몇 가지 면에서 다릅니다. 예를 들어 유닉스 도구 대부분은 타입이 없는 텍스트 파일을 가정하고 처리하기 때문에 입력을 파싱하는 부담이 있습니다(URL을 추출하기 위해 {print $7}을 사용한 것처럼). 하둡에서는 구조화된 파일 형식을 사용하면 저수준 구문 변환 작업 중 일부를 하지 않아도 됩니다. 아브로와 파케이가 자주 사용하는 구조화 파일 형식인데, 이런 형식은 효율적인 스키마 기반 부호화를 제공하고 시간이 지남에 따라 스키마를 발전시킬 수 있습니다.

### 6. 하둡과 분산 데이터베이스의 비교

지금까지 살펴본 대로 하둡은 유닉스의 분산 버전과 다소 비슷합니다. HDFS는 파일 시스템이고 맵리듀스는 특별한 방식으로 구현된 유닉스 프로세스입니다(맵 단계와 리듀스 단계 사이에서는 항상 sort 유틸리티를 실행합니다). 또한 하둡의 맵리듀스 기본 요소 위에서 조인과 그룹화를 구현하는 다양한 방식에 대해 알아봤습니다.

맵리듀스 논문이 발간됐을 때 어떻게 보면 맵리듀스는 전혀 새로운 개념이 아니었습니다. 지난 몇 개 절에서 설명했던 처리 알고리즘과 병렬 조인 알고리즘은 수십 년 전에 이른바 대규모 병렬 처리(MPP) 데이터베이스라 불리는 것에서 모두 구현됐습니다. 감마 데이터베이스 머신, 테라데이터, 탠덤 논스톱 SQL이 이 영역의 선구자입니다.

맵리듀스와의 가장 큰 차이점을 보면 MPP 데이터베이스는 장비 클러스터에서 분석 SQL 질의를 병렬로 수행하는 것에 초점을 두지만, 맵리듀스와 분산 파일 시스템의 조합은 아무 프로그램이나 실행할 수 있는 운영체제와 비슷한 속성을 제공합니다.

#### 6.1 저장소의 다양성

데이터베이스는 특정 모델(예를 들어 관계형 또는 문서형)을 따라 데이터를 구조화해야 합니다. 반면 분산 파일 시스템의 파일은 어떤 데이터 모델과 인코딩을 사용해서도 기록할 수 있는 연속된 바이트일 뿐입니다. 이 파일은 데이터베이스 레코드 집합일 수도 있지만 텍스트나 이미지, 비디오, 센서 판독값, 희소 행렬, 특징 벡터, 게놈 시퀀스 등 다른 어떤 형태도 가능합니다.

극단적으로 말하자면 하둡은 데이터가 어떤 형태라도 상관없이 HDFS로 덤프할 수 있는 가능성을 열어놓았습니다. 데이터를 어떻게 처리할지는 덤프 이후에야 생각합니다. 반대로 MPP 데이터베이스를 사용하면 대개 데이터베이스에 특화된 저장 형태로 데이터를 가져오기 전에 데이터와 질의의 형태를 신중하게 선행 모델링해야 합니다.

당연하게도 순수주의자 관점에서 보면 세심하게 모델링하고 데이터를 가져오는 일은 바람직한 작업입니다. 데이터베이스 사용자가 작업하기 좋은 양질의 데이터를 가지게 된다는 뜻이기 때문입니다. 그러나 현실에서는 이상적인 데이터 모델을 만들려고 하기보다 데이터를 빨리 사용 가능하게 만드는 것(데이터가 특이하거나 사용하기 어렵거나 원시 형식일지라도)이 더 가치 있는 경우가 많습니다.

이 아이디어는 데이터 웨어하우스의 개념과 유사합니다. 커다란 조직의 다양한 부분에서 나온 데이터를 한 곳에 모으는 작업만으로 큰 가치가 있습니다. 이전에는 이질적이던 데이터셋을 조인 가능하게 만들기 때문입니다. MPP 데이터베이스가 요구하는 세심한 스키마 설계는 중앙 집중식 데이터 수집을 느리게 만듭니다. 원시 데이터를 수집하고 스키마 설계는 나중에 고민하면 데이터 수집의 속도가 올라갑니다(데이터 호수 또는 엔터프라이즈 데이터 허브라고 알려진 개념).

제약 없는 데이터 덤핑은 데이터를 해석하는 부담을 이전시킵니다. 데이터셋 생산자에게 데이터셋을 표준 형식으로 바꾸게끔 강제하는 대신 데이터 해석은 소비자가 해결할 문제가 됩니다(스키마 온 리드 접근법). 생산자와 소비자가 서로 다른 우선순위를 가진 다른 팀에 있다면 이것은 이점이 있습니다. 하나의 이상적인 데이터 모델은 존재하지 않을지 몰라도 데이터에는 여러 목적에 적합한 다양한 관점이 존재합니다. 원시 상태로 데이터를 덤핑하는 것만으로도 이런 여러 변환이 가능합니다. 이 접근법을 초밥 원리라 부릅니다. 원시 데이터가 더 좋다는 뜻입니다.

따라서 하둡은 ETL 프로세스를 구현하는 데 종종 사용되기도 합니다. 트랜잭션 처리 시스템에서 데이터를 원시 형태로 분산 파일 시스템에 덤프합니다. 그다음 맵리듀스 작업은 데이터를 정리하고 관계형으로 변환한 후 데이터 분석을 위해 MPP 데이터 웨어하우스로 옮깁니다. 여전히 데이터 모델링도 하지만 데이터 수집과는 분리된 단계입니다. 이런 디커플링은 분산 파일 시스템이 어떤 형식으로 부호화된 데이터든지 지원하기 때문에 가능합니다.

#### 6.2 처리 모델의 다양성

MPP 데이터베이스는 일체식 구조로서 디스크 저장소 레이아웃과 질의의 계획, 스케줄링과 실행을 다루는 소프트웨어 조각들이 긴밀하게 통합됩니다. 이 구성 요소들은 데이터베이스의 특정한 필요에 따라 튜닝하거나 최적화하기 때문에 전체 시스템은 설계된 질의의 유형에 대해서는 매우 좋은 성능을 얻을 수 있습니다. 게다가 SQL 질의 언어를 사용하면 코드를 작성하지 않고도 풍부한 질의의 표현과 우아한 시맨틱을 허용하므로 타블로 같은 비즈니스 분석가용 그래픽 도구에 SQL 질의 언어로 접근이 가능합니다.

반면 SQL 질의로 모든 종류의 처리를 표현하지는 못합니다. 예를 들어 머신러닝이나 추천 시스템, 또는 관련성 랭킹 모델을 탑재한 전문 검색 색인을 구축하거나 이미지 분석을 한다면 더 범용적인 데이터 처리 모델이 필요합니다. 이런 처리는 특정 애플리케이션(이를테면 기계 학습에 사용하는 특징 엔지니어링, 기계 번역에서 사용하는 자연어 모델, 사기 행위 예측용 위험 예측 기능 등)에 한정되는 경우가 많아서 단순한 질의 작성이 아닌 코드 작성이 반드시 필요합니다.

맵리듀스를 이용하면 엔지니어는 자신이 작성한 코드를 대용량 데이터셋 상에서 쉽게 실행할 수 있습니다. HDFS와 맵리듀스가 있으면 그 위에 SQL 질의의 실행 엔진을 구축할 수 있는데 하이브 프로젝트가 바로 그런 역할을 합니다. 물론 SQL 질의로 표현하기 어려운 다양한 일괄 처리 형태도 직접 작성할 수 있습니다.

시간이 흘러 사람들은 맵리듀스가 너무 제한적이고 어떤 형태의 처리에서는 성능도 나쁘다는 점을 깨달았습니다. 그래서 하둡 위에서 다른 다양한 처리 모델이 개발됐습니다. SQL과 맵리듀스 두 가지 처리 모델만으로는 충분하지 않았습니다. 더 많은 모델이 필요했습니다. 하둡 플랫폼의 개방성 때문에 일체식 MPP 데이터베이스에서는 불가능했던 모든 범위의 접근법을 구현할 수 있었습니다.

결정적으로 이런 다양한 처리 모델은 모두 단일 공유 클러스터 장비에서 실행되고 분산 파일 시스템 상에 존재하는 동일한 파일들에 접근 가능합니다. 하둡 접근법에서는 다른 종류의 처리를 하기 위해 여러 다른 특정 시스템으로 데이터를 보낼 필요가 없습니다. 하둡 시스템은 동일한 클러스터 내에서 다양한 작업부하를 함께 지원할 수 있을 정도로 충분히 유연합니다. 데이터를 옮길 필요가 없기 때문에 데이터로부터 가치를 끌어내기 쉽고 새로운 처리 모델을 사용한 실험도 훨씬 쉽습니다.

하둡 생태계는 HBase 같은 임의 접근 가능한 OLTP 데이터베이스와 임팔라 같은 MPP 스타일의 분석 데이터베이스를 포함합니다. HBase와 임팔라는 맵리듀스를 사용하지는 않지만 둘 다 HDFS를 저장소로 사용합니다. HBase와 임팔라는 데이터에 접근하고 처리하는 데 매우 다른 접근법을 사용함에도 공존할 수 있고 같은 시스템으로 통합할 수도 있습니다.

#### 6.3 빈번하게 발생하는 결함을 줄이는 설계

맵리듀스와 MPP 데이터베이스를 비교할 때 설계 방식에서 큰 차이점 두 가지가 두드러집니다. 결함을 다루는 방식과, 메모리 및 디스크를 사용하는 방식이 그 두 가지입니다.

일괄 처리는 온라인 시스템에 비해 결함에 덜 민감합니다. 일괄 처리 작업이 실패하더라도 즉시 사용자에게 영향을 주지 않으면서 언제든지 다시 실행할 수 있기 때문입니다.

질의 실행 중에 한 장비만 죽어도 MPP 데이터베이스 대부분은 전체 질의가 중단됩니다. 그러면 사용자가 질의를 다시 제출하든지 아니면 자동으로 재실행하게 해야 합니다. 일반적인 질의는 수 초에서 수 분 내로 대부분 수행이 끝나기 때문에 이런 방식으로 오류를 다루는 방식은 재시도 비용이 크지 않아 수용 가능합니다. MPP 데이터베이스는 또한 디스크에서 데이터를 읽는 비용을 피하기 위해 해시 조인 같은 방식을 사용해 가능하면 메모리에 많은 데이터를 유지하는 것을 선호합니다.

하지만 맵리듀스는 맵 또는 리듀스 태스크의 실패를 견딜 수 있습니다. 개별 태스크 수준에서 작업을 재수행하기 때문에 전체 작업으로 보면 영향을 받지 않습니다. 또한 맵리듀스는 데이터를 되도록 디스크에 기록하려 합니다. 한편으로는 내결함성을 확보하기 위함이고 다른 한편으로는 메모리에 올리기에는 데이터셋이 너무 크다는 가정 때문입니다.

맵리듀스 접근법은 대용량 작업에 더 적합합니다. 많은 데이터를 처리하고 오랜 시간 수행하는 작업이라면 그 사이에 최소한 태스크 하나는 실패할 가능성이 높습니다. 이 경우 태스크 하나가 실패했다고 작업 전체를 재수행하는 일은 분명 낭비입니다. 개별 태스크 수준에서 복구를 하려면 결함이 없는 처리는 느려지는 오버헤드가 생기지만 태스크 실패율이 상당히 높다면 해볼 만한 시도입니다.

하지만 이런 가정이 얼마나 현실적일까요. 대부분의 클러스터에서 장비 장애는 항상 발생하지만 그렇다고 그렇게 자주 발생하지는 않습니다. 아마도 대부분의 작업은 장비 장애를 겪지 않을 정도로 드물 것입니다. 내결함성을 확보하기 위해 상당한 오버헤드를 감당하는 게 실제로 가치가 있을까요.

맵리듀스가 메모리를 아껴 쓰고 태스크 수준에서 복구하는 이유를 이해하려면 원래 맵리듀스를 설계한 환경을 살펴보면 도움이 됩니다. 구글은 혼합 사용 데이터 센터를 소유하고 있습니다. 이곳에서는 온라인 프러덕션 서비스와 오프라인 일괄 처리 작업이 같은 장비에서 실행됩니다. 각 태스크는 컨테이너를 사용해 CPU 코어, RAM, 디스크 공간 등의 자원을 할당받습니다. 모든 태스크에는 우선순위가 있습니다. 우선순위가 높은 태스크에 더 많은 자원이 필요하다면 자원 확보를 위해 같은 장비에서 수행되던 우선순위가 낮은 태스크를 종료(선점)할 수도 있습니다. 또한 우선순위는 연산 자원의 가격을 결정합니다. 자원을 사용하는 팀은 팀이 사용한 자원에 대한 비용을 지불해야 하고 우선순위가 높은 처리일수록 비용도 더 듭니다.

이 아키텍처를 사용하면 비프러덕션(낮은 우선순위) 연산 자원을 초과 할당할 수 있습니다. 자원이 필요하면 회수할 수 있다는 점을 시스템이 알고 있기 때문입니다. 추가 자원 할당은 프러덕션과 비프러덕션을 분리하는 시스템과 비교했을 때 장비 가동률이 높고 효율성도 매우 좋습니다. 그러나 맵리듀스 작업이 낮은 우선순위로 실행될 때 우선순위가 상대적으로 높은 작업이 자원을 요청한다면 언제라도 선점 당할 위험이 있습니다. 일괄 처리 작업은 사실상 식탁 아래에서 조각들을 모읍니다. 우선순위가 높은 프로세스가 필요한 작업을 수행한 뒤 남은 자원을 사용해 연산을 수행합니다.

구글에서 어떤 맵리듀스 태스크가 한 시간 정도 수행된다면 높은 우선순위의 프로세스를 위한 공간을 마련해주기 위해 태스크가 종료될 위험이 약 5퍼센트로, 하드웨어 문제나 장비 재시작 등 다른 이유로 실패할 확률보다 상당히 높습니다. 작업이 5퍼센트 선점 확률로 10분간 수행하는 100개의 태스크를 가지고 있다면 작업이 완료되기 전에 적어도 태스크 하나가 종료될 가능성이 50퍼센트를 넘습니다.

이런 이유로 맵리듀스는 태스크 종료가 예상치 못하게 자주 발생하더라도 견딜 수 있게 설계됐습니다. 즉 하드웨어를 신뢰할 수 없기 때문이 아니라 프로세스를 임의로 종료할 수 있으면 연산 클러스터에서 자원 활용도를 높일 수 있기 때문입니다.

오픈소스 클러스터 스케줄러는 선점 방식을 많이 사용하지는 않습니다. YARN에서 사용하는 캐퍼시티 스케줄러는 다른 큐 간 자원을 할당할 때 균형을 유지하기 위해 선점 방식을 지원하지만, 일반적인 우선순위 선점 방식은 YARN, 메소스, 쿠버네티스를 작성할 당시에는 지원하지 않았습니다. 태스크가 그렇게 자주 종료되지 않는 환경이라면 맵리듀스를 이런 식으로 설계한 점은 선뜻 이해하기 어렵습니다.

### 7. 맵리듀스를 넘어

2000년대 후반 맵리듀스는 매우 인기를 끌었고 그런 인기로 인해 과대 포장된 면이 있었습니다. 하지만 맵리듀스는 분산 시스템에서 가능한 여러 프로그래밍 모델 중 단지 하나일 뿐입니다. 데이터 양에 따라, 자료 구조에 따라, 또는 데이터를 처리하는 방식에 따라 다른 도구가 연산을 표현하는 데 더 적합할지도 모릅니다.

그럼에도 이번 장에서는 맵리듀스에 대해 논의하는 데 시간을 많이 쏟았습니다. 맵리듀스는 학습하기가 매우 유용한 도구로서 분산 파일 시스템 상에서 상당히 단순 명료하게 추상화된 모델이기 때문입니다. 즉 여기서 말하는 단순함은 사용하기 쉽다는 의미가 아니라 무엇을 하고 있는지 이해하기 쉽다는 뜻입니다. 정반대로 맵리듀스 원시 API를 사용해서 복잡한 연산을 구현하는 일은 실제로 매우 어렵고 수고가 많이 들어갑니다. 이를테면 조인 알고리즘을 하나 작성한다고 해도 처음부터 모두 구현해야 합니다.

맵리듀스를 직접 사용하는 일은 어렵기 때문에 맵리듀스 상에서 추상화한 다양한 고수준 프로그래밍 모델(피그, 하이브, 캐스캐이딩, 크런치)이 등장했습니다. 이런 고수준 프로그래밍 모델은 맵리듀스가 어떻게 동작하는지 이해하고 있으면 확실히 배우기 쉬울 뿐 아니라 일반적인 일괄 처리 태스크를 구현하기에 상당히 편합니다.

그러나 맵리듀스 실행 모델 자체에도 문제가 있으며 이는 추상화 단계를 올린다고 해결되지 않고 일부 유형의 처리에 대해서는 성능 저하를 유발하기도 합니다. 반면 맵리듀스는 매우 견고합니다. 태스크가 자주 종료돼 신뢰할 수 없는 멀티 테넌트 시스템에서도 대규모 데이터를 처리하기 위해 맵리듀스를 사용할 수 있고, 그 작업은 느릴지언정 성공합니다. 반면 특정 유형의 처리는 다른 도구들이 훨씬 빠를 때도 있습니다.

#### 7.1 중간 상태 구체화

앞서 설명한 것과 같이 모든 맵리듀스 작업은 다른 작업과 모두 독립적입니다. 작업이 외부 세계와 만나는 주요 접점은 분산 파일 시스템 상의 입력과 출력 디렉터리입니다. 첫 번째 작업의 출력을 두 번째 작업의 입력으로 사용하려면 두 번째 작업의 입력 디렉터리를 첫 번째 작업의 출력 디렉터리와 같게 설정해야 합니다. 그리고 외부 워크플로 스케줄러에서 반드시 첫 번째 작업을 완료한 후에 두 번째 작업을 수행해야 합니다.

첫 번째 작업의 출력이 조직 내에 널리 공개하는 데이터셋이라면 이런 설정은 합리적입니다. 이 경우 이름으로 참조가 가능해서 다른 여러 작업에서 입력으로 재사용이 가능해야 합니다(다른 팀에서 개발한 작업을 포함해서). 분산 파일 시스템 내 잘 알려진 위치에 데이터를 올리면 작업 간 연결이 느슨해 어떤 작업이 입력을 생성하고 출력을 생산하는지 알 필요가 없습니다.

그러나 대개 한 작업의 출력은 같은 팀 내에서 유지보수하는 다른 특정 작업의 입력으로만 사용됩니다. 이 경우에 분산 파일 시스템 상에 있는 파일들은 단순히 한 작업에서 다른 작업으로 데이터를 옮기는 수단, 즉 중간 상태입니다. 추천 시스템을 구축할 때 사용하는 복잡한 워크플로는 맵리듀스 작업이 50개에서 100개로 구성되는데 여기에는 많은 중간 상태가 존재합니다.

중간 상태를 파일로 기록하는 과정을 구체화라 합니다. 구체화는 요청이 왔을 때 계산을 시작하는 것이 아니라 미리 특정 연산 결과를 만들어 둔다는 의미입니다.

반대로 이번 장 초반부에 나온 로그 분석 예제는 한 명령의 출력을 다른 명령의 입력으로 연결하기 위해 유닉스 파이프를 사용했습니다. 파이프는 중간 상태를 완전히 구체화하는 대신 작은 인메모리 버퍼만을 사용해 점진적으로 출력을 입력으로 스트리밍합니다.

중간 상태를 완전히 구체화하는 맵리듀스 접근법은 유닉스 파이프에 비해 여러 단점이 있습니다.

- 맵리듀스 작업은 입력을 생성하는 모든 선행 작업이 완료됐을 때만 시작 가능합니다. 반면 유닉스 파이프로 연결된 프로세스들은 동시에 시작되고 출력은 생산되는 즉시 소비됩니다. 장비들 사이에 부하가 한 쪽으로 쏠리거나 변한다면 작업에는 다른 태스크보다 완료할 때까지 시간이 훨씬 긴 뒤처진 태스크가 있게 마련입니다. 모든 선행 작업 태스크가 종료될 때까지 기다리면 워크플로 전체 수행 시간은 느려집니다.
- 매퍼는 종종 중복되기도 합니다. 이 매퍼들은 리듀서에서 막 기록된 동일한 파일을 읽어서 다음 단계인 파티셔닝과 정렬 단계를 준비합니다. 대부분 매퍼 코드는 이전 리듀서의 일부가 될 수 있습니다. 리듀서의 출력을 매퍼 출력과 같은 방식으로 파티셔닝하고 정렬한다면 매퍼 단계를 끼워넣지 않고 리듀서끼리 직접 연결할 수 있습니다.
- 분산 파일 시스템에서 중간 상태를 저장하는 것은 중간 상태 파일들이 여러 장비에 걸쳐 복제됐다는 의미로서, 이런 임시 데이터에게는 과잉조치입니다.

#### 7.2 데이터플로 엔진

맵리듀스에 있는 이러한 문제를 해결하기 위해 분산 일괄 처리 연산을 수행하는 엔진이 새롭게 몇 가지 개발됐습니다. 그 가운데 스파크와 테즈, 플링크가 널리 알려진 엔진입니다. 설계 방식에는 많은 차이가 있지만 이 엔진들은 공통점 하나가 있습니다. 전체 워크플로를 독립된 하위 작업으로 나누지 않고 작업 하나로서 다룬다는 점입니다.

이 엔진들은 여러 처리 단계를 통해 데이터 흐름을 명시적으로 모델링하기 때문에 이 시스템을 데이터플로 엔진이라고 부릅니다. 데이터플로 엔진은 맵리듀스처럼 단일 스레드에서 사용자 정의 함수를 반복 호출해 한번에 레코드 한 개씩 처리합니다. 데이터플로 엔진은 입력을 파티셔닝해 병렬화합니다. 그리고 한 함수의 출력을 다른 함수의 입력으로 사용하기 위해 네트워크를 통해 복사합니다.

맵리듀스와 달리 이 함수들은 맵과 리듀스를 번갈아 수행하는 식의 규칙을 엄격하게 지킬 필요가 없습니다. 대신 더 유연한 방법으로 함수들을 조합할 수 있습니다. 이런 함수를 연산자라고 부르고, 데이터플로 엔진은 연산자의 출력과 다른 연산자의 입력을 연결하는 여러 가지 선택지를 제공합니다.

- 한 가지 선택지는 레코드를 키로 재파티셔닝하고 정렬하는 것으로 맵리듀스의 셔플 단계와 비슷합니다. 이 기능을 사용하면 맵리듀스에서와 같은 방식으로 정렬 병합 조인과 그룹화를 수행할 수 있습니다.
- 여러 입력을 가져와 파티셔닝하는 점은 동일하지만 이때 정렬을 건너뛰는 선택지도 있습니다. 이를 이용하면 파티션 해시 조인에서 수행하는 일을 덜 수 있습니다. 파티션 해시 조인에서 레코드를 파티셔닝하는 일은 중요하지만 해시 테이블을 사용하면 순서가 어차피 무작위로 부여되기 때문에 순서 자체가 무의미합니다.
- 브로드캐스트 해시 조인을 사용한다면 한 연산자의 출력을 조인 연산자의 모든 파티션으로 보낼 수 있습니다.

이런 스타일의 처리 엔진은 드라이어드와 네펠레 같은 연구용 시스템에 기초를 두고 있는데 맵리듀스 모델과 비교했을 때 몇 가지 장점이 있습니다.

- 정렬과 같은 값비싼 작업은 실제로 필요할 때만 수행합니다. 반면 맵리듀스 모델은 기본적으로 모든 맵과 리듀스 사이에서 정렬 작업이 항상 발생합니다.
- 필요없는 맵 태스크는 없습니다. 매퍼가 수행한 작업은 종종 선행 리듀스 연산자로 통합될 수 있기 때문입니다(매퍼는 데이터셋의 파티셔닝을 변경하지 않으므로 가능합니다).
- 워크플로에 모든 조인과 데이터 의존 관계를 명시적으로 선언하기 때문에 스케줄러가 어느 데이터가 어디에 필요한지에 대한 개요를 가져서 지역성 최적화가 가능합니다. 예를 들면 어떤 데이터를 소비하는 태스크를 그 데이터를 생산하는 태스크와 같은 장비에 배치할 수 있습니다. 그러면 네트워크 상에서 데이터를 복사하지 않고 공유 메모리 버퍼를 통해 데이터를 교환할 수 있습니다.
- 연산자 간 중간 상태는 대개 메모리나 로컬 디스크에 기록하는 것으로 충분한데 HDFS에 중간 상태를 기록할 때보다 I/O가 훨씬 적게 듭니다. 맵리듀스는 매퍼 출력에 대해 항상 이런 최적화를 사용하지만 데이터플로 엔진은 이 아이디어를 모든 중간 상태로 일반화합니다.
- 연산자들은 입력이 준비되는 즉시 실행을 시작할 수 있습니다. 다음 단계를 시작하기 위해 선행 단계 전체가 끝나기를 기다릴 필요가 없습니다.
- 새로운 연산자를 실행할 때 이미 존재하는 자바 가상 머신(JVM)을 재활용할 수 있어 각 태스크마다 새로운 JVM을 구동하는 맵리듀스에 비해 시작 부담이 적습니다.

맵리듀스 워크플로와 동일한 연산을 데이터플로 엔진을 사용해 구현할 수 있습니다. 게다가 일반적으로 앞서 설명한 최적화로 인해 수행 속도가 훨씬 빠릅니다. 연산자는 맵과 리듀스를 일반화한 것이기 때문에 피그와 하이브, 캐스캐이딩으로 구현된 워크플로를 코드 수정 없이 간단한 설정 변경만으로 맵리듀스에서 테즈나 스파크로 전환할 수 있습니다.

테즈는 노드 간에 데이터를 실제로 복사하는 데 YARN 셔플 서비스에 의존하는 상당히 가벼운 라이브러리입니다. 반면 스파크와 플링크는 자체 네트워크 통신 계층과 스케줄러 그리고 사용자 측 API를 갖춘 대형 프레임워크입니다.

#### 7.3 내결함성(데이터플로 엔진)

분산 파일 시스템에 중간 상태를 모두 구체화할 때 생기는 이점은 내구성입니다. 맵리듀스는 중간 상태를 모두 구체화하기 때문에 쉽게 내결함성을 확보합니다. 태스크가 실패하더라도 다른 장비에서 태스크를 재실행할 수 있고 파일 시스템으로부터 동일한 입력을 다시 읽을 수 있습니다.

스파크와 플링크, 테즈는 HDFS에 중간 상태를 쓰지 않기 때문에 내결함성 확보를 위해 다른 접근법을 사용합니다. 장비가 죽어서 장비에 있던 중간 상태까지 잃게 되면 아직 유효한 데이터로부터 계산을 다시 해서 복구합니다(가능하다면 선행 중간 단계를 사용하고 그렇지 않다면 HDFS 상에 있는 원본 데이터를 사용합니다).

재계산이 가능하려면 프레임워크에서 주어진 데이터가 어떻게 연산되는지 추적해야 합니다. 어느 입력 파티션을 사용했는지와 어떤 연산자를 적용했는지도 추적해야 합니다. 스파크는 데이터의 조상을 추적하기 위해 RDD(resilient distributed dataset) 추상화를 사용합니다. 플링크는 연산자 상태를 체크포인트로 남겨 작업 실행 중 실패한 연산자 수행을 재개할 수 있습니다.

데이터를 재연산할 때 중요한 점은 해당 연산이 결정적인지 아닌지 파악하는 것입니다. 즉 동일한 입력 데이터가 주어졌을 때 연산자들이 항상 같은 출력을 생산할까요. 이미 다운스트림으로 보낸 데이터 중 일부를 잃어버렸다면 이 질문은 매우 중요합니다. 연산자를 재시작해서 재연산된 데이터가 잃어버린 원본 데이터와 같지 않다면 다운스트림 연산자가 이전 데이터와 새로운 데이터 간의 모순을 해결하기는 너무 어렵습니다. 연산자가 비결정적인 경우 해결책은 다운스트림 연산자도 죽이고 신규 데이터를 기준으로 다시 수행하는 방법이 일반적입니다.

이처럼 아래로 전파되는 결함을 피하려면 연산자를 결정적으로 만드는 것이 좋습니다. 그러나 우연히 비결정적 동작이 생기기 쉽다는 점을 주의해야 합니다. 예를 들면 많은 프로그래밍 언어는 해시 테이블의 원소를 탐색할 때 특정 순서를 보장하지 않습니다. 그리고 많은 확률 통계 알고리즘이 임의로 생성한 숫자에 명시적으로 의존합니다. 또한 시스템 시계나 외부 데이터 출처를 쓰는 것도 비결정적입니다. 결함으로부터 신뢰성 있게 회복하기 위해서는 비결정적 원인을 제거해야 합니다. 이를테면 고정된 시드를 사용해 의사 난수를 생성하는 방법이 있습니다.

결함에서 복구할 때 데이터를 재연산하는 방식이 항상 정답은 아닙니다. 중간 데이터가 원천 데이터보다 훨씬 작거나 연산이 CPU 중심적이라면 재연산보다 중간 데이터를 파일로 구체화하는 방식이 더 효과적입니다.

#### 7.4 구체화에 대한 논의

다시 유닉스에 비유하자면 맵리듀스는 각 명령의 출력을 임시 파일에 기록하는 것과 유사한 반면 데이터플로 엔진은 유닉스 파이프와 매우 비슷합니다. 특히 플링크는 파이프라인 실행 개념을 기초로 합니다. 즉 연산자의 출력을 다른 연산자로 점진적으로 전달하고 입력을 처리하기 전에 입력이 완료될 때까지 기다리지 않습니다.

정렬 연산자는 출력을 생산하기 전에 전체 입력을 소비해야 합니다. 맨 마지막 입력 레코드가 가장 낮은 키를 가져서 첫 번째 출력 레코드가 돼야 할 수도 있기 때문입니다. 따라서 정렬이 필요한 연산자는 적어도 일시적이라도 상태를 누적할 필요가 있습니다. 그러나 워크플로의 여러 다른 부분은 파이프라인 방식으로 실행이 가능합니다.

작업을 완료하면 출력을 다른 사용자가 찾아 사용할 수 있게 지속성 있는 어딘가로 보내야 합니다. 대개 출력을 분산 파일 시스템에 다시 기록합니다. 따라서 데이터플로 엔진을 사용할 때 HDFS 상에 구체화된 데이터셋은 보통 작업의 입력과 최종 출력입니다. 입력은 불변이고 최종 출력을 완전히 교체하는 방식은 맵리듀스와 비슷합니다. 맵리듀스보다 개선된 점은 사용자가 직접 모든 중간 상태를 파일 시스템에 기록하는 수고를 덜어준다는 점입니다.

### 8. 그래프와 반복 처리

그래프를 사용해 데이터 모델링을 하고 그래프 질의 언어를 사용해 그래프의 간선과 정점을 순회하는 방법을 앞서 다뤘습니다. 이전에는 OLTP 스타일에 초점을 두고, 특정 기준을 만족하는 적은 수의 정점을 찾기 위해 질의를 빠르게 실행하는 방법을 설명했습니다. 전체 그래프에서 오프라인으로 처리를 수행하거나 분석을 하는 등 일괄 처리 맥락에서 그래프를 살펴보는 것도 흥미롭습니다. 추천 엔진 같은 머신러닝이나 랭킹 시스템 분야에서도 그래프 처리의 필요성이 떠오르고 있습니다. 예를 들면 가장 유명한 그래프 분석 알고리즘 중 하나인 페이지랭크를 들 수 있습니다. 페이지랭크는 웹 페이지를 링크하는 다른 웹 페이지를 기반으로 인기도를 측정하는 알고리즘입니다. 페이지랭크는 웹 검색 엔진에서 검색 결과를 나타낼 때 사용하는 순서를 결정하는 방법 중 하나로 사용됩니다.

참고로, 스파크와 플링크, 테즈 같은 데이터플로 엔진에서 작업에 있는 연산자를 비순환 방향 그래프(DAG)로 배열합니다. 이것은 그래프 처리와 다릅니다. 데이터플로 엔진에서는 데이터 자체가 전형적으로 관계형 튜플의 형태로 구성된 채 한 연산자로부터 다른 연산자로 가는 데이터 흐름이 그래프로 구성됩니다. 그래프 처리에서는 데이터 자체가 그래프 형식입니다. 이름을 잘못 지어 혼란을 초래합니다.

많은 그래프 알고리즘이 한 번에 하나의 간선을 순회하는 방식으로 표현되는데, 특정 정보를 전파하기 위해 정점 하나와 인접한 정점을 조인하면서 특정 조건(예를 들면 따라갈 간선이 없어질 때까지 또는 특정 지표가 수렴할 때까지)에 도달할 때까지 반복합니다. 어떤 지역이 어느 다른 지역 내에 속하는지 가리키는 간선을 반복적으로 따라가는 방식으로 데이터베이스에 포함된 북미 지역의 모든 위치 목록을 만드는 예제를 살펴본 적이 있습니다. 이런 알고리즘을 이행적 폐쇄라 합니다.

그래프는 분산 파일 시스템에 정점과 간선 목록이 포함된 파일의 형태로 저장할 수 있습니다. 하지만 완료할 때까지 반복이라는 개념은 일반적인 맵리듀스로는 표현할 수 없습니다. 맵리듀스는 데이터를 일회성으로만 처리하기 때문입니다. 따라서 이런 알고리즘은 대개 반복적 스타일로 구현됩니다.

1. 외부 스케줄러가 이 알고리즘의 한 단계를 연산하기 위해 일괄 처리를 수행한다.
2. 해당 일괄 처리가 완료되면 스케줄러는 종료 조건(예를 들면 따라갈 간선이 더 이상 없는지, 이전 반복과 비교해서 변화가 어떤 기준점 이하인지)을 기반으로 완료됐는지 확인한다.
3. 아직 끝나지 않았다면 스케줄러는 1단계로 돌아가서 다음 일괄 처리를 수행한다.

이 접근법을 맵리듀스로 구현해도 동작하지만 상당히 비효율적입니다. 맵리듀스는 알고리즘의 반복적 속성을 고려하지 않기 때문입니다. 맵리듀스는 항상 전체 입력 데이터셋을 읽어서 완전히 새로운 출력 데이터셋을 생산합니다. 이전 반복과 비교해 그래프의 일부만 변경됐더라도 동일한 수행을 합니다.

#### 8.1 프리글 처리 모델

일괄 처리 그래프를 최적화하는 방법으로 벌크 동기식 병렬(BSP) 연산 모델이 널리 사용됩니다. 그중에서도 아파치 지라프, 스파크 그래프X API, 플링크 젤리 API 등이 유명한 BSP 구현체입니다. 또한 BSP는 프리글 모델로 불립니다. 프리글 모델은 구글의 프리글 논문에서 그래프 처리 방법론으로 소개돼 널리 보급됐습니다.

맵리듀스에서는 개념적으로 매퍼가 특정 리듀서를 호출해 메시지를 전달합니다. 맵리듀스 프레임워크가 매퍼의 출력을 동일한 키를 기준으로 수집하기 때문입니다. 프리글에도 이 같은 개념이 있습니다. 한 정점은 다른 정점으로 메시지를 보낼 수 있습니다. 이 메시지는 대개 그래프에서 간선을 따라 보내집니다.

반복할 때마다 개별 정점에서 함수를 호출해 그 정점으로 보내진 모든 메시지를 전달하는데 리듀서를 호출하는 방식과 비슷합니다. 맵리듀스와 프리글 모델의 차이점은 정점은 반복에서 사용한 메모리 상태를 기억하고 있다는 점입니다. 그래서 정점은 새로 들어오는 메시지만 처리하면 됩니다. 아무 메시지도 받지 않는 그래프 부분은 아무 일도 하지 않습니다.

프리글 모델은 액터 모델과 살짝 비슷합니다. 각 정점을 액터로 본다면 정점 상태를 제외하고 정점 사이의 메시지는 내결함성과 지속성이 있습니다. 메시지 통신은 고정된 횟수 안에 처리됩니다. 각 반복에서 이 프레임워크는 이전 반복에서 보내진 모든 메시지를 전달합니다. 액터 모델은 그런 타이밍 보장을 하지 않습니다.

#### 8.2 내결함성

정점이 서로 직접 질의하는 방식이 아니라 메시지 전달로 통신한다는 점은 프리글 작업 성능 향상에 도움을 줍니다. 메시지는 일괄 처리가 가능해 통신 중 대기 시간이 발생하지 않기 때문입니다. 대기 시간은 반복과 다음 반복 사이에서만 발생합니다. 프리글 모델은 앞선 반복에서 보낸 모든 메시지는 다음 반복에 도착됨을 보장하기 때문에 다음 반복을 시작하기 전에 앞선 반복은 반드시 끝나야 하고 모든 메시지는 네트워크 상에서 복사돼야 합니다.

네트워크 상의 문제로 메시지가 사라지거나 중복되거나 지연되더라도 프리글 구현상 다음 반복에서 메시지는 목적지 정점에서 정확히 한 번만 처리됩니다. 맵리듀스와 마찬가지로 프리글 상에서 알고리즘을 구현하기 위한 프로그래밍 모델을 단순화하기 위해 프리글 프레임워크 차원에서 완벽히 결함을 복구합니다.

이런 내결함성은 반복이 끝나는 시점에 모든 정점의 상태를 주기적으로 체크포인트로 저장함으로써 보장됩니다. 즉 전체 상태를 지속성 있는 저장소에 기록합니다. 노드에 장애가 나서 인메모리 상태가 손실됐을 때 가장 간단한 해결책은 전체 그래프 연산을 마지막 체크포인트로 되돌리고 연산을 재시작하는 것입니다. 알고리즘이 결정적이고 메시지가 로그로 남는다면 손실된 파티션만 선택해서 복구할 수도 있습니다(앞에서 데이터플로 엔진을 설명했을 때처럼).

#### 8.3 병렬 실행

정점은 어떤 물리 장비에서 실행되는지 알 필요가 없기 때문에 메시지를 다른 정점으로 보낼 때 단순히 정점 ID를 사용해 메시지를 전달합니다. 그래프를 파티셔닝하는 일은 프리글 프레임워크가 담당합니다. 즉 정점을 어떤 장비에서 실행할지와 올바른 장소로 메시지를 보내기 위해 네트워크 상에서 어떻게 라우팅할지를 결정하는 일을 담당합니다.

프로그래밍 모델은 한 번에 정점 한 개를 다루기 때문에(때론 정점과 같이 생각하기라고 부릅니다) 프리글 프레임워크가 임의의 방법으로 그래프를 파티셔닝할 수 있습니다. 이상적으로는 빈번하게 통신하는 정점끼리는 같은 장비에 위치하는 식으로 파티셔닝하는 게 좋습니다. 그러나 그렇게 최적화해서 분할하는 것이 어렵기 때문에 실제로는 단순히 임의로 부여된 정점 ID를 기준으로 단순하게 분할하고 관련성이 높은 정점끼리 그룹화하지는 않습니다.

결과적으로 그래프 알고리즘은 장비 간 통신 오버헤드가 많이 발생합니다. 원본 그래프보다 중간 상태(노드 간 전송된 메시지)가 더 클 수도 있습니다. 네트워크 상에서 메시지를 보내는 오버헤드 때문에 분산 그래프 알고리즘이 심각하게 느려질 수도 있습니다.

이런 이유로 그래프가 단일 컴퓨터 메모리에 넣을 수 있는 크기라면 단일 장비 알고리즘이 분산 일괄 처리보다(심지어 단일 스레드를 사용할지라도) 훨씬 성능이 좋을 가능성이 높습니다. 그래프가 메모리보다는 크지만 단일 컴퓨터의 디스크에 넣을 수 있는 크기라면 그래프치(GraphChi) 같은 단일 장비 그래프 처리 프레임워크를 사용하는 것도 쓸만한 방법입니다. 그래프가 단일 장비에 넣기에 너무 크다면 프리글 같은 분산 접근법을 꼭 사용해야 합니다. 효율적인 병렬 그래프 알고리즘은 지금도 연구가 진행 중인 분야입니다.

#### 8.4 고수준 API와 언어

맵리듀스가 유명해진 지 수 년이 흐르자 분산 일괄 처리용 수행 엔진도 성숙해졌습니다. 이제 인프라는 10,000대가 넘는 장비로 구성된 클러스터 상에서 페타바이트급 데이터를 충분히 저장하고 처리할 정도로 견고해졌습니다. 물리적으로는 이런 규모로 일괄 처리를 운영하는 문제가 거의 해결됐기 때문에 프로그램 모델을 개선하고 처리 효율을 높이고 이 기술로 해결할 수 있는 문제 범위를 확장하는 등 다른 분야에 더 집중할 수 있게 됐습니다.

이전 설명처럼 직접 맵리듀스 작업을 작성하는 일은 상당히 어렵기 때문에 하이브, 피그, 캐스캐이딩과 크런치 같은 고수준 언어나 API가 인기를 끌었습니다. 게다가 테즈가 등장하면서 고수준 언어를 사용하면 작업 코드를 새로 작성하지 않고도 맵리듀스 엔진에서 새로운 데이터플로로 옮겨갈 수 있는 이점도 있습니다. 스파크와 플링크 또한 자체 고수준 데이터플로 API를 가지고 있습니다. 두 언어는 플룸자바에서 영감을 얻었습니다.

이런 데이터플로 API는 일반적으로 관계형 스타일의 빌딩 블록을 사용해 연산을 표현합니다. 예를 들어 특정 필드의 값을 기준으로 데이터셋을 조인하고 키로 튜플을 그룹화하고 특정 조건으로 필터하고 튜플을 세거나 더하거나 혹은 다른 연산을 해서 집계합니다. 내부적으로 이 연산들은 이번 장에서 앞서 설명한 다양한 조인과 그룹화 알고리즘을 사용해 구현됐습니다.

이런 고수준 인터페이스는 코드를 적게 작성해도 되는 명백한 이점뿐만 아니라 대화식 사용도 지원합니다. 즉 셸에서 분석 코드를 점진적으로 작성하고 코드가 어떻게 동작하는지 바로 확인할 수 있습니다. 이런 개발 스타일은 데이터셋을 조사하고 데이터셋을 처리하기 위해 여러 접근법을 실험해볼 때 매우 유용합니다. 이것은 앞서 설명했던 유닉스 철학을 떠올리게 합니다.

더욱이 고수준 인터페이스를 사용하면 사용자가 시스템을 생산성 높게 사용할 수 있을 뿐 아니라 장비 수준에서도 작업을 더욱 효율적으로 수행할 수 있습니다.

#### 8.5 선언형 질의 언어로 전환

조인을 수행하는 코드를 작성하는 방식에 비해 관계형 연산자로 조인을 나타내면 프레임워크가 조인 입력의 속성을 분석해 자동으로 앞서 기술한 조인 알고리즘 중에 어떤 방법이 적절한지 자동으로 결정할 수 있다는 장점이 있습니다. 하이브, 스파크, 플링크는 이런 식으로 작동하는 비용 기반의 질의 최적화기를 내장하고 있습니다. 질의 최적화기는 중간 상태를 최소화하기 위해 조인 순서를 바꾸기도 합니다.

어떤 조인 알고리즘을 선택하느냐에 따라 일괄 처리 작업의 성능이 크게 달라집니다. 이번 장에서 설명한 모든 다양한 조인 알고리즘을 모두 이해하고 기억할 필요는 없습니다. 선언적인 방법으로 조인을 지정하면 가능합니다. 애플리케이션에서 단순히 어떤 조인이 필요한지 명시하면 질의 최적화기가 최적의 수행 방법을 결정합니다.

하지만 어떤 면에서는 맵리듀스와 맵리듀스의 데이터플로 계승자들은 SQL의 완전한 선언형 질의 모델과는 많이 다릅니다. 맵리듀스는 함수 콜백 개념으로 각 레코드 또는 레코드 그룹을 입력으로 사용자 정의 함수(매퍼 또는 리듀서)를 호출합니다. 이 함수에는 출력을 결정하는 코드를 임의로 작성할 수 있습니다. 파싱, 자연어 분석, 이미지 분석, 수치 또는 통계 알고리즘 등을 수행하는 라이브러리는 대규모 생태계에 이미 존재하고, 이런 라이브러리를 그대로 활용할 수 있다는 점이 이 방법의 장점입니다.

코드를 임의로 실행할 수 있다는 점은 MPP 데이터베이스와 맵리듀스를 계승하는 일괄 처리 시스템을 오랜 세월 동안 구별해준 특성입니다. 데이터베이스가 사용자 정의 함수를 지원한다고 해도 사용하기에 부담스럽고, 대부분의 프로그래밍 언어에서 널리 사용하는 패키지 관리자 및 의존성 관리 시스템(자바용 메이븐, 자바스크립트용 npm, 루비의 Rubygem)과의 통합이 어렵습니다.

그러나 데이터플로 엔진도 조인 외에 좀 더 선언적인 기능을 통합하면 이점이 있습니다. 예를 들어 콜백 함수에 간단한 필터링 조건만 포함되거나 레코드의 특정 필드만 선택하는 경우에 모든 레코드를 대상으로 해당 함수를 호출하는 작업은 CPU 오버헤드가 심하게 발생합니다. 그런 간단한 필터링과 매핑 연산을 선언적 방법으로 표현한다면 질의의 최적화기가 칼럼 기반 저장 레이아웃을 이용해 디스크에서 필요한 칼럼만 읽을 수 있습니다. 또한 하이브와 스파크 데이터프레임, 임팔라는 벡터화 수행(딱 맞는 내부 루프에서 데이터를 반복해서 CPU 캐시가 잘되게 하거나 함수 호출을 피하는 방식)을 사용합니다. 스파크는 JVM 바이트코드를 생성하고 임팔라는 LLVM을 사용해 이런 내부 루프의 원시 코드를 생성합니다.

고수준 API에 선언적 측면을 포함하면서 실행 중에 이용할 수 있는 질의의 최적화기를 가진다면 일괄 처리 프레임워크는 MPP 데이터베이스와 한층 비슷해집니다(비교할 만한 성능도 냅니다). 동시에 일괄 처리 프레임워크는 임의의 코드를 실행하고 임의 형식의 데이터를 읽을 수 있는 확장성을 지녀 일괄 처리 프레임워크의 장점인 유연성은 그대로 유지합니다.

#### 8.6 다양한 분야를 지원하기 위한 전문화

임의 코드를 실행할 수 있는 확장성은 매우 유용하지만 표준화된 처리 패턴이 계속 나타나는 공통 사례 또한 많습니다. 그래서 재사용 가능한 공통 빌딩 블록을 구현하는 일은 가치가 있습니다. 전통적으로 MPP 데이터베이스는 비즈니스 정보 분석가와 비즈니스 보고서의 요구에 부합했습니다. 하지만 그것도 일괄 처리가 사용되는 많은 분야 중 하나일 뿐입니다.

중요성이 증가하고 있는 다른 분야로 통계학과 수치 알고리즘이 있습니다. 통계학과 수치 알고리즘은 분류, 추천 시스템과 같은 머신러닝 애플리케이션을 구축하는 데 필요합니다. 떠오르는 재사용 가능한 구현의 예로는 머하웃이 있습니다. 머하웃은 맵리듀스, 스파크, 플링크 상에서 실행되는 다양한 머신러닝용 알고리즘 구현을 가지고 있습니다. 반면 매드립은 관계형 MPP 데이터베이스(아파치 HAWQ) 내부에 이와 유사한 기능 구현이 있습니다.

또한 k 최근접 이웃 알고리즘 같은 공간 알고리즘도 유용합니다. k 최근접 이웃 알고리즘은 다차원 공간에 주어진 아이템과 근접한 아이템들을 찾는 일종의 유사도 검색 알고리즘입니다. 근사 검색은 유전자 분석 알고리즘에서도 중요하게 사용됩니다. 유전자 분석에는 동일하지는 않지만 비슷한 염기 서열을 찾는 작업이 필요합니다.

일괄 처리 엔진은 점차 광범위한 영역에서 필요한 알고리즘을 분산 수행하는 데 사용됩니다. 일괄 처리 시스템은 내장 기능과 고수준 선언적 연산자를 모두 가지고 있고 MPP 데이터베이스는 한층 프로그래밍이 가능하게끔 유연해졌기 때문에 이 둘은 더욱 비슷해 보이기 시작했습니다. 일괄 처리 시스템과 MPP 데이터베이스 모두 결국에는 데이터를 저장하고 처리하는 시스템이기 때문입니다.

### 9. 정리

이번 장에서는 일괄 처리에 대해 설명했습니다. awk, grep, sort 등의 유닉스 도구를 살펴보는 것을 시작으로 이 도구들의 설계 철학이 어떻게 맵리듀스와 최근에 개발된 데이터플로 엔진에 녹아 있는지 살펴봤습니다. 이 설계 원리 중 몇 가지를 뽑아보면 다음과 같습니다. 입력은 불변이고 출력은 다른(아직 알지 못하는) 프로그램의 입력으로 사용됩니다. 그리고 복잡한 문제도 한 가지 일을 잘하는 작은 도구를 엮어서 해결합니다.

유닉스 환경에서 프로그램과 다른 프로그램을 연결하는 단일 인터페이스는 파일과 파이프입니다. 맵리듀스의 인터페이스는 분산 파일 시스템입니다. 데이터플로 엔진은 파이프와 비슷한 자체 데이터 전송 메커니즘을 사용해 분산 파일 시스템에 중간 상태를 구체화하는 것을 피합니다. 다만 작업의 초기 입력과 최종 출력은 여전히 HDFS를 사용합니다.

분산 일괄 처리 프레임워크가 해결해야 할 두 가지 중요한 문제가 있습니다.

#### 9.1 파티셔닝

맵리듀스에서 매퍼는 입력 파일 블록에 따라 파티셔닝됩니다. 매퍼의 출력은 재파티셔닝해 정렬하고 리듀서 파티션으로 병합합니다. 리듀서 파티션 개수는 설정할 수 있습니다. 이 과정의 목적은 관련된 모든 데이터(예를 들면 같은 키를 가지는 모든 레코드)를 같은 장소로 가져오는 것입니다.

맵리듀스 이후 데이터플로 엔진은 필요한 경우가 아니라면 정렬하지 않습니다. 그렇지 않다면 대체로 비슷한 방법으로 파티셔닝합니다.

#### 9.2 내결함성

맵리듀스는 빈번히 디스크에 기록합니다. 디스크에 기록하면 개별 태스크가 실패하더라도 전체 작업을 재수행하지 않고 쉽게 복구할 수 있습니다. 하지만 작업이 실패하지 않는 경우 수행 시간이 느려지는 것은 감수해야 합니다.

데이터플로 엔진은 중간 상태를 최대한 구체화하지 않고 대신 메모리에 상태를 유지합니다. 이것은 특정 노드가 실패한다면 재계산 양이 늘어난다는 것을 의미합니다. 결정적 연산자를 사용하면 재계산이 필요한 데이터의 양을 줄일 수 있습니다.

앞서 맵리듀스에서 사용하는 몇 가지 조인 알고리즘을 설명했습니다. 이 알고리즘 대부분은 MPP 데이터베이스와 데이터플로 엔진 내부에서도 사용합니다. 또한 이 알고리즘들은 파티셔닝 알고리즘이 어떻게 동작하는지 잘 설명해주는 예제입니다.

#### 9.3 정렬 병합 조인

조인할 각 입력은 조인 키를 추출하는 매퍼를 통과합니다. 파티셔닝, 정렬, 병합 과정을 마치면 같은 키를 가지는 모든 레코드는 하나의 리듀서에서 호출됩니다. 이 리듀서 함수에서 병합된 레코드를 출력할 수 있습니다.

#### 9.4 브로드캐스트 해시 조인

조인할 입력 두 개 중 하나가 상대적으로 작다면 파티셔닝하지 않고 해시 테이블에 모두 적재할 수 있습니다. 큰 조인 입력의 각 파티션에서 매퍼를 시작할 때 각 매퍼는 작은 입력으로 만들어진 해시 테이블을 적재하고 큰 입력에서 한 번에 하나씩 레코드를 스캔하면서 각 레코드가 해시 테이블에 존재하는지 질의합니다.

#### 9.5 파티션 해시 조인

조인 입력 두 개를 같은 방식으로 파티셔닝하면(같은 키와 같은 해시 함수와 같은 파티션 수를 사용) 해시 테이블 방식을 각 파티션별로 독립적으로 사용할 수 있습니다.

분산 일괄 처리 엔진은 의도적으로 제한된 프로그래밍 모델을 제공합니다. 매퍼와 리듀서 같은 콜백 함수는 상태 정보가 없다고 가정합니다. 그리고 지정된 출력 외에 외부에서 보이는 부수 효과가 없어야 합니다. 이 제한으로 프레임워크는 분산 시스템에서 발생하는 어려운 문제들을 추상화 아래로 숨길 수 있습니다. 장비가 죽거나 네트워크 문제에 직면하더라도 태스크는 안전하게 재시도됩니다. 그리고 실패한 태스크의 출력은 버립니다. 한 파티션에서 여러 태스크가 성공한다면 실제로는 그중 하나의 출력만 보입니다.

이 프레임워크 덕분에 일괄 처리 작업을 하는 코드는 내결함성 메커니즘을 구현할 필요가 없습니다. 프레임워크는 작업의 최종 출력이 결함이 생기지 않을 때와 동일하게 보장합니다. 실제로는 여러 태스크가 재시도됐을지도 모릅니다. 이런 신뢰성의 시맨틱은 온라인 서비스에서 사용자 요청을 처리하고 그 부수 효과로 데이터베이스에 기록하는 것에 비해 훨씬 강력합니다.

일괄 처리 작업의 차별화된 특징은 입력을 수정하지 않고 입력을 읽어 출력을 생산한다는 점입니다. 다시 말하자면 출력은 입력으로부터 파생됩니다. 결정적으로 입력 데이터는 고정된 크기로 한정됩니다. 예를 들어 입력 파일은 특정 시점의 로그 파일 집합으로 구성되거나 데이터베이스 내용의 스냅숏으로 구성됩니다. 크기가 한정되기 때문에 작업은 입력 전체를 다 읽었는지 알 수 있고 그래서 결과적으로 작업을 종료할 수 있습니다.

다음 장에서는 스트림 처리를 다룹니다. 스트림 처리에서는 입력이 한정되지 않습니다. 즉 작업의 입력은 끝이 없는 데이터 스트림입니다. 이 경우 작업은 결코 끝나지 않습니다. 언제라도 입력이 더 들어올 수 있기 때문입니다. 어떤 점에서는 일괄 처리와 스트림 처리가 비슷하지만 입력이 제한 없는 스트림이라는 가정 때문에 시스템을 구축하는 방법이 크게 달라집니다.
