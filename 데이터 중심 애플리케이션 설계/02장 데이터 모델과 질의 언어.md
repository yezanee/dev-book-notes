### 1. 왜 데이터 모델이 중요한가

- 데이터 모델은 소프트웨어가 어떻게 작성되는지뿐 아니라, **문제를 어떻게 생각해야 하는지**에 대해서도 큰 영향을 준다.
- 대부분의 애플리케이션은 하나의 데이터 모델을 다른 데이터 모델 위에 계층을 둬서 만든다.
    1. 애플리케이션 개발자 → 현실을 보고 객체나 데이터 구조, API로 모델링
    2. 저장 단계 → JSON, XML, 관계형 테이블, 그래프 등 범용 모델로 표현
    3. DB 엔지니어 → 이 범용 모델을 메모리/디스크/네트워크의 바이트로 표현
    4. 하드웨어 엔지니어 → 바이트를 전류, 빛, 자기장 등으로 표현
- 각 계층은 명학한 데이터 모델을 제공해 하위 계층의 복잡성을 감추는 추상화 역할을 한다.
    - 다른 그룹의 사람들(DB 엔지니어와 애플리케이션 개발자)이 효율적으로 일할 수 있게 한다.

### 2. 관계형 모델 vs 문서 모델

#### 2.1 관계형 모델

- 데이터는 릴레이션(테이블)과 튜플(로우)로 구성
- 원래는 비즈니스 데이터 처리(트랜잭션 처리, 일괄 처리)를 위해 만들어졌으나 이후 범용적으로 확산

#### 2.2 NoSQL의 탄생

- 등장 배경
    - 대규모 데이터셋/높은 **쓰기** 처리량에 대한 확장성 필요
    - 무료 오픈소스 선호
    - 관계형이 지원하지 않는 특수 질의 필요
    - 더 동적이고 표현력 있는 데이터 모델 요구
- 결론: 다양한 요구사항에 맞춰 관계형 DB + 비관계형 DB를 함께 쓰는 **다중 저장소 지속성(polyglot persistence)** 추세

#### 2.3 객체 관계형 불일치

- **임피던스 불일치(impedance mismatch)**: OOP 언어의 객체와 SQL의 테이블/로우/컬럼 사이의 변환 계층이 필요한 문제
- ORM(ActiveRecord, Hibernate 등)이 상용구 코드를 줄여주지만 완전히 없애지는 못한다.
    - **예: 이력서(프로필) 데이터**
        
        ![2-1](/데이터%20중심%20애플리케이션%20설계/image/2장/2-1.png)
        
        - 하나의 문서 형태 데이터를 관계형 다중 테이블로 쪼개서 저장해야 한다.
    - **왜 쪼개야 하나?**
        - 프로필 전체는 고유 식별자인 `user_id`로 식별한다. `first_name`과 `last_name` 같은 필드는 사용자마다 **정확하게 하나씩 존재(1:1)**하므로 `users` 테이블의 칼럼으로 모델링할 수 있다.
        - 하지만 대부분의 사람들은 경력(직위)에 넣을 직업이 하나 이상이며, 학력 기간다 연락처 정보도 다양하다**(1:N)**
        - 그런데 관계형 테이블은 **한 로우 = 고정된 개수의 컬럼** 구조라 개수가 가변적인 데이터를 하나의 컬럼에 담을 수 없다.
        - 그림 2-1은 전통적인 SQL에서 가장 일반적인 정규화 표현이다.
            - 직위(`positions`), 학력(`education`), 연락처 정보(`contact_info`)를 개별 테이블에 넣고, 외래 키로 `users` 테이블을 참조
        - 구조화된 데이터타입(array 등)과 XML 데이터에 대한 지원을 추가했다.
            - 단일 로우에 다중 값을 저장할 수 있고, 문서 내 질의와 색인이 가능해졌다.
        - 직업, 학력, 연락처 정보를 JSON이나 XML 문서로 부호화해 데이터베이스의 텍스트 칼럼에 저장한 다음 애플리케이션이 구조와 내용을 해석하게 할 수 있다.
            - 부호화된 칼럼의 값을 질의하는 데이터베이스를 사용할 수 없다. 데이터베이스 입장에서는 칼럼 안의 내용이 그냥 긴 문자열이기 때문.
                - `WHERE 직업 = '개발자'` 처럼 문서 내부의 특정 필드를 대상으로 질의할 수 없고
                - 그 필드에 인덱스를 걸 수도 없고
                - 결국 애플리케이션 코드가 직접 그 문자열을 파싱해서 구조와 내용을 해석애햐 한다.
    - **왜 문제인가?**
        - 원래 애플리케이션 입장에서 이력서는 하나의 완결된 덩어리(문서)인데, 여러 테이블로 쪼개면
        (1) 프로필 전체를 가져올 때마다 여러 테이블을 조인해야 하고,
        (2) 조인 결과를 다시 하나의 객체로 조립하는 코드가 필요해지며(임피던스 불일치와 연결),
        (3) ‘이력서 하나’라는 직관과 ‘테이블 여러 개에 흩어진 조각들’이라는 저장 구조 사이에 괴리가 생긴다.
- JSON 표현은 문서 하나에 모든 정보가 담겨 있어(지역성 locality) **다중 테이블 조인 없이 한 번의 질의**로 가져올 수 있다.

#### 2.4 다대일과 다대다 관계

- **다대일**: 여러 사람이 하나의 지역/업계에 속한다.
    - **ID로 정규화해서 저장**하면 **일관성, 모호함 회피, 갱신의 편의성, 현지화(언어 번역), 검색 편의성** 등의 장점이 있다.
        - 그림 2-1에서 `region_id` 와 `industry_id` 를 평문인 “그레이터 시애틀 구역”과 “자선 활동”이 아닌 ID로 주어진 이유
        - ID 자체는 아무런 의미가 없기 때문에, 식별 정보가 변경 되어도 ID는 동일하게 유지할 수 있다. 하지만, 의미를 가지는 ID인 경우에는 변경해야 할 수도 있다. 그리고, **정보가 중복**돼 있으면 모든 중복 항목을 변경해야 한다. → **쓰기 오버헤드와 불일치**(정보의 일부 중복은 갱신됐지만 다른 중복 항목이 갱신되지 않음) 위험이 있다.
    - **문서 모델**은 다대일 정규화(조인)에 약함 → **조인 없이 애플리케이션 코드에서 흉내**내야 함.
- **다대다**: 추천서 기능 추가 시 **조직/학교 같은 엔티티**를 참조 → 문서 모델에서도 조인이 필요해진다.
- 결론: 애플리케이션이 커지면 데이터는 점점 상호 연결되는 경향이 있다.
- **엔티티로서의 조직/학교**
    - 지금까지는 `organization`(회사명), `school_name`(학교명)을 단순 문자열로 저장했는데, 이걸 각자 별도의 엔티티로 참조하도록 바꾸면 어떨지 생각해볼 수 있다.
    - 각 조직/학교를 엔티티로 참조하면, 이력서에서 해당 조직/학교로 연결되는 링크를 걸거나 로고·추가 정보를 함께 보여줄 수 있다.
    
    ![2-3](/데이터%20중심%20애플리케이션%20설계/image/2장/2-3.png)
    
    - **추천서 기능**을 예로 들면, 다대다 관계가 왜 필요해지는지 알 수 있다.
        - 한 사용자가 다른 사용자의 추천서를 작성하는 기능을 추가한다고 하면, 추천서는 추천인의 프로필(이름, 사진)을 참조해야 하고, 추천인이 사진을 갱신하면 그 사람이 작성한 모든 추천서에도 반영되어야 한다.
    - 그림 2-4처럼 조직·학교·다른 사용자(추천인) 등은 여러 이력서에서 공유해서 참조할 수 있어야 하므로, 각 항목은 문서 하나로 묶이더라도 서로 다른 문서/엔티티 간에는 참조(다대다 관계)가 필요해지고, 질의 시 조인이 필요해진다.

#### 2.6 문서 데이터베이스는 역사를 반복하고 있나?

- IMS(1968, IBM) → 계층 모델 사용, 계층 모델은 JSON과 유사한 중첩 트리 구조.
- 계층 모델은 일대다에는 강하지만 다대다 관계 표현이 어렵다. → 관계형 모델과 네트워크 모델(코다실)이 등장해 경쟁.
- **네트워크 모델(코다실)**: 레코드가 다중 부모를 가질 수 있다. 질의 시 정해진 "접근 경로"를 따라가야 한다. → 유연성 부족, 질의/갱신 코드가 복잡.
- **관계형 모델**: 접근 경로 없이 임의 조건으로 로우를 조회 가능. 질의 최적화기가 자동으로 실행 계획(접근 경로)을 결정 → 새 기능 추가가 훨씬 쉽다.

#### 2.7 관계형 데이터베이스와 오늘날의 문서 데이터 베이스

- MySQL을 제외한 대부분의 관계형 DB(포스트그레스큐엘, IBM DB2 등)는 2000년대 중반 이후부터 XML을 지원하기 시작했고, 이후 JSON 지원도 추가되었다.
    - XML/JSON 문서 내부를 색인하고 질의할 수 있는 기능까지 포함되어, 관계형 DB를 쓰면서도 문서 DB와 비슷한 방식으로 데이터를 다룰 수 있게 되었다. (FinQ 프로젝트의 `body_data`)
- 반대로 문서 DB 쪽에서도 관계형 기능을 흡수하는 흐름이 있다.
    - 리싱크DB는 질의 언어에서 관계형 조인을 지원하고, 몽고DB 드라이버는 자동으로 데이터베이스 참조를 확인해주는 기능이 있다.
    - 다만 실제로는 서버가 아니라 클라이언트 측에서 조인을 수행하는 것이라 네트워크 왕복이 추가로 필요하고, 서버 측 조인보다 최적화가 덜 되어 느릴 수 있다.
- 이처럼 관계형 DB와 문서 DB는 시간이 지나면서 점점 비슷해지고 있고, 각 모델이 서로 부족한 부분을 보완해가는 이 흐름은 긍정적으로 평가된다. 저자는 **관계형과 문서의 혼합 모델이 미래 데이터베이스가 나아가야 할 방향**이라고 명시적으로 결론을 내렸다.
    - 데이터베이스가 문서처럼 데이터를 다룰 수 있으면서 동시에 관계형 질의도 수행할 수 있다면, 애플리케이션은 필요에 따라 가장 적합한 기능을 골라 쓸 수 있다.

#### 2.8 문서 모델 vs 관계형 모델 비교 요약

| 관점 | 문서 모델 | 관계형 모델 |
| --- | --- | --- |
| 스키마 유연성 | 강함(스키마리스/읽기 스키마) | 약함(쓰기 스키마) |
| 지역성 | 좋음(관련 데이터가 한 문서에) | 다중 테이블 조인 필요 |
| 일대다(트리 구조) | 자연스러움 | 여러 테이블로 쪼개야 함(shredding) |
| 다대일/다대다, 조인 | 약함 | 강함 |
| 상호 연결 많은 데이터 | 불리함 | 유리함(그래프 모델도 고려) |

#### 2.9 스키마: 쓰기 스키마 vs 읽기 스키마

- **쓰기 스키마(schema-on-write)**: 관계형 DB 전통 방식. 스키마가 명시적이며 DB가 강제.
- **읽기 스키마(schema-on-read)**: 문서 DB 방식. 구조는 암묵적이며 읽을 때 해석.
- 데이터 타입 변경 예시
    - 문서 DB: 새 필드를 가진 새 문서를 쓰고, 읽는 코드에서 예전 형식도 처리하도록 분기 처리.
    - 관계형 DB: **`ALTER TABLE`로 마이그레이션 필요**. 대부분 DB는 수 밀리초 내 처리되지만 MySQL은 테이블 전체를 복사해 몇 시간이 걸릴 수도 있다.
- 읽기 스키마가 유리한 경우: 컬렉션 내 항목들의 구조가 다양하거나, 외부 시스템에 의해 구조가 결정되는 경우.

#### 2.10 질의를 위한 데이터 지역성

- 문서는 보통 단일 연속 문자열(JSON/XML/BSON)로 저장 → **문서 전체를 한 번에 읽어야 할 때 성능상 이점(저장소 지역성).**
- 단점: 문서의 일부만 필요해도 전체 문서를 읽어야 하고, 갱신 시에도 보통 전체 문서를 재작성해야 한다. → 문서를 작게 유지하고 크기가 커지는 **쓰기는 피하는 게 좋다.**
- **지역성 개념은 문서 모델 전용이 아님**: 구글 스패너(중첩 테이블), 오라클(다중 테이블 색인 클러스터 테이블), 빅테이블의 칼럼 패밀리도 유사한 목적을 가진다.

### 3. 데이터를 위한 질의 언어

- **선언형(declarative) 질의**: SQL, 관계 대수
    - "무엇을" 원하는지만 명시, "어떻게"는 DB가 결정.
- **명령형(imperative) 질의**: IMS, 코다실
    - 특정 순서로 연산을 수행하도록 직접 지시.
- 선언형의 장점
    - 코드가 더 간결하다.
    - DB 엔진의 내부 구현이 숨겨져 있어, 질의를 바꾸지 않고도 성능 개선이 가능하다.
    - 병렬 실행에 유리(결과의 패턴만 지정하므로 실행 순서에 자유도가 있다)
- **웹에서의 선언형 질의 예시:** CSS 선택자, XSL/XPath (자바스크립트 DOM 명령형 코드와 비교하면 훨씬 간결).

#### 3.1 맵리듀스(MapReduce) 질의

- 선언형과 명령형의 중간 형태. `map`과 `reduce` 함수로 질의 로직을 표현.
- 몽고DB 등 일부 NoSQL에서 제한된 형태로 지원(읽기 전용 질의).
- map/reduce 함수는 순수 함수여야 함(부수 효과 없음) → 임의 순서 실행, 장애 시 재실행 가능.
- 몽고DB 2.2부터는 더 선언적인 **집계 파이프라인(aggregation pipeline)**도 지원.

### 4. 그래프형 데이터 모델

- 데이터 간 다대다 관계가 매우 일반적이고 복잡해지면 그래프 모델이 자연스럽다.
- 구성 요소: **정점(vertex)** = 엔티티, **간선(edge)** = 관계.
- 예시: 소셜 그래프(사람-친구관계), 웹 그래프(페이지-링크), 도로/철도 네트워크(교차로-도로).
- 그래프는 동종 데이터에 국한되지 않는다. 페이스북처럼 여러 타입의 정점/간선을 한 그래프에 저장이 가능하다.

#### 4.1 속성 그래프 모델

- 정점: 고유 식별자, 유출 간선 집합, 유입 간선 집합, 속성(키-값 쌍) 컬렉션.
- 간선: 고유 식별자, 시작 정점(꼬리), 끝 정점(머리), 관계를 설명하는 레이블, 속성 컬렉션.
- 관계형 테이블(vertices, edges 두 개)로도 구현 가능하지만, 스키마 제약이 없어 유연하다.
- 국가별로 다른 지역 구조(프랑스는 주/도, 미국은 군/주), 데이터 입도 차이 등 이질적인 데이터를 유연하게 표현 가능하다.

#### 4.2 사이퍼(Cypher)

- 네오포제이(Neo4j)용 선언형 질의 언어.
- `MATCH (person) -[:BORN_IN]-> () -[:WITHIN*0..]-> (location)` 형태로 패턴을 매칭.
- 화살표로 방향성 있는 패턴 표현, `0..`은 "0회 이상 반복"(정규식의 와 유사).

#### 4.3 SQL로 그래프 질의하기

- 가능하지만 어렵다. 관계형 DB는 질의에 필요한 조인 수를 미리 알아야 하는데, 그래프 질의는 가변적인 순회 경로가 필요하기 때문이다.
- SQL:1999 이후 **재귀 공통 테이블 식(WITH RECURSIVE)**으로 표현 가능하지만 사이퍼 대비 문법이 훨씬 복잡(4줄 vs 29줄 예시).

#### 4.4 트리플 저장소와 스파클(SPARQL)

- 트리플 저장소: 모든 정보를 (주어, 서술어, 목적어) 3부분 구문으로 저장. 속성 그래프 모델과 거의 동등.
- 목적어는 (1) 원시 타입 값 또는 (2) 다른 정점(이 경우 서술어=간선 레이블) 둘 중 하나.
- **터틀(Turtle)/N3** 형식: 사람이 읽기 쉬운 트리플 표현. 동일 주어는 세미콜론으로 묶어서 간결하게 표현 가능.
- **스파클(SPARQL)**: RDF 데이터 모델을 사용하는 트리플 저장소 질의 언어. 사이퍼가 스파클의 패턴 매칭을 차용해서 매우 유사하다.
- **시맨틱 웹**: 웹의 데이터를 기계가 읽을 수 있는 형태로 만들자는 개념(RDF). 현실에서는 크게 성공하지 못했지만, 트리플 개념 자체는 애플리케이션 내부 데이터 모델로 유용.

#### 4.5 데이터로그(Datalog)

- 스파클/사이퍼보다 훨씬 오래된 언어(1980년대 학계 연구). 이후 질의 언어들의 이론적 기반.
- 트리플 대신 **서술어(주어, 목적어)** 형태로 사실(fact)을 기술.
- **규칙(rule)**로 새로운 서술어를 정의 가능 (재귀적으로 다른 규칙을 참조 가능) → 복잡한 질의를 작은 단위로 나눠서 구성.
- 대문자로 시작하는 단어는 변수.
- 간단한 일회성 질의에는 불편하지만, 데이터/질의가 복잡할수록 결합·재사용성 면에서 강력하다.

### 5. 그래프 데이터베이스 vs 네트워크 모델(코다실) - 왜 다른가?

겉보기엔 유사해 보이지만 중요한 차이가 있다.

1. 코다실은 레코드 타입과 중첩 구조를 지정하는 스키마가 있지만, 그래프 DB는 이런 제약이 없어 훨씬 유연하다.
2. 코다실은 접근 경로(정해진 경로 탐색)로만 레코드에 도달 가능. 그래프 DB는 고유 ID로 직접 참조하거나 색인으로 특정 값을 바로 찾을 수 있다.
3. 코다실은 레코드의 하위 항목이 정렬된 집합이라 삽입 시 위치를 고려해야 한다. 그래프 DB의 정점/간선은 정렬되지 않는다(질의 시 정렬).
4. 코다실 질의는 명령형이라 스키마 변경에 취약하다. 그래프 DB는 대부분 사이퍼/스파클 같은 고수준 선언형 질의 언어를 제공한다.

### 6. 장 전체 정리

- 역사적으로 데이터를 **트리(계층 모델)**로 표현하려 했으나 다대다 관계 표현에 한계 → **관계형 모델** 등장.
- 최근에는 관계형에도 잘 맞지 않는 애플리케이션들이 발견되며 NoSQL 등장, 크게 두 갈래:
    1. **문서 데이터베이스**: 데이터가 자기 완결적 문서 안에 있고, 문서 간 관계가 거의 없는 경우에 적합.
    2. **그래프 데이터베이스**: 문서 모델과 반대로, 모든 것이 잠재적으로 서로 연결된 경우에 적합.
- 세 모델(문서, 관계형, 그래프) 모두 각자 영역에서 훌륭함.
    - 즉, ‘만능 솔루션’은 없고 목적에 맞는 시스템을 선택/조합해야 함.
- **문서/그래프 DB의 공통점:** 대부분 저장할 데이터에 스키마를 강제하지 않아 **요구사항 변화에 유연하게 대응 가능**(단, 스키마가 명시적이냐 암묵적이냐의 차이일 뿐, 여전히 암묵적 구조는 존재).
- **각 데이터 모델은 자기만의 질의 언어/프레임워크를 가짐:** SQL, 맵리듀스, 몽고DB 집계 파이프라인, 사이퍼, 스파클, 데이터로그 등.
- **다루지 않은 특수 사례:** 게놈 데이터의 염기 서열 유사도 검색처럼 기존 데이터 모델로 처리하기 어려운 경우, 특화된 소프트웨어(예: GenBank)가 별도로 존재.
- 이 외에도 책에서 다루지 않은 데이터 모델들이 남아 있음
    - **입자 물리학 분야의 빅데이터**: LHC 같은 프로젝트는 데이터 규모가 수백 페타바이트에 달해 하드웨어 비용 통제를 위한 사용자 정의 솔루션이 필요.
    - **전문(full-text) 검색**: DB와 자주 함께 쓰이는 데이터 모델의 일종. 이 책의 범위 밖이지만, 색인 검색은 3장과 3부에서 다룸.
- 다음 장(3장)에서는 이번 장에서 설명한 데이터 모델들을 실제로 **구현**할 때 발생하는 트레이드오프를 다룰 예정.
