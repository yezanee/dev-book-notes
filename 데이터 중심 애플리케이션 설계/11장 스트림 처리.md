## 1. 핵심 개념 구조

### **1.1 일괄 처리 vs 스트림 처리**

- 일괄 처리(10장) = 유한한 입력을 읽고 끝남 (하루치 배치 등)
- **스트림 처리(11장) = 무한한 입력을 이벤트 발생 즉시 처리, 절대 끝나지 않음**
- **실무 포인트:** 배치 지연이 문제되면(예: 사용자 행동 반영이 하루 늦음) 스트림 처리로 전환할 신호. 다만 무조건 스트림이 낫다는 건 아니고, 지연 시간 요구사항과 운영 복잡도를 저울질해야 함

## 2. 이벤트 전달 방식 3가지

1. **직접 메시징** (UDP 멀티캐스트, ZeroMQ, 웹훅): 브로커 없이 생산자-소비자 직접 통신. 빠르지만 노드 다운 시 메시지 유실 위험
2. **메시지 브로커** (RabbitMQ, ActiveMQ 등, AMQP/JMS 스타일): 큐에 쌓아두고 소비자가 확인 응답(ack)하면 삭제. **메시지 순서가 뒤바뀔 수 있음**(재전송 때문에), 큐가 비면 메시지도 사라짐
3. **로그 기반 메시지 브로커** (Kafka, Kinesis): 파티션에 오프셋 순서로 추가만 함. 순서 보장, 재생(replay) 가능, 소비자를 여러 개 붙여도 원본에 영향 없음

### **2.1 실무 판단 기준**

- 메시지 처리 비용은 비싸고 병렬화가 필요한데 순서는 안 중요 → JMS/AMQP 스타일 브로커 (예: SQS도 이 계열, 순서 보장 안 됨이 기본)
- 처리량 많고 순서가 중요 → 로그 기반(Kafka) 적합
- 본인 스택 기준:
    - SQS는 팬아웃/로드밸런싱은 되지만 파티션 순서 보장이 기본으로 없음(FIFO 큐 쓰면 처리량 희생).
    - 순서가 중요한 이벤트(예: 계좌 잔액 변경, 결제 상태 전이)라면 Kafka나 Kinesis처럼 파티션 키 기반 순서 보장이 되는 걸 검토해야 함

### **2.2 메시지 브로커 vs 데이터베이스의 근본 차이**

- **브로커는 소비자가 확인 응답하면 즉시 삭제(일시 저장 개념)**, DB는 명시적으로 지울 때까지 영구 보관
- 새 소비자를 늦게 추가하면: 전통 브로커는 등록 이후 메시지만 받음(과거 복구 불가), 로그 기반은 처음부터 재생 가능
- **오래된 메시지 재생**: 로그 기반 브로커는 메시지 소비가 읽기 전용 연산이라 파일을 다시 읽는 것과 유사함. 실수로 잘못 처리된 구간을 다른 오프셋 위치에 출력을 기록해서 재처리하는 것도 가능 (일괄 처리와 비슷한 유연성)
- 실무 판단: "나중에 붙는 소비자가 과거 데이터도 봐야 하는가"가 브로커 선택의 중요한 기준

## 3. 메시지 전달과 RPC / 액터 프레임워크와의 차이

- 메시지 전달 시스템(웹훅 등)은 RPC의 대안으로 서비스 간 통신에도 쓰이지만, 일반적으로 스트림 처리자로 취급하지는 않음
- **액터 프레임워크 vs 스트림 처리**: 액터는 동시성 관리와 통신 모듈 분산 실행이 목적, 스트림 처리는 데이터 관리 기법이 목적
- 액터 간 통신은 단기적/일대일, 이벤트 로그는 지속성 있고 다중 구독 가능
- 액터는 임의 방식(순환 요청/응답 포함)으로 통신 가능하지만 스트림 처리는 대개 비순환 파이프라인
- 실무 참고: 액터 프레임워크는 장애 상황에서 메시지 전달을 보장하지 않아서, 재시도 로직을 직접 구현하지 않으면 내결함성이 떨어짐. 안정성이 중요한 처리라면 액터보다 스트림 처리 프레임워크나 로그 기반 브로커가 나음

---

## 4. 파티션과 오프셋

- 토픽은 여러 파티션으로 나뉘고, 파티션 내에서만 순서 보장. 파티션 간 순서는 보장 안 됨
- 같은 키를 가진 이벤트는 같은 파티션으로 보내야 순서가 유지됨 (예: 같은 계좌 ID의 이벤트는 항상 같은 파티션)
- 소비자 오프셋만 기록하면 되므로 개별 메시지 ack보다 오버헤드 적음
- **실무 팁**: 컨슈머 그룹 설계 시 파티션 수 = 최대 병렬 소비자 수라는 제약을 기억. 특정 메시지 처리가 느리면 같은 파티션 뒤 메시지가 막힘(head-of-line blocking) → 파티션 키 설계가 곧 병렬성/순서 트레이드오프 설계

### **4.1 소비자가 생산자를 못 따라갈 때의 선택지 3가지**

- 버리기 / 버퍼링(배압) / 배압 적용(생산자 자체를 막기)
- 로그 기반 브로커는 "디스크 공간만큼 버퍼링"하는 형태라 뒤처져도 다른 소비자에 영향 안 줌 (원형 버퍼 구조)
- 실무 포인트: 소비자가 뒤처져서 오프셋이 이미 삭제된 구간을 가리키면 메시지 유실 가능 → 컨슈머 랙(lag) 모니터링이 필수. SQS/Kinesis 쓸 때도 컨슈머가 처리 속도를 못 따라가면 재시도 폭주나 유실로 이어질 수 있어서 랙/큐 길이 알람은 꼭 걸어야 함

## 5. 데이터베이스와 스트림

### **4.1 이중 기록(dual write)의 함정**

- DB 쓰고 나서 캐시/색인 따로 갱신하면 두 쓰기가 경쟁 조건으로 서로 다른 최종 순서를 가질 수 있음 → 데이터 불일치
- 실무에서 흔히 겪는 버그 패턴. "DB엔 A인데 캐시엔 B" 같은 문제의 원인

### **4.2 변경 데이터 캡처(CDC)**

- DB를 리더로 두고 변경 사항을 로그로 뽑아 다른 시스템(색인, 캐시, DW, 다른 서비스)에 순서대로 전파하는 방식
- Debezium(MySQL binlog), Maxwell 등이 대표적 구현체
- **실무에서 써먹는 법**: 마이크로서비스 간 데이터 동기화, 이벤트 기반 아키텍처 구축 시 이중 기록 대신 **CDC**를 쓰면 원자성 문제를 근본적으로 회피 가능. Outbox 패턴(트랜잭션 아웃박스)도 이 아이디어의 응용
- **CDC 초기 스냅숏 문제**
    - 변경 로그만 있으면 최근 갱신 안 된 데이터는 로그에 없어서 놓침. 색인을 새로 구축할 때는 초기 스냅숏이 필요하고, 스냅숏은 로그의 특정 오프셋과 정확히 대응돼야 함
    - 실무에서 CDC 도구 선택 시 스냅숏 기능 내장 여부가 중요한 기준 (Debezium은 지원)

### **4.3 로그 컴팩션(log compaction)**

- 저장 엔진처럼 같은 키의 오래된 레코드를 지우고 최신 값만 유지하는 방식. 툼스톤(tombstone, 특별한 null 값)으로 삭제 표시
- 실무 적용: 상태 저장용 토픽(예: 사용자 프로필 변경 이력)을 컴팩션 토픽으로 만들면, 새 컨슈머가 붙을 때 전체 DB 스냅숏 없이도 오프셋 0부터 스캔해서 현재 상태를 재구축할 수 있음. Kafka Streams의 상태 저장소(state store)가 이 방식으로 동작함

### **4.4 변경 스트림용 API 지원**

- RethinkDB(구독 가능한 질의), Firebase/CouchDB(변경 피드), Meteor(MongoDB oplog 구독), VoltDB(스트림 형태 출력)처럼 DB가 변경 스트림을 기본 인터페이스로 점점 지원하는 추세
- Kafka Connect는 카프카를 다양한 시스템용 CDC 도구로 쓰기 위한 도구

## **5. 이벤트 소싱**

- CDC는 DB를 로우 레벨에서 변경 로그로 뽑는 것, 이벤트 소싱은 애플리케이션 로직 수준에서 의도(사용자가 무엇을 했는지)를 불변 이벤트로 저장
- 이벤트는 추가만 하고 갱신/삭제 안 함. 현재 상태는 이벤트 로그를 재생해서 도출
- 실무 적용 시 주의: **이벤트 로그와 별개로 스냅숏(현재 상태 캐시)을 유지해야 재처리 비용을 줄일 수 있음.** 무조건 매번 처음부터 재생하면 안 됨

### **5.1 명령(command)과 이벤트(event)의 구분**

- 사용자 요청이 처음 도착하면 명령이고 실패할 수 있음(무결성 조건 위반 등)
- 명령이 검증/승인되면 비로소 이벤트(불변 사실)가 됨. 이벤트는 소비자에게 이미 전파됐으므로 거부 불가
- 실무 팁: 예약/좌석 배정처럼 동시성 검증이 필요하면 명령을 가예약 이벤트와 확정 이벤트로 쪼개는 패턴 사용 가능. 동기 검증은 가예약에서, 나머지는 비동기 처리

## 6. 상태, 스트림, 불변성

- 애플리케이션 상태는 시간에 따른 이벤트 스트림을 적분한 것, 변경 스트림은 상태를 시간으로 미분한 것 (수학적 비유)
- 변경 로그를 지속성 있게 저장하면 상태를 쉽게 재생성할 수 있음. 팻 헬랜드의 말처럼 "로그가 진실이고 데이터베이스는 로그의 최근 레코드 값을 캐시한 것"이라는 관점
- 회계의 원장(ledger) 개념도 불변 이벤트 로그의 오래된 실사례

### **6.1 불변성의 한계**

- 규제상 삭제해야 하는 경우 존재(개인정보보호법 등)
- 데이터를 진짜로 삭제하는 건 어려움 - 저장 엔진, 파일 시스템, SSD는 덮어쓰기보다 새 위치에 기록하는 구조라 복제본이 여러 곳에 남음. 백업은 의도적으로 불변이라 더 어려움
- 삭제는 "찾을 수 없게" 만드는 문제로 접근. 데이터토믹의 적출(excision), 버전관리 시스템의 셔닝(shunning) 같은 개념
- 실무 대응: 핀테크는 개인정보/거래정보 규제가 엄격하니 이벤트 소싱 도입 전에 삭제 요구사항 처리 방식을 설계 단계에서 정해둬야 함

## 7. 동일 이벤트 로그로 여러 뷰 만들기 (CQRS)

- 불변 이벤트 로그에서 가변 상태를 분리하면 여러 읽기 전용 뷰를 만들 수 있음 (한 스트림에 여러 소비자)
- 명령과 질의 책임의 분리(CQRS): 쓰기 최적화 로그에서 읽기 최적화 상태로 전환하면 정규화/비정규화 논쟁이 무의미해짐. 읽기 뷰는 비정규화하는 게 합리적
- 실무 적용: 검색 색인, 캐시, 분석 DB 등 각각 목적에 맞게 비정규화해서 유지 가능. 마이크로서비스에서 읽기 모델 분리 시 자주 쓰는 패턴
- 신구 시스템을 나란히 구동하다가 기존 시스템을 내리는 마이그레이션 전략도 가능

### **7.1 동시성 제어**

- 이벤트 소싱/CDC의 실질적 약점: 소비가 보통 비동기라 이벤트를 기록한 직후 읽기 뷰를 조회하면 반영 안 된 걸 볼 수 있음(자신이 쓴 내용 읽기 문제)
- 해결책1: 로그 추가와 읽기 뷰 갱신을 동기적으로 같은 트랜잭션에 묶기(분산 트랜잭션 필요할 수 있음)
- 해결책2: 이벤트 로그로 현재 상태를 만들면 동시성 제어가 단순해짐(단일 스레드가 파티션 하나씩 순차 처리하면 락 불필요)

## 8. 스트림 처리 용도 3가지 큰 분류

1. 이벤트 데이터를 DB/캐시/색인에 기록하고 다른 클라이언트가 질의 (구체화 뷰 유지)
2. 이벤트를 사람에게 직접 전달 (이메일, 푸시 알림, 실시간 대시보드)
3. 하나 이상의 입력 스트림을 처리해 하나 이상의 출력 스트림 생산 (파이프라인)

### **8.1 복잡한 이벤트 처리(CEP)**

- 특정 이벤트 패턴을 검색하는 데 적합. 정규표현식처럼 스트림에서 패턴 규칙 정의
- 실무 예: 사기 감시(카드 사용 패턴 이상 감지), 거래 시스템(가격 변화 감지 후 자동 거래), 제조 시스템(기계 오작동 감지)
- Esper, IBM InfoSphere Streams, Apama 등이 구현체. Samza 같은 분산 스트림 처리자는 선언형 SQL 질의도 지원

### **8.2 스트림 분석**

- CEP와 경계는 불분명하지만 대량 이벤트 집계, 통계 지표 추출에 더 집중 (이벤트 빈도, 이동 평균, 추세 비교)
- 확률적 알고리즘(블룸 필터, HyperLogLog, 백분위 추정) 활용, 근사 결과지만 메모리를 훨씬 적게 씀
- 실무 연관: 핀테크 사기 탐지 시스템이라면 CEP 개념이 직접 적용됨

### **8.3 구체화 뷰 유지하기**

- 캐시, 검색 색인, 데이터 웨어하우스 같은 파생 데이터 시스템이 원본 최신 내용을 따라잡게 하는 특별한 사례
- 어떤 데이터셋에 대한 또 다른 뷰를 만들고 기반 데이터가 변경될 때마다 뷰를 갱신
- Druid(카프카에서 직접 읽음), Pistachio(분산 키값 저장소), Kafka Connect Sink 등이 이 방식 활용

### **8.4 스트림 상에서 검색하기**

- CEP 외에도 전문 검색 질의 같은 복잡한 기준으로 개별 이벤트를 검색해야 하는 경우
- 실무 예: 미디어 모니터링 서비스(특정 회사/상품 언급 뉴스 검색), 부동산 웹사이트(사용자 설정 기준에 맞는 새 매물 알림)
- 전통 검색 엔진은 문서를 먼저 색인하고 질의를 실행하지만, 스트림 검색은 반대로 질의를 먼저 저장하고 문서(이벤트)가 질의를 지나가면서 매칭 실행. 엘라스틱서치의 퍼콜레이터(percolator) 기능이 대표적 구현

---

## 9. 스트림 조인 3종 (실무에서 헷갈리기 쉬운 부분)

1. **스트림-스트림 조인**: 두 활동 이벤트 스트림을 시간 윈도우로 묶어서 상관관계 찾기 (예: 검색 이벤트-클릭 이벤트 매칭). 윈도우 크기 선택이 핵심 설계 포인트
2. **스트림-테이블 조인(강화, enriching)**: 활동 이벤트에 참조 데이터(사용자 프로필 등)를 붙임. 매번 원격 DB 조회하면 느리니 로컬에 DB 사본을 캐싱(CDC로 최신화)해서 조인하는 게 실무 표준 패턴
3. **테이블-테이블 조인**: 트위터 홈타임라인처럼 구체화 뷰(materialized view)를 유지. 팬아웃 캐시 갱신 로직으로 구현

### **9.1 조인의 시간 의존성**

- 상태를 유지하는 이벤트 순서는 매우 중요(먼저 팔로우한 다음 언팔로우했는지가 순서에 따라 결과 다름). 파티션 간 순서 보장하는 일반적 방법은 없음
- 시점 의존적 조인(판매 시점 세율 적용 등)은 데이터 웨어하우스에서 천천히 변하는 차원(SCD, slowly changing dimension) 패턴으로 해결. 레코드 특정 버전에 유일 식별자 부여
- 복수 스트림에 걸친 이벤트 순서가 결정되지 않으면 조인도 비결정적 (같은 입력이라도 재수행 시 다른 결과 가능)
- 실무 포인트: 이렇게 변경한 조인은 결정적이지만 테이블의 모든 레코드 버전을 보유해야 해서 로그 컴팩션이 불가능해짐

---

## 10. 시간 다루기

- 처리 시간 기준 윈도우는 처리 지연/재시작 시 통계 왜곡 발생 (재배포 시 백로그 처리 중 요청률이 비정상적으로 튀는 것처럼 보임)
- 실무 대응: 이벤트 시간과 처리 시간을 혼동하면 안 됨. 이벤트 시간 기준이 정확하지만 메시지 지연 시 순서 예측 불가

### **10.1 준비 여부 인식 (윈도우 종료 판단)**

- 이벤트 시간 기준 윈도우의 까다로운 문제: 모든 이벤트가 도착했는지 확신할 수 없음
- 특별한 메시지("t보다 이른 타임스탬프의 메시지는 더 이상 없음")를 윈도우 트리거 소비자가 사용하는 방법도 있음(워터마크 개념)
- 여러 생산자가 각자 최소 타임스탬프 임계치를 갖는 경우 소비자가 개별 생산자를 모두 추적해야 해서 생산자 추가/제거가 더 까다로워짐

### **10.2 낙오자 이벤트 처리**

1. 무시하기 (놓친 이벤트 수를 지표로 추적해서 경고)
2. 수정 값 발행하기 (낙오자 포함한 갱신된 값, 이전 출력 취소 필요할 수도)

### **10.3 어떤 시계를 쓸 것인가 (장치 시계 vs 서버 시계)**

- 모바일 앱처럼 장치가 오프라인일 때도 이벤트를 버퍼링하다 나중에 보내는 경우, 장치 로컬 시계는 부정확할 수 있음
- 서버 시계가 더 정확하지만 사용자와의 실제 상호작용 시점 설명에는 부족
- 해결책: 이벤트 발생 시간(장치 시계), 서버로 보낸 시간(장치 시계), 서버가 받은 시간(서버 시계) 세 가지 타임스탬프를 로그로 남겨서 오프셋을 추정하고 실제 발생 시간을 역산

### **10.4 윈도우 유형 4가지**

- 텀블링 윈도우: 고정 길이, 겹침 없음
- 호핑 윈도우: 고정 길이지만 결과를 매끄럽게 하기 위해 윈도우 중첩
- 슬라이딩 윈도우: 시간 간격 사이 발생한 모든 이벤트 포함, 고정 경계 없음
- 세션 윈도우: 고정 기간 없이 같은 사용자의 활동을 묶고 일정 시간 비활성화되면 종료 (웹사이트 분석에서 그룹화 용도로 흔히 필요)

## 11. 장애 허용과 정확히 한 번 처리 (실무에서 가장 중요한 부분)

**핵심 원칙: 정확히 한 번(exactly-once)은 사실상 불가능, "결과적으로 한 번(effectively-once)"이 현실적 목표**

### 11.1 세 가지 실무 전략

1. **마이크로배치 + 체크포인트** (Spark Streaming 방식): 배치 크기 약 1초, 실패 시 체크포인트부터 재시작. 단, 재시작 시 외부 부수 효과(이메일 발송, 외부 API 호출)가 중복 실행될 위험 있음
    - 배리어(barrier)가 마이크로배치 경계를 트리거. 출력이 스트림 처리자를 떠나면(DB 기록, 메시지 전송, 이메일 발송) 이미 되돌릴 수 없어서 재시작 시 부수 효과가 중복 발생 가능 → 이것만으론 문제 방지 불충분
    - Flink는 변형된 접근법: 주기적으로 상태의 롤링 체크포인트를 지속성 있는 저장소에 저장, 장애 시 최근 체크포인트에서 재시작
2. **원자적 커밋:** 상태 변경과 메시지 확인을 하나의 트랜잭션으로 묶음. 오버헤드 크지만 정확성 보장 강함(VoltDB, Google Cloud Dataflow 등)
    1. 처리 성공 시에만 모든 출력과 부수 효과(다운스트림 전송, DB 쓰기, 상태 변화, 입력 메시지 확인 등)가 원자적으로 발생하게 함. XA와 달리 이종 기술 간 트랜잭션은 지원하지 않되 프레임워크 내부에서 상태 변화와 메시지를 관리해 트랜잭션 유지. 트랜잭션 오버헤드는 단일 트랜잭션 내에서 여러 입력 메시지를 처리해 상쇄 가능. Google Cloud Dataflow, VoltDB 등이 사용
3. **멱등성(idempotence) 활용:** 가장 실무적인 해법. 연산 자체를 여러 번 수행해도 결과가 같게 설계
    - 예: 특정 키에 고정 값 설정(멱등), 카운터 증가는 멱등 아님
    - 연산 자체가 멱등적이지 않아도 여분 메타데이터(카프카 오프셋 등)로 멱등하게 만들 수 있음: DB 기록 시 마지막 처리 오프셋을 함께 저장해서 이미 갱신됐는지 확인
    - Storm의 Trident도 유사 아이디어 기반. 전제조건: 실패한 태스크 재시작 시 반드시 같은 순서로 같은 메시지 재생해야 함(로그 기반 브로커가 이를 지원), 처리는 결정적이어야 하며 노드 펜싱 필요(죽었다고 생각한 노드가 실제로 살아있어 간섭하는 것 방지)
    - VoltDB는 각 입력 메시지를 여러 노드에서 중복 처리해 상태를 복제하는 방식 사용
    - **실무 적용**: 결제/정산처럼 중복 실행이 치명적인 로직은 idempotency key를 요청/이벤트에 포함시키고 DB 유니크 제약이나 처리 이력 테이블로 체크. Lambda + SQS 조합에서 SQS는 최소 한 번(at-least-once) 전달만 보장하므로 핸들러 자체를 멱등하게 짜는 게 사실상 필수

### **11.2 실패 후 상태 재구축**

- 윈도우 집계나 조인용 상태는 실패 후에도 복구돼야 함
- 상당히 작은 윈도우라면 상태 복제 없이 입력 이벤트를 재생해도 충분히 빠름
- 원격 저장소에 상태를 유지·복제(느림) 또는 로컬 상태를 주기적으로 스냅숏(Flink는 HDFS 같은 지속성 저장소에 기록, Samza/Kafka Streams는 로그 컴팩션 사용한 전용 카프카 토픽에 상태 변화 전송해 복제, CDC와 유사한 방식)
- 모든 트레이드오프는 인프라 성능 특성에 좌우됨(디스크 vs 네트워크 지연/대역폭)

---

## 12. 시간 다루기 (이벤트 시간 vs 처리 시간)

- 처리 시간 기준으로 윈도우를 만들면 처리 지연/재시작 시 통계가 왜곡됨 (그림 11-7)
- 이벤트 시간 기준이 정확하지만, "이 윈도우에 더 이상 이벤트 안 온다"를 확신할 수 없는 문제(낙오자 이벤트) 발생
- 실무 대응: 낙오자 이벤트 무시 또는 수정값 발행(이전 출력 취소 포함) 중 선택. 워터마크 개념(타임아웃 기반 윈도우 종료 판단)도 여기서 나옴
- 윈도우 유형: 텀블링(고정, 겹침 없음) / 호핑(고정, 겹침 있음) / 슬라이딩(연속) / 세션(사용자 비활성 기준)

---

## 13. CEP와 스트림 분석

- **CEP(복잡한 이벤트 처리)**: 이벤트 패턴 자체를 찾음 (예: 이상거래 탐지 - "5분 내 3번 이상 실패한 로그인 후 성공"). Esper 등이 대표적
- **스트림 분석**: 집계/통계 위주 (이동평균, 빈도 측정). 확률적 알고리즘(블룸 필터, HyperLogLog)도 여기 씀
- 실무 연관: 핀테크 사기 탐지 시스템이라면 CEP 개념이 바로 적용됨. 규칙 기반 패턴 매칭이 필요하면 이 개념을 참고

## 14. 정리 한 줄씩

- **AMQP/JMS 스타일 메시지 브로커**
    - 브로커가 개별 메시지를 소비자에게 할당, 소비자는 처리 성공 시 개별 확인 응답. 확인 응답 받은 메시지는 삭제됨. RPC와 같은 비동기 양식에 적절(순서가 안 중요하고 처리 후 과거로 돌아갈 필요 없는 경우)
- **로그 기반 메시지 브로커**
    - 파티션 내 모든 메시지를 동일 소비자 노드에 할당하고 항상 같은 순서로 전달. 병렬화는 파티션 나누는 방식 사용. 소비자는 오프셋을 체크포인트로 남김. 브로커가 디스크에 메시지 유지하므로 필요시 과거 메시지 재읽기 가능
- **로그 기반 접근법과 DB의 유사성**
    - 데이터베이스(복제 로그)와 로그 구조화 저장 엔진과 유사. 스트림 처리 시스템이 입력을 소비해 파생 상태나 파생 출력 스트림을 생성할 때 특히 적합

---

## 15. 실무 체크리스트 요약

- 순서 보장 필요 → 로그 기반 브로커(Kafka류), 아니면 전통 메시지 브로커(SQS류)로 충분
- 여러 시스템 동기화 문제 → 이중 기록 대신 CDC
- 실패 후 재처리 시 부수 효과 중복 방지 → 멱등성 설계
- 시간 기준은 처리 시간 아닌 이벤트 시간으로, 낙오자 이벤트 처리 전략 미리 정하기
- 컨슈머 랙 모니터링, 파티션 키 설계, idempotency key 적용은 바로 쓸 수 있는 체크리스트
- 이벤트 소싱 도입 시 삭제 요구사항(규제 대응)을 설계 초기에 반드시 정의
- CDC 도구 선택 시 초기 스냅숏 지원 여부 확인
- 스트림 강화(join) 시 원격 DB 직접 조회보다 로컬 캐시(CDC로 갱신) 방식 우선 고려
