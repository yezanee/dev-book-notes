## 19.1 프로세스 vs 스레드

- **프로세스**: 더 큰 실행 단위로, OS로부터 독립된 메모리 공간을 받습니다. 프로세스끼리는 메모리를 공유하지 못하므로 명시적으로 데이터를 주고받아야 합니다.
- **스레드**: 프로세스 안의 더 작은 실행 단위로, 같은 프로세스 내 스레드끼리 메모리(큐, 리스트, 객체 등)를 공유합니다.
- 일반적으로 메모리를 공유하는 멀티스레드가 멀티프로세스보다 프로그래밍하기 쉽지만, 그 편리함에는 대가가 있습니다.
- **GIL(전역 인터프리터 잠금)**: 여러 스레드가 같은 코드 행을 동시에 실행하지 못하게 막아 공유 메모리 손상을 방지합니다. 대신 병목의 원인이 될 수 있습니다.

## 19.2 멀티스레드 크롤링

**기본 사용법**

- `threading.Thread(target=함수, args=(...))`로 스레드를 만들고 `start()`, `join()`으로 실행과 대기를 관리합니다.
- 피즈버즈 예제: Fizz(3초), Buzz(5초), Counter(1초) 세 스레드가 각자 주기로 출력합니다.
- 위키백과 크롤링 예제: 두 스레드가 각각 Kevin_Bacon, Monty_Python에서 출발해 무작위 링크를 따라갑니다. `time.sleep(5)`로 서버 부담을 줄였는데도 싱글스레드보다 약 두 배 빠릅니다.

**방문 기록 공유와 경쟁 상태(race condition)**

- 전역 `visited` 리스트로 중복 방문을 줄일 수 있지만, 두 스레드가 동시에 같은 링크에 접근하면 둘 다 스크랩하는 경쟁 상태가 생길 수 있습니다.
- 크롤러에서 이 정도 중복은 치명적이지 않지만, 경쟁 상태가 얼마나 자주, 얼마나 심각하게 발생할지 따져보는 습관이 중요하다고 강조합니다.

### 19.2.1 경쟁 상태와 큐

- 리스트는 스레드 간 통신용으로 설계된 자료구조가 아닙니다.
    - `pop(0)`처럼 앞에서 꺼내는 연산은 리스트 전체를 다시 써야 해서 느립니다.
    - `myList[len(myList)-1]` 같은 코드는 길이 계산과 접근 사이에 다른 스레드가 리스트를 바꾸면 엉뚱한 값을 읽거나 예외가 납니다.
    - 전역 변수로 메시지를 주고받는 것도 읽기와 쓰기 사이에 다른 스레드가 값을 덮어쓸 수 있습니다.
- 해결책은 **큐(Queue)**입니다. FIFO 또는 LIFO로 동작하고, `put()`으로 어느 스레드든 넣고 `get()`으로 꺼냅니다. 꺼낸 데이터는 그 스레드에만 존재하므로 작업 위임이나 알림 전달에 적합합니다.
- 활용 예: 스레드 100개가 각각 DB 연결을 들고 있으면 대부분 시간 동안 놀고 있는 연결이 됩니다. 대신 크롤링 스레드는 결과를 큐에 넣고, **저장 전담 스레드(storage)** 하나가 큐에서 꺼내 MySQL에 저장하게 하면 연결 관리가 훨씬 쉬워집니다.
- 이 버전에서는 `visited`를 리스트에서 `set`으로 바꿨습니다. 완벽한 스레드 안전성은 아니지만 중복 작업이 최종 결과에 영향을 주지 않도록 설계했습니다.

### 19.2.2 threading 모듈

- 저수준 `_thread` 모듈 위에 만든 고수준 인터페이스로, 편의 기능이 많습니다.
    - `enumerate()`: 활성 스레드 목록
    - `activeCount()`: 전체 스레드 수
    - `currentThread()`: 현재 스레드
- **로컬 스레드 데이터** `threading.local()`: 각 스레드만 쓰는 데이터를 만들어 공유 객체로 인한 경쟁 상태를 피합니다. 스레드별 방문 목록 관리에 유용합니다.
- **스레드 감시**: `isAlive()`로 스레드가 죽었는지 확인하고, 크롤러가 충돌하면 다시 시작시킬 수 있습니다.
- **Thread 상속**: `threading.Thread`를 상속한 `Crawler` 클래스에 `isDone()` 같은 상태 메서드를 추가하면, 완료 여부를 확인하고 예외로 죽은 경우 재시작하는 등 더 견고한 크롤러와 동시 모니터링이 가능합니다. `isDone`은 방문 페이지 수, 현재 위치 같은 진행 상황 메서드로 확장할 수 있습니다.

## 19.3 멀티프로세스

- `multiprocessing.Process`로 프로세스를 만들고 `start()`, `join()`을 씁니다. Windows 호환 등을 위해 `if __name__ == '__main__':` 안에서 실행합니다.
- 피즈버즈를 멀티프로세스로 실행하면 활성 상태 보기에 파이썬 프로세스가 따로따로 보입니다(메인 1개 + 서브 3개 + 노트북 등).
- `os.getpid()`는 각 프로세스의 PID, `os.getppid()`는 공통 부모 PID를 반환합니다.
- `join()`이 없어도 메인 프로세스는 서브 프로세스가 끝날 때까지 기다리지만, 서브 프로세스 완료 후 실행할 코드가 있다면 `join()`이 필요합니다. 없으면 Program complete가 먼저 찍힙니다.
- Ctrl+C로 메인을 종료하면 서브 프로세스도 같이 종료됩니다.

### 19.3.1 멀티프로세스 크롤링

- 위키백과 크롤러를 프로세스로 바꾸면 `thread_name` 대신 `os.getpid()`로 실행 주체를 구분할 수 있습니다.
- 이론상 멀티스레드보다 약간 빠른 이유
    - GIL에 묶이지 않아 여러 프로세스가 같은 코드를 동시에 실행할 수 있습니다.
    - 멀티코어를 활용하므로 CPU 의존적인 작업에서 이득이 있습니다.
- 큰 단점: 각 프로세스가 **자기만의 visited 리스트**를 가지므로 다른 프로세스가 방문한 페이지를 다시 방문하는 것을 막을 수 없습니다.

### 19.3.2 프로세스 간 통신

- `visited`를 출력해 보면 프로세스마다 리스트가 따로 쌓이는 것을 확인할 수 있습니다.
- 해결책은 `multiprocessing`의 **Queue와 Pipe**입니다. 다만 큐는 일시적 데이터 전달용이라 방문 목록 같은 정적 참조 데이터를 담기엔 부적합합니다.
- 그래서 **위임자(delegator) 패턴**을 씁니다.
    - `taskQueue`: 스크랩할 경로(작업)를 담는 큐
    - `urlsQueue`: 각 스크레이퍼가 찾아낸 링크 목록을 담는 큐
    - 위임자 프로세스(`task_delegator`)만 `visited`를 관리하면서, `urlsQueue`에서 새 링크를 받아 방문하지 않은 것만 `taskQueue`에 넣습니다.
    - 스크레이퍼 프로세스들은 `taskQueue`에서 작업을 꺼내 처리하고 결과 링크를 `urlsQueue`로 돌려보냅니다.
- 구조적 차이: 각 프로세스가 자기 출발점에서 무작위로 헤매는 대신, 공동 작업으로 사이트 전체를 커버합니다. 프로세스는 자신이 찾은 링크가 아니라 큐에 있는 아무 작업이나 수행합니다.

## 19.4 멀티프로세스 크롤링의 다른 접근법

- 지금까지는 메인 프로그램이 서브 스레드/프로세스를 감독한다고 가정했습니다.
- 감독이나 통신이 필요 없게 설계한다면, 그냥 `python my_crawler.py website1`, `python my_crawler.py website2`처럼 스크립트를 따로 여러 번 실행하는 것도 훌륭한 멀티프로세스 크롤링입니다. 관리용 메인 프로세스도 없으니 CPU 부하도 적습니다.
- 단점과 보완책
    - 같은 사이트를 두 크롤러가 돌리면 중복을 막을 장치가 필요합니다. URL 규칙으로 분할하거나(블로그 담당, 상품 담당), Redis 같은 중간 DB로 방문 여부를 확인해 조율할 수 있습니다. 이때 DB가 사실상 프로세스 간 통신 수단이 되며, 경쟁 상태와 원격 DB 지연에 주의해야 합니다.
    - 확장성이 부족합니다. 프로세스 수를 동적으로 조절하려면 사람이 직접 하거나 배시 스크립트, cron 같은 별도 관리 도구가 필요합니다.
- 그래도 저자는 이 방식으로 좋은 결과를 얻었고, 소규모 프로젝트나 여러 웹사이트 대상일 때 효과적이라고 말합니다.
