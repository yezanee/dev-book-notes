## 7.1 객체 계획 및 정의

- **흔한 함정**: 첫 번째 사이트에 보이는 필드를 그대로 모델로 삼는 것입니다. 사이트를 추가할 때마다 필드가 늘어나면 파이썬 객체와 DB 구조를 계속 고쳐야 하고, 데이터셋이 지저분해집니다.
- **출발점을 바꾸기**: 이 사이트에 어떤 데이터가 있는지가 아니라, 내게 필요한 데이터가 무엇인지에서 출발해야 합니다.
- **필드 채택 체크리스트**
    - 프로젝트 목표에 꼭 필요한가, 있으면 좋은 정도인가
    - 나중에 필요해지면 다시 수집하기 얼마나 어려운가
    - 이미 수집한 데이터와 중복되지 않는가
    - 이 객체에 저장하는 게 논리적으로 맞는가 (예: 사이트마다 다른 설명을 제품 객체에 넣으면 안 됨)
    - 항상 등장하는가, 드물게 등장하는가 / 크기는 얼마나 큰가 / 얼마나 자주 바뀌는가
- **가격 비교 예시에서 나온 설계**
    - 제품: 이름, 제조사, 제품 ID, 속성(별도 리스트나 딕셔너리)
    - 속성: 속성 이름, 속성값 (희소하고 자주 바뀌는 속성은 key-value 구조로 분리해 스키마 변경 없이 확장. DB에서는 JSON 컬럼 또는 별도 테이블, 9장에서 다룸)
    - 가격: 제품 ID, 상점 ID, 가격, 날짜와 시간
    - 사이즈별로 가격이 달라지면 제품 세부 항목(제품 ID + 세부 항목 타입)을 따로 두고, 가격은 제품 세부 ID를 참조
- 뉴스 기사도 같은 방식으로 제목, 작성자, 날짜, 내용을 기본으로 두고, SNS 공유 수 같은 부가 정보는 체크리스트로 판단합니다.

## 7.2 다양한 웹사이트 레이아웃 다루기

- 사람이 고른 소수의 사이트를 수집하는 경우가 대부분이라, 머신러닝으로 제목/본문을 판별할 필요 없이 사람이 직접 선택자를 지정하면 됩니다.
- **1단계, 사이트별 함수**: `scrapeCNN`, `scrapeBrookings`처럼 사이트마다 함수를 만들어 `Content(url, title, body)`를 반환합니다. 해 보면 모든 함수가 제목 선택, 본문 선택, Content 반환이라는 같은 일을 하고 **달라지는 건 CSS 선택자뿐**이라는 걸 알게 됩니다.
- **2단계, 구조를 데이터로 분리**
    - `Content`: 개별 페이지에서 수집한 결과 (url, title, body)
    - `Website`: 사이트 전체에 적용되는 **수집 방법** (name, url, titleTag, bodyTag). 제목 텍스트가 아니라 제목을 찾을 선택자를 저장한다는 점이 포인트입니다.
    - `Crawler`: 상태 없이 정적 메서드만 가짐
        - `getPage(url)`: 요청 실패 시 None 반환
        - `safeGet(bs, selector)`: `bs.select()`로 찾고, 없으면 빈 문자열 반환 (우아한 실패)
        - `getContent(website, path)`: 위 둘을 조합해 Content 생성
- **장점**: 사이트 정의가 문자열 리스트라서 DB나 CSV에서 불러올 수 있고, HTML만 아는 비개발자도 사이트를 추가할 수 있습니다. 사이트가 수천 개로 늘어도 코드는 그대로입니다.
- **단점**: 각 사이트에 필드가 반드시 존재해야 하고, 고유하고 안정적인 CSS 선택자가 있어야 합니다. 사이트별 맞춤 파싱의 유연성은 포기합니다.

## 7.3 크롤러 구성

세 가지 기본 크롤러 구조를 제시합니다.

### 7.3.1 검색을 통한 크롤링

- 대부분 사이트는 `example.com?search=키워드` 형태로 검색되고, 결과는 일정한 태그로 감싼 링크 목록으로 나옵니다.
- `Website`에 추가되는 속성
    - `searchUrl`: 검색어를 붙일 URL
    - `resultListing`: 결과 하나를 감싼 박스 선택자
    - `resultUrl`: 박스 안에서 링크를 뽑을 선택자
    - `absoluteUrl`: 결과 링크가 절대 URL인지 여부 (False면 사이트 URL을 앞에 붙임)
- `Crawler`가 이제 인스턴스를 가지며 `site`와 `found` 딕셔너리(중복 방지)를 상태로 보관하고, `search(topic)`이 결과 링크를 돌며 `getContent`를 호출합니다. `Content`에는 `topic`이 추가됩니다.
- **루프 순서**: 바깥 루프가 검색어, 안쪽 루프가 사이트입니다. 사이트를 기준으로 모든 검색어를 몰아서 요청하면 한 서버에 요청이 몰리므로, 이렇게 해야 부하가 사이트들에 고르게 분산됩니다. 총 요청 수는 같아도 시간적으로 분산되는 편이 낫습니다.

### 7.3.2 링크를 통한 크롤링

- 검색 페이지 대신 홈페이지에서 시작해 내부 링크를 따라가며, `targetPattern`(정규식)에 맞는 URL만 수집합니다. 구조가 엉성하거나 페이지가 흩어진 사이트에도 쓸 수 있습니다.
- `Website`: name, url, targetPattern, absoluteUrl, titleTag, bodyTag
- `Crawler(site)`가 `visited`로 방문 기록을 관리하고 `crawl()`이 `findAll('a', href=re.compile(pattern))`으로 대상 링크를 찾습니다.
- **설계 포인트**: 크롤러가 사이트 정보를 가지면 크롤러 하나가 여러 사이트를 돌 수 없고 사이트마다 인스턴스를 만들어야 합니다. 어느 쪽이든 동작하니 프로젝트에 맞게 선택하면 됩니다.
- **한계**: 홈페이지에서 한 단계만 따라가고 끝납니다. 방문한 페이지마다 다시 링크를 찾거나, 패턴에 맞지 않는 URL도 따라가며 대상을 찾도록 확장할 수 있습니다.

### 7.3.3 여러 페이지 유형 크롤링

- 내부 링크를 다 따라가면 무엇이 걸릴지 모르므로 페이지 유형을 판별해야 합니다.
    - URL 패턴 (예: `/blog/`)
    - 특정 필드의 존재 여부 (날짜는 있고 작성자가 없으면 보도자료, 가격은 있고 본문이 없으면 제품 등)
    - 식별용 태그의 존재 여부 (예: `div#relatedproducts`가 있으면 제품 페이지)
- **처리 방법 두 가지**
    - 페이지들이 비슷하면 `Website`에 `pageType` 속성 하나만 추가 (DB에서는 같은 테이블에 pageType 컬럼)
    - 필드가 서로 다르면 `Website`를 상속한 하위 클래스로 분리: `Product`는 productNumber, price 추가, `Article`은 body, date 추가

## 7.4 웹 크롤러 모델에 대한 생각

- 인터넷의 정보는 소화전에서 쏟아지는 물과 같아서, 무엇이 필요하고 어떻게 얻을지 첫 단계에서 답해야 합니다.
- 여러 소스에서 비슷한 데이터를 모을 땐 항상 일반화를 시도하세요. 필드가 통일된 데이터는 원본 형식에 의존하는 데이터보다 훨씬 다루기 쉽습니다.
- 앞으로 소스가 더 늘어난다고 가정하고, 새 소스 추가 비용을 최소화하도록 설계합니다.
- 유형, 크기, 주제처럼 여러 소스에 걸친 속성을 어떻게 저장하고 검색할지도 고민해야 합니다.
- 스크레이핑에 필요한 아키텍처 지식은 범위가 좁아서, 비밀 지식보다는 한발 물러서 프로젝트 자체를 생각하는 시간이 더 중요합니다.
