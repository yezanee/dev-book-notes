## 15.1 API에 대한 간단한 소개

- **API의 정의**: 한 소프트웨어가 다른 소프트웨어와 통신하기 위해 표준화한 문법입니다. 원래는 더 넓은 개념이라 인터넷이나 웹 기술과 꼭 연결될 필요는 없지만, 이 장에서는 웹 API에 한정해서 씁니다.
- **공개 API 예시**: 미국 국립기상청의 날씨 API, 구글 개발자 콘솔의 번역/분석/지오로케이션 API 등이 소개됩니다.
- **엔드포인트와 매개변수**: 엔드포인트는 요청을 보내는 URL입니다. 매개변수는 경로의 일부(`/the-api-route/pathparam`)로 넣을 수도, GET 쿼리(`?param1=pathparam`)로 넣을 수도 있습니다.
- **응답 형식**: 보통 JSON이나 XML이며, 매개변수로 형식을 고를 수 있는 API가 많습니다. ip-api.com은 경로만 `/json/`, `/xml/`, `/csv/`로 바꾸면 같은 데이터를 다른 형식으로 돌려줍니다.

### 15.1.1 HTTP 메서드와 API

- **GET**: 정보를 읽기만 하며 서버 DB를 변경하지 않습니다. 브라우저 주소창으로 접속할 때 쓰는 메서드입니다.
- **POST**: 폼 전송, 로그인처럼 서버에 정보를 보내 저장해달라고 할 때 씁니다. 새 사용자 등록이 예시입니다.
- **PUT**: 기존 객체나 정보를 업데이트할 때 씁니다. 각주에서는 현실적으로 PUT 대신 POST로 업데이트하는 API도 많다고 언급합니다.
- **DELETE**: 객체를 지울 때 씁니다(`/user/23`에 DELETE 요청). 공개 API에서는 드뭅니다.
- HEAD, OPTIONS, CONNECT도 있지만 거의 쓰이지 않고, 실제로는 GET만 쓰거나 GET과 POST만 쓰는 API가 많습니다.
- POST, PUT, DELETE는 URL 외에 요청 본문에 데이터를 실어 보낼 수 있고, 이 본문도 보통 JSON이나 XML입니다. 블로그 댓글 예시처럼 게시글 ID는 URL 매개변수로, 댓글 내용은 본문으로 보낼 수 있으며, 어디에 무엇을 넣을지는 API 문법이 정합니다.

### 15.1.2 API 응답에 대해

- **JSON이 우세한 이유 1, 크기**: 같은 사용자 데이터가 XML로 98자, JSON으로 73자입니다. 속성 방식 XML(`<user firstname=... />`)로 줄일 수는 있지만 깊은 중첩이 불가능해 잘못된 설계로 봅니다.
- **JSON이 우세한 이유 2, 기술 변화**: 예전엔 PHP, .NET 같은 서버 사이드가 API를 주로 다뤘지만, 지금은 앵귤러, 백본 같은 자바스크립트 프레임워크가 API를 직접 호출하고 이들은 JSON을 선호합니다.
- **다양한 응답 형태**: CSV, 이미지, 엑셀, PDF를 돌려주는 API도 있고, 응답 본문 없이 HTTP 200만 주거나 `{"success": true}`처럼 아주 간단히 응답하는 곳도 있습니다.
- **에러 응답**: `{"error": {"message": ...}}` 형태가 일반적이지만, 설계가 허술하면 스택 트레이스나 평문이 나올 수도 있습니다. 요청 전에 원하는 형식으로 응답이 오는지 먼저 확인하라고 권합니다.

## 15.2 JSON 파싱

- ip-api.com 응답을 `urlopen`으로 받아 `json.loads`로 디코딩하고 `countryCode`를 꺼내는 `getCountry` 함수를 만듭니다. 결과는 `US`입니다.
- `json`은 표준 라이브러리라 따로 설치할 필요가 없습니다.
- 파이썬은 JSON을 특별한 노드 객체로 바꾸지 않고 기본 자료형으로 변환합니다. JSON 객체는 딕셔너리, 배열은 리스트, 문자열은 문자열이 됩니다.

```python
jsonObj = json.loads(jsonString)
jsonObj.get('arrayOfNums')                  # 딕셔너리 리스트
jsonObj.get('arrayOfNums')[1]               # {'number': 1}
jsonObj.get('arrayOfFruits')[2].get('fruit')  # 'pear'
```

## 15.3 문서화되지 않은 API

- 공개 문서가 있는 API보다 문서 없이 존재하는 API가 훨씬 많습니다. 이유는 자바스크립트 때문입니다.
- **전통적인 방식**: 서버가 GET을 받고, DB에서 데이터를 가져와 HTML 템플릿에 넣고, 완성된 HTML을 보냈습니다.
- **현재 방식**: HTML 조립이 브라우저로 넘어가면서, 서버는 빈 템플릿을 주고 데이터는 별도 Ajax 요청으로 채웁니다. 그래서 스크레이퍼는 콘텐츠 없는 껍데기 HTML만 받게 됐습니다.
- **셀레니움의 비용**: 사용자 통계, 광고, 이미지, CSS, 폰트 같은 곁가지까지 전부 불러와 필요한 것보다 수백 배 많은 요청을 보냅니다.
- **희망**: 서버가 HTML 조립을 안 하게 되면서 사실상 DB 인터페이스 역할만 하게 됐고, 이 인터페이스가 바로 숨은 API입니다. 개발자는 아무도 모를 거라 가정하고 문서 없이 만들었지만 API는 분명히 존재합니다.
- **타깃 사례**: 검색 결과 페이지를 `urllib`이나 `requests`로 받으면 아무것도 없지만, `redsky.target.com/.../plp_search_v2` API가 결과를 JSON으로 줍니다. 셀레니움은 약 260번 요청에 메가바이트 단위 데이터를 받지만, API는 한 번 요청에 10kB 남짓한 정리된 데이터만 받습니다. 단 이 API는 매 요청에 API 키가 필요하고 키는 일정 시간 후 만료됩니다.

### 15.3.1 문서화되지 않은 API 찾기

- 크롬 개발자 도구의 네트워크 탭을 엽니다. 도구가 닫혀 있는 동안에는 추적하지 않으므로, 페이지 로드 전에 열거나 열고 나서 새로고침해야 합니다.
- API 호출을 구별하는 단서는 다음과 같습니다.
    - 보통 JSON이나 XML을 포함하므로 검색/필터 필드로 걸러낼 수 있습니다.
    - GET 요청이면 URL에 매개변수가 들어 있으니 검색어, 페이지 ID 같은 식별 정보로 필터링합니다.
    - 보통 XHR 타입입니다.
- 큰 사이트는 처음엔 서울에서 김 서방 찾기 같지만 연습하면 금세 익숙해집니다.

### 15.3.2 문서화되지 않은 API 문서화하기

스크레이퍼가 특정 호출에 많이 의존할수록 직접 문서화해 두는 것이 중요합니다. 여러 페이지에서 호출이 어떻게 바뀌는지 관찰하며 다음 항목을 기록합니다.

- 사용된 HTTP 메서드
- 입력: 경로 매개변수, 헤더(쿠키 포함), 본문 콘텐츠(PUT, POST에 한해)
- 출력: 응답 헤더(쿠키 세트 포함), 응답 본문 타입, 응답 본문 필드

## 15.4 API와 다른 데이터 소스의 결합

- 저자는 API 하나를 예쁘게 재포장하는 것보다, 둘 이상의 데이터 소스를 독창적으로 조합하는 것이 훨씬 흥미롭다고 봅니다.
- **예제 주제**: 위키백과 익명 편집자는 사용자 이름 대신 IP 주소가 개정 히스토리에 기록됩니다. 이 IP를 수집해 국가로 변환하면 어느 지역이 위키백과에 많이 기여하는지 알 수 있습니다. 저자는 이 데이터를 구글 지오차트로 시각화한 적이 있습니다.
- **getLinks**: 6장 코드를 재사용해 본문의 `/wiki/` 링크 목록을 가져옵니다.
- **getHistoryIPs**: `/wiki/`를 떼어 `index.php?title=...&action=history` URL을 만들고, 클래스가 `mw-anonuserlink`인 링크(익명 사용자 IP)만 찾아 집합으로 반환합니다.
- **getCountry 수정판**: ipwho.is로 바꾸고, 잘못된 IP로 `HTTPError`가 나면 `None`을 반환하도록 했습니다. 키 이름도 `country_code`입니다.
- **흐름**: 시작 페이지(파이썬 프로그래밍 언어 항목)의 링크마다 히스토리 IP를 뽑아 국가를 출력하고, 무작위로 새 시작 페이지를 골라 링크 없는 페이지를 만날 때까지 반복합니다. 출력에는 IPv4, IPv6가 섞여 IN, PK, US, MX, CA 등이 나옵니다.

## 15.5 마치며

- API는 웹 데이터에 더 빠르고 깔끔하게 접근하는 길이며, 더 깊이 알고 싶다면 『RESTful Web API』와 마이크 애먼슨의 Designing APIs for the Web 영상을 추천합니다.
- 저자는 동적 웹사이트의 확산을 환영합니다. 사람이 보는 HTML보다 엄격한 포맷의 JSON에 의존하게 되면서 누구나 더 정리된 데이터를 얻을 가능성이 열렸기 때문입니다.
- 핵심 메시지: 눈앞의 페이지가 아니라 그 뒤를 보고 소스에서 직접 데이터를 가져오는 것이 해답일 때가 많습니다.
