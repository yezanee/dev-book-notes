## 8.1 설치와 프로젝트 초기화

- 설치는 `pip install scrapy`로 가능하지만 의존성이나 버전 충돌이 잦아서 가상 환경 사용을 강력히 권장합니다. 저자는 아나콘다(`conda install -c conda-forge scrapy`)를 선호합니다.
- `scrapy startproject wikiSpider`로 프로젝트를 만들면 `scrapy.cfg`, `spiders/`, `items.py`, `middlewares.py`, `pipelines.py`, `settings.py` 등 기본 뼈대가 생성됩니다.
- 스크레이피에서는 크롤링 단위를 스파이더라고 부릅니다. 하나의 프로젝트 안에 여러 스파이더(예: 블로그용, 보도자료용)를 둘 수 있고, 스파이더 이름은 프로젝트 내에서 고유해야 합니다.

## 8.2 간단한 스크레이퍼

- `Spider`를 상속한 `ArticleSpider`를 만들고 `name`을 지정합니다.
- 핵심은 두 함수입니다.
    - `start_requests`: 크롤링할 URL로 `Request` 객체들을 만들어 반환하는 진입점입니다.
    - `parse`: `callback=self.parse`로 연결되는 사용자 정의 콜백으로, 응답에서 제목 등을 추출합니다.
- `scrapy runspider spiders/article.py`로 실행하며, 기본 출력에 디버그 로그가 매우 많이 섞여 나옵니다.
- 이 스파이더는 지정된 URL 세 개만 방문하고 종료합니다. 스스로 새 페이지를 찾지는 못합니다.

## 8.3 규칙에 의한 스파이더링

- 진짜 크롤러를 만들려면 `CrawlSpider`를 사용합니다. `start_requests` 대신 `start_urls`(시작 위치)와 `allowed_domains`(허용 도메인)를 지정하고, `rules`로 어떤 링크를 따라갈지 정합니다.
- 본문 텍스트는 XPath(`//div[@id="mw-content-text"]//text()`)로 추출합니다. 하위 태그 안의 텍스트까지 모두 포함하기 때문입니다.
- `allow=r'.*'`로 모든 링크를 허용하면 사실상 무한 루프가 되므로 서버 부하를 고려해 오래 돌리지 말라는 경고가 있습니다. 허용 도메인 밖의 링크는 offsite로 걸러집니다.
- `Rule`의 매개변수 4가지
    - `link_extractor`: 필수인 `LinkExtractor` 객체
    - `callback`: 페이지를 파싱할 함수
    - `cb_kwargs`: 콜백에 넘길 인자 딕셔너리로, 같은 파서를 다른 용도로 재사용할 때 편리
    - `follow`: 해당 페이지의 링크를 계속 따라갈지 여부. 콜백이 없으면 기본값 True, 있으면 False
- 규칙은 리스트 순서대로 검사되며 처음 일치하는 규칙 하나만 적용되고, 어떤 규칙에도 맞지 않는 링크는 무시됩니다.
- `LinkExtractor`의 주요 매개변수는 `allow`(정규식에 맞는 링크 허용)와 `deny`(정규식에 맞는 링크 거부)입니다.
- 응용 예제: 첫 번째 규칙은 문서 페이지 패턴(`/wiki/`로 시작하고 콜론이 없는 URL)에 `is_article=True`를, 두 번째 규칙은 나머지 전부에 `is_article=False`를 넘겨 하나의 `parse_items`에서 분기 처리합니다. 실무에서는 그냥 문서 패턴만 허용하는 편이 간단하지만, URL에 따라 파싱 방식을 달리해야 하는 경우에 쓸 수 있는 방법입니다.

## 8.4 항목(Item) 만들기

- 수집 데이터를 구조화하려면 `items.py`에 `scrapy.Item`을 상속한 `Article` 클래스를 만들고 `url`, `title`, `text`, `lastUpdated` 필드를 `scrapy.Field()`로 선언합니다.
- 스파이더의 `parse_items`는 `Article()` 객체를 채워서 반환합니다.
- 수집하는 페이지 유형이 여러 개라면 유형마다 Item 클래스를 만듭니다. 규모가 커지면 파일을 분리해도 됩니다.

## 8.5 항목 출력하기

- `scrapy runspider articleItems.py -o articles.csv` 처럼 `o` 옵션으로 CSV, JSON, XML 파일에 바로 저장할 수 있습니다. 최신 버전은 확장자로 형식을 판단하므로 `t`가 필요 없습니다.
- 본문 텍스트는 문자열 리스트로 수집되는데, 형식별 처리 방식이 다릅니다.
    - CSV: 리스트를 하나의 문자열로 합치고 쉼표를 이스케이프해 셀 하나에 넣음
    - XML: 각 요소를 하위 `value` 태그로 감쌈
    - JSON: 리스트 그대로 유지

## 8.6 파이프라인

- 스크레이피는 단일 스레드지만 요청을 비동기로 처리합니다. 파이프라인을 쓰면 응답을 기다리는 동안 이전 데이터를 처리할 수 있어 처리 비용이 큰 경우 속도 이득이 있습니다.
- 다만 빠른 크롤링은 곧 상대 서버에 부하를 준다는 뜻이므로 윤리적 고려가 필요하다고 강조합니다(19장에서 다룸).
- 설정 방법
    1. `settings.py`의 `ITEM_PIPELINES` 주석을 해제합니다. 숫자는 우선순위로 보통 0~1000 범위를 쓰며 작을수록 먼저 실행됩니다.
    2. 스파이더는 데이터 추출만 하고 Item을 반환하도록 정리합니다(응답 객체 자체를 반환하는 것은 허용되지 않음).
    3. `pipelines.py`의 `process_item`에서 후처리를 합니다. 예제에서는 `lastUpdated`를 `datetime`으로 파싱해 ISO 형식 문자열로 바꾸고, 파편화된 `text` 리스트에서 공백 줄을 제거해 하나의 문자열로 합칩니다.
- `process_item`은 모든 파이프라인 클래스의 필수 메서드입니다.
- 모든 Item은 유형과 관계없이 등록된 파이프라인을 순서대로 모두 거치므로, 여러 Item 유형이 있다면 `isinstance(item, Article)` 같은 검사를 넣는 것이 좋습니다.
- 결론적으로 데이터를 스파이더에서 처리할지 파이프라인에서 처리할지 프로젝트 규모에 맞게 신중히 정해야 합니다.

## 8.7 스크레이피 로깅

- `settings.py`에 `LOG_LEVEL = 'ERROR'`처럼 지정해 출력량을 조절합니다.
- 로그 수준은 심각도 순으로 CRITICAL, ERROR, WARNING, INFO, DEBUG입니다. 설정한 수준 이상만 표시됩니다.
- `scrapy crawl articles -s LOG_FILE=wiki.log`로 로그를 파일에 저장하면 터미널에는 직접 넣은 `print` 출력만 남습니다.

## 8.8 마치며

스크레이피는 URL 수집, 규칙 비교, 중복 제거, 상대 URL 정규화, 깊이 탐색까지 자동으로 처리하는 강력한 도구입니다. 같은 기능을 여러 방식으로 구현할 수 있게 설계되어 있으니 공식 문서와 튜토리얼을 함께 보길 권합니다.
